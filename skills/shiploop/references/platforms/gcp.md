# Google Cloud development

Return to the [guidance selector](../coding-guidance.md#select-guidance) when the runtime or boundary changes. Decide first what proves identity and what a server is allowed to trust. Firebase Authentication issues a signed ID token that a client sends to the backend, and the server must call `verifyIdToken()` itself; that check does not cover revocation unless revocation-checking is explicitly requested ([Admin Auth API](https://firebase.google.com/docs/auth/admin), [Verify ID Tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens)). Identity-Aware Proxy forwards a signed header at the load balancer, but the app must independently verify its signature and audience — IAP gates network access, not application authorization ([Signed headers](https://cloud.google.com/iap/docs/signed-headers-howto)). Firestore Security Rules evaluate `request.auth` only for direct client SDK access; server and REST/RPC calls bypass rules entirely and need access control enforced in server code via IAM ([Security Rules](https://firebase.google.com/docs/firestore/security/get-started)). A single-user, client-only product needs none of this server-side machinery.

Where state lives shapes what a plan can promise. Firestore realtime listeners give strongly ordered changelogs, and its transactions retry automatically on read/write contention, pessimistic in Standard edition and optimistic in Enterprise ([Real-time queries](https://docs.cloud.google.com/firestore/native/docs/real-time_queries_at_scale), [Transaction contention](https://firebase.google.com/docs/firestore/transaction-data-contention)). Cloud SQL gives standard relational ACID transactions, reached through the Cloud SQL Auth Proxy, which does not pool connections itself ([Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy)). Cloud Run instances are stateless with no guaranteed in-memory persistence between requests, so cross-request coordination belongs in a Firestore or Cloud SQL transaction, not instance memory ([Cloud Run FAQ](https://github.com/ahmetb/cloud-run-faq)).

Pick the lightest connectivity channel that meets a stated freshness need. Plain REST polling needs no special feature. Cloud Run also carries chunked streaming and `text/event-stream` SSE with no extra configuration, and WebSockets as a long-lived HTTP request, both bounded by the request timeout; WebSocket session affinity is best-effort and breaks on instance termination or max concurrency ([Invoke with HTTPS](https://docs.cloud.google.com/run/docs/triggering/https-request), [WebSockets](https://docs.cloud.google.com/run/docs/triggering/websockets), [Session affinity](https://docs.cloud.google.com/run/docs/configuring/session-affinity), [Request timeout](https://docs.cloud.google.com/run/docs/configuring/request-timeout)). Firestore listeners push ordered changes and Pub/Sub push subscriptions deliver via HTTPS POST at-least-once ([Listen](https://firebase.google.com/docs/firestore/query-data/listen), [Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)). After any push, read authoritative state back from Firestore or Cloud SQL rather than trusting a cached copy.

Caching sits in front of storage, not instead of it. Cloud Storage objects without `Cache-Control` metadata default to `public, max-age=3600`, fully overridable per object; Cloud CDN honors an origin's `stale-while-revalidate` and a client's `max-stale` request ([Object metadata](https://docs.cloud.google.com/storage/docs/metadata), [Serving stale content](https://docs.cloud.google.com/cdn/docs/serving-stale-content)). Firestore client SDKs cache locally for offline use and reconcile through listeners once reconnected.

Secrets live in Secret Manager as immutable, versioned values gated by `roles/secretmanager.secretAccessor`; Cloud Run resolves secret env vars at instance startup, so a plan pins a version rather than "latest" ([Access control](https://docs.cloud.google.com/secret-manager/docs/access-control), [Configure secrets](https://docs.cloud.google.com/run/docs/configuring/services/secrets)).

Background work needs its own retry and idempotency story. Cloud Tasks retries with exponential backoff per queue but has no native dead-letter queue, so a plan writes failed payloads elsewhere after the final attempt ([Configure queues](https://cloud.google.com/tasks/docs/configuring-queues), [Retry parameters](https://docs.cloud.google.com/tasks/docs/configure-retry-task)). Pub/Sub is at-least-once by default, so consumers must be idempotent; its dead-letter topic and exactly-once mode apply only to pull subscriptions, not push or export ([Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)). Cloud Run jobs carry a per-task timeout and three retries by default ([Task timeout](https://docs.cloud.google.com/run/docs/configuring/task-timeout), [Max retries](https://docs.cloud.google.com/run/docs/configuring/max-retries)).

Check current quotas rather than remembered numbers: [Cloud Run](https://docs.cloud.google.com/run/quotas), [Firestore](https://docs.cloud.google.com/firestore/quotas), [Pub/Sub](https://docs.cloud.google.com/pubsub/quotas), [Cloud Tasks](https://docs.cloud.google.com/tasks/docs/quotas), [Secret Manager](https://docs.cloud.google.com/secret-manager/quotas), [Cloud SQL](https://docs.cloud.google.com/sql/docs/quotas).

Local development does not prove production behavior. The Firestore emulator does not enforce all production limits, does not track compound indexes, and can hold contention locks up to 30 seconds; the Cloud Storage emulator lacks bucket-level config and Pub/Sub notifications ([Firestore emulator](https://docs.cloud.google.com/firestore/native/docs/emulator), [Emulator Suite](https://firebase.google.com/docs/emulator-suite/connect_storage)). None of it proves real IAM enforcement, quota or throttling behavior, Cloud Run autoscaling or cold-start timing, or VPC/Memorystore latency — those require testing against real deployed resources.

## Current facts (as of 2026-09-26)

- Cloud Run request timeout defaults to 5 minutes, maximum 60 minutes. [Request timeout](https://docs.cloud.google.com/run/docs/configuring/request-timeout)
- Cloud Run jobs default per-task timeout is 10 minutes, up to 168 hours (lower for GPU jobs), with 3 retries by default. [Task timeout](https://docs.cloud.google.com/run/docs/configuring/task-timeout), [Max retries](https://docs.cloud.google.com/run/docs/configuring/max-retries)
- Pub/Sub delivery is at-least-once by default; exactly-once delivery exists only for pull subscriptions. [Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)
- Cloud Storage objects without `Cache-Control` metadata default to `public, max-age=3600`. [Object metadata](https://docs.cloud.google.com/storage/docs/metadata)
- Secret Manager access requires `roles/secretmanager.secretAccessor`. [Access control](https://docs.cloud.google.com/secret-manager/docs/access-control)

Recheck these against the linked pages when they matter to a decision.

## Claims to check

- "Cloud Run keeps reliable in-memory state or cache across requests." False — instances are stateless with no persistence guarantee between invocations. [Cloud Run FAQ](https://github.com/ahmetb/cloud-run-faq)
- "IAP is sufficient application authorization; the backend can trust the header blindly." False — the app must independently verify the JWT's signature and audience. [Signed headers](https://cloud.google.com/iap/docs/signed-headers-howto)
- "Firestore Security Rules protect data accessed via the Admin SDK or server." False — server client libraries bypass rules entirely; use IAM instead. [Security Rules](https://firebase.google.com/docs/firestore/security/get-started)
- "Pub/Sub guarantees exactly-once delivery by default." False — the default is at-least-once; exactly-once applies only to pull subscriptions. [Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)
- "Cloud Tasks has a built-in dead-letter queue like Pub/Sub." False — a dead-letter pattern must be built manually. [Configure queues](https://cloud.google.com/tasks/docs/configuring-queues)
- "Passing tests against the Firebase Emulator Suite proves production limits or index requirements are respected." False — the emulator does not enforce all production limits or index checks. [Firestore emulator](https://docs.cloud.google.com/firestore/native/docs/emulator)
