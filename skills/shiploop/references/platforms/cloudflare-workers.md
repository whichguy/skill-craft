# Cloudflare Workers development

Return to the [guidance selector](../coding-guidance.md#select-guidance) when the runtime or boundary changes. Cloudflare Access can be enabled per-Worker or account-wide, enforcing an identity policy at the edge before code runs, across custom domains, routes, workers.dev and previews. ([changelog](https://developers.cloudflare.com/changelog/post/2026-08-14-workers-access/)) Access injects `ctx.access`; call `await ctx.access.getIdentity()` for email, name, groups, IdP and device posture. ([docs](https://developers.cloudflare.com/workers/configuration/cloudflare-access/)) If the origin is reachable other than through Access, validate the signed `Cf-Access-Jwt-Assertion` JWT server-side. ([API Shield](https://developers.cloudflare.com/api-shield/security/jwt-validation/jwt-worker/)) Workers has no built-in consumer identity provider; non-Zero-Trust apps implement OAuth/OIDC themselves, and Turnstile is bot mitigation, not identity. ([Turnstile](https://developers.cloudflare.com/turnstile/))

For authorization, Access policies gate Zero Trust apps at the edge. ([docs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/)) Service bindings let one Worker call another without a public URL, with auth implicit via account membership. ([docs](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/)) Service Tokens authenticate machine callers through an Access app. ([docs](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/)) mTLS certificate bindings let a Worker present a client cert to an mTLS-secured origin. ([docs](https://developers.cloudflare.com/workers/runtime-apis/bindings/mtls/))

A single-user, client-only product needs none of this server machinery, or the state layer below.

For state, Durable Objects storage is private, transactional and strongly consistent per object, with SQLite-backed DOs exposing full SQL and rollback on throw. ([docs](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)) DOs are single-threaded per instance; input gates pause new event delivery during storage ops (opt out with `allowConcurrency: true`) and output gates delay externally-visible confirmation until prior writes commit. ([blog](https://blog.cloudflare.com/durable-objects-easy-fast-correct-choose-three/)) Scale-out is per object ID, not within one object, so shard across IDs. ([docs](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/)) Workers KV is an eventually-consistent global cache with delayed propagation and last-write-wins on concurrent writes to a key, and has no locking or CAS; use a Durable Object or D1 transaction for correctness-sensitive counters or locks. ([docs](https://developers.cloudflare.com/kv/concepts/how-kv-works/)) D1 gives snapshot isolation on its primary, the Sessions API adds sequential consistency across read replicas, and only one `db.transaction()` runs at a time per database. ([blog](https://blog.cloudflare.com/d1-read-replication-beta/)) R2 is strongly consistent: reads, metadata, deletes and lists all reflect the latest state immediately, globally. ([docs](https://developers.cloudflare.com/r2/reference/consistency))

For connectivity, request/response via the `fetch` handler is native. Polling has no special primitive and is just repeated `fetch` calls. Streaming and SSE run over `ReadableStream`/`TransformStream` response bodies with no dedicated SSE API. ([docs](https://developers.cloudflare.com/workers/runtime-apis/streams/)) WebSockets work as server (`WebSocketPair`) or outbound client (`fetch` with `Upgrade: websocket`), and the DO Hibernation API keeps sockets connected while the object is evicted from memory, avoiding duration billing, with up to 32,768 connections per DO cited. ([docs](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)) Platform push has no built-in primitive; call the provider's API via `fetch`. Pick the lightest channel meeting the stated freshness, and after any push, read authoritative state back from the DO, D1 or R2 store rather than KV or cache, given KV's propagation delay.

Cache API follows RFC 9111 heuristic freshness and respects `Cache-Control`, but does not honor `stale-while-revalidate`/`stale-if-error`, and never caches responses with `Set-Cookie`. ([docs](https://developers.cloudflare.com/workers/runtime-apis/cache/))

Per-Worker secrets (`wrangler secret put`) are encrypted, exposed only via `env`, and unreadable after creation. ([docs](https://developers.cloudflare.com/workers/configuration/secrets/)) Secrets Store holds account-level secrets shared across Workers via store ID and name bindings. ([docs](https://developers.cloudflare.com/secrets-store/integrations/workers/)) mTLS bindings store certs and keys as a managed resource, not inline code.

Cron Triggers call `scheduled()` on a Wrangler-configured schedule; test locally with `--test-scheduled`. ([docs](https://developers.cloudflare.com/workers/configuration/cron-triggers/)) Queues are at-least-once, not exactly-once, so consumers must be idempotent; `max_retries` defaults to 3, exhausted messages go to a `dead_letter_queue` or are discarded, and batch failures retry the whole batch unless acked individually. ([docs](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)) Workflows give step-based durable execution where each step retries and memoizes independently and billing runs only while executing. ([blog](https://blog.cloudflare.com/workflows-ga-production-ready-durable-execution/))

Check current limits at the linked pages rather than relying on memorized numbers: [Workers](https://developers.cloudflare.com/workers/platform/limits/), [Durable Objects](https://developers.cloudflare.com/durable-objects/platform/limits/), [KV](https://developers.cloudflare.com/kv/platform/limits/), [D1](https://developers.cloudflare.com/d1/platform/limits/), [R2](https://developers.cloudflare.com/r2/platform/limits/), [Queues](https://developers.cloudflare.com/queues/platform/limits/), [Workflows](https://developers.cloudflare.com/workflows/reference/limits/).

`wrangler dev` (Miniflare) emulates KV/D1/DO/Queues/R2 locally, with `--remote` covering behavior hard to simulate. ([docs](https://developers.cloudflare.com/workers/local-development/)) It does not enforce real CPU-time limits, since reported timing includes I/O wait, so a local pass does not prove you're under the production CPU cap. Local dev also does not reproduce real cross-datacenter KV propagation, R2's actual replication path, DO jurisdiction placement, or Access's true edge enforcement; validate those via `--remote` or staging. The `access.dev` config simulates `ctx.access` locally, proving handler logic, not real Access policy enforcement. ([docs](https://developers.cloudflare.com/workers/configuration/cloudflare-access/))

## Claims to check

- False: DOs process one object's requests across multiple threads. Correction: single-threaded per object; scale by sharding IDs. ([docs](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/))
- False: KV is strongly consistent everywhere. Correction: eventually-consistent cache with propagation delay. ([docs](https://developers.cloudflare.com/kv/concepts/how-kv-works/))
- False: R2 has S3-style eventual consistency. Correction: R2 is documented strongly consistent for reads, metadata, deletes and listing. ([docs](https://developers.cloudflare.com/r2/reference/consistency))
- False: Queues guarantee exactly-once delivery. Correction: at-least-once; dedupe in the consumer. ([docs](https://developers.cloudflare.com/queues/reference/delivery-guarantees/))
- False: Cache API honors `stale-while-revalidate`. Correction: explicitly unsupported by `cache.put`/`match`. ([docs](https://developers.cloudflare.com/workers/runtime-apis/cache/))
- False: hibernating DO WebSockets keep accruing duration billing. Correction: hibernation exists so duration doesn't accrue while evicted. ([docs](https://developers.cloudflare.com/durable-objects/best-practices/websockets/))
- False: local `wrangler dev` proves you're under the production CPU-time limit. Correction: local timing includes I/O wait and doesn't enforce the real cap; only a deployed/`--remote` run does.
