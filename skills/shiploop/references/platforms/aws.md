# AWS serverless development

Return to the [guidance selector](../coding-guidance.md#select-guidance) when the runtime or boundary changes. A single-user, client-only product needs none of what follows; this applies once a plan crosses into shared server state or multi-user access.

Identify identity and authorization first. Cognito user pools authenticate users and issue JWTs via hosted UI, SDKs, or Amplify ([Cognito user pools JWT docs](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-with-identity-providers.html)). API Gateway HTTP API JWT authorizers validate the signature against the issuer's jwks_uri, support only RSA-based algorithms, and cache the key briefly ([HTTP API JWT authorizer](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-jwt-authorizer.html)); a Lambda authorizer or backend code can instead verify the same token directly, e.g. via aws-jwt-verify ([Decode/verify Cognito JWT](https://repost.aws/knowledge-center/decode-verify-cognito-json-token)). IAM auth needs SigV4-signed requests satisfying both the resource policy and the IAM policy ([Resource policy authorization flow](https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-authorization-flow.html)). Cognito authorizers work on REST/HTTP APIs but not WebSocket APIs, which need a Lambda REQUEST authorizer instead ([WebSocket + Cognito sample](https://github.com/aws-samples/websocket-api-cognito-auth-sample/blob/main/README_en.md)). Cognito identity pools exchange an identity for temporary IAM credentials via AssumeRoleWithWebIdentity for direct per-user AWS API access ([Identity pools guide](https://tutorialsdojo.com/amazon-cognito-user-pools-vs-identity-pools/)).

State, consistency, and concurrency come next. DynamoDB reads default to eventually consistent; ConsistentRead=true forces strong consistency at higher RCU cost ([Read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html)). TransactWriteItems/TransactGetItems are ACID only within one Region, not across Global Tables replicas, and double the capacity consumed ([Transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)). S3 gives strong read-after-write consistency for all GET/PUT/LIST and metadata operations automatically, at no extra cost ([S3 consistency](https://aws.amazon.com/s3/consistency/)). Concurrent writers use DynamoDB optimistic locking: a version-attribute condition expression evaluated atomically with the write, raising ConditionalCheckFailedException on mismatch ([Optimistic locking](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/BestPractices_OptimisticLocking.html)). Lambda reserved concurrency caps or guarantees per-function executions from the account pool; provisioned concurrency pre-initializes environments and bills separately ([Lambda concurrency](https://docs.aws.amazon.com/lambda/latest/dg/lambda-concurrency.html), [Provisioned concurrency](https://docs.aws.amazon.com/lambda/latest/dg/provisioned-concurrency.html)).

Pick the connectivity channel by the freshness actually needed, and read authoritative state back through the paths above rather than trusting a push as final. Plain request/response uses API Gateway with Lambda proxy integration ([API Gateway dev guide](https://docs.aws.amazon.com/apigateway/latest/developerguide/limits.html)); polling the same endpoints needs no special primitive. Streaming/SSE can use Lambda function URLs with RESPONSE_STREAM invoke mode, native only on Node.js elsewhere, and unsupported inside a VPC via function URL, where InvokeWithResponseStream should be used instead ([Response streaming](https://docs.aws.amazon.com/lambda/latest/dg/configuration-response-streaming.html), [Streaming + function URLs](https://docs.aws.amazon.com/lambda/latest/dg/config-rs-invoke-furls.html)). API Gateway WebSocket APIs (connect/disconnect/route plus @connections POST) give bidirectional push, subject to the authorizer caveat above. AppSync subscriptions deliver real-time GraphQL over a managed WebSocket connection triggered by mutations, supporting only pure WebSockets, not SSE ([AppSync real-time data](https://docs.aws.amazon.com/appsync/latest/devguide/aws-appsync-real-time-data.html)). Platform push via APNs/FCM sits outside these services, typically through SNS mobile push, and is unverified beyond that here.

Caching is a derivative layer, not authority. DAX's item/query cache is eventually consistent only; strongly consistent reads and TransactGetItems bypass it and hit DynamoDB directly ([DAX consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DAX.consistency.html)). ElastiCache staleness is whatever the app's own TTL and invalidation logic set; specifics beyond that are unverified here.

Secrets Manager supports automatic rotation, versioned staging labels, and cross-region replication, charged per secret plus API calls; SSM Parameter Store's SecureString parameters are KMS-encrypted and free on the Standard tier but have no built-in rotation or cross-region replication ([Secrets Manager vs Parameter Store](https://tutorialsdojo.com/aws-secrets-manager-vs-systems-manager-parameter-store/)).

Background work needs retries and idempotency named explicitly. EventBridge Scheduler supports a configurable retry policy plus an SQS dead-letter queue for exhausted schedules ([Scheduler DLQ](https://docs.aws.amazon.com/scheduler/latest/UserGuide/configuring-schedule-dlq.html)). SQS-to-Lambda delivery is at-least-once, so handlers must be idempotent; failed batches reappear after the visibility timeout, and a redrive-policy DLQ plus ReportBatchItemFailures handle partial-batch retries ([SQS+Lambda](https://docs.aws.amazon.com/lambda/latest/dg/with-sqs.html)). Step Functions Retry fields (backoff and jitter, matched top-to-bottom by ErrorEquals) and Catch fields on Task/Parallel/Map states define recovery; an uncaught error fails the execution ([Error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)).

Check current numeric limits rather than remembered ones: [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html), [API Gateway quotas](https://docs.aws.amazon.com/apigateway/latest/developerguide/limits.html), [DynamoDB quotas](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotasRevised.html), [EventBridge Scheduler DLQ config](https://docs.aws.amazon.com/scheduler/latest/UserGuide/configuring-schedule-dlq.html).

Local development proves little beyond handler logic. sam local start-api/invoke emulate the Lambda runtime and API Gateway routing but not other AWS services — calls to DynamoDB, S3, and the like hit real AWS or fail — and cannot emulate Lambda /mnt mounts ([SAM local start-api](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/serverless-sam-cli-using-start-api.html)). Passing local tests does not establish IAM permissions, cold-start behavior, or integration wiring.

## Claims to check

- "S3 is only eventually consistent." It has strong read-after-write consistency automatically. [S3 consistency](https://aws.amazon.com/s3/consistency/)
- "DynamoDB transactions are ACID across Global Tables regions." ACID holds only within the region where the write API was called. [Transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)
- "WebSocket APIs support a built-in Cognito user-pool authorizer like REST/HTTP APIs." Not supported; a Lambda authorizer is required. [WebSocket sample](https://github.com/aws-samples/websocket-api-cognito-auth-sample/blob/main/README_en.md)
- "DAX makes strongly consistent DynamoDB reads eventually consistent." Strong reads and TransactGetItems bypass DAX entirely. [DAX consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DAX.consistency.html)
- "SAM local fully emulates AWS for integration testing." It only emulates Lambda/API Gateway routing, not downstream services. [SAM local start-api](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/serverless-sam-cli-using-start-api.html)
- "Lambda function URL response streaming works the same inside a VPC." Not supported there; use the SDK InvokeWithResponseStream API instead. [Response streaming](https://docs.aws.amazon.com/lambda/latest/dg/configuration-response-streaming.html)
