These facts separate actual baseline, controlled fixture capability, and
unresolved candidate. They do not assert a production deployment or
third-party-package availability.

* The copied non-Git product is a static embedded web fixture. It has plain
  same-origin `app.js`, `index.html`, and `styles.css`, a self-only CSP, no
  deployed server process, no external CDN, no persistent socket, and foreground
  reconciliation; see [docs/platform.md](../../product/docs/platform.md).
* The baseline's native account selector, note list/detail/editor, focus
  restoration, live regions, navy/amber typography and narrow layout are real
  source facts. It has no accepted reusable export-activity component contract,
  shared transition policy, or motion-token layer for a compact-to-expanded
  activity view.
* Ordinary DOM composition, same-origin CSS transitions/keyframes,
  `aria-live`, and `prefers-reduced-motion` are controlled available primitives
  for this fixture. They can support a CSS/DOM evolution. They do not make an
  animation a domain-success confirmation.

  establish this target question before adoption; it must extend the existing
  environment/verification path rather than become a parallel design harness.

  package availability/licensing record exists. A framework or design-system

  selected as present tooling.
* `node --check app.js` and `node --test` are the existing commands; the latter
  currently discovers zero tests. Future validation belongs in the existing
  product test/probe route. This control creates neither an implementation nor
