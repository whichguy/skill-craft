## Reuse, state ownership, and lifecycle decisions

- Reuse the existing same-origin request/response export contract and its revisioned read path. Do not add a WebSocket, background receiver, client storage carrier, framework migration, or new dependency from these observations.
- Export job state and revision remain server-authoritative. Client display state is only current after a successful authoritative read. A POST acknowledgement means durable acceptance of the export operation, not completion; an invalidation cue is not confirmation.
- The client currently has no export component, collection binding, or revision-comparison state. Q-R2a requires the later spec to define active-account scope, relevant collection, temporary notice/cursor semantics, and identity/foreground reset behavior; it is an application decision, not evidence that a persistent notification store or API exists.
- The current UI owns presentation and in-memory editing; observed `switchAccount` aborts outstanding detail/save work. That does not satisfy reload recovery or prove cross-account protection for a future durable draft.
- The durable pending-draft owner, account key, authorization enforcement, storage lifecycle, conflict/replay behavior, and clear-on-identity-change semantics are intentionally unresolved under Q-R1. Do not infer them from the account selector or historical v1 storage statement.
- A visible/foreground export reconciliation must retain a person’s active edit, focus, and reading position. If a server refresh conflicts with pending text, the later spec must provide a truthful non-destructive state and recovery action; no current contract resolves that conflict.

## Contradiction, access, and verification boundary

`docs/design.md` records a historical v1 browser-storage assumption, while the current v2 controlled probe records unavailable browser persistence and no draft API. The current v2 observation governs this request’s feasibility assessment; historical v1 is context only. The absence of a named remote target/owner means there is no authorized, discriminating remote read to run. More source reading cannot determine the owner’s storage policy, draft API, authorization model, or deployment route.

Independent planning can continue with Q-R1, Q-R3, and Q-R5 disclosed as prerequisites. They block the first dependent draft/API implementation and meaningful real-target/service/browser verification. Revalidate the fixture probe before relying on runtime facts, recheck the maintained API contract before implementation, and request the smallest named target/owner decision only when a dependent work item reaches that gate.
