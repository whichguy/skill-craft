# W1 step-plan evidence — remote export status

## Scope and disposition

This is the real producer attempt for W1, **Add remote export status using the
existing API**. It is planning-only: no product source, dependencies, target,
account, deployment, commit, or push was changed.

The producer is blocked on an API-contract/requirements prerequisite that is
outside this item's authority:

- The only stated write contract is POST /api/exports, which requires
  collectionId and clientOperationId.
- The Field Notes UI carries only an account, note IDs, and a note record.
  There is no collection identifier, collection-to-note/account relationship,
  export payload schema, status vocabulary, operation-result schema, or error
  representation anywhere in the inspected product sources.
- Inferring any of those would create an unapproved collection mapping and
  response contract. In particular, a generic status card cannot truthfully
  decide whether an operation was durably accepted, failed, complete, or has a
  safe same-origin download until those response shapes and transitions are
  defined.

The selected item remains distinct from W2. The current controlled target
explicitly reports unavailable client persistent storage and no draft API; this
plan does not add a storage fallback or fold persistent drafts into export work.

## Concrete implementation plan after the supplier is available

1. **Contract supplier before W1 implementation.** The API/requirements owner
   must add an authoritative, account-scoped export fixture or a concise
   docs/api.md contract that names: the UI's allowed collectionId source;
   request/response JSON for all four routes; revisions; legal
   pending/complete/failed states; idempotency and lost-confirmation behavior;
   error payloads; and the complete-only same-origin download path. It must
   include a sanitized fixture for a visible export, a lost POST confirmation,
   a failed job, and a completed job. This is the earliest blocking supplier;
   W1 must be re-planned against that current source.

2. **Keep the existing static client architecture.** After step 1, add a small
   classic same-origin export-status helper and load it before app.js, or keep
   equivalent narrowly scoped helpers in app.js only if the supplied contract
   permits direct unit testing. Do not introduce a framework, external asset,
   server process, WebSocket, storage mechanism, or API endpoint. Add DOM
   elements only after the collection relationship tells whether export status
   belongs to a note detail, an account view, or another already-approved
   surface.

3. **State and recovery behavior.** Use a new clientOperationId once per
   explicit user request. POST only after the user-triggered action has a
   documented collection. If the POST response is lost or ambiguous, retain the
   pending operation identity and call GET /api/operations/:clientOperationId;
   do not display confirmation until that route establishes it. Poll only while
   the page is visible, abort/supersede account-scoped requests on account
   change, ignore stale callbacks using the existing generation pattern, and
   reconcile GET /api/exports and GET /api/exports/:jobId state on
   visibilitychange foreground. Server job state remains authoritative. A
   complete-only same-origin download link is exposed only when the supplied
   schema establishes completion.

4. **UI delta after the mapping is known.** Preserve the Field Notes
   navy/amber/white-card vocabulary and existing focus/textarea/read-position
   behavior. The tentative signature is one quiet amber folio mark whose
   adjacent text gives the actual export state; it is a status cue, never a
   success animation. Pending work uses an accessible live status with a static
   reduced-motion equivalent. Failure stays visible with a plain recovery action
   such as “Refresh export status”; no transient cue can claim a server result.
   The implementation must use end-user copy tied to the documented outcome
   rather than system-internal terminology.

5. **Test bootstrap and cases after step 1.** There is no repository test
   harness. Establish the smallest no-dependency Node node:test route and
   deterministic API fixtures before feature code. The intended durable files
   are tests/export-status.test.js and tests/fixtures/exports/*.json, with
   stable selectors only after the placement decision. Use a pure
   request/reconciliation helper or a browser-compatible test seam; do not
   depend on a deployed server or a browser login for local unit cases. Add the
   focused command node --test tests/export-status.test.js; add the full command
   node --test; retain node --check app.js as a syntax smoke rather than
   treating it as behavior coverage.

   Planned cases, all **not run** until the supplier exists:

   - **TC-EX-01:** initial status render from a documented authorized
     collection response; only a complete status exposes its documented
     same-origin download path.
   - **TC-EX-02:** explicit export request gets one stable clientOperationId;
     a lost POST confirmation reconciles through the operations route and never
     displays false success.
   - **TC-EX-03:** visible-only polling transitions pending to complete or
     failed using the supplied state vocabulary; an unknown/error payload
     remains visible and actionable.
   - **TC-EX-04:** account change, hidden page, and foreground reconciliation
     abort or reject stale callbacks and never let an old account update the
     replacement view.
   - **TC-EX-05:** existing note editing/save/cancel/back behavior retains its
     current syntax smoke plus a targeted regression once a local DOM test seam
     is selected.
   - **TC-EX-06:** the environment probe remains an explicit unavailable-boundary
     check: no W1 code writes or depends on persistent client draft storage.

   Local fixture cases are stateless after mocked fetches are reset in each
   test; their independent oracle is the supplied API contract, not the
   implementation. A real browser journey is required later for rendered
   status/focus/live-region behavior, but it remains unrun because this
   experiment has no deployed target or authorized service fixture. A local
   unit pass will not substitute for that consumer check.

6. **Required post-implementation checks.** Run the focused and full Node
   suites, node --check app.js, the target probe, and an authorized browser
   journey against the exact candidate/target when one exists. Recheck CSP,
   same-origin asset loading, hidden/foreground behavior, keyboard focus,
   narrow layout, and reduced motion. Keep remote integration/deployment and
   consumer verification separate from local evidence.

## Environment and authority

The controlled fixture is a static target named fieldnotes-embedded-v2. It
allows same-origin HTTPS request/response only; it has no server runtime,
WebSocket, client persistent storage, or draft API. The current run has no
remote deployment access and no authority to create an API fixture, mutate a
remote account, or deploy. The API contract prerequisite therefore needs a
supplier/correction before this work can continue. No browser or HTTP probe can
prove remote behavior because no target/service binding exists.
