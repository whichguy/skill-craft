## Carried contract and design basis

The planned client is a dependency-free static browser artifact with same-origin scripts, styles, fonts, images, and HTTPS API calls. It has no deployed server runtime, CDN dependency, inline script/style, or persistent WebSocket. The embedded host owns authorization and account identity; the API owns authorized collections, durable operation acceptance, job status, revision, and a complete-only same-origin download path. The client owns only selection, transient request/reconciliation state, accepted display revision, focus, and feedback. Visible polling and foreground reconciliation are the only planned freshness route; a notification, if one later exists, is an invalidation hint rather than a state update. These fixture boundaries were rechecked by the controlled probe (`run/evidence/global-plan-probe-stdout.json`).

The visual direction remains an archive ledger: graphite `#17212B`, catalog blue `#294C67`, paper-gray `#E2E8E5`, circulation green `#3A765C`, and rust `#A84638`; quiet sans controls, restrained serif collection/status text, monospace metadata, and a state-bearing accession strip. The four planned surface components are a native collection selector, explicit export request control, status ledger, and complete-only open-export action. The strip communicates queue/progress/completion chronology rather than decoration. This carries the selected frontend-design card (`sha256:1608ea77fbb6fc30d13a97d12cfa8ebf31358d40f0dd97beed24829d6b3f45dd`) and `run/notes/spec.md` R-06/R-07 forward; the actual same-origin font/asset route remains W2 work.

Planned asynchronous language must distinguish “recording request,” “reconciling status,” current queue/running/failed/complete status, and an unresolved lost confirmation. It must never announce a durable success without confirmed or reconciled API evidence. Motion is limited to a status-bearing cue, with `prefers-reduced-motion` suppressing nonessential animation while preserving text and state. Native controls and visible focus provide the keyboard route; the narrow layout must retain labels, order, state, and action targets.

The key recovery boundary is a client crash or lost confirmation after API acceptance but before the client has processed the response. A known operation ID may be reconciled through `GET /api/operations/:clientOperationId`; if no ID is available, the UI remains unresolved and does not infer success. Persistence across a full reload, duplicate/repeat POST behavior, retries, and error vocabulary are deliberately unselected until W2 receives an API-owner decision or approved fixture.

- No implementation begins in this experiment. Each future item rechecks its cited source, the W1 requirements home and W2 durable decision locator where applicable, current repository/target identity, and authority before edits or external actions.

- Runtime state and delivery claims remain separate: API acceptance is not client display; a local browser preview is not embedded-target compatibility; target deployment is not authorized consumer proof.
- The normal ShipLoop Improve handoff immediately follows this plan producer. It reviews this planning candidate and its proposed checks only; it does not implement features or certify future target behavior.
