# Codybot · Salesforce managed-package build specification

Build **Codybot** as a namespaced, second-generation Salesforce managed package. A subscriber can publish many bots, choose a Chief of Staff, and give each bot a purpose, permissions, tools and operating scope. An employee can ask about the org, open a supporting record and approve a precise change with the conversational ease of Grokbot and a Gemini-inspired Lightning chat. An authorized integration can do the same through REST. Support OpenAI and Anthropic Claude as selectable backends behind the same Salesforce permission, approval and client contracts. Accept and return text, images, PDFs and voice notes in Lightning and authenticated REST. Each response appears as the originating bot on the bound channel and is saved as one ordered assistant message. [Multimodal turn contract](#multimodal-turns-in-lightning-and-rest)

**Deliver working v1 software.** Supply the Salesforce DX source, Apex services and tests, Lightning components, package metadata, permission sets, subscriber setup and upgrade procedure, and evidence from the release scenarios below. Work in thin, usable increments. Start with an isolated user session that accepts a slow multimodal turn, produces a mixed-media reply, reopens to its exact files, schedules a private follow-up and eventually expires. Then exercise persistent instances, configurable delegation, administrative bots, backlog and memory, approved single-record Salesforce writes and read-only external MCP tools. Use an authorized subscriber test org for installation and live qualification. Record which claims remain unverified if a prerequisite is missing.

Reviewing this specification or preparing a ShipLoop workspace uses local fixtures. Start a build explicitly. Use only the subscriber org and metered services authorized for that run, within any supplied spending limit. If a live prerequisite is missing, continue the local work and record the open claim in the [release evidence map](#release-evidence-map).

**Build the complete path first.** The first acceptance run starts with an authenticated turn, commits one ordered assistant reply, delivers its media on the original channel, recovers it after reconnect and retires it at lease expiry. Salesforce owns the authoritative run, dialogue, asset versions and delivery intent. A qualified service can own the long inference or rendering step. Use these contracts together. [Turn and UI rendezvous](#one-contract-in-both-directions) · [Same-channel replies](#returning-media-on-the-originating-channel) · [Instance and channel ownership](#bot-instances-channel-sessions-and-expiry) · [Whole-dialogue JSON](#the-dialogue-as-a-salesforce-json-file) · [Native timers](#built-in-salesforce-timer-tools) · [Message-based expiry](#package-wide-message-service-for-expired-leases)

Use Salesforce-hosted JSON Files for memory documents, indexed custom records for fast authorized lookup, and typed run checkpoints for recovery. Design the **Poppy 1.0 Company adapter** in detail in this assignment. Its implementation and interoperability qualification are a follow-on. Treat the November 22, 2026 research as a baseline. Verify the Salesforce release, Apex class API versions, subscriber entitlements, model endpoint and protocol versions in the target environment. ## The experience the package must deliver

An admin can create a bot, set its purpose and instructions, choose eligible users, limit its Salesforce objects, fields and actions, configure allowed delegates and MCP policy, preview effective access, and publish a version. A Chief of Staff is a capability an admin can enable on any bot. Ship a configurable example and demonstrate two independently configured coordinators. Resolve a new conversation from an explicit accessible bot selection, the user’s pinned entry bot, or the subscriber’s configured coordinator reference for that channel. A subscriber may point different channels at different published coordinators. If the configured target is unavailable or inaccessible, show the authorized picker. Pin the resolved bot, instance and binding for that conversation. A later default change affects new conversations. An attributed specialist returns its contribution through the same coordinator and route. In v1, coordinators can use a specialist one at a time with one level of delegation. Clarify when an ambiguous handoff would change the result. Pass the minimum task context, retain one thread, and identify who answered or proposed an action.

Distinguish an end-user specialist from a bot allowed to draft, revise, and propose publication of Codybot configuration. Require the initiating user to hold the corresponding administrative entitlement. Define what a configuration admin may assign to others. Prevent a bot from expanding its own effective authority through edits, publication, delegation, alternate entry points, or changes to another bot. Keep Salesforce principal assignments, credentials and trust-root administration under subscriber-admin control. Define whether an in-flight run can finish after its bot is edited, disabled, unpublished or superseded. A version snapshot explains what ran. Current revocations still apply.

Use an original, spacious Gemini-inspired chat canvas in Lightning. Include a prominent composer, first-use bot picker, visible bot switcher, collapsible history, accessible record links, specialist attribution, and inline approval cards. Use the early interactive design checkpoint to refine clarification, handoff, a long wait, file delivery and readback. Demonstrate that same journey in the installed package. Show loading, reconnect, empty, restricted, failed and cancelled states. Test keyboard focus, contrast, reduced motion, accessible status announcements, and draft isolation between conversations. Validate supported Lightning containers and viewport sizes. Sanitize model/tool content, construct record navigation from authorized identifiers, and load the interface within Lightning Web Security and CSP. [Lightning Web Security HTML handling](https://developer.salesforce.com/docs/platform/lightning-components-security/guide/lws-sanitize-html.html)

## Multimodal turns in Lightning and REST

**V1 accepts and returns text, images, PDFs and voice notes with either OpenAI or Anthropic Claude as the selected reasoning provider.** A person can send any supported item on its own or combine them in one turn. For example, attach a photo of two product labels and a quote PDF, then record “Which of these matches line three on page two?” A useful answer identifies the matching label and cites the page. Test that the answer depends on the attached evidence. Reading the filename or displaying a thumbnail does not establish model access.

| Input | Experience and minimum implementation |
|---|---|
| Text and images | Preserve the order of text, images and captions within the same message. Support selecting or pasting an image, an accessible preview and removal before send. Start with JPEG and PNG. Verify supported types, pixel limits, byte limits, image count, fidelity/cost and any subscriber upload restrictions per model and channel. Keep legible small print when that is material to the task. |
| PDFs | Upload or select a Salesforce File and pin its exact version. Support text and scanned/visual pages. For a chart or quoted term, name the source document and page and let the user open the authorized page or file. Qualify a page/byte limit and preview it before send. Surface a password-protected, corrupted or oversized PDF with an actionable outcome. Any selected page range must be visible to the user. |
| Voice notes | Allow a recorded message or an uploaded audio file. Include record/stop, playback, remove, retry and a file-picker path when microphone access is unavailable. Show transcription progress, the recognized text and a correction path. A voice note alone can start a turn. Preserve the relationship among the original recording, derived transcript revision and user corrections. An uncertain product name or amount can trigger a clarification. The same approval rules apply to a spoken instruction. A correction to a name or amount supersedes a pending proposal derived from the earlier transcript and requires a fresh preview. |
| An ordered mixed turn | Lightning and REST submit one request key with an ordered `parts[]` array. A text part carries text. An image, PDF or audio part carries a scoped asset handle and optional caption. Server-side records pin the accepted version. For admission, compare the ordered parts, exact source versions, captions, text, any submitted transcript correction and the normalized reply requirements. Reordering input parts or changing any of those values with the same key conflicts. Ground replies in the correct part, page or voice transcript. |

**Upload, admit, then dispatch.** Let an authenticated caller create a short-lived staging intent bound to the org, participant, bot instance and channel session. Upload through a supported Files/blob path or select an existing accessible File. Evaluate `lightning-file-upload` for the supported container. For signed-in users its completion event identifies the document. Resolve and pin the intended `ContentVersion` at admission and validate ownership, actual file format, size, availability and the subscriber’s file-security policy. A later upload to the same document cannot change an accepted turn. Surface stage-specific errors. Expire abandoned uploads, including an upload completed after the session closed. Size and hash bytes outside large Apex strings where required. Audit native file ownership and raw historical downloads for newly uploaded private content. [Lightning file upload](https://developer.salesforce.com/docs/platform/lightning-component-reference/guide/lightning-file-upload.html) · [Salesforce blob uploads](https://developer.salesforce.com/docs/platform/api-rest/guide/dome-sobject-insert-update-blob.html)

For REST, expose a method to obtain a scoped upload intent, check readiness and submit the ordered asset handles with text in the ordinary turn request. Bind readiness checks and final adoption to the session epoch. Return the normal 202/run receipt once the inputs and run are durable. If transcription, PDF processing or inference is pending, advance the same run through bounded asynchronous steps. Keep pending statuses in the temporary activity area. Retries and reopening a chat must not upload or transcribe the same accepted asset again without a new authorized operation.

**Media custody and erasure.** Store original bytes and necessary renditions in Salesforce Files. In the transcript, store typed parts referencing exact versions through stable, authorized asset IDs. Include the text that was actually said or shown, relevant page references and the provenance of transcription/OCR edits. A recipient can resolve media through the same scoped service while authorized. Keep binary base64, public file links, raw provider URLs and credentials out of JSON transcripts, events and logs. A session upload, thumbnail, page image, waveform, transcript and provider file handle inherit the session’s retention owner. A user-selected pre-existing CRM File retains its independent owner. Expiry removes the session’s link, derived copies and provider uploads without deleting the independently owned source. Check source access before transfer, model replay, export and delivery. A file, OCR result or recorded instruction has the same authority as ordinary user data. It cannot grant a tool permission or supply a human approval receipt.

**Provider and speech settings.** The subscriber selects a permitted reasoning provider and, where needed, a separately authorized speech-to-text processor. Pin both destinations, accounts/regions, model IDs and retention settings per run. Use a documented direct-audio path only when the chosen endpoint and model have been qualified. The portable path is recorded audio → an approved transcription step → text in the selected reasoning model, with the source handle preserved. For OpenAI speech, qualify multipart `POST /v1/audio/transcriptions` with a supported transcription model and recording format. Use the worker when uploading or transcribing a recording would exceed the remaining Apex byte or callout-time budget. The checked native Claude Messages input schema defines text, image and document blocks. For recorded speech on Claude, use a subscriber-approved speech service or an approved subscriber-controlled transcriber. Provision and exercise at least one working voice path for each backend. Enforce residency, language/codec/duration limits and revocation on the audio transfer itself. Where policy forbids every available speech path, explain that configuration gap before accepting audio. [OpenAI file transcription](https://developers.openai.com/api/docs/guides/speech-to-text) · [Claude Messages API](https://platform.claude.com/docs/en/api/messages) · [Anthropic’s speech-to-text example](https://platform.claude.com/cookbook/third-party-elevenlabs-low-latency-stt-claude-tts)

Apply the tightest measured limit across Salesforce upload, Apex heap/callout, worker, provider and model context. Budget base64 expansion, decoded pixels, PDF pages, transcription duration, number of inputs and cost. Transfer bytes through a registered credentialed path with the least data required. A provider receives only media approved for its destination, never a Salesforce login cookie or an unrestricted URL. Keep provider-managed file IDs scoped by project/workspace and version. Record and reconcile their deletion separately from local Files. Claude’s Files API is workspace-scoped and ineligible for Zero Data Retention. Do not accept a caller-supplied provider file ID as authority. Keep external copy/expiry receipts for each admitted version, under the owning session. If content access is revoked mid-inference, suppress affected late responses and derived data. [Anthropic Files](https://platform.claude.com/docs/en/build-with-claude/files)

### Returning media on the originating channel

**An assistant reply is one ordered message.** It may contain text, an image, a PDF, a voice note, or a mixture. V1 must produce and return all three media types with either reasoning backend. A text-only question can request a media-only answer. The user can ask in ordinary language, and REST can pass `replyRequest.requiredTypes` or `replyRequest.preferredTypes`. At admission apply documented defaults, treat required types as a set and preserve preference order. Include both fields in the request identity. Changing a required PDF to audio with the same key returns a conflict before dispatch or rendering. An equivalent retry recovers the original receipt. Check the bot’s grants, available renderers and the bound channel’s delivery capabilities. Treat an explicit natural-language request for a format as required unless the caller accepts an alternative. REST `preferredTypes` permits fallback among the caller’s acceptable choices. If a required format cannot be rendered or delivered on that binding, explain this before spending on generation and let the caller choose an authorized alternative. A bot can also select a helpful preferred format within those grants. Treat a request for a particular format as satisfied only when the recipient can obtain that media.

| Reply part | How to produce it | What the recipient gets |
|---|---|---|
| Image | Reuse an authorized exact File version, render a chart or mark up an admitted photo, or call an approved image-generation tool. For a factual annotation, overlay the mark on the pinned source and preserve evidence outside the marked region. Identify a newly generated illustration as such. Validate the finished image, MIME type, dimensions and byte count. | A real image part with useful alternative text and an action to open the pinned image. Partial generator previews stay in temporary activity and disappear on completion. |
| PDF | Render an authorized, versioned document template with the permitted facts and source citations, or attach an authorized existing PDF version. Qualify server-side Salesforce Visualforce PDF rendering for the layout, fonts, page count and size. An approved renderer can handle formats outside that envelope. | A PDF part with a safe display name, title and accessible summary. The example one-page comparison identifies label B and cites the quote on page two. Verify the received bytes open as a PDF. [Visualforce PDF rendering limitations](https://developer.salesforce.com/docs/platform/salesforce-pages-developers-guide/guide/pages-output-pdf-considerations.html) |
| Voice note | Compose an authorized spoken answer and send it to the subscriber’s approved speech-synthesis service, or return an authorized existing recording. Store the finished audio and the text actually spoken. If the synthesizer can paraphrase, verify the transcript against the recording for material names, quantities and dates. | A playable audio part with MIME type, duration, transcript and a clear AI-generated voice label when synthesized. Playback is user initiated. Where inline playback is unavailable, give an authorized audio download and its transcript on the same channel. |

For an evidentiary image, keep the original version and a deterministic render recipe. For a photo annotation, include overlay geometry and produce a lossless file. Compare normalized source and result pixels outside the overlay and check that the mark covers the identified subject. For a chart, bind the values and units to their permitted data. An original creative image is labelled as AI-generated when applicable. Derive alt text and PDF summaries from the verified render or the accepted bytes. Check material identifiers, values and cited pages against the source. A generator’s edit prompt cannot establish what appears in the output. [OpenAI image editing and mask precision](https://developers.openai.com/api/docs/guides/image-generation)

#### Commit once before delivery

1. **Reserve and produce.** Reserve each stable `partId` when a production step starts. The coordinator can request more parts during its tool loop. Its final composition sets their order independent of completion order. Reap omitted candidates. Give each production step an idempotency key, current worker attempt and a size budget for the full delivery path. Pass the applicable image dimensions, PDF pages or voice length to the renderer. A missed callback or worker failure must settle via the durable step deadline, claim and retry policy. Pin the input versions, rendering instructions, permitted destination and retention owner. Run a slow renderer or synthesizer outside the UI transaction. Reuse an already successful step on retry. Reconcile an ambiguous provider result before generating a different or chargeable replacement.
2. **Stage exact bytes.** Copy final provider/tool output into private Salesforce Files or validate an existing authorized version. Verify declared versus actual media type, size, checksum, completeness and any subscriber file policy. Record provenance, including the source records/versions the output could reveal and whether the bytes are session-owned or independently owned. The server mints immutable, opaque asset handles for the tenant and retention owner (session/epoch for private output). Each message part names an explicitly authorized use of the asset. A `BotMediaAsset__c` index or equivalent maps the handle to exactly one accepted `ContentVersionId`, its parent `ContentDocumentId` and owner. Stage new output under a separate least-privileged Files custodian. Before adoption, test that the requester cannot retrieve the new version in Files Home, search or the native version/blob API. Selecting a pre-existing File preserves its original ownership and access. Before any upload, persist its staging intent with a bounded `adoptBy` deadline, producing attempt and recoverable upload receipt. A quarantined, rejected, abandoned or late upload is eligible for the independent staged-file cleanup below. Serve only the admitted media types, with safe disposition and content-type handling. Qualify active-content blocking and `nosniff` on the selected transfer route.
3. **Commit the message.** In a short Salesforce transaction, recheck the current participant/delegation permissions, source access, audience, worker attempt, session epoch and deadline. Verify that every required part is ready. Atomically commit the assistant message with its stable message ID, conversation sequence, producing bot, ordered parts and pinned asset references, complete the run, and persist the delivery intent for the immutable origin. Large bytes may have been staged earlier. The committed message makes accepted references visible. A failed commit leaves recoverable staging. A repeated completion returns the original receipt. If a required renderer exhausts its retries while the session is live, atomically mark the run `failed`, commit one stable assistant error message naming only permitted missing formats, and queue that error for the same channel. Staged partials stay private and are reaped. A duplicate completion or retry of error delivery cannot reopen the run. For a failed preferred part, a run with usable content and all required parts ready may complete with a visible omission notice. With no usable reply, apply the failure rule. Expiry suppresses even a queued failure response.
4. **Deliver and reconcile.** Dispatch as the bot bound to the original channel, installation, audience and thread. A specialist can produce a part while the coordinator owns the reply. Store the channel-visible bot identity separately from the producing specialist and renderer. A service job with no approved outbound route leaves its result in its own authorized inbox. Recheck the route, grants and lease immediately before physical handoff and on each content fetch. Track channel delivery separately from run completion. Use a stable delivery ID for the message and, if the channel requires separate sends, one for each ordered part. Retry only missing deliveries from the same pinned bytes. An unknown external outcome requires a receipt lookup, idempotent resend or an explicit uncertain state. Never regenerate the files to redeliver. If capability or access changes, report the outcome on the same authorized route. An acknowledgement from an adapter records what it accepted. User playback or download is separate evidence.

#### Channel presentation and retrieval

**Lightning conversation.** The fresh run snapshot names the final message. Replace the temporary activity area with that message. Show the image with alt text, a PDF card with preview and download controls, and an audio player with its transcript. Provide keyboard-accessible controls and an accessible download when inline presentation is unavailable. Desktop `filePreview` opens a document-level modal. Mobile normally initiates a download. For a pinned or lease-protected part, use an authorized path that returns its exact version. Test after a newer native version exists. [Salesforce file navigation](https://developer.salesforce.com/docs/platform/lwc/guide/use-open-files.html)

**Authenticated REST integration.** A completed run identifies the assistant message. Reading that message returns ordered parts and a protected content location for each file. At read and download, check the caller and client, binding, session epoch and deadline, message/part scope and current access to each contributing source. Withhold affected bytes and revealing filenames, captions, thumbnails or transcripts if a grant has been lost. These rules also apply to native-file and link fallbacks. Serve verified MIME type, byte length and a safe filename. Offer playback and byte ranges where the transfer path supports them. [REST request and response](#authenticated-rest-in-v1)

Salesforce’s native sObject Blob GET below addresses one file version. Use it directly only when native File access and the required cutoff have been demonstrated for this recipient. Use a bounded authenticated streaming path for larger or mediated assets. [Salesforce exact-version blob retrieval](https://developer.salesforce.com/docs/platform/api-rest/guide/resources-sobject-blob-retrieve.html)

```text
GET /services/data/vXX.X/sobjects/ContentVersion/{versionId}/VersionData
```

**Registered callbacks and channel adapters.** Prefer a content-free wake to the registered installation followed by a scoped read. If the adapter supports native attachments and policy allows the recipient to keep the bytes, send the same pinned files under that channel’s authenticated bot identity and size/count limits. For a text-only or size-limited transport, send a readable description and an authenticated, lease-bound retrieval link on the same channel when supported. If neither attachment nor protected retrieval is available, report the undelivered part on that channel. A description alone leaves the file undelivered.

Conversation JSON stores `partId`, type, authorized `assetId`, MIME type and the visible content appropriate to each part, including alt text, PDF title/summary, voice transcript and synthetic-voice disclosure. Record the producing bot and authorized source handles per media part (`producedBy` and `derivedFrom` in the example), distinct from the channel-visible author. Keep the renderer identity, provenance for the description, exact version, byte count, SHA-256 digest, source-access dependencies and retention owner in the protected asset index. If source access is lost, apply the same restrictions to any text part, citation or accessible description that reveals its contents. Keep the channel presentation linked to the authored message. Record which part IDs were offered as native attachments or protected references, any user-visible fallback notice and the accepted version of a different authorized rendition. If a channel resizes or transcodes bytes outside Codybot, record what was handed off and what the adapter can actually verify. Preserve the visible presentation when exporting or replaying what was said. Retrying a delivery creates no duplicate chat message. Delivery attempts, transport acknowledgements and provider file IDs belong in scoped operational records. Mint fetch locations when an authorized client reads the message. Credentials, signed URLs and base64 bytes do not belong in the durable transcript. A transcript export states which assets its references cover and how an authorized recipient can retrieve them. Apply the original scope’s export and erasure rules to package-controlled copies. Redisplay never repeats generation, synthesis or tool actions. When building later model context, recheck current source and destination grants. Use authorized descriptions for ordinary recall. For a request that depends on the visible pixels, pages or recording, explicitly resolve the pinned bytes for that task. Do not let a prior provider handle bypass the check.

## Core v1 mechanism · asynchronous turns and UI rendezvous

Assume from the first prototype that **every model turn can take several minutes** and that the person can disconnect before it finishes. Implement one shared turn service for Lightning and REST. The leased channel session binds an instantiated bot to its participant and return route. Within that session a Salesforce-owned run matches the original prompt to its steps, clarification and final answer. Closing the tab does not end a live lease. Make the first vertical slice carry a single slow turn through this entire path in an installed subscriber org. Use the same contract later for delegation, backlog work that needs a person, and the Poppy adapter.

### One contract in both directions

| Action | Durable behavior | Client-visible result |
|---|---|---|
| Submit a prompt | The client creates a request key before sending. In one short transaction, authorize the caller, resolve the instance and live channel session, deduplicate by tenant, authenticated origin, session/epoch and request key, persist the user message and run, and persist dispatch intent that a recovery worker can find. | REST returns 202 with the instance, session/epoch, conversation, turn, run, lease deadline (where applicable) and status location after commit. The Lightning Apex action returns the equivalent receipt. A retry with the same normalized turn and key recovers the same receipt. A changed input or reply requirement with the same key conflicts before dispatch. |
| Dispatch a model step | Assign and commit a logical step ID and current attempt ID before sending work. Use a short native provider submission if qualified, or dispatch to a worker that acknowledges durable custody and owns the long provider connection. | The UI can already show the accepted prompt. Workers can advance an authorized run with every browser closed while its owning session remains live. |
| Receive progress, a tool request, or a result | Authenticate the sender and bind it to the assigned tenant, instance, session generation, run, step and worker attempt; verify the owning scope is still live. In a short transaction, deduplicate the receipt, verify the permitted transition, and commit the new state. When a result requests output media, park the run while the required parts are staged and verified. Commit the canonical final message, accepted part references, terminal run transition and same-channel delivery intent atomically. Emit the wake-up after commit. | An authorized fresh snapshot supplies the latest milestone, open question/proposal or final message. Publishing and delivery may be retried independently of the model work. |
| Ask the user | Persist the question, its intended respondent, an interaction ID, its version, and the continuation needed for that exact model/tool step. For a write, link the immutable proposal and its own revision. Set the run to awaiting input or approval and release execution resources. | Lightning renders an addressable question or approval card. REST exposes the same pending interaction. Until scope expiry it survives refresh and is discoverable in that context’s authorized conversation or pending-work list, even if no tab was open when it arrived. |
| Answer or approve | Authorize the respondent in the live session and bind the response key to the original instance, route, open interaction and its expected version. Atomically consume it once, record the reply and queue its continuation. For writes, apply the separate proposal checks and execution receipt specified below. | A second tab sees that the interaction was answered. A replay returns its receipt. A conflicting response or superseded proposal produces a fresh snapshot and no new effect. A new free-text chat message starts ordinary work unless explicitly linked to the pending question. |

Define a compact run snapshot with `instanceId`, `bindingId`, `sessionId`, session `epoch`, `expiresAt` when leased, `conversationId`, `turnId`, `runId`, monotonic `revision`, `state`, the current display-safe activity if any, and references to the open interaction or final message as applicable. Offer a read of authorized conversations and their pending or recently completed turns so users can recover even if the original acknowledgement never reached the browser. Preserve request keys through uncertain delivery without persisting secrets in browser storage. A Salesforce async job ID, provider response ID or event replay ID identifies only its own subsystem.

An independent text-and-clarification trace follows. Its IDs are different from those in the stored media example. Routes are relative to the package’s versioned service and the actor is derived from authenticated context. Timestamps in the worked examples use a fixture clock. Anchor test deadlines to the test clock or the current run’s server time.

```text
POST /conversations/C9/turns   {sessionHandle: S9, requestKey: K9,
                               parts: [{type: text, text: "Which renewal needs attention?"}]}
  202  {instanceId: I9, bindingId: B9, sessionId: S9, epoch: 1,
        conversationId: C9, turnId: T9, runId: R9, revision: 1, state: queued,
        expiresAt: "2026-11-22T17:30:00Z", statusUrl: /services/apexrest/codybot/v1/runs/R9}
POST /sessions/S9/resume       {requestKey: K-resume9, expectedEpoch: 1}
  200  {instanceId: I9, bindingId: B9, sessionId: S9, epoch: 1}   # authenticated bound participant
GET  /runs/R9                  # read-only snapshot after resume
  200  {runId: R9, revision: 4, state: awaiting_input,
        interaction: {id: Q9, version: 1, kind: clarification, text: "Which account?"}}
POST /runs/R9/interactions/Q9/responses   {requestKey: K10, expectedVersion: 1, choice: A9}
  202  {runId: R9, interactionId: Q9, receiptId: U9, revision: 5, state: queued}
GET  /runs/R9                  # the final wake-up can be lost
  200  {runId: R9, revision: 8, state: completed, finalMessageId: M9}
```

Show legal transitions for queued work, provider wait, tool execution, awaiting input/approval, preparing required output parts, reconciliation and terminal outcomes. Track per-channel delivery separately so a missing delivery acknowledgement cannot move a completed run back to model execution. Define transitions for `pending`, `available` (pull client), `accepted` (acknowledged handoff), `uncertain`, `failed` and `suppressed`. Track the last disposition per part for adapters that must send them separately. A later content read is a separate observation. Give the application sole authority to advance the run revision. Bind a human reply to the **interaction version** so unrelated status updates cannot invalidate it. A retry of the same outbound dispatch uses the same idempotency key. A deliberately superseded execution gets a new attempt identity, and any late result from the old attempt cannot take ownership. An authenticated completion may arrive before the submit acknowledgement. Correlate it by the preassigned ID and ensure a late acknowledgement cannot move the run backwards. Record the worker delivery ID and, if progress can arrive out of order within an attempt, sequence it or discard superseded milestones. Return the same receipt when Salesforce committed a result but the callback acknowledgement was lost. Provider callbacks may deliver results or request a tool. They cannot impersonate the Salesforce caller, approve a proposal, or write arbitrary Salesforce records.

Make waiting inexpensive in both directions. Release the Salesforce transaction, record lock and browser request during model inference. Only the provider or a qualified external worker owns a long model connection. While waiting for a person, park the continuation and release the worker on either architecture. Resume an authorized model step with its structured tool-call result and the necessary conversation context in a fresh execution. Specify how to resume if provider-held context expires while a person is away. Committing a cancellation invalidates uncommitted work from the superseded attempt. If a business write already committed, retain its receipt and report that outcome. A provider acceptance or business effect with an uncertain outcome enters reconciliation before any reissue with potential side effects.

### How Lightning catches up

1. Open the conversation and fetch fresh authorized state immediately. On supported desktop surfaces, establish one shared notification subscription. Once the subscription is ready, fetch again to cover the interval in which an update could have been missed. Listen before submitting subsequent turns when possible. Reading still works during subscription startup or failure.
2. Treat a wake-up as a hint to reread. Coalesce bursts into one in-flight read and remember whether another read is due if a hint arrives during it. Apply a snapshot only to its matching instance, binding, live session/epoch, conversation and run, at the current or a newer revision. Keep each run's display state independent when two turns complete out of order. Check authorization before returning even an “unchanged” result. Clear protected state, pending cards, drafts and cached replies on access loss or session expiry, including already completed turns. Schedule the local display to clear at the deadline even for a completed turn. On return to the foreground or reconnect, clear expired content before fetching authoritative state.
3. Request authoritative state on reconnect, return to the foreground, and after an interval of silence while work is active. Use a fresh imperative Apex read or explicitly refresh wired data. A client cache hit cannot establish that the worker is still running. When push is unavailable or quota-constrained, use adaptive, jittered short snapshot reads for visible active conversations. Stop active monitoring on terminal state, suspend it while away, and recover on return. The browser's reads have no power to enqueue model jobs. ## Bot instances, channel sessions and expiry

Resolve two questions before accepting work: **which bot instance owns this interaction, and through which channel can it answer?** The session is the leased meeting place for a participant and an instance. A run is the durable rendezvous for one turn inside that session. Many runs can finish independently. Keep the IDs distinct even in a simple chat where one instance currently has only one session.

### Identities and ownership

| Identity | What it owns |
|---|---|
| `templateId` and `templateVersionId` | The named bot definition, published instructions, default capabilities and schedule definitions. The main bot reference can also own live service triggers and receive explicitly addressed service messages. Route those to a configured **main operating instance** with its own service authority and destination. A template trigger fires once for its declared target. A template may also define a timer that is copied at instantiation, in which case the copy belongs to that instance. Make these two choices explicit in the builder. |
| `instanceId` | One instantiation of a published template in a subscriber org. Store its lifetime mode, owner/audience, authorized principal or grant, pinned configuration and state. An **interaction-scoped** instance belongs to one end-user/channel context and expires with it. A **persistent** instance can run its own inbox, backlog and timers between interactions and serve multiple isolated channel sessions. It can be the main operating instance or a separately named user/service instance. Pin each run’s effective config version and enforce current revocations. |
| `bindingId` and `sessionId` | A binding identifies a verified return route, including the adapter installation, channel-side bot account, external tenant/client, recipient or authorized audience, and conversation/thread as appropriate. A session binds one instance, that route and that participant to an explicit interaction context. Store its lifecycle generation (`epoch`), lease holder, lease policy and state. A fresh context may have the same bot, user and external thread as another context. Issue a distinct session handle. Physical reconnects can reuse a live session after authorization. |
| `conversationId`, `turnId` and `runId` | The conversation partitions history and model context within the session. The turn identifies the initiating message, and the run identifies its execution and pending questions. Bind worker steps and attempts beneath the run. The logical conversation, Salesforce login session, OAuth token, Poppy request proof, provider conversation and Queueable job each have separate lifetimes. |

Reuse existing packaged objects where they already provide these boundaries. A practical minimum adds `BotInstance__c` and `BotSession__c`, with the verified route on the session or a referenced binding record. Put required tenant-scoped references or validated foreign keys on work, timers, journal indexes, approvals and output records. Deny a child whose parent references disagree. A reference to the template alone never resolves a private inbox, history, memory namespace, credential grant or return address.

### Admission, isolation and replies

Provide three explicit operations: **start a new interaction** from an accessible template, **resume a live session** with its bound participant and handle, and **address a named persistent or main instance** with a permitted service or user identity. Resolve the inbound route from authenticated adapter facts. For APIs, bind the verified OAuth client/installation, represented subject or service principal, and caller context. For Lightning, bind the current org, authenticated person and selected conversation. An authenticated REST control request may recover that Lightning run only through a client authorized for the same participant and existing binding. The resume service verifies that relationship server-side and preserves the original reply destination. A separate API installation starts or resumes only its own authorized context. Require an explicit new/resume choice or parent-message correlation if a channel cannot distinguish two active contexts. Reject ambiguous, expired or unauthorized resumes. A late reply must never start a fresh session implicitly. Mint non-reusable instance/session IDs. Never bind an old handle to a newly created context with the same external thread ID.

For every accepted input persist the origin instance, binding, session/epoch, conversation, turn, authenticated source event/request key, intended respondent and immutable reply destination. Check inbound idempotency within this namespace. For the very first create, use a unique key scoped to org, authenticated principal, adapter installation, target and client start key, before a session ID exists. A retried creation resolves to the same live admission or its expired outcome. Use a fresh, verifiable start for genuinely new work.

Partition transcripts, inbox reads, pending questions, model/provider context, caches, events and drafts by the verified context. A named persistent instance may share only explicitly authorized instance-level knowledge across its sessions. A coordinator’s delegated step inherits the origin for its result and receives only authorized task context. Stamp stable delivery IDs on outbox items. Send each reply, media part, progress signal, approval request and follow-up **as the bot on the initiating channel**. A timer-originated response uses the timer’s stored destination. A private timer remains tied to the participant’s session and epoch. Verify the same audience, registered endpoint and permission against the run’s session ID and epoch again at dispatch. For a group conversation, the entire current recipient audience must be authorized for the content. Surface an unavailable destination on the original route or its authorized status endpoint. A blocked channel cannot cause delivery to the bot’s most recently used channel. Retire a binding when its channel-side bot identity, registered callback ownership, or recipient audience changes. Treat reassignment of an external thread ID as a new binding. Revalidate changes against authenticated adapter evidence. An old delivery may never follow a newly assigned route.

An authorized second browser, device or API client may explicitly resume or read the same logical session where policy permits. Answering an exact interaction uses that session and expected interaction version. This permits recovery of a Lightning submission through authorized REST while its outbound answer remains addressed to Lightning. An independent REST submission receives its own REST receipt/status stream or preregistered callback. Same template, same human or equal external thread numbers never merge sessions automatically.

### Who owns a timer

| Timer owner | Target when it fires | After a private session expires |
|---|---|---|
| Main bot reference (`templateId`) | The explicitly configured main/service instance and its service inbox or registered service destination. A template-level inbound API interaction follows the same service addressing rule. | The main schedule continues under its own grants. No expired user state or recipient is inherited. |
| Named persistent instance (`instanceId`) | That instance’s own work queue, using its assigned principal and an explicit destination if an outward message is required. | Its independent work continues. Any child follow-up addressed to the expired session is retired. |
| End-user follow-up (`instanceId`, `sessionId`, `bindingId`, `epoch`) | The exact instance, conversation and return route that requested it. Store due time/timezone, owner, approval for any lease extension, and occurrence key. | Cancel or suppress the occurrence and purge its payload. A late scheduler or retry may not deliver it to the main bot, another connection, or a replacement session. |

Use one shared due-work dispatcher over typed, indexed records. Key each occurrence by tenant, owning scope, timer ID, schedule generation and scheduled occurrence. Revalidate ownership, authorization, session lifetime and occurrence uniqueness when claiming and again before delivery. In the authorized UI and API, let a participant list and cancel their private follow-ups. Show the owner, audience, destination, due time and lease deadline, with states for consent pending, scheduled, delivered, cancelled and missed/expired. | `timer_update` | Accept a timer ID, expected revision, request key and allowed changed fields. Preview the next occurrence. Require separate service authority for template-wide schedules, and keep package-maintenance messages outside the user-bot tool surface. ### Pickup, keep-alive and expiry

Support leased channel sessions on both lifetime modes. A long-lived instance can outlast every individual channel session. Allow a deliberately persistent service context an explicit subscriber retention policy. Record which policy applies at creation. For a leased context, implement `offered → active → expired → purging → purged` and an explicit close that enters the same cleanup path.

1. **Pickup.** Issue an opaque, single-use offer with the intended claimant and a server-set `claimBy`. Keep the offer deadline within the absolute cutoff. Declare whether pickup is by the intended user/client, authorized channel adapter or designated bot consumer for that handoff. Queue insertion and notification delivery alone do not prove pickup. A verified start-and-talk request can open and claim in one transaction when the caller is the intended claimant. A competing claimant cannot take over. A retry by the authorized successful claimant recovers its receipt. At `now >= claimBy` an unclaimed offer expires with its owned payload.
2. **Keep-alive.** Use server time for `lastActivityAt`, `idleUntil`, any expressly authorized `keepThrough` and the policy’s absolute `hardStopAt`. While active, the effective deadline is `min(hardStopAt, max(idleUntil, keepThrough))`, omitting an unset keep-through. For a personal lease, only a fresh authenticated interaction or explicit keep-alive attributable to its bound participant may renew before that deadline. A trusted adapter may convey that participant’s action. Debounce repeated keep-alives and return the committed expiry. Idempotent retries return the already committed deadline. Passive status reads, an open event subscription, model progress, timer delivery, work-claim heartbeats and activity on another session do not renew it. Return the current deadline to Lightning/REST and show it when a decision depends on it. Separate lease-edit revision from session epoch so an ordinary renewal leaves valid in-flight work usable.
3. **Follow-up consent.** For a media follow-up, estimate queue delay, production time and delivery/pickup from the measured route. Generate at the authorized occurrence under then-current permissions. If due time plus that allowance would exceed the current deadline, ask **before scheduling**. If the run overruns the approved deadline, record a content-free missed occurrence and let the session expire. Show the requested time, original channel, new expiry and which session data stays available. Open an extension request with a single-use ID, due time and proposed deadline. Only a matching, timely affirmative response by the authorized holder may atomically extend the lease and activate that timer. Bind the decision to the session epoch, proposed terms and unique request. Process decline and extension attempts without implicit idle renewal. Decline, silence, stale approval or an unsupported extension leaves the original deadline in effect and the follow-up unscheduled. Changing a proposed time or destination requires a fresh decision. Deduplicate competing tab confirmations. Track each approved follow-up’s hold separately. The latest outstanding approved hold supplies `keepThrough`. Cancel or shorten only its own hold on an explicit user change, return the resulting deadline, and preserve another confirmed follow-up’s hold. Preserve the agreed pickup window after the worker sends the reminder. A recurring private timer has a finite consent horizon. The timer, model and worker cannot consent on the user’s behalf. If policy forbids the requested deadline, say so. A delayed scheduler that misses the agreed window skips the follow-up.
4. **Cutoff and fencing.** At `now >= effectiveDeadline` reject new work, keep-alives, replies, approvals, content reads and outward content release for that lease. During the bounded replay window, the authenticated, previously bound holder may read a content-free terminal receipt. That read cannot resume the session, renew the lease or retrieve its dialogue. Check the deadline at each operation even when cleanup has not run. Serialize competing renew/expire transitions with a short lock or equivalent version check, rereading time and state under the lock. Fence retired sessions and stale worker generations. Validate the authenticated callback envelope and session fence before persisting or logging any returned content. Duplicate callbacks and delayed timers receive a content-free terminal outcome and cannot reopen the session or recreate its instance. The separate **worker claim lease** controls retry of a step. Its loss may reassign work while the session is live. Its renewal cannot extend a participant’s lease. Size the participant window for the promised multi-minute turn and queue delay. Within it a worker can finish while the client is offline. An unread final answer expires with its session just as an unanswered question does. [Apex locking and callout boundaries](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexref/langCon_apex_locking_statements.htm)

Expose owner-checked start/claim, explicit keep-alive, request/confirm extension, status and close operations through the package service. A start or claim receipt includes `instanceId`, `bindingId`, `sessionId`, `epoch` and the applicable `claimBy` or `expiresAt`. An extension request names the follow-up, channel, due time and proposed `keepThrough`. Confirmation returns the committed timer ID and expiry. Use the retained session fence to return expiry to its authenticated holder. A wrong holder, an unknown handle and a handle past the fence’s retention window receive the same unavailable response. Require measured pickup, idle and hard-limit settings per channel; they must cover expected queue and inference delays and bound abandoned data.

Use an explicit authorized participant list for claim and consent. Record visibility or email address alone cannot establish who can extend a lease. Use a content-free session fence that survives data deletion for the bounded replay period. All relevant result commits, file publications and dispatch grants check that same fence. Persist a reply intent atomically with its run result and bound route. Recheck before handing any content to an external destination. A send already handed to another service cannot be recalled atomically by a later Salesforce transaction. Where access must end precisely at the deadline, deliver an opaque wake-up and require a fresh authorized read of the content. Resolve ambiguous sends by delivery key and provider acknowledgement, without replaying an external side effect on a new session.

### What expiry purges

Declare a retention owner when each item is created. A session expiry purges **all content owned by that rendezvous**. For an interaction-scoped instance this includes the instance’s private state. For a persistent instance it removes only the expired session’s partition. Immediately suppress the material on every read and commit path, fence the route, cancel its pending questions, approvals, timers, queues and outbox deliveries, then delete in restartable bounded batches. Cover prompts, replies, provider continuations, checkpoints, scoped backlog entries, journal indexes, native Files and every version in their chain, source references, drafts, caches, staged payloads and authorized copies held by a worker. Include generated and annotated images, PDF renditions, synthesized audio, transcripts, alternative text, thumbnails, incomplete renders and provider/container copies. Retire fetch handles immediately and verify owned bytes by store. Revoke raw file access or use mediated custody from the outset for files with a hard access cutoff.

Independent template schedules, another session, separately authorized durable instance tasks and CRM effects already committed have their own owners. Persisting content beyond a leased scope requires an explicit, permitted save or assignment to a named durable destination. Expiry itself cannot promote data. For an uncertain external write, reconcile the existing operation under its independent authority without retaining the chat or sending an expired reply. ### The conversation contract

Specify the following exchange for the selected `agent.protocols[]` entry with `type: "poppy"`, an HTTPS `endpoint`, a `description`, and an appropriate access hint. | Exchange | Expected behavior |
|---|---|
| `POST {endpoint}` | Accept the first message with its caller-generated request ID. Return 201 and the conversation ID for an ordinary successful start. Scope deduplication across the user's requests so repeating an initial submission recovers the same conversation. |
| `POST {endpoint}/{id}/messages` | Accept an ordered subsequent turn with 202. Match path, request ID and body for replay, excluding query parameters from the path. Detect `request_id_conflict` for a reused ID with different content. Keep the check for the conversation retention period. |
| `GET {endpoint}/{id}/events` | Support JSON reads with opaque cursor, pagination and bounded `wait`. Return ordered events, next cursor, `has_more`, `working`, `handoff`, `responder` and `closed`. | `POST …/handoff`, `…/handoff/cancel`, `…/close` | Implement the specified outcomes, including inability to offer a human handoff. Internal specialist delegation keeps the automated responder. A human handoff means a person at the Company. Model closure separately from cancelling an individual Codybot run. |
