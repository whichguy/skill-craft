# Report every E2E run and resulting change

Issue a linked findings-and-changes artifact after every run and improvement iteration, including failed, blocked, incomplete and cancelled attempts. Share the report while generated output remains available for owner inspection. Keep this reporting procedure on the operator side; it adds no fixed check or implementation instruction to the customer brief.

Lead with the actual result and identify what ran. A completed harness qualification, an app-building attempt and independent hosted acceptance establish different facts. When the live builder never launched, say **NOT_STARTED** and keep product outcomes **UNKNOWN**. A passing harness bank does not establish generated-app coverage.

## Retain these facts in each report

| Part | Required evidence |
| --- | --- |
| Run and result | Case, attempt, timestamps, source and installed build, requested model and effort, actual launch controls, served identity when attested, terminal status and exact failed or incomplete stage. |
| Product and test breadth | The independent [seven-journey evaluation](OUTCOME_REVIEW.md), generated definitions versus executions, decisive assertions, layers, environments, provenance and material gaps. Distinguish conditional test skips from missing suites. |
| Findings and changes | For each material finding, cite evidence, disposition, exact change and validation. Classify the change as production ShipLoop, E2E apparatus, generated app or retained learning. Explicitly report **NONE** when the campaign made no production ShipLoop change. |
| Delivery of a change | Exact commits and main/CI receipts. For an accepted production ShipLoop change, record release, publication, installed-host refresh and revision verification before the next hosted iteration. Do not claim another session's release as this campaign's change. |
| Effectiveness and limits | State what a rerun actually establishes. Keep findings open when a fix has only local or fixture evidence. A different brief, model or case does not constitute a matched improvement comparison. Preserve evaluator qualification and generic-gain limits. |
| Reviewable output | App URL when verified, retained generation state, source/deployment identity, original observations and screenshots, report files and retirement disposition. Use unavailable explicitly. A report grants no retirement authority. |

Use a compact change ledger when several findings are parallel:

| Finding and evidence | Exact accepted change or NONE | Validation | Remaining gap |
| --- | --- | --- | --- |
| Link the observation that supports the finding. | Name its category and commit or retained-learning receipt. | Link the checks or exact-generation rerun. | Keep unproven outcomes open. |

Write each report as a new immutable snapshot. Keep the original failures, grades and identities when later fixes or adoption decisions occur. Report missing measurements as **UNKNOWN**, **NOT_RUN** or **NOT_MEASURED**, according to what is missing; never replace them with zero-cost or improvement claims.

Validate the independent evaluation using its documented provenance checks. Check the report's evidence links and source identities. Include a machine-readable change ledger when available. If shared Run Review publication is unavailable, deliver local artifacts and state that publication was not performed. Link the report directly in the owner-facing response and distinguish it from older historical reports.
