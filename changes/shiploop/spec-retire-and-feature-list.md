At the final handoff ShipLoop checks that every requirement ID the run's feature spec (`docs/shiploop/features/<slug>/spec.md`) names is in the living spec (`docs/shiploop/spec.md`) and, when the run's commits reach your branch (an in-place run, or a fast-forward return), removes that file in a commit of its own, `docs(shiploop): retire <slug> spec: checked its requirement IDs against the living spec`; the commit goes back with the knowledge follow-up return, its message gives the recover command and the commit the plan was recorded in, and the branch's history keeps the last committed version (a squash merge drops it). The file stays after a working-tree return or a return that recorded no change, when the living spec lacks an ID it names or names none, when the file has uncommitted changes or was never committed, and when it is a symbolic link; ShipLoop prints one line saying which, and the handoff is never refused for the IDs or the route (a removal or list write that cannot be made leaves the handoff pending with the file's absolute path and the next step). The run's plan, test and outcome records stay. ShipLoop's knowledge commits now also write `docs/shiploop/features/README.md`, a list of the feature folders with commands that find a requirement ID in them (`grep -rlw`, `git log -G`, `git show` of a removed spec, the prepare commit's plan); it is derived from the tree, never makes a commit of its own, and a file at that path that is not ShipLoop's is left alone with a notice. The progress view shows a retired feature spec as Retired with its commit, not as a missing document. A knowledge follow-up return that fails after the retire commit alone no longer replaces the handoff guard's return commands with a dead end. `workspace.return_kind` reads the route of the recorded return.
