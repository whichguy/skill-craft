skill-craft · Plan Orchestrator · live end-to-end testing

What we expected, what happened, and why we changed things

A record of the live tests that check whether ShipLoop and the Plan Orchestrator deliver a real request on a real host. Every verdict here comes from a script reading files on disk, never from a model's account of its own work.

The goal

What an end-to-end test is for

The hermetic suites already prove the orchestration logic without a model: readiness, fan-out and join, locks, retries, crash recovery. They cannot show what happens when a real model, on a real host, has to follow ShipLoop's packets. That is the only thing a live end-to-end test is for.

Each live test answers one question with a pass or fail that a script decides:

Does a real host follow the plan?

The model plans a dependency graph and launches workers only when ShipLoop's packets say so, in the order the graph allows.

Does the product actually work?

The case's own checks run against the committed result: imports, exact outputs, exit codes, error handling.

Does the run survive real conditions?

Session limits, lost hosts, network errors and retries are normal. A run should resume in place and finish without a person.

The method

Every live check is a loop with the expectation written first

An expectation is written down before the run, as a case's checks and its "chain" block in cases.json. The harness grades against it. A gap between expected and observed becomes a named finding, and only a finding justifies an engine change. The change is then verified by rerunning the run that exposed it.

Findings

Where observed differed from expected, and what we are changing

F2 · A step that needed a retry blocks the chain from finishing fixed, awaiting live rerun

Expected
A retried step gets a fresh attempt; once every step is accepted, the chain finishes and the run returns the product.
Observed
All 5 steps accepted and the product passing 7/7 in ShipLoop's worktree, but chain finish refused because the two retried attempts left workspaces that can never be closed. The run paused with no way forward.
Why
A deliberate rule (3e217ad5): rejected work must never be deleted without authority, and the Ask-Agent helper has no "close without merging" option. The rule was right; making it block finish was the defect.
Change
Superseded workspaces stay on disk with their receipts, but no longer hold the chain open. finish completes and lists them under retained_superseded. Nothing is deleted.
Decision
Product: the expectation traces to S-6, and a normal run hits it whenever a step is retried.
Verified by
Five hermetic lifecycle tests now assert the new contract (finish completes; the old workspace, receipt and HEAD are untouched). Next: the kill-and-resume reruns, which retry steps.

F1 · Losing the host mid-chain needs a person fixed, awaiting live rerun

Expected
After the host dies with workers in flight, a fresh session retries those steps and finishes, unattended (E2E spec S-6 and S-14).
Observed
In 2 of 2 runs the fresh session found the workers gone (TaskStop: No task found), could not prove they had stopped, and paused to ask whether it may retry.
Why
Retry requires confirmed_stopped. Native workers die with their host, but nothing records which session launched them, so a later session can never prove it.
Change
Allow retry when a handle is unavailable, recorded as native_status: unavailable. This is safe for code: the old workspace is kept, never merged, and the bridge already refuses any late callback from a retried attempt. Chosen by the owner on 2026-10-03.
Decision
Owner, then product: the behaviour came from a deliberate rule, so the owner weighed it against S-14.
Verified by
Plan Dispatcher scenario S15 (with a mutant it catches) and a chain-bridge test that loses a worker, retries it and finishes. Then the two kill-and-resume runs again.

Making this routine

How expectations are set and mismatches decided

  1. Every expectation names its source. In cases.json: checks_source (the request), chain.source (a spec clause), budget.source. Recovery runs cite S-6 and S-14.
  2. Must and should are separate. Must-level verdicts fail a run. The time budget is should-level: reported, never failing.
  3. Every grade prints expected beside observed. For example: "expected ≥ 3 in flight (S-1, S-2) · observed 4".
  4. A failing run writes mismatch.md. Expected and observed are filled in; the triage questions follow in order: is the check wrong, is it the environment, is it reproduced, does the expectation trace to its source, is it a deliberate rule, would a normal run hit it, does it describe how instead of what.
  5. The decision is recorded. Product, expectation, owner, known limit or environment, with why and what verified it, in LEARNINGS.md. Changing an expectation needs the same evidence as changing the product.
