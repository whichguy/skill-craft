## 1. Ralph loop
Sources: ghuntley.com/ralph/ (Huntley, 2025-07-14, updated 2026-02); snarktank/ralph (**21,939 stars**; `ralph.sh`, `prompt.md`, `prd.json.example`, `skills/ralph/SKILL.md`). Other: frankbria/ralph-claude-code 9,678; anthropics/claude-code `plugins/ralph-wiggum` (in-session variant, see 2).
Mechanisms:
1. **Fresh context = process restart.** `ralph.sh` runs `for i in 1..MAX` and each pass starts a new `amp`/`claude --print` process fed `prompt.md`/`CLAUDE.md`. Nothing carries over except files + git. Why: Huntley says quality clips near 150k of a 200k window; each loop is stamped from the same "stack" (plan + specs). SDLC: the script, not the model, owns the loop; state must survive context loss (matches our main tenet).
2. **Task selection is data, one item per loop.** `prd.json` stories carry `priority`, `passes:false`, `acceptanceCriteria`; `prompt.md` says pick "highest priority" with `passes:false`, implement that single story. The model flips `passes` itself. Huntley's variant: `fix_plan.md`, "choose the most important thing". SDLC: a script should pick the next item and emit the packet (we are stricter); keep the flag flip script-side so the model cannot self-certify.
3. **Story sizing is the real control.** `skills/ralph/SKILL.md`: a story must fit "ONE Ralph iteration (one context window)"; test: describe it in 2-3 sentences; order schema -> backend -> UI. Acceptance criteria must be checkable ("Typecheck passes", not "works correctly"). SDLC: lint step sizes/orders work items and rejects vague exit criteria.
4. **Memory by append-only notes + promotion.** `progress.txt` append-only with "Learnings for future iterations"; a top `## Codebase Patterns` section consolidates reusable ones; nearby `AGENTS.md` gets durable rules. Huntley: tests carry a "why this test exists" doc comment so a later loop can decide delete/modify. Why: later contexts lack the reasoning. SDLC: write rationale into repo artifacts; have a script-owned consolidation step.
5. **Backpressure = gate before commit.** `prompt.md`: run typecheck/lint/test; only commit if green; UI stories need browser verification. Huntley: wheel must turn fast; run only the unit's tests; wire static analysers for dynamic languages; only ONE subagent for build/test (fan-out of validators = "bad form back pressure"). SDLC: test stage must be a script exit code, and serialised.
6. **Stop = sentinel + hard cap.** `ralph.sh` greps output for `<promise>COMPLETE</promise>` (the model declares it after checking all `passes:true`), else exits 1 at MAX_ITERATIONS (default 10). Plugin stop hook (`plugins/ralph-wiggum/hooks/stop-hook.sh`) does the same by exact-match of the promise inside last assistant message, state in `.claude/ralph-loop.local.md` frontmatter; it removes state and allows exit on any parse failure. Why it works: cap bounds cost. SDLC: derive completion from the script (all flags true) not a model-claimed string.
7. **Operator tuning of the prompt ("signs").** Huntley: each observed failure becomes a one-line sign in the prompt (e.g. "don't assume not implemented", search before changing). Archive on branch change (`ralph.sh` copies prd/progress to `archive/DATE-branch`).
What fails (stated by sources): ripgrep false "not implemented" -> duplicate implementations; placeholder/minimal implementations (models chase compiling); spec errors (a keyword defined twice cost a month); in-session plugin variant keeps one context (Huntley's video says "the claude code plugin isn't it"); prompt cannot be copied verbatim; completion string can be emitted falsely (the hook text warns "do not lie").
**Surprise:** the most-starred implementation's anti-drift engine is a markdown prompt plus a JSON flag file; the only enforced parts are the loop counter and a grep for a string.

## 2. anthropics/claude-code plugins (**150,157 stars**)
Files: `plugins/code-review/commands/code-review.md`, `plugins/feature-dev/commands/feature-dev.md`, `plugins/feature-dev/agents/code-reviewer.md`, `plugins/pr-review-toolkit/commands/review-pr.md`, `plugins/hookify/hooks/*.py`, `plugins/ralph-wiggum/hooks/stop-hook.sh`.
Mechanisms:
1. **Tiered model cost via gate -> fan-out.** code-review.md step 1 launches a haiku agent to stop early (closed, draft, trivial, already reviewed); step 2 haiku lists CLAUDE.md paths; step 3 sonnet summarises the PR; step 4 launches 4 independent reviewers in parallel (2 sonnet CLAUDE.md-compliance, 2 opus bug agents with different scopes). Why: cheap models do eligibility/lookup, expensive models only hunt. SDLC: a script-side eligibility check before any expensive review packet.
2. **Validate-then-filter instead of a numeric score (current file).** Steps 5-6: every finding gets its own validation subagent (opus for bugs, sonnet for CLAUDE.md) given the PR title/description + the claim; unvalidated findings are dropped. Different eyes confirm, so the finder cannot self-approve. Note: the current code-review.md has NO 0-100 score; the score lives in `feature-dev/agents/code-reviewer.md` (below).
3. **Confidence rubric with anchored levels.** feature-dev `code-reviewer.md`: 0/25/50/75/100 each defined behaviourally ("double-checked", "will be hit in practice"); "Only report issues with confidence >= 80". Anchors make the self-score comparable across runs. SDLC: filter findings by a script reading the numeric field.
4. **Negative list is the precision lever.** code-review.md "Do NOT flag" + a false-positive list (pre-existing issues, linter-catchable, silenced by lint ignore, style); "If you are not certain an issue is real, do not flag it". Cuts noise more than any reviewer count.
5. **Phase gating by explicit human stops.** feature-dev.md has 7 phases; Phase 3 "CRITICAL ... DO NOT SKIP ... Wait for answers"; Phase 5 "DO NOT START WITHOUT USER APPROVAL"; Phase 4 offers 2-3 architects with deliberately different biases (minimal / clean / pragmatic) and requires a recommendation; Phase 6 asks fix-now/later/as-is. Gates are prose only, no script enforces them. SDLC: our scripts can enforce what these only request.
6. **Agents return file lists; parent reads them.** Core principle in feature-dev.md: explorers return "5-10 key files", the parent then reads those files itself, so context is built in the decider, not trusted from summaries. 2-3 explorers each take a different aspect.
7. **Real enforcement is in hooks.** hookify (`hooks/pretooluse.py`, `stop.py`, `core/rule_engine.py`, `examples/require-tests-stop.local.md`) turns markdown rules with frontmatter into deterministic tool/stop blocks; ralph-wiggum's Stop hook returns `{"decision":"block","reason":<prompt>}` to re-feed the prompt. Hooks are the only hard control point in the plugins.
8. **Prompt hygiene for fan-out.** code-review.md opens with "All tools are functional... Do not test tools" for all subagents, and gives each reviewer the PR intent. Pin the cheap, repeated boilerplate in every sub-prompt.
Limits: review pass counts and model choices are static; no measured precision/recall is stored in the repo; `--comment` posting logic is long prose a model can mis-execute.
**Surprise:** the flagship code-review plugin dropped the numeric confidence threshold in favour of an independent validator per finding, while the score survives only in the feature-dev reviewer.

## 3. anthropics/skills (**180,434 stars**)
Files: `skills/skill-creator/SKILL.md` (+ `scripts/run_loop.py`, `agents/grader.md`), `skills/pdf/SKILL.md` + `forms.md` + `scripts/`, `skills/docx/SKILL.md`, `skills/mcp-builder/`.
Mechanisms:
1. **Three-level progressive disclosure, stated explicitly.** skill-creator: metadata (~100 words, always loaded) -> SKILL.md body (<500 lines) -> bundled resources "unlimited, scripts can execute without loading". Rule: past ~500 lines add a hierarchy with pointers; >300-line references get a table of contents. Pdf: SKILL.md is the quick start and says read `reference.md` for advanced, `forms.md` only for forms.
2. **Description is the trigger, and is deliberately pushy.** skill-creator: "All 'when to use' info goes here, not in the body"; Claude undertriggers, so list contexts and file extensions. pdf/docx descriptions enumerate verbs and artifacts ("mention a .pdf file...", "Word doc", ".docx") and docx ends with an explicit "Do NOT use for PDFs, spreadsheets". Tune it empirically: `scripts/run_loop.py` splits queries 60/40 train/held-out, runs each 3x, up to 5 revisions, picks best by TEST score to avoid overfitting.
3. **Bundle scripts so the model doesn't re-derive them.** pdf has `check_fillable_fields.py`, `extract_form_field_info.py`, `fill_fillable_fields.py`, `check_bounding_boxes.py`; docx has `validate.py` (XSD checks, `--original`, `--author`), `merge_runs.py`, `accept_changes.py`. The body names each script with exact flags and when to run it.
4. **Branch-by-detection ordering.** `pdf/forms.md`: "CRITICAL: You MUST complete these steps in order. Do not skip ahead to writing code." Step 1 is a script that classifies the file (fillable or not) and the doc routes to a different section. A script's output chooses the path, not the model.
5. **Validators as a verify loop with a visual check.** pdf: `create_validation_image.py` / `check_bounding_boxes.py` verify annotations before filling; docx: validate after edit, with the redline check reporting text changed without `<w:ins>`/`<w:del>`. Verification is a script run with an artefact, not a self-assessment.
6. **Gotcha lists beat theory.** docx SKILL.md is mostly concrete traps ("never `SOLID`", "PageBreak must be inside a Paragraph", "Never use `\n`"), each a past failure encoded in one line. Same idea as Ralph's signs.
7. **Evaluate skills against a baseline.** skill-creator: spawn with-skill and without-skill (or old-version snapshot) runs in the SAME turn, grade via `agents/grader.md` with fixed `grading.json` fields (`text`,`passed`,`evidence`), prefer scripts over eyeballing for assertions, aggregate with `aggregate_benchmark.py`, human reviews in `eval-viewer`. Writing guidance: explain why instead of heavy MUSTs; generalise rather than overfit to the test prompts.
8. **Domain split by reference file.** One workflow SKILL.md + `references/aws.md|gcp.md|azure.md`; model reads only the relevant one.
**Surprise:** Anthropic's own authoring guide tells authors to make descriptions "a little bit pushy" and to prefer explaining reasons over capitalised MUSTs, while its production pdf/docx skills rely on exact flags and script-first ordering.

## Cross-cutting for a script-driven SDLC harness
- Put the loop, selection, caps, completion decision and test gating in scripts (Ralph's enforced parts are only count + sentinel; ours can be stricter). Keep model judgement for single bounded steps.
- Independent validators + anchored confidence + a "do not flag" list make reviews precise; self-scoring alone is weak.
- Give each packet exactly the files/state it needs; durable rationale goes to repo files because the next context starts empty.
- Descriptions trigger skills; scripts carry determinism; reference files carry bulk. Test triggers and outputs against a no-skill baseline with a held-out set.
