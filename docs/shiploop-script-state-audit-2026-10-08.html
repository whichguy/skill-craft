The inspected scripts select successors, validate callbacks and issue detailed action packets. Tactical fixes harden transaction validation, truthful error recovery and coherent status reads. A complete linear JSON transaction history remains a design decision.

Proposed JSONL history AWAITING DESIGN DECISION

Recommendation: retain state.md as authority and add one append-only JSON Lines transaction history. Making the log authoritative would be a broader migration of hydration, recovery and every state consumer. No format migration is included in these tactical fixes.

A concrete follow-on contract should use a versioned JSON object per line: sequence, transaction ID, UTC timestamp, run ID, before/after revision and cursor when applicable, affected paths, and content hashes. Distinguish durable transaction intent from successful application; an intent alone must never be reported as completed work. Generic evidence-only transactions may have no navigator revision.

Keep the same transaction ID in the recovery manifest. Under the existing exclusive lock, validate the retained prefix and record intent durably before target writes; after all targets are durable, record application before removing the pending manifest. Recovery must recognize identical IDs without duplicate logical events. A torn final line needs an explicit recovery rule tied to the pending manifest; corruption inside the retained prefix must stop recovery. Neither a malformed record nor a missing timestamp should silently become an empty history.

Scanning the whole history on each transition is a reasonable first implementation under the stated O(n²) allowance. It avoids an index as a second authority. Retain existing chain history until an explicit migration preserves all events; do not claim that a newly enabled log reconstructs earlier transactions or makes Git/remote side effects atomic.

This is a proposal, not an implemented or tested log. JSON Lines gives each record an explicit newline boundary; repeatedly appending ordinary JSON documents is not a valid single JSON document. Journaling also requires ordering and synchronization, not just a format change. Sources: JSON Lines specification, Python JSON framing limits, SQLite atomic commit and filesystem assumptions.

Portability and remaining limits

macOS and Linux are the declared platforms. The core storage uses the Python standard library, POSIX locks, same-filesystem replacement and file/directory synchronization. Git handles repository operations; implementation chains bind a Node.js helper. Native Windows and network-filesystem crash durability are not established. Local runtime contract; Python locking availability and portability.

Within one transaction, names must remain distinct after Unicode normalization and case folding on every host. This intentionally rejects some combinations that a case-sensitive filesystem could store, such as case-only variants. Existing safe in-root symlink paths remain usable when their destinations and dependencies do not conflict.

save() relies on callers hydrating under the run lock; it does not independently enforce compare-and-swap against a saved revision. The normal CLI follows the locking contract. A future event-log design should make the expected previous revision explicit. Filesystem recovery also cannot by itself roll back Git commits or external actions.

Exit 0 is command-specific. For example, Backchain structural validity and workflow completion are separate receipt fields; a valid plan can still be incomplete. This audit preserves that distinction instead of treating every successful process as completed delivery.
