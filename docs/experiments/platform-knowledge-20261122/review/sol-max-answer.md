## 1. Is the intention sound?

Yes, for **specific platform facts that change a decision or the test that proves it**. The strongest example is a hosted feature whose metadata is deployed but whose intended user cannot open it. The card distinguishes presence, visibility and access by the intended role. That distinction can change the work order and the acceptance check. The October review describes a Salesforce delivery where the tab was hidden and the owner granted access by hand. The same review reports good query, DML, CPU and heap decisions in the two deliveries it examined. Missing guidance is a plausible explanation for particular failures. The record gives little reason to treat it as the general bottleneck. ## 3. Card or wiki

Keep headings or keyed entries **inside one file** while they are easy to review. The navigator can extract three entries from a 14,000-character file for the same model-facing cost as extracting them from three pages. Split when sections have independent owners or release cycles, or when measured lookup cost falls at comparable pickup and decision quality. For a model-pulled route, count the visible index, lookup calls, returned pages and repeat reads across cold stages. The comparison is against the relevant excerpt as well as the whole card. A fixed word threshold would miss those costs.

A deterministic lookup needs **a platform ID, an affected boundary or capability ID, the decision phase, an applicable version or environment predicate where it matters, and a stable entry ID**. The concern ID is useful for placement in ShipLoop. `when it applies` written in prose is useful editorial context and still requires judgment. For machine selection, use facts already established for the target or simple predicates over declared evidence. Where the evidence cannot choose, preserve the unknown. Once entries are selected, a command can take the exact IDs and return just those entries. Multiple targets can share an entry without duplicating it.

Borrow the wiki suite’s **provenance, cited updates, generated index, and lint for broken links, stale material and contradictions**. Defer a separate authoring skill until ingestion and upkeep become recurring work. The supplied plugin’s runtime does something different. `wiki-query` reads the full index and asks the model to select up to eight pages. `wiki-load` asks it to choose matches, can read seven full pages and updates access metadata. The supplied notifier sends optional pointers and explicitly says previews were removed. That corrects the journal’s description of this copy. There is no reason to carry these Claude-specific hooks and mutable counters into the two harnesses to test three facts. ## 5. The cheapest credible test

The proposed three-arm run changes too many things together. D2 changes detection and placement. D3 changes the content packaging, tool action and response duty. A difference would be hard to attribute. Use this sequence.

1. **Start with zero model calls.** In the original archives, find plans with an applicable fact, an observable decision gap and a consequence. Check what reached the planner before the draft. Render the released and proposed packets from identical upstream records and diff the actual text and placement. Include one mixed or unrelated target where the block should be absent. `graph-dry-run` can exercise packet shape with synthetic declarations. It cannot establish pickup. The bundle supplies the count rows but lacks the archived plans needed for the retrospective decision audit. [Dry-run contract](/private/tmp/review-eyzTGR/skills/shiploop/references/graph-dry-run.md:1) · [Archive fields](/private/tmp/review-eyzTGR/docs/experiments/platform-knowledge-20261122/card_reads.py:111)
2. **Run a four-session screen.** One known applicable case, released versus inline, on Sol medium and Sonnet medium. Freeze the request, scoped repository, target and upstream artifacts. Enter through the real planner and host transport. Use the same review settings and save both the first submission and the accepted plan. If a reproducible checkpoint is unavailable, use paired native runs with a frozen fixture and stop at plan acceptance. Four sessions screen exposure and decision plausibility. Repeat on fresh matched cases and include repeated controls before drawing an adoption conclusion.
3. **Compare one exact-section lookup if the fact earns its place.** Give it the same content and comparable prominence as the inline arm. Keep the decision duty the same. This tests pull versus push. Test automatic selection separately on explicit greenfield, existing mixed-target and inapplicable cases. Ratchet F51 gives the lookup arm a fair shot. All nine command runs delivered every nonblank line of one roughly 9.7k-character packet when the prompt named the command and asked for its full output. The study covered one short spec task. In the real ShipLoop sample only 17/26 plan packets showed at least four fifths of their unique duties, and 4/26 showed under a third. [Ratchet F51](/private/tmp/review-eyzTGR/docs/ratchet-pilot-journal.md:3622) · [Real plan exposure](/private/tmp/review-eyzTGR/docs/spec-elaboration-journal.md:3232)

**Register the decision rule before starting.** Require confirmed exposure of each applicable treatment fact **before the decision**, a repeatable gain in at least one predeclared material decision or discriminating check on **each** driver, and zero new critical factual, scope, privacy or other safeguard regressions. Calibrate the required repeatability with baseline repeats and blind regrades. Treat a valid alternative or a consequential unknown with an appropriate probe as a good decision. A card name, a copied sentence and a completed row are exposure or compliance signals. A pass requires an actionable choice or check. For example, credit a plan that distinguishes feature visibility for the intended user from metadata presence and commits to a check that could fail when visibility is missing.

Have the checklist author work from the request, fixture, target contracts and credible failure evidence **blind to the card and treatment wording**. A second reader should check applicability and alternatives before the runs. A checklist written from the card measures reproduction of the treatment. Blind the judges to the arm where possible and strip any lookup receipts. Record per-fact and generic decision outcomes, actual text received per stage before draft and review, extra reads, total input and output tokens where available, wall time, retries and blocks. Keep all assigned runs in the main comparison and use delivered-only results to diagnose the mechanism. A stopped Sonnet run can lack reported spend. A bench can verify markup, measurement and scoring. Its pickup rate is a poor forecast for live runs. The **116–120/120 versus 0/35** comparison was for one main spec guide, with an advertised index and different workspaces. A short lookup placed in live duties deserves its own test. If the inline facts reach both authors and the decisions fail the registered bar, keep the released route. If the plans improve, take a matched pair through the affected downstream check before changing the default. That last rung tests the owner’s delivery goal.
