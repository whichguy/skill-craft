## 2. Proposal A

**A1. Keep the entry format as an authoring convention.** A stable ID, concise fact, decision, and discriminating check are a good start. A reusable entry also needs a source revision, affected boundary and phase, applicability conditions, and a recheck trigger. Distinguish a binding constraint, an evidenced default, and a question to investigate. Put deployment-specific facts in the project’s `environment.md` with target and evidence. Lint the bundled material before release. The current `entry_lint.py` checks shape and, in sourced mode, local file and quote presence. It cannot certify truth or applicability. `_platform_planning_lines()` reads the entire section body, ignoring entry IDs, applicability, and even the lint. Adding longer provenance there would add it to every matching packet. Keep the rendered excerpt short and give it a source locator. [Entry lint](/private/tmp/review-sh5Pjk/docs/experiments/platform-knowledge-20261122/ingest/entry_lint.py:151) · [Planning renderer](/private/tmp/review-sh5Pjk/skills/shiploop/scripts/shiploop_navigator.py:6371) · [Knowledge-home ownership](/private/tmp/review-sh5Pjk/skills/shiploop/references/project-knowledge.md:511)

**A2. Select guidance for the affected target.** `platform_cards()` currently unions every literal card path in a Markdown section with every matching repository glob. It loses the target-to-card association, can recognize a path in a denial, and cannot let a reasoned `none` override a glob. `_applies_patterns()` takes the first backticked text on a bullet. `_repository_matches()` accepts any matching file, including untracked files, filters excluded names after the glob traverses, and has no resolved-path containment check. `package.json` proves neither a server nor Express, and this fixture actually uses `node:http`. The same selector also feeds `_platform_testing_lines()`, so enabling it changes testing guidance outside discovery and plan. Keep planning eligibility independent of that consumer until its change is separately justified. [Candidate selector and testing consumer](/private/tmp/review-sh5Pjk/skills/shiploop/scripts/shiploop_navigator.py:6269) · [Node fixture](/private/tmp/review-sh5Pjk/test/shiploop_e2e/fixtures/pk-nodeplain/src/app.js:1) · [Coding guidance’s selection rule](/private/tmp/review-sh5Pjk/skills/shiploop/references/coding-guidance.md:7)

For a pilot, start with an explicit target or one strong marker in an already identified package root. A production card could declare **positive predicates over bounded evidence**, with all-of and any-of only where needed. An Express entry could require an Express runtime dependency **and** evidence that the affected service starts through it. A Salesforce metadata entry could require an in-scope `sfdx-project.json` and a matching package path. Org access still needs org-specific evidence. Restrict reads to the effective worktree and relevant source or manifest paths. In a mixed repo, attach each match to its package, target role, and affected boundary. Include multiple scoped matches when the change crosses them, deduplicate shared entries by ID while retaining scope, and surface conflicts or absent evidence as unknowns through the existing discovery route. Lexical order should decide display order only. For greenfield or remote-only work, use the explicit request or discovered target evidence. This preserves discovery’s ownership of target selection and authority.
