## What the round showed

The rule, as you last saw it: in a clean copy of the returned result, release-verify runs the consumer checks and
then each regression command of the last work item that records one (where no check is that command), and holds each
of those commands to a count. The count was the latest passed run of that command under a done action, read from the
run's records.

1. A wrong refusal. One delivery's `npm test` ran 148 tests in the clean copy, all passing, against a recorded 152.
   After the run that recorded 152, the builder (at release-plan) moved six fixture files out of `test/`, where the
   test runner had been counting each as a test, and two system tests had been added: 152 - 6 + 2 = 148. The work
   area, as returned, ran 148 too. The count was an earlier tree's. The refusal cost a corrective work item nobody
   asked for and about a quarter of the run.
2. An uncommitted return, in the same delivery, by a separate fault. The moved files' deletions were never committed,
   so the candidate had a tracked change at the return, the return applied a working-tree delta in place of a
   fast-forward, and the user's checkout holds the delivery uncommitted. Cause, reproduced in an empty repository:
   `commit_paths` stages its paths and then lists what is staged with `git diff --cached --name-only`, which names
   only the new path of a move (rename detection); the path-limited commit then leaves the old path's deletion
   staged. `_stageable` then drops a staged deletion (it is in neither the checkout nor the index), so no later
   commit takes it either.

The other two deliveries were accepted correctly, one of them with a consumer check of 3 tests and the full suite of
159 added and run by ShipLoop.

## The two corrections

A. The count is measured, not looked up (`work_area_counts`). When release-verify is about to run its commands in the
   clean copy, ShipLoop first runs each of the last work item's regression commands that is among them (added, or
   written as a check) in the work area, with the caller's environment, and holds the clean copy's run to that count:
   `too-few-tests` when the copy runs fewer, `uncounted` when the copy's count cannot be read and the work area's
   could. A command that fails or cannot be counted in the work area at that moment has no floor; its exit code in
   the copy still judges it. `latest_counts` and `copy_floors`, which read the run's records, are removed. The record
   gains `work_area` (those runs). The packet's list marks such a command "(floor: its count in the work area)".

B. A moved file is committed whole. `commit_paths` passes to `git add` only paths that are in the checkout or the
   index, lists staged changes with `--no-renames`, and `_stageable` keeps a path that is in HEAD alone (a staged
   deletion). `commit_leftovers` and one other listing in `shiploop_workspace.py` also use `--no-renames`.

Checked so far: the refused attempt, replayed on its returned tree with a work area at that head, now passes (148 in
the work area, 148 in the copy, floor 148); the unit class (20 tests), the real-gate class (9 tests, three of them
for this rule: a short count refused and repaired through a corrective item with a replacement command; a missing
install step repaired through send-back; an ordinary delivery accepted); 16 mutants of the rule, all caught; the
moved-file test fails for both forms of a move (left as it is, staged first) without correction B and passes with
it. A batch of 24 suites and the gate on 28 saved release checks are running as you read.
