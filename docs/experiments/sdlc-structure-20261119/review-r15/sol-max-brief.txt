WHAT HAPPENED. Two blind judges a pair read 16 deliveries (two small cases, two drivers, medium and high effort); I then ran every claimed fault against both sides of each pair. No case check and no delivery's own test had caught any of the 14 confirmed faults. Tracing them into the run records gave three things about ShipLoop itself:
1. release-verify runs the model-written `consumer_checks` in a clean copy of the returned tree with no Git history. 15 of 16 deliveries named the whole suite. One wrote `SKIP_ROLLBACK_TEST=1 npm test`, recorded as suite `check`: a switch its own tests read to skip the 9 tests that need the repository's history. The gate passed; the recorded regression command was `npm test`.
2. The plan fills a row for each of fifteen concerns. None asks what the previous release does with data the new one writes, or how the new release is entered again after going back. Six of eight deliveries of the ticket case move a due time from +4 h to +168 h after a rollback and return, although the request says a due time is set once and a later change of priority does not move it. The two that keep it (one driver at high effort) built a backfill option that takes the copy saved before the rollback. Note: all eight products document the rollback, and the four Sonnet ones document that a return re-stamps due times. So the miss may be a decision, not an omission.
3. Tests that the judges called brittle or out of scope confirm ShipLoop's own step-plan criteria marked `executed`: a test that runs the whole suite again ("the suite runs under node --test, prints every TC ID"), a count of test files ("the suite is discoverable"), a test of the wording of docs/operations.md ("the rollout and rollback order is documented, settling A2"), a test of package.json against the changelog. The step-plan duty already says documentation is `searched`. Two gates push the other way: a criterion that settles an open plan assumption must be `executed`, and each executed criterion needs a focused test ID of its own. Six of eight Sonnet deliveries carry at least one such test; none was reported for the other driver. Some tests the judges also called scope execute a documented operator command or replay the README against the real server; I do not want to discourage those.

PROPOSED CHANGES (the owner said "Yes, do these"; the design is mine and open).

C1. The clean-copy gate. At release-verify, a consumer check that is a recorded test command (equal once leading NAME=value settings are removed from both) is held to that command's count: it must run at least as many tests as the latest accepted work-area run of that command (the latest, not the most, so a later consolidation of tests does not dead-end). Fewer becomes `too-few-tests`, with the add-work exit that _copy_refusal already names, and the packet states the rule before it refuses. Earlier decision to weigh: commit 53ab8b788 (A5) left the outer stages without a floor because they have no revise to lower one and a union across items would dead-end on a legitimate consolidation; its audit marked it "open, needs an owner decision".
 Alternatives I rejected, to be challenged: (a) ShipLoop itself runs the recorded regression command in the clean copy: it would fail for any project whose dependencies are installed in the work area and not delivered, unless a consumer check happened to install them; (b) refuse at release-plan any consumer check that sets a variable in front of a recorded command: it would refuse harmless settings such as TZ=UTC; (c) wording only.

C2. A sixteenth concern row, id `rollback`: "going back to the previous release and coming forward again: what each release does with data the other wrote". A row to fill (applies yes with decision, anchor and owner stage, or no with a reason), because another study in this repository found that a planning question is answered only when the plan has a section to fill. Acceptance test planned: the ticket case on the candidate, medium effort on both drivers; shown to work if at least 3 of 4 new deliveries keep the due time across a rollback and return (quality_checks/rollback.js), where 0 of 4 medium ones did. If it is not shown, the row is not shipped.

C3. Step-plan duty 3 and the test duty: say that a test which only reads a file's text (a document, the changelog, package metadata) or counts files is a search, so its criterion is `searched` with a `check` row and no such test is added to the product's suite; and that "the tests exist and run" is confirmed by the regression row itself. Tests that execute the product, including documented commands, stay `executed`. Measured by a count over step-plan criteria and over delivered test files, before and after.

C4. The E2E cases gain round 13's checks as observations that do not change pass or fail: the return after a rollback (ticket case), odd names and ids (expenses case), the delivered suite started from another folder with a clean environment. They were run on 16 independent builds, with passing and failing examples of each.
