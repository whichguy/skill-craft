### Mechanism and §5.5

1. **An answer can reach a review whose work has already ended.** `current_stage()` still returns `test-strategy` or `plan` while `sequence_stage()` returns `improve`. The producer’s `apply()` has parked its draft in `active_improve.seed_result`. The import branch in `dispatch()` skips the ordinary note hold and imports the seed or a full `--final-result`. If a note arrives after the child’s receipt is complete, a new gate can refuse that import even though `_improve_pass()` refuses another pass and `_improve_restart()` only admits specific restart cases. Adding text to `_render_improve()` leaves that dead end. The smallest first version closes intake when the producer’s `done` draft is successfully submitted and makes the review revalidate the answer IDs carried by that draft. If the owner wants intake through final import, refresh the actual child handoff before the next pass and define an unattended route to re-review a completed child that missed an answer. An import refusal must name the full replacement result path and the Improve callback with `--final-result`, as `_next_step()` already does for other gates. 2. **A held note can be applied without being delivered, and a delivered note can still be unapplied.** `to_hold()` checks both `packet` and `held`. `mark_held()` writes only `held`. `deliver()` reads only `packet`. If `complete` first sees N3 through `NotesHeld`, the retry can successfully apply N3 while the ledger leaves it open and the next packet quotes it again. Conversely, `dispatch()` calls `deliver()` whenever `apply()` changes state, including when it parks a review seed or accepts `blocked`. An answers gate that uses `undelivered()` can then miss N3 at import or after resume. Derive application from a validated `answers` row in the current accepted `done` result and use that projection to stop presenting the typed note as open. Keep the existing delivery semantics for ordinary notes. For an unseen eligible answer, the hold must print its binding and the required edit. `check` prints the note and still evaluates the draft. If `mark_held()` cannot save, the answers refusal must give the note path and repair instructions so the host can proceed without a successful write to `shown.json`. 3. **The three gate sites fit one validator, with different inputs.** In `_evaluate()`, validate a fresh producer’s `done` draft on both `check` and `complete`. In `dispatch()`’s `matching_yes` branch, rerun the cheap answer check before `take_check()`. A yes issued before the note arrived cannot establish that the draft addresses it. At review import, validate the effective result against the review’s required answer IDs and the live entry. A replacement result can drop a seed’s proof or leave a quote that the review has edited away. Keep previously accepted replays idempotent, including a producer retry while its seed is parked. At admission, require the submitted rows to match the expected note IDs exactly, with one row per ID and the bound requirement. Checking only that each open note has a match leaves room for extra rows that claim credit for ordinary, late, or unknown notes. 4. **Define the cutoff at one inbox read.** `shiploop_protocol._main()` routes `note` outside the run lock, and `owner_notes.write()` publishes the finished file with `os.link()`. A note can land between `to_hold()`, the gate, and the state save. Read the inbox once for each fresh admission attempt and pass that same set to the hold, gate, and settlement. Tell the requester that eligibility depends on whether the answer was visible at that admission read. Arrival before the callback returns is a wider promise. The same race exists at terminal output. 5. **A displayed row number can silently bind to the wrong decision.** `defaults.recorded()` reads the currently projected spec. A requester can answer row 3 from spec A after reconcile has issued spec B with a different row 3. Copying the question and default at write time preserves whichever row the CLI picked. Put the spec action ID in the displayed selector and in the note, alongside the row number. Validate the source row and the live target before writing a bound note. The store deliberately permits older `defaults` rows with arbitrary text keys, and the target may already be absent or retired. Give a specific refusal in those cases. A note encountered during the rerun of `research` or `spec` did not necessarily arrive after plan acceptance. ### Requester behavior and §5.1–4

9. **§5.1. Pilot at `test-strategy`, with intake closing at its producer submission.** That is where the list first appears and where the earlier successful plain-note corrections happened.
