**What the service does now**
- **Due time:** a ticket's `due` is its creation time plus 4, 24, 72 or 168 hours (urgent, high, normal, low). It is set once and never moves when the priority or the hours change.
- **Changing the hours:** set `RESPONSE_HOURS_URGENT`, `RESPONSE_HOURS_HIGH`, `RESPONSE_HOURS_NORMAL` or `RESPONSE_HOURS_LOW` and restart. The new hours apply to tickets created after that.
- **Overdue list:** `GET /tickets?overdue=true` lists only open and in-progress tickets whose due time has passed.
- **Production file:** the first start of the new release gives every ticket in the data file its due time and saves the file.
- **Switch:** `due` and `overdue` appear only with `DUE_TIMES=on`. Until then the service answers as 1.4.0 does, even though the file already holds the times.
- **Rollback:** the data file stays version 1. I started the real 1.4.0 code on the file the new release wrote and it listed every ticket. It drops the due times when it saves, and the new release fills them in again at its next start.
- **Docs and release notes:** README, API doc, operations doc, decision 0009 and CHANGELOG 1.5.0.

**Choices made for you** (the report lists each with its reason)
1. **Hours are environment variables.** A bad value stops the start with a message naming it.
2. **`overdue` accepts only `true` when due times are on.** Any other value gets a 400, and a ticket due exactly now counts as overdue.
3. **The first start backfills and saves the file,** even with `DUE_TIMES` off, so the file holds the times before you switch on.
4. **After a rollback to 1.4.0 and a later roll-forward,** the times are recomputed from the hours in force then. They can differ from before if the hours changed in between.
