### R-5 Existing tickets are backfilled and keep their due time
Nobody prepares the data file by hand: when the service starts with DUE_TIMES `on`, it gives every ticket without a `due` one (created + hours(priority), hours as set then), saves the file, and then serves; it never refuses to start because due times are missing. Decided by the requester (owner note N1, 2026-11-22), replacing the spec's earlier default of backfilling before switch-on. Basis: request S6.
- Positive: a v1 file written by the 1.4.0 persistence (fixture) holds four tickets created `2025-09-01T08:00:00.000Z`, one per priority; after `TicketStore.open` with dueTimes on and default hours the in-memory tickets and the file on disk hold due `...T12:00`, `2025-09-02T08:00`, `2025-09-04T08:00`, `2025-09-08T08:00` for urgent, high, normal, low; a second open with `DUE_HOURS_*` all 1 leaves them unchanged and the file's bytes (apart from `savedAt`) unchanged. Confirmed by persistence/service test.
- Boundary: with dueTimes off, opening the store backfills nothing and leaves the file's bytes unchanged; a `due` already in the file is kept and rewritten as is on later saves. Tickets that already have `due` are untouched; backfill writes no audit entry and no outbox event and does not change `updated`.
- Failure: a `due` in the file that is not a time refuses the file with the record named (like other checks); a file whose tickets lack `due` never refuses the start.
- The CLI never writes: it shows due only for tickets that hold it.
