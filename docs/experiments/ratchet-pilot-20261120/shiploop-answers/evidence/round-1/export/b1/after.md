### R-6 Existing tickets get due times, once, from their own creation time and priority
Basis: request "tickets already in the production data file get due times too ... and keep them", and the requester's decision of 2026-11-22 (note N1): nobody prepares the data file by hand; when the service starts with DUE_TIMES `on`, it gives every ticket that has no due time one, from that ticket's own creation time and priority, saves the file, and then serves. It never refuses to start because due times are missing. The requester decided this; it is not a default of the spec.
- Positive: a data file of 1.4.0 tickets (no `due`) started with DUE_TIMES=on: before the first request the file on disk has `due` = created + the hours in force for every ticket, and the responses show them; a second start changes no `due` and does not rewrite the file.
- Boundary: with DUE_TIMES not `on` the start does not touch the file (it answers as 1.4.0 does); tickets created by the new release always get `due` at creation (R-1) whatever the flag. The file is saved at start only when at least one ticket lacked `due`; a file without `due` on its tickets is valid input (that is what 1.4.0 wrote). The backfill belongs to the service's start, so bin/tickets.js and scripts/weekly-report.js, which only read, never write the file. A ticket that already has `due` is never recomputed; a file with no tickets or no data file is unaffected. Backfill writes no audit entry and no outbox event and leaves `updated`.
- Failure: a ticket `due` that is not a time makes the file refused with a message naming the record, like every other record check.
