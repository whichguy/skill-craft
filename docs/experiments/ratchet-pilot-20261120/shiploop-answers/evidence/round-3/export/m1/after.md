### R-5 Existing tickets are backfilled and keep their due (S6)
REVISED 2026-11-22 by owner note N1 (run owner, 21:47Z); the start-time backfill below is superseded, kept as history, and W2 implements the revision. Backfill is an explicit operator step: the operator stops the service and runs a separate command (`node bin/backfill-due.js --data FILE`, or DATA_FILE) that gives every ticket without `due` one, from that ticket's own creation time and priority with the configured hours, and saves the file; it prints the count and changes nothing else; a ticket that already has `due` is never recomputed, so a second run changes nothing. The service does not backfill when it starts. Started with DUE_TIMES=on while any ticket has no `due`, it refuses to start (exit 2, message names the command and the count). Started with the flag off it starts as today; tickets it creates still get `due`. Confirmation (replacing the start-time example below): starting the service on the example file leaves it untouched; flag on with a ticket lacking due refuses and names the command, flag off starts; the command fills the three tickets of the example with the same three values, audit, outbox and updated unchanged, and a second run reports 0 and changes nothing.

Superseded 2026-11-22: When the service starts on a data file (a store opened with persistence) whose tickets lack `due`, it sets due from each ticket's own created time and current priority with the configured hours, and saves the file at once at start. A ticket that already has due is never recomputed. Backfill changes nothing else: `updated`, audit and outbox stay as they were. The command line and weekly report open the file without persistence and never write it, so they never backfill. With no data file there is nothing to backfill.
