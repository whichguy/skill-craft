THE IDEA UNDER REVIEW (the repository owner's, stated as an open question, working title "ShipLoop 2"):
ShipLoop today elaborates a request, writes a spec, a test strategy and a plan, cuts the work item into steps, and builds step by step. The owner suspects the step breakdown is not what makes a delivery correct. Alternative: elaborate the request into a well-understood spec; derive test cases from the spec; then take ONE shot at the whole request, with the duties of today's fixed stages (lint, documentation, tests and so on) folded into that one prompt; run the tests; the failed tests and unmet criteria become the next task; repeat as a full iteration cycle until nothing fails. Possibly no planning stage at all. Every shot still passes through the inner-loop gates (lint and the rest). The owner says it depends on the spec being very well understood and the tests enforcing the spec or its implied intent, and asks: is this a good idea, and what test scenarios would show whether it works, perhaps as a small separate skill used as a simulation environment.

MY DRAFT SHAPE (attack it; it is a draft, not a decision):
spec (kept, with its review) -> acceptance tests written from the spec by a session that never sees the product code, then a second look that is handed every spec condition; the tests are frozen (the builder cannot edit them) -> one build packet with all duties folded in -> script-run gate: lint, frozen acceptance tests, the existing suite, the seeded-fault check -> the script writes the list of failing checks, each with the spec clause it pins, and that list is the next packet -> repeat until the list is empty -> one end-of-work review -> release stages unchanged. No plan, step-plan or test-spec stage; no per-step review. A shot that turns a passing frozen test red is refused.
