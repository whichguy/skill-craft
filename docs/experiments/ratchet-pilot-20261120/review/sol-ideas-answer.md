## B. Where breadth pays

| Stage | Where I would spend the attention | Who should settle it |
|---|---|---|
| Intake | A choice that changes the outcome, a promise, or the cost of reversing the build. Use ShipLoop’s routes to distinguish what can be inspected, tried, provisionally chosen, or asked. | The intake session finds and ranks the forks. A requester settles material preferences that evidence cannot resolve. |
| Specification | A behavior the change requires, a public promise it touches, or two plausible readings that would produce different results. Ground each in a request span, an existing contract, or a reproducible observation. | The writer makes the initial pass. A fresh reviewer is useful when a draft has already committed to one reading and the stakes justify another look. |
| Plan | Interactions with the actual proposed design, such as shared state, retry, migration, or rollback. Pick the pertinent concerns after seeing the approach. | The planner can settle implementation choices and propose reversible defaults. A change to what a user is entitled to needs stronger authority. |
| Test design | Find an input that separates the promised behavior from plausible wrong behavior. Use both a permitted and a refused path when a guard changes. | A test designer proposes the distinguishing observations. A script verifies execution and runs the comparison against frozen correct and incorrect products. |
| Built-product review | Find a violated promise that the delivery’s own spec and tests may have agreed to overlook. Exercise the public boundary from the original request and the base behavior. | An independent reviewer proposes and runs probes. The product or a trustworthy execution trace supplies the evidence. |

The distinction I would put at the center of this work is **a missing fact versus a missing decision**. A repository can show which states currently permit an edit. It cannot show whether a requester wants a new operation to diverge from that rule, unless a contract already settles it. Conversely, a real requester should rarely have to answer a question a quick repository check can settle. The costs differ too. A missed obligation can ship a regression. An invented obligation can force work and reject correct implementations. Leaving a consequential point open avoids binding a guess, but it has a cost if an irreversible decision is buried in a build report. Choose the route and the threshold for asking based on the consequences of a wrong answer. [ShipLoop’s intake routes](/private/tmp/review-fKyfPC/texts-under-test.md:200) · [Ratchet’s current open-point handoff](/private/tmp/review-fKyfPC/texts-under-test.md:99)

A requester can answer “Should reminders repeat until the requester replies, or should each waiting episode send at most one?” They can evaluate the difference in message volume. “What are the state and timing rules?” hands them the analysis. A good intake question supplies the concrete fork, what it changes, and whether a reversible default lets other work proceed. The released intake already contains the right fields for much of this. I would test whether an actual consequential answer survives into a named acceptance observation and the plan. Merely classifying the question as `person` has little value if the build then silently chooses. [Intake duties and defaults](/private/tmp/review-fKyfPC/texts-under-test.md:203)

For question selection, I’d use the **request** to generate intent forks, the **repository** to generate preservation questions, the **proposed design** to generate operational questions, and **past defects** to generate failure patterns. Past failures are especially useful when abstracted to a mechanism, such as “a widened guard wrongly rejects a nearby legal state,” and evaluated on a different case. Reusing the exact known failure as both a hint and an exam would answer whether the agent can follow a hint. The catalog gives these questions a vocabulary and a place to look. The evidence for asking one should come from the particular change.

## C. Experiments ranked by information per dollar

These are proposed screening rules. I would freeze the input revision, target behaviors, valid alternatives, harm criteria, cost ceiling, and promotion rule before each run. For model comparisons, use at least three draws per arm, interleave them by case at the same model and effort, and match output shape and work budget when testing question content. Keep the held-out probes and their expected results outside every model session. Report item-level outcomes, delivery failures, and genuine regressions separately from aggregate net scores. The estimates below assume the harness and archived artifacts described in the journals are available.

### 1. Replay the gate on known-good and known-bad inputs

Replay existing suites with execution observed outside the child process. Use an independently valid alternative product to check whether a failure comes from the product, the assertion, or how the test reaches the product.

- **For the smallest version,** use the archived broken regression fixture and one valid fixture for the old-suite invocation, then replay one archived due-times suite against its own build and the alternate reference. Repeat the replays in isolated, equivalent copies with the needed Git history and canonical paths. This costs no model calls and should take minutes once the copies are ready.
- **Measure** discovered and completed checks, their results, and which invocation caught each defect. The ground truth is the independently known passing and failing behavior. A successful exit with no expected checks executed is its own outcome. For the overlay, a small adapter for each documented configuration interface lets the same assertion exercise both valid products.
- **Change the gate** if it accepts a known failing fixture without executing the expected checks, or if a stable valid-product rejection disappears when only the driver binding changes. A change in word-match attribution alone leaves the gate decision where it is. The main threat is an adapter tailored to pass the sampled products. Check that the same assertion still rejects the known bad one. Apply the execution rule generically in ShipLoop and handle runner-specific behavior in the relevant adapter. [Nested test reproduction](/private/tmp/review-fKyfPC/pilot-journal-sections-20-to-24.md:1274) · [Overlay corrections](/private/tmp/review-fKyfPC/pilot-journal-sections-20-to-24.md:825)

### 2. Test one repository-grounded question with a fixed specification

Give both arms the same request, draft, and repository, then ask each for two executable regression scenarios. The control gets the generic preservation question. The other gets one question grounded in a relationship visible in the base, such as which neighboring states take different paths through an operation the change touches.

- **For the smallest version,** use two small fresh changes, each with one predeclared preservation risk the base suite misses. Freeze independently verified good and bad variants before drawing the questions. Ask for compact scenario rows with an initial state, public action, expected result, and expected side effect. Execute those rows through a fixed fixture adapter. Three paired draws per case means 12 short calls, plausibly a few dollars and minutes with the short-stage setup. The known resolved-ticket failure can calibrate the harness. Use fresh targets for the comparison.
- **Measure** whether the submitted scenario passes both valid variants and rejects the relevant bad variant, with supporting evidence available in the repository. Include a legal near neighbor that an overbroad assertion would reject. The hidden variants and their behavior adjudicate the test. A scenario that only reproduces the reference’s optional implementation choice fails the precision guard.
- **Advance to a narrow test-design trial** if the grounded question yields at least two more clean discriminators out of three on each case, without introducing a verified false rejection or losing a critical check. A single catch, two arms at ceiling, or more scenario text leaves the larger decision open. The main threat is hand-picking a question from the answer key. Have the question selector work from the public request and repository, independently of the fixture evaluator. The first result would support this selection method, with generality still to establish.

This is the first paid experiment I would run. It directly tests the benefit the plan’s K2 result hinted at, while holding the spec fixed and measuring a behavior the old suite cannot already detect. [Plan-added catch and counterexample](/private/tmp/review-fKyfPC/pilot-journal-sections-20-to-24.md:1303)

### 3. Test whether one requester answer reaches acceptance

Give both arms a one-question budget on a short request with a consequential fork and a tempting question the repository already answers. Compare ordinary intake with an instruction to present the consequential fork as concrete alternatives, say what the answer changes, and carry the reply into acceptance.

- **For the smallest version,** use a compact reminder-like request with two valid policies, such as once per waiting episode or repeating until reply. Before the experiment, have a human author commit to the possible replies and the observations each implies. Use three paired intake draws and a short continuation after any appropriate question. Vary the precommitted reply across pairs so the same guess cannot win every time. Both arms get the same access to evidence and to the scripted requester.
- **Measure** whether the question resolves the decision, whether the recorded decision and an observable acceptance example reflect the reply, and whether the session spends its one question on something it could have inspected. Where the requester hasn’t answered, score the stated default or the scope of what blocks work against the predeclared policy. The ground truth is the human’s answer once supplied, plus the base’s evidence for the resolved detail.
- **Pilot the handoff** if the treatment resolves and carries the right decision in at least two more pairs, with no increase in questions a requester needn’t answer and no unsupported commitment. More `Open:` lines or an unverified promise to reflect the answer later would leave me unconvinced. The main threat is that a scripted requester is more responsive and has firmer preferences than a real one. A later trial needs a real request and a real answer, with the extra round trip counted as a cost.

### 4. Check a finished product independently of its green gate

Give both arms the same frozen deliverables and the same inspection budget. Have the treatment start from the original request and the starting product, record its acceptance hypotheses, and then examine the delivery’s spec and gate.

- **For the smallest version,** make a coded bundle with one green-but-wrong build and two valid builds that differ on a genuinely open choice. Use three fresh reviews per arm with a two-probe budget and ready-to-run small products or captured public-boundary traces. Use a clearly grounded failure for the primary result. The historical due-times failure can serve as a calibration example.
- **Measure** correct rejection of the bad build, acceptance of both valid builds, and whether a reported issue can be reproduced at the public boundary. The external evaluator can also identify cases where the reviewer could not drive the product. Freeze these classifications before any review.
- **Trial independent acceptance** if at least two additional treatment reviews catch a serious violation with a reproducible probe and accept both valid builds. More findings without that precision would argue against adding a new review gate. The main threat is the curated bundle. A blind replay can show that the review catches this failure mechanism. The frequency and cost in real deliveries would still need to justify a routine stage.

### 5. Compare same-session and fresh review of a frozen draft

Give the same author and a fresh session the same draft, source evidence, targeted question, and budget of one proposed substantive change. Compare whether each finds a grounded omission or removes a harmful commitment.

- **For the smallest version,** use three short drafts frozen before review, with a mix of a real omission, an unsupported restriction, and a valid draft with a legitimate open choice. Continue the original author’s context in one arm and give the other the same visible inputs in a fresh context. Six short review calls and deterministic replay of the proposed contract against small fixtures are enough for a first screen.
- **Measure** whether each edit permits the valid products and rules out the actual bad behavior, and whether it preserves explicit obligations from the request. Have an evaluator use independent fixtures or precommitted behavior examples. Keep the reviewer’s citation and proposed observable together so disagreements can be inspected.
- **Buy a fresh review** if it resolves substantive defects on at least two drafts the same author misses and leaves the valid open choice intact. More comments, stylistic improvements, or a single useful catch would be weak grounds for buying a session routinely. The main threat is making planted flaws easier to spot than natural ones. If the screen works, repeat on naturally occurring drafts before comparing pre-draft questioning against post-draft review with matched total effort.

I would defer another round of general guides, a full fifteen-concern matrix per work item, more ticket-assignment draws on the unchanged 27-defect pool, and a bigger build picked mainly for size. Those buy repetitions of known limitations. If §52 produces a credible item-level signal, the cheapest specification follow-up is a **matched-format comparison**. Keep the same acceptance-line duty and vary only the question’s specificity. Use a fresh task with valid alternatives and a behavior probe, then invest in a full build only if the small screen changes what could be correctly accepted. If the desired benefit is easier navigation, evaluate an index by whether a downstream reader can locate the authoritative requirement and distinguish it from an open choice. That is a plausible value of the section even with zero added coverage.

## D. The case for moving on from specification wording

The strongest case for stopping is that the experiments have already found several failures downstream that better wording would have little leverage over. A suite skipped the product’s existing tests and reported success. Two suites failed to construct an input that separated correct pagination from defective pagination. Two other suites depended on one viable product’s configuration interface. In the rich-page comparison, 108 of 111 initial failures of the build-blind suite came from execution code. And the earlier due-times gate was entirely green while the product failed the independent scenario that mattered. A longer spec could leave every one of those mechanisms intact. Improving test execution, checking both sides of an invariant, and independently checking the built product address directly observed failures. Carrying one consequential open question to the person who can answer it addresses the input that a model cannot infer. [Test execution and pagination](/private/tmp/review-fKyfPC/pilot-journal-sections-20-to-24.md:1274) · [Rich-page catch-up](/private/tmp/review-fKyfPC/pilot-journal-sections-20-to-24.md:909) · [Green due-times gates](/private/tmp/review-fKyfPC/pilot-journal-sections-20-to-24.md:78)

I believe that case for **general specification prompting**. I would spend the next budget on the gate and on one targeted, behavior-scored comparison. I would keep the specification question alive only for a specific example where an evidence-grounded prompt changes a consequential obligation or gets an intent decision made in time. If neither §52 nor a small objective follow-up produces that result, stop this line of spec experiments. Reuse the reference material where it helps select a test, expose a design interaction, or route a real question.

## E. Changes to the texts before the next comparison

1. **Make the declared output shape agree with the treatment.** The spec says “in exactly this form,” gives two sections, tells the writer to draft once, and calls the standard questions aids to thinking. The K2 additions expect a separate writing duty or a third section that the canonical schema never names. The bare K2 wording also quotes “what is in and out” while the operational instructions mainly ask for preserved behavior. A model can satisfy much of this by putting the answer in an existing umbrella clause. If testing an additional form, put that form in the schema in both arms. Require a checkable link to a governing clause or an open decision, and verify the meaning of selected links. F47 improved the shape, but K2 changed to K4 and the request changed too. The 2, 1, 2 test-clause counts in both K4 arms also show that a link rule alone does not guarantee retention of every stated obligation. [Spec format and drafting duties](/private/tmp/review-fKyfPC/texts-under-test.md:19) · [Question variants](/private/tmp/review-fKyfPC/texts-under-test.md:150) · [F47 and its control](/private/tmp/review-fKyfPC/pilot-journal-sections-20-to-24.md:1683)

2. **Track explicit obligations separately from how prose gets split.** “Every sentence of the request” and “a statement joined by ‘and’ is two clauses” turn punctuation and grouping into questionable proxies for completeness. A requested behavior, an instruction to keep the old tests passing, and a requirement to deliver new tests are all obligations. They require different evidence. Give every explicit obligation a traceable acceptance or delivery check, and keep one externally verifiable promise per behavioral clause. For a transition, let its precondition, effect, and forbidden side effect be checked together when that is what distinguishes the behavior. The artifact can then catch a lost test obligation without relying on the number of clauses. [Clause rules](/private/tmp/review-fKyfPC/texts-under-test.md:29) · [Explicit obligations displaced by K2](/private/tmp/review-fKyfPC/pilot-journal-sections-20-to-24.md:1523)

3. **Require evidence that a preserved rule applies to the changed path.** “Name the accepted behaviour” and cite a file are sensible starts. Add a question about scope of applicability. Which old caller, state, or promise does the change touch, and what establishes that the exact rule governs it? Ask for the allowed neighbor as well as the refusal when a state guard changes. The relevant distinction in the pilot was “closed cannot be patched, resolved still can,” while the lists mostly repeated the closed-ticket refusal. An analogy for a new field belongs in an assumption or open decision unless an applicable contract binds it. Apply the same authority standard to the planner’s ability to append clauses. Give the planner an explicit way to flag an unsupported or contradictory clause for correction, since an append-only rule cannot repair it. [Preservation lens and plan append rule](/private/tmp/review-fKyfPC/texts-under-test.md:85) · [Plan instructions](/private/tmp/review-fKyfPC/texts-under-test.md:126) · [Resolved versus closed in the section outputs](/private/tmp/review-fKyfPC/pilot-journal-sections-20-to-24.md:1514)

4. **Define what a finished open point has to accomplish downstream.** “An open line is a finished piece of work” is sound for the writer, but the next packet says the build takes a reasonable answer and the test passes whichever answer it took. That skips the distinction between an implementation choice, a provisional choice with a material consequence, and a preference that someone must settle. Record the affected observable, alternatives and consequences, route, and what can proceed. Permit an open decision with no parent clause yet if there is no common promise to assert. When an authorized answer arrives, bind it in the acceptance contract. When implementations may legitimately differ, give the test the documented way to drive *this* build and assert the common behavior across valid choices. The pilot shows why the assertion and the means of driving it both matter. [Spec open-point rule](/private/tmp/review-fKyfPC/texts-under-test.md:45) · [Downstream instruction](/private/tmp/review-fKyfPC/texts-under-test.md:99) · [Portability diagnosis](/private/tmp/review-fKyfPC/pilot-journal-sections-20-to-24.md:849)

5. **Allow §52-style questions to return an unresolved decision.** “Questions settled,” one answer per entry, and “first add” an acceptance line push toward settling by fiat. Q1 should ask about partial success *if it is possible under the contract*. Q3 should ask about behavior under an evidenced load or bound, with an open decision where the bound itself matters. Q4 should ask which harmful or malformed input is relevant to the affected boundary. Q5 should ask which value forms change the outcome, rather than enumerating every conceivable form. For reminders, I would ask what starts, pauses, and ends a waiting episode before asking about a caller’s result. In a future treatment, let an entry point to a grounded acceptance observation, route a genuine open decision, or explain briefly why it does not apply. Keep the existing registration intact when reading §52. [Registered question wording](/private/tmp/review-fKyfPC/elaboration-journal-sections-37-to-52.md:1284)

The decision I would make now is to reuse ShipLoop’s **routing scheme and concern categories selectively**. A question earns its place when its answer changes a required observation, catches a regression, or gets a consequential choice to the right person. Those outcomes are all measurable in small experiments, and they would tell the owner more about useful fullness than another count over the specification.
