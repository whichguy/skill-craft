1. R-2 How does the help desk change the hours? Decided: Operators set DUE_HOURS_URGENT, DUE_HOURS_HIGH, DUE_HOURS_NORMAL, DUE_HOURS_LOW in the service's environment and restart; unset means 4/24/72/168; a bad value stops start with a message naming it. Each value must be a whole number from 1 to 100000 hours, else start stops. Otherwise: A settings file or an API to edit hours live; it would add a new file or endpoint to maintain.
2. R-5 Is a ticket due exactly now overdue, and what does overdue=false do? Decided: Overdue means due strictly before now; overdue=true narrows the list; overdue=false or any other value gets a 400 invalid error. Otherwise: Accept overdue=false as 'only tickets not overdue'; it would add a second filter meaning.
3. R-7 What happens with DUE_TIMES unset, off or misspelt? Decided: Only the exact value on switches it on; anything else acts as off: no due in answers and overdue ignored. The service still stores due times in the data file. Otherwise: Refuse to start on an unknown value; a typo would stop the service instead of silently staying off.
4. R-6 When do existing tickets receive due times and what hours are used? Decided: At the first start of the new release, whatever DUE_TIMES says, using the hours set at that moment; the file is rewritten once with no audit entries. Otherwise: A separate migration command run by operators before the switch; it adds a step that can be forgotten.
5. R-8 What do operators lose by rolling back? Decided: 1.4.0 starts and shows every ticket, but its next save drops the due times; the next upgrade recomputes them from created time and priority with the hours then in force. Otherwise: Keep due in a side file that 1.4.0 never touches; it adds a second file to back up.
6. R-2 What is the largest number of hours accepted? Decided: 100000 hours (about 11 years); a larger value stops the service at start with a message naming the variable. Otherwise: No limit; an absurd value would make a due time that is not a valid date and fail at ticket creation.
