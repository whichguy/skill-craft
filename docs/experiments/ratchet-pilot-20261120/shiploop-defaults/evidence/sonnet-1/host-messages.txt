Due times are built and merged into `master` of your checkout (now at 3a27163, version 1.5.0). `npm test` passes: the 117 existing tests, unedited, plus 27 new ones in five `test/due-*.test.js` files.

I have not deployed it or switched it on anywhere. That is the operators' step.

- **Due time:** each ticket gets `due` = created time plus the hours for its priority (4 urgent, 24 high, 72 normal, 168 low). It is set once, so changing the hours or the priority later does not move it.
- **Hours:** set with `DUE_HOURS_URGENT`, `DUE_HOURS_HIGH`, `DUE_HOURS_NORMAL` and `DUE_HOURS_LOW`, whole numbers from 1 to 100000. A bad value stops the service at start and names the variable.
- **Overdue listing:** `GET /tickets?overdue=true` lists only open and in-progress tickets whose due time has passed. A ticket due exactly now is not yet overdue. Any other `overdue` value is a 400 error.
- **Existing tickets:** at first start the new release gives each ticket in the data file its due time, computed from its own created time and priority, and saves the file once.
- **The switch:** the service stores `due` always, but shows it and answers `overdue` only when `DUE_TIMES` is exactly `on`. Otherwise it answers as 1.4.0 does.
- **Rollback to 1.4.0:** the data file stays version 1, and 1.4.0 ignores the extra field. I ran the real 1.4.0 server from commit 23f8879 on a file the new release wrote, and it started and showed every ticket. Its next save drops the due times, and the next upgrade recomputes them from created time and priority with the hours then in force. This is documented in `docs/operations.md`, along with the rollout order: deploy with `DUE_TIMES` unset, check the file holds the due times, then switch on.
- **Start-up write failure:** if the data file can't be written at that first start, the service now stops with a message naming the file and what to do. Without that fix the failure would have shown as a bare stack trace.

Also checked: with `DUE_TIMES` unset, twelve requests give identical answers on 1.4.0 and the new release. Four system tests (ST-1 to ST-4, run against real server processes) pass.

**Left for the operators:**
- Deploy 1.5.0 and confirm the production file holds one `due` per ticket (`grep -c '"due"' <data file>`).
- Then set `DUE_TIMES=on` and restart. I had no production access, so this is unverified.

**For the API owners:** `docs/api.md` says list filters combine with AND, but `matchesFilters` in `src/tickets/query.js` combines them with OR. I left it alone because fixing it would change today's answers; `overdue` narrows the result either way. Do you want it fixed?
