## Approach

Add `src/orders.js` as a strict-mode CommonJS module with named exports `parseOrders` and `total`. `parseOrders` takes a primitive string and builds a fresh array of `{id, qty, price, status, shippedAt}` objects in physical line order. Each row has a temporary field map. The parser validates the map and converts the values before appending a record. `total` takes a dense array of records with numeric `qty` and `price` and folds their products into a JavaScript `Number` starting at `0`. It uses the shared `src/meter.js` module for each entry it attempts. (C-1–C-7, C-15–C-17, C-39–C-45)

Add `test/orders.test.js` using the package’s existing `node:test` and `node:assert` conventions. `package.json` already runs `node --test`, which discovers both test files. The existing meter and its tests continue to supply the platform contract. The build adds two files, with no dependencies, configuration changes, or data migration. (U-7, U-8, C-50–C-63)

## Decisions

| Choice | Reason | Alternative considered |
| --- | --- | --- |
| Split on `\n`, retain the original index, and use `trim()` on a row only to decide whether to skip it. Split the original row on `;`, take the first `=` as the boundary, and trim the value substring. | This preserves physical lines and exact keys, handles CRLF through normal trimming, and gives validators the complete value. (C-4–C-12, C-36) | Trimming the entire input or row, filtering rows before numbering, or splitting all occurrences of `=` would discard meaningful characters or positions. |
| Collect each row into a `Map` using the five exact allowed keys. Check the delimiter and reject unknown or duplicate keys as fields are read, then check completeness. Validate values in the fixed order `id`, `qty`, `price`, normalized `status`, date shape, and status/date agreement. | Explicit keys allow reordering while structural defects take precedence over invalid values. A row-local map keeps repeated IDs across rows independent. (C-12–C-16, C-37–C-38) | Position-based parsing, last-write-wins collection, or validating values as fields arrive would change acceptance or error precedence. |
| Share a decimal spelling check and finite `Number` conversion across the three numeric fields. Use `Number.isInteger` and each lower bound for quantity and price. | The same syntax applies to all three fields, while the resulting numbers have field-specific constraints and error types. (C-18–C-28) | `parseInt` would accept partial values or truncate fractions. Bare `Number` would coerce an empty string and accept hexadecimal. `Number.isSafeInteger` would reject explicitly supported numbers. |
| Lowercase the trimmed status and validate the trimmed nonempty date against the exact ASCII digit shape. Keep the date text and then check its agreement with status. | The output keeps the original date text after trimming, including a date-shaped value such as `2026-02-30`. (C-29–C-35) | `Date` parsing or calendar validation would alter or reject date-shaped values the spec accepts. |
| Accumulate in one left-to-right loop. Call `meter.tick()` on the imported meter object at the start of each entry, then read its operands and add the product. Let any tick exception leave the loop immediately. | Each entry uses exactly one tick, even if it contributes zero. The original meter exception and the count at failure remain observable. (C-40–C-49) | A length precheck or batch charge would change behavior near an already-used limit. Summing first, grouping entries, or changing the order of additions would change observable behavior. |

## Nuances

- **C-4–C-14, C-36–C-38**. Keep the index even when a line is blank, and keep leading whitespace on a nonblank row so a key such as ` id` still fails. A final line needs no newline. A trailing `;` produces a malformed empty field, while `shipped_at=` contains a valid delimiter and an empty value. Handle all structure checks before conversion, including a missing key discovered at the end of a row. Report every row error with its class and a message containing `Line N` using the physical line number. The first bad row wins even if a later row has a different error class. Let the exception end the call before an array can be returned.
- **C-18–C-28, C-42**. Require the whole trimmed numeric value to match `[+-]?(?:[0-9]+(?:\.[0-9]*)?|\.[0-9]+)(?:[eE][+-]?[0-9]+)?` before conversion and reject nonfinite results. An invalid `id` raises `SyntaxError`. Conversion failures and fractional or out-of-range values in `qty` or `price` raise `RangeError`. A finite fractional or negative `id` is allowed. Apply integer and lower-bound checks to the converted number, so values like `2.0`, exponent notation, and representable integers beyond the safe integer range work. Keep ordinary `Number` multiplication and addition in `total` so rounding and overflow follow the runtime.
- **C-29–C-38**. An empty or whitespace-only date value survives the shape check and is then allowed only for `open`. A nonempty value needs four, two, and two ASCII digits separated by literal hyphens. Check status before date shape, and shape before status/date agreement. Use fixed validation order even when the fields appear in reverse order.
- **U-3, U-5, U-6, C-39, C-43–C-49, C-52–C-58**. Import and parse without charging ticks, including successful parsing at the limit and failed parsing after a valid row. Keep the accumulator local and leave the input read-only, so the same frozen array can be totaled repeatedly while its shared meter count rises. An empty array returns `0` at every meter count. The meter increments before throwing, so a failed tick leaves the count at `10001` when the budget was just exhausted. Let the caller own resets and let the meter own the limit and error. After a failed tick, later entries in that batch receive no work or ticks.
- **U-7, C-50–C-60**. The CommonJS module cache shares the meter between local callers in one process. Starting a distinct Node process initializes the count to `0`. Verify that with a child process after the parent exceeds the limit. Requiring the orders module first in the child also checks that loading it has no meter cost. Text and record arrays are the only order inputs. The existing test command and meter live in the prior checkout independently of the two add-on files, so returning to it requires no state cleanup or migration.
- **U-8, C-60–C-63**. Keep meter-dependent order tests serial within their file. Reset at the beginning of each independent meter scenario and register cleanup so an assertion failure cannot leak state into a later test. Keep consecutive calls in U-5 and the boundary transitions in U-6 within a single scenario, with the shared count intact during each sequence.

## Build order

1. Add `src/orders.js` and export `parseOrders`. Implement the primitive-string guard, physical-line loop, row structure checks, fixed value validation, and record construction. Use direct `require` and the U-1 input to check the returned objects, then try one structural defect and one invalid quantity after a blank line.
2. Implement and export `total` with the shared meter call inside the left-to-right accumulation loop. Check `399`, the two ticks charged by the example, and `0` with no extra tick for an empty array. Verify that the meter seen by a direct caller is the same one the module charges.
3. Add the parser and total cases below to `test/orders.test.js`, including the limit and fresh-process cases. Run `node --test test/orders.test.js` as a focused check, then `npm test` from the package directory and inspect the changed files for scope.
