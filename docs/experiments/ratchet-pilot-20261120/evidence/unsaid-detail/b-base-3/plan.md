# Plan: ticket assignment

## Approach

The service is layered: `app.js` handlers validate (`tickets/validate.js`) and call one `TicketStore` method; the store checks state, applies the change through `apply()` (audit + effects + save), and notifications go through `notify()` into the outbox, delivered later by the worker through `templates.js`. Assignment follows that path exactly and adds no new mechanism.

Parts touched:

- **`src/tickets/validate.js`**: new `assignment(body)` : `onlyFields(body, ['assignee'])`; `assignee` must be present (`'assignee' in body`); `null` returns `null`; a string is trimmed, must be non-empty, and is single-line (reuse the `text()` rules with a limit, see Decisions); anything else is `InvalidError`.
- **`src/store.js`**: new `assign(id, assignee, actor)`. `find` (404) → if `!isActive(status)` throw `ConflictError` (409) → `changes = ticket.assignee !== assignee ? { assignee: {from, to} } : {}` → `apply(ticket, 'ticket.assigned', changes, actor, effects)`. The effect enqueues a notification only when `to !== null`. `create()` adds `assignee: null` to the ticket object but NOT to `CREATED_FIELDS`. Existing `store.test.js` deep-equals the creation audit entry, so the creation entry must stay as it is.
- **`src/app.js`**: `router.put('/tickets/:id/assignee', ...)` (the router already has `put`).
- **`src/templates.js`**: a template for the new notification type (`ticket.assigned`). Without one the worker would retry five times and mark the event dead.
- **`src/persistence.js`**: `ticketRecord` gains `assignee: ticket.assignee ?? null`. `readTicket` validates it: `null`, or a non-empty string. Old files have no `assignee`, so loading yields `null` (see Nuances).
- **`src/tickets/query.js`**: `parseListQuery` reads `assignee` (`params.has('assignee')`: `''` becomes `null`, otherwise the string). `matchesFilters` changes from `some` to `every`. This also corrects the existing status/priority OR bug (C-14).
- **`src/format.js`** + **`bin/tickets.js`**: an ASSIGNEE table column and an optional raw column after column 4. The usage text and the `--assignee` option are optional extras (see Decisions).
- **Docs**: `docs/api.md` (endpoint, filter, `assignee` field, notification), `README.md` (command-line listing, raw columns), `CHANGELOG.md`, and a short decision record if the repo's habit calls for one. Journal rule from the user's CLAUDE.md does not apply (no experiments).
- **Tests** (new files only; existing ones untouched): `test/assignment.test.js` (API + store), plus additions in new files for query/persistence/format/CLI. Do not edit existing test files, since "must still pass as they are".

Data: ticket = `{id,title,priority,requester,status,created,updated,assignee}`. The audit entry has `changes.assignee {from,to}`. The outbox event has `{key, type:'ticket.assigned', to:<agent>, ticket, data:{title}}`.

## Decisions

1. **Method `assign(id, assignee, actor)` on the store, validation in the validator.** Matches CONTRIBUTING ("changes go through the store", handlers never touch tickets or the notifier). Rejected: reusing `update()`/PATCH. `PATCH` must keep refusing `assignee` as unknown (C-17), and `update` has different state rules (rejects only final states, which is the same set, but keeps the concerns apart).
2. **State check uses `isActive` (open/in_progress), before the no-change check.** A resolved ticket with the same assignee still answers 409 (C-4 says "any assignment" to resolved/closed is refused; U-3). Rejected: letting a no-op on a final ticket return 200.
3. **Validation before the state check, 404 before both.** Order: route → body validation (400) → find (404) → state (409). Existing handlers validate the body first, then the store finds; follow that. An invalid body for a missing ticket is therefore 400. A test must not depend on that order for combined faults.
4. **Notification key includes the agent: `ticket.assigned:<id>:<agent>`** (pass it as `notify`'s fifth argument). The default key `type:ticket` would make a second assignment wait behind a still-pending first and silently drop the new agent's notice (C-9). With a per-agent key, A→B→A while A's first event is still pending reuses that pending event (the outbox dedupes by key): dana still has a pending notice, so the last-named agent is notified, and she is not mailed twice. Rejected: a key with a counter or audit `seq`; it would mail dana twice. A test checks only that a pending event to the last agent exists after A,B,A.
5. **Name rules (C-3 Open):** trim; non-empty; `typeof string`; reject control characters (reuse `CONTROL`); upper bound 64 (same as requester). That is the reasonable answer to the Open point and is reported by the build. Tests must not assert on length or control characters. Implementation: export a helper from `validate.js` or call `text(body,'assignee',LIMITS.assignee)` after the null check. Add `assignee: 64` to `LIMITS`.
6. **Notification wording (C-8 Open):** type `ticket.assigned`, subject `[T-0001] Assigned to you`, body names the id and the title ("Ticket T-0001 "title" was assigned to you."). Recipient = the agent's name as the `to`. Agents are names, not addresses, and the outbox only needs a non-empty string.
7. **Audit action:** `ticket.assigned` for both assign and unassign (one string; C-10 Open). The `changes.assignee` shape carries the difference.
8. **Filter parse:** `assignee` present with `''` → `filters.assignee = null`; else the exact string (not trimmed; case-sensitive, C-12). `matchesFilters` treats `null` as a real value to match (`ticket.assignee === null`); the existing `value !== undefined` skip keeps working. A ticket without the property (old in-memory object) must be read as `null`: compare `(ticket.assignee ?? null)`.
9. **`matchesFilters` → `every`.** Existing `query.test.js` and `api.test.js` filter tests use single filters, so they stay green; verified by reading them. The documented behaviour (docs/api.md) is AND.
10. **CLI:** table gets an `ASSIGNEE` column after PRIORITY (before the free-text TITLE, so the unpadded last column stays the title); an unassigned cell shows `-`. Raw: append the assignee as column 5, `''` for unassigned. Appending is safe for `weekly-report.js` (columns 2 and 3 by position, no column count check). `RAW_COLUMNS` stays the first four, so a separate `rawLine` that appends the fifth keeps the comment's contract. Because names are control-char-free, the cell has no tab. Add `--assignee` to the CLI only if cheap; it is not required. If added, `--assignee ''` must map to the unassigned filter, so `options.query.set('assignee', value)` does that for free because `parseListQuery` handles `''`. Recommended: add it, since `parseArgs` already generalises over the three options.
11. **`show` output:** add `assignee` to `details()` fields (not required, harmless; keep the order of existing fields). `describeChanges` uses `from === null` to print `field to`, so an unassign prints `assignee dana -> null`. Make it print sensibly for `to === null` if cheap. No test checks it.

## Nuances

- **C-14 / existing behaviour: `some` → `every`.** The existing bug is a behaviour change in the status/priority combination. Do it, and test `?status=open&priority=urgent` explicitly. Check pagination: `paginate` runs after filtering, so cursors are unaffected.
- **C-9 key collision.** See Decision 4. Without a per-agent key the second `notify` returns the pending event for the first agent and the new agent is never told. Test with the worker off: assign dana then eli, `GET /admin/outbox` pending contains a `to: eli` event for the ticket.
- **C-6 no-op.** `apply()` already returns the unchanged copy when `changes` is empty, with no audit, no `updated` bump, no effects, and no `save()`. Rely on that; do not set `ticket.assignee` or enqueue before the comparison. A trimmed name equal to the existing one is a no-op, so compare after trimming. `null` on an unassigned ticket is a no-op. A ticket loaded from an old file has `assignee` undefined unless `create`/`load` normalise it. Normalise in `readTicket` (and in the `TicketStore` constructor copy, `{ assignee: null, ...ticket }`) so `undefined !== null` never counts as a change for `{"assignee": null}` on an old ticket.
- **C-11 old data files.** `readTicket` builds from `ticketRecord`, which would copy `assignee: undefined`. Use `?? null` in `ticketRecord`, and validate the value only when it is not `null`. Do not bump `VERSION` (1): that would refuse every old file (`document.version !== VERSION`). A new file must still load in the format check; saved files now contain `assignee` for every ticket. `persistence.test.js` compares the `fields` of tickets, so check how it picks them before relying on that. The tests I read use a field subset, so added fields pass. A hand-edited file with `assignee: 5` or `""` is refused with a `DataFileError`, like other bad fields.
- **C-7 the field on every response.** Tickets are returned as `{...ticket}` copies, so `create()` setting `assignee: null` covers POST, GET, list, PATCH and transition. Property order does not matter. Tickets loaded from old files are covered by the normalisation above. Do not strip `assignee` on a resolved/closed ticket (kept, per C-7). Reopen (`resolved → open`) keeps the assignee too.
- **C-3 body shapes.** `readJson` already turns non-object, array, empty and non-JSON bodies into 400. Missing `assignee` must be 400, not treated as `undefined → null` unassign: test `'assignee' in body` explicitly. `{"assignee":"  "}` → 400. `{"assignee":"dana","x":1}` → 400 via `onlyFields`. `{"assignee": " dana "}` stores `dana` and counts as equal to `dana` for the no-op check. A name such as `"__proto__"` or `"constructor"` is only a string value, so it is harmless here. Keep `body.assignee` access on the parsed object.
- **C-4 / C-8 ordering with 409.** On 409 nothing may be written: check state before anything else in `assign`, and make sure no audit/outbox/save has happened. Test by comparing the audit and outbox before and after.
- **C-8 not within the request.** `notify` only enqueues. Never call the notifier in the handler. The worker is off in tests (`workerIntervalMs: 0`); to see delivery, call `service`'s worker tick as `worker.test.js`/`service.test.js` do (read those for the helper before writing the test). The template must exist, or the delivery fails and the event goes to retry and `dead`. Add a template unit test via `render`.
- **C-8 unassign sends nothing.** Effects run only when `to !== null`. Reassignment from dana to eli notifies only eli; dana's earlier pending notice is left (C-9 allows it). Resolving a ticket still notifies the requester as before, and `ticket.resolved` is unaffected.
- **Notice recipient field is `to`.** `outbox.enqueue` requires non-empty string `to`; the trimmed name guarantees this. `persistence.readEvent` also requires non-empty `to`, so saved events reload.
- **C-10 audit.** `apply()` writes the audit entry with `changes` from the call, so `assignee: {from, to}` appears. The actor comes from `actorOf(req)` (`X-Actor` or `system`). The creation entry stays untouched (no assignee in `CREATED_FIELDS`), because `store.test.js` deep-equals it.
- **`updated` on an assignment** is the change time (C-1) and `apply()` sets it, so use the manual clock in tests and advance it between steps.
- **C-16 raw output.** `RAW_COLUMNS` is exported and its comment documents the weekly report's contract; if the builder appends to it, the comment, README and any test of it must still say the first four are fixed. Test: run `weekly-report.js`'s `count` on raw lines with assignees present and compare the counts to those before the assignment.
- **C-15 table.** `table()` pads every column but the last; keep TITLE last. An unassigned cell must not contain any agent name. Header text is the builder's choice; tests find the name in the row of the right ticket only.
- **CLI is read-only and builds a store with `state`**, so an old file goes through `fromDocument` → the normalisation above. Test the CLI with `main(argv, {out, err})` writing to collectors, as the existing tests do (look at how `test/` already drives it, or spawn with a data file under TMPDIR).
- **Routes:** `PUT` on `/tickets/:id/assignee` must not make `/tickets/:id` answer PUT. The router tells methods by pattern, so a wrong method answers 404 as before. A `GET /tickets/:id/assignee` is not required.
- **Restart:** after a restart the outbox pending event and the assignee survive because both are in the snapshot. Test with `DATA_FILE` in a temp folder: assign, build a second store from the file, check `get` and `outboxReport`.
- **Going back:** assign then unassign leaves two audit entries (`from null to dana`, `from dana to null`) and one notification.
- **Existing-test traps:** do not change `CREATED_FIELDS`; do not change the JSON shape of other things; keep the `matchesFilters` signature. `test/query.test.js` asserts `parseListQuery('')` gives exactly `{filters:{},...}`, so add `assignee` to filters only when the parameter is present.

## Build order

1. `validate.js`: `LIMITS.assignee`, `assignment()`. Quick node REPL check of the cases in C-3.
2. `query.js`: `assignee` parsing and `every`. Run `npm test` (existing must stay green).
3. `store.js` (`create` with `assignee: null`, constructor normalisation, `assign`), `templates.js` (type `ticket.assigned`). Check by a store-level script/test: assign, no-op, 409, audit, outbox, A→B→A.
4. `persistence.js`: record, read check, old-file load. `npm test`.
5. `app.js`: the route. Start a service on port 0 with the manual clock or a short script, and exercise U-1 to U-4.
6. `format.js` + `bin/tickets.js`: table column, raw fifth column, optional `--assignee`, usage and `details`. Run the CLI and `scripts/weekly-report.js` against a data file.
7. New tests under `test/` for everything above. `npm test` whole.
8. Docs: `docs/api.md`, `README.md` (including raw column text), `CHANGELOG.md`. Report the choices made for the Open points (name limit and control characters, wording, action string, CLI cell text, raw column).

## How we will know

- **U-1:** create a ticket, `PUT …/assignee {"assignee":"dana"}` → 200, `assignee: "dana"`, `GET` agrees; `/admin/outbox` pending has one event `to: dana` for the ticket; with the worker ticked, `notifier.delivered` has the line with the ticket id in its text. Works for an `in_progress` ticket too.
- **U-2:** `{"assignee":null}` → 200, `assignee: null`; a later `GET` agrees; no new notification; audit has `from dana to null`.
- **U-3:** the same assignment twice → both 200, same `updated`, one audit entry, one outbox event. `null` on an unassigned ticket is a no-op. On `resolved` and `closed`: 409 `conflict` for a name and for `null`, with audit and outbox unchanged. Missing ticket 404. Bad bodies (empty, blank, number, boolean, object, array, missing field, extra field, non-object body) 400 `invalid`, ticket unchanged.
- **U-4:** several tickets with mixed assignees, statuses and priorities: `?assignee=dana`, `?assignee=` (and `?assignee=Dana` finds nothing), `?status=open&assignee=dana`, `?status=open&priority=urgent` (AND), pages with `limit`/`next` over a filtered set.
- **U-5:** `node bin/tickets.js --data FILE list` shows the name in the right row and none in unassigned rows; `list --raw` has columns 1–4 as before (split on tab) and `weekly-report` counts are identical before and after assigning.
- **U-6:** the unchanged existing tests pass; `PATCH {"assignee":"x"}` is 400; an old-format data file (tickets with no `assignee`) loads, shows `null` everywhere, and accepts a first assignment; a data file saved after assignment reloads with the same assignees and pending notification.
- **Tests must not forget:** the C-9 sequence (worker off, dana then eli, and A,B,A); `every` semantics on the existing two filters; the old-file load; the creation audit entry left unchanged; that no test depends on the open points (name length or control characters, wording, `type`, audit `action`, CLI header or empty cell, raw column present or not); the use of the manual clock for `updated`; stopping every server a test starts (use `withService`).
