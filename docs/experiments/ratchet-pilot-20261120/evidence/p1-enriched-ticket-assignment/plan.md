## Approach

Add a nullable `assignee` to the existing ticket record. Initialize it in `src/store.js` and carry it through the store's existing ticket copies and the version 1 record projection in `src/persistence.js`. Keep `POST /tickets` and `PATCH /tickets/:id` body allowlists unchanged. Edits and lifecycle transitions retain the assignee, including on inactive tickets. (C-1–C-20, C-56, C-126–C-134)

Register `PUT /tickets/:id/assignee` in `src/app.js` with the existing router, bounded JSON reader, validators, actor parser and response envelope. The handler passes the decoded id, validated name or null and actor to one synchronous store operation. It returns the full resulting ticket with status 200, including on an active-ticket repeat. A real change sets `updated`, appends one audit entry and enqueues an event only for a non-null destination. With persistence configured, the candidate ticket, history and outbox are saved together before becoming visible to live readers. (C-3–C-4, C-21–C-82, C-122–C-125, C-187–C-188, C-191)

In `src/tickets/query.js`, add the optional filter and make the shared matcher intersect all supplied filters. Keep the store's existing numeric id order and cursor pagination. The CLI already reads the same store and matcher, so extend its table, raw and detail renderers in `src/format.js`. Keep the weekly report's positional parser and the CLI's existing options. Add the new worker template in `src/templates.js` and document the API, CLI and rollback in `docs/api.md`, `README.md` and `docs/operations.md`. Use the repository's decision record convention for the public and persisted contract. Add new `node:test` files under `test/` and use the existing scripts, configuration and service entry point. (C-57–C-121, C-135–C-157, C-183–C-190)

## Decisions

| Choice | Reason and rejected alternative |
|---|---|
| Use one assignee-name validator for PUT and a non-empty list value. Reuse `validate.text` with the assignee label and 64-unit limit, then check Unicode well-formedness. Keep null handling in the assignment body validator and empty-query handling in the query parser. | The two entry points accept the same canonical name. Contract-specific meanings would be lost if a generic truthiness check converted omitted, blank and null into the same state. Counts use JavaScript string length, and comparisons use exact case-sensitive equality with no Unicode normalization. |
| Keep a dedicated store assignment method using `isActive`, strict equality and the store's existing `apply` machinery. Use `ticket.assignee_changed` for the audit action and `ticket.assigned` for the notification type. | One audit action describes set, replacement and clear, while only a set or replacement produces a notice. Generic PATCH has different allowed states and fields. `isFinal` alone would also admit resolved tickets. |
| For a persisted change, construct a candidate `TicketStore` with the current snapshot, the same clock and no persistence. Run the same assignment change against the candidate with `apply` and `notify`, save the candidate snapshot through the live persistence adapter, then publish its changed ticket, audit and outbox to the live store. For memory-only operation, apply directly. | The existing save is synchronous and ends at atomic rename. Client-visible state and counters advance only after it succeeds. This reuses normal audit sequence and enqueue rules without editing a committed history or adding rollback paths to unrelated mutations. Cloning is confined to real persisted assignments, where existing saves already serialize the whole small dataset. |
| Pass the audit record returned by `AuditLog.append` as an additional argument to `apply`'s effect callback. Use `ticket.assigned:<ticket-id>:<audit-seq>` as the assignment key and the event's stored `to`, ticket id and title for delivery. | The sequence distinguishes every committed assignment and survives restart. Ticket-only and ticket-plus-agent keys suppress legitimate handoffs or returns to a former assignee. A time-based key can collide within one clock tick. Existing transition callbacks can keep taking only the timestamp, and creation and resolution retain their current default keys. |
| Keep the file version and add one ticket field. Default a missing assignee to null. Validate present values as null or canonical names, checking that the validated name equals the stored string and reporting failures as normal data-file errors. | Older files already have a defaultable field boundary. Accepting padded names in storage would leave the equality rules ambiguous or silently alter hand-edited data at load time. A version bump or migration would prevent rollback on the same file. Also default missing fields in a directly constructed store, since it accepts plain saved state. |
| Represent omitted assignee with no filter key, empty decoded value with a null filter, and names with validated strings. Switch `matchesFilters` from `some` to `every` while keeping its existing undefined-value exclusion. | The API and CLI already advertise status/priority intersection, but share a matcher that currently implements OR. Fixing the helper covers all combinations, including status plus priority alone. The existing id-only cursor works even if the ticket that supplied it changes assignment. |
| Append `assignee` as raw column five. Use an explicit `(unassigned)` label for null in the human table and details and quote assigned names in those views so the literal name `(unassigned)` remains distinguishable. | The report continues to read the original fields at the original indexes. A raw sentinel could be an actual agent name, and the empty fifth cell already has the required meaning. Human formatting can distinguish the two without restricting assignable names. |

## Nuances

- **HTTP ordering and boundaries (U-5, U-6, C-18–C-47, C-192).** Router matching and percent-decoding precede the handler. An undecodable id for PUT gives 400, while a decoded id with no record gives 404 through `find`. The handler reads a JSON object, rejects unknown keys, validates the required assignee value and parses `X-Actor` before the lookup. The store finds the ticket, checks `isActive`, then checks equality. Checking equality earlier would return 200 for an inactive-ticket repeat. Use the existing app catch path for normal envelopes, content type and fault logging. The body limit counts the full UTF-8 request including JSON syntax and padding. Trim the name before checking length and internal ASCII controls. A string of 32 emoji fits 64 UTF-16 units and 33 exceeds it. An escaped lone surrogate survives JSON parsing but is replaced in a URL query or UTF-8 stream. Reject it in assignee validation without changing the requester or title rules.
- **Tickets, time and retries (U-1–U-4, U-7, C-5–C-17, C-48–C-56, C-181–C-182, C-188).** Add null at creation without extending `CREATED_FIELDS` or altering the request validators for creation and PATCH. The dedicated operation modifies only assignee and updated. Compare the canonical value, so padded input for the current name and repeated null are both no-ops. Return a defensive ticket copy before reading the change clock, appending, notifying, cloning state or saving. Take one change time for the actual mutation and use it for the ticket, audit and newly due notification. Keep the lookup, gate, comparison, apply and publish in the same synchronous turn after request-body awaits. Overlapping identical PUTs then observe the first committed change and produce a single effect. Reopen without clearing ownership, and permit a new assignment once open. Resolution still notifies the requester.
- **Atomic save and its failure boundary (U-17, C-37–C-44, C-122–C-125, C-187, C-191).** Calling the current `apply` against the live store with persistence would mutate the ticket, append history and consume an outbox id before a failed save. Even swapping just the ticket back would leave audit or notification state behind. Apply to the isolated candidate and bind the effect to the same candidate's `notify`. A callback that captures the live `this` would enqueue before the save. Publish only on a successful synchronous save. A failed pre-rename write or rename leaves the old document and live state intact, including counters and the trackable notification key for a successful retry. Keep the existing same-directory temporary-file rename and let the app log the exception and return 500 `internal`. Compare stored bytes while the service is still running because graceful shutdown performs an independent save.
- **Queue identity and delivery (U-3, U-4, U-10, U-11, U-14, C-57–C-82, C-132).** Queued notices describe assignments when they occurred. Clearing, editing, changing status or reassigning leaves previous notices and recipients in place. The worker must render the new event from its own payload, so it can deliver a notice for Dana even when the current assignee is Sam or null. Keep the existing worker, notifier, outbox pending-key deduplication, status transitions and backoff. Check both append-to-file and memory delivery. A delayed or failing relay never blocks the PUT. A crash after the relay write but before the sent-state save can result in a duplicate delivery with the original key and id. Keep the relay's existing deduplication contract.
- **Filtering and mutable queues (U-8, U-9, C-83–C-102).** Branch on `URLSearchParams.has` and compare `get` to the exact empty string before trimming. Space-only input is invalid, `assignee=null` is a name, and encoded `%2B` represents a literal plus. Take the first repeated value per the current convention. Preserve validation for existing filters, limit and cursor even when no tickets match. Apply the intersection before paging, continue strictly beyond the last id numerically, and use the filtered lookahead for `next`. If the cursor row is reassigned out of the result between pages, its sort key still defines the boundary. Unknown query parameters remain ignored.
- **CLI output and readers (U-12, C-103–C-121, C-190, C-192).** Preserve the trailing tab for an empty fifth field. Tests that trim the whole output could erase it and miss the regression. Preserve the no-header raw output and empty table message. The CLI loops in pages of 100, and all pages should inherit the same filter intersection and id order. Use a running maximum for table column widths if needed to avoid the spread-argument limit for large listings. Keep the report's use of status and priority and its JSON fields. CLI and report use the loader without a persistence writer, so both legacy and new files must stay byte-for-byte unchanged when inspected.
- **Existing data and restart (U-13, U-14, C-126–C-134, C-138–C-157).** The persistence projection explicitly names fields, so a change just at the API or store would disappear on reload. Include assignee when writing, add the legacy default on read, and report malformed present values with the file and `tickets[i].assignee`. Keep audit and outbox records intact, including ids, keys, delivery state and retry times. Never synthesize history or events during old-file reads. Check a legacy file while the service runs, since a normal shutdown may rewrite it in the current shape. Restart tests need tickets with both named and null assignees, including retained inactive assignments. Preserve missing-file start, in-memory restart, counter and format validation, startup diagnostics, port/configuration and graceful shutdown.
- **Rollback is file-compatible with an operational limit (U-15, C-135–C-137).** The previous loader projects away the added ticket property but accepts non-empty audit actions and notification types and preserves their existing envelopes. Its worker lacks the new template and would retry pending assignment events until dead. Keep a copy before rollback. Let the compatible worker deliver pending assignment notices first, or set `WORKER_INTERVAL_MS=0` on the old executable to preserve pending events. The old writer drops assignees on save, including at clean shutdown. Verify on a copy and describe the saved pre-rollback file as the recovery source for ownership.
- **Regression constraints (U-16, C-146–C-186, C-189–C-190).** Existing tests compare the creation history payload exactly and assert legacy outbox keys or types. Keep those contracts and the existing notifier output field set. Existing list tests exercise single filters, so add a test that independently detects OR for just status and priority. Existing entry points already handle health, logging, config limits, shutdown and worker scheduling. Verify them through unchanged tests and entry-point checks. Keep standard-library-only CommonJS and test discovery through `node --test`.

## Build order

1. Confirm the baseline with `npm test` and retain a disposable copy of the pre-change source for rollback verification. Add the shared assignee name rule and PUT body validation. Implement the optional query filter and the shared intersection, checking exact-empty semantics and status/priority-only matching at the module level.
2. Add null to new and legacy ticket records in the store and persistence projection. Check version 1 round-trips, malformed record diagnostics and legacy load behavior before adding write effects. Keep the original creation audit field set.
3. Add the store mutation, staged save and assignment template. Verify active-state gates, timestamps, actor and audit data, distinct keys, unchanged no-ops and retry after an injected pre-replacement save error. Check the existing worker with the new event.
4. Wire the HTTP route and exercise it using the existing `withService` and PUT client on port 0. Check routing, validation precedence, concurrent repeats, filtered cursors and on-disk state before shutdown. The helper hardcodes `silentLogger`. For error, warning and request-log assertions, start `createService` with a capturing logger or inspect a child service's stderr.
5. Extend all three CLI displays and add API, CLI and operations documentation plus the decision record. Exercise the real CLI and report entry points on copied fixtures and check the rollback executable against the new version 1 file. Use temporary files and stop every service started for a check.
6. Run the added focused `node --test` files and the full `npm test`. Check that existing tests stayed untouched and that the normal `npm start` and SIGTERM paths still work with the configured data file and worker.
