## Approach

The workspace has `ratchet/spec.md` and no existing application, tests, package configuration, or saved games. Add `server.js`, `game.js`, `index.html`, and `test/game.test.js` in one build pass. Use CommonJS and Node built-ins so `node server.js` and `node --test` work from a clean checkout without an install step.

- `game.js` owns the 10×10 board, fleet placement, and shot resolution. Expose game creation and a synchronous fire function. Keep the square-to-ship mapping, each ship's remaining unhit square count, a count of ships still afloat, and a map of prior shot results in the returned server-side game state. A first shot records its result and updates the relevant counts as one operation. Derive `gameOver` from the afloat count. The rule tests call these same functions directly and can read the returned board to choose shots.
- `server.js` uses `node:http` and keeps a `Map` from game id to rules state. Serve `index.html` with an HTML content type from a path relative to `server.js`. Route `GET /api/new` to game creation and `POST /api/fire` to JSON parsing, game lookup, and shot resolution. The fire route reads `{ game, row, col }` and sends `{ result, gameOver }` on success, with a string outcome and boolean completion flag. Send JSON for API errors too. Start with the configured `PORT`, with 3000 as the fallback when the variable is absent.
- `index.html` contains the browser UI, CSS, and script. Use 100 labeled buttons in a 10-column grid. On load, create a game and keep its id in the page. Send the selected button's coordinates on click and mark the square from the returned result. Display the result in text and show a persistent completion message after the final sink. Reloading the page starts another game.

## Decisions

These are build choices for the current pass. The builder should record its choices in its report. The six `Open:` lines remain the requester's to settle. Checks for those clauses must accommodate other reasonable implementations.

| Clause | Choice for this build | Reason and alternative considered |
| --- | --- | --- |
| C-8 | Place five straight ships of lengths 5, 4, 3, 3, and 2. Randomly choose among legal horizontal and vertical placements for each ship. Forbid overlap and allow touching, including diagonally. Generate a fleet for each game. | The sizes give clear examples of hits and sinks with water left on the board. Enumerating legal placements gives bounded work and avoids an unbounded random retry loop. Independent generation allows coincidental repeats, so a forced difference from the previous game's board adds unnecessary shared state. |
| C-13 | Return `{ "game": "<opaque string>" }`, using `crypto.randomUUID()` for the id. | The client can pass the field back directly. A bare JSON scalar would also work, but a named field makes the request and response easy to read. |
| C-14 | Keep each id and its state in memory until the process exits. `GET /api/new` allocates a new record. Return a JSON `404` for a string id absent from the map. | Simultaneous tabs and API clients can play their own rounds. Replacing a single global game would interrupt other players. Disk persistence or an expiry policy adds lifecycle work the request leaves open. |
| C-15 | Accept zero-based JSON integers `0` through `9` for both coordinates. Return a JSON `400` on any other coordinate. | Zero-based coordinates match array and grid indices. A one-based API would require a translation between the rules and the client. Check integers before indexing so numeric strings and fractional values cannot identify a square by coercion. |
| C-20 | Replay the square's original `result` on a duplicate and report the game's current `gameOver`. | A client can retry if it lost the response to an already committed shot. Refusing duplicates would leave that client without the outcome unless it used another way to recover it. A square that first returned `hit` keeps that result after the ship sinks. |
| C-21 | After completion, allow result replays for tried squares and return a JSON `409` for an untried square. | This freezes play while still allowing a retry of the winning shot. Accepting new shots after completion would allow marks to change after the round is finished. |

Keep request handling as a small explicit method/path dispatch. Read the local HTML once at startup. Serve the page and API from the same origin with relative URLs. A framework, static file router, and runtime assets would add setup without serving these four use cases. Treat `GET /api/new` as non-cacheable because it creates a fresh game each time. Keep a small bounded JSON body reader for `POST /api/fire` and short JSON error responses for invalid input.

## Nuances

| Clause or use case | What can go wrong | What to do |
| --- | --- | --- |
| U-1, C-1–C-5 | Passing `PORT` straight to Node as a string can select the pipe-path form of `listen`. A truthiness fallback can also lose port `0` when used to ask the OS for a free port. Relative file reads can depend on the operator's current directory. | Default only when `PORT` is absent, convert a supplied decimal port to a number, and validate the integer range `0`–`65535` before calling `listen`. Surface binding errors clearly. Resolve the HTML from `__dirname`, declare `text/html; charset=utf-8`, and set both the document title and visible heading to `Battleship`. |
| C-6–C-9, C-13, C-15 | Row and column can be transposed, edge cells can be inaccessible, or the browser can receive the secret board as part of creation data. | Use the same `(row, col)` convention in grid generation, request creation, and rule lookup. For the chosen convention, `(0, 0)` and `(9, 9)` are opposite corners. Serialize only the id on creation and only the shot result fields on success. The browser starts with an unmarked grid and learns about squares only through shots. |
| C-8, C-16–C-19, C-21 | Out-of-bounds placements, overlap, or using adjacency to find a ship can make a legal shot behave unpredictably. A global hit count alone cannot report an individual sink. | Enumerate starts whose entire straight segment fits and whose squares are free. Pick one candidate per length and tag each occupied square with a ship identity. For the chosen lengths the candidate list always has a legal horizontal placement even before considering vertical ones. Before placing lengths 5, 4, 3, 3, and 2, there are 0, 5, 9, 12, and 15 occupied squares respectively. Blocking every horizontal segment of length `L` would require at least `10 × floor(10 / L)` occupied squares, by considering disjoint segments in each row. Keep each ship's count independent, including when ships touch. Only the shot that takes a ship's count to zero decrements the afloat count. |
| U-3, C-12–C-15 | A cache can return the previous creation response. A new round, an unknown id, or a server restart can cause a shot to land in the wrong game if the server falls back to a global current game. | Send `Cache-Control: no-store` on creation. Allocate new shot state for each id and always use exact lookup. After a process restart old ids fail lookup and a fresh request gets a playable game. The in-memory design has no migration or persistent state to restore on restart or rollback. |
| C-14–C-15, C-19–C-20 | Malformed, incomplete, or excessively large bodies can throw, consume unbounded memory, or reach game state before the request is known to be valid. | Collect at most 8 KiB and parse only on complete receipt. Accept a JSON object with a string game id and coordinates that the rules can validate. Map malformed bodies, bad shapes, and invalid coordinates to `400`, and oversized bodies to `413`. Stop buffering on overflow and finish the error response once. If the connection closes or errors before a complete body arrives, discard it without applying a shot. Keep later stream events from causing a second response. |
| C-17–C-21 | Repeats can count twice, concurrent shots can compute a sink from stale state, or the winning shot can return `gameOver: false`. A retry after the last sink can lose the original result. | After the body is read, resolve coordinates, consult prior shots, check whether the game is over for an untried square, apply a first shot, and produce its response synchronously with no async gap. Compute the boolean after applying a first shot and from current state for a replay. The last new hit returns `sunk` and `true` together. |
| U-2, C-7, C-10–C-11, C-20–C-21 | Early clicks can fire before there is an id. Double clicks can race terminal feedback. If the winning shot commits but its response is lost, another untried square is already too late to fire at, and its refusal cannot recover the winning result. | Gate clicks until creation succeeds and allow one request in flight. Guard tried squares and the completed board. Set pending before awaiting the response, clear the in-flight flag when the request settles, and write the result and mark only after success. When a shot response is lost, prompt the player to retry that same square before continuing so the replay can restore the missed feedback, including completion. Show failures to create or find a game with a reload instruction. Keep outcome text available without relying on color, and announce both the final shot result and completion. |
| U-4, C-22–C-24 | Tests can pass against duplicated logic or flake by assuming the location of a randomly placed ship. | Make the server import the rules file directly. Use `node:test` and `node:assert/strict` and derive water and ship shot coordinates from the generated state in the tests. Drive shots through the exported function, including earlier shots needed for a sink. Inspect per-game state or results to distinguish a replay from another damage event. |

## Build order

1. Implement the rules module and the requested direct tests together. Check generated placement invariants, miss, non-final hit, sink, duplicate safety, invalid coordinates, independent fresh game state, and the transition to completion with `node --test` before adding transport.
2. Add the `Battleship` HTML shell so the server can load it at startup. Implement server startup, routes, id map, JSON response helpers, and bounded request-body handling. Check the root and API on a free port. Exercise both a valid round and rejected input followed by valid shots against the same game.
3. Complete the grid, styling, and event handling using the implemented response shape and coordinate convention. Start the API round on page load and verify the grid sends the same squares that the rules resolve. Verify shot feedback, retry, and completion in the browser, including recovering a lost completion response by retrying the same square.
4. Run `node --test` again and check the final root page, creation, and fire routes as a single flow. Verify that `server.js` imports the rules module and that the repository needs no installed packages. Report the chosen answers to all six open points with the verification results.
