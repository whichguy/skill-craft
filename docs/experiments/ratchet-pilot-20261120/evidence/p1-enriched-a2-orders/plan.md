## Approach

Add a CommonJS module at `src/orders.js` exporting `parseOrders(text)` and `total(orders)`. `parseOrders` reads caller-supplied text into a fresh array of plain records with exactly `id`, `qty`, `price`, `status`, and `shippedAt`. `total` reads a valid orders array and returns cents using the shared `src/meter.js` module. Add `test/orders.test.js` using `node:test` and Node assertions. The existing `npm test` command discovers both suites. The feature needs no dependencies, configuration, storage, or data migration (C-1–C-18, C-43–C-45, C-53–C-55, C-66–C-69).

## Decisions

| Choice | Reason and alternative considered |
| --- | --- |
| Require a primitive string and traverse LF/CRLF-separated lines in source order. Use a trimmed view to detect blanks and pass the original line into field parsing. | The string type check preserves C-3, and keeping each line's original position and spelling preserves C-28 and C-30. Filtering upfront loses physical line numbers, and trimming a whole nonblank line can hide whitespace in its first key. |
| Collect fields in a per-record `Map` using the five literal keys. Split each segment at its first `=` and trim the value. Check membership and uniqueness as fields are read, then check completeness. | Keyed storage preserves arbitrary field order and distinguishes an explicit empty value from a missing key. A positional split depends on order, last-write-wins hides duplicates, and splitting at every `=` can drop a suffix that should fail value validation (C-9–C-12, C-23, C-30–C-34). |
| Accept signed or unsigned decimal text with at least one digit, allowing an optional decimal point. Check the whole input before converting with `Number`. Require a finite result for each field. For `qty` and `price`, require any digits after the decimal point to be zero and check the converted value against the field minimum. | C-35 leaves other spellings open. A prefix conversion can ignore trailing junk. Checking only `Number.isInteger` after conversion can accept fractional text rounded to an integer, while `Number.isSafeInteger` would exclude the large whole values C-38 permits (C-13–C-15, C-19–C-22, C-34–C-38). |
| Validate the field list, then `id`, `qty`, `price`, normalized `status`, the shape of a nonempty date, and status/date agreement. Use an anchored digit-pattern check and return the trimmed date text. | This gives a straightforward first-error order while C-40 leaves priority unspecified. A date parser would introduce calendar rules or normalization. Tests can isolate each fault without freezing priority (C-16–C-18, C-24–C-28, C-39–C-40). |
| Use one sequential pass in `total`, starting the sum at `0` and calling the shared module object's `tick()` before adding each product. Let a meter error propagate directly. | The meter owns the budget and increments even on failure. An up-front size check, bulk charge, private counter, or reset would alter observable calls or state. Using the exported method directly also supports observing calls through the real meter (C-43–C-51, C-57–C-65). |

## Nuances

- **Physical lines and exact keys (U-2, U-5–U-7, C-23, C-28–C-34).** A blank row advances the line number even though it adds no record. All line-validation errors should use a consistent `Line <n>` prefix, including missing or duplicate keys and field-agreement errors. Missing separators and empty segments are structural faults. A value such as `2=3` reaches the quantity validator in full and raises `RangeError`.
- **Empty values and validation boundaries (U-1, U-5–U-7, C-19–C-27, C-35–C-40).** `Number('')` gives zero, and `Number('1.00000000000000001')` gives one. Check the spelling before conversion so these inputs give a `RangeError` in `price` and `qty`, respectively. Empty or nonfinite `id` is a `SyntaxError`. An empty `shipped_at` value is allowed only for `open`. Check a populated date for ASCII digits in the exact widths, so `2026-02-30` is returned as written while `2026-1-01` fails. Compare status after trimming and lowercasing.
- **Whole batches and repeat calls (U-3, U-10, C-4–C-8, C-41–C-42).** Keep the result array local to the parse call and its field map local to the line. Duplicate IDs on separate lines produce separate records. A malformed later line causes the call to throw, and another parse starts fresh. Parsing has no meter dependency or record limit, including after an over-budget total.
- **Exact charges and failed totals (U-8–U-10, C-43–C-52, C-59–C-65).** Zero-price orders still cost one tick. Empty input returns `0` even after the meter is exhausted. At `9999`, a three-order total attempts two ticks and throws on the second, leaving count `10001`. Keep that failed tick charged and leave the third order untouched. A later call shares the existing count until the caller resets it. Read the array and records without writing to either.
- **Loading, restart, and rollback (U-11–U-12, C-54–C-69).** The orders module can require the meter at load time. It must leave a previously seeded meter count intact, including on first import. Existing meter state is process-local, so a fresh process starts at zero. Preserve the meter API, package test command, and input format so current meter callers work across revisions and existing text can be supplied directly. Returning to the previous revision requires no state conversion.

## Build order

1. Add the CommonJS module and implement parsing through its exported entry point. Establish the type check and line traversal, then field collection, value conversion, and status/date agreement. Check successful records and isolated failures through `parseOrders`.
2. Implement the total through the same module. Check cents, one real tick per record, and propagation at the real meter's boundary.
3. Add the orders suite and exercise the complete matrix below. Run `node --test test/orders.test.js` while working on the suite, then run `npm test` from the project root and confirm both suites are discovered.

## How we will know

| Use case | What to check in the build pass |
| --- | --- |
| U-1 | Deep-compare the example against both complete records in order and check their exact keys and types. From a fresh meter, assert `399` cents and two ticks. |
| U-2 | Check `''`, whitespace-only lines, and blanks between records. Reorder fields, pad values including a shipped date, use mixed-case statuses, and join valid records with CRLF. |
| U-3 | Check that two records sharing one ID both survive, using different quantities so reordering is visible. In another input use IDs `[2, 1]` to catch sorting. Parse a separate batch and then an empty string to check call isolation. |
| U-4 | Assert `TypeError` for omitted input, `42`, `null`, an array, and a boxed string. |
| U-5 | Check `qty=1` and `price=0`, accepted decimal spellings and values past the safe-integer ceiling. Reject zero or negative quantity, negative price, fractions including one that rounds to a whole number, text, infinity, and blank numeric values as applicable. Assert `RangeError` and the exact line number on physical lines 1 and 3. |
| U-6 | Check each missing `=`, invalid or empty status, malformed date from C-25, shipped without a date, and open with a date as a separate `SyntaxError` case. Check the reported physical line, including line 3 after one valid row and a blank. For a row with multiple faults, assert only the allowed error types and the line. |
| U-7 | Exercise unknown, case-changed, and padded keys, each missing key, a repeated key, and leading, trailing, and doubled semicolons. Reject empty, nonnumeric, and infinite IDs. Check that `qty=2=3` raises the quantity error and that a correctly shaped out-of-calendar date is returned as text. |
| U-8 | Check the empty sum and zero ticks, then two consecutive totals for `399` each with counts `2` and `4`. Include a zero-price order and frozen valid input to check the tick and read-only behavior. |
| U-9 | With the real meter, check 10,000 unit orders from zero and one from `9999`. Check an empty total at `10000` and `10001`. From `10000`, assert the next nonempty total throws the exported `LimitError` with its existing message. From a fresh baseline of `9999`, assert exactly two tick attempts for three eligible orders, final count `10001`, and success after explicit reset. |
| U-10 | Seed the meter, parse 10,001 valid rows, and check all records are present and the count is unchanged. Repeat the count check after an invalid parse. |
| U-11 | Keep the existing meter tests and confirm its exports and behavior remain intact. In fresh Node processes check the initial zero even after another process spends ticks. Check that first loading orders after seeding the meter at `1` leaves it at `1`. Confirm rollback compatibility by review of the additive changes and lack of persistent state. |
| U-12 | In a fresh Node process require the two helpers and pass in the example string directly. From the project root run `npm test` and confirm it discovers the meter and orders suites and exits `0`. |

Keep tests that share the meter serial and reset it around independent scenarios. To observe attempts directly, wrap the exported `meter.tick` before loading `src/orders.js`, increment a test counter before forwarding to the real method, and restore the original method and reset the meter in cleanup. Seed boundary counts outside the measured call. Use the real meter for all limit and final-count assertions so tests catch both a skipped call and work attempted after the first failure.
