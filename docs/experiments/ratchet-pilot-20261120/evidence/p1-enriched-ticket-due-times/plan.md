## Approach

- Read the four independent response-hour settings and the exact `DUE_TIMES=on` visibility gate in `src/config.js`. Use one small deadline calculation shared by startup validation, ticket creation and preparation. `src/server.js` supplies the settings and the clock to the store and supplies visibility to the HTTP app.
- Keep optional `due` on each version 1 ticket record in `src/persistence.js` and in the store's ticket state. Prepare existing data in the store's startup path before the HTTP server or worker can start. The service assigns deadlines at creation in either mode and commits an enabled persistent create before publishing it to readers.
- Project tickets at the HTTP boundary for create, detail, list, patch and transition. Keep the query parser's existing status, priority, limit and cursor handling and pass overdue as a separate option to `TicketStore.list`. Match against live status, priority and the request's clock instant before the existing numeric ID sort and cursor pagination.
- Let the CLI use the same version 1 reader in read-only mode. Apply visibility in its human-readable formatters. The weekly report continues through the existing four-field raw CLI output.
- Update the README configuration and CLI instructions, API reference, production operations runbook, decision record and index, package version and changelog. Add focused `node:test` files alongside the unchanged suite. Keep the Node.js 22 minimum, CommonJS and standard library, and the existing `npm start` and `npm test` entry points.

## Decisions

| Choice | Reason | Alternative considered |
|---|---|---|
| Store a canonical UTC deadline beside each ticket's legacy fields and retain file version 1. | The deadline belongs to the ticket and can be inspected and recovered by ID. The 1.4.0 reader explicitly picks known fields. | A new version would prevent direct rollback. A sidecar creates two writes and a new ownership and recovery problem. |
| Validate the schedule at server startup in both visibility modes. Assign deadlines for every service create, including while visibility is off. Pass visibility explicitly to HTTP and the CLI and evaluate the same exact environment value in both. | Disabled service startup and creates prepare the state needed for cutover. The CLI only reads assigned deadlines. | Deferring assignment or schedule validation until visibility turns on would leave a gap in cutover and change what counts as the creation schedule. Reading the full server config in the CLI would make unrelated settings affect operator reads. |
| Use the existing startup owner for preparation and require a complete file to start enabled. | The operator can inspect the completed file while serving the legacy API. An enabled start against a partially prepared file fails visibly before serving. | An enabled startup that silently migrates would remove the verification step. A migration CLI or worker job would add a second write path and complicate ownership and readiness. |
| Use synchronous staging for the enabled persistent create. Keep the scope of this commit-before-publish behavior to that path. | C-52 and C-237 require the ticket, audit, outbox and their sequence positions to stay together even on save failure. C-20 through C-22 require legacy responses in disabled mode. | Hiding a failed create only in the response leaves a ghost in later reads and saves. Reworking all ticket mutations and delivery failure handling would change existing behavior outside the new requirement. |
| Keep the existing default query behavior and opt into conjunction only for `overdue=true`. Keep the cursor format and freshly evaluate membership for every page request. | Ordinary queries, CLI filters and old cursors have existing consumers. Overdue depends on current status, current priority and time. | Changing the existing matcher globally would change ordinary results. Binding a cursor to a time snapshot or filter set would change the cursor contract. |
| Add a `DUE` column to the enabled human-readable table before the final title column and a `due` line to enabled details when present. Show the full saved UTC timestamp, with a blank cell for an unassigned record. | Operators can distinguish assigned from unassigned tickets in mixed files and see the exact deadline. | Computing a deadline in the CLI could present an unassigned ticket as prepared. Adding a raw column would change the report's input contract. |
| Retain a copy of the latest prepared file before handing ownership to 1.4.0. On return, merge deadlines offline into its latest state. | A legacy full-state save drops optional deadlines, and the rolled-back service can have valuable newer state. | Restoring the whole earlier file would discard work and could reuse IDs. Recalculating old deadlines would lose assignments. |
| Use version 1.5.0 and decision record 0009 for the opt-in addition and compatible storage extension. | The package release and decision index make the rollout and compatibility contract discoverable. | Editing accepted decision 0008 would bypass the repository's decision history. |

## Nuances

- **Clock and range (C-1–C-11, C-17, C-63–C-66, C-82–C-84).** Calendar arithmetic changes elapsed hours around time-zone transitions. Floating-point arithmetic can also lose precision when a negative creation instant and a large positive duration are combined near the Date limits. Reuse the trimmed decimal whole-number parser with minimum 1, and apply the shared calculator to one startup clock sample for every nonblank override, including with visibility disabled. Use integer milliseconds, with exact intermediate arithmetic such as `BigInt`, check the inclusive Date range before conversion, and call `toISOString()` on the result. Use the creation clock sample for both `created` and `updated` and derive the deadline from that same instant. A valid startup check cannot guarantee that a later create or a future-dated saved ticket fits. Treat these as different failures with the variable, stored record or internal request diagnostic appropriate to the context.
- **Optional and invalid are distinct (C-42–C-49, C-63–C-65, C-187–C-209, C-212–C-215).** The persistence projection currently discards unknown ticket fields in both directions. Include `due` when it is an own field, and distinguish omission from a present null, empty string or other invalid value. For a present value, check that its parsed time is finite, ISO round-tripping reproduces the exact value, and its numeric time is later than the parsed `created`. This covers millisecond UTC strings including supported expanded years, and rejects Date parser normalization of impossible dates. Keep the legacy `created` and `updated` validation and their original strings. A legacy record can have a parseable noncanonical time, or text that passes the file reader's rules but fails HTTP rules. Existing due values are accepted on their own merits even when the current schedule would calculate a different value.
- **Startup is a whole-state operation (U-7, U-8, U-10, C-42–C-51, C-56–C-65, C-181–C-209).** Load and validate all of the document first, including later audit and outbox records. In `TicketStore.open` or its startup helper, inspect every loaded ticket without using an API page. If any deadline is missing in enabled mode, throw a `DataFileError` naming the file and incomplete preparation. When disabled, build the complete prepared ticket array in memory from stored `created` and stored priority, even for closed and resolved tickets or when the audit records a different priority at creation. Wrap calculation failure with the file and ticket index or ID. Save the validated loaded state with the prepared tickets once before constructing the live service. Bypass ticket mutations so IDs, timestamp values, audit entries, outbox events and counters are preserved. A missing file, valid zero-ticket file or a fully prepared file needs no preparation write. Check for no rewrite before shutdown, since the existing shutdown path saves even without mutations. Memory-only startup has no file to prepare or verify.
- **Save failure and retry (U-7–U-10, C-52–C-55, C-60–C-62, C-66, C-128–C-129, C-152, C-185, C-237).** Reuse the whole-file writer with an owned temporary file in the destination directory and a single rename after the full write and close. Keep the target untouched on write or rename failure, clean up the owned temporary file on an ordinary failure, and preserve the underlying error if cleanup also fails. Wrap startup preparation's save error as a `DataFileError` naming the destination so the existing exit-2 branch handles it. The existing single-owner and atomic-replacement model is sufficient for readers and process crashes. At create time calculate the deadline before allocating or mutating anything. In the enabled persistent path, stage the new ticket and next number along with copies of the existing audit and outbox. Use their normal append/enqueue operations, preserving pending-key deduplication and next event ID. Save the staged snapshot, then publish it to the live store synchronously before returning HTTP 201. With no await between staging, save and publication, another request or worker tick cannot observe the draft. A pre-publication failure follows the existing generic 500 and logging path and leaves subsequent reads, saves and retries free of the failed creation. Keep the disabled request path's existing response and failure semantics while including due in its successful saves.
- **Identifier exhaustion (U-11, U-14, C-67, C-78–C-79, C-192–C-193, C-206–C-207, C-238).** Both 1.4.0 counters load at `Number.MAX_SAFE_INTEGER`, but incrementing either at that limit would write a file both releases reject. In either persistent visibility mode, preflight ticket and outbox allocations before mutating the ticket, audit or outbox. The final usable allocation is one below that limit and leaves a readable file with the counter at the limit. Apply the outbox check only when create or resolve would actually enqueue a new event, using the existing pending-key rule. Preparation, ordinary edits, deduplicated resolves and delivery saves can continue without consuming the exhausted identifier. Keep the reader's accepted counter range.
- **Visibility belongs at the edge (U-1, U-2, U-9, U-12, C-12–C-22, C-50, C-54–C-55, C-93, C-96–C-108, C-136–C-155).** A store-wide field removal risks erasing deadlines on worker or shutdown saves. Use one ticket projection at the five HTTP ticket-response shapes, including all list items and no-op patches. Keep the seven legacy fields and ordering in disabled mode. Leave history, health, outbox, actor handling and error responses on their current paths. The body allowlists already reject `due` on all three write routes. Patching priority/title or transitioning changes only the existing fields and never reassigns a deadline. Keep audit creation's four fields, existing notification payloads, and the no-op behavior for timestamps, audit and outbox. Direct store callers and the CLI need sensible optional settings without relying on the environment or implicitly triggering preparation. The service supplies a complete default schedule even for programmatic callers whose settings predate these additions. CLI store construction stays read-only.
- **The matching rule depends on whether the restriction is applied (U-3–U-5, U-9, C-21, C-23–C-41, C-110–C-125, C-157).** `matchesFilters` uses OR today despite the API prose. Leave its default behavior for disabled lists, plain enabled lists, enabled `overdue=false`, and CLI lists. When visible, parse the first decoded `overdue` value via `URLSearchParams.get`, accept exactly `true` or `false` and reject empty, bare or other decoded values with an `InvalidError` naming the parameter. Disabled skips validation of the new parameter entirely. Keep the default parser result shape for callers without the restriction. For true, validate the cursor and take one clock sample, use the existing `isActive` and numeric `Date.parse(due) < now`, then require each supplied status/priority filter as well. A missing deadline in a direct store read cannot qualify. Reading overdue or crossing a deadline does not write, change status, or enqueue work. Existing cursor semantics continue strictly after the returned numeric ID even if it no longer qualifies. Across moving pages, a ticket that newly qualifies at or below the cursor can appear in a fresh scan.
- **Rollback can read immediately but preserves due only through the copy (U-11, C-67–C-73, C-138, C-163, C-180, C-186–C-187).** 1.4.0 loads the version 1 document and strips the unknown field from its live records. A ticket change, delivery save or even graceful shutdown can rewrite the file without deadlines. Document copy-before-handoff after the new owner has stopped. For return, stop 1.4.0, back up its latest file, and recover only the saved deadlines for matching ticket IDs from the retained copy. Use the latest file for ticket data, audit, outbox and both counters. Verify the copy belongs to the same file lineage and check the recovered creation instant for matching tickets. Preserve existing valid deadlines and flag conflicts for correction. Validate the merged version 1 state and replace the file whole while the owner is stopped. Restart disabled to fill only the remaining gaps, verify all tickets, then restart enabled. The file written by the new release itself needs no conversion or restoration to start 1.4.0.
- **CLI output has two consumers (U-12, U-13, C-210–C-230).** Continue falling back to `DATA_FILE` with `--data` taking precedence. Keep `show` history and the current errors and exit codes. Preserve `allTickets` numeric cursor traversal across 100-ticket pages. Use visibility only in the ordinary table and details, including mixed prepared and legacy tickets. Keep the raw output headerless with ID, status, priority and title in exactly that order, and preserve empty raw stdout, human empty-list text and the report's total and status/priority counts. Current HTTP text validation protects the raw delimiter contract for tickets produced by the service. Preparing or reading a file does not apply stricter HTTP text rules to legacy records.

## Build order

1. Add the shared calculation and schedule/gate configuration. Check all defaults, exact gate spellings, independent overrides, whitespace and representability, including the final Date millisecond. Leave the existing config and query test signatures usable.
2. Extend persistence to round-trip optional `due`, reject malformed or nonpositive stored relationships and maintain version 1. Add the startup preparation and refusal paths over the fully validated state, and save using the atomic replacement path. Check legacy, mixed, prepared and empty documents and verify startup failure leaves the original.
3. Assign `due` on create, preflight persistent identifier allocation, and stage the enabled persistent creation with its sequence, audit and outbox effects. Connect service config and HTTP ticket projection. Check the save-before-success guarantee, failure followed by retry, and the complete enabled and disabled response shapes before changing the list query.
4. Extend list parsing and matching with the distinct overdue option. Exercise strict cutoff, conjunction against current values, ordinary OR behavior, and numeric pagination before adding CLI presentation for saved deadlines. Run CLI and report checks in both visibility modes.
5. Finish the API reference, README, operations runbook, decision 0009 and index, 1.5.0 package version and changelog. Walk through production preparation, activation, rollback to the actual baseline and recovery. Run focused and full tests and compare existing test files to the baseline.

## How we will know

Use existing HTTP helpers on port 0 with an injected manual clock and worker off unless testing delivery. Use isolated temporary directories and explicit env for process tests. Start the real entry point when testing process exit or signal behavior, wait for confirmed readiness or exit, stop only the process started and wait for it before reusing the file. Assertions about the file at startup or immediately after a request happen before teardown. Cover the following in the build's new tests or release checks.
