Verdict: reject
## Findings
- Each new ticket gets a deadline based on its creation time, original priority and the response hours in effect at creation. The flag gates API visibility, and later priority and schedule changes leave the deadline fixed. | The new release skips assignment for tickets created with the flag off, even on a file where deadlines have already been enabled. On re-enabling, it assigns those tickets deadlines using their latest priority and the new schedule. | Probe: With the clock at `2025-09-01T08:15:00.000Z`, start with `PORT=0 DUE_TIMES=on` and POST an urgent ticket. Its saved deadline is `2025-09-01T12:15:00.000Z`. Restart the same release on the same `DATA_FILE` with `DUE_TIMES=off DUE_HOURS_URGENT=4`, then POST two urgent tickets. Both return 201 with the legacy response and both disk records lack `due`. PATCH the first new ticket (`T-0002`) to low, leave the second (`T-0003`) urgent, and restart with `DUE_TIMES=on DUE_HOURS_URGENT=6`. GETs return `2025-09-08T08:15:00.000Z` and `2025-09-01T14:15:00.000Z` respectively. The creation-time schedule gives both tickets a deadline of `2025-09-01T12:15:00.000Z`.
## Decisions made for the requester
- Read one `DUE_HOURS_*` environment override per priority at startup, use the defaults for empty values, and accept positive safe whole hours | Use a single schedule setting, reload settings while running, or support zero and fractional hours.
- Reject an enabled create whose deadline exceeds the timestamp range with HTTP 500 and refuse preparation with a file and ticket diagnostic | Clamp the deadline or return a specific API error for overflow.
- Keep the existing status-or-priority match when both filters accompany `overdue=true`, then require overdue eligibility | Require both status and priority on overdue requests.
- Treat a single `overdue=false` as an ordinary listing and return HTTP 400 for empty, malformed or repeated values when enabled | Ignore malformed values or use the first value when repeated.
- Prepare missing deadlines on enabled startup before opening the listener and allow enabled operation with in-memory state when no data file is configured | Provide a separate preparation command or require a data file for all enabled operation.
- Store deadlines as an optional field in the version-1 ticket record and omit first assignment from the audit log | Store deadlines separately or record assignment in the creation audit or a backfill entry.
- Refuse enabled startup for malformed saved deadlines and preserve their stored values while off | Treat malformed values as missing and calculate replacement deadlines.
- Backfill again on re-upgrade if a 1.4.0 save has removed the deadlines | Retain the original assignments in storage that survives a 1.4.0 rewrite.
- Keep human-readable CLI output in its existing format | Display deadlines in the CLI table or ticket details.
