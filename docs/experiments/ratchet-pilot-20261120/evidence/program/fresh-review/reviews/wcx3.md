Verdict: reject
## Findings
- Existing ticket queries keep their results when the deadline feature is enabled unless the new overdue filter is requested | The enabled API changes an ordinary status-and-priority listing from matching either filter to requiring both | Probe: On each release, create an open normal ticket `T-0001` and move an urgent ticket `T-0002` to `in_progress`. `GET /tickets?status=open&priority=urgent` returned 200 with both IDs on 1.4.0 and on the delivered release with the flag off. With `DUE_TIMES=on` it returned 200 with `items: []`, including with `overdue=false`.
- Preparing the production file must give its existing tickets deadlines before activation and keep one live snapshot available for rollback | Preparation succeeds through a symbolic link by replacing the link with a separate file, leaving the backing production file unprepared | Probe: Point `live.json` at a one-ticket `production.json` and run `DATA_FILE=live.json npm run prepare:due-times`. It exited 0 and `live.json` became a regular file with `due`, while `production.json` still lacked `due`. An enabled start using `production.json` exited 2 with `tickets[0].due (T-0001) is missing`. After creating `T-0002` through the enabled service on `live.json`, 1.4.0 listed both tickets from `live.json` and only `T-0001` from `production.json`.
- A legacy ticket's due time is based on its creation instant plus its response hours | Preparation and activation accept a deadline earlier than an explicitly offset creation instant when the legacy timestamp uses an RFC-style spelling, so a ticket can appear overdue before it was created | Probe: For an urgent ticket created at `Mon, 01 Sep 2025 08:15:00 +0200`, preparation with no `due` exited 0 and assigned `2025-09-01T10:15:00.000Z`. With `due` already set to `2025-09-01T06:14:59.998Z`, preparation also exited 0 and the enabled service returned the ticket from `GET /tickets?overdue=true` at `2025-09-01T06:14:59.999Z`, one millisecond before its creation instant.
- With due times off, HTTP answers match 1.4.0 | The delivered service refuses the final ticket-number allocation on a file that both versions accept at startup, protecting the file from an unsafe next counter | Probe: Start each version with the flag off on separate copies of a version-1 file with `nextNumber: 9007199254740991`. `POST /tickets` with a valid urgent ticket returned 201 and ID `T-9007199254740991` in 1.4.0, which saved `nextNumber: 9007199254740992`. The delivered version returned 500 `internal` and kept the counter at `9007199254740991`.
## Decisions made for the requester
- Read four separate `RESPONSE_HOURS_*` environment variables at startup, accepting whole elapsed hours including zero | Use a configuration file or accept fractional hours.
- Use `overdue=false` to disable the extra filter and return 400 for malformed enabled values | Treat false as a separate search for tickets that are not overdue, or silently ignore malformed values.
- Store `due` as a UTC ISO timestamp on each ticket in the existing version-1 JSON file | Store deadlines in a separate file that must be backed up alongside ticket state.
- Assign historical deadlines with a separate offline command and refuse enabled startup on an incomplete existing file | Backfill missing deadlines automatically during enabled startup.
- Leave tickets created with the flag off unassigned until preparation | Assign deadlines during dark operation and hide them until activation.
- Keep deadline metadata out of audit entries and notification payloads | Add the deadline to the creation audit and the receipt notification.
- Show saved deadlines in enabled `tickets show` while keeping list columns stable, and escape embedded tabs and line breaks in legacy raw titles | Add a deadline column to CLI lists or continue emitting embedded separators literally in raw rows.
- Restore deadlines during roll-forward from an explicitly supplied pre-rollback copy matched by ticket ID and creation text | Discover the copy automatically or add a separate persistent store for promises.
- Interpret ambiguous offset-free legacy times using Node's rules in the operator's recording zone, choosing the earlier occurrence in the repeated hour and moving skipped times forward by the clock gap | Require the operator to supply an explicit offset for those records before preparation proceeds.
