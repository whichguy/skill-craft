Verdict: reject
## Findings

- A deadline must be the ticket’s creation instant plus nonnegative response hours, and production activation requires usable deadlines | Preparation, recovery and enabled startup accept deadlines earlier than creation when an explicit offset is written in a legacy format | Probe: Set `T-0001.created` to `Mon, 01 Sep 2025 08:15:00 +0200` and `due` to `2025-09-01T06:14:59.999Z`, one millisecond before creation. `DATA_FILE=state.json npm run prepare:due-times` exited 0, and enabled `GET /tickets/T-0001` returned 200 with that `due`. Supplying the same bad deadline only in `DUE_TIMES_RECOVERY_FILE` also exited 0 and copied it into the live file. With `created` written as `2025-09-01T08:15:00+02:00`, preparation and startup both exited 2.
- Preparation must add due times to the production snapshot that activation and rollback use | Preparing a symlinked `DATA_FILE` replaces the link with a separate file, leaving the backing snapshot unprepared. The runbook gives no instruction to use the backing path consistently | Probe: Run `ln -s backing.json production.json` with a legacy `T-0001` in `backing.json`, then `DATA_FILE=production.json npm run prepare:due-times`. It exited 0 and `production.json` became a regular file. Enabled startup on the backing path exited 2 for missing `due`. After an enabled `POST /tickets` through the configured path returned 201 with `T-0002`, 1.4.0 listed both tickets through `production.json` and only `T-0001` through `backing.json`.
- In 1.4.0, an ordinary ticket listing with both `status` and `priority` includes tickets that match either filter | Activating deadlines changes existing queries to require both filters even when `overdue` is absent | Probe: Seed `T-0001` as open and low and `T-0002` as in progress and urgent. `GET /tickets?status=open&priority=urgent` returned 200 with both tickets on 1.4.0 and on the delivered release with `DUE_TIMES=off`. With `DUE_TIMES=on` it returned 200 with an empty list.
- With due times off, HTTP answers must match 1.4.0 | The delivered release rolls back visible ticket changes when a save fails, which changes subsequent dark-mode reads | Probe: Start each release with `DUE_TIMES=off` and a file-backed `T-0001` titled `Before`. Move the data file’s parent directory aside and put a regular file in its place. `PATCH /tickets/T-0001` with `{"title":"Attempted change"}` returned 500 `internal` on both releases. The next `GET /tickets/T-0001` returned 200 with title `Attempted change` on 1.4.0 and `Before` on the delivered release.
- With due times off, 1.4.0 accepts an allocation at the largest safe ticket number | The delivered release refuses the allocation in dark mode to keep the next counter readable | Probe: Start both releases on separate copies of a version-1 file with `nextNumber: 9007199254740991`, `DUE_TIMES=off` and the worker stopped. `POST /tickets` with `{"title":"Allocation","requester":"desk"}` returned 201 with `T-9007199254740991` on 1.4.0 and 500 `internal` on the delivered release.

## Decisions made for the requester

- Configure four independent `RESPONSE_HOURS_*` environment variables as whole elapsed hours, including zero, and read them at startup or preparation | Use a reloadable schedule file that supports fractional hours.
- Assign deadlines to existing tickets through a separate offline `npm run prepare:due-times` step and require readiness before enabled startup | Backfill during enabled startup before opening the HTTP listener.
- Store `due` as a UTC ISO string on each version-1 ticket record and use an optional separate pre-rollback snapshot to recover promises after 1.4.0 rewrites the file | Keep deadlines in a persistent sidecar that 1.4.0 does not rewrite.
- Use the recording `TZ` and Node’s local-time parsing for offset-free legacy dates. For urgent tickets in `America/Los_Angeles`, preparation accepted the repeated `2025-11-02T01:30:00` and the skipped `2025-03-09T02:30:00`, producing `2025-11-02T12:30:00.000Z` and `2025-03-09T14:30:00.000Z` respectively. The runbook leaves those exact choices implicit | Require an explicit offset or operator correction for ambiguous or nonexistent local times.
- Treat `overdue=false` as disabling overdue filtering, return 400 for other unrecognized values when enabled, and use the first occurrence of a repeated parameter | Accept only `overdue=true` and reject all other supplied values and duplicates.
- Display the deadline in enabled CLI `show`, and keep the existing table and four raw columns with visible escapes for embedded title delimiters | Add ticket deadlines to the CLI list and use a new format for script output.
