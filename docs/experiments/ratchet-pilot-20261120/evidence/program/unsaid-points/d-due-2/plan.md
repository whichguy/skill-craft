## Approach

Keep the Node.js CommonJS service dependency-free. Use `src/config.js` for the exact `DUE_TIMES=on` switch and the response schedule, and pass those settings through `createService` to the store and HTTP app. Keep a single due calculation in `src/tickets/`, shared by creation and preparation. The store assigns the deadline from the same creation instant it records on the ticket, or from the saved creation instant and priority during preparation.

Add an optional `due` property to the **ticket record** in the existing version 1 document, using `src/persistence.js` on both load and save. Keep persisted deadlines independent of HTTP visibility. In `src/app.js`, use one ticket response projection for the five ticket-producing routes, including each item of a list page. Parse `overdue` only in enabled HTTP requests, pass an explicit overdue constraint into `TicketStore.list`, and use the existing ID ordering and paginator. The existing write validators, audit actions, notification triggers and CLI formatters already provide the intended interfaces.

Add a one-shot preparation entry point, proposed as `node scripts/prepare-due-times.js` using `DATA_FILE` and the same response-hour settings. It opens and checks the existing state using the normal reader, invokes a store operation to fill missing deadlines, commits a whole-file replacement if needed, and reports completion. File-backed enabled startup checks the loaded state before listening or starting the worker. Document the configuration, enabled API, offline rollout and rollback sequence in README and the API and operations docs. Record the optional version 1 field and release change using the repository's decision and changelog conventions.

## Decisions

The choices below give the build a concrete path through the open points. Record the answers actually taken in the build report. The options marked `Open:` in the specification remain open for contract testing.

|---|---|---|
| C-3, C-4, C-9 | Use four variables `DUE_HOURS_URGENT`, `DUE_HOURS_HIGH`, `DUE_HOURS_NORMAL`, `DUE_HOURS_LOW`, with independent defaults of 4, 24, 72 and 168. Reuse the trimmed decimal whole-number convention, with unset or blank selecting the default and explicit values 1 through `Number.MAX_SAFE_INTEGER` hours. Read settings once at process startup or per preparation invocation. Validate the schedule for enabled service startup and the explicit preparation command. Disabled HTTP startup ignores these settings. | A JSON map needs its own grammar and error reporting. Live reload needs a policy for when a changed schedule starts applying. |
| C-5 | Calculate elapsed milliseconds from the saved or newly captured instant. With the proposed configuration range, use exact integer arithmetic for the hour multiplication and addition, then check the inclusive Date bounds before converting the result to a Number and calling `toISOString()`. If the result is out of range, fail the assignment. Give the operator context in the diagnostic, including the relevant setting and ticket for preparation. Use the existing logged internal error path for a create that cannot calculate a valid deadline. | Calendar arithmetic changes behavior across time zones or daylight saving boundaries. Clamping or wrapping creates a different promise. |
| C-6, C-9, C-17, C-24 | Store the optional ticket property inline in version 1 and hide it at the HTTP response boundary when disabled. The 1.4.0 reader already projects known fields, so the old binary can read this layout directly. | A version bump is refused by 1.4.0. A sidecar would add another commit point and complicate restart and rollback. Hiding at load time would discard saved deadlines on the next write. |
| C-11, C-12, C-14 | On enabled HTTP lists, recognize exactly one literal `overdue=true`, leave an absent argument unrestricted, and send other supplied values or repetitions through `InvalidError`. Combine overdue with the result of the existing legacy matcher, which uses OR when both status and priority are supplied. Preserve all existing parser validation and defaults. | Accepting `false` as an unrestricted query and using AND for the two legacy filters on overdue requests are also possible policies. Reusing the current matcher avoids changing how agents' existing filter combinations behave when adding overdue. |
| C-15–C-17, C-23, C-32 | Prepare offline with an explicit command and the existing single-writer operating model. Stop the current writer cleanly before taking the preparation snapshot. Disabled creates leave `due` absent. A successful command reports how many were filled and that all saved tickets are ready, including zero when already prepared. Enabled startup rechecks readiness independently. Require an existing file for the file-backed preparation path and enabled startup, so a mistaken path cannot look like a successful rollout. A real, valid empty file is ready. For a fresh file the operator can start and stop the disabled service to write an empty state. Allow enabled memory-only use outside the file-backed rollout, starting from an empty store. | Startup preparation and continued writes during migration would tie activation to a mutation or need writer coordination. Treating a missing file as empty is convenient for bootstrap but can conceal a wrong production path. |
| C-9, C-16, C-18 | Treat an absent property as eligible for fill. Preserve any present value when projecting a legacy-compatible version 1 record, so a disabled process can read and resave old-reader-compatible data. During readiness checks and preparation, require each present due to be a valid canonical UTC millisecond ISO string. Refuse malformed present values with file and ticket context and leave repair to the operator. | Treating malformed as missing can silently move a saved promise. Rejecting the file in the shared reader for a field 1.4.0 ignores would change disabled startup and CLI behavior. |
| C-19–C-21, C-28 | Make backfill an administrative store operation that only adds missing due fields. Leave `updated`, audit entries, sequence numbers and outbox state as saved. | C-22 | For persistent enabled creation, calculate the deadline first and stage the candidate state using the existing audit and outbox representations. CLI deadline display is optional. |

## Nuances

- **C-2–C-5, C-7, C-15 and C-22.** The validator supplies normal for an omitted priority. Pass the effective priority and the exact captured `created` value into assignment. Preparation uses each record's `created` and saved priority, including on final tickets and on legacy timestamps accepted by the existing `Date.parse` check. Do not tighten that legacy check while requiring canonical output for new deadlines. Avoid assuming the intermediate duration itself must fit in the Date range. A negative creation epoch can make the final instant fit even when the duration exceeds that range. An unrepresentable create must fail before allocating an ID or queueing an audit entry or notification.
- **C-6–C-9, C-17, C-20 and C-26–C-28.** `get`, `list`, `create`, and `apply` return ticket copies, including the no-op patch path. Project all of them at the HTTP boundary without deleting from a live store record. Keep old responses identical on prepared files and keep `due` out of the accepted write-field lists. Patching a priority affects the priority filter immediately while leaving the assignment fixed. Reopening an expired ticket can make it overdue again. Deadline checks add no transition guards, notifications or audit activity.
- **C-9–C-14.** `matchesFilters` calls `some` over generic field/value entries. Putting `overdue` into that map can give OR semantics or compare against a nonexistent ticket property. Keep it as a separate mandatory predicate. Validate existing query arguments even if the overdue result could be known to be empty. Use one snapshot of the service clock per overdue query, compare epoch milliseconds with strict `<`, and restrict eligibility to `open` and `in_progress`. ISO strings with expanded years do not sort safely against ordinary years. Apply both eligibility and legacy filtering before pagination. Reuse numeric ID ordering, cursor decoding and the store's ticket-ID check for decoded cursors. A later page reevaluates the conditions at its own time but still starts strictly after the cursor ID, even if that ID no longer qualifies.
- **C-15–C-19, C-21 and C-32.** The service saves the entire in-memory snapshot on changes, worker delivery attempts and shutdown. Running an offline preparer beside any writer can lose either deadlines or tickets even though each replacement is atomic. Stop the writer and wait for final save and process exit, prepare the latest file, then start enabled on that file. If disabled service resumes in between, new tickets can lack deadlines and the operator repeats preparation after the next clean stop. Keep readiness checks before the listen call. Readiness depends on the file actually loaded, with no sentinel or prior success report serving as proof.
- **C-15–C-22.** Prepare every missing value in a candidate snapshot before replacing the live file. Reuse the persistence writer's temporary file in the target directory and rename as the commit point. Calculation and pre-rename write failures must keep the original readable. Use the ordinary file and record diagnostics for bad input and report failed commits with the target path. Only report completion after the replacement succeeds and the saved state is ready. Skip the write entirely if no due times needed filling. A retry after an interruption on either side of rename preserves all previously committed deadlines and the existing inventory, audit entries, outbox states and counters.
- **C-17, C-20–C-22 and C-24–C-25.** Both `readTicket` and `toDocument` use explicit record projection. Confirm that all new-release writers retain present deadlines, including a disabled worker's delivery save and `SIGTERM`. Leave the legacy document layout and its version, timestamp conventions, audit entries and notification records readable by 1.4.0. A mock that reconstructs old responses from the new reader cannot detect a real rollback failure. Take any comparison copy before starting 1.4.0. Its ordinary shutdown save can strip due fields even during a rollback that only served reads.
- **C-1, C-4, C-18, C-23 and C-33–C-34.** `createService` is called with hand-built settings from `test/helpers.js`. Keep absent due settings equivalent to disabled for existing callers. Give the preparation command an explicit call to the shared schedule loader. Passing its environment through the ordinary disabled server path would skip the overrides it needs, and making it use enabled server startup would reject the very file it needs to prepare. Startup config and readiness errors need to occur inside the current startup error handling, which logs to stderr and exits 2. Keep `npm start`, normal health and port behavior, and `node --test` discovery. Put any frozen release fixture in a format that test discovery will not execute.

## Build order

1. Establish a baseline with `npm test` and identify the unmodified 1.4.0 sources at `5daec3e5bb9e7a446a11d55d40065e0cb4840087` in this repository. Keep a reproducible source for the rollback check before editing service files.
2. Add schedule parsing, timestamp calculation and the persistence field round trip. Check default and overrides, disabled config isolation, date bounds, and legacy reader compatibility. Keep scope in configuration and ticket/storage modules.
3. Add store assignment and wire enabled creation, readiness and HTTP projection through `createService`. Check creation (including omitted priority), all response paths, immutable due times and disabled response parity. Exercise failure before commit before depending on the new state for listing.
4. Add the overdue query constraint and check it through real HTTP requests with a controlled clock, current status/priority and more than one cursor page. Check unchanged legacy list/query behavior.
5. Add the offline preparation command over the store's shared calculation and persistence save. Check mixed and complete files, failed saves and retries, preservation under disabled writes, and stable activation after restart. Document exact commands, settings, single-writer order, readiness and rollback limitations.
6. Add the new `node:test` cases under `test/` as the behaviors land, then run all of them with `npm test`, including the unchanged suite. Use stock Node and a checked-in inert fixture of the original 1.4.0 runtime sources, extracted into a test temporary directory, to exercise actual old startup without needing Git in the distributed test environment. Source the fixture byte-for-byte from the baseline and keep provenance with it. Finish by checking the rollout, rollback and operational commands against a disposable file.

## How we will know

Each check below targets the clause observables. Use the setting names and operator workflow recorded by the build to drive the checks. For an open point, assert only the stated invariant and accept reasonable choices on the open part.

- **U-1 (C-1, C-2, C-5, C-6, C-8, C-23).** Start the normal entry point on port 0 and check health on the reported port. With `manualClock` at the specification instant, assert all four exact default UTC due values and a separate omitted-priority create. The existing `ticketBody` helper supplies a priority, so explicitly omit it. Exercise due on 201 create and 200 read, patch, transition and list, including resolved and closed tickets. Submitting `due` in any write body still returns 400 `invalid`. Exercise a representable assignment at the upper Date boundary and one millisecond beyond it using a supported schedule. Inspect persisted state after a failure.
- **U-2 (C-3, C-4, C-7, C-17, C-22, C-26–C-28).** Change the configured schedule and verify that a later assignment uses it, then read a previously created ticket and patch its title and priority, resolve and reopen it, and prove its exact saved due time still holds after restart. Check no-op audit and update behavior, original lifecycle errors, and creation/resolution notification behavior. Give a malformed override under the build's syntax to an operation that consumes it and verify the setting is named. Check stderr and exit 2 if the configuration prevents startup. Verify a successful file-backed create survives restart with its due, audit and outbox entry together. Use a deterministic pre-rename failure or interruption check to verify a readable whole state, with no partial ticket/audit/outbox commit.
- **U-3 (C-9–C-14).** Seed past, equal and future deadlines under every relevant state. Advance the injected clock by one millisecond from equality and repeat the request. Include a reopened ticket, a priority edited after assignment, existing status and priority filters each alone, a resolved or closed status alone, and a combined-filter case where every returned ticket must be overdue regardless of the chosen legacy combination. Interleave eligible and ineligible IDs across a numeric width boundary, fill pages up to the requested limit, follow a cursor after the last returned ID and change eligibility on the next request. Verify default and limit bounds, malformed cursor and filter errors, final-page `next`, and the exact empty envelope. Check unrestricted enabled listing as well as disabled listing with `overdue` present.
- **U-4 (C-9, C-15–C-21, C-32).** Seed a valid legacy file covering all four states, with later `updated` times, audit history and pending, sent and dead outbox entries. Also cover mixed already-assigned and missing dues. Observe the documented readiness workflow and compare file contents, ticket inventory and next ticket number. Check original audit and outbox values with the worker off. Exercise a malformed saved due, an already-bad legacy record, and an injected failure before commit. Check readiness never serves unprepared data, including a stale check followed by a new ticket without a saved due. For a build that completes preparation at startup, observe the saved file before the first enabled response. Test an empty file, repeat preparation under changed hours and confirm saved values stay fixed. Start disabled on prepared data, compare status codes and response bodies to 1.4.0 for representative routes and query values, run a ticket mutation and an outbox delivery save, stop with `SIGTERM` and inspect the resulting file for retained deadlines. Start enabled on ready data and compare API due values to disk.
- **U-5 (C-24, C-25, C-32).** Use the original 1.4.0 server to seed the legacy state, then prepare, activate and write at least one new ticket with the new release. Stop the writer cleanly and run the original server on the same last-written file with `PORT=0` and its worker off. Check health, walk all cursor pages and compare the exact ID set with the pre-rollback inventory. Fetch carried-over and new IDs individually and check their original ticket fields. The old server must read the new file directly. No assertion should require deadline recovery after a 1.4.0 rewrite.
- **U-6 (C-29–C-31).** Compare weekly JSON counts before and after preparation, including every state/priority bucket. Use both `DATA_FILE` and `--data` for CLI show/list, exercise existing status and priority options and verify the four raw fields by position. Compare file bytes before and after the read-only invocations. Human-readable due display remains an open choice.
- **U-7 (C-33, C-34).** Run `npm test` on Node 22 or later and check discovery of the new cases and passing pre-change cases without editing their files or narrowing the test command. Reuse the existing HTTP helper and manual clock where appropriate. Use isolated fixtures, free ports and PID-specific cleanup for spawned servers.
