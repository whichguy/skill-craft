## Approach

Keep assignment in `TicketStore`, selection in the existing store listing, wire-format visibility in `createApp`, and durable representation in `src/persistence.js`. Use one deadline calculation for creation and preparation. Pass the validated schedule and the exact `DUE_TIMES=on` flag from startup through the existing composition in `src/server.js`. The request validators already reject client-supplied `due`. The HTTP feature gate covers both response projection and query parsing.

Add optional `due` to ticket records in the existing version-1 whole-state file. Support an offline operator command that loads, validates, assigns and saves missing deadlines through the same store and persistence code as the service. Enabled startup checks completeness before it listens or starts the worker. Enabled creates persist the complete new state before returning 201. The existing read-only tools continue to use the shared reader.

## Decisions

The choices below resolve implementation details for this build. Record the answers to the specification's open points in the build report. Verification of a clause must allow the other reasonable answers its `Open:` line permits.

| Clauses | Choice and reason | Alternative considered |
|---|---|---|
| C-1–C-4, C-19 | Use one environment setting per priority, `DUE_HOURS_URGENT`, `DUE_HOURS_HIGH`, `DUE_HOURS_NORMAL`, `DUE_HOURS_LOW`. Reuse `wholeNumber` with 1 through 2,400,000 hours inclusive, the whole hours in one Date half-range. This keeps the millisecond interval exactly representable. Each priority can be overridden independently. Unset and blank values take the defaults. Read a schedule at enabled startup or preparation. The disabled service and read-only tools need no schedule. | A combined JSON setting requires parsing an additional format. Validating unused settings could break disabled startup. |
| C-5, C-14, C-21 | Retain the stored value in the store. Project ticket responses at the HTTP boundary and omit the field when disabled. Keep old constructor and query-parser callers working through defaults. | Removing deadlines when loading for disabled operation loses them on the next save. |
| C-10–C-13 | Accept a single literal `true` for an enabled overdue query. Treat other supplied values and duplicates as malformed using `InvalidError`. Keep the current status/priority union when both are supplied, and combine its result with the overdue predicate using AND. This retains the existing filters' implementation in both modes. | Silently accepting malformed values can broaden an agent's listing. Changing the legacy union while adding overdue would change an independent behavior. |
| C-15–C-18 | Provide `DATA_FILE=… node bin/tickets.js prepare-due`, using the CLI's existing `--data` override too. Require the operator to stop the writer before preparation. Print completion only after successful save or confirmation that an existing file is already complete. Disabled creates have no deadline until the next preparation. Enabled startup refuses a configured file containing any missing deadlines, naming the file and a ticket and pointing to preparation. A genuinely empty store can start enabled. | Lazy assignment or background migration can expose partially prepared results. Startup backfill would couple initial assignment to service restarts. |
| C-19–C-21 | Treat absence as the legacy case. Validate present deadlines during preparation and enabled startup as canonical UTC ISO strings, including expanded years emitted by `toISOString()`. Report an invalid or unrepresentable value with the file and ticket or record field. Disabled service and read-only CLI preserve the old interpretation of base records. The shared codec carries through a present deadline even in those modes. | Recalculating a present bad value silently would change historical data. Rejecting that extra field during disabled operation could refuse a file the old service could use. |
| C-22 | For an enabled file-backed create, stage the ticket, next sequence, audit append and outbox enqueue, using the existing audit and outbox logic. Save the candidate and publish it to the live store only after the rename succeeds. A failed save leaves the live store ready for a retry. | The existing mutation-before-save sequence can leave a failed create in memory, which a later worker save or shutdown could commit. Keep this fix scoped to the new enabled creation path. |
| C-23–C-27 | Keep the original `updated` during preparation and leave existing audit and outbox data alone. Use the existing creation audit fields with due times enabled, with no extra audit entry for assignment. Preparation assigns metadata without invoking create, patch or transition. | Using lifecycle mutations for backfill would change timestamps or history and could replay notifications. |
| C-29–C-30 | Store additive `due` on each ticket under version 1 so 1.4.0 can read the same file. Document that a 1.4.0 write can discard the field. If later upgrading a file with missing values, prepare that file following the normal procedure. Preserve a copy if the assigned values are needed for investigation. | A schema version bump makes 1.4.0 refuse startup. A second store would add coordination and recovery work beyond rollback readability. |
| C-31–C-32 | Keep human-readable CLI output and its read commands as they are, independent of the API flag. Preserve the raw four-column format. Give preparation its own named command and usage. | Exposing deadlines through table or raw output creates another display policy and risks breaking the weekly report. |

## Nuances

- **U-1, C-1–C-6, C-19.** Calculate from the exact instant recorded as `created`, after request validation has defaulted priority. An extra clock read or calendar arithmetic can shift the promised deadline. Convert elapsed hours to milliseconds, check the summed instant against both inclusive Date boundaries before formatting, and use UTC ISO output. Use an internal error through the existing HTTP envelope if an enabled create cannot calculate a deadline, before changing the ticket number, audit or outbox. Startup configuration errors should use `ConfigError` and name the variable. Legacy files can include any creation string accepted by the existing reader, so derive the instant from its parsed value and retain the original `created` text.
- **U-2 and U-3, C-5–C-12, C-14.** Updates, transitions and no-op patches return ticket copies, and each of those responses also needs the same visibility rule as creation and detail. Project every list item while preserving the page envelope. Leave audit, health, outbox and error responses on their current paths. Keep `overdue` out of the generic status/priority filter map. Use the existing `isActive` helper and a single `clock.now()` per overdue query, compare timestamps numerically with strict `<`, and leave a reopened ticket's deadline alone. The disabled parser must skip even malformed overdue values entirely. Keep its exact legacy return shape of `{ filters, limit, after }`, which existing tests compare by deep equality. Add an overdue query option only for an enabled request that supplies it.
- **U-3, C-12–C-13.** Filtering after cursor paging can underfill pages or emit a cursor for a nonmatch. Apply both predicates before calling the existing numeric ID sort and paginator. Keep cursor decoding, ID validation, limit handling and the null sentinel intact. Each new request evaluates overdue membership again. A cursor continues after its ID even if that ticket has since stopped matching. A ticket with a lower ID that becomes overdue between pages only appears on a fresh traversal, since the cursor represents position rather than a time snapshot.
- **U-4, C-15–C-20, C-23–C-25, C-28.** Stage all calculations before committing preparation, including closed and resolved records. Preserve every present valid deadline exactly without reapplying the schedule. Carry ticket sequence, audit order and contents, and outbox events and sequence into the same save. A bad later record or a rename failure must prevent a success message. Use the existing same-directory temporary write and rename, wrap preparation save failures in a file diagnostic and handle them with the CLI's data-file exit path. Use the `env` injected into CLI `main` for schedule settings as well as the file path, and handle `ConfigError` there as an operator diagnostic. An abandoned temp file is never loaded as production data. A file with zero tickets passes readiness. An explicitly targeted missing file should be diagnosed by the offline command so a typo cannot be reported as prepared. First service start with no existing file remains supported.
- **U-4, C-14–C-18, C-21–C-22.** Follow the one-writer contract from decision 0008. Stop the disabled service and wait for its final save before preparing. Start enabled on that file as the next writer. A disabled service started between these steps could create a missing deadline, so enabled startup must inspect every ticket each time, even after a prior successful preparation. A marker or count from an earlier run cannot establish readiness. Check the version-1 record codec in both directions because worker, shutdown and disabled writes all go through it. In the enabled creation path keep staging, save and publication synchronous so another request or worker tick cannot see intermediate state. Reuse the existing audit and enqueue routines for staging, including the saved event sequence.
- **U-5, C-29–C-30.** The old reader reconstructs tickets from an explicit field list, skips additive `due`, and its writer skips it too. Prove compatibility with the real 1.4.0 source at baseline commit `5daec3e` using a separate temporary extraction and a fixture written by the new release. Stop the new writer before starting 1.4.0 on that file. Even graceful shutdown writes the whole file, so use a disposable file for the rollback drill and keep retention checks on a separate fixture.
- **U-6 and U-7, C-31–C-36.** The CLI opens the store without persistence by design for reads. Only the new command should use a writer. Shared parser and store defaults matter because the existing tests and CLI bypass service configuration. Keep CommonJS and the existing npm script entry points. In the build, document settings, the enabled query and the exact preparation/activation/rollback commands in the existing docs. Describe the simultaneous filters according to the chosen union, including the overdue requirement for every result. Follow the repository's release and decision-record conventions for the additive file format.

## Build order

1. Add and check the shared schedule parser and deadline calculation, including direct service construction with defaults and Date endpoints. Thread configuration through the service while retaining disabled defaults for callers that omit the new properties.
2. Extend version-1 ticket encoding and decoding. Add strict due validation for the modes that use deadlines and implement store preparation over a candidate snapshot. Wire up the CLI command and the enabled startup readiness check. Check mixed and empty files, repeated runs and failure paths before attaching any enabled API behavior.
3. Assign due on create and commit it with the associated ticket state. Add the HTTP response projection to every ticket-returning route. Check both modes against saved data and preserve mutation validators, current audit effects and outbox deduplication.
4. Parse the opt-in overdue query and combine its predicate with the existing filters ahead of pagination. Check clock boundaries and multiple pages. Verify list calls without overdue and existing CLI callers still use their established contracts.
5. Add the new `node:test` files, using existing helpers and real version-1 fixtures as appropriate. Update operator and API docs, add the file-format decision and release notes, and follow the version convention. Run the complete suite and exercise preparation, activation, read-only tools and actual 1.4.0 rollback using disposable files and port 0.
