## Approach

Keep assignment on the existing ticket resource. Add a nullable `assignee` to new tickets in `src/store.js` and to the ticket record reader and writer in `src/persistence.js`. Load older version-1 records with a missing assignment as unassigned. The store's existing copy-on-read behavior exposes the new field from create, detail, list, patch, and transition. The CLI already opens the same saved state.

Register `PUT /tickets/:id/assignee` with the existing router in `src/app.js`. Use the configured JSON reader, a dedicated validator in `src/tickets/validate.js`, and the existing actor parser, then call one synchronous store method. The store owns lookup, the lifecycle guard, equality, and the change itself. Use the existing `apply` path for the update timestamp, audit entry, outbox enqueue, and whole-state save. Add a template in `src/templates.js` and let the existing worker and notifier deliver it.

Extend the list query parser in `src/tickets/query.js` and apply the HTTP filter conjunction in the store before numeric sorting and cursor pagination. Update the human table and full ticket detail in `src/format.js`. Use the existing service, clock, HTTP client and worker helpers for new `node:test` coverage. Keep the existing test files and npm scripts intact.

## Decisions

These are proposed build defaults. The build report should record the choices it actually makes for each open point. Acceptance checks use the observables in the clauses, including where the defaults below are provisional.

| Clause | Proposed choice and reason | Alternative considered |
|---|---|---|
| C-3 | Use 200 with the full current ticket for every accepted operation, following PATCH and transition. | A JSON acknowledgement would require the caller to fetch the ticket for its updated representation. |
| C-5 | Apply the closed guard before checking equality, following PATCH's treatment of closed tickets. | Checking equality first would give the new mutation route a closure exception. A closed same-value request is open either way. |
| C-6, C-27 | Follow the requester validator for names. Trim first, reject empty values and remaining ASCII control characters, and count UTF-16 code units with the existing 64-character precedent. Require well-formed Unicode so a saved name can round-trip through a URL filter. Use the same accepted-name rules at input and persistence boundaries and store the canonical trimmed form. | Grapheme or code-point counting would introduce a different length rule from the requester field. Accepting unpaired surrogates could create a name that URL query decoding cannot reproduce. |
| C-18 | Enqueue one event for each real change to a named agent. Keep pending notices addressed to the original event recipient, including during A → B → A. Use a key containing the event type, ticket ID, and the assignment audit sequence from that change. The sequence survives restart and distinguishes changes in the same millisecond. | The default type/ticket key can discard Sam's notice while Dana's is pending. A recipient-only suffix coalesces a return to Dana, and cancellation would require a new outbox policy. |
| C-19 | Use the agent name as the outbox and notifier recipient and the current JSON-line handoff as the delivery boundary. | A separate address lookup needs a directory or relay contract the service does not have. |
| C-28 | Compare canonical names exactly for both equality and filtering, with case and Unicode normalization preserved. | C-33, C-35 | Keep the four raw columns exactly as they are. Show an explicit unassigned label and distinguish it from a named value in both human views. | Appending a fifth column preserves positions for the weekly report but still changes the row schema for other raw consumers. |
| C-15, C-18 | Use `ticket.assigned` for assignment notices and a dedicated audit action such as `ticket.assignee_changed` for set, replace, and clear. ## Nuances

- **C-6–C-10, C-16 and U-2.** A missing field is invalid, while an explicit JSON null is a successful input. Check the object whitelist and value after the shared reader. Parse the actor before the store's lookup, state check, or no-op decision, following the existing write routes. A hand-rolled parser risks different byte boundaries or closing the connection before an oversize upload gets its JSON error. Unchanged requests still undergo input validation.
- **C-1–C-5, C-11–C-17 and U-1/U-6.** `resolved` can reopen and is eligible for assignment. `closed` alone is final. Compare the canonical value while the store still has the old one, and pass an empty change set or return an unchanged copy on a no-op. Avoid invoking the clock, save, audit or notification path for a repeat. For a real change pass only `assignee: {from, to}` to `apply`, with actual nulls, and use the same change time for the ticket, audit, and notice. Keep POST and PATCH whitelists and lifecycle rules as they are. A status transition, including closing an assigned ticket, preserves its owner.
- **C-15, C-18–C-23 and U-3/U-6.** Pass the audit entry returned by `AuditLog.append` to the existing synchronous effect callback alongside the timestamp. Use its sequence for the notice key. The transition effect can keep using just the timestamp. Identity comes from the real change, so repeated requests exit earlier regardless of whether the original event is pending, sent, or dead. A replacement snapshots its own recipient and ticket in the event, and a clear creates no new assignment notice. The new event must have a matching template or it will appear queued and then die on retries. The existing handoff can repeat an event if the process stops after the notification append and before marking it sent. Preserve the event's ID and key across restart for existing relay deduplication.
- **C-10, C-22, C-24–C-27 and U-7.** A save must include the ticket, audit entry, and queued event in one snapshot, before returning success. The existing write-then-rename handles interruption on disk, but `apply` mutates live state before saving. For a persisted real assignment, checkpoint the affected ticket and the audit/outbox state before calling `apply`. If the synchronous save throws, restore those in memory, including the outbox counter, and rethrow through the existing internal-error path. This keeps a later request, worker tick or shutdown save from committing the failed change. Keep that recovery scoped to the new operation. Neither HTTP calls nor worker ticks can interleave with the synchronous mutation and save in the single process. Delivery failure belongs to the worker and leaves the committed assignment in place.
- **C-11, C-24, C-26–C-27 and U-7.** The record serializer explicitly enumerates fields, so adding the property only to the store loses it at restart. Check own-property presence on the original saved record before defaulting, and fail with the ticket record path on a bad value. Normalize missing assignees before any match, change or display, including when a caller constructs a store directly from an older state. Verify the new version of the service can open old data. The previous binary discards unknown ticket fields on save and lacks the assignment template, so rolling back the binary over a live post-upgrade file can lose active ownership and strand queued notices. A pre-upgrade backup is the compatible restore point under the existing operations model.
- **C-28–C-32 and U-4.** The parser needs three states: absent, present with an empty value, and present with a name. Preserve null as an active filter and continue ignoring undefined predicates supplied by internal callers. The current matcher uses `.some()`, so conjunction matters even on HTTP requests with only status and priority. Filter before taking the page. Treat the cursor as the last numeric ID from the earlier page even if that ticket subsequently stops matching. Compute `next` from remaining matches, including gaps in IDs, and reuse the existing opaque cursor and limit parsing.
- **C-26, C-33–C-36 and U-5.** The CLI reads the same file through `createPersistence`, then walks all pages. Put display logic in its existing human formatters. Choose a representation where a legitimate name such as `Unassigned` looks different from the null label, for example by quoting named values. Escape accepted Unicode line separators in both the ownership display and assignment history text so an agent name cannot split a row or a history entry. Preserve the CLI's existing flag behavior, raw columns and no-results output, and check the weekly report against a file containing assignments.

## Build order

1. Add assignment value validation, the ticket field and the version-1 record handling. Check that newly created and legacy tickets read with null and saved named assignments reload with their expected value.
2. Add the store mutation with its closed guard, no-op branch, audit entry and unique assignment outbox key. Add the template alongside the enqueue path. Check store state, saved snapshots and controlled worker ticks before exposing the route.
3. Add the PUT route using the existing body, actor and response helpers. Exercise success and the error envelope on the configured service. Check that creation, patching and transitions keep their existing contract.
4. Extend list parsing and match evaluation. Check sparse pages of named and unassigned matches, conjunction for the original HTTP filters, and the CLI's current flag selection.
5. Add the human table and detail presentation. Check the CLI and weekly report using the same saved file. Run the focused new test files and then `npm test` with the existing test files as written. Smoke-test `npm start` with `PORT=0` and use the reported port.
