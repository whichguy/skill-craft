## Approach

- Add `assignee` as a string or explicit null in the ticket store. Initialize it on creation, normalize absent fields in existing state, and serialize it through the version 1 data-file record. Normal ticket reads and mutation responses already copy the store's ticket objects. The file reader also supplies the current assignee to the read-only CLI.
- Register `PUT /tickets/:id/assignee` with the existing router. The handler uses the shared JSON reader, an assignment-specific body validator and `actorOf`, then calls a synchronous store mutation. The store checks eligibility and runs a real change through `apply`, including the audit entry, any outbox event and the snapshot save.
- Add an assignment notification type and template. The existing worker delivers it to the stored recipient using the configured notifier, then records delivery or failure through the existing store interface.
- Extend `parseListQuery` and fix the shared filter predicate before pagination. Add assignee rendering to the CLI table, raw listing and detail view in `src/format.js`. The CLI already uses the data-file reader, shared filters and store pagination, and the weekly report reads the raw CLI output.

## Decisions

The following proposals cover every `Open:` line. The builder should record the choices it actually implements in its report. Verification follows the clauses and allows the other reasonable answers to the open points.

| Clause | Proposed choice | Reason and alternative considered |
|---|---|---|
| C-5 | Return 200 with the ticket for assignment, clearing and accepted no-ops. | Matches patch and transition and uses the existing JSON response path. A bodyless 204 could work with different response handling. |
| C-6 | Trim leading and trailing whitespace, reject empty or whitespace-only strings, ASCII controls (including tab, newline and DEL) and ill-formed Unicode, and preserve internal spaces and case. Check controls on the original string. Cap the normalized name at 1,024 UTF-8 bytes and apply the same name rules for nonempty query selectors. | Follows the single-line text convention and keeps valid names usable as query values. Relying only on the 65,536-byte body limit could admit names too long for the HTTP request line once encoded. Case folding and a CLI escape format would introduce additional conventions. |
| C-11 | Check eligibility before comparing the requested and current assignee, so even a same-value request on an inactive ticket returns 409. | Enforces the state boundary uniformly. Equality first could also make inactive repeats succeed without effects. |
| C-26 | Coalesce only while a notice for this ticket and recipient is pending. Use an unambiguous key containing the type, ticket ID and canonical recipient, such as a JSON-encoded tuple. | Keeps the existing pending-deduplication policy and distinguishes a new recipient. A key per audit sequence could instead give each real reassignment back to the same agent its own pending notice. |
| C-28 | Use the stored agent name directly as the event's `to` through the existing notifier. | The configured relay is the delivery boundary. Address lookup or email validation would require additional data or reject valid names such as Dana Lee. |
| C-36 | Read the first assignee query value, including an empty first value. | Matches the status and priority parameter convention. Rejecting duplicates or aggregating their values would make assignee parsing differ from those filters. |

- Use a single audit action, e.g. `ticket.assignee_changed`, for assigning and clearing, and an event type `ticket.assigned` for named changes. The audit delta already distinguishes the three operations. Keep the creation audit field list as written, since assignment is initially null and existing tests compare the exact entry.
- Keep the version 1 document and add a ticket field with a default for missing values. A schema bump would add migration and deployment work for a field the previous format can load with a default in the new service. Keep the ticket record as the source of current assignment, since reconstructing it from audit history would entangle reads and recovery with historical entries.
- Use the existing synchronous mutation and atomic snapshot replacement. For a persistent, real assignment change, capture enough prior state to recover if the operation throws before committing. A targeted approach is to keep the original ticket values and the pre-change audit and outbox snapshots, restore them in the catch path and rethrow. Saving each component separately or leaving mutated memory after a failed save would expose a change that the API reported as failed.
- Append assignee to the raw column list and use an empty fifth field for null. In the human table and detail view, quote named values and use a bare `(unassigned)` for null so an agent with that literal name remains distinguishable. Appending keeps positional consumers working and avoids writing a sentinel name into the raw field. The existing weekly report can keep consuming positions two and three.

## Nuances

| Clauses or use cases | Failure to avoid and handling |
|---|---|
| C-6–C-13, C-24–C-25, U-3 | A falsiness test can confuse missing with null or accept an otherwise valid value alongside an unknown field. Let `readJson` enforce the object shape and byte limit, reuse the allowlist helper, explicitly distinguish null from absent, then resolve the actor before calling the store. Use the shared error types and envelope. Preserve body-first validation as in patch and transition. Keep assignee name rules separate from the 64-character actor limit. |
| C-9, C-25 | Request size is UTF-8 bytes, while actor length is checked after trimming by the existing helper. Reuse both paths and check the exact inclusive limits. Pad valid JSON with whitespace for byte-boundary tests so a name policy does not accidentally determine the result. |
| C-3–C-5, C-11, C-14, C-18–C-25 | `isFinal` only excludes closed tickets. Use `isActive` so resolved tickets also refuse changes. Keep lookup, guard, comparison, audit, enqueue and save in the same synchronous store call after body reading, with no asynchronous boundary for a competing transition. Use the same timestamp for `updated`, audit and enqueue. Pass an empty change set to the existing no-op path or return an equivalent copy before checkpointing, reading the clock, enqueuing or saving. Use null on the appropriate side of the audit delta. |
| C-15–C-21, C-33, C-42–C-44 | Adding the field in one handler misses create, patch, transition, listing and legacy state. Initialize and hydrate at the shared ticket boundary, including direct store construction from existing state. Keep create and patch allowlists as they are and preserve the field through lifecycle changes, including reopen. Keep the original creation audit entries and requester notices. |
| C-23, C-26–C-31, U-4 | The default notice key combines only type and ticket, so a waiting Dana notice would swallow a Sam notice. Snapshot the recipient and ticket data when enqueueing the change and give different recipients distinct keys. Old pending notices are records of assignments that did happen. Clearing or handing off the ticket does not rewrite, retarget or cancel them. The assignment template must name the ticket and say it was assigned to the recipient. A missing template would make enqueue tests pass while the worker retries to dead. Filter out requester notices when checking assignment delivery. |
| C-29–C-33, U-4, U-8 | Keep the configured background schedule, retry and sent-state recording. A bad notification destination is a delivery failure and the assignment can still succeed. Preserve event IDs, keys, recipients and retry state across restart. A send followed by interruption before its recorded save can repeat with the same event identity. No extra timer or pre-save delivery path is needed. |
| C-32–C-33, C-46, U-8 | `ticketRecord` enumerates the durable fields in both directions. Save assignee explicitly, load missing as null and validate a present value without silently substituting null for invalid data. Keep persisted names compatible with the chosen API name policy. Leave prior audit and outbox records and counters intact. A graceful stop saves again, so inspect the data file immediately after the PUT to prove the request committed before a restart. |
| C-12–C-14, C-22–C-23, C-32, C-46 | `apply` mutates memory before saving. If write or rename fails before commit, undo the attempted field and timestamp change, audit append and outbox change, including its ID counter, before control returns to the worker or HTTP handler. Restore the prior state through the scoped checkpoint and let the app emit the sanitized 500. With the existing synchronous rename as the commit point, there is no extra fallible work between successful commit and publication of the result. Retrying the same request must still make a real change. |
| C-32–C-33, C-43, U-8 | Operational rollback has a direction. The new service reads pre-feature files. The previous writer drops fields it does not recognize and its notifier lacks the assignment template, so running it as a writer on new data can lose the current field and affect pending notices. Retain a before-upgrade snapshot for deployment rollback. A live downgrade with new records is outside the restart use case. |
| C-34–C-37, U-5 | Use parameter presence, not truthiness, to distinguish absent from empty. Map empty to null, leave omitted filters out, and compare all supplied fields, retaining null as a real predicate and continuing to ignore undefined internal filter values. Replace `some` with `every` in the shared predicate to fix the pre-existing status-plus-priority OR. Use URLSearchParams decoding and the chosen name policy consistently. The store already filters, sorts by numeric ID and then pages, so keep cursor and limit handling in place. Cursors cover the stable matching set with the same filters. |
| C-6, C-9, C-34–C-35, U-5 | JSON can carry an escaped lone surrogate that URL query decoding cannot round-trip. Under the proposed name policy, reject ill-formed strings before storing them. The proposed name limit keeps its percent-encoded query value within 3,072 ASCII bytes, leaving room for the path, other filters and headers in an ordinary request. Check for the literal empty decoded selector before normalizing a name so whitespace-only selectors cannot accidentally include the unassigned queue. |
| C-38–C-42, U-6, U-7 | A raw value containing a tab or line break could shift columns or inflate the report total. Enforce single-line names under the proposed naming policy and render one raw row per ticket. Preserve the first four columns, CLI filter options, read-only file access and existing empty-list behavior. The detail view should read the current ticket field even if the latest visible name in history is an earlier assignment. |

## Build order

1. Add the assignment name and body validation, ticket field and version 1 record handling. Check that new tickets and older loaded ticket records have explicit null, assigned records round-trip, and creation audit and outbox behavior stay intact.
2. Add the store mutation and template together. Exercise eligible and ineligible states, changed and unchanged requests, recipient-specific pending events, and rollback on an injected pre-commit persistence failure. Verify the saved document after a successful mutation before stopping the service.
3. Wire the route through the shared body and actor helpers. Exercise representation, refusal and limit boundaries over HTTP, then run a worker delivery check with the new template.
4. Add filter parsing and conjunction in the existing query module. Check mixed assignments, lifecycle states and filter combinations across cursor pages. Add table, raw and detail formatting and exercise the CLI and weekly report over a saved file.
5. Run the focused `node:test` files added under `test/` as each part landed, then run the whole existing and new suite. Run process-level startup and restart checks. Align README and API examples with the new field, endpoint, filter and raw column, and record the format and notification decisions following the repository's decision-record convention. Document actual open-point choices in the build report.

## How we will know

Use the existing `withService` and HTTP client on port 0, a manual clock for timestamps and retry boundaries, and temporary data and notify files. Assert behavior at public interfaces where possible. Test open points without freezing a single permitted answer, including response shape, special-name rules, inactive repeats, same-recipient pending coalescing, address mapping and duplicate query parameters.
