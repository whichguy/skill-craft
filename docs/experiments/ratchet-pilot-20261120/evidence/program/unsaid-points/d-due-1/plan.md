## Approach

Add due times to the existing CommonJS service using Node's standard library. Read the switch and priority settings in `src/config.js`, wire them through `src/server.js`, and use one elapsed-time calculation for ticket creation and file preparation. Keep the schedule separate from the clock. Read the existing injected clock once for a creation and derive `due` from the exact `created` instant and the validated effective priority. Give the store the creation schedule only in enabled mode. Keep an optional saved `due` on the ticket in version 1 of the existing JSON document. [C-1–C-9, C-17–C-24, C-29]

Have `src/app.js` control HTTP exposure and opt-in query parsing. Project ticket copies in create, get, patch, transition and list responses, including list items inside the existing page envelope. Keep request validation, history, outbox, error handling and health on their existing paths. Pass the overdue flag as its own listing option from `src/tickets/query.js` to `TicketStore.list`. Filter saved deadlines in the store before applying the existing numeric cursor pagination. [C-6, C-10–C-16, C-27–C-28]

Use a documented, one-shot preparation entry point backed by the store and its existing persistence adapter. Calculate all missing deadlines from the loaded records, save the resulting whole state once, and check completeness at enabled startup before listener or worker startup. Treat loading, writing, assigning and exposing deadlines as separate operations so shutting the feature off can hide deadlines while routine saves still retain them. Keep `bin/tickets.js` and the weekly report working through the same reader. [C-16–C-31]

## Nuances

- **Compatibility at both serialization boundaries (C-6, C-16, C-19, C-21, C-24, C-29).** `ticketRecord` is a whitelist used by both `toDocument` and `readTicket`. Extend both paths via the shared record function. Distinguish a missing own property from an assigned value such as null, an empty string or a malformed timestamp. Preserve assigned values as data, including damaged values in off mode, and do due-specific validation explicitly for preparation and activation. Use a ticket response projection so the off switch cannot leak a value through a spread copy or accidentally erase it from the persisted record. Keep the original HTTP ticket shape everywhere the switch is off.
- **One meaning for a stored instant (C-6, C-7, C-11, C-19, C-21).** Use the same interpretation for activation validation, overdue comparison and UTC presentation. Give new values explicit UTC, accept usable timestamps with explicit offsets, and reject ambiguous local wall-clock deadlines in modes that require them. Otherwise the same persisted text could produce a different deadline after restart in another host time zone. Keep this rule specific to the new field so production files accepted by the existing `created` and `updated` validators still load.
- **Arithmetic and failed creation (C-3–C-5, C-22, C-23).** Multiply supported hours by 3,600,000 and add to the creation epoch milliseconds. Validate the resulting Date before calling `toISOString`, admitting both inclusive Date endpoints and expanded ISO years. Comparing ISO strings lexically fails across expanded years and offsets. Use the persisted creation time and priority for backfill regardless of status, migration wall clock, updated time, or audit history. Calculate before consuming an id, appending audit, or enqueueing a notification. If the enabled persistent creation save throws, keep the candidate ticket, id advance, audit entry and outbox enqueue out of live state. Stage that creation through the existing creation logic and publish the staged state only after the save commits, keeping the failure on the normal HTTP internal-error path. Otherwise a later save can accidentally commit a creation that returned 500.
- **All ticket routes and existing mutation rules (C-6–C-10, C-16, C-23, C-27–C-28).** Create uses the priority already defaulted by `validate.newTicket`. Keep `due` outside client input whitelists and preserve existing conflicts, actor validation, no-op patches and ordinary error envelopes. Update and transition change only their existing fields. Resolve/reopen can change overdue membership without changing the deadline. Use the same ticket projection for the early no-op response and ordinary patch response. Keep event payloads and notification scheduling independent from ticket deadlines.
- **Page membership versus page size (C-11–C-16, U-3).** Initialize an overdue request only in enabled HTTP handling. Keep the legacy parser's result shape for callers without the option. Outside `matchesFilters` apply the active-status and saved-deadline predicate as an AND. Putting `overdue` inside the field matcher risks making it an OR or comparing against a nonexistent ticket field. Use `isActive`, then sort by numeric id and use `paginate` over the entire matching set, with one sampled cutoff per request. Keep both cursor decoding and the store's canonical-id check. Reuse the same filters with each opaque cursor. A later request evaluates current time and status, even if the previous page's last id ceased to qualify. The no-gap assertion assumes a fixed matching set.
- **Preparation and the last writer (C-17–C-20, C-24–C-28, U-4).** A live hidden service still writes through request handlers, worker deliveries and the final `stop()` save. Disable restarts and drain and stop the old writer completely before preparing. Retain the same `DATA_FILE` through preparation and enabled startup. Start enabled directly from the prepared file so there is no write window for hidden-mode creations. If serving hidden again introduces missing deadlines, repeat preparation before enabling. A read-only CLI can operate during the cutover using the complete old or new file. A malformed record or overflowing calculation should fail before file replacement, with the path and record in the diagnostic. Treat the no-op rerun as success without a rewrite.
- **Complete state at the rename boundary (C-19, C-23, C-25–C-28).** Work from a single loaded snapshot, validate existing values and calculate every missing value before writing. Reuse the same-directory temporary write followed by rename as the commit point. Preserve the ticket sequence, audit history and outbox sequence and records. The old file is usable if the process is interrupted before rename, even if a temporary file remains. An interruption after rename leaves the new complete file. A retry reads the configured path and uses only its saved state. Report write failures as preparation errors with the path. Keep listener startup and outbox execution out of the preparation process.
- **Rollback includes shutdown writes (C-24, C-29–C-31, U-5, U-6).** The 1.4.0 reader accepts the known fields and ignores the optional field, but its worker, ticket mutations and even its clean shutdown can rewrite the file using its own field list. Verify old-release health and reads before such a rewrite and check that the old release still has every ticket. Document that original deadlines can be lost on rewrite and that a pre-rollback record of them may be needed to recover originals on roll-forward. Reconcile by ticket id against the current file when recovering authoritative deadlines to avoid losing tickets or intervening changes. Keep the weekly report on the original `RAW_COLUMNS` and verify CLI reads do not save.
- **Process wiring and direct test callers (C-1, C-2, C-5, C-16, C-20, C-32, C-33).** `main` already catches `ConfigError` and `DataFileError` from config loading and service construction and exits 2. Put the startup gate there in the service construction path so the same rule applies to programmatic callers. Existing tests directly instantiate the store and call `createService` with hand-built settings. Give the added options safe off defaults and ensure existing callers can omit them. Keep `node --test` discovery and the worker-off convention for deterministic HTTP tests.

## Build order

1. Add the default hours, shared calculation and schedule parsing. Preserve existing defaults and accept the exact `DUE_TIMES=on` switch. Check default and partial schedules, invalid values when required, and time arithmetic at and beyond the Date limit.
2. Extend the version-1 file record mapping and add store support for validating saved deadlines, staging enabled creations, and preparing a complete state. Exercise old, mixed, empty and damaged files, off-mode round trips, replacement failure and idempotent preparation.
3. Add the explicit preparation command and the pre-listener startup gate. Check command and startup exit status and diagnostics, including a refusal that leaves the configured file as it was. Verify the gap-free cutover procedure.
4. Wire the HTTP ticket projection and overdue query option. Use the existing query, status and pagination logic. Run the existing API, store and parser tests and the new deterministic lifecycle, error, and pagination scenarios.
5. Record configuration, API and rollout instructions in the existing docs, including supported values, the exclusive cutover, the rollback file behavior and the selected open-point choices. Follow the repository's decision-record convention for the version-1 extension and its changelog and version conventions if packaging the release. Run the CLI and weekly report on the new file, verify rollback with the baseline release, and run the complete suite. Keep all of this within the one build pass.
