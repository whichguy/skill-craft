## Approach

Keep the CommonJS service and its version 1 whole-state JSON file. Store `due` as an optional field on each ticket record. Extend both directions of the persistence mapping and retain the field in the store regardless of HTTP visibility. The 1.4.0 reader projects the fields it knows, so the old release can load the same document and serve its ticket inventory.

Read the switch and schedule in `src/config.js` and wire them through `createService`. Put deadline arithmetic and stored-deadline validation in the ticket domain. Give `TicketStore` responsibility for assignments during startup preparation and creation. Use the existing atomic replacement path for preparation and the existing whole-state write for creation. Complete preparation within service initialization, ahead of HTTP listen and worker startup.

In `src/app.js`, use a common projection for the five ticket-bearing responses. Gate the overdue option at the HTTP boundary, then apply its predicate together with the existing filter matcher before sorting and paging in `TicketStore.list`. Keep the body validators and cursor format. Surface schedule settings, startup behavior and rollback caveats in the existing configuration, API and operations documentation.

## Decisions

These are implementation choices for the open points. Record the choices actually taken in the build report. Verification of the specification accepts any reasonable answer where a clause leaves a choice open.

| Clauses | Choice and reason | Alternative and trade-off |
| --- | --- | --- |
| C-3, C-4 | Use `DUE_HOURS_URGENT`, `DUE_HOURS_HIGH`, `DUE_HOURS_NORMAL` and `DUE_HOURS_LOW`. Read once at startup. Reuse the trimmed decimal whole-number convention, allowing zero and safe integers. Unset or blank uses the corresponding default. Parse when the exact switch is on. This follows existing environment settings and avoids requiring a configuration file. | Fractions and live reload introduce rounding rules and a new configuration lifecycle. The spec leaves both open. |
| C-5 | Use integer milliseconds and explicit inclusive Date bounds. Report a startup calculation failure with the file, ticket ID and applicable setting. Let operators correct the data or hours and retry, or start with the feature off. For an enabled create that would overflow, log the setting and computation failure and use the existing internal-error envelope. | Clamping to an endpoint or substituting the current time would produce a different promise. Automatic data repair requires policy from the requester. |
| C-11 | When enabled, use the first `overdue` value, as the existing query parser does for its parameters. Only literal `true` activates the filter. Treat all other values as unrestricted. | Rejecting unrecognized values adds a new client error for parameters the old release ignores. |
| C-12 | Reuse the existing status/priority matcher as a group and AND its result with the overdue predicate. This retains the service's current OR behavior when both legacy filters are supplied. | Using the documented AND interpretation for the legacy pair on overdue queries would make those filters interact differently depending on the overdue option. |
| C-16 | Prepare before listening, with one process owning the file. Use the existing listening log and health endpoint as the readiness signal. Assign deadlines to tickets written with the switch off when a subsequent enabled startup prepares them, using their saved priority at assignment. | Preparing while serving presents a race with writes and requires an additional readiness mechanism. Assigning during disabled writes would make off-mode operations depend on the schedule. |
| C-18 | When enabled, fail initialization for a stored malformed `due`, with the file and ticket identified. Leave the stored value available for operator correction. When disabled, carry the optional field through without interpreting it. | Recomputing a present malformed value could overwrite evidence of an earlier assignment. Validating it while off would make some files previously accepted by 1.4.0 fail to start. |
| C-19, C-20 | Preserve `updated` during preparation. Keep preparation out of the audit history and retain the existing creation audit fields. This keeps agent-edit timestamps and audit output stable. | Recording due assignment as an edit would require a timestamp and actor policy and could alter the off-mode audit response. |
| C-23 | Support enabled memory-only operation. The store starts empty and assigns deadlines before exposing creates. | Requiring a file would impose production's readiness prerequisite on local runs. |
| C-25 | Put dues on version 1 ticket records. After a 1.4.0 rewrite, a later enabled start assigns newly missing dues using the then-current configuration. Document the distinction between rolling back to read the file and letting the old release rewrite it, including at shutdown. | Preserving old deadlines across an old writer would require metadata outside what its serializer discards and a policy for reconciling that metadata with the live file. |
| C-29 | Keep human-readable CLI formatting and raw output as they are. The CLI continues as a read-only consumer of the shared persistence reader and does not load HTTP feature settings. | Displaying deadlines adds CLI presentation and switch semantics the requester left open. |

## Nuances

- **Switch scope and default callers (C-1, C-4, C-6, C-9, C-23, C-33).** A truthiness, trimming or case-folding check on `DUE_TIMES` could enable existing environments accidentally. Use `env.DUE_TIMES === 'on'`. Treat omitted options in direct `createService`, `createApp` and store calls as disabled, as existing tests construct their options by hand. Preserve the disabled list parser's arguments and result shape. Suppress `due` in ticket responses only, on copies, across create, read, patch (including no-op), transition and list items. Keep the audit and outbox envelopes on their existing paths. Ignoring hours while off lets a staged rollout serve even with bad new settings.
- **One promise on the write path (C-2, C-5, C-7, C-8, C-22, C-26–C-28).** Derive `due` from the single creation instant also used for `created`, and from the already defaulted and validated priority. Compute and validate before incrementing the ID or mutating ticket, audit or outbox state. Keep the existing input allowlists and lifecycle and patch functions. Persist the completed ticket, normal audit entry and normal outbox event in the same save, with no separate deadline write. The current create mutates memory before a synchronous save. For an enabled file-backed create, keep a pre-create snapshot and restore the store's ticket map, number, audit and outbox if commit fails, reusing the constructor's state restoration logic. Otherwise a failed create could appear in later reads or be committed by the next save or shutdown.
- **Instant arithmetic (C-2–C-5, C-10, C-15, C-18).** Elapsed hours are independent of calendar dates and daylight-saving changes. Parse saved creation strings using the existing reader's date semantics. The legacy reader allows parseable times beyond canonical ISO, so tightening the checks on `created` would reject valid 1.4.0 files. Multiply the safe integer hours by 3,600,000 and add the parsed creation epoch as integers (use `BigInt` for the intermediate). Check the final value against both Date endpoints before converting to a Number and formatting via `toISOString()`. The intermediate offset can exceed the safe integer range even when the sum fits the Date range. Validate an existing `due` for canonical UTC millisecond format via Date round-trip, including signed extended years. Compare instants numerically. Lexical order can be wrong across extended years.
- **Startup is the commit boundary (U-4, C-4, C-15–C-22, C-32).** Verify legacy records with the existing reader, then distinguish absence of the `due` property from a present empty, null or invalid value. Validate present values and calculate all missing deadlines in a candidate state before saving. Preserve every eligible saved due exactly. Update the store's live tickets only after the candidate is saved, keeping all original ticket fields, the ID counter, audit sequence, outbox events and outbox counter. Use the file's same-directory temp write and rename. A failed calculation, write or rename leaves the prior file readable. Include the file path in preparation write errors and route expected startup failures through the existing stderr and exit-2 path in `main`. No network listener or worker should start on a failed preparation. A crash before rename leaves the previous file authoritative, and a crash after rename leaves the committed deadlines authoritative on retry. A clean or empty file needs no preparation rewrite. For a missing file, the first successful file-backed creation writes a complete ticket with its due.
- **Every save matters (U-5, C-17, C-18, C-24, C-25, C-32).** The persistence whitelist is used in both `readTicket` and `toDocument`. Extending only one would lose due values on reload or rewrite. Pass the optional field through both directions, omitting it only when absent. Keep the version and document shape and exercise off-mode patches, creates, worker delivery updates and shutdown saves on a prepared file. An off-mode ticket may have no due until the next activation, so enabled preparation must scan on every startup, including a mixed file. Stop the new process before giving the pathname to 1.4.0. There is no coordination between simultaneous writers. Retain the existing shutdown order of stopping the synchronous worker, draining HTTP and saving.
- **Filter membership and cursor timing (U-3, C-10–C-14, C-26).** Parse and validate all existing query arguments even when the filters can yield no matches. Keep `overdue` out of the generic OR matcher. Capture one `clock.now()` per active filtered list, and require both `isActive(ticket.status)` from `src/tickets/states.js` and `due < now`. The existing helper covers exactly `open` and `in_progress`. Use current priority for the priority filter and the saved original due for elapsed-time comparison. Filter before paging and use the existing numeric ID sort and cursor logic, including the store's ticket-ID check on a decoded cursor. Every page request takes a fresh time sample and applies the current conditions to IDs after the cursor, even if the prior cursor's ticket no longer qualifies. A newly qualifying ticket whose ID is at or before the cursor is seen only by starting a new traversal.
- **Read-only consumers (U-6, C-29–C-31).** The CLI invokes the shared loader directly and uses the store and formatters without the service. Keep preparation and feature validation out of that path. Keep `rawLine` and the four tab-separated columns in place because the report parses by position.

## Build order

1. Add the switch and schedule options, exact deadline calculation and a due validator. Check default and overridden arithmetic, named config errors and the Date bounds before wiring the assignment paths.
2. Add the optional persistence round-trip and store startup preparation. Wire it into initialization under the existing startup error handler. Inspect version 1 files before and after preparation and after a restart. Exercise a failed replacement using a temporary fixture.
3. Assign deadlines in the create path before store side effects, retain them through later changes and project ticket responses at the HTTP boundary. Check activation and disabled parity on the same file. Exercise the existing audit and outbox behavior.
4. Wire the gated overdue query through listing. Check strict time comparison and filter-before-cursor behavior with the injected clock.
5. Update operator and API documentation. Finish the new `node:test` coverage, prove rollback with the baseline release and run the complete suite. Keep all of this in the same build pass.

## How we will know

Add tests under `test/` and reuse the manual clock and HTTP client from `test/helpers.js`. Use port 0, per-test temporary directories and a paused worker except where exercising delivery. Clean up processes by PID and use bounded child startup and shutdown waits. Tests of open points should follow the implemented interface for setup and check the mandatory result. They should avoid requiring a particular variable name, policy, query interpretation, preparation log, audit addition, CLI display or rollback-rewrite behavior as a condition of satisfying the spec.

- **U-1 (C-1, C-2, C-5, C-6, C-8, C-22).** At the use case's fixed instant, POST each priority and a body omitting priority, then verify the exact due values and 201. Verify field presence on the individual read, list, patch and transition, including resolved and closed ticket responses. Send `due` in each write body and expect 400 `invalid`. Exercise exact representable endpoints where reachable and an overflowing assignment, with no substitute deadline. Restart a file-backed service and check that a successful create, its audit entry and outbox event persisted together. Inject a file-backed creation save failure before rename. Check the old file and live inventory, audit, outbox and counters, then remove the fault and retry.
- **U-2 (C-3–C-7, C-17, C-26–C-28).** Change the supported settings and restart if needed. Show that a new promise reflects the configured hours and the previously assigned due remains identical across the restart, a priority or title change and a resolve/reopen lifecycle. Check no-op patch semantics, lifecycle errors and ordinary notification triggers including pending deduplication. Supply a value malformed under the implemented syntax and check the diagnostic names the setting, and that startup failure, if used, exits 2.
- **U-3 (C-9–C-14).** Test no overdue parameter, active overdue selection across all four states and a disabled switch. At a fixed time include deadlines before, equal to and after now. Advance by one millisecond and show membership can change without a write. With the worker paused, compare the outbox before and after crossing the deadline and listing. Check reopened tickets and each legacy filter independently, including resolved or closed alone giving an empty result. If testing combined filters, require overdue membership and allow either specified interpretation of the legacy pair. Interleave qualifying and nonqualifying IDs across several pages, including IDs crossing a digit-width boundary. Check default size, sizes 1 and 100, next cursors, a full final page with no qualifying successor, the empty envelope and changed membership between requests. Check existing 400 errors for bad status, priority, limit and cursor, even on an otherwise empty result.
- **U-4 (C-1, C-9, C-15–C-23, C-32).** Start with a real version 1 fixture containing all statuses, a mixed fixture with a valid preexisting due and fixtures for empty/missing files. Use the startup path rather than calling a migration directly. On first availability, read the file and confirm preparation was already committed. Verify deadlines against saved creation and priority, compare original ticket fields and audit/outbox records, and create the next ticket to check numbering. Restart with a different schedule and preserve committed values. Between enabled starts, run off on the prepared file and verify the 1.4.0 HTTP shape, including audit and ignored overdue parameters. Exercise ticket, outbox and shutdown saves while off, then check saved dues and fill any missing ones on reactivation. Inject failure before rename, check that the previous file and any committed deadlines survived, correct the cause and retry. Check bad legacy data and malformed stored dues never establish enabled readiness. Exercise `npm start` with `PORT=0` and read the chosen port from the listening diagnostic on stderr. Check `GET /health`, send SIGTERM to the Node service PID and inspect the file after exit. For a dedicated drain test, spawn Node directly and hold a request open after the server begins reading its body. Send SIGTERM to that PID, finish the request, then await the successful response and process exit before inspecting or reopening the file.
- **U-5 (C-24, C-25).** Use unmodified 1.4.0 code from base commit `d7c78c1`. Archive the baseline tree to a temporary directory for the integration check, without changing the checkout or Git history. Point 1.4.0 at the exact file left by the stopped new service after preparing and adding tickets. Prefer generating the initial fixture through 1.4.0 too. Follow ordinary list cursors until exhausted and compare every ID and legacy field with the pre-rollback inventory. Check individual reads of both an original and a new ticket. A successful read with the new loader in disabled mode cannot stand in for running the old executable. Capture the evidence before stopping 1.4.0, whose shutdown can rewrite the fixture.
- **U-6 (C-29–C-31).** Run CLI `show` and `list` with both file-selection methods. Exercise existing status and priority options and verify the raw column positions. Compare weekly report JSON totals and breakdowns before and after preparation of the same tickets. Compare bytes before and after the read-only commands.
- **U-7 (C-33, C-34).** Run `npm test` on Node.js 22 or later. Confirm the new tests were discovered and the original test files have zero diff against the baseline. Keep the normal suite independent of network access and Git metadata. Use a self-contained frozen 1.4.0 reader contract in the regression test for a file produced by the new process. Also run the exact old executable against that file in the U-5 build check using the local baseline archive.
