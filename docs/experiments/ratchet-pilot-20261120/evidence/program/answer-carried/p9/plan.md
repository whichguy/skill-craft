## Approach

- Keep the existing version-1 data document and add one optional `due` string to its ticket record. In `src/persistence.js`, preserve the field in both directions independently of whether the API exposes it. The original version-1 reader picks out known fields, so it can read the same file on rollback. Deadlines belong to ticket state alongside `created` and `updated`; they are assigned once and saved through the existing whole-state write.
- Read the exact literal `DUE_TIMES=on` flag and response-hours configuration through `src/config.js`. Put elapsed-hour arithmetic in a small ticket module shared by creation and preparation. In `src/store.js`, enabled creation assigns the deadline before changes to the ticket ID sequence, audit or outbox. Add a store operation to assign missing deadlines in a single save. `src/server.js` checks readiness before HTTP or the worker starts and routes startup failures through its existing diagnostics.
- In `src/app.js`, project the copy of each ticket returned by create, detail, patch, transition and list according to the flag. Pass the parsed overdue switch separately from the status and priority filters. In the store, apply both predicates to the full set before existing numeric ID sorting and cursor pagination. Use the store's clock and leave the body validators, audit view and outbox view on their existing paths.
- Add one offline operator entry point, `DATA_FILE=... node bin/prepare-due-times.js`, using the existing config helpers, persistence and store operation. Add rollout and rollback instructions to `docs/operations.md`, document the environment and command in `README.md`, and describe the enabled ticket and list behavior in `docs/api.md`. Record the compatible file format and API decision using the repository's decision template. Add focused `node:test` files under `test/` and use the existing npm entry points.

## Decisions

These choices resolve implementation details for the build. The build report should record the choices taken for every `Open:` line. The clause observables govern acceptance across reasonable answers to those open points.

| Clauses | Choice, reason and alternative |
| --- | --- |
| C-3, C-4 | Use independent `DUE_HOURS_URGENT`, `DUE_HOURS_HIGH`, `DUE_HOURS_NORMAL` and `DUE_HOURS_LOW` settings with defaults 4, 24, 72 and 168. Reuse the trimmed decimal whole-number parser with a positive minimum. The maximum is 4,800,000,000 hours, the full span between the two Date endpoints, so every individually usable whole-hour offset is allowed. A per-ticket sum still needs a range check. Independent settings let operators override one priority and keep the other defaults. A structured setting would introduce a new parser for ordinary environment configuration. Validate the schedule at enabled service startup and during explicit preparation. Have the command read just the data path and schedule through shared helpers so an unrelated HTTP or worker setting cannot block an offline data operation. Parsing it during disabled service startup would introduce an unrelated startup failure on the legacy path. |
| C-11 | Enable the filter for exactly one value of `true`. When enabled, reject any other supplied form, including repeated values, with the established invalid-query envelope. Explicit rejection exposes malformed queries. Treating any supplied spelling as true or silently picking the first occurrence risks returning the wrong queue. With the flag off, ignore the parameter altogether regardless of value or multiplicity. |
| C-12, C-14 | Keep the runtime's status/priority union everywhere and intersect its result with overdue. This preserves existing combined-filter behavior, including the CLI's shared predicate. Changing the legacy predicate to match the documented intersection would expand the release scope. Update the relevant API description to reflect the behavior selected for the build. |
| C-15, C-16 | Use explicit offline preparation and refuse enabled startup on an existing incomplete file. This gives the operator a readiness checkpoint before opening the listener. Automatic preparation on early enabled startup is another possible design, but ties saving the upgrade to process launch. Disabled creates keep the legacy record shape and first receive a deadline at preparation from their then-current priority. An intervening disabled writer can add new missing rows, so stop it and rerun preparation before enabling. |
| C-19 | Use the full Node Date range with inclusive bounds. Reject and diagnose a record whose computed deadline is outside it. Clamping would promise a different interval. After restoring a usable file or correcting an applicable setting, the operator can retry. |
| C-20 | For enabled startup and preparation, validate each present deadline as a canonical UTC timestamp in the `toISOString()` convention, including extended years. Refuse invalid values with a file and field diagnostic. Treat only an absent property as eligible for assignment, since replacing a present value could change a previously promised deadline. Disabled startup and read-only tools tolerate and preserve stored values opaquely, avoiding a new legacy startup error. |
| C-23, C-24 | Keep `updated` and existing audit content unchanged during preparation. Use the existing creation audit fields for enabled creates too. An added audit field or preparation entry would add visible history that the disabled API would need to account for. Deadline assignment during preparation records a derived value without presenting it as an agent edit. |
| C-29, C-30 | Support rollback by keeping the same version-1 file and optional ticket field. A new schema version would cause 1.4.0 to refuse the file. Support reading and listing all tickets after rollback. Deadline retention across a subsequent 1.4.0 write is outside the required guarantee, since its writer strips extra fields. Document that subsequent re-upgrade needs a new preparation of missing deadlines and that recalculation may differ. |
| C-31, C-32 | Keep CLI table and detail formatting as-is, without a due-time toggle in the CLI. The new field is available through enabled HTTP views. Adding it to human-readable output would widen the operator-facing change, and adding it to raw output would alter the report's input format. |

## Nuances

| Clauses or use case | What goes wrong and how to handle it |
| --- | --- |
| C-1–C-5, C-19, C-22 | A second clock read can put the deadline a tick away from the recorded creation instant. Use the same instant as `created`, adding elapsed milliseconds independent of timezone and DST. Preserve the existing request validation and default priority path. Compute with exact integer arithmetic through the bounds check, such as converting the parsed millisecond instant and hours to BigInt before multiplication and addition. Convert the bounded result back to Number and call `toISOString()`. This handles both endpoints, offsets larger than the safe integer millisecond range, and one-millisecond overflow. |
| C-6–C-9, C-21, C-26, C-27 | Calculating on reads, generic ticket updates or serialization would move deadlines when config, priority, status or time changes. Keep `due` out of each request body allowlist and preserve the stored scalar during normal copy/update paths. Same-value patches retain their no-op behavior. Leave notification payload, requester, deduplication keys and audit actors on the existing path. A reopened overdue ticket reenters the list with the original deadline. |
| C-10–C-14 | The shared predicate uses `some`. Inserting overdue into that object would give ordinary matches a way around the deadline check. Apply a separate conjunctive predicate for `open` or `in_progress` and `Date.parse(due) < nowMs` at one injected-clock sample per overdue request. ISO string comparisons can misorder extended years. Filtering after pagination loses matches and miscomputes `next`. Preserve parsing, cursor validation, numeric comparison and the current page envelope. Each request reevaluates time and status, so the stable-set pagination guarantee does not promise a frozen result set across pages. |
| C-5, C-14, C-21 | Persistence strips fields unless the record codec explicitly carries them. Conversely, store copies currently flow straight to HTTP, which would leak a loaded deadline while disabled. Preserve optional own-property presence in the file codec, and project due only on returned ticket copies at the API boundary. Keep schedule parsing and overdue query evaluation off the disabled path. Preserve the exact default `parseListQuery` return shape `{ filters, limit, after }`, asserted by `test/query.test.js`. Only include an overdue option when requested and enabled. Existing `createService` callers pass config objects without new keys, so absent options must keep the disabled behavior. Compare audit and outbox responses too, since they are publicly observable even when ticket fields are redacted. |
| C-15–C-20, C-23–C-25, C-28 | Preparation is a state operation over all statuses. Load and check the entire original document, validate existing assignments, build prospective copies for all missing deadlines using each row's `created` and priority, then save once using the existing same-directory temp-and-rename path. Keep ticket order and fields, audit entries, all outbox states and counters, and the ticket sequence. Applying normal update/transition methods would change timestamps or produce side effects. Treat a fully prepared or valid empty document as successful with zero assignments and no rewrite. Refuse a missing file in the explicit command to catch path mistakes. An ordinary enabled first start on a nonexistent file or in memory can start empty since it has no existing tickets. |
| C-16, C-18, C-20, U-4 | Run the command after stopping the service gracefully and waiting for it to exit. A live disabled worker or a final shutdown save could otherwise replace the prepared file from its own snapshot. Follow the existing one-writer rule through rollout and rollback. Before rename, an error or interruption leaves the original file. After rename, rerunning sees the saved assignments. Diagnostic failures should name the file and offending record or operation, and exit nonzero with no success summary. Emit the path and assigned/already-assigned counts after successful preparation, including an idempotent run. An early `on` process must check all loaded tickets before binding or starting the worker. |
| C-19, C-21, C-22 | A create that cannot represent its deadline must fail through the existing internal-error path before consuming an ID or recording effects. Existing creation mutates memory before saving, so guard the enabled creation commit against a failed write: stage or undo its ticket, ID counter, creation audit and queued notification as a unit, keeping the legacy path's existing behavior. With a data file, report 201 after rename succeeds. Enabled in-memory creates commit in the store without a file write. Keep the write path synchronous and reuse the file codec and atomic save for subsequent updates, notifications and shutdown. |
| C-29–C-32, U-5, U-6 | Compatibility requires running the original code against a file containing both backfilled and new tickets. The original reader loads the old fields and discards the new field in memory; the original writer can then discard it on disk, including at graceful shutdown. Use a test copy for rollback rehearsals, but give 1.4.0 that very file unchanged between the two releases. In the new CLI, retain existing file selection, read-only behavior, filtered pagination and tab layout. |

## Build order

1. Trace and preserve existing constructor defaults and call signatures so direct store, service, parser and CLI callers still work. Add flag and schedule config plus the shared arithmetic and optional version-1 record field. Check default-disabled loading and saving, including existing deadlines and legacy records.
2. Wire enabled creation and the store preparation operation, then the operator command and startup readiness check. Verify against real version-1 files and the normal entry points before layering on the API changes. Exercise invalid configuration, incomplete/mixed files, idempotence and failed saves.
3. Wire enabled ticket projection, query parsing and overdue eligibility before existing pagination. Exercise all response routes, disabled equivalence, the strict time boundary and filtered pages through the HTTP server.
4. Complete the operator, configuration and API documentation and the repository decision record. Follow the repository release convention if cutting the new release in this pass. Finish the new test files, run `npm test`, and rehearse preparation and rollback using actual command-line entry points, including the CLI and weekly report.

## How we will know

- **U-1 (C-1–C-6, C-22)**. Start an enabled service on port 0 at a fixed injected instant. POST each priority and omit the priority field in a separate request. Verify the exact UTC strings and elapsed offsets. Verify create, detail, list, patch and transition responses. Send otherwise valid bodies with `due` on each mutation route and verify 400 `invalid` with unchanged state. After a successful create and before a shutdown save can mask a persistence bug, read the file and check the deadline, audit entry and outbox event together.
- **U-2 (C-3–C-4, C-7–C-9, C-19, C-26–C-27)**. Restart on the same file with one positive whole-hour override, verifying the old deadline and the new interval on newly created tickets. Check unaffected defaults, default normal priority, and startup diagnostics for an unsupported value when the schedule is used. Patch priority, do a same-value patch, and exercise reopen and close on separate eligible tickets. Assert stored deadline, timestamps on no-op, audit actor and actions, and receipt/resolution effects including deduplication of a pending resolution.
- **U-3 (C-10–C-14)**. Use the manual clock to exercise exactly due, one millisecond after, future, past resolved/closed, and past reopened tickets. Use each existing filter independently and prove every result with both is still overdue without imposing union or intersection as acceptance. Verify unrestricted listing without the parameter. Keep nonmatches between matches and cross the T-9999/T-10000 boundary. Walk cursor pages with stable inputs and check empty/no-next cases, default size, limits 1 and 100, malformed and out-of-range limits, and existing invalid cursor handling. For enabled queries, exercise the required single literal and the omitted parameter. Leave alternate and repeated values open for acceptance.
- **U-4 (C-14–C-25, C-28)**. Make an authentic 1.4.0 fixture across all statuses with differing `created` and `updated`, audit/outbox state and saved counters. Compare disabled responses on unprepared and prepared fixtures, including expired `overdue=true`, invalid requests and status/priority combinations. Run preparation with the previous service process fully stopped, compare assignments and the rest of the state, then enable and restart. Repeat preparation with changed hours on mixed and fully prepared files. Include a compatible empty document, malformed legacy state and a deterministic failed save before rename. For date boundaries, choose a legacy creation instant whose computed deadline lands on the upper Date endpoint, then move creation one millisecond later while leaving it valid and check that preparation fails. A positive interval cannot produce the lower endpoint from a valid creation time, so exercise that endpoint as an already stored deadline when checking the selected file validator. Use controlled fault injection at the save boundary, since permission-based fixtures can behave differently under privileged test accounts. For a failed enabled create, compare both live and persisted state, then retry and check the next ID, audit and outbox are each committed once. Verify failure leaves a readable prior file, no readiness claim, and retry after correction. Verify an early enabled run exposes no enabled ticket data while the file is incomplete. Exercise a disabled mutation and a worker delivery save before another enabled restart, and verify the original deadline and next ticket number. Also create an additional ticket during the disabled window and confirm the file goes through the selected readiness procedure again before enabled views are available. Test C-20 against invalid legacy fields and file structure. Its stored-deadline policy is open, as are preparation changes to `updated` and extra audit entries, so compare the required ticket fields and preexisting audit entries independently of those choices.
- **U-5 (C-29–C-30)**. Materialize the unchanged 1.4.0 source from the baseline commit `d7c78c1` identified by its package version, for example by extracting a Git archive to a temporary directory without changing history. Have the new release prepare and add tickets to a test file, stop it and launch old `npm start` on that exact path with `PORT=0`. Check HTTP 200 on health and follow all ticket pages, comparing IDs and ordinary fields against the pre-rollback state even across multiple pages. Stop each child by PID. A new reader accepting its own version-1 file is insufficient evidence of rollback.
- **U-6 (C-31–C-32)**. Run CLI `list` with its filters and `show ID` with history using both `DATA_FILE` and `--data`. On the prepared fixture, assert each raw line has the four existing positional columns and compare weekly report totals and breakdowns. Verify the file bytes are unchanged after the reads. Avoid assuming an output requirement for human-readable deadlines.
- **U-7 (C-33–C-36)**. Run `npm start` with `PORT=0` and verify health at the reported port. Verify numeric setting limits without binding a fixed default port. Use Node.js 22 or later and built-ins only. Run `npm test` to discover both old and new `node:test` files and confirm original tests are byte-identical to the baseline. Reuse `test/helpers.js` and `manualClock` for deterministic HTTP tests and isolated temporary files for process and persistence checks.
