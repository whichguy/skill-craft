## Approach

- Keep `npm start`, the CommonJS entry points, and the dependency-free setup. In `src/config.js` read the exact `DUE_TIMES=on` switch and resolve a response-hours schedule for operations that assign dues. Pass enablement and the schedule through `createService` to `TicketStore` and the HTTP app. Keep feature-off defaults for callers that construct a service, app, store, or list query directly.
- Add a shared due-time calculation for creation and preparation. `TicketStore.create` assigns `due` from the same instant it uses for `created`, with the priority normalized by the existing create validator. The store owns the saved value. Ticket-update and transition paths continue to touch only their existing fields.
- Add an optional per-ticket `due` field to both directions of the existing version 1 persistence codec. Keep the single whole-state file and the existing replacement boundary. Add a one-shot operator command, proposed as `npm run prepare:due-times`, using `DATA_FILE`, the shared schedule parser, and a store preparation method. Run it with exclusive ownership of the file after stopping the writer. Use the same readiness predicate for preparation and for the enabled server's pre-listen check.
- Shape ticket responses explicitly in `src/app.js` for create, get, patch, transition, and each list item. Keep audit and outbox responses on their existing paths. In `src/tickets/query.js` parse the enabled overdue option separately from the legacy fields. In `TicketStore.list` apply it before the existing numeric sort and cursor pager.
- Keep `bin/tickets.js` and the weekly report on their existing read-only paths through the compatible loader. Add operator instructions to the existing README and operations docs and describe the HTTP behavior in the API docs. Record the compatible file and API decision, and follow the repository release conventions in the build.

## Decisions

These are build selections where the specification leaves room for a choice. The build report should record the selections it actually implements. Shared acceptance checks follow the clauses and allow other reasonable answers to the open points.

| Clauses | Build choice | Reason and alternative considered |
| --- | --- | --- |
| C-3, C-4 | Use independent environment variables `DUE_HOURS_URGENT`, `DUE_HOURS_HIGH`, `DUE_HOURS_NORMAL`, and `DUE_HOURS_LOW`. Use trimmed positive decimal whole hours within the safe-integer range, with unset or blank using 4, 24, 72, and 168 respectively. Resolve them at enabled startup and for preparation when it has assignments. A changed environment takes effect at the next start or preparation. | This fits the existing whole-number environment settings and gives errors a specific variable name. A structured schedule or live reload would add parsing or runtime state. Hour policy and live reload remain open. |
| C-5, C-18 | Use exact elapsed-millisecond arithmetic and the inclusive Node Date bounds. On overflow, fail preparation with the file, ticket, and applicable setting in the diagnostic. An enabled create whose calculation overflows uses the logged server error path before any store mutation. Keep any malformed saved `due` uninterpreted while off, and fail readiness and preparation with the file and record identified until an operator corrects the data. | A clamped timestamp would change the promise. Silently replacing a malformed field would choose a repair policy and could move a promise. |
| C-9, C-16, C-17, C-23 | Use offline preparation followed by a separate enabled startup that checks the freshly loaded file. Off-mode writes leave new tickets without a due until preparation and carry existing due fields through. Allow enabled memory-only mode and empty enabled stores. A missing file is an ordinary first start for the service, and an error for the preparation command. | Operators can see completion before exposure, and the original first-start behavior can still serve a new installation. Automatic startup preparation or assigning dues to off-mode writes would make the changeover less explicit. |
| C-11, C-12 | For the enabled query, use the first value as `URLSearchParams.get` does for the existing parameters. Exact `true` activates selection. Other supplied values apply no due restriction. In this branch, combine legacy status and priority with their current OR semantics, then require overdue as an additional condition. | This preserves the list behavior agents already see and the parser's handling of repeated keys. Rejecting other values or using the documented AND rule in overdue queries are possible alternatives. Ordinary listings keep the existing OR behavior. |
| C-19, C-20, C-21 | Treat preparation as addition of ticket metadata. Keep each ticket's `updated` and its history, keep the original creation audit fields even when enabled, and emit no backfill notifications. | This preserves chronology, history and off-mode responses. Administrative timestamps or audit entries would need a policy for what users see and would complicate off-mode history. |
| C-24, C-25 | Store dues only as additive ticket fields in the version 1 file. The rollback path uses the same file. After a 1.4.0 rewrite, choose to prepare missing dues again on re-upgrade with the then-current settings and saved priorities. | The old reader ignores unknown ticket fields, and its writer drops them. Sidecar storage or retaining dues across an old-writer run would add a reconciliation protocol to solve an open point. |
| C-29 through C-31 | Keep both human-readable CLI views in their current layouts, independent of HTTP enablement. Keep four fields in raw output. | This protects the existing operator and script interfaces. An optional human-readable due column would be an additional interface choice. |

## Nuances

- **Separate storage from visibility (C-6, C-8, C-9, C-17).** `ticketRecord` is used by both the reader and the writer, so preserve a saved `due` in both directions regardless of enablement. Copy it only when present as an own property so legacy tickets can remain absent, and distinguish absence from a present malformed value such as null. Strip `due` from response copies only at the HTTP boundary when off. Cover list items, even those on later pages, and the no-op patch response. Mutating a store record while shaping a response would lose due on the next ordinary save. Keep all body validators' field allowlists and the existing audit payload unchanged.
- **Use the legacy reader's accepted creation timestamps (C-2, C-5, C-15).** `readTicket` accepts any string that `Date.parse` can use for `created`. Calculate from its parsed epoch milliseconds and leave the original string in place. Derive a new ticket's deadline from its stored creation instant, never from another clock read. Hours are elapsed time across calendar changes. Use integer milliseconds, with `BigInt` for the multiplication and addition before checking the inclusive Date range. A large offset alone can exceed the safe Number range even when it lands on a valid date from a negative start. Convert to Number only after the range check, then use `toISOString()`. The readiness check can use a finite parse and equality with its canonical ISO rendering, accepting the expanded years emitted at the Date bounds.
- **Preserve error boundaries (C-4, C-5, C-8, C-9, C-18).** Keep the existing validations and startup diagnostic classes. Off startup never parses due-hour overrides, so an unused malformed setting does not break the old API. Enabled startup reports `ConfigError` or `DataFileError` through the existing stderr/exit-2 path before starting the listener or the worker. Preparation should report file and record or setting context and exit nonzero on read, calculation, or replacement failure. HTTP write validation and actor validation retain their current precedence. A calculation failure is a server-side fault and should use the existing internal-error envelope and detailed operator log.
- **Commit before advertising readiness (U-4, C-15 through C-22, C-32).** Stop and await the owning service, including its shutdown save, before preparing. Pausing only the worker still allows requests, and even an idle server can overwrite the replacement from its in-memory snapshot during shutdown. Rely on the existing single-writer operating model and document that no service or other preparation process may write the file during the command. Load through normal version 1 validation, stage all missing assignments from saved priorities and creation times, validate the resulting state, and replace once via the same-directory temporary-file save. Leave ticket IDs, `nextNumber`, audit entries, outbox events and `nextId` intact. Check the committed file with the readiness predicate and report assigned, retained and total counts. A no-op retry should avoid a rewrite. The original file remains intact if staging or replacement fails before rename. Treat a path left behind by interrupted work as a temporary file, never as the authoritative data file.
- **Readiness belongs to the loaded data (C-16 through C-18).** Inspect every ticket in the very snapshot the enabled service uses, including closed tickets, just before starting to serve. A previous success report, marker, or elapsed time cannot make a since-modified file ready. A disabled process may have preserved the old dues while adding a new ticket without one. In that case, stop it, rerun preparation, and recheck that earlier saved values survive. Keep the production file's legacy structural checks for every mode.
- **Failed creates must not leave work for a later save (C-5, C-7, C-22, C-28).** Calculate before consuming a ticket number, appending history or queuing the received event. The current create path mutates live state before the synchronous save. For enabled creation with persistence, stage the ticket, next number, audit append and notification using the store's existing state representations and rules, persist the candidate whole snapshot, then publish it to the live store. Keep a single creation implementation with a narrow commit boundary. If the rename never commits, the next request, worker tick or shutdown should not save or deliver pieces of the failed create. File-free creation needs only the existing synchronous in-memory change once calculation succeeds.
- **Check the number that will be saved next (C-19, C-22, C-24, C-26, C-28).** The version 1 reader accepts a current ticket or outbox counter at `Number.MAX_SAFE_INTEGER`, but it rejects the incremented counter. Preparation can keep such counters verbatim. Before a due-enabled file-backed write that allocates an ID, check that the resulting counter would still pass the legacy reader. Check the outbox counter only when the existing pending-key rule calls for a new event. On exhaustion use the server fault path before mutating live state. Otherwise a seemingly successful create or resolution can make a prepared file unreadable by both releases. Preserve feature-off behavior.
- **Match overdue at request time before taking the page (C-10 through C-14, C-26).** Reuse `isActive` and compare epoch milliseconds with strict less-than using a single `clock.now()` for the page. No timer, notification, or persisted overdue flag is needed. Apply the legacy and overdue conditions independently, so an old ticket in a final state cannot slip in when a priority matches. Reuse existing parser and cursor validation, including the store's validation of the decoded ID. Filter before paging with `compareIds` and `paginate`. A fresh request with a cursor evaluates current eligibility after the last returned ID, even if that ticket no longer matches. An earlier ID that becomes eligible belongs on a new traversal from the first page.
- **Verify both sides of rollback (U-5, C-24, C-25, C-32).** The baseline version check is strict, and `ticketRecord` in the old release is an allowlist. Keep all legacy fields and envelope values that its loader checks. Exercise rollback on the file written after the new service has created a ticket and shut down, before any old rewrite. Verify each saved ID using the old HTTP API, then distinguish the old process's own save, which can remove due fields. Document the need to prepare again after such a save before enabling the new service.
- **Keep legacy consumers independent of feature wiring (U-6, C-29 through C-31, C-33).** The CLI instantiates a store with loaded state and no persistence, calls the original list parser, and pages internally. It does not use `createService`. A readiness check in the shared codec or in the default store constructor would incorrectly bar CLI reads of a file mid-rollout. `rawLine` already names its four columns and the report reads positions 2 and 3, so a generic ticket serialization would risk this interface. The existing direct callers also rely on `parseListQuery` retaining its default return shape when the new option is inactive.

## Build order

1. Add the due-time calculator and feature configuration. Check the default values, explicit schedules, invalid setting names, exact toggle, and finite date bounds before connecting them to any write.
2. Make version 1 persistence round-trip the optional field, then implement and check the store preparation, shared readiness predicate and one-shot command. Use legacy, partially prepared and malformed fixtures to exercise staging, reruns, refusal and file replacement. Verify the codec through the current read-only CLI as soon as it can read a prepared file.
3. Wire enabled startup checks and atomic enabled creation. Exercise both in-memory and file-backed lifecycles and compare existing audit and outbox behavior. Verify a fresh file, a prepared file and an incomplete file before connecting the list option.
4. Add the HTTP projection and the overdue predicate ahead of the existing pager. Check every ticket response path with the switch off and on. Check the boundary and pagination using the injected clock, then rerun the ordinary list and write-validation cases.
5. Finish focused new `node:test` integration coverage, the actual 1.4.0 rollback exercise and the operator and API documentation in the same build. Run `npm test` using Node 22 or later and verify start, preparation, activation, shutdown and rollback on a disposable version 1 file.
