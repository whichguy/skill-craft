## Approach

Keep the dependency-free CommonJS service and its existing entry points. Read the feature flag and schedule in `src/config.js`, wire the schedule through `createService` to `TicketStore`, and share deadline arithmetic between ticket creation and startup preparation. The store owns assignment, the persistence module owns the disk representation, and `src/app.js` controls API exposure. Use an optional `due` string on version-1 ticket records. An absent property represents a ticket awaiting preparation. Persist the assigned UTC instant and use it for every later read and comparison.

At enabled startup, load and validate the whole file, prepare all missing deadlines, and finish any required save before constructing a serving HTTP listener or starting the worker. Do this in the synchronous startup path covered by `main()`'s configuration and data-file error handling. The existing temporary-file and rename pattern commits the ticket array, audit, outbox and counters as one document. Creation with a data file uses that same commit boundary. Memory-only mode assigns deadlines in memory and retains its existing restart semantics.

On the API, use one ticket representation helper for create, detail, patch, transition and list items. In enabled mode include the assigned deadline. In disabled mode omit the field in the response copy even when the underlying record has one. Gate interpretation of `overdue` at the HTTP list entry point or in an opt-in query parser path. Apply the overdue predicate in the store before paginating. Keep validation of write request bodies in the existing validators.

Update the README configuration table, API ticket and query documentation, and the rollout and rollback instructions in the operations guide. Follow the repository's conventions for recording the compatible file-format decision and documenting the release. As the final build handoff, report the choices taken for each `Open:` line and the verification performed.

## Decisions

The choices below give the builder a coherent implementation. Where a clause has an `Open:` line, its observable requirement is the acceptance criterion and other reasonable answers remain valid.

Read `DUE_HOURS_URGENT`, `DUE_HOURS_HIGH`, `DUE_HOURS_NORMAL` and `DUE_HOURS_LOW` once per enabled startup, with defaults of 4, 24, 72 and 168. Use the existing trimmed decimal whole-number convention, with positive hours up to 4,800,000,000, the full Date span in whole hours. ## Nuances

- **C-1–C-4, C-19, U-1/U-2/U-4** — Sample creation time once and compute from the same instant recorded in `created`. Backfill from each stored `created` and current stored priority, including tickets reprioritized while disabled. Use elapsed milliseconds, independent of locale and daylight saving. Parse stored creation times with the existing reader's Date semantics so usable legacy dates still load. Guard the sum before ISO serialization. Use exact integer arithmetic for the addition, for example by converting parsed epoch milliseconds and the whole-hour offset to BigInt, checking the inclusive limits, and converting the final in-range instant back to Number for Date. The span between the two Date endpoints exceeds the safe-integer range in milliseconds. A valid schedule can still overflow for a particular record. Keep extended signed ISO years valid and compare instants numerically. Reject overflow before allocating an ID, appending audit, or enqueuing a notification. An enabled create that cannot compute a representable deadline follows the existing internal-error envelope.
- **C-5–C-9, C-14, C-21, U-1/U-2/U-4** — Projection in the disk writer alone loses the value on load. Projection in the disk reader alone loses it at the next write, including worker saves and graceful stop. Keep the internal record and API view independent. Strip the field from a copy, so disabled responses cannot erase stored deadlines. Check no-op patches and successful transitions, which return through different store paths. Leave the create, patch and transition body allowlists intact so a supplied `due` remains a field error even when disabled.
- **C-10–C-14, U-3** — Read the injected clock once per overdue query. Reuse `isActive` from `src/tickets/states.js` on current status and require strictly earlier deadlines. Clock movement and reopening can change membership without any change to `due`. Inserting overdue into `matchesFilters` would put it inside the existing OR logic and let through non-overdue tickets. Filter first, sort with `compareIds`, then use the existing cursor and limit implementation. A cursor is an ID boundary even if its ticket is absent from the current matching set. A change in time or status between pages may change membership. Preserve the default result shape of `parseListQuery` used by module tests and the CLI, and preserve existing validation of status, priority, limit and cursor.
- **C-14–C-21, C-23–C-25, C-28, U-4** — Validate all records and compute the complete candidate before saving. Use the loaded snapshot for preparation so historical fields, counters and event state go through the existing version-1 persistence path without lifecycle calls. Mixed input must preserve every existing valid deadline byte for byte while filling only the missing ones. Empty, absent and already prepared files need no preparation write. Wrap preparation save failures as `DataFileError` naming the path and failing operation. The pre-listen failure must produce the usual startup diagnostic, with no health response or worker delivery. A write or rename failure leaves the prior document in place, and the next attempt must ignore stale temporary artifacts. Where practical, clean up only the temporary file created by that attempt without masking the primary error. A crash after rename leaves the new state for the next startup.
- **C-16, C-18, C-21–C-22, C-29–C-30, U-4/U-5** — The existing data-file contract assumes one writer. Stop the previous process before enabled startup, and stop the new release before starting 1.4.0. A process running with a stale snapshot could otherwise overwrite the prepared file on a later save. Keep preparation in the existing startup transaction boundary and runtime creates synchronous through save. A committed enabled create includes its ticket, deadline, updated counter, creation audit and pending receipt before the response or any worker tick. On a failed save, restore all four in-memory components (ticket map, counter, audit and outbox) before returning the error. This prevents a later mutation or shutdown from persisting the failed create. Disabled mode hides existing deadlines and skips assignment. Any tickets it creates are picked up at the next enabled startup.
- **C-24–C-32, U-5/U-6** — A success with the new reader only proves that reader understands its own format. Verify rollback with the unchanged 1.4.0 service, and read every page including tickets created after rollout. Verify CLI and report against the new file with the flag set as well, since those commands should remain read-only regardless of service settings. Preserve the raw column count and order, existing filters and history formatting. Keep preparation separate from notification enqueue and delivery so neither existing attempts nor deduplication keys change.

## Build order

1. Add the feature configuration and common deadline calculation. Check exact flag handling, default and partial overrides, config diagnostics, and Date boundaries.
2. Teach version-1 persistence to round-trip the optional property without changing the old required fields. Add the store's startup preparation and diagnostic path, then wire it into service creation before listen and worker startup. Check disabled, empty, mixed and unusable files and a forced pre-rename failure.
3. Assign deadlines on enabled create and integrate their persistence into the existing creation transaction. Exercise in-memory and file-backed creates, including the committed audit and outbox, failure recovery, and retention through subsequent saves.
4. Add the shared API view and opt-in overdue query path. Exercise all returning routes, the injected clock boundary, legacy filters and pagination through HTTP.
5. Document the schedule, API and single-writer rollout and rollback. Complete the new `node:test` coverage and run `npm test`. Verify the CLI/report and a real rollback against the unchanged 1.4.0 sources before handing off the build.
