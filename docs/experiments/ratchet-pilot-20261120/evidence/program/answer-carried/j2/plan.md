## Approach

Add `assignee: string | null` to the ticket held by `TicketStore`. Initialize new tickets with `null`, and default a missing field on load and on direct construction from an older state. The store already returns copies for all ticket responses, so the field reaches create, read, list, patch, transition and assignment through the same representation. Keep it outside the create and patch input allowlists and the existing creation audit field list. Extend the version 1 persistence ticket record on both read and write. The CLI uses the same loader and store.

Register `PUT /tickets/:id/assignee` with the existing `Router.put` in `src/app.js`. Use its configured JSON reader, a dedicated validator in `src/tickets/validate.js`, and `actorOf`, then call one synchronous store method. In that method, find the current ticket, check `isActive`, and compare the requested value with the current value. Use the audited mutation path for a real change, with one update time and a single `changes.assignee` delta. Queue a named recipient through `TicketStore.notify` and add the corresponding template in `src/templates.js`. The existing worker, relay feed, retry policy and outbox report handle delivery.

Teach `parseListQuery` to distinguish an omitted assignee from an explicit empty value. Apply the HTTP intersection to the full set of tickets before the existing numeric ID sort and cursor pagination. Give the CLI an explicit way to request its existing union from the same store listing path. Put the assignee in the human-readable table in `src/format.js`.

## Decisions

- **C-3, success response.** Use HTTP 200 with the current ticket, including for eligible no-ops. This follows patch and transition and gives the caller the updated representation in one round trip. HTTP 204 is viable, but callers would need a separate read to see the result.
- **C-4, blocked-state no-op.** Check eligibility before comparing values, so a well-formed request on a resolved or closed ticket conflicts even for the current value. The endpoint is for active tickets and that ordering matches the closed-ticket patch guard. The alternative is to short-circuit an equal value before the guard.
- **C-9, C-14, C-32 and C-45, agent names.** Follow the existing single-line input convention. Trim surrounding whitespace, reject a result that is empty or contains embedded ASCII control characters, and apply the 40-character bound to the trimmed name using the existing text validator's JavaScript string-length convention. Reject ill-formed Unicode strings that cannot make a round trip through a URL. Store the trimmed spelling and compare it case-sensitively without Unicode normalization. For filtering, reserve the decoded empty string for unassigned, trim non-empty values for comparison, and treat a non-empty value that trims to empty as unmatched. Take the first repeated value, consistent with status and priority. Literal surrounding whitespace, folded names and repeated-value unions would add matching rules that the other filters do not use. A query for an agent outside the accepted name range can simply return no matches.
- **C-21, transitions.** Preserve the current assignee through all existing moves, including resolution, closure and reopening. Assignment history and state history then record the dispatcher's action and the lifecycle action independently. Automatic clearing would require extra lifecycle effects and a policy for restoring ownership on reopen.
- **C-17, C-23 and C-26, history and notice identity.** Use a distinct action and notification type such as `ticket.assigned`, with the audit delta distinguishing set, replace and clear. For each actual change to a name, use an assignment event key containing the type, ticket ID and just-appended audit sequence. A genuine return to an earlier agent gets a new notice even if their prior notice is pending. This captures each assignment even when writes share a timestamp. A type-and-ticket key would swallow Lee's notice while Dana's waits, and a recipient-based key could share the earlier pending notice on a genuine return. Use the saved agent name directly as the existing relay's `to`, with a subject and body identifying the assigned ticket. Address mapping and exact wording are left to the requester and relay operator.
- **C-29 through C-31, saved state.** Keep version 1 and add the field to the existing whole-document write. Legacy files load through a default on read, which avoids a compulsory migration or a second storage location. The new loader should validate explicit non-null assignees against the same stored-name rules used for new assignments. Put ticket, audit and outbox in one synchronous save, then return success.
- **C-35, C-36 and C-40, filter combination.** Use conjunction by default and an explicit CLI-only OR option on the store list/matcher path. Keep one path for filtering, sorting and paging. A shared change from `.some` to `.every` alone would change the CLI's combined selections, and merging separately paged lists in the CLI would duplicate paging and ordering logic.
- **C-38 and C-39, CLI output.** Add an `ASSIGNEE` table column before `TITLE`, with names shown as quoted strings and an unquoted dash for null so even an agent named `-` is distinguishable. Keep the four-column raw format and omit a new current-assignee field in `show`. The table meets the human listing need while scripts keep their positional contract. Adding a fifth raw column or a field in `show` is possible if the requester later wants those displays.

These choices give the build a default for every `Open:` line. Record the choices actually used in the build report. Acceptance should follow the corresponding clause, allowing any reasonable answer where the requester left one open.

## Nuances

- **U-1, U-2 and C-5 through C-11, C-13, C-18, C-19, C-45.** Read and validate the body, then validate the actor, before entering the store, as for the existing mutations. The reader rejects no body, bad JSON, arrays and scalars, and drains an oversized body before answering. Use the field allowlist and handle explicit null before the string validator. Missing, empty and null have different meanings. Check the body byte count separately from the name and actor bounds. With otherwise valid input, an absent ticket is 404 and a disallowed change is 409. Use the shared error envelope throughout.
- **U-1, U-2 and C-12, C-14 through C-20.** Setting already-current null or name on an active ticket returns a copy before reading the clock, mutating, appending audit, enqueuing or saving. Even a later retry must preserve `updated`. For an actual change, give `updated` and the audit entry the same timestamp and keep the audit sequence global. The fact that every newly created ticket contains null does not add a null-to-null entry to creation history, which the original store test compares exactly.
- **C-21 and C-22.** Body reads can finish in either order. Read the ticket and check eligibility inside the synchronous store mutation after the body read, keeping validation against current state, assignment, history, outbox and save in that invocation. There should be no await or delayed ticket read between guard and commit. Use sequence numbers to reason about a race, since timestamps can tie and response arrival need not show commit order.
- **U-3 and C-23 through C-28.** Capture recipient and ticket identity at enqueue time. The worker should deliver each pending event using its own payload, even if the ticket was reassigned or cleared before the tick. Without a template, the worker will treat the event as a failure and eventually mark it dead. Same-value repeats skip enqueue even once the first notice is sent. Clearing adds no notice. Leave requester keys, payloads and templates in place. Reuse the existing at-least-once relay behavior around a crash between writing a delivery line and recording it as sent.
- **U-7 and C-29 through C-31.** Spreading tickets in the store alone would give correct responses until the first restart because the persistence whitelist would drop the field. Add it to the shared record and default only an absent legacy field, keeping explicit null and validating supplied names. Loading a legacy file must not create historical changes or notification events. Save once after both the audit and any notice are ready. The existing temporary-file rename gives a single old-or-new restart boundary. Since `apply` currently mutates memory before `save`, protect changed assignments against synchronous save failure as well. With persistence enabled, stage the mutation in a draft store from the current snapshot, reuse `apply` on the draft's own ticket with no persistence attached, save the draft snapshot once through the original persistence, and publish the draft's ticket map, audit and outbox only after the save succeeds. A failed write then leaves reads, retries and shutdown saves on the prior state. The in-memory path can apply directly. Scope this to changed assignments so refusals and no-ops never copy or save state. A single server owns the file, as before.
- **U-7 and C-29 through C-31, going back.** A backup of the version 1 file taken before deploying provides a consistent rollback point. The old reader can open the extended file but its whitelist drops the assignee when its writer saves, and an older worker lacks the assignment template. Avoid using the downgraded binary to rewrite a live post-change file if those assignments or pending notices must survive a rollback. Restore a pre-change backup for a rollback that can discard post-backup work, or keep the post-change file for resuming with the new binary. For dispatchers, undoing an assignment is a new clear or reassignment, with its own audit delta.
- **U-4 and C-32 through C-37.** `URLSearchParams.has` distinguishes omission from the empty value. Represent the unassigned filter as null and retain it when dropping undefined filters. Evaluate every supplied HTTP criterion, including status plus priority when assignee is omitted. Filter before pagination so nonmatches cannot consume slots or create a false cursor. Keep the existing cursor format, invalid query checks, unknown query parameter handling and numeric ID comparator. Subsequent requests use the same filters against current state. A ticket whose membership changes between requests follows the existing last-seen-ID contract.
- **U-5 and C-38 through C-40.** The CLI walks multiple store pages with the same filter set. Carry its OR mode on every page and keep it read-only. The raw and table paths have separate column definitions. The weekly report reads the raw row by position, so the table column belongs only in `TABLE_COLUMNS`.

## Build order

1. Extend ticket initialization, the persisted record and legacy loading. Check that both newly created and manually constructed legacy tickets carry null in reads and that the existing creation audit shape is intact.
2. Add assignment validation and the store mutation. Wire the outbox key and template before exposing the route. Add the route using shared HTTP helpers. Check a real assignment and its audit and outbox together, a later repeat with no effects, and reopening the file after a save.
3. Extend query parsing and filter combination, updating the CLI caller in the same change. Add the table column and sample both table and raw output. Check combined filters on each entry point before moving on.
4. Add focused `node:test` files under `test/` using the existing helpers where possible. Keep the original tests and npm scripts intact. Run the focused tests and `npm test`, then smoke-test the documented `npm start` entry point on a free port. Update the API and operator documentation for the user-visible behavior, record the API, storage and notification decisions using the repository's decision template and index, and report the open-point choices in the build report.
