## Approach

Use the existing startup, ticket store, query parser and file format. In `src/config.js`, read the enable switch and a per-priority response schedule. Pass the schedule through `createService` to the store and the enable switch to `createApp`. Share elapsed-time arithmetic between creation and startup preparation. Store each assigned deadline alongside the ticket as an optional `due` field in version 1 JSON. The file loader and writer retain that field in every mode. In enabled mode, finish preparing and saving the store before creating the listening service or starting its worker.

The store assigns new deadlines from the existing `created` timestamp and effective priority and evaluates overdue selections with its injected clock. The app projects ticket response fields and opts into enabled query parsing. The body field allowlists, audit and outbox APIs, delivery worker, cursor format, CLI format and weekly report retain their current interfaces. Add focused `node:test` tests and document the settings and rollout in the existing README, API and operations docs.

## Decisions

The choices below cover the specification's open points for this build. Record the choices actually used in the build report. Acceptance checks should follow the clauses and allow other reasonable answers.

| Scope | Build choice and reason | Alternative considered |
|---|---|---|
| C-4, C-5, C-22 | Enable only on an exact `DUE_TIMES=on` match. Read `DUE_HOURS_URGENT`, `DUE_HOURS_HIGH`, `DUE_HOURS_NORMAL` and `DUE_HOURS_LOW` at startup, and only parse these settings when enabled. Use the existing trimmed whole-number setting convention, with empty meaning default and positive integers through `floor(Number.MAX_SAFE_INTEGER / 3_600_000)`. This keeps duration arithmetic exact and is consistent with the existing environment controls. Apply configuration changes on restart. | Hot reload would add a second configuration path. Fractional hours would require choosing a precision and rounding rule. |
| C-6, C-30, C-31 | Expose `due` on enabled ticket HTTP responses. Keep human-readable CLI output in its current format, since operators already depend on its legacy fields and history. | Adding a CLI column or detail row would expose the deadline outside the HTTP switch. |
| C-11 | Compare strictly earlier than the sampled current instant, matching “has passed.” | At-or-before would include equality. |
| C-13, C-16 | Use the current status/priority OR rule even with overdue filtering and require overdue independently. This keeps the meaning of existing filters consistent across listings and the CLI. | Applying the documented AND rule in the overdue listing would give the same legacy filters different meanings by mode. |
| C-15 | Accept exactly one case-sensitive `overdue=true` when the parameter is present in enabled mode. Use `InvalidError` for every other enabled form. Omission is ordinary listing. In off mode continue ignoring every form. | First-value parsing could silently accept duplicates. Accepting `false` as an alias for omission would broaden the supported syntax. |
| C-18 | Prepare absent deadlines using the enabled process's configured hours and the stored priority at preparation. Off-mode creations start without deadlines. This keeps off-mode configuration and creation independent of due times and makes preparation use the operator's activation settings. | Assigning while hidden would lock in the earlier schedule and priority. Using defaults for legacy records would override the configured schedule during activation. |
| C-20 | Allow enabled memory-only use. Assign at creation, with no production-file prerequisite for that mode. An absent configured file or zero-ticket document starts empty. | Requiring a file whenever enabled would make local in-memory use depend on disk. |
| C-21, C-22 | If an assigned value is unusable, or a legacy calculation is out of range, refuse enabled startup with a file and record diagnostic. Off mode can keep serving and preserve any raw deadline value, including a damaged one. Restore an exact saved value from known-good data or correct the preparation configuration for an unassignable legacy record before retrying. | Dropping or treating a damaged value as absent could silently replace a commitment. Clamping out-of-range arithmetic would invent a deadline. |
| C-26, C-27 | Backfill only the missing `due` fields. Leave `updated` intact and retain the normal creation audit field list. This treats recording the deadline as part of creating or preparing the ticket and preserves history when the switch is turned off again. | Calling normal edit methods or recording a new audit field or event would change the observable history of the rollout. |
| C-29 | Keep version 1 with an optional inline field. Support 1.4.0 startup and reads of the same file. Treat a subsequent 1.4.0 write, including its shutdown save, as a possible loss of the deadline extension. Document that exact deadlines surviving that write and a later re-enable are outside the chosen rollback behavior. | A sidecar or encoding deadlines into legacy fields would complicate atomicity or change legacy data solely to survive 1.4.0 saves. |

For an enabled persistent create, build the prospective state and save it before publishing the ticket, id increment, audit append and outbox enqueue in the live store. Use the existing audit and outbox logic on detached state so a write failure cannot leave a partial create and the existing deduplication still applies. Keep the ordinary off-mode creation path's behavior. For preparation use one synchronous, whole-state replacement through `createPersistence`, so the startup operation has one observable commit point. A background migration or per-record writes would put readiness and restart semantics on separate paths.

## Nuances

- **C-3–C-10, C-22–C-23, C-34.** Calculate from the single `created` sample already used for `updated`, the audit timestamp and the creation notification. Use epoch milliseconds and ISO serialization, so time zones and daylight-saving transitions have no effect. Check the resulting instant against both inclusive Date limits before serializing, including expanded years. The duration bound keeps the offset an exact integer. Use the existing internal HTTP error envelope when a valid request cannot get a representable deadline. Compute before touching any live state. The current `create` mutates state before `save()`. For enabled persistent creation, stage audit and outbox via their existing constructors and methods, save the snapshot with the new ticket and advanced counters, then publish the staged changes synchronously. A later worker tick or shutdown must never save a failed creation. Keep request validation for extra `due` fields as-is.
- **C-6–C-9, C-16, C-19, C-21, C-24.** Disk and HTTP are separate boundaries. The same explicit `ticketRecord` projection is used when both reading and writing. Copy `due` only if it is an own property, preserving its exact value. Give missing deadlines no sentinel. Validate assigned times before readiness using the legacy timestamp convention of a nonempty string with a finite parse result. Check the type before calling `Date.parse`, which coerces numbers and arrays to strings. An explicit `null`, empty string or other unusable value is present and becomes an enabled startup error. For a parseable stored value with a noncanonical time representation, preserve the saved value while presenting its UTC ISO representation in the enabled API. Use the same parsed instant for comparisons. Project create, get, patch (including no-ops), transition and each list item at the app boundary. Strip `due` from off-mode response copies, including after a restart on a prepared file, while the store snapshot, worker and shutdown saves still retain it. Raw CLI columns and audit/outbox bodies stay independent of ticket projection.
- **C-11–C-16, U-3.** Keep overdue separate from the generic `matchesFilters` object, whose `some` logic could otherwise admit a ticket based on one field alone. Sample the clock once per overdue request, compare numeric timestamps, and check current `open` or `in_progress` status. Apply both the overdue predicate and existing selection before sorting with `compareIds` and calling `paginate`. Keep the cursor based on the last matching id, preserve limit and cursor checks including the store's decoded-id validation, and preserve the parser's default return shape for existing callers. Enabled requests without overdue and all off-mode requests keep the ordinary listing path. A cursor still walks by id with the same filters. Each page uses the current clock and state, so a newly overdue ticket at or below the cursor is visible on a fresh walk.
- **C-17–C-22, C-25–C-28, U-4.** Load and validate the legacy document first. For each record, distinguish absence from an assigned value, check assigned values, and calculate missing values from `created` and the saved priority for all statuses. Stage the full result before trying to save, so a bad later record leaves the original file untouched. Save once if anything changed, before listening or running the worker. For a preparation calculation error, convert to `DataFileError` with the file path and `tickets[index]` or id. Wrap preparation I/O failure in a path-specific `DataFileError` so it reaches the existing exit-2 startup path. Use the existing same-directory temporary write and rename. If interrupted before rename, a leftover temporary file is irrelevant to the configured file and to the next attempt. If rename happened, the next enabled startup sees assigned values and keeps them. Preserve ticket fields, audit order, outbox records and both sequence counters, and avoid a preparation write when nothing needs filling. Preserve the established single-writer ownership of `DATA_FILE`.
- **C-23–C-29, U-4–U-5.** Exercise a hidden-mode edit, delivery result or shutdown save after preparation. A same-process read alone misses writer loss, and reading on the new loader alone misses rollback breakage. The old loader accepts the additional per-record key because it explicitly extracts known fields, and its writer serializes only those known fields. Keep the top-level version and legacy record shapes. Run the rollback against the exact file the new process leaves after shutdown, including a ticket created while enabled. Read it with the baseline before its graceful shutdown rewrites the file.
- **C-30–C-33, U-6–U-7.** CLI opens the shared persistence loader into a read-only store and directly calls the list query parser. Do not make deadline preparation or enabled-only validation an unconditional consequence of either shared entry point. Existing direct constructors and helpers omit due configuration. They should still work without changes to fixtures and assertions. Test a genuine new-release file with the actual report program. Existing title validation already excludes tabs and line breaks from newly created titles.

## Build order

1. Add the switch, schedule parsing and shared deadline arithmetic. Check exact switch semantics, defaults, sparse overrides, invalid configuration, and elapsed calculations at clock limits.
2. Extend the version 1 ticket record round-trip and install store preparation in service construction. Check legacy loading, off-mode retention, mixed-state restart and failure before readiness. Use the existing snapshot and persistence machinery.
3. Assign deadlines in the store's create path and implement response projection for all ticket routes. Check the saved creation, audit/outbox consistency, error paths, immutable deadlines, and hidden responses.
4. Add enabled query parsing and apply the overdue predicate before pagination. Check clock and lifecycle changes, interaction with filters, malformed requests and existing cursor behavior.
5. Finish the operator/API documentation and new tests under `test/`. Run the focused tests, full `npm test`, launch via `npm start`, and check CLI/report and rollback with actual file artifacts. Use independent copies of test data and stop all child processes by PID.

## How we will know

Use `manualClock` and the existing `test/helpers.js` for deterministic HTTP checks with port 0 and a paused worker. Supply settings via `loadConfig` for normal wiring coverage and use fresh temporary files. Test clause requirements separately from policy examples in the Decisions section. For example, a clause test should use times distinctly before or after the deadline, a single legacy filter at a time when checking C-13, and any supported usable hour override.
