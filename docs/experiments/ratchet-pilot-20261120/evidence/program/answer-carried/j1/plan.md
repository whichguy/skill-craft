## Approach

Keep the HTTP handler in `src/app.js` thin. Register `router.put('/tickets/:id/assignee', …)` using the existing request reader, validation and actor handling. Add a dedicated validator under `src/tickets/` and a synchronous assignment method in `TicketStore`. Create and load tickets with an explicit `assignee` string or `null` so the existing store return paths provide the field in every API ticket representation. Keep create, patch and transition request schemas as currently documented.

Use the store's audited-change path to set the assignee and timestamp, append the audit entry, enqueue any notice and save the whole snapshot. Add an assignment template in `src/templates.js`. The existing outbox, worker, notifier and data-file replacement handle delivery, retries and restart. Extend the version 1 ticket record in `src/persistence.js` so both the service and the read-only CLI see saved assignees.

Extend `src/tickets/query.js` to parse the three filter states and make its shared matcher conjunctive. `TicketStore.list` already filters before sorting and paging. Add an assignee cell to the human listing in `src/format.js`. The CLI already reads via persistence and the store. Add new dependency-free `node:test` coverage under `test/` and use the existing npm scripts.

## Decisions

These are proposed build choices for the open points. Record the choices actually taken in the build report. Tests of the requirements should allow any reasonable answer to an open point.

| Clauses | Choice and reason | Alternative considered |
|---|---|---|
| C-3, C-27, C-38 | Trim surrounding whitespace, reject blank names, and reject remaining C0 controls, DEL and Unicode line/paragraph separators for a single-line display. Accept well-formed Unicode, count code points after trimming for the 40-character bound and use case-sensitive equality without Unicode normalization. This accepts international names, gives an encoded GET filter the same identity as the PUT, and keeps names legible. Apply one agent-name rule to PUT, nonempty filters and saved strings. Treat only the literally empty query value as the unassigned selector. | Exact preservation of surrounding whitespace would make accidental spaces and whitespace-only names hard to distinguish in the CLI. Case folding or normalization could merge distinct names without a directory to define identity. UTF-16 length would count supplementary characters twice. |
| C-5 | Return HTTP 200 with the resulting ticket for both changed and unchanged PUTs, matching PATCH and transition. Callers get the current version in the acknowledgment. | A minimal JSON acknowledgment would require a GET for those callers. |
| C-17, C-19 | Use `ticket.assignee_changed` as the audit action for all effective changes and `ticket.assigned` as the notice type for named assignments. Pass the saved name directly as the notifier destination. That follows the existing relay interface without introducing agent-directory configuration. | Treating assignment as a generic patch obscures it in the audit trail. An address lookup or an assumed email domain would require an external naming policy. |
| C-19 | Queue one notice per genuine named assignment, including a return to the same agent while their first notice is pending. Key the event by type, ticket id and the assignment audit sequence. The persisted sequence distinguishes real changes even at the same clock instant, and the event's key and id stay stable across retry. | A key by type and ticket suppresses the new recipient's notice. A key by ticket and agent can coalesce pending repeats, also a reasonable answer to the open point, but the proposed choice records each time an agent gained the ticket. |
| C-27 | Use the first `assignee` parameter, consistent with the existing `URLSearchParams.get` behavior for status and priority. | Rejecting repeated parameters or using the last would introduce an assignee-specific convention. |
| C-32, C-33, C-35 | Show an `ASSIGNEE` table column with quoted names and a plain `unassigned` label, which remains distinct even if an agent is named “unassigned.” Keep `--raw` at its current four columns and keep the `show` detail fields as they are. Its existing history display can render the assignment entries. | Appending a fifth raw column could surprise scripts that expect four. Adding a field to `show` would expand a display the requester specifically asked to change in `list`. |
| C-12, C-24–C-26 | Add a nullable field to the shared version 1 ticket record and default a missing field at load. Also default absence when the store is constructed directly from legacy state. An HTTP-only fallback would miss filters, audit diffs and the CLI. |

## Nuances

- **C-6–C-11, C-18.** Follow the existing order of body read, schema validation, actor parsing, ticket lookup, then status check. Use the configured JSON reader so padding and multibyte input count toward the byte limit and oversized requests can still receive the JSON envelope. Require the body's own `assignee` property and refuse extra fields. An explicit field value of `null` passes validation. Reuse `isActive` from `states.js` to cover both ineligible states. A well-formed same-value PUT on an inactive ticket is a conflict. A bad actor is invalid even for a same-value PUT. Existing error handling logs unexpected details and sends the public 500 envelope. The HTTP test helper sends a string argument as raw bytes, so pass JSON string literals with their quotes when exercising valid JSON of the wrong top-level type.
- **C-12–C-18, C-35.** Use the stored value after lookup and the eligibility check. For the same value, return a copy before reading the clock or touching audit, outbox or disk. Keep the check, change and save synchronous after the body has been read so concurrent same-target PUTs see one effective change. For an effective change record only the assignee delta, using one time for `updated`, the audit entry and any notice. Keep the creation audit field set intact. Existing tests compare it exactly, and initializing an assignee to null makes no assignment change. Edits, resolution, closure and reopening preserve the field. Correction or reversal is a new audited assignment change.
- **C-10, C-16–C-17, C-19, C-25.** Reuse one store change and one save, including the notice. Pass the appended entry to the existing notification effect so it can use the actual global sequence. The current `apply` mutates live state before `save`; an exception before file replacement could otherwise leave a phantom assignment that a later retry treats as successful. For assignment, keep the pre-change ticket plus audit and outbox state and counters when persistence is enabled. Restore them on failure before commit and propagate the error. Keep rollback inside the store and the write synchronous. The rename is the commit point. The existing persistence path returns immediately after rename. Keep this work scoped to the assignment path and reuse the underlying audited mutation.
- **U-2, C-19–C-23, C-25, C-35.** Capture recipient and ticket details in the event when the change happens. Looking up the current agent at delivery would send Dana's pending notice to Sam. Reassignment or clearing leaves earlier events available for delivery and their history intact. Clearing queues no new notice. Template wording should identify the ticket and say it was assigned to the recipient. Existing creation and resolution notices keep their destinations and dedupe behavior. A file delivery failure stays in the outbox retry flow and cannot undo assignment. A crash after delivery and before recording it may retry the same event id and key.
- **U-4, U-7, C-24–C-26, C-34.** Add the field on both sides of the explicit ticket serializer. Validate present values before accepting a record and name `tickets[index].assignee` in failures. Distinguish absent from explicitly invalid values and preserve explicit null. A default supplied when reading is in-memory only until an ordinary service save. Keep the existing one-writer model and same-directory temporary-file rename. An older executable can read the version 1 shape but a save by that executable drops the assignee field and its worker lacks the assignment template. The existing persistence test projects only old ticket fields, so verify the new field directly.
- **U-3–U-5, C-27–C-35.** Build filters as absent, `null`, or a valid name. Skip only `undefined` entries when checking provided filters and replace the current `some` with an all-match test. This also fixes the existing status-plus-priority combination in both API and CLI. Sorting stays numeric, and pagination sees only matching records. Leave the opaque cursor format and existing validation alone. Cursors resume by id on the current matching set using the same filters. CLI table formatting should use its normal paging and preserve the empty-table output. Raw output remains one physical line per ticket with its established fields in their original positions.

## Build order

1. Establish the assignee input rule and nullable ticket state. Wire the field through create, legacy load, record validation and snapshot serialization. Check the old data-file fixtures, the exact creation audit and ticket reads.
2. Add the store mutation and its audited notification effect, plus the matching template. Check changed versus unchanged saves, audit ordering, outbox entries across two agents and two tickets, and the recovery path on save failure.
3. Register the endpoint and use existing body, validation, actor and error helpers. Check live API responses for the state matrix, payload errors and request-size boundary.
4. Extend query parsing and shared filter matching. Check the omitted/empty/named distinction, status plus priority, and matching records across cursor boundaries.
5. Add the table column and exercise the CLI and weekly report against saved data. Complete the restart, worker and integration coverage and run the full suite with the original tests intact.
