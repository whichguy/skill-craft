## Approach

Use the existing HTTP, store and whole-file persistence path. A ticket gains an optional saved `due` field in the version-1 ticket record. It is absent on legacy records, is assigned by the store for enabled creates or by explicit preparation for missing records, and stays in the store and on disk across all subsequent edits and saves. Keep the existing body allowlists. A shared deadline calculation and saved-value validation serve creation, preparation, activation and overdue selection as appropriate.

`src/config.js` reads the exact rollout switch and the per-priority settings. `src/server.js` passes the mode and schedule explicitly into the components and verifies the production file before the HTTP listener or notification worker can start. Provide a one-shot `npm run prepare:due-times` command that reads only the file and schedule settings through shared config helpers and uses the existing persistence writer. Its store operation can prepare a full snapshot without starting a service, worker or notifier.

`src/app.js` uses one mode-aware projection for all five ticket responses and parses the overdue opt-in only when enabled. `TicketStore.list` applies the overdue predicate to the existing matching set before the existing numeric sort and cursor pagination. Audit and admin-outbox routes retain their existing bodies. The CLI continues to open a read-only store on either file shape. Add configuration and activation instructions to README, the operations guide and the API reference. Cover the changes with new CommonJS `node:test` files under `test/`.

## Decisions

The choices below are working answers to the open points. The build report should record its actual choices. Acceptance of an open point follows the applicable clause under any reasonable answer.

| Clause | Choice and reason | Alternative considered |
| --- | --- | --- |
| C-4, C-5, C-16 | Use restart-scoped `DUE_HOURS_URGENT`, `DUE_HOURS_HIGH`, `DUE_HOURS_NORMAL`, `DUE_HOURS_LOW`, with defaults 4, 24, 72, 168. Use the existing decimal whole-number syntax with trimmed input, empty/unset defaults, and a positive range of 1–2,400,000,000 hours so the integer millisecond offset is exact. Parse the schedule only for enabled service or preparation. Treat the switch as literal `DUE_TIMES=on`. | Live reload and zero or fractional hours would introduce additional policy and parsing rules. Validating schedule overrides in off mode could make a working deployment fail to start. |
| C-6, C-30, C-31 | Keep human-readable CLI output as it is. The new display field belongs to enabled HTTP ticket responses in this plan. | Adding a human-readable due column would expand the display change into an operator interface whose treatment is open. |
| C-11 | Require elapsed time strictly beyond the due instant. Read the clock once per overdue request. | Including equality would make a ticket overdue at the instant its allotted time ends. |
| C-12, C-13, C-16 | Retain the legacy OR for status and priority everywhere, including overdue lists, and apply overdue as a separate AND condition. Document this predicate for the overdue query. | Changing the combined filter to AND, even just for overdue, would introduce two different interpretations of the same pair of filters. |
| C-15 | Accept a single exact `true` to opt in and a single exact `false` as ordinary listing. Reject empty, other values and repeated keys in enabled mode with `InvalidError`. Off mode ignores all of them. | First-value-wins or silently ignoring misspellings makes it harder to tell whether overdue filtering happened. |
| C-17, C-25 | Use a one-shot offline preparation command. Stop the server and all writers, back up the configured file, run preparation to completion, then start the desired mode. The command uses the existing single-writer model and needs no new locking protocol. | Live preparation would race the store's in-memory snapshots, worker writes and shutdown save unless coordinated across writers. |
| C-18, C-19 | Use the schedule provided to preparation for all missing values, including tickets created while off. Use the record's then-saved priority, and preserve every assigned value exactly. Off-mode creates defer assignment. | Earlier configuration and priority history are unsuitable for reconstructing an intended historical schedule. Assignment while off would make ordinary off-mode writes use the new arithmetic and its failure modes. |
| C-20 | Refuse enabled startup if a configured file contains missing deadlines. Allow an empty or absent file on first start, and allow enabled in-memory operation without `DATA_FILE`. A persisted create uses the regular commit path. | Implicit startup migration conceals the preparation checkpoint. Falling back silently could leave an operator thinking activation succeeded. Refusing in-memory mode would prevent a useful local deployment. |
| C-21 | Distinguish an absent key from a present damaged value. Enabled startup and preparation refuse damaged values with the file and record in the diagnostic. Off mode can serve and keeps the damaged value on rewrite. Document that an operator must recover the original value from a trusted record or backup before activation. | Treating bad values as absent would silently give an already assigned ticket a different deadline. Refusing off mode would prevent a legacy-compatible recovery path. |
| C-22 | Reject out-of-range calculations. For enabled creation, use the existing HTTP 500 internal envelope. For preparation, report the offending file and record and leave the old file intact, so an operator can investigate the source data or choose a usable schedule if applicable, then retry. | Clamping or wrapping violates the deadline rule, and skipping a record leaves a file unready for activation. |
| C-26, C-27 | Treat preparation as metadata maintenance. Preserve `updated`, skip migration audit entries and retain the legacy creation audit fields. Existing histories and future patch and transition entries keep their usual meaning. | Touching `updated` or logging preparation as an edit would imply ordinary ticket activity and alter history visible to off-mode callers. |
| C-29 | Extend the version-1 record and use 1.4.0's existing tolerance for extra keys. Document that 1.4.0 writes, including clean shutdown, can strip deadlines. Keep a rollback-time copy for investigation and treat deadline recovery after old-release writes as an operator decision. | A version bump would block rollback startup. A parallel file or an encoding hidden inside existing fields would add consistency problems or change legacy data and is unnecessary for the required rollback. |

## Nuances

- **C-3–C-5, C-22, U-1 and U-2.** Derive `created` and `due` from a single injected clock reading. Use `created` in the existing create audit and notification. Let the existing validator supply the default normal priority. Use numeric epoch milliseconds and elapsed-hour multiplication, independent of local clocks and daylight saving. Check finite, integer milliseconds and the inclusive Date bounds before ISO serialization. Support extended-year Date strings. Do the calculation before taking an id or touching audit and outbox. Thread settings through `createService` explicitly, with off defaults for existing direct callers and helpers that do not call `loadConfig`.
- **C-6–C-10, C-16 and C-24.** Store copies from `get`, `list`, `create`, `update` and `transition` go through the same HTTP projection. Omit `due` from these copies in off mode, including items on every list page and responses from already-prepared tickets. Keep the saved field on the underlying record. Preserve an assigned value on disk verbatim and render UTC ISO from its instant at the enabled API boundary. Validate saved deadlines as absolute timestamps with an explicit zone so a restart under a different local time zone cannot shift the instant. Accept ISO UTC strings and valid ISO times with an explicit offset, including the Date boundary forms. Keep the existing parser for legacy `created` and `updated`. Editable fields stay on the existing allowlists and ordinary no-op and lifecycle rules still apply.
- **C-11–C-16, U-3.** `matchesFilters` uses `some` over the filter entries. Putting overdue into that object can allow unrelated rows through or select nothing. Use a separate list option, compare parsed deadline instants to one captured clock value, and explicitly allow only `open` and `in_progress`. Filter the entire matching set before slicing pages, including when cursor ids cross the four-digit boundary or the cursor ticket itself no longer matches. Preserve existing cursor token and validation, limit, envelope and unknown-query behavior. Membership can change between requests as time or state advances. The fixed-set pagination promise applies when matches stay fixed.
- **C-17–C-22, C-25–C-28, U-4.** Treat preparation as one load, validation and save. Require a configured path, treat an absent file as an error for this explicit command to catch mispointed paths, and succeed on an existing empty or fully prepared file without rewriting it. Inspect the entire state, calculate all missing values in a candidate snapshot and validate assigned values before calling the writer. Use the ticket's own `created` and priority, even if `updated` is later or the ticket is closed. Keep ticket and event counters, legacy ticket fields, audit sequences and all outbox states. Wrap migration calculation errors with file and ticket context and use exit 2 for unusable config or data, including a missing prerequisite on activation. A failed write reports failure with the file named. Use the existing temporary file and same-directory atomic replacement. Leave the configured file readable before or after an interruption, and ignore any incomplete temporary sibling on a retry. Clean up temporary files from handled failures where possible without masking the original error. Restarting off allows more undated creates, so repeat preparation after the last off-mode writer stops and before every activation that follows off-mode writes.
- **C-19–C-21, C-24 and C-29.** `ticketRecord` is shared by the old-style reader and whole-file writer. Copy `due` only when it is present as an own property, in both directions, including through worker and graceful-stop saves. Do not default a missing field to null, and preserve even a present invalid value while hidden. Use deadline-specific validation for prepare and enable, keeping legacy validation of other fields identical. Presence alone is insufficient for activation. Validate a loaded production state before serving any route and tell the operator how to prepare when a deadline is missing.
- **C-22, C-23, C-28 and C-34.** `TicketStore.create` currently mutates live state before calling `save`. For enabled persistent creates, stage the ticket, counters, audit and notification using the existing representations and helpers, synchronously save the complete candidate through the existing persistence interface, then publish it as live state and return it. Reuse the normal creation logic against the staged state and take care to perform one save. If a write fails before replacement, the handler returns the existing 500 envelope and the worker, later requests and final shutdown save still see the pre-create state. Keep the legacy create path for off mode. The outcome after successful replacement but before the client receives 201 is the ordinary ambiguous HTTP outcome, with a complete ticket, audit entry and outbox event surviving restart.
- **C-24, C-28–C-31, U-5 and U-6.** The worker's notification due predicate is independent of ticket overdue. Use the existing notification data, keys and delivery path. Rollback verification must boot the actual unchanged 1.4.0 code and read the same file. The old loader discards `due` in memory. A read-only session followed by graceful shutdown still rewrites the file because `service.stop()` always calls `store.save()`. Keep a deadline-bearing copy before starting the old release and inspect the live file before and after its shutdown. If 1.4.0 accepted writes, keep those writes in the current file when planning deadline recovery. The raw CLI must keep id, status, priority and title at positions 1–4 and must remain read-only. Keep tab-safe title validation and the report's entry point.

## Build order

1. Confirm the original suite and identify the rollback baseline. In this repository `d7c78c1` contains the 1.4.0 service, and `20e07d6` only adds the specification. Record the baseline so the rollback check can run the original code from a temporary archive without switching branches.
2. Implement the shared schedule and elapsed-time calculation, then the conditional version-1 ticket serialization and the two load policies. Check defaults, invalid overrides, a legacy file and a mixed file, including valid and damaged assigned values.
3. Implement the preparation command as an explicit store operation. Verify changed and unchanged runs, preparation with an out-of-range record, and atomic replacement failure before wiring activation. Add the boot gate in service construction so failures occur before network or worker activity.
4. Assign deadlines on enabled creation and complete the enabled persistent commit, then route all ticket API responses through the mode-aware projection. Exercise a create, no-op and changing patches, lifecycle transitions, a failing save and restart. Run the existing suite with the feature in its default mode.
5. Add flag-scoped overdue parsing and the store predicate ahead of pagination. Verify numeric ordering, filter combinations, legacy behavior and an advancing clock. Check CLI and report on the same saved file.
6. Finish operational and API documentation, including the chosen answers to open points. Complete the new tests, run `npm test` and the actual 1.4.0 rollback rehearsal. Record the chosen answers and verification results in the build report.

## How we will know

- **U-1 (C-1–C-6, C-10, C-22, C-23, C-34).** Start via `npm start` on a free port and check health with no dependencies installed. With `manualClock` at the use case timestamp, create four explicit priorities and an omitted priority. Check exact ISO deadlines and all response shapes. Check body attempts to set `due`. Calculate a result exactly at the upper Date bound and one millisecond beyond. Test creation from the lower Date bound and reading a ticket with a saved deadline at that bound. Check an elapsed-hour fixture spanning a local clock change. For persistent creations inspect the file immediately after 201, before shutdown, for ticket, audit and outbox. Inject a pre-replacement write failure without relying on OS permissions, prove live reads and the persisted state see no partial effects, restore the writer before shutting down and check again after restart. Then verify a successful retry.
- **U-2 (C-4, C-7–C-9, C-24, C-27).** Start with one schedule and restart with an override under the same file. Confirm old and new deadlines side by side and repeat after a priority patch and the resolve/reopen and resolve/close branches. Check legacy actor and field changes and that a no-op leaves history and `updated` alone. In a hidden restart change a prepared ticket and save an outbox delivery result. Re-enable and compare the persisted values exactly.
- **U-3 (C-11–C-16).** Seed past, future and boundary deadlines across all statuses and interleave matching and nonmatching ids, including a four-to-five-digit id boundary. Check ordinary listing, overdue listing with no other filters, single legacy filters, the combined-filter behavior selected for the build, a reopening and time advancing without mutation. Follow `next` with the same filters and test limit 1, default 20, limit 100, empty and terminal pages, invalid limits, malformed cursors and a decodable token with an invalid ticket id. Check required selection using instants strictly before and after the clock. Exact equality and nonrequired values may be characterized for this build without making its choices acceptance gates.
- **U-4 (C-5, C-16–C-28, C-34).** Populate a legacy file with all statuses and distinct creation and update times, original history and pending, sent and dead notifications. Attempt premature activation and confirm no enabled ticket is served with missing persisted deadlines. Test an empty file and a mixed file, repeat preparation under changed settings, and verify that an interrupted pre-rename write or a simulated atomic-write failure leaves an old whole file and a retry finishes preparation. Include bad response hours and damaged assigned dates, verifying diagnostics for refused input when applicable. Compare off-mode responses including create, fetch, patch, transition, list, audit and outbox with legacy responses for unset, empty and other switch values. Confirm every overdue form is ignored while off and a prepared file survives worker and graceful-stop saves.

Stop each service or child by its own handle or PID. Test open points against the observable clauses so other reasonable choices remain acceptable in the ratchet review.
