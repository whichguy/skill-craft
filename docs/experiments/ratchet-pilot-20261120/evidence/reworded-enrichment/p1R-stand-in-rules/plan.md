## Approach

Add `src/orders.js` as a CommonJS module with named `parseOrders` and `total` exports, consistent with `src/meter.js` and the existing `require` callers. Load the existing meter from `./meter`. Put the new coverage in `test/orders.test.js` using `node:test` and Node assertions. The current `npm test` script already discovers tests with `node --test` (C-1, C-2, C-25, C-26).

`parseOrders` accepts a primitive string and walks lines in source order, preserving physical line numbers. For each nonblank line, collect the trimmed field values, validate the order, and append a plain object with `id`, `qty`, `price`, `status`, and `shippedAt`. Return the completed array. Keep the per-line field data and the result local to the call (C-3–C-21).

`total` walks the supplied orders once. For each order, call the shared `meter.tick()` before adding `qty * price` to a local sum initialized to `0`. Return the sum when the traversal finishes. The existing meter owns the count, limit, error, and reset (C-22–C-24, C-27).

## Decisions

The defaults below let the builder proceed on the specification’s `Open:` points. Record the choices actually taken in the build report. The requester can settle those points later, and acceptance checks must pass other reasonable choices that satisfy the clauses.

| Clause | Build choice and reason | Alternative considered |
| --- | --- | --- |
| C-3 | Match the five exact field names in any order, trim values, and split each segment at its first `=` so the full value reaches its validator. Reject missing, repeated, or unknown keys and empty segments with a line-specific `SyntaxError`. A line-local `Map` gives exact lookup and detects repeats, including a repeat of a field with an empty value. | Fixed positions couple recognition to the sample order. Trimming keys expands accepted syntax, truncating at a second `=` discards input, and silently skipping or overwriting fields can hide mistakes. |
| C-4 | Support LF and CRLF. Test for blankness with `trim()` on each line and keep the split index for diagnostics. | Splitting on additional separators such as lone CR or Unicode line separators expands what counts as a physical line. |
| C-8 | Accept nonnegative base-10 digit strings for `id`, including zero and leading zeros. Convert with `Number` and require a safe integer. Reject empty, nonnumeric, fractional, signed, or out-of-range IDs with a line-specific `SyntaxError` under this default. This preserves exact identifiers within the accepted range. | Broad JavaScript coercion can silently round distinct IDs to the same value or turn empty text into zero. |
| C-9, C-10 | Require one or more base-10 digits for `qty` and `price`, accepting leading zeros. After conversion, require a safe integer at least `1` for `qty` and at least `0` for `price`. Use `RangeError` for failures, including empty price and signed, exponent, fractional, or nondecimal text under this default. That keeps accepted values integral and exactly representable. | General numeric coercion accepts extra spellings and can turn empty price into zero. `parseInt` can accept `1.5` or a numeric prefix and discard the rest. |
| C-17 | Validate the shape of nonempty dates with an anchored pattern for four ASCII digits, a hyphen, two digits, a hyphen, and two digits. Return the trimmed text. Shape-valid strings such as `2026-02-30` are accepted under this default. | Calendar validation adds a rule that the requester left open. Converting through `Date` can normalize the input and lose its original text. |
| C-20 | Stop on the first invalid nonblank line. On that line, scan segments left to right for malformed, unknown, or repeated keys, then check required key presence. Validate `id`, `qty`, `price`, normalized `status`, date shape, then status and date consistency. This gives a simple deterministic order for diagnostics. | Collecting several errors adds an error aggregation contract. Prioritizing validation categories across lines can make a later bad line mask the first one. |
| C-22 | Accept arrays of valid orders as the supported input, use ordinary `Number` multiplication and addition, and apply no extra validation or overflow handling. Products or sums outside the safe integer range have normal JavaScript rounding under this default. The result remains a number in cents. | Generalized input validation, overflow rejection, or `BigInt` arithmetic would choose additional behavior and `BigInt` would change the result type. |

## Nuances

- **C-4, C-5, C-20 and U-2.** Removing blank lines or trimming the entire input before numbering would renumber errors. Traverse the original split lines, skip whitespace-only lines at their original indices, and include `Line N` in each required line error. Check `typeof text === 'string'` before splitting so boxed strings and other non-string inputs take the argument-level `TypeError` path.
- **C-3, C-12, C-15, C-18 and C-19.** A segment with no `=` and a present field with an empty value take different paths. Preserve `shipped_at=` as a present field with an empty string. Use presence checks that distinguish missing keys from empty strings. Detect a malformed segment even if the corresponding required key will also be absent.
- **C-6, C-9–C-19.** Normalize trimmed values before validation. Check status membership after lowercasing. Apply the date shape check only to nonempty text, then require empty text for `open` and a nonempty date for `shipped`. Otherwise a shape check can reject every valid open order or a consistency check can admit a malformed shipped date. Construct the output object after validation so its properties have their required names and types.
- **C-13–C-21.** Match the error class and original line for each independent validation failure. `qty=two` and `price=free` are range errors, a bare `qty` token is a syntax error, and an invalid argument has no source line. Testing several problems in the same input would depend on the open precedence decision.
- **C-22, C-23 and U-3.** Both statuses and zero-price orders count toward the work budget. Tick on every visited order, including one that contributes zero cents. A single tick for the whole call, a tick per unit of quantity, or a tick only for nonzero subtotals fails the budget. The empty input performs no work even when the meter already has ticks. Parsing needs no meter calls.
- **C-23, C-24, C-27 and U-4.** `tick()` increments the shared count before testing the limit. With the count at 9,999, one more tick succeeds and the next attempt throws the exported `LimitError` with the count already advanced. Let the exception propagate at that point. Preflight checks, resets, or rollback in `total` would change the meter’s behavior. In a longer traversal, ticks already spent remain charged, the failed tick is recorded, and later orders are skipped as the exception exits the call. A caller reset restores the budget and a retry starts its sum from zero.
- **C-23–C-27 and U-3–U-5.** Meter state is shared by callers in the same Node process. Reset around each meter-sensitive test and register cleanup before exercising the helpers so an assertion failure leaves the next test with a clean state. Keep cases that seed and assert the shared count sequential in the test file. Use the real meter, including its exported `LIMIT` and `LimitError`, so the test exercises the same integration as callers.
- **U-1–U-5.** This is an additive module in a project with the meter and its tests. The parser retains no records between calls and the only state modified by totaling belongs to the meter. There is no persisted data to migrate. Reverting the two added source and test files restores the prior project without a meter or test-runner migration.

## Build order

1. Add the CommonJS orders module. Implement parsing from argument and line handling through field collection, value normalization, typed validation, and object construction. Add and run the parser cases in `test/orders.test.js` with `node --test test/orders.test.js`.
2. Complete the exports with `total` and the existing meter integration. Extend the same test file with cents, repeated calls, empty and zero-price orders, the hard limit, and recovery after reset. Rerun the focused file.
3. Run `npm test` to check discovery and compatibility with the existing meter tests. Confirm the implementation and tests meet all numbered clauses. Record the open-point choices in the build report.

Inputs whose outcomes depend on an `Open:` choice are outside those assertions, including field permutations, alternative separators and number spellings, shape-valid calendar anomalies, multiple simultaneous errors, and out-of-contract or overflowing totals.
