## Approach

- Add a nullable `assignee` to the ticket records in `src/store.js` and to the version 1 record reader and writer in `src/persistence.js`. Initialize it at creation and supply null for old records on load. The store's existing copy-based reads and mutation responses will then expose it throughout the API (C-12, C-13, C-27, C-28).
- Register `router.put('/tickets/:id/assignee', ...)` in `src/app.js`. Use the existing bounded JSON reader and actor extractor. Add an assignment body validator in `src/tickets/validate.js`, then call one synchronous store method. It looks up the ticket, checks `isActive`, compares the requested value to the current one, and applies a real change through the existing store mutation path. Save the ticket, audit and any notice together (C-1–C-18, C-27, C-44).
- Enqueue `ticket.assigned` for each real change to a named agent, using the assignee as the event recipient and the ticket id and title captured at the time of assignment. Add a template in `src/templates.js`. Use the existing outbox, notification output and worker, including retry and restart handling (C-19–C-26).
- Extend `src/tickets/query.js` and use the existing store list path for all filters and cursor paging. Add the assignee column to the table in `src/format.js`. The CLI already reads the same records through a read-only store, and the weekly report already consumes its raw listing (C-29–C-38).
- Add assignment-focused `node:test` files under `test/` using the existing service helper, manual clock and isolated data and notification files. Keep the Node and npm entry points and configuration in place (C-39–C-43).

## Decisions

The choices below cover all seven `Open:` lines. The build report should record the choices it actually takes. Acceptance tests should use inputs and assertions that pass for any reasonable answer to each open point.

- **C-1, success response.** Return 200 and a copy of the current ticket for changes and successful no-ops, matching PATCH and transition. A 204 would make clients issue another read to get the resulting ticket. Tests assert 2xx and check the value through GET.
- **C-5, equal values on inactive tickets.** Apply the active-state check first, returning 409 even when the value is already present. This matches the status-first mutation style in the store. An equality-first check would make eligibility depend on which value the caller sent. Tests assert conflict on changes in resolved and closed states.
- **C-7, name handling.** Trim outer whitespace, reject empty results, measure the trimmed name with JavaScript string length, and reject controls and line breaks in the retained name. Reuse the existing text rules and add assignment-specific checks for C1 controls, Unicode line and paragraph separators, and unpaired surrogates so accepted names round-trip through the UTF-8 query and CLI. Literal untrimmed storage would make accidental surrounding whitespace part of the identity. Byte counting would diverge from the existing text fields. Tests assert the body shape and the ordinary ASCII bounds.
- **C-19, recipient.** Set the event's `to` to the stored agent name. The available delivery boundary is the existing in-memory record or JSON line consumed by the relay. It already carries a string recipient. An address syntax requirement or new directory lookup would add a prerequisite to using ordinary names. In the delivery test, check that the output identifies the selected recipient and ticket and conveys an assignment.
- **C-21, repeated delivery to the same agent after an intervening change.** Queue a distinct notice when a new assignment returns the ticket to a previous agent. Use a key containing the notification type, ticket id and appended audit sequence. Each real change has its own sequence, including changes in the same millisecond, and the existing outbox preserves the key and event id for retries. A key per ticket would wrongly merge different recipients, and a key per ticket and agent would coalesce a return to an earlier agent while their first notice is pending. Tests require two notices for two different agents and a single notice for an uninterrupted repeat.
- **C-29, filter identity and query edge cases.** Use the same name parser for a nonempty decoded query value as for a string in PUT. Compare stored names exactly after trimming, case-sensitively and without Unicode normalization. An empty decoded value is the unassigned sentinel. A nonempty value that fails name validation gives 400, and repeated keys use the first value like status and priority. Separate normalization rules could produce stored names that the same apparent query fails to find. Case folding could merge distinct names. Tests use ordinary names and a single assignee key.
- **C-36, CLI output.** Add an `ASSIGNEE` table column before `TITLE`. Show null as `(unassigned)` and quote agent names as JSON strings. An agent can legitimately be named `(unassigned)`, so displaying every name literally would make that row indistinguishable from an empty assignment. Keep the raw listing at its existing four fields, preserving consumers that expect that exact layout. Appending a fifth raw field is compatible with the weekly report's position-based parsing but changes the output for consumers that count fields. Tests check the visible assignee and existing field positions and counts, allowing an optional extra raw field.

These choices apply to the shared store and data format.

- **C-3, C-12–C-16.** Introduce `ticket.assigned` as the audit action for any change of assignee, including clearing. Use `changes.assignee` to carry the direction and values. Keep the four existing creation audit fields. Adding a null-to-null creation change would invent a change of responsibility and fail the exact existing creation history assertion. Keep assignment input on the dedicated endpoint because accepting it through creation or PATCH would bypass that endpoint's eligibility and side effects.
- **C-27, C-28.** Keep version 1 and extend its explicit ticket record. Default an absent assignee to null. Check a present non-null value against the stored-name rules, with a ticket-field-specific data file error for invalid data. A separate migration rewrite or version bump offers no benefit for an optional field and would complicate opening existing data and the current version check.
- **C-27, C-44.** Keep the synchronous store transaction and same-directory atomic rename. For a real assignment with persistence enabled, checkpoint the store before calling `apply`. If `apply` throws, restore the ticket map, audit and outbox including its next event id from the checkpoint, then rethrow. Reuse the constructor's state hydration for the restore. The pre-change snapshot already copies the scalar ticket fields, audit change records and outbox state. A second save or an inverse audit event would leave evidence of a refused change or fail at the same unavailable destination. Limit the checkpoint to assignment changes. The existing file save writes and renames before it returns, so a synchronous exception in that path means the replacement failed.

## Nuances

| Clauses / use cases | What a quick build could miss | How to handle it |
| --- | --- | --- |
| C-5–C-11, C-17 / U-1, U-2 | An inactive ticket can still accept ordinary edits when resolved. Reusing PATCH's final-state check permits assignment there. Validating or reading state after mutation also gives refused requests side effects. | Parse a bounded JSON object, check the sole field and read the actor before entering the store. Recognize explicit null by presence and value. In the store use `find` for 404 and `isActive` for 409. Use the existing exception envelope and allow unexpected faults to reach the existing generic 500 handler. |
| C-7–C-9 / U-1 | Body bytes, agent string length and actor string length are different limits. A bare JSON null differs from an object with a null value. | Use `readJson` with the same configured max and preserve its drain-on-oversize behavior. Validate the field separately. Pass the trimmed/defaulted actor through `actorOf` even on a no-op. |
| C-4, C-14–C-18 / U-1, U-6 | Two handlers can finish reading their bodies in either order. A stale ticket or equality check done before an await can cause duplicate notices or a forbidden update after resolution. A fixed clock can hide an accidental timestamp change. | After body and header validation, perform lookup, status check, equality check, timestamp, audit append, notice enqueue and save in one synchronous store call. Return a copy immediately on equality so every side effect is skipped. Take one UTC change time from the injected clock and use it for `updated`, audit and enqueue. Check audit sequence for races, and advance the test clock before the no-op. |
| C-12, C-13, C-15, C-28 / U-2, U-6, U-7 | Missing legacy values can disappear in JSON, fail the null filter or make the first audit `from` undefined. Clearing ownership during resolve or close would lose responsibility history. | Normalize every ticket at creation and hydration, including a legacy snapshot supplied directly to the store. Use the same explicit field in the persistence record. Keep update and transition limited to their own fields. Reopening retains the assignee and makes subsequent assignment changes eligible again. Preserve existing audit records and let `AuditLog.append` assign the global sequence. |
| C-19–C-22, C-26 / U-3, U-8 | The default type-and-ticket outbox key can drop a new recipient's notice while the first is pending. Rendering from the current ticket at delivery can send the wrong news after reassigning, clearing or editing the title. | Let `apply` pass the appended audit entry to its effects callback along with the time. Use its sequence in the assignment event key. Capture the recipient and text inputs at enqueue time. Leave queued records intact when clearing or reassigning. Keep creation and resolution event recipients, keys and templates on their current paths. |
| C-22–C-25, C-27 / U-3, U-7, U-8 | A missing template eventually looks like a broken destination. A delivered line is possible before its status is saved, and elapsed wall time alone does not run a worker with interval 0. | Render assignment from its event with the ticket id and clear assignment wording. Let the worker alone deliver, record failures and apply backoff. A reloaded pending event remains eligible at its recorded due time with the same key and id. An already-sent event stays out of the due set. |
| C-10, C-11, C-27, C-44 / U-1, U-7 | The current `apply` mutates memory before saving. A rename failure can return 500 yet leave the assignment, history and notice visible. The next PUT then looks like a no-op, and a worker tick or shutdown save can write the refused change. | Restore the checkpoint before returning control to the app, so following reads, retries, worker ticks and shutdown saves all see the original state. Keep one atomic disk save for all three records and use the same persisted path for clear and reassignment. Test a failed replacement separately from a delivery failure and separately from a crash after sending. |
| C-27, C-28 / U-7 | Backward reading has two directions. The old executable's explicit field list drops assignee on load/save, and its templates do not support the new notice type. | Keep previous files readable in the new service. For operational rollback, treat an older binary with a newer file as lossy. Restoring a pre-change backup is a return to that snapshot and takes later changes with it. Keep that distinction in the build handoff. |
| C-29–C-35 / U-4 | `matchesFilters` currently uses `some`, although documented status and priority already combine with AND. A truthiness check drops the unassigned filter. Paging first leaves short pages and incorrect cursors. | Use `params.has` to distinguish omission, set empty to null, and change the matcher to require every supplied entry, still ignoring undefined values. Filter using current ticket values before numeric id sorting and `paginate`. Continue strictly after the cursor id even if it no longer matches. Reuse the existing limit rules and cursor format and validation. |
| C-36–C-38 / U-5 | The CLI reads persisted records, so a correct API response alone cannot make its table work. Adding the text to the raw formatter can change script input. | Use the shared record loader and table formatter, and keep the list command's page loop and status/priority options. Compare file bytes around the command. Run the actual weekly report against mixed assignments to check its input contract. |

## Build order

1. Introduce the name parser and nullable ticket model. Update the record reader and writer with legacy defaults, and verify old and new fixtures can load through the same store. Keep the creation history check intact.
2. Add the assignment store method, effects callback entry and assignment template together. Check assign, reassign, clear and equality against ticket reads, the audit log and the outbox. Check a failed assignment save and its retry before exposing the HTTP route.
3. Wire up PUT with the existing parser, actor extraction and router. Exercise successful and refused requests through real HTTP, including the limits and the two races.
4. Extend list query parsing and combine the filters in the shared matcher. Check mixed matches and nonmatches across page boundaries. Add the table column, then verify the real CLI against the service's data file and run the weekly report against it.
5. Complete the end-to-end restart and delivery coverage with the real data file and worker, using a manual clock and explicit ticks for retry intervals. Run focused assignment tests, then run `npm test`. Smoke-test `npm start` with `PORT=0`, use the logged port and stop the processes by their PIDs.
