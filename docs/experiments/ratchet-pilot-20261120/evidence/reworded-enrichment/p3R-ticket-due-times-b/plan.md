## Approach

- Keep the version-1 JSON document and add an optional `due` field to each ticket record in `src/persistence.js`. Teach both the reader and the writer to carry it through. The absence of the key is the legacy case. The saved UTC timestamp is the assigned deadline. Current settings, later ticket edits and the visibility flag do not recalculate it.
- Wire the exact `DUE_TIMES=on` switch and the schedule through `src/config.js` and `src/server.js`. Use the existing service clock and one deadline calculation for new tickets and preparation. The store owns deadline assignment. The HTTP app controls which ticket fields are sent and whether the list query activates overdue filtering.
- On enabled startup with `DATA_FILE`, load and validate the entire current state, validate saved deadlines, prepare all missing ones in a candidate state, and commit through the existing whole-file save before accepting requests or starting the worker. Enabled creates save their deadline together with the ticket, audit entry and outbox event before returning success. Reuse the existing ticket filter, ID comparison and cursor functions.
- Use the CLI's current read-only path and its explicit display fields. Keep the raw column contract and weekly report intact. Document the settings in `README.md`, the HTTP behavior in `docs/api.md`, and preparation, retry and rollback in `docs/operations.md`. Correct the existing API docs' description of how the ordinary status and priority filters combine. Keep `npm start`, `npm test`, the Node.js requirement and the dependency-free setup.

## Decisions

These are implementation choices for this build. The build report should record its actual answers to the open points. Acceptance of the clauses applies to any reasonable answer to those points.

| Clauses | Choice and reason | Alternative considered |
| --- | --- | --- |
| C-3–C-5, C-10, C-11 | Use one startup environment override per priority, `DUE_HOURS_URGENT`, `DUE_HOURS_HIGH`, `DUE_HOURS_NORMAL` and `DUE_HOURS_LOW`. Unset or empty uses that priority's default. For C-4's open duration policy, accept positive safe whole hours using the existing integer config convention, with no additional help-desk cap. Validate these settings when the feature is enabled. This fits how operators already set and change configuration. | A single JSON schedule requires more parsing and makes partial overrides less direct. Hot reload adds another point at which the effective schedule can change. |
| C-6, C-19 | Compute elapsed UTC milliseconds using exact integer arithmetic, with `BigInt` for the multiply and add, then convert a result inside the inclusive Node.js Date range to ISO UTC. For C-6's open overflow policy, refuse an enabled create through the existing internal-error path before changing state. If preparation encounters overflow, refuse startup with a file-and-ticket diagnostic. | Calendar addition can change elapsed hours at DST. Clamping changes the promised duration. An invalid Date can leak a null or error after state has already changed. |
| C-7–C-12, C-21 | Keep store reads and snapshots independent of HTTP visibility. Use one ticket response projection for every ticket-returning HTTP route, including items in either listing. Off mode starts with no new deadline assignments and preserves any already saved deadlines on every save. Off-mode tickets with missing deadlines participate in the next preparation under C-19. | Using the flag in disk serialization would erase assignments during ordinary off-mode saves. Computing deadlines on read makes them depend on current settings and prevents a meaningful readiness check. |
| C-14 | For the open two-filter policy, keep the existing union of `status` and `priority` on overdue requests and intersect that result with overdue eligibility. This reuses the service's current filter semantics. | Using intersection between the two legacy filters in the overdue path is also reasonable and follows the prose in the existing API docs. Changing the ordinary listing's union would break C-15. |
| C-12, C-15 | For the open query policy, recognize a single exact `true` as active and a single exact `false` as an ordinary listing. When enabled, reject other supplied forms, including empty, malformed and repeated values, with the usual 400 `invalid` envelope. When off, ignore all occurrences. Keep the overdue option outside the legacy filter map. | Accepting arbitrary forms as ordinary listings can hide a mistyped filter. Taking only the first value makes conflicting repetitions order-dependent. |
| C-19–C-21, C-25, C-26 | For the open preparation policy, use one enabled startup to prepare missing deadlines synchronously before listening. Document that operators stop the sole writer, keep a consistent backup, set the schedule and flag, start with the same file and confirm readiness by a successful startup and the saved records. Allow enabled memory-only operation for development and testing. | A separate preparation command can support a staged rollout but adds a second writer entry point and a window in which the old process can add unprepared tickets. Background or first-read preparation can expose a partly prepared service. |
| C-23, C-24 | For the open audit policy, leave first assignment out of the audit output, both on create and during preparation. A create still records its existing fields. Preparation fills only the ticket field and emits no notifications. | Recording assignment in creation audit or adding preparation entries would require audit visibility decisions and could change existing history output when the feature is off. |
| C-11, C-21, C-27 | For the open corruption policy, enabled startup refuses a present but malformed deadline with the file and ticket record identified. Validate it as a string that round-trips to UTC ISO with `toISOString()`. Preserve the value as stored when off, so the old API can still operate and a saved deadline is not silently replaced. Document restoring the affected deadline from a known-good saved copy before retrying. | Treating corrupt data as missing would silently assign a different deadline. Rejecting an otherwise valid file even while off would change the legacy startup behavior. |
| C-28 | For the open re-upgrade policy, support rollback reads using the unchanged 1.4.0 reader. If 1.4.0 resaves the file and drops deadlines, a later enabled release prepares the missing ones from the ticket data and effective schedule then available. Document that this can change deadlines after a downgrade write. | A sidecar to preserve deadlines across old-writer saves would add a second state file and a second commit boundary. A format version bump would prevent 1.4.0 from starting. |
| C-29–C-32 | For the open CLI display policy, keep the human table and `show` output as they are, independent of the HTTP flag. The updated version-1 reader makes both formats usable. | Adding a visible CLI column or field would require a separate visibility choice. The script-facing raw format must stay at four columns. |

## Nuances

- **C-1–C-5, C-11–C-12, C-33**. `test/helpers.js` and other callers construct service settings directly, and the CLI and unit tests call the list parser and store without HTTP feature options. Default the added options to off when omitted. Check `DUE_TIMES` literally. Trim only the numeric schedule inputs in the same way as the existing integer settings. Keep validating the existing settings, including `PORT`, regardless of the flag. Run enabled preparation inside the existing startup error boundary. `main()` currently catches configuration and file errors around service construction, with `start()` outside that catch.
- **C-3–C-10, C-19**. The HTTP validator supplies a missing priority as `normal`, while direct store callers already pass validated data. Sample the store clock once for creation and base `due`, `created`, `updated` and the creation effects on that instant. Backfill uses the persisted `created` and current stored priority, even if `updated` differs or the audit history shows a different creation priority. Use the existing loader's accepted timestamp formats for legacy creation times and leave those strings as stored. Preserve saved values byte for byte at the field level, including across a changed priority or schedule. Perform overflow checks before converting the result or changing state. Compare timestamps numerically, since valid extended ISO years need not sort in numeric order as strings.
- **C-7–C-12, C-23**. Every successful ticket path includes create, get, patch with changes, patch with no changes, transition, and each item in both ordinary and overdue pages. Project copies at those response boundaries. A projection that deletes from the live record would also delete the value from future saves. Keep the create, patch and transition input allowlists in `src/tickets/validate.js`, so `due` stays invalid in request bodies in either mode. Preserve the no-op patch's `updated` and history, existing conflict and error behavior, and the separate audit, outbox and health representations.
- **C-12–C-18, U-3**. `matchesFilters` uses `some()`, and the existing parser ignores unknown parameters. Adding `overdue` to that map could let a non-overdue ticket through or match nothing at all. Parse it only for enabled HTTP listing and apply it as a separate predicate before pagination. Capture one clock instant per overdue request, use the existing active-state predicate, and compare the stored deadline strictly earlier than that instant. A resolution removes eligibility immediately and reopening uses the same deadline. When disabled, keep the existing query shape and validation of the other fields even with an `overdue` parameter present.
- **C-16–C-18, U-3**. Reuse numeric ID ordering, existing limit validation, cursor decoding and the store's separate ticket-ID check on decoded cursors. Page the matches, including when nonmatches appear on either side of a cursor. An anchor can become ineligible between requests. Resume after its ID without requiring the anchor to appear in the filtered set. Each request evaluates fresh eligibility. The existing cursor carries a position, so an earlier ID that qualifies after that position is passed is visible on a fresh listing.
- **C-19–C-27, U-4**. First load and validate the full legacy document. Stage the preparation in a candidate snapshot and preserve `nextNumber`, every legacy ticket field, audit entries and sequence, outbox events and `nextId`. Distinguish an absent own `due` key from a present bad value such as `null`. Check every saved deadline before making a preparation commit. Only save if something was added, then use that state for the live store. Repeat preparation skips already assigned values, including when the file has a mix of assigned and unassigned rows. A missing file or empty store has no rows to prepare. Keep `savedAt` as save metadata. Use the same-directory temporary file and rename, wrap preparation write failures in the startup file error path, and leave the retained file suitable for retry. A temporary file from an interrupted save is not the readiness signal. Wait for the old process to stop before starting the new one so a shutdown or worker save cannot replace the prepared state.
- **C-20, C-24, C-25**. The existing `create` mutates the live store before calling `save()`. Adding a deadline and keeping that sequence on an enabled persistent create could let a GET expose the ticket after the create's save failed, or a later shutdown save commit the failed create. Reuse one creation mutation path. In the enabled persistent path, stage its ticket, number, audit and notification together on candidate state, synchronously save the candidate snapshot once, then publish the candidate in memory and return the ticket. A failed save leaves the old live state and old file. Keep the existing path for off and memory-only creates. The synchronous mutation and save stay within one store call, so worker and request writes do not interleave.
- **C-21, C-28–C-32, U-5–U-6**. `ticketRecord` is a field whitelist shared by loading and saving, so both paths must carry optional `due`, even with the flag off and even when an outbox delivery or shutdown causes the save. Leaving the optional key absent in a legacy record avoids introducing a spurious null. The unmodified 1.4.0 reader drops unknown fields but accepts version 1, and its writer also drops them on rewrite, including a graceful shutdown save. Prove compatibility by starting the real old code after new writes, and account for old-writer loss separately from rollback reads. The CLI uses that same file path via its own parser, constructs a store with no persistence, and paginates internally. Keep preparation out of the generic loader and store constructor so a CLI read cannot prepare or save a production file or depend on enabled schedule settings.

## Build order

1. Record the local 1.4.0 reference at `ada051d` and inspect the unchanged suite. Add the optional version-1 ticket field, then check that a file can round-trip mixed records with the rest of the document preserved and still be read by the old code.
2. Add the startup settings and the shared deadline calculation. Check the default schedule, a per-priority override, config diagnostics, elapsed-time arithmetic and representable endpoints.
3. Implement store assignment for enabled creates and the pre-listen preparation path. Check a real file before any HTTP visibility, preparation retry after a failed commit, and a failed create save with the previous live and disk states still available. Exercise fixed deadlines after edits, a worker save, shutdown and restart.
4. Wire the HTTP projection and overdue query, leaving request body checks and legacy filter/cursor behavior in place. Exercise all ticket responses, the exact time boundary and the combined filtering and pagination cases.
5. Finish the operator documentation and new `node:test` coverage. Exercise CLI and report outputs against both file generations, run the real 1.4.0 rollback drill, and run `npm test` with the original test files untouched.
