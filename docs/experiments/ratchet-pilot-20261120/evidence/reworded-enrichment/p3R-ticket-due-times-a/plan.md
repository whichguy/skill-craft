## Approach

Keep one ticket record and one version `1` data file. Add an optional `due` string to the ticket projection in `src/persistence.js`, used by both the writer and reader. Legacy records without it still load. `TicketStore` owns assignment at enabled creation and preparation of existing records. The app owns whether the HTTP ticket representation exposes that field. The CLI can read either file through the shared loader and keep using its current formatters.

Read the feature switch and per-priority hours in `src/config.js` and pass them through `createService` to the store and app. On enabled startup, prepare missing deadlines in the configured file before listening or starting the worker. Use the store's injected clock for the creation instant and overdue queries. The existing body validators, ticket lifecycle, audit and outbox paths, ordinary filters and cursor codec carry the existing behavior through rollout.

## Nuances

- **Exact activation and response boundary (U-4, U-5, C-3, C-7, C-8, C-21).** Gating the loader would lose preexisting deadlines on a disabled save. Gating only the create response would leak deadlines through GET, PATCH, transition, or list items. Read and write the optional field regardless of the switch, distinguish field absence from an assigned value, and project every ticket-bearing HTTP response in one place without mutating the ticket or changing page metadata. Skip parsing `overdue` and the hours variables when disabled. Treat `ON` and ` on ` as disabled. Default optional service/app/store inputs so existing direct callers and test helpers can use their old settings objects.
- **Elapsed time and representability (U-1, U-2, U-4, C-4–C-7, C-10, C-17, C-18).** Use a shared calculation over epoch milliseconds, `hours * 3_600_000`, with a Date-range check before serialization. Take the creation time once and use it for `created`, `updated` and the calculation. For old records, parse the instant the existing loader accepted, including offsets, without altering the saved `created` spelling. Use the recorded priority at the moment of first assignment, never a priority inferred from audit or the preparation clock. Never validate a saved deadline against today's configured hours or current priority. When present, validate `due` as a usable canonical UTC timestamp with the existing record-level error convention. Compare instants numerically, including years that need an expanded ISO representation.
- **Assignment and saves (C-9–C-11, C-20, C-25–C-27).** Assign before changing ticket numbering, audit or outbox so a calculation error leaves no partial creation. Keep the ticket, audit and ordinary create notification in the same file save and wait for it before sending `201`. The current `create` mutates live state before saving. For enabled file-backed creation, stage those changes with the existing store logic and publish them after the save succeeds so an I/O failure cannot leave a visible unsaved deadline, consumed ID, or pending notification. Keep `due` outside all three request allowlists. Patches and transitions use the existing mutation path, including no-op edits and final-state conflicts. Deadline passage itself is a read-time condition with no job, audit entry or notification.
- **Filter composition and cursor order (U-3, C-12–C-16).** Do not pass `overdue` as a ticket field to `matchesFilters`, whose `some` would let an ordinary filter admit an ineligible row. Carry a separate opt-in through query parsing into `TicketStore.list`, retaining the existing default query result shape. Use `isActive`, read `clock.now()` once per filtered request and apply strict `due < now` as well as the existing matcher. Missing deadlines do not qualify. Filter before the numeric ID sort and pagination, using the existing cursor's ID as a lower bound even if its ticket has stopped matching. Eligibility may change between requests. A cursor resumes at larger IDs and does not imply a snapshot of earlier rows. Keep all legacy query validation, including decoded cursor ID validation in the store.
- **Complete preparation and commit point (U-4, C-17–C-24, C-27).** Prepare a candidate over the loaded store snapshot and calculate every missing value before touching the active file. A mixed file is normal if the disabled service created tickets after a prior enabled run. Preserve assigned `due`, `updated`, IDs, `nextNumber`, audit contents, outbox events and `outbox.nextId`. Persist once only when assignments are needed, without invoking any ticket edits, and publish the prepared store only after success. Call this preparation from `createService` inside the existing startup error boundary. Keep it out of the generic constructor and loader, which the read-only CLI also uses. An absent file, an empty state and memory-only mode need no preparation write or durability check for existing deadlines.
- **Interruption and readiness (U-4, C-18, C-20, C-22).** Reuse the same-directory temporary write and atomic rename in `createPersistence`. For preparation, flush the complete temporary file before rename and sync the containing directory after rename before allowing startup. Clean up only the current writer's temp file on a handled failure. An interrupted save may leave an orphan temp file, which must never be loaded in place of `DATA_FILE`. Fail startup with a `DataFileError` naming the path and failure, using the existing `cannot start` handling before any listener or worker starts. A failure after rename can leave a complete prepared file in place. On enabled startup with an already complete, nonempty file, sync the existing file and directory without rewriting the document. This covers a prior interruption after rename as well as a complete file last saved by an ordinary write. Keep ordinary write and stop paths able to retain the field and check new-ticket persistence by reading the file before shutdown as well as after restart.
- **One writer and rollback (U-4–U-6, C-21–C-24, C-28, C-29).** Both versions rewrite the whole document from memory. Stop the previous process and allow its shutdown save before preparing, and stop the new process before starting 1.4.0. A concurrent old owner could overwrite the completed preparation or drop new tickets. The old `readTicket` selects its known fields via `ticketRecord`, so optional `due` is ignored while `version: 1`, numbering, audit and outbox data remain readable. Verify against the original release, since the new reader accepting its own output proves no rollback compatibility. The old process can rewrite on clean stop alone, so capture the preactivation and enabled file samples before exercising rollback with copies.
- **CLI is a reader (U-7, C-30–C-32).** `bin/tickets.js` loads the file directly and constructs a store without persistence. Keep preparation in enabled service startup so a CLI invocation never migrates or rewrites; it should also work without the feature environment. `scripts/weekly-report.js` consumes the four tab-separated positions and all pages produced by the CLI, independently of how HTTP hides or shows `due`.

Add the requested `node:test` coverage under `test/`, leaving the existing tests intact. Run all use-case checks below during this same build pass.

## How we will know

Use `test/helpers.js` and `manualClock` for deterministic HTTP tests, with the worker off unless observing its writes. Real process checks use isolated file copies, `PORT=0`, the logged bound port and `GET /health` for readiness. For shutdown checks, signal the actual server by PID, await exit and close clients. New tests run with Node's standard library and no external service.

Exercise preparation interruption without racing a real disk write. In an isolated child, pause at the replacement boundary and tell the parent when the temporary write is complete, then stop the child by PID. Test a reported I/O failure separately. For this build, verify that a preparation failure exits before binding. The contract test should check that due-time responses are unavailable on failure and use the preparation entry point of the build under test. Inspect the active file directly and restart from it. Use controlled I/O injection since privileged test runs can ignore file permissions.
