## Approach

The repository has a dependency-free `package.json` whose `test` script already invokes `node --test`. There are no engine files, tests, or existing callers in the repository. Add `src/chess.js` and CommonJS rule tests in `test/`. The public API is `startFen()`, `legalMoves(fen)`, `applyMove(fen, move)`, `status(fen)` and the exported `IllegalMoveError` class. Everything else stays private to the module.

Parse the six FEN fields into a flat board of 64 squares, the active color, the two king locations, the castling rights, the en-passant target or an empty sentinel, and the two counters. Index a1 as 0 with the file increasing first. Use zero-based ranks and files for geometry, and FEN rank order (8 down to 1) for parsing and serialization. Keep piece color in the FEN letter case. Treat each incoming FEN as authoritative for that call, including the rights and target fields. Serialize empty rank runs and the metadata in standard FEN field order. Keep the starting FEN as a constant.

Generate internal move records with origin and destination indices, promotion where applicable, and explicit information for a two-square push, en-passant capture, or rook relocation. Use one legal-move iterator for all three position-taking APIs. It generates candidates by piece geometry, then checks the moving side's king on the resulting board using a direct attack query. A shared board transition places the pieces for both filtering and application. Only `applyMove` advances the FEN metadata after finding a legal record. `legalMoves` formats and sorts the full list of UCI strings, `applyMove` matches a UCI string against legal records, and `status` combines the current attack result with whether the iterator yields a legal move.

## Decisions

| Choice | Reason | Alternative considered |
| --- | --- | --- |
| Use a flat board with rank and file bounds, conventional direction tables, and ordinary arrays. | There are at most 64 squares to scan, and the geometry and board updates are easy to verify. | Bitboards add bookkeeping and are unnecessary for the two timing targets. |
| Query attacks independently of move generation, using pawn and knight offsets, adjacent kings, and rays that stop at the first occupied square. | The same query handles check, king safety and castling, including attacks from pinned pieces. | Generating opposing legal moves loses pinned attacks and introduces recursive king-safety checks. |
| Copy the board for each candidate and keep metadata out of trial transitions. Compute the tested king square from the record when the king moves. | The work is bounded, and early exit, castling and en passant need no undo bookkeeping. | In-place make and unmake would need to restore each changed square on every path. |
| Use shared legal records and exact UCI matching in `applyMove`. Format moves only as needed and sort only the public list. | Generation and application agree on eligibility and special-move interpretation. `status` can stop at the first legal record. | Building the sorted public list inside every API call adds work and requires interpreting matched UCI again. |
| Store counters as exact decimal integers, using `BigInt` internally, and serialize them as decimal digits. | FEN carries its own starting counter values, and a large supplied value can still be incremented exactly. | JavaScript `Number` can round large integer fields. |
| C-4 open point. For this build, validate the six-field FEN structure, eight ranks of eight squares, valid piece symbols, exactly one king per color, active color, rights and target syntax, and decimal counters (halfmove at least zero, fullmove at least one). Throw `TypeError` for inputs that fail these checks. Skip game-history or global reachability validation. Guard the local prerequisites of every special move before generating it. | This keeps caller mistakes from leaking into board operations and handles playable inputs, including targets with no possible capture. | Accepting abbreviated forms needs defaults, and requiring proof of reachability goes beyond the supplied position. |
| C-40 open point. For this build, use case-sensitive matching against the generated UCI strings. Reject whitespace, uppercase spellings and non-string move arguments with `IllegalMoveError` on playable input. | One matching rule covers normal calls, and generated UCI is already canonical. | Normalization can accept additional spellings outside the caller contract. |
| C-53 open point. Use the start position at depths 1 and 2 and the established Kiwipete position at depths 1 and 2. | Independently known counts check broad generation and the child FEN path. Kiwipete exercises a dense board with castling and captures. | Start-only counts give little exercise to special moves and fail the multiple-position coverage requirement. |
| C-55 and C-56 open points. Use Kiwipete for the middlegame timing and measure the specified start depth-2 workload through the public API on the available machine. Use synchronous elapsed time from `node:perf_hooks`, with module load and fixture setup outside the measured interval. Report the environment and observed times. | A direct timing verifies the complete public operations and keeps machine assumptions visible. | An internal counter can bypass FEN parsing, legal validation and move application. |

The four rows covering open clauses describe working choices for this build. The build report should record the choices it actually used. Verification should accept other reasonable choices consistent with C-4, C-40, C-53, C-55 and C-56.

## Nuances

| Clauses or use cases | Failure to avoid | What to do |
| --- | --- | --- |
| C-3–C-7, C-27, C-31, U-1–U-2 | Board orientation, call order, or a shared move array corrupts otherwise valid positions. | Parse ranks 8 through 1 and serialize them in the same order. Derive pawn direction from color. Keep each call's board, state, and returned array independent. Use the default string sort for ASCII UCI, including the fourth and fifth characters. Alternate calls on original, child and unrelated positions. |
| C-8–C-17, C-20–C-21 | A flat index wraps across a file edge, a ray passes a blocker, or the castling attack check uses ordinary capture eligibility. | Bound each step in rank and file. End a ray at its first occupant. Keep friendly destinations out of candidate moves and exclude captures of the opposing king. For attacks, reverse the attacking pawn's direction to find possible source squares, check both diagonal offsets regardless of target occupancy, and include adjacent kings, pinned pieces and the first occupant of each ray. |
| C-18, C-20–C-21, C-28, C-36, U-2–U-3 | A parser requires a usable target, an old target survives a reply, or a trial en-passant move leaves the captured pawn on the board. | Accept the FEN target after a double push even when no capture exists. For en passant, require the active pawn to be on its capture rank (5 for White, 4 for Black), its empty diagonal target to match the field, and an opposing pawn on the square just behind the target. Remove the victim and vacate the origin before checking king safety. A legal en-passant capture can itself remove a checking pawn. Recompute the field from every move. |
| C-19, C-27, C-29, C-34, C-37, C-40, U-3–U-4 | A generator offers a pawn on the last rank or only a queen, or a promoting capture loses the captured rook information before updating rights. | Expand every legal last-rank advance or capture into four distinct move records and place the selected piece of the mover's color during the transition. Read the victim and mover from the original board. Require exactly one valid suffix per promotion and disallow suffixes on other moves. |
| C-4, C-20–C-26, C-30, U-3 | Testing castling with stale occupancy misses an attack, testing every empty square for attacks forbids a legal queenside castle, or an inconsistent fixture turns the parser's open policy into a requirement. | Require the corresponding right, home king and same-color rook, and clear path, including b1/b8 for queenside. Check the origin on the original board, then transit with the king moved one square and the rook still home. Test the destination on the final board including the rook move. Only the king's three squares require protection. For conformance, use playable FENs when asserting returned arrays. An inconsistent FEN claiming a right with a missing home rook can probe the generator when accepted under the build's FEN policy. |
| C-20, C-26–C-30, C-40, U-3–U-4 | Trial boards diverge from applied boards, or the king-safety test uses the opponent after color switches. | Use the same board update for trial and application, including all changed squares for special moves. Test the mover's king on the trial board, using its destination for any king move. Advance the active color only when committing the result. Reject unmatched input without retaining any trial state. |
| C-32–C-35, C-37, U-2–U-3 | Rights are inferred from occupancy, or a corner-to-corner rook capture clears the mover's right but leaves the victim's right. | Start with the existing rights. Independently clear both for a moving king, the corresponding right for a home-corner rook moving away, and the corresponding opposing right for a home-corner rook being captured. Check piece type and color from the pre-move board. Emit remaining rights in `KQkq` order or `-`. Castling is a noncapturing king move for the halfmove clock. |
| C-27–C-28, C-31, C-36–C-38, U-2 | Move counters restart from defaults, or a pawn promotion is counted as a quiet move by the new piece. | Base all updates on the input state and original mover, using the victim square for en passant. Reset halfmove on every pawn move or capture and increment it otherwise. Increment the fullmove number exactly for Black, before flipping the active color. |
| C-4, C-20, C-39–C-44, U-4–U-5 | Bad input is conflated with illegal play, or status consults the wrong king, draw counters, or inferred game history. | On playable input, reject each canonical UCI move absent from the legal set with the exported class. A safe king with legal moves gives `ongoing`, and an attacked king with legal moves gives `check`. Without legal moves, an attacked king gives `checkmate` and a safe king gives `stalemate`. A bare-kings position with legal moves remains `ongoing`. Keep the parser's out-of-domain policy outside the conformance assertions. |
| C-45–C-56, U-6–U-7 | Counts hide illegal substitutions, or a fast benchmark measures incomplete work. | Pair independent aggregate counts with exact move, FEN, status and error assertions. Time one complete middlegame `legalMoves` call and the complete public start depth-2 traversal separately. Use both strict limits. Keep timing verification separate from the correctness suite so routine `npm test` remains independent of machine load. |

## Build order

1. Implement the CommonJS surface, starting FEN and position representation. Check the exact start string and inspect parse/serialize orientation and six-field round trips, including a supplied target with no adjacent capturing pawn and nondefault counters.
2. Implement coordinate geometry, direct attacks, and ordinary candidate moves, then the shared board transition and resulting king-safety filter. Check the 20 sorted opening moves, blocked rays, edge squares, check evasions and the C-21 pinned attack example.
3. Add pawn promotion, en passant and both castle directions. Route their board effects through the transition used by king-safety filtering. Check all UCI forms, each of the king's three squares in castling, and promotion suffixes. Check that an en-passant trial moves the capturing pawn and removes the victim before evaluating attacks.
4. Add legal-record matching, exported errors, metadata updates and FEN output, then status. Check exact opening FEN progression, reusing an earlier FEN after a failure, simultaneous loss of rights on a rook capture, and the four status strings.
5. Complete the rule suite under `test/` with `node:test` and `node:assert/strict`. Exercise the public API from independent fixtures and successive returned positions. Run `node --test` and `npm test`, then run the timing workloads against the completed module and report observed results and the choices for the open points.

Focused fixtures for interactions in U-2 and U-3

- From `r3k2r/8/8/8/8/8/8/R3K2R w KQkq - 17 42`, applying `a1a8` should return `R3k2r/8/8/8/8/8/8/4K2R b Kk - 0 42`. The same initial layout, with the appropriate side active, allows each castle independently.
- In `1r2k3/8/8/8/8/8/8/R3K3 w Q - 0 1`, the black rook attacks b1 and `e1c1` remains legal.
- In `7k/8/8/r4pPK/8/8/8/8 w - f6 0 2`, `g5f6` exposes the white king to the rook on a5 and is illegal. In `7k/8/8/3pP3/4K3/8/8/8 w - d6 0 2`, `e5d6` is legal and removes the pawn checking the white king.
