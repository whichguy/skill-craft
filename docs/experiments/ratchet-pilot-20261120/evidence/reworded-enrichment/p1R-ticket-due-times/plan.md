## Approach

Add a server-owned UTC `due` timestamp to the ticket stored by `TicketStore`. Reuse the injected clock for assignment and overdue evaluation, the version-1 whole-file snapshot for durable storage, and the existing HTTP routes and cursor contract. Keep feature exposure separate from storage. Even with the feature off, the new release reads and saves assigned deadlines, while HTTP responses look like 1.4.0. The CLI and weekly report keep their current read-only entry points.

- In `src/config.js` and `src/server.js`, parse the feature and response hours, and pass the policy to the store and visibility to the app. Enabled file-backed startup checks the loaded snapshot before the HTTP listener or worker can start.
- Share one deadline calculation between live creation and offline preparation. Keep deadline assignment in the store layer. In `src/persistence.js`, accept an optional `due` on read and retain it on save in the existing ticket record. Use the current loader and whole-file replacement for preparation.
- Expose the stored timestamp through a shared HTTP ticket representation in `src/app.js`. Add opt-in query parsing in `src/tickets/query.js` and apply the overdue predicate in `TicketStore.list` before paging. Reuse `isActive`, numeric ID ordering and the existing cursor decoder and paginator.
- Document the four environment settings and exact flag value in the README, and the prepared-file requirement, API shape and shipped OR behavior in the API docs. Put the preparation, checks and rollback procedure in operations. Follow the repository's decision and release conventions for the persisted field and opt-in API. Add focused `node:test` coverage under `test/` using the current test script and helpers.

## Decisions

These are proposed build choices for the open points. Record the choices actually taken in the build report. Tests of the specification must allow any reasonable answer to those open points.

| Clause | Choice and reason | Alternative considered |
| --- | --- | --- |
| C-3, C-5, C-6 | Use exact `DUE_TIMES=on` and independent `RESPONSE_HOURS_URGENT`, `RESPONSE_HOURS_HIGH`, `RESPONSE_HOURS_NORMAL`, and `RESPONSE_HOURS_LOW` settings. Read hours on enabled startup and on preparation, using 4, 24, 72 and 168 for unset or empty variables. Restart to apply new hours. For the open range, choose whole decimal hours from 1 to 2,400,000,000 inclusive. The upper bound keeps the millisecond delta integral and within the positive Date limit. Check the final timestamp separately. This fits the existing environment parser and yields a diagnostic naming the bad variable. | Hot reload would make the policy depend on when configuration is read. Fractional hours would need a rounding rule. Zero would allow a deadline equal to creation. |
| C-4, C-7, C-16, C-31 | Add elapsed milliseconds to the parsed creation instant and emit `toISOString()` after checking the inclusive Date range. A calculation out of range during live creation is a server failure and flows through the generic 500 envelope before any change. For legacy overflow, refuse the preparation with a diagnostic naming the file, ticket and range problem and leave the snapshot intact. Document that an operator can retry with supported hours that produce a valid date, or resolve the affected record through the help desk if no supported duration works. | Local calendar arithmetic would depend on time zones and DST. Clamping or skipping a ticket would give it the wrong deadline or leave the file incomplete. |
| C-8, C-10, C-11, C-25 | Put the optional field in the existing version-1 ticket record and project it at the HTTP boundary. The old loader selects its known fields and accepts the file, while the new writer preserves deadlines in either mode. For the rollback open point, require preparation again before later re-enablement if 1.4.0 has rewritten the file. Its writer drops the extension, so the original deadlines of those tickets are not recovered by this rollout. | A version bump prevents 1.4.0 startup. A second file or encoding deadlines into audit or outbox would complicate atomicity or alter existing behavior. Stripping the field in the store or persistence when off would discard it. |
| C-12, C-13, C-14, C-15 | In enabled mode accept a single exact `true` to filter and a single exact `false` for ordinary listing. Refuse empty, repeated, case-variant and other values as invalid. With two legacy filters, keep the shipped OR match and require the overdue predicate independently. This reuses observable legacy semantics and keeps active status and past due mandatory. | First-value-wins is ambiguous for repeated flags. Using AND for the legacy pair in this view is a reasonable open choice but creates a difference between views. Adding overdue to the legacy OR would admit ineligible tickets. |
| C-17 | Use the saved priority at first assignment. It is present on every valid ticket. 1.4.0 accepts files without complete priority history, so this also defines a consistent fallback-free rule. | Reconstructing original priority from audit depends on history the loader does not require. |
| C-18, C-19, C-20 | Add a one-shot offline command, proposed invocation `DATA_FILE=... npm run prepare:due-times`, with the same response-hours inputs. It reports assigned and total counts after reopening the file and confirming every saved ticket is assigned. The operator stops and waits for the current writer to exit, runs preparation, then starts enabled on that file without an intervening writer. Tickets created while off start unassigned and get their first deadlines in preparation. Enabled startup refuses incomplete files with an actionable diagnostic. | Assigning invisibly on every disabled create complicates the disabled configuration contract. Online backfill would race the current writer. Automatic enabled-start preparation is another reasonable option, but makes the rollout check less explicit. |
| C-23, C-24 | Keep the existing creation audit fields and preparation produces no audit entry. Assignment is stored metadata. Preserve historical entries, continue ordinary action history and notifications, and treat expiry as a listing condition. | Adding a creation change or a preparation action would require an audit policy and care to preserve disabled responses and sequence numbers. Scheduled expiry events would change the outbox contract. |
| C-26, C-27, C-28 | Leave human CLI output as shipped for the open display point. Keep the raw column layout and report invocation. The shared reader makes prepared data available without a new CLI option or flag-sensitive behavior. | Appending a human-readable field is possible, but changing raw output would affect the report. |

## Nuances

- **C-3, C-5, C-6, C-18.** Parse SLA settings only when an operation uses them. Ordinary disabled startup must ignore even invalid duration values, while offline preparation must use and validate them with the feature flag off. Share the duration parser and defaults across those entry points. Honor `createService`, `TicketStore` and query parser calls that omit new options, including the existing test helper's literal configuration. Keep the old query parser result shape when overdue is absent or disabled.
- **C-4, C-7, C-9, C-10, C-16, C-31.** Use the same clock instant for `created` and the due calculation, after body validation has chosen a priority. Check the millisecond result before formatting, including exact endpoints and expanded-year timestamps. Leave the allowlists for create, patch and transition in force. A calculation failure must occur before assigning the ID or modifying state. For an enabled file-backed create, stage the ticket, audit entry, outbox event and next number together, save through the existing persistence path, and publish the staged state only after the save succeeds. Keep the existing mutation logic shared so durable creation has the same audit and notification effects. A failed save must not leave a ghost create that can be picked up by a later worker or shutdown save. Keep the preexisting disabled mutation path and error handling.
- **C-3, C-8, C-10, C-11.** Existing store methods return detached ticket copies. Apply the same HTTP projection to create, get, patch (including no-op), transition and every list item. Omit the field entirely when off. Keep it on the internal ticket through edits, transitions, worker delivery attempts and shutdown, regardless of the current hours or feature mode. Continue returning the existing audit and outbox shapes.
- **C-12–C-16.** Read the injected clock once per overdue request and compare epoch milliseconds with strict `due < now`. ISO string comparison fails across expanded years. Filter before page slicing, apply the predicate alongside legacy selection and use the cursor as an ID boundary even when its anchor stops matching. Reevaluate eligibility per request. Keep invalid legacy filter, limit and cursor handling, including the store's check of the decoded ticket ID. Resolved and closed tickets retain due dates but cannot pass the overdue predicate, and reopening never resets the clock.
- **C-7, C-17, C-18, C-20–C-24.** Missing `due` means unassigned. An explicit malformed `due`, including null, is a bad saved record. Validate it as a representable canonical ISO timestamp with a field-specific diagnostic. Preserve a valid assignment verbatim without comparing it with current hours. Use the existing reader's broader accepted `created` formats and parse the instant without rewriting that source field. Validate the entire snapshot and compute every missing deadline before saving any changes. The offline store operation can build a replacement ticket array on the loaded snapshot and pass the rest of the loaded state straight to the existing writer. This avoids rebuilding audit entries through the live store's normalizer and preserves the outbox and counters. On reopen, verify expected IDs and assignments, including dates already present. On a complete or empty existing file, verification can succeed without rewriting it. Refuse a missing `DATA_FILE` setting or nonexistent input for preparation so a wrong path cannot look successfully prepared. A new server with no file yet, or without a file configured, can start empty.
- **C-11, C-18–C-25.** The current owner keeps an in-memory snapshot and rewrites it on graceful shutdown as well as on ticket and outbox changes. Even an atomic rename by an offline preparer would lose against a later writer with a stale snapshot. Wait for the service and worker to exit before preparation, and serialize preparation attempts. The command is a write operation distinct from `tickets list` and `tickets show`. Use the existing same-directory temporary file and rename. Before rename, the prior file remains authoritative. After rename, retries see the complete new file. Never recover by copying a partial temporary file over the data file. Report a write error with the file path and return a failure status. At enabled startup, check for missing assignments on the state actually loaded even if preparation was reported successful earlier.
- **C-23–C-28.** Leave notification timing and pending-key deduplication to the outbox. Preparation and crossing a deadline leave pending, sent and dead records untouched. Exercise rollback with the actual baseline checkout. Its reader ignores a new ticket field but its writer drops it on normal save and shutdown. Check the rollback startup and listing first, then inspect the rewritten file and follow the re-upgrade procedure. The CLI and report share the loader and legacy matching, so avoid changing the defaults of the parser, record projection or formatter to implement HTTP visibility.

## Build order

1. Add duration defaults, the shared configuration parser and the pure UTC calculation. Keep opt-in service configuration backward compatible, and check default, custom, malformed and overflow inputs before wiring any HTTP behavior.
2. Extend the version-1 ticket record reader and writer. Add store assignment at create time, the enabled file-backed commit path and the enabled startup completeness check. Check round-trips, failure before mutation, successful persistence before the response and preservation across disabled saves.
3. Add preparation using the same policy and snapshot path. Support mixed state and idempotent retry, verify by reopening, and exercise bad records and failure before replacement. Document the single-writer procedure alongside the command.
4. Wire app projection and the enabled overdue query to store filtering and pagination. Check both visibility modes and their response envelopes as the paths are connected. Keep CLI, raw export and weekly report behavior covered through their existing entry points.
5. Complete the API, operations, configuration and release documentation. Run the new and preexisting suite together. Exercise the documented rollout on a disposable production-shaped file and roll back using the unmodified 1.4.0 source on that same file.
