## Approach

Build the complete app in one pass around the existing `package.json`, `provider/standin.js`, and `records/` fixtures. The package already declares Node 22, `node server.js`, and `node --test`. Add a CommonJS HTTP entry point, static HTML/CSS/browser JavaScript, and server-side modules for persistence, session and workspace rules, provider turns, record proposals, and the task runner. Import `check`, `respond`, and `runStep` directly from the stand-in. Read `people.json` as the chooser roster and `records.json` as the seed for each new data folder. Serve a fixed set of application assets and same-origin JSON endpoints on the configured port. Keep fixtures, provider files, and durable data outside the served asset set.

Keep a versioned JSON snapshot under `DATA_DIR` with the working records, browser sessions, and person workspaces. Each workspace holds bots, last selections, and the two saved libraries. A bot owns applied instruction text, memory and conversations. Each conversation owns its ordered turns and the proposal and task IDs created from those turns. Use stable opaque IDs and explicit ownership for anything addressed by a command. Store reply attempts and states, immutable proposal previews and recorded resolutions, and task definitions, attempts and step results. Use a separate owner-readable credential file in the same directory. Keep the environment token server-side in process memory. Treat one Node process as the writer for a data folder.

The browser loads the chooser or workspace through a single view endpoint such as `GET /api/view`. Its projection contains public names, a selection version, the selected workspace data relevant to the screen, and a setup-ready flag. It contains no credential, raw working record collection or other workspace. Use `POST` commands for continuing and switching, bot and conversation selection and editing, saved item and memory actions, setup, sending and retrying turns, deciding proposals, and cancelling or retrying tasks. Commands identify the object and carry an expected selection version. Derive the person from an opaque `HttpOnly` session cookie and a durable server-side selection. Resolve object ownership at the server. Return accepted IDs, updated state or safe errors. Leave commands that start replies and steps quick by persisting acceptance and starting the work on the server independently of the request lifecycle.

Render the main view with persistent navigation, a transcript and composer, and an adjacent inspector at desktop width. Place proposals and their outcomes in the originating chat. Show the current person's tasks once in `Tasks`, prioritize the open conversation's tasks, and link each task back to its owning discussion. Use focused polling and refresh after commands to reflect provider completion and task progress. Polling updates the browser's view of durable state. The Node service owns execution even with no browser connections. Ship concise local start/setup instructions and exercise the same rule modules in `test/` that the HTTP app uses.

## Nuances

- **Initialization and transaction boundaries (U-1, C-5–C-8, C-18, C-73, C-76).** Seed only when the committed snapshot is absent. Validate a present snapshot and fail with an operator-readable error if it cannot be used. An unreadable file is different from a fresh directory. Commit a draft through a unique same-directory temp file, flush, atomic rename and directory sync where supported. Publish it in memory and acknowledge only after the commit. Use restrictive permissions for the secret file and its temporary copies. A restart trusts the committed file, never a partial temp file. A write failure leaves an uncommitted draft unpublished. If commit status cannot be established, recover from the store before giving an outcome; a background writer must surface storage failure instead of leaving a phantom `Running` status indefinitely. Keep provider waits outside the serialization boundary and re-read the current draft at each commit so a late callback cannot replace newer data.
- **Person selection and async origin (U-2, U-4, C-12–C-14, C-28–C-32, C-40).** Validate chooser IDs against the supplied roster. Resolve each mutation against the session's current selection and expected version at commit time. Repeated selection changes, stale tabs, API calls addressed to another person's objects, and old fetches arriving late are different cases: reject stale or foreign mutations, scope every projection, and have the client discard responses from the previous view generation. Clear previous-person DOM, forms, drafts, cached views and live announcements when switching. Session selection survives reload without putting private workspace data in browser storage. Provider writes and task workers keep the person, bot and conversation IDs captured on acceptance and continue after the selection changes. Bot display names in articles come from the owning bot so a rename preserves the transcript and updates its speaker label. A title and a name are display strings, never ownership keys.
- **Credential leakage at other entry points (U-3, U-10–U-11, C-15–C-22, C-65, C-69).** Use a native single-line control with the accessible role `textbox` and label `Provider token`, visually masked where supported. Clear the value after acceptance and keep it out of the refreshed view. Ensure a blank submission produces the app's alert rather than being intercepted by native validation. Validate through `check`; the UI receives readiness and safe feedback only. Keep private API responses free of caching and error and logging paths free of raw payloads. Guard copies of the exact configured or saved token in provider echo, titles, instructions, remembered facts, and older stored values that newly match a credential. Apply the guard to values before deriving a display title or other excerpt. If a proposal preview needs secret redaction, make it non-actionable and recheck this at decision time. It cannot be approved while a value is concealed. Use ordinary text rendering for other content and present app outcomes beside the provider reply.
- **What gets a position in history (U-5, U-10, C-21, C-32–C-44, C-51).** Persist one accepted turn with a client submission ID before launching its attempt. A transport retry of that submission finds the same turn, while intentionally repeating the text creates a new turn. Clear the composer only after acceptance, retaining it if submission failed. `Run` reads the saved request on the server and goes through the same send path. Keep a durable attempt count. Retry identifies the displayed failed or interrupted attempt so a stale click cannot re-trigger a later failure, and a reply commits only if its outstanding attempt still matches. Build the provider's ordered message array through that user turn, with the user turn last. Pending status, errors, task updates and change receipts stay out of provider history. The clarifying answer depends on the immediately preceding bot text and its original conversation. Rebuilding history without the assistant turn or appending a fake system message between the question and answer breaks this path. Set status promptly and expose a stable retry control for failure or interruption. Start recovery before serving views, and let a once-committed reply be rendered once after a lost response.
- **Reply plus actions (U-5, U-8, U-10–U-12, C-14, C-38–C-40, C-55–C-60, C-68, C-78, C-83–C-84).** Translate provider outputs to state operations by their structured fields. Commit the assistant text, memory delta, proposal creation, task launch or steering outcome, and resolved turn status together. Only schedule a new worker after the task exists durably. If the service stops between provider return and commit, recover the turn as unresolved and apply the retried outcome once. A slow memory reply applies its delta to current facts of the originating bot; later attempts read current instructions and facts. Use fact IDs for edits and deletes so a stale edit cannot hit a neighboring item. Provider `steer` replies are affirmative even when no work can accept the addition. Render the actual applied or unapplied outcome prominently beside that reply. Likewise, a provider may propose a disallowed field; show the validation outcome without usable approval controls.
- **Grounding, proposed numbers, and safe fields (U-9–U-11, C-61–C-70, C-74–C-75).** Pass only committed records listing the acting person as reader, including shared records at current values. Pass own record fields so inherited JavaScript properties cannot be interpreted as synthetic data. Work with provider-supplied typed values, preserve numbers as numbers, distinguish missing fields from present values in validation, and reject invalid or non-finite values before serialization. Validate an entire proposal in both preview and confirmation. Confirm requests identify only which stored proposal the reviewer is deciding. They cannot supply substitute field values, IDs, scope, or readers. The server derives creator readership and computes the next free order ID from committed records at confirmation. Preview values need readable formatting that preserves the exact before/after values, including numbers, whitespace where meaningful, and the difference between an empty value and an absent one.
- **Confirm vs. reject vs. another writer (U-10–U-11, C-65–C-77).** Serialize confirmation with rejection and every other mutation. In that transaction, load the proposal by owner and ID, return its stored terminal resolution if decided, otherwise recheck permissions, schema and displayed before-values against the current working data. For any nonapplicable member, apply none of the proposal. On success persist every effect and the final receipt in the same snapshot, including any created ID. Capture the actual after-values in the receipt instead of reconstructing them from a later record. A later duplicate confirm can report the historical approval even if another valid proposal has since changed that field. A race between unrelated creations allocates distinct IDs. On HTTP failure or reload re-read the proposal state and display unresolved or the durable result. An absent acknowledgement alone cannot tell the person whether the mutation happened.
- **Background step bookkeeping (U-12, U-14, C-78–C-84, C-88–C-92).** Persist the returned task title, provider `controls`, ordered steps and per-step attempts. Before `runStep`, claim the next unfinished index, assign a run/attempt identity, and durably increment that step's attempt. Pass the original provider task shape including appended steps, the zero-based index, and that step's attempt number. On settlement check the claim and commit the result and next status together. Completion uses the latest step list in the transaction, so an appended step cannot vanish when the prior last step succeeds. Dispatch each task sequentially, independently of other tasks or tabs. A new launch and a retry each get a run ID; use it to avoid duplicate workers and protect against duplicate retries, stale cancel requests, and delayed steering meant for an earlier run. A retry keeps the task ID, completed prefix, and attempt history. Resume at the first unfinished step; a started step without a committed result is unfinished. A stopped process has no live worker: reconcile those states before the first view, and report the unrecorded in-flight result as unknown rather than inventing success.
- **Ordering cancellation against dispatch (U-13–U-14, C-80, C-85–C-91).** Check persisted cancellation at step claim time; invoke the provider as part of the same dispatch turn after the claim is committed, with no intervening await that could let cancellation slip between the final check and invocation. If cancellation wins before a claim, record `Cancelled` immediately. If a step was already called, show `Running` with stopping detail and an inert `Cancel task` until it settles. Record successful in-flight work, or the failure of that in-flight step, and finalize cancellation with the skipped suffix. If that was the final successful step, record `Completed` and explain that all work finished. On restart with cancellation committed, preserve the cancelled intent and account for any unrecorded in-flight outcome. Multiple cancel requests read back the same stopping or terminal state.
- **Return summary vs. current conversation (U-12–U-14, C-6, C-13, C-81–C-93).** Use monotonic task activity revisions, advancing them with durable task changes. A new browser has no seen cursor and can show existing task activity after the person chooses their workspace. Acknowledge only the revision actually displayed, without consuming events that have raced ahead. Keep active and unresolved work visible even if its previous update was acknowledged. Aggregate within the current person's work across conversations, and offer return paths to the owning discussion. Never advance the cursor in a background poll or during work in another person. Task progress and recovery state live in the store and stay available after browser closure, reload and polling failures.
- **Freshness of the view (U-2, U-5, U-10, U-12–U-14, C-13, C-36–C-40, C-77, C-80–C-93).** A poll that started before a confirmation or step outcome can arrive after the new state and visually undo it. Keep one current view read, invalidate reads started before a command acknowledgement or selection change, and fetch again on either event. Treat command replies as acknowledgements for the addressed object, without replacing the wider view with stale state. When returning to a page kept in the browser's history, get the current session view before showing restored private content. On loss of connection, make clear that displayed work is last known and refresh by reading durable state when the service returns.
- **Usable screen during background updates (U-3–U-8, U-10–U-15, C-15, C-24–C-38, C-45–C-59, C-65–C-67, C-77, C-79–C-80, C-85, C-90, C-93–C-99).** Use semantic labeled regions and navs, named articles, native buttons and labeled form controls, `aria-current` for selected navigation, polite status announcements, and alerts for failures. Match the requested names exactly, including each contextual action. Use keyed updates or targeted updates so polling does not replace focused controls, clear in-progress editors, jump the transcript, or announce unchanged statuses. Route Enter through the Send form unless a composition is in progress; preserve native Shift+Enter. Keep recent replies in view when the reader is already at the bottom and preserve reading position when scrolled back. Wrap multiline and long unbroken text, constrain side columns, keep a usable reading scrollport and a separately visible composer, and support narrow-window and keyboard focus changes. Make desktop panels visible directly without a menu. Move focus deliberately on intentional screen and form changes and when the clicked action disappears.

No additional requirement is needed to build the stated use cases. The choices above address open behavior within the existing clauses.

## Build order

1. Establish runtime, static shell and store. Resolve `PORT` and `DATA_DIR` with the specified defaults, seed from fixtures and build the atomic transaction path. Verify isolated directories, committed state on restart, and availability of `/` before introducing async work.
2. Implement the server session, fixture-driven chooser, stable bot and conversation selections, scoped view and setup flow. Build the desktop and narrow scaffold with named controls, then verify reload, switch, secret rejection, recovery and absence of cross-person data.
3. Implement persistent turns and the provider adapter end to end. Connect the transcript, composer, pending state and resend/retry UI. Check normal provider text, multiline input, slow and failing attempts, same-conversation context and startup recovery. Add saved libraries and bot memory through the same scoped APIs and current context builder.
4. Add readable-record filtering to the adapter, then ingest provider proposals and build preview/decision/result UI. Verify provider clarification and readable queries before testing reject, confirm, stale and repeated decisions, restart, and allocation of successive IDs.
5. Add the task runner, durable step claims, provider steering effects and cancellation/retry, then connect task cards and return summary. Validate them independently of browser polling by closing the page, switching workspace and restarting the service at controlled points.
6. Finish interaction polish, complete the rule tests and run the full use-case checks with a clean and a populated temporary data folder. Use an available ephemeral port for live checks, stop only the test service, and verify the original provider and fixtures stayed intact. Document the local cold-start path and summarize the chosen open-point defaults in the build report.

## How we will know

Use `npm test` to run `node:test` against the app's state transition and service modules and add integration checks through the running app where the interaction is the behavior under test. Use temporary data roots and an available port per live instance. Wait for observable milestones around slow calls, step claims or completion; use the stand-in's delay controls to widen race windows and bounded polling for terminal state. Compare test fixture files before and after. Check explicit labels and workflows in a real browser with the keyboard at the stated desktop width and a narrow width. A test can exercise chosen implementation defaults directly for regression coverage, but acceptance for an open clause follows its required behavior regardless of the reasonable choice made.
