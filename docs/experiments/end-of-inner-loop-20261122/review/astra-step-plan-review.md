## 1. Route from discovery to commit

**Revise before shipping.** The navigator already returns the item to step-plan. Two failures matter more than the proposed wording change.

- **Document can be refused for following the refusal’s own instruction.** When an `implement` or `document` `done` changes a committed spec clause, `_evaluate` writes a marker opening send-back. `check_terminal` honors that marker only at `implement`. At `document`, if the test rerun passed and the loop already completed, the callback still requires `done`. Document’s repeat rule also says to stop blocked *only* for unobservable behavior. Honor the existing marker at document and allow a requirement finding as a reason to stop its loop. If document’s Improve review finds the change, it can return a send-back, but must first undo its own forbidden spec edit because import checks the tree even on that outcome. There is no truthful green result. Keep S1’s commit and historical case. Specify how an amendment supersedes the old *active* test obligation, or demonstrate a separate corrective-item route where the current item can truthfully finish first. ## 2. Exact duty 10

Give the owed owner note precedence. A send-back may itself have been prompted by that note, so “a rewrite a send-back asks for” can misattribute an owner decision to step-plan. Also, a requirement ID alone does not identify the affected clause or tell the requester what changed. I would use the following text. [Released `DUTIES["step-plan"]`, items 3–10](/private/tmp/review-4puR0J/skills/shiploop/scripts/shiploop_prompts.py:1326) · [Owner-note `StandingTextTests`](/private/tmp/review-4puR0J/test/shiploop-owner-notes.test.py:1074)

> **10. Knowledge.** Record a structural choice missing from `KNOWLEDGE/architecture.md` as the next AD-<n> under `## Decisions` and cite it in the step. Record a newly working command under `## Commands` in `KNOWLEDGE/environment.md`. Keep every R-<n> and AD-<n>. Make no other knowledge edit except the following requirement amendment.
>
> If an owner note this stage owes asks for a requirement change, rewrite that requirement in place as the note directs. Otherwise, when the send-back this plan answers identifies an existing R-<n> whose requirement must change, read the named entry and the evidence in the sending result. Rewrite the affected clause in `KNOWLEDGE/spec.md`. Keep its ID and unaffected clauses, leave no copy of the superseded clause in the entry, and never relax a clause to fit code or tests already written.
>
> For either amendment, state its source and reason in the entry. In `summary`, name the R-<n>, what changes for the requester, and why. Include the R-<n> in `follows` and amend the remaining steps, criteria and checks that depend on it.

This keeps the owner-note path available on a first visit, preserves duties 1 and 11 on item scope and script-owned navigation, and leaves test authorship to test-spec and test. Also qualify the step-plan loop’s blanket prohibition on changing a recorded command or expected result. An amendment may replace the *pending plan’s* command or expectation. Otherwise the loop and duty 10 issue opposing instructions. ## 4. What the requester sees

**Use the accepted amendment as the notice for this feature.** Give its summary a recognizable first line such as `Revised R-4 — equal timestamps are ordered by comment ID because the source emits ties.` The script already places the entire accepted summary in the report’s **Accepted transitions** table. Surface those lines together near the request and in the done packet, with an explicit instruction to relay them. The saved report then carries the notice even if Sol omits it from chat or the checkout disappears. Label these *reported amendments*. ## 7. What else the design missed

**The interrupted tree is evidence, and it can already contain the forbidden edit.** A producer send-back does not roll back files. The owner-note route test explicitly restores the previous spec before sending back. Tell the sender to undo only its attempted requirement rewrite, preserve unrelated work, and cite the observation. Otherwise the next planner can encounter the proposed text already in place and mistake it for the accepted clause. On import, the producer’s `expectations.check_step_plan` also lacks a corresponding call on a replacement Improve `final_result`. Reuse that existing check when review changes the plan. [Owner-note route’s explicit restore](/private/tmp/review-4puR0J/test/shiploop-owner-notes.test.py:1459) · [Step-review test preserving interrupted edits](/private/tmp/review-4puR0J/test/shiploop-step-edges.test.py:235) · [Producer `_inner_gates`](/private/tmp/review-4puR0J/skills/shiploop/scripts/shiploop_navigator.py:4962) · [Import `dispatch`](/private/tmp/review-4puR0J/skills/shiploop/scripts/shiploop_navigator.py:10293)

The smallest useful regression set answers three decisions: can document take the route its refusal advertises, can the **reviewed** amendment survive into HEAD and an executable test, and can a cold W2 plan use the changed behavior while unrelated W3 survives the queue replacement? Update the literal owner-note and document assertions alongside those behavior checks. Preserve the existing note route as a control.
