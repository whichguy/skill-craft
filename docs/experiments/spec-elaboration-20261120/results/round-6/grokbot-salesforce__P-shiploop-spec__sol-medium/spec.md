# Grok Bot for Salesforce

## Scope and basis

The incoming request of 2026-11-20 is “Create a Grok bot in a Salesforce development org.” The direct outcomes are a usable entry in the intended development org (R-1) and a reply from Grok to a prompt submitted there (R-2). This standalone stage has no earlier specification, repository, discovery or research result, or selected baseline. Public documentation inspected here establishes supported building blocks. Actual org state, installed metadata, privileges, and provider behavior for the intended account are unobserved.

The proposed product is an authenticated Lightning Experience browser page for a small development evaluation with synthetic text. It answers one prompt at a time. The xAI API is authoritative for generation. No existing bot is named as a parity reference. The separately marketed Grok Bot describes collaboration, tool use, scheduling, and memory. Those behaviors and parity with that product are outside the proposed scope. The same applies to Agentforce, Salesforce record queries and changes, external messaging, attachments, shared or saved conversations, and production rollout. [xAI Grok Bot product page](https://x.ai/bot#faq)

Implementation and target verification are pending. ### R-2 — Ask Grok and read its reply

**Basis and change.** The 2026-11-20 request, “Create a Grok bot in a Salesforce development org,” supplies the Grok-backed interaction. Text-only independent turns with one current exchange per open view are proposed product defaults. This adds prompt-to-reply behavior. Preserve Salesforce business data and existing automation by making no business record reads or writes. The Responses API documents text inference and completion states. Availability, model fit, effective quotas and latency for the target account remain unknown. Implementation and independent boundary/browser checks are pending. **Affected state.** The authenticated user's current view owns its draft, submitted prompt, answer and status. Before a valid send there is no active attempt. Admission fixes the submitted text for that attempt. The first current terminal result wins. A new accepted send replaces the previous exchange. Page state is volatile and scoped to that view and Salesforce session. Salesforce owns request processing for the lifetime of the invocation. xAI owns generation and provider usage; see R-4 for provider retention. There are no conversation records, provider history links, shared writes or Salesforce business object permissions required by this feature.

**Open gaps.** The provider account owner confirms a permitted xAI project/team, supported text model, credentials, available usage and spend authority before live traffic. The implementation owner resolves prompt units and bounds, output cap and timeout against the selected model and actual org. The runtime limit assessment below gates selection of the transport parameters and the exact maximum-size fixture. The request supplies no specific model, instructions/persona, context memory or answer-quality benchmark. Basic factual prompt/reply is the proposed evaluation scope.

### R-3 — Recover honestly when a reply cannot be shown

**Basis and change.** The 2026-11-20 request, “Create a Grok bot in a Salesforce development org,” implies a consumer can distinguish a reply from a failed attempt. This adds pending, failure and recovery behavior, preserving the user's current prompt on recoverable failure. The xAI error and response documentation identifies provider alternatives. Target timeout and status propagation remain unobserved. Implementation and controlled failure/browser checks are pending. [xAI Debugging Errors](https://docs.x.ai/developers/debugging) · [xAI Responses, “Create new response”](https://docs.x.ai/developers/rest-api-reference/inference/responses)

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| TC-7 Actionable failure | When an attempt fails, the page leaves pending, keeps the submitted text editable, and displays a durable, accessible status with the applicable next action. An authorized new send can succeed after recovery. | Provider authorization/model setup failure points to the org administrator. Rate limiting points to trying again later. Timeout, network failure, provider error or unusable output allows another manual send. No answer appears for the failed attempt. | A timeout or disconnect can leave provider execution and charges unknown. There is no automatic retry, fallback answer, or implication that upstream work was canceled. | Inject 401, 403, 404, 429, 503, transport timeout, incomplete, malformed, and completed-with-blank-text outcomes independently. Check visible state, unchanged editable text, sanitized message and one upstream attempt. Recover with the accepted input and a distinct successful result. |
| TC-8 Isolation from late results | Returning to a fresh bot view after reload or navigation starts an empty exchange. A current response in that new view can display normally. | A completion from a prior view or invalidated attempt never populates the new view or overrides its result. | Leaving the view or ending the session abandons local feedback. Already dispatched provider work may finish. No background delivery or eventual reply is promised. | In the browser, hold the first response, reload, send the second prompt, complete it first and release the earlier response. Check visible text and absence of restored content. A new user session also starts empty. |

**Affected state and recovery.** Errors and pending status are owned by the open view. Failure retains the submitted prompt until edit, new send or view end. A manual resend is a new operation subject to current access and may incur new usage. No durable, partially saved exchange requires compensation. The app owns feedback for invalid input, admitted/pending, complete, denied, rate limited, timed out and unavailable/unusable outcomes. A single failure can correspond to uncertain provider execution, so the UI reports reply availability only.

**Open gap.** The implementation owner must validate representative cancellation-by-navigation and timeout behavior on the chosen browser and target runtime. The request gives no delivery guarantee or cancellation/recovery requirement beyond the live interaction. As a default, there is no automatic retry or resumable job.

This adds a minimal data boundary for a development evaluation and preserves existing identity and data access. Effective target grants, team terms and retention settings are unknown. Implementation, payload inspection, and redaction/authorization checks are pending. **Affected state and recovery.** The Salesforce access admin and provider account owner control the durable runtime credential and upstream key, respectively. After a partial rotation, verify non-secret setup and live status before reopening access. Before and after these changes no app artifacts contain the secret. App text is visible only in the initiating view and the short-lived request/response processing path, plus xAI under the account policy. The provider publishes a default audit retention of 30 days with a separate Zero Data Retention option. The actual team policy governs. The app has no transcript deletion route at xAI. There is no new durable app event store. Use existing provider and Salesforce admin/access evidence for their own changes. App status and redacted case evidence cover distinct bot outcomes without storing content or creating a diagnostic dependency.

The provider owner performs any person-only provisioning or revocation. The request supplies no approval to process records, personal information or secrets, or a policy for treating such content in a prompt. Synthetic-only is an operating restriction disclosed in the UI, with no claim of automatic detection or filtering.
