# User Administration

## Basis and scope

**Request source**. The 2026-11-21 request, “The incoming request,” says “Let admins upload a CSV to bulk-create users.”

**Evidence and limits**. The request establishes the actor, input and create-only outcome. The standalone stage provides no prior spec, selected baseline, repository, discovery or research result, or reference product. The guide packet informs the specification method. Existing roles, account rules, entry points, UI, external dependencies and runtime capabilities are unknown. Each proposed default below is a product assumption for this draft. If a default conflicts with an established rule, use the correction route before freezing the affected contract.

**Actors and boundary**. An admin acts in the account scope where they have current creation authority. The admin-facing Users surface owns interaction feedback. The product's user-management authority owns authorization, validation and durable account creation. “Scope” is the established account-creation boundary, whether deployment-wide or narrower. No new account scope, roles, permissions, login route, or external service is part of this request.

### R-2 — Validate the CSV and identify actionable errors

**Basis and delta**. The 2026-11-21 request, “The incoming request,” says “Let admins upload a CSV to bulk-create users,” specifically “a CSV.” Add a documented input format and pre-write validation. Preserve whatever identity, required attributes and eligibility rules govern ordinary creation. The format below is a draft because no account schema, uniqueness scope, or limits were supplied. Validation checks are pending. [Behavior model](GUIDES/behavioral-requirements.md#behavior-model)

**Draft input contract**. The upload guidance shows the required header `email` and a sample row. Use UTF-8 with an optional initial byte order mark, comma separators, and LF or CRLF line endings. A final newline is optional. Quotes can enclose a field, and doubled quotes encode a literal quote inside such a field. A quoted line break belongs to its field. The header is the first CSV record and must contain exactly the single field `email` after decoding. The file needs at least one data record. Each data record has exactly one field. An interior blank record is an invalid row. A single final record terminator adds no record. In the draft contract, trim leading and trailing spaces and tabs from the email and compare its ASCII letters case-insensitively using the full address. A canonical email must have a nonempty part on each side of exactly one `@`, no whitespace, and pass the established account creation validator. This is an import contract to reconcile against that validator, with no independent internationalized-address policy. Row numbers count logical CSV records, with the header as row 1.

| --- | --- | --- | --- | --- |
| TC-3 | A correctly formed CSV with at least one valid data row reaches account eligibility checks. | Empty bytes, a header-only file, invalid UTF-8, unexpected headers, malformed CSV and a file over an enforced limit reject the batch before creation with an actionable file error. | Check a single quoted record with CRLF and BOM, with and without the final newline. At each approved byte or record ceiling, a valid file at the ceiling remains eligible and one unit over is rejected. Numeric ceilings are open. | UI feedback and actual import boundary. Submit the concrete files in the case walkthrough and compare directory read-back along with each message. Limit probes are pending confirmation of the ceilings. |
| TC-4 | Each valid data row is evaluated for ordinary account eligibility. | Missing or invalid email, wrong field count or a duplicate candidate key rejects the whole batch. Report the applicable record numbers and reasons, including both occurrences of an in-file duplicate. No account is created from any row. | Canonical equivalents collide under the confirmed identity rule. Blank records before the next record receive their own row numbers. File errors take precedence when records cannot be reliably interpreted. | Admin error view and authoritative directory. Submit mixed valid/invalid records and duplicates. Assert record-specific feedback and compare the directory, including the valid candidate from the rejected file. |

**State and recovery**. The admin's selected file starts as transient UI state. Submission binds an input snapshot to the current scope. The import authority reads the snapshot, applies file checks, then row and duplicate checks. If validation fails, show reasons and let the admin correct the source file and reselect it. The directory has the same records before and after rejection. Uploaded fields cannot assign roles, credentials, account scope or privileges.

**Open gaps**. Product and account owners must confirm required columns, normalization, uniqueness, eligibility and the exact condition for an ordinary account before freezing file guidance or eligibility rules. Platform owner must establish byte/row ceilings inside runtime limits before capacity-dependent upload work. Draft checks unaffected by identity and size choices can proceed.

**State invariant**. The write concerns only the candidate identities in the bound scope. Before creation, every candidate must still be eligible at the authority. After confirmed creation, all candidates exist once with ordinary account attributes and unrelated accounts are intact. Validation rejection, authorization denial and a definitive failed write leave no accounts or creation effects attributable to that batch. Directory visibility follows authoritative confirmation. No bulk update, replace, disable, delete, rollback of confirmed accounts, or CSV-driven privilege assignment is in scope.

**Service contract**. The Users surface delegates creation and read-back to the authority that owns ordinary accounts. If the authority is external, the same scope, fresh-grant, canonical uniqueness, all-or-nothing and read-back expectations apply at the actual boundary. Confirm effective runtime identity, exact write semantics, ordinary provisioning effects and a privileged read-back before relying on a route. Cached lists cannot authorize writes or settle a conflict. The change is incremental and create-only. Reuse existing account authority and directory; their facilities and quotas are unknown.

## Interaction and transitions

**F-1, submit and create (R-1 through R-4)**. In an authorized Users view, open Import users and choose a CSV (T-1). Activate **Import** to submit the selection and see Importing (T-2). The import authority validates and either rejects with actionable feedback (T-3) or decides whether the current scope and eligible candidates can be created (T-4). While waiting, the view keeps its focus and status available to assistive technology. It can show a confirmed result only from an authoritative outcome (T-5). Opening Users checks account visibility using the normal directory.

**F-2, reject, correct or recover (R-1 through R-4)**. Unauthorized access ends before any account change (T-1, T-2 or T-4). With a definitive rejection, use the reason to correct the file or restore the prerequisite and submit a new attempt (T-3 or T-4, then T-1 and T-2). If communication ends before confirmation, an active view shows Outcome unconfirmed (T-5). The admin can open Users and, when appropriate, select and resubmit from a fresh view. A late response cannot populate the replacement view (T-6).

## Non-functional requirements

## Submission

**summary**. Specified an admin-only, scoped CSV upload that creates ordinary user accounts and reports authoritative outcomes. Assumptions are an entry within Users, explicit submit, a UTF-8 email-only CSV with trimmed and ASCII case-insensitive comparison, whole-file rejection on invalid or conflicting rows, an atomic create-only write, ordinary account defaults, and transient in-view results with directory-based reconciliation. For an unspecified new web surface, assume light first with a dark option. With no observed baseline, these assumptions stay subject to the account and product gaps under their requirements. Open material risks are identity and provisioning rules, current authority, all-or-nothing feasibility and side effects, runtime capacity and deadlines, UI compatibility, and observability/retention. A confirmed incompatibility with atomic creation or with preserved account behavior leaves dependent work unready pending a product decision. Independent validation, interaction and acceptance design can proceed. Only the rule walkthrough was performed.

**primary**. R-1 (admin upload), R-2 (CSV input), R-3 (bulk creation). At product acceptance, at most one primary requirement may remain unverified, and only with a passed lower-layer test for that requirement.
