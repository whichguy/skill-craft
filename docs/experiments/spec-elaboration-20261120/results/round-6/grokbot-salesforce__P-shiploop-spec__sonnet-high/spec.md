`KNOWLEDGE/architecture.md` (`AD-<n>`); this file holds product requirements (`R-<n>`), product decisions
(`PD-<n>`), open gaps (`GAP-<n>`) and acceptance lines. Nothing here has been built, deployed or run against an
org: every acceptance line is **not run**.

## Product decisions and assumptions

Each is a default taken unattended. Each is changeable by the requester; none is an `AD`.

- **PD-1 What "bot" means.** An interactive chat assistant inside Salesforce Lightning Experience: a user opens a
  page, types text, and receives replies generated by an xAI Grok model. Source: the request's words "Grok bot",
  2026-11-20. The request does not say whether "bot" means a chat page, a Slack/Chatter responder, an Agentforce
  agent, a Messaging/Experience Cloud channel or an automation. Only the chat page is in scope. Others are listed
  under "Left out" and are not blocking.
- **PD-2 "Development org."** A disposable non-production org: a sandbox, a scratch org or a Developer Edition org.
  Production is out of scope and a deployment target of production is refused (R-1.3). Which org is GAP-1.
- **PD-3 Conversation lifetime.** A conversation exists only in the user's open browser page. It ends on New chat,
  page refresh, tab close or navigation away. There is no saved history and no cross-device continuity.
- **PD-4 No org-data grounding and no actions.** The bot answers from the model and the conversation only. It reads
  no Salesforce record, and Grok is given no tool, function or action that touches the org.
- **PD-5 Non-streaming.** A reply appears when complete.
- **PD-6 One shared key.** One xAI API key, held once for the org, serves every permitted user. Per-user keys and
  per-user billing are out of scope.
- **PD-7 Default limits** (configurable, R-9): maximum prompt 4,000 characters (UTF-16 code units; one emoji counts
  2); remembered history 10 completed exchanges; callout timeout 60 s; no automatic retry; maximum output tokens
  not set (provider default). These numbers are product defaults chosen here, not derived from the request and not
  platform limits; each lies inside the platform limits cited in `AD-3`.
- **PD-8 Reply rendering.** Plain text with line breaks and code fences preserved as literal text. Markdown
  rendering (headings, lists, formatted code blocks) is a deferred product choice, not blocking.
- **PD-9 Keyboard.** Enter sends; Shift+Enter inserts a new line; Enter during IME composition does not send.
- **PD-10 Failed turns.** A turn that failed is shown flagged and is excluded from the context sent on later turns.
- **PD-11 Language.** English interface text; translation of interface text is out of scope.
- **PD-12 Surface.** Lightning Experience in a desktop browser. Salesforce mobile app, Lightning Classic, Experience
  Cloud sites and Slack are out of scope.

## Actors, channels and state ownership

Actors: **User** (a Salesforce user holding the access grant); **Org admin** (person: deploys, enters the key,
assigns access); **Bot page** (browser component); **Bot service** (server side of the Salesforce org, with the
platform credential store); **xAI API** (external service, authority for model output and key validity).
Development tools (CLI, any MCP) are not product runtime actors.

Channels: User → Bot page: UI events (local). Bot page → Bot service: request/response, one call per turn, carrying
the new message and windowed prior exchanges. Bot service → xAI API: one synchronous HTTPS request per turn, key
attached by the platform credential store, never by the page. Return path: reply or error category, rendered by
the page. Acknowledgment meaning: "reply received" means xAI returned a usable body to the Bot service; it does not
prove the user saw it.

State owners: transcript, in-flight flag and conversation generation number: Bot page, transient (PD-3). Configuration:
org metadata (R-9), durable, admin-owned. API key: platform credential store, durable, admin-owned, never readable by
users. Access grants: org permission assignments, admin-owned. No other state exists (no records, no cache).

### Flows

- **F-1 Ask** (R-3, R-4, R-8, R-10, R-11): User types and sends → page validates (T-7) → page appends the message as
  sending and starts Pending (T-1) → Bot service checks access (R-6), reads configuration (R-9), re-applies limits,
  builds the request from system prompt + last configured exchanges + new message (R-4, R-10) → xAI API replies →
  Bot service maps to reply or category (R-7) → page appends reply and returns to Idle (T-2) or flags the message
  failed (T-3).
- **F-2 Retry** (R-7): User activates Retry on a failed message → T-4 → as F-1 from the request step with the same
  text.
- **F-3 New chat** (R-4, R-8): User activates New chat → T-6; if a turn is pending its eventual result is discarded.
- **F-4 Admin setup** (R-1, R-2, R-5, R-6): Org admin deploys source → enters the key in the credential store →
  assigns the access grant to the consumer user → consumer opens the entry (R-2) → F-1. Each step is a separate
  action with its own authority; the agent performs none of the person steps.

### Turn state and transition ledger

Entity: conversation view. States: **Idle** (accepts input), **Pending** (one turn in flight). Message states:
**sending**, **answered**, **failed**. Owner: Bot page; transient.

| T | Before and guard | Trigger | Operation | After and observation | Failure / recovery | Cases |
| --- | --- | --- | --- | --- | --- | --- |
| T-1 | Idle; input passes T-7 guard | Send | Append user message (sending); begin service call; capture generation number g | Pending; composer send disabled; pending indicator | none until reply | R-3.1, R-8.1 |
| T-2 | Pending; g equals current generation | Service returns reply | Mark message answered; append Grok message | Idle; composer enabled and focused | n/a | R-3.1, R-4.1 |
| T-3 | Pending; g equals current | Service returns error category | Mark message failed with category text and Retry | Idle; message excluded from later context (PD-10) | no automatic retry; user may Retry or send new | R-7.1–R-7.8 |
| T-4 | Idle; a failed message exists | Retry on that message | As T-1 with the same text; the failed flag is cleared on sending | Pending | may fail again as T-3 | R-7.9 |
| T-5 | Pending | Send (button, Enter, double click) | Ignored; no service call; unchanged state | Pending, one in-flight call only | n/a | R-8.2 |
| T-6 | Idle or Pending | New chat | Clear transcript; increment generation; if pending, mark the in-flight call stale | Idle, empty; a late result for stale g changes nothing and shows nothing | late success or error discarded silently | R-4.3, R-8.3 |
| T-7 | Idle; input empty after trimming, or longer than configured maximum | Send | Reject inline; no service call; keep typed text | Idle; inline message | n/a | R-3.3, R-3.4 |

Forbidden or ignored events audited: send while pending (T-5); empty or over-long input (T-7); stale result after New
chat (T-6); Retry with no failed message (control not shown, no event); navigation away while pending (no server
state, result lost, no orphan, PD-3). Excluded with reasons: restart/resumption (nothing durable); partial persistence
(nothing persisted); cancellation of an in-flight call by the user (not offered: the platform call cannot be aborted
from the page, so New chat discards the result instead; the call still completes and may be billed).

## Requirements

Each requirement lists its basis, what is preserved or changed, source locators, evidence limits, pending work, then
acceptance lines. Every acceptance line says what is observed, on which surface, and how it is confirmed. "n/a" lines
give a reason. All requirements are added by this first version; nothing is preserved from earlier versions
because none exists. Every acceptance line's status is **not run**.

### R-1 The bot is delivered to one identified development org

- Basis: request words "in a Salesforce development org", 2026-11-20; PD-2. Added. Locators: PD-2, `AD-1`, `AD-7`,
  `GUIDES/platforms/salesforce.md` "Service discovery".
- Behavior: the whole bot ships as deployable Salesforce source and is deployed to one named, non-production org.
  Deployment is additive: it creates the bot's components and changes nothing unrelated. Deploy, secret entry and
  access assignment are separate steps (F-4).
- Evidence limits: no org identity, edition, API version or component listing has been observed (GAP-1).
- Pending: org identity and authorization; name-clash listing; deployment; read-back.
- State and data: target identity = the org alias recorded by GAP-1 (not yet known). Resources changed: org metadata
  (new components only). Resources observed: org identity record, metadata listings. Before invariant: no component
  of the bot exists (to be observed) and unrelated metadata is as listed. After invariant: bot components exist,
  unrelated metadata unchanged. Recovery: remove the added components (destructive change or manual delete); the
  deploy is all-or-nothing by default, so a failed deploy changes nothing (unverified for the selected command; see
  R-1.2).
- R-1.1 Positive. Deployment of the source to the identified org ends in terminal status Succeeded, and a metadata
  listing by type (`sf org list metadata`) shows the tab, the app, the component, the Apex classes, the
  configuration type, the permission set, and the credential components, each by API name chosen at step-plan.
  Surface: CLI deploy report and metadata listing. Confirmed by: deploy status (not merely an accepted request ID)
  and the listing.
- R-1.2 Failure. A deploy that fails (for example a missing dependency introduced in a test copy) ends in a terminal
  failed status and the listing afterwards shows none of the new components that were not present before.
  Surface: CLI. Confirmed by: failed terminal status and before/after listing. Limit: whether a given deploy command
  is atomic must be confirmed on the first failure; until then this line is open.
- R-1.3 Boundary. The target is not production: the recorded identity shows a sandbox, a scratch org or a Developer
  Edition org, read by query `SELECT IsSandbox, OrganizationType FROM Organization` (field availability confirmed
  by `sf sobject describe` first). A production org identity makes the deploy step refuse. Surface: CLI query.
  Confirmed by: recorded query result in the release evidence. Limit: how a scratch org reports `IsSandbox` is
  unverified (PROBE).
- R-1.4 Preservation. Before deploy, listings of every component type the bot adds show no existing component with a
  chosen name; after deploy, a listing of one unrelated type (for example all pre-existing tabs) equals the earlier
  listing. Surface: CLI listings. Confirmed by: diff of listings.

### R-2 A permitted user opens the bot from a Lightning entry

- Basis: request "Create a Grok bot", PD-1; consumer-entry rules in `GUIDES/platforms/salesforce.md`. Added.
  Locators: `AD-7`, PD-12.
- Behavior: the bot appears as a tab in a custom app, reachable from the App Launcher and by URL path
  `/lightning/n/<TabApiName>`. A user without the access grant (R-6) sees neither the app nor a usable page.
- Evidence limits: the consumer user, their profile and permission-set assignments are unobserved (GAP-1).
- Pending: consumer user identification; entry names; browser check.
- R-2.1 Positive. Signed in as the consumer user holding the grant, opening the App Launcher lists the bot app;
  selecting it shows the tab with the chat page (empty state, R-13), and the URL after redirects is
  `/lightning/n/<TabApiName>`. Surface: Lightning Experience in a browser, as that user. Confirmed by: browser
  observation of the visible tab, the URL, and the user's identity; a logged-in org home or a successful CLI
  command is not acceptance.
- R-2.2 Failure. Signed in as a user lacking the grant, the App Launcher does not list the app, and the same URL
  shows the platform's "Page does not exist" result; no bot service call occurs. Surface: browser. Confirmed by:
  observation as that user; the read-only `PermissionSetTabSetting` query shows no row for that user's permission
  sets. Limit: a second, ungranted test user must exist (GAP-1).
- R-2.3 Boundary. A user who holds the grant but whose credential is unconfigured reaches the page and the first
  send ends in the CONFIG-class error of R-7.7, not a blank or broken page. Surface: browser. Confirmed by:
  observation with the key not yet entered.

### R-3 A user asks a question and receives a Grok reply

- Basis: request "a Grok bot", 2026-11-20; PD-1, PD-5. Added. Locators: F-1, T-1, T-2, T-7, `AD-1`, `AD-3`, `AD-4`.
- Behavior: the user sends text; the message appears in the transcript as the user's; after the model replies, the
  reply appears attributed to Grok. Input is trimmed; empty and over-long input is rejected before any call.
- Evidence limits: no xAI key, no live probe of the endpoint shape or model IDs (GAP-2, `AD-4`).
- Pending: Apex logic with mocked xAI; component behavior; one live turn.
- R-3.1 Positive. With the key configured and the default configuration, the user sends exactly
  `What is the capital of France?`; the user message appears at once, then a Grok reply whose text contains `Paris`
  (case-insensitive) is appended, attributed to Grok, and the composer is enabled again.
  Surface: Lightning browser, live. Confirmed by: browser observation. Model output is nondeterministic, so the
  oracle is containment of `Paris`, not equality. Companion lower-layer check: an Apex test whose mock returns
  `{"choices":[{"message":{"role":"assistant","content":"Paris."}}]}` yields reply `Paris.`; the mock shape is
  provisional until the `AD-4` probe.
- R-3.2 Failure. Service and provider failures are specified in R-7; none of them leaves a blank reply bubble.
  Otherwise n/a here: covered by R-7.
- R-3.3 Boundary, empty. Sending the empty string or `   ` (three spaces) shows the inline message
  `Enter a message to send.`, calls the service zero times, and keeps the typed text. Surface: Jest on the component
  (service mock call count 0) and browser. Confirmed by: Jest assertion and browser observation.
- R-3.4 Boundary, length. A message of exactly 4,000 characters (`a` repeated 4,000 times) is sent; a message of
  4,001 characters is rejected with the inline message `Message is too long (maximum 4,000 characters).` and zero
  calls; the bound read is the configured maximum (R-9), and the service independently rejects an over-limit
  message with the category BAD_INPUT even if the page is bypassed. A message with one emoji counts 2. Surface: Jest
  for the page; Apex test for the service. Confirmed by: both assertions. The inline texts are the defaults;
  wording changes require this line to change.

### R-4 The conversation remembers earlier turns

- Basis: "bot" in the request read as conversational, PD-1, PD-3, PD-7, PD-10. Added (derived, not stated).
  Locators: F-1, F-3, T-2, T-6, `AD-6`.
- Behavior: each request carries the system prompt, the most recent configured number of completed exchanges
  (default 10) in order, then the new message. New chat clears the conversation.
- State and data: owner Bot page; transient (PD-3); readable only by the user in that page; simultaneous changes:
  one in-flight turn per conversation (R-8), two pages are two independent conversations; ends on New chat, refresh,
  close, navigation; no runtime quota beyond request size (NFR-2).
- R-4.1 Positive. Turn 1 `My name is Ada.` is answered; turn 2 `What is my name?` produces a request whose messages
  are, in order: system prompt, user `My name is Ada.`, assistant (turn 1's reply), user `What is my name?`;
  live, the reply contains `Ada`. Surface: Apex test captures the outgoing request body; live browser for the
  reply. Confirmed by: assertion on captured body; browser observation.
- R-4.2 Boundary. After 11 completed exchanges, the request for message `q12` contains exchanges 2 to 11 and `q12`:
  20 messages plus the new one = 21 messages, 22 entries with the system prompt; exchange 1 is absent. With 10
  exchanges or fewer, nothing is dropped. (Recomputed by hand: 10 kept x 2 = 20, +1 = 21, +1 system = 22. Not
  executed.) Surface: Jest on the window function and Apex test on the request body (service re-applies the limit).
  Confirmed by: both assertions.
- R-4.3 Reset. After New chat, the next request contains only the system prompt and the new message; the transcript
  area shows the empty state. Surface: Jest, browser. Confirmed by: captured request and DOM.
- R-4.4 Failure. A failed turn (PD-10) is absent from the next request: turn 1 fails with 500, turn 2 `hello` is
  sent; the request for turn 2 contains the system prompt and `hello` only (the failed text is not included).
  Surface: Jest and Apex test. Confirmed by: captured body.

### R-5 The xAI API key is held only in the platform credential store

- Basis: security necessity of calling a paid third-party API from a shared org; no request wording. Added.
  Locators: PD-6, `AD-2`, `GUIDES/service-discovery.md` "Runtime state placement" (credentials custody).
- Behavior: the key is entered by a person in the org's credential store and attached to outgoing calls by the
  platform. It is never in source, in deployed or retrieved metadata, in configuration records, in any browser
  payload, in any log or in any error text.
- State and data: personal/secret data. Shown: nowhere (write-only). Stored: platform credential store only. Logged:
  never. Kept: until rotated or the credential is deleted. Removed: delete the credential entry or rotate.
  Authority: org admin only; the agent never reads, stores or reports the key value.
- Evidence limits: whether source can carry the secret is unprobed (`AD-2` PROBE).
- R-5.1 Positive. After the admin enters the key once, the first live turn (R-3.1) succeeds without the key
  appearing in the page's network requests or responses. Surface: browser developer-tools network view (headers and
  bodies of the Bot page's service calls), live. Confirmed by: inspection of those calls. Person step: key entry.
- R-5.2 Negative. A search of the full repository and of a fresh metadata retrieve for the key value (given by the
  admin to the checker out of band, never written to a file) and, as a heuristic, for the string `xai-` finds
  nothing. Surface: repository and retrieve. Confirmed by: search with zero hits; a key-shaped string in
  `tests/` fixtures is itself a failure. Limit: the `xai-` prefix is an unverified assumption about key format.
- R-5.3 Boundary, rotation and revocation. Replacing the key in the store takes effect on the next call with no
  redeploy; a revoked or wrong key yields the AUTH category of R-7.1 and the error text shows no part of the key.
  Surface: live. Confirmed by: one turn before and one after rotation with the admin; a deliberately wrong key in a
  test org (not the real key) for the AUTH case.

### R-6 Only users with the access grant can use the bot

- Basis: org security hygiene for a shared paid key; PD-6. Added. Locators: `AD-7`, `AD-8`,
  `GUIDES/platforms/salesforce.md` (separate sharing, object permissions, field permissions).
- Behavior: access is granted by one named permission set covering the entry (R-2), the server operation and the
  use of the credential. Sharing, object CRUD and field-level security are separate concerns and are each recorded:
  - Sharing: n/a: the bot reads no record (PD-4).
  - Object CRUD: n/a: no object is read or written (R-11).
  - Field-level security: n/a: no field is read.
  - Entry, server operation, credential use: required, as below.
- State and data: access assignment is changed only by the org admin (person); the product changes no assignment.
  Granting is a separate step with its own authority (F-4). Unknown: which user is the consumer (GAP-1).
- R-6.1 Positive. A user assigned the permission set can open the entry and complete R-3.1. Surface: browser as
  that user. Confirmed by: observation plus read-only queries of the user's assignments and tab/class/credential
  access (`PermissionSetAssignment`, `PermissionSetTabSetting`, `SetupEntityAccess` for the Apex class and app).
- R-6.2 Failure. For a user without the permission set, the server operation is not callable: an attempt as that
  user is denied by the platform (no callout is made), and the credential is not usable. Surface: Apex test using
  `System.runAs` with a user lacking the permission set (the service-level denial) and, where a second user exists,
  browser. Confirmed by: test assertion of denial and zero mock callouts. Limit: whether the platform check of
  credential access is exercised by `runAs` inside a test is unverified; the browser or anonymous-Apex check as the
  second user is the fallback and keeps this line open until done.
- R-6.3 Boundary, revocation mid-session. After the permission set is removed from a user with an open page, the
  next send ends in the ACCESS category of R-7.8; the transcript stays visible; no further reply is produced.
  Surface: browser with admin action between sends. Confirmed by: observation. Limit: platform propagation time of
  the revocation is unknown.

### R-7 Failures are reported in distinct, safe, non-destructive ways

- Basis: PD-7, PD-10; error behavior required for a call to a third party. Added. Locators: F-2, T-3, T-4,
  `AD-3`, `AD-4`.
- Behavior: every failure of a turn ends as a failed message in the transcript with a category-specific text and a
  Retry control, never a blank bubble, a raw provider body, a stack trace, a credential, or a hung pending state.
  The user's typed text is kept. There is no automatic retry. On TIMEOUT the outcome at the provider is unknown (the
  request may have been processed and billed), and the text says so.
- Categories, triggering conditions and default texts (default texts are the oracle; a change updates these lines):

| Category | Trigger (mock oracle in Apex tests) | Default text |
| --- | --- | --- |
| AUTH | HTTP 401 or 403 | `Grok rejected the credentials. Ask your administrator to check the API key.` |
| RATE_LIMIT | HTTP 429 | `Grok is rate limited right now. Try again in a moment.` |
| UNAVAILABLE | HTTP 500, 502, 503 | `Grok is unavailable right now. Try again later.` |
| TIMEOUT | `CalloutException` with message containing `Read timed out` | `Grok did not answer in time. It may still have processed your message. Retry?` |
| INVALID_RESPONSE | HTTP 200 with `{"choices":[]}`, with an empty content string, or with a body that is not JSON | `Grok returned a reply that could not be read.` |
| BAD_REQUEST | HTTP 400, 404, 422 (for example an unknown model ID) | `The request was rejected. Ask your administrator to check the model setting.` |
| CONFIG | required configuration missing or invalid (R-9), or the credential not set up | `The bot is not set up yet. Ask your administrator.` |
| ACCESS | the platform denies the operation or the credential (R-6) | `You no longer have access to this bot.` |

- Evidence limits: the real provider's status codes and bodies for each condition are unobserved (`AD-4` PROBE);
  the exact exception message for a timeout is a platform detail to confirm; `CalloutException` message text may
  vary. A status not in the table (for example 409 or 5xx other than 500, 502, 503): mapped to UNAVAILABLE for 5xx
  and BAD_REQUEST for other 4xx (documented default, untested until probed).
- R-7.1 AUTH: given a mock returning 401 with body `{"error":"Incorrect API key"}`, the page shows the AUTH text,
  the provider body is not shown, and no part of any key appears. Surface: Apex test (category value) and Jest (text
  and Retry). Confirmed by: assertions.
- R-7.2 RATE_LIMIT: mock 429 gives the RATE_LIMIT category and text. Surface and confirmation as R-7.1.
- R-7.3 UNAVAILABLE: mock 500 gives UNAVAILABLE. Surface and confirmation as R-7.1.
- R-7.4 TIMEOUT: a mock that throws `CalloutException('Read timed out')` gives TIMEOUT and its text containing
  `may still have processed`. Surface and confirmation as R-7.1.
- R-7.5 INVALID_RESPONSE: mocks `{"choices":[]}`, a 200 with `content` empty, and a 200 with the non-JSON body
  `<html>` each give INVALID_RESPONSE. Surface and confirmation as R-7.1.
- R-7.6 BAD_REQUEST: mock 404 gives BAD_REQUEST. Surface and confirmation as R-7.1.
- R-7.7 CONFIG: with the model configuration blank, the service returns CONFIG and the mock records zero callouts.
  Surface: Apex test. Confirmed by: zero callouts and the category.
- R-7.8 ACCESS: see R-6.3; in Jest the service mock rejecting with an access exception shows the ACCESS text.
- R-7.9 Retry: on a failed message, activating Retry sends the same text once (call count increases by exactly 1),
  the failed flag is cleared on sending, and a second failure shows the failed state again; sending a different new
  message instead leaves the failed message visible and unsent in context (R-4.4). Surface: Jest. Confirmed by:
  assertion.
- R-7.10 Safety. No error text contains: the Authorization value, a stack trace, an Apex class name, or the raw
  provider body. Surface: Apex test asserts the returned message against these. Confirmed by: assertion.

### R-8 A turn in flight is shown truthfully and cannot be duplicated

- Basis: PD-3, `GUIDES/behavioral-requirements.md` UI async-feedback guidance. Added. Locators: T-1, T-5, T-6,
  `AD-6`.
- Behavior: from send until the reply or failure, the page shows a pending state and does not allow a second
  send; New chat during pending is allowed and discards the pending result. Two open pages are independent.
- R-8.1 Positive. Immediately after send, before the service returns, the page shows the user message, a pending
  indicator exposed to assistive technology as a status (live region text `Grok is thinking`), and the send control
  disabled. Surface: Jest with a never-resolving service promise; browser. Confirmed by: DOM assertions.
- R-8.2 Boundary, duplicates. Pressing Enter twice quickly, or double-clicking the send control, on one message
  results in exactly one service call (mock call count 1) and one user message in the transcript. Surface: Jest.
  Confirmed by: assertion.
- R-8.3 Stale result. Send `q1`; before the reply, activate New chat; then the mock resolves with reply `late`.
  The transcript stays empty, the empty state is shown, and no error is shown; the same with a late failure.
  Surface: Jest. Confirmed by: assertion. Limit: the discarded call may still be billed (stated in T-6).
- R-8.4 Failure. A pending state never persists past the service's return: with the mock rejecting after the
  configured timeout, the page leaves Pending (T-3). Surface: Jest. Confirmed by: assertion.
- R-8.5 Independence. Two browser tabs on the bot hold separate transcripts; a message in one does not appear in the
  other. Surface: browser, two tabs. Confirmed by: observation.

### R-9 An administrator can change the bot's behavior without a code change

- Basis: PD-7 and the need to follow xAI model naming (`AD-4`). Added. Locators: `AD-5`.
- Behavior: model ID, system prompt, maximum prompt characters, remembered exchanges, callout timeout and optional
  maximum output tokens are administrator-editable configuration that deploys with the code; the bot follows the
  stored values on the next turn.
- State and data: owner org metadata; read by the bot service; changed by an admin; before: shipped defaults
  (PD-7); after: the edited values; recovery: restore the shipped defaults by redeploying the shipped record.
- R-9.1 Positive. Changing the model value from the shipped model to another valid model ID changes the `model`
  member of the next outgoing request body and nothing else. Surface: Apex test (config set via test setup) and one
  live turn after the change. Confirmed by: captured request body; live reply received.
- R-9.2 Failure. A blank model or a blank system-prompt-field is allowed only where stated: blank model gives CONFIG
  with zero callouts (R-7.7); a blank system prompt is allowed and means no system entry is sent. Surface: Apex
  test. Confirmed by: captured body has no system entry.
- R-9.3 Boundary, timeout. A timeout of 120,000 ms is accepted; 120,001 ms or 0 ms gives CONFIG with zero callouts,
  because 120 s is the platform's cumulative callout limit and a request below 1 ms is invalid. A non-integer or
  negative history limit or prompt limit gives CONFIG. Surface: Apex test. Confirmed by: category and callout count.
- R-9.4 Live model validity. The shipped default model ID appears in the key's `GET /v1/models` list. Surface: live
  call through the credential. Confirmed by: recorded list excerpt. Blocked by GAP-2; the shipped default model ID
  is a placeholder to be set from that list at implementation, not asserted here.

### R-10 Only the conversation and configured settings leave the org

- Basis: privacy for a call to a third party; PD-4. Added. Locators: `AD-4`, `AD-6`.
- Behavior: each request to xAI contains the model ID, the system prompt (if any), the windowed conversation
  messages, and the configured optional output limit. It contains no Salesforce username, email, user Id, org Id,
  record data or client metadata, and no identity field of the API. The page shows a short line that messages are
  sent to xAI.
- Evidence limits: xAI's own retention and training terms apply after receipt and are not controlled or observed
  here (GAP-5).
- R-10.1 Positive. The captured outgoing request body of an Apex test has exactly these top-level members: the
  model, the messages, and the optional output limit when configured; no other member (so no `user`). Surface: Apex
  test. Confirmed by: assertion on the key set. A stand-in that only checks the message text does not satisfy this.
- R-10.2 Negative. With a sentinel in the user's profile name and a prompt `hello`, the request body does not
  contain the sentinel. Surface: Apex test. Confirmed by: string-not-contained assertion.
- R-10.3 Disclosure. The empty state shows the text `Messages are sent to xAI to generate replies.` (default
  wording). Surface: Jest and browser. Confirmed by: DOM text.

### R-11 No conversation content is stored by the org

- Basis: PD-3 and data-minimization; the request needs no persistence. Added. Locators: `AD-6`, `GUIDES/service-discovery.md`
  "Observability coverage".
- Behavior: message text, replies and keys are not written to any record, file, platform event, cache or debug log.
  Debug entries, if any, carry only: category, HTTP status, elapsed milliseconds and the count of messages sent.
- State and data: the conversation is shown only in the user's page; stored nowhere; logged never; kept until
  refresh, New chat, close or navigation; removed with it. No deletion path is needed because nothing is stored.
- R-11.1 Negative, storage. A full successful turn and a failed turn each perform zero DML statements
  (`Limits.getDmlStatements()` equals 0) in the Apex test, and a record-count comparison of all custom objects
  before and after a live turn shows no change. Surface: Apex test and CLI query. Confirmed by: both.
- R-11.2 Negative, logs. With debug log level FINEST for the test user, a live turn whose prompt is
  `SENTINEL-7f3a hello` leaves no occurrence of `SENTINEL-7f3a` (nor of the reply text) in the retrieved Apex log
  (`sf apex get log` or `sf apex tail log`); the log lines for the turn include the category or status and the
  elapsed time. Surface: live org log. Confirmed by: log retrieval and text search. Limit: platform-generated
  callout log lines (for example HTTP callout request/response detail) may be emitted by the platform at FINEST;
  if the log shows the prompt, the line stays open and the debug level for end users must be restricted (a person
  decision), not silently accepted. PROBE.
- R-11.3 Persistence boundary. After a page refresh the transcript is empty and the empty state shows. Surface:
  browser. Confirmed by: observation.

### R-12 Model output is displayed as text and cannot run in the page

- Basis: model output is untrusted content; PD-8. Added. Locators: `AD-9` (rendering rule).
- Behavior: a reply is shown as literal text; markup in it is not interpreted; line breaks and code fences keep
  their characters.
- R-12.1 Positive/negative. With the service mock returning the reply
  `<script>alert(1)</script><img src=x onerror=alert(1)> **bold**`, the transcript text content equals that string,
  no `script` or `img` element exists inside the transcript, and no alert occurs. Surface: Jest on DOM. Confirmed by:
  assertion on `textContent` and on element absence.
- R-12.2 Boundary, whitespace. A reply of three lines with a fenced block
  `line1\n```\ncode\n```\nline3` shows 5 lines with the fence characters visible. Surface: Jest. Confirmed by:
  assertion on rendered text and `pre-wrap`.
- R-12.3 Live. Sending `Reply with exactly: <b>hi</b>` shows `<b>hi</b>` literally. Surface: browser, live.
  Confirmed by: observation. Limit: model output is nondeterministic; failure to produce exactly that string is
  inconclusive, not a pass.

## Non-functional requirements

Operating conditions: a development org, a small number of interactive users, one shared key, Lightning Experience in a
desktop browser, human-typed prompts. No workload figure was given and none is invented.

- **NFR-1 Latency.** Basis: platform limits. No numeric end-to-end latency target: model latency is the provider's
  and no bound was requested (unresolved bound, non-blocking; a target would need a requester decision and a
  measured baseline from the live probe). Hard bounds: callout timeout between 1 ms and 120,000 ms; shipped default
  60,000 ms (PD-7). Observable acceptance: the pending state (R-8.1) is shown before the service returns, and a
  turn that exceeds the configured timeout ends in TIMEOUT (R-7.4), never hangs. Verification: Jest and Apex test.
- **NFR-2 Capacity and platform limits.** One callout per turn (limit 100 per transaction); cumulative callout time
  within the 120 s cap (R-9.3). Request size: at most 21 messages x 4,000 characters plus replies of unknown size;
  well under any documented request size limit but that limit was not checked (unresolved, to confirm at plan). A
  provider reply larger than the Apex heap cannot be caught by the product; optionally bounded by maximum output
  tokens (R-9) and left unresolved as GAP-7 (no figure invented). Concurrency: the platform's limits on concurrent
  long-running requests are documented to exclude callouts since Winter '20 (search summary); re-verify at plan.
- **NFR-3 Security.** Key custody (R-5), access (R-6), safe rendering (R-12), no data egress beyond R-10, no org
  data or actions reachable by the model (PD-4), so prompt injection in a reply cannot act on the org. Verification:
  the lines cited. Apex server-side limit re-application means a tampered client cannot exceed configured limits
  (R-3.4).
- **NFR-4 Privacy and retention.** R-10, R-11. xAI-side retention: unresolved (GAP-5). The dev-org default assumes
  non-sensitive test content.
- **NFR-5 Reliability.** The product depends on one external service. Required behavior on its failure is R-7; no
  availability target is claimed beyond that. No data durability requirement exists (PD-3).
- **NFR-6 Interface quality (a deliverable with a UI).** The chat page is a designed interface, not scaffolding.
  Concrete direction and the named visual reference are in `AD-9`: the light Gemini look and Material 3 Expressive
  starting point, adapted inside Lightning Experience; platform conventions (SLDS) take precedence; light first,
  dark option through the same tokens. Observable criteria, each verified in the browser as the consumer user
  unless stated:
  - NFR-6.1 Consistent visual system: spacing, type sizes, radii and colors come from one token block (the platform's
    design tokens, see `AD-9`); a grep of the component stylesheet finds no color literal outside that block. Surface: file check.
  - NFR-6.2 Light and dark: with the dark token set applied, text and controls keep contrast and no element
    disappears (screenshots at both). Whether Lightning offers a user dark theme is unknown (GAP-6).
  - NFR-6.3 Designed states: empty (introduction, R-10.3 disclosure, optional starter prompts left to plan),
    loading (R-8.1 indicator), error (R-7 failed message with Retry, kept visible until acted on, not a transient
    toast), and answered, all distinct. Surface: browser.
  - NFR-6.4 Responsive: no horizontal scrollbar on the page at 320 px and at 1440 px CSS width; the composer and
    send control stay reachable at both; the transcript scrolls and keeps the newest message in view on send and on
    reply unless the user has scrolled up, in which case reading position is preserved. Surface: browser at both
    widths.
  - NFR-6.5 Keyboard and focus: every control reachable by Tab in reading order; visible focus ring on each;
    Enter sends, Shift+Enter newline (PD-9); after a reply focus returns to the composer; Escape does nothing
    destructive. Surface: browser.
  - NFR-6.6 Contrast: text meets WCAG 2.x AA (4.5:1; 3:1 for large text and for control boundaries) in both token
    sets. Surface: contrast measurement of the rendered colors.
  - NFR-6.7 Motion: motion only for pending state and for appearing messages; under `prefers-reduced-motion:
    reduce` the pending indicator is static and message appearance is not animated. Surface: browser with the
    preference set.
  - NFR-6.8 One icon set: all icons are from the platform's utility icon set; no mixed sets or emoji as icons.
  - NFR-6.9 Assistive technology: the transcript is a labelled region; a new reply is announced politely once;
    the pending indicator is a status; errors are announced. Surface: browser plus accessibility tree inspection.
- **NFR-7 Compatibility.** Lightning Experience, a current desktop browser supported by Salesforce; API version
  selected at plan from org evidence (unresolved, `AD-8`); xAI endpoint per `AD-4`.
- **NFR-8 Operability.** Observability reused: Apex debug logs with category, status, elapsed time (R-11); the
  provider's own usage console is the spend record (not owned here). **Justified exclusion:** no persistent audit
  of who asked what, because PD-3/R-11 forbid storing content and a development org of a single admin and a

- **NFR-9 Maintainability and testability.** All xAI request building and parsing in one class (`AD-4`) so the

- **NFR-10 Cost.** Paid per-token usage on one shared key with no cap by the product. No budget was given

## Service boundaries

- **xAI API (external).** Current authority: xAI is the authority for model output and key validity; the org is
  authority for configuration and access. Freshness versus revocation: no response is cached; each turn reads
  live; a revoked key fails the next call (R-5.3). Incremental state: none (stateless requests; the client sends the
  window). Asynchronous completion: none; one synchronous request per turn bounded by the timeout; on timeout the
  provider-side outcome is unknown and the user is told (R-7.4); there is no provider idempotency key evidenced,
  so a Retry may duplicate work and cost (stated in TIMEOUT text). Recovery owner: the user (Retry). Owned event
  coverage: the product logs category, status and elapsed time (R-11); provider-side usage events are the
  provider's (not owned, not observed).
- **Salesforce metadata deployment (development tool boundary, not runtime).** Authority: the org; completion is
  the deploy's terminal status plus listing read-back, not an accepted request ID (R-1.1). Inapplicable: cache and
  invalidation (nothing is cached), incremental sync, event streams.
- **Credential store.** Authority for the secret; read path is only the platform's callout machinery (R-5); a
  connector login or metadata read does not prove runtime callout access (R-6.2 requires a runtime-path check).

  attempted and blocked by the sandbox, so this is **hand-recomputed, not executed**. Start reachable: yes, a user

  not executed here).

  start depends on GAP-1 and the `AD-2` PROBEs, so those steps are open prerequisites, not claimed executions.

  the category and the text and the callout count; R-12.1 requires absence of elements, not only text equality;
