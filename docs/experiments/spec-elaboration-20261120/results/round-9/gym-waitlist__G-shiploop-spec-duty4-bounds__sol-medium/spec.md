# Class Booking App Specification

## Basis and scope

**U1 · Incoming request · 2026-11-21.** “Add a waitlist to our class booking app so full classes don't turn people away.”

U1 identifies an existing class booking app and asks for an alternative when a class is full. The specification interprets a waitlist as a way to request a future seat and to receive that seat when it can be assigned. Existing booking for available seats and applicable eligibility, capacity, cancellation, and access rules are preserved; waitlist participation and fulfillment are the feature delta. The workspace supplies U1 and the ShipLoop guides. No prior spec, selected baseline, reference product, runtime, or observed app behavior was supplied. Preservation clauses describe intent; the listed gaps identify what must be recovered before depending on a specific existing behavior.

## Requirements

### R-1 — Join a full class's waitlist

**Basis and delta.** [U1, Incoming request](#basis-and-scope), “Add a waitlist … so full classes don't turn people away.” Preserve the existing booking path for available seats and applicable booking restrictions. Add a waitlist action for an eligible booker at capacity. The relevant existing rules and consumer route are unverified. Implementation and the live checks below are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| R-1.a | An eligible booker viewing a full, bookable class instance sees a Join waitlist action and, before acting, sees that joining authorizes automatic booking if a seat opens and existing rules allow it. | Closed or canceled instances and users ineligible to book cannot enter the waitlist. Show the applicable existing restriction where the user is allowed to see the class. | At authoritative occupancy equal to capacity, an otherwise eligible user can join subject to R-1.c. Below capacity, use existing booking when R-2 leaves a seat available for direct booking. | Class booking surface. Compare open full, open available, closed, canceled, and ineligible states for the same applicable route. |
| R-1.b | Joining creates a confirmed waiting entry for the booker and class instance. The accepted entry consumes no seat. | If eligibility, availability, or authority changes before acceptance, re-evaluate and show the latest permitted outcome. **State and data.** The existing booking authority owns the waiting entry for the same booker identity and class-instance scope used by existing booking. Before acceptance there is no active entry for that pair; afterward there is one and the confirmed booking count is unchanged. The join is ordered on authoritative acceptance. Conflicting actions are resolved using current booking and waitlist state. If the response is lost, read current own status and reconcile or retry as in R-3. An unresolved join replay is the same intent; a new explicit join after confirmed removal is a different intent.

**Open gaps.** The app owner must identify the current class-instance and booker identities, eligibility rules, full/closed semantics, and actual consumer route before integration. No queue capacity is implied by U1. The runtime owner must establish actual capacity and shared quotas before choosing an intake bound or proving one unnecessary, including constrained scope and recovery capacity. A user decision is needed if a verified constraint forces a product allocation policy beyond preserving accepted entries. The abstract join rules and model checks can proceed meanwhile.

### R-2 — Use an opening to fulfill the waitlist

**Basis and delta.** [U1, Incoming request](#basis-and-scope), “so full classes don't turn people away.” Preserve the booking authority's existing rules for creating a booking, including capacity, eligibility, and any transaction or consent prerequisites. Add fulfillment for waiting bookers. Automatic booking and FIFO are provisional product defaults. Cancellation, capacity changes, and any existing booking obligations are unverified. Implementation and the live checks below are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| R-2.a | By default, allocate each newly bookable seat to the earliest authoritatively accepted active entry currently eligible to book. A confirmed booking replaces that waiting entry as one outcome. Use the same confirmed booking surface as ordinary enrollment. | If an entry cannot currently book, it receives no booking and retains its order while it remains active under R-3. Consider the next eligible entry. If current eligibility or the prior operation's outcome cannot be determined, keep the affected allocation unresolved and reconcile before assigning that seat. | Zero bookable seats means no fulfillment. With openings and eligible entries, allocate up to the smaller of the two counts, rechecking at each commit. Order equal-time joins by their recorded acceptance sequence. With no eligible entry after a successful evaluation, remaining seats use the ordinary booking path. | Waiting members' booking/status surfaces and authoritative counts and order. Compare different opening sizes, order ties, skipped candidates, and empty eligible lists. See F-2. |
| R-2.b | The same seat is adjudicated under the same capacity and priority rules for fulfillment and direct booking. | A failed promotion leaves no partial outcome visible as confirmed. Recover an interrupted allocation using current state. Duplicate or stale work cannot create a second booking, move a different entry, or displace a committed booking. | At the last seat, a valid waiting entry takes priority over a competing direct booking. If leave or closure takes effect first, the obsolete entry cannot win; if promotion takes effect first, any subsequent cancellation follows the existing booking rules. | Booking and waitlist surfaces for separate users plus authoritative state. Exercise both orderings for leave/promotion and overlapping attempts to allocate the last seat, including interruption before and after commit. |
| R-2.c | A vacancy enters fulfillment when existing booking rules make it bookable, including a cancellation that makes a seat bookable. Accepted waitlist work remains eligible for fulfillment with all clients closed. | A pending cancellation or other operation that has yet to make a seat bookable cannot trigger confirmation. If the authority is unavailable, recover when it can evaluate current state, subject to closure. | Fulfillment runs inside the existing permitted booking window. At its effective closing boundary use the existing authority's definition of open; once closed, no promotion can commit. A cancellation or capacity change that creates zero bookable seats yields zero promotions. | Ordinary booking/cancellation and waitlist status surfaces, plus the actual authority's completion path. Compare pending and committed changes and exercise the recovered booking-window boundary. |

**State and data.** Affected resources are the existing confirmed bookings, bookable capacity and class lifecycle, and active entries for that same instance. Promotion observes a vacancy, live authority, and the current eligible queue head. It commits a confirmed booking and ends that entry together from the consumer's perspective. Waitlist actions cannot introduce a booking in excess of authoritative capacity or an active waitlist entry alongside a confirmed booking for the same booker and instance. A partial or uncertain operation must reconcile before the capacity is reused; a lost response does not undo a commit. The app's booking authority owns processing and recovery under its existing permissions, including reassessment without a consumer session.

**Open gaps.** The booking owner must recover actual vacancy-producing events and cutoff semantics, occupancy rules, existing cancellation/eligibility and payment or confirmation prerequisites, and any required delay before an opening becomes bookable. It must also establish whether the existing authority can observe a return to eligibility while a seat remains vacant; decide when to reassess such entries if that change is invisible, while always rechecking eligibility at the next allocation. Automatic fulfillment is conditional on the existing rules allowing it with informed join consent. If interactive confirmation, charging, or another irreversible user action is required, the product owner must decide how to allocate the seat in that flow before planning dependent fulfillment. No offer hold, claim deadline, or retry duration is selected. The runtime owner must establish how the existing authority can complete/recover this work without an open client, including its deadline and workload limits. This gates the affected allocation and timing work, while waitlist membership, ordering rules, and status design can be refined independently.

**State and data.** Active waiting state belongs to the booking authority, survives client closure, and is disclosed to the booker for that entry and existing authorized service roles as required to administer booking. The client holds only its permitted view and transient pending or error state; discard it on logout, account switch, or loss of access. Leave, promotion, and terminal class closure remove the entry from active use. Keep only existing identity/class references, acceptance order, and the disposition data necessary to reconcile the operation. Use existing authorized booking, retention, logging, and deletion processes. When that policy permits removal and reconciliation no longer needs the waitlist record, remove it from persistent feature data and derived views. Bookings have their existing lifetime. Personal or secret data is excluded from feature diagnostics as described under Service boundaries.

**Open gaps.** The app owner must supply supported class/booking views, existing identity and access rules including revocation/account deletion, closure versus suspension semantics, and any existing notification obligations. The data owner must recover retention/deletion rules, applicable quotas, and the fate of any minimal reconciliation record, including how long the target can accept replays before stale mutations must be refused. If no applicable retention policy exists, the data/product owner must set the permissible retention and deletion behavior before persistent storage and purge work. No numeric retention or update interval is selected. Status, leave, and recovery behavior can be designed independently of the physical cleanup mechanism.

Preserve focus and reading position during updates. Support keyboard and touch; verify visible focus, WCAG AA contrast, and usable narrow and wide layouts without horizontal overflow. Motion communicates a change and respects reduced motion. Confirm on rendered feature states in both themes, across the supported narrow and wide viewports and with keyboard and reduced motion. The actual device/viewport matrix is open.
- **Component and appearance premise (R-1 to R-3).** Extend the existing class booking action and status components, reusing product typography, tokens, iconography, and theme behavior where available. Inspect the actual UI before choosing treatment. For unspecified choices in any newly designed graphical view, the named reference is the light Google Gemini look and feel described in [UI development, Light expressive starting point](GUIDES/platforms/ui.md#light-expressive-starting-point), based on Material 3 Expressive. The starting appearance is a light canvas with airy spacing and a tonal action/status area, with a dark option for new web UI. Established app identity, explicit constraints, and platform conventions take precedence. The plan chooses the concrete visual treatment after baseline inspection.
- **Integrity, reliability, and freshness (R-1 to R-3).** Under simultaneous booking, membership, and lifecycle changes, the consumer-visible and authoritative outcomes obey the invariants in R-1.b and R-2.a–c. Follow R-3.d when availability or completion cannot be confirmed. Verify independent users, stale reads, lost responses, interrupted allocation, and recovery on the existing booking boundary. No independent background completion guarantee can be established until its owner and runtime are known.
- **Performance, capacity, and cost (R-1.c, R-2.c, R-3.d).** Peak demand on one class, concurrent independent classes, latency/freshness targets, runtime quotas, and resource budget are unresolved. The runtime owner must recover available quotas and expected workload before committing a capacity or time bound. Check the actual platform under both contention patterns; observe last-seat integrity, truthful pending feedback, and recovery within any established deadline. There is no evidenced numeric performance or availability commitment.
- **Privacy, compatibility, and operations (R-1 to R-3).** Preserve existing supported booking paths and eligibility, apply the read/write and retention controls in R-3, and exercise recovery and diagnostic redaction on the real boundary. Actual runtime interoperability, any migration of existing booking data, applicable audit policy, and deployment/rollback constraints need baseline inspection. A separate service, external communications channel, new identity system, and general booking redesign have no requirement basis.

## Behavior model and case evidence

**Logical state inventory.** Class instances have existing lifecycle and bookable capacity; status and capacity are authoritative inputs. A booker/class pair may have no active entry, an active waiting entry, or a confirmed booking. An ended entry is ineligible for allocation and any retained disposition is subject to R-3. Consumer pending/error cues are transient and independently recoverable from authoritative status. A booking has its existing cancellation path.

| --- | --- | --- |
| F-1 · T-1 · R-1, R-3.d · Join | Authorized, eligible, unbooked booker requests entry for an open full instance. Authority checks capacity, existing membership and any effective intake limit; accepts a new entry in its recorded order. | Waiting and unchanged occupancy. Repeat returns current status; rejection leaves entries unchanged. An uncertain reply uses read-back. C-1, C-5, C-6, C-7. |
| F-2 · T-2 · R-2, R-3.d · Fulfill | Authority evaluates a bookable opening using current access, eligibility, lifecycle, capacity and acceptance order. Commit booking and completion of the active entry together as a consumer outcome. | Booked on ordinary booking surface; waiting ends. Reconcile partial/unknown completion before reallocation. | F-3 · T-3 · R-3.a, R-3.b, R-3.d · Read status or leave | Read authorized own state; for leave, end the caller's active waiting entry. | F-4 · T-4 · R-2.c, R-3.c · Close | Existing authority ends booking for that instance permanently. Active waitlist participation ends and late work rechecks lifecycle. | Show closed/canceled under existing access rules. No later adjustment can promote against the closed instance. C-4 and C-5. |

### Replay evidence

The following is a manual walk of the proposed rules. The fixtures are synthetic and describe a model start, including authority. No real class, account, runtime, or product output was available. For each case reset to the named initial state. `G17` is an open, visible, cancelable class instance with capacity 1. Confirmed booker `A` may cancel their own booking under the fixture's existing rules, and cancellation immediately makes a seat bookable. `B`, `C`, and `D` can each join for themselves and can accept a booking without further payment or confirmation. `Z` has no access to their entries. Queue starts empty. Fixture role `O` is the existing booking authority's authorized class operator and may close booking for `G17`. For independent comparison, track the ordered active identifiers separately from the set of confirmed bookings and observe each permitted consumer as their own identity.

- **C-1 · Join and retry.** In `G17`, `B` selects Join waitlist twice, then `C` selects Join waitlist once. Under T-1 the first request records `B`; the repeat reads existing membership; `C` is eligible and the class remains full. Recomputed queue `[B,C]`, bookings `{A}`. `B` and `C` each see waiting and neither sees the other's record. In a separate stale-view branch, `B` loads the full class, `A` cancels before `B` submits, and T-1 finds a directly bookable seat. Queue `[]`, bookings `{}`; `B` can choose ordinary booking.
- **C-2 · Open the last seat.** In `G17`, `B` then `C` join under T-1. `A` cancels their booking, releasing one seat. `D` attempts direct booking while it is adjudicated. R-2.b and T-2 require the authority to evaluate the active queue before awarding the last seat, including when `D`'s request reaches it first. Recomputed bookings `{B}`, queue `[C]`. `B` sees a confirmed booking, `C` sees waiting, and `D` receives no booking. In a branch where `B` loses eligibility before allocation but retains class access, the recomputed bookings are `{C}`, queue `[B]`. The authority confirms both the allocation and that `B` was skipped without consuming capacity.
- **C-3 · Leave, rejoin, and reject unauthorized access.** In `G17`, `B` then `C` join. `Z` attempts to read and leave `B`'s entry; T-3 denies both. `B` leaves twice and rejoins while `A` still fills the class. T-3 removes the first entry once and T-1 puts the new entry behind `C`. Recomputed queue `[C,B]`. If the first join or leave submission for `B` is delivered again, R-1.b and R-3.b leave this queue unchanged. `A` cancels and T-2 assigns the seat to `C`; final bookings `{C}`, queue `[B]`. In the alternative ordering from initial queue `[B,C]`, `A` cancels and T-2 finishes before `B` selects Leave waitlist from a stale view. T-3 returns the current booking and keeps final bookings `{B}`, queue `[C]`.
- **C-4 · Close before delayed fulfillment.** In `G17`, `B` joins, and `A` cancels. Consider the permitted ordering where `O` closes booking permanently for `G17` while allocation is still pending, before any promotion commits. T-4 makes `B`'s entry inactive. A delayed allocation then re-evaluates and T-2 rejects it. Recomputed bookings `{}`, active queue `[]`, and `B` sees a closed class. This models the closure guard and does not establish that the target has a delayed path.
- **C-5 · Unknown target boundaries.** **NOT-REPLAYED: no authoritative intake limit L, actual booking cutoff/inclusivity, or closure/suspension lifecycle was supplied.** The runtime and booking owners must establish those inputs and permitted transitions before exercising R-1.c and the target-specific boundaries of R-1.a, R-2.c, and R-3.c.
- **C-6 · Interrupted completion.** In `G17`, run T-1 for `B` and lose the reply after commit. Until a successful authorized refresh, `B` cannot infer success from the lost reply; T-3 then returns waiting. Repeat join leaves queue `[B]`. Let `A` cancel and interrupt T-2 before commit. Recovery can evaluate the vacancy and allocate to `B` while their client is closed. Duplicate allocation after commit finds the seat booked and no active entry. On reopening, `B` sees booked; recomputed bookings `{B}`, queue `[]`. ## Submission

### summary

The specification covers joining a full class and receiving a seat when one becomes bookable, with own status, withdrawal, and recovery. Model walks recomputed the identified outcomes under synthetic fixtures. The existing app, target boundaries, and required product observations remain unverified.

- **R-1.b default.** One active entry per existing booker and class instance because retries and simultaneous submissions express the same enrollment intent. Alternatives are multiple entries or group-seat requests, neither implied by U1. Revalidate against existing booking identity and class-instance semantics, including any supported delegated or group booking.
- **R-2.a defaults.** Explicit join consent allows automatic enrollment when existing booking rules allow it. This gives the booker a real seat without requiring a second visit and avoids introducing a seat hold and deadline. Alternatives include an offer requiring acceptance, or an alert with a return to booking. Revalidate before dependent fulfillment against actual consent, eligibility, payment, and cancellation semantics. FIFO by authoritative acceptance, considering currently eligible entries, uses the only priority evidenced by the interaction itself and lets vacancies go to bookers who can use them. Alternatives are an existing priority policy, a lottery, or blocking on an ineligible head. Revalidate against any established priority or holds, and whether the authority can evaluate eligibility and order together.
- **R-2.c and R-3.c lifecycle premise.** Existing booking boundaries determine when allocation can occur and when participation ends. An independent waitlist deadline or handling after closure would need a product rule and runtime basis. Revalidate on the actual lifecycle and any cutoff policy; these values are open.
- **R-3.a and R-3.d defaults.** Show own status in the existing class/booking experience, with authoritative refresh. U1 requires fulfillment and understandable feedback but supplies no need for a public roster, numeric position, or new outbound channel. Alternatives include a personal position indicator or an existing notification mechanism if the app's contract calls for it. Revalidate against existing booking communications, supported surfaces, privacy policy, and app identity. Existing notification obligations, if found, apply.
- **Open bounds and readiness.** No evidence justifies a numeric intake cap, promotion deadline, retry budget, latency target, or retention period. R-1.c, R-2 and R-3 retain the affected gaps and owners. A requirement for separate interactive booking confirmation or payment would put the automatic fulfillment default in conflict with the existing contract; dependent fulfillment remains unready until the app rule is known and any needed product decision is made. No material conflict is established by the available evidence. Independent behavior definition and fixture planning can proceed.
