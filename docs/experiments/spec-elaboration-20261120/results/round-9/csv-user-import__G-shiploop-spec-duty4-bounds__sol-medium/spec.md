# User Administration

This specification covers an admin selecting and submitting one CSV to create the users represented by its data rows, then seeing the outcome. Bulk updates, deletion, role management, scheduled imports, and shared import history are outside the requested scope.

## Source and evidence status

The source is the 2026-11-21 incoming request under “Specify: ShipLoop's spec stage, run on its own”, section “The incoming request”: “Let admins upload a CSV to bulk-create users.” The run provides no prior spec, repository, Discovery or Research result, selected baseline, or reference system. The request establishes the actor, input and create outcome. The guides govern specification and review. Product behavior and defaults below are proposed for this request. No current workflow, policy, integration, or capacity has been observed. Where an applicable account policy exists, resolving and preserving it is a prerequisite to binding the import to that system.

## Requirements

### R-1 — Authorize the admin upload

**Basis and delta.** The dated incoming request, “Let admins upload”; modeled with [Actors, channels, and state ownership](../GUIDES/behavioral-requirements.md#actors-channels-and-state-ownership). Preserve any applicable account-creation and target-access rules; add an admin upload entry and enforce the same authority on the operation. No current permissions or navigation were observed. Permission mapping, implementation and target checks are pending.

- **Offer the upload entry.** Positive: An admin with create authority in the selected user-management scope can open the import and select a CSV. Failure: An unauthenticated or unauthorized actor receives no usable upload entry, including through direct access. Boundary: An admin's authority applies only to targets where that actor may create users. Observe the admin entry and direct navigation as permitted and denied identities; confirm through the actual user-management surface (C-1).
- **Enforce authority for effects and results.** Positive: Submission, creation and result access require current authority for the target; the initiating admin receives their own attempt's feedback. Failure: A denied call returns a generic access failure, provides no input or result data, and causes no user creation. Boundary: Authority withdrawn before creation takes effect prevents creation; authority withdrawn after creation leaves committed accounts in place and denies further access to import feedback. A different actor cannot read the initiating admin's attempt merely by identifying it. Confirm at the authoritative operation and result surfaces, with delayed completion, revocation and direct invocation, and check account state (C-1, C-5).

**State and gaps.** The product permission authority owns actor identity, target selection and grants. The import observes those resources, adds no grants and checks authority at the point it gates an effect or disclosure. Before and after a denied operation, user records and grants are unchanged by the import. A denied actor must regain authorized access to begin a fresh attempt. Open prerequisite for the product owner and planning lead: identify the admin grant, scope model, target selection and how current authority is enforced for creation and result reads. This gates actual access wiring, cross-scope checks and the revocation race.

### R-2 — Accept and validate a CSV upload

**Basis and delta.** The dated incoming request, “upload a CSV”; modeled with [Behavior model](../GUIDES/behavioral-requirements.md#behavior-model) and [Define non-functional requirements](../GUIDES/requirements-definition.md#define-non-functional-requirements). Preserve applicable account input rules and add file intake and validation. The CSV dialect is a proposed default; no existing dialect, field mapping or platform limits were supplied. Implementation and product checks are pending.

- **Provide the input contract and accept one file per attempt.** Positive: The import surface identifies accepted columns, required fields and the accepted CSV format before submission; the admin can select a file, replace it or clear it before submission. Failure: Submitting with no file makes no creation attempt and prompts the admin to select one. Boundary: An attempt accepts one selected file; replacement discards the preceding selection instead of combining files. Confirm through file selection, replacement, clearing and submission, inspecting the selected input and resulting users (C-2).
- **Read CSV records.** Positive: Default CSV dialect is UTF-8 with an optional initial byte-order mark, comma-delimited fields, one header record, CRLF or LF record separators, and a final record with or without a final separator. Double-quoted fields can contain commas, line breaks or doubled quotes representing a literal quote. A final separator terminates a record without adding a row. Failure: Invalid encoding, malformed quoting, missing or duplicate headers, unsupported headers, and data records with the wrong field count reject the file with actionable feedback; no user is created. Boundary: Empty input, header-only input and data made up entirely of empty records produce a no-data error. An empty record has zero bytes between record separators; an empty record among populated data is invalid and gets a record locator. Delimiters or whitespace in a record are subject to normal field count and account validation. Confirm at intake using actual file contents and at the user-management surface for unchanged state or exact created values (C-2, C-3).
- **Apply the user-creation input rules.** Positive: Each valid row supplies the account fields accepted for this import, with values interpreted by the applicable user-creation policy. Failure: An invalid field or missing required value rejects the entire file and identifies the affected CSV record and, where identifiable, its column and the reason. Boundary: Record numbers are 1-based with the header at 1; a quoted embedded line break does not advance the record number. CSV fields cannot select a target or bypass the assigned permissions of ordinary user creation. Confirm with otherwise valid rows surrounding a malformed or invalid row, including one after a multiline field; verify that reporting uses record numbers and zero records are created (C-3).
- **Enforce a safe input envelope.** Positive: An otherwise valid file within the effective upload-byte ceiling and any independently justified processing bound can proceed. Failure: Input above the effective byte ceiling is rejected with a size-limit outcome, zero creations and a way to choose a smaller file. An applicable processing bound must likewise stop the attempt without creating any users and explain how to bring the input within the supported envelope. Boundary: Exactly the effective ceiling is eligible; the smallest excess is rejected. Count bytes of the file itself, including a present byte-order mark and line separators. The operation reports the effective envelope before submission and enforces it at the creation boundary even when the UI is bypassed. Confirm the exact maximum and first excess with otherwise eligible input and inspect authoritative user state (C-6).

**State and gaps.** The admin's selected file belongs to the current view. The authoritative import operation temporarily holds accepted input and derived validation data for the attempt. Only the initiating actor with current authority gets the attempt's feedback. Replacing or clearing before submission discards the old selection; malformed or oversized input leaves the user store unchanged. The domain contract must supply allowed headers and matching rules, required/optional fields, normalization, valid field values and handling of omitted optional values. Product owner approval is needed where no policy supplies those rules. The target/runtime owner must establish the effective file-byte limit using ingress and safe processing capacity, including how upstream rejection reaches the admin as a size error. A separate record cap is open only if the byte envelope and native account constraints cannot safely bound verification and creation work. Its need and value depend on measured record-processing cost and runtime/write limits. These gaps hold schema-specific validation, capacity checks and their dependent work open; format and validation error semantics can be planned independently.

### R-3 — Create the requested users and preserve account invariants

**Basis and delta.** The dated incoming request, “bulk-create users”; modeled with [State and data change assessment](../GUIDES/requirements-definition.md#state-and-data-change-assessment). Preserve applicable account identity, uniqueness, authorization and provisioning rules; add creation of the CSV's users as one import. No actual account policy or write guarantees have been observed. Atomic publication is a proposed default. Implementation and authoritative checks are pending.

- **Create every eligible row.** Positive: A successful import creates one user per valid data record in the authorized target, with the supplied values as interpreted by the account policy and the ordinary creation defaults. The admin can find those users on the authoritative user-management surface. Failure: Rejection or a confirmed creation failure creates zero users from this attempt. Boundary: A single valid data row is enough for an import. Existing users are preserved. Compare identities, values, scope and assigned permissions before and after through the authoritative account surface; match the admin's result to those records (C-2, C-4).
- **Protect uniqueness under conflict.** Positive: A file with distinct eligible identities that are free in the applicable uniqueness scope may create them. Failure: An identity collision within the file or with an existing account rejects the full attempt without modifying the conflicting account. Boundary: For competing imports of the same identity, at most one creates it; if one commits, the losing attempt creates none of its other rows. A repeat of a successful file while those identities still exist fails with conflicts and creates no duplicates. Confirm through the real account authority with a changed-value retry, an in-file collision and two overlapping attempts; compare all affected identities and values (C-4).
- **Keep publication whole.** Positive: The complete creation set becomes authoritative before success can be reported. Failure: A confirmed pre-commit failure after partial preparation leaves zero created users from that attempt and permits a fresh attempt after the cause is resolved. Boundary: A lost response after commit neither rolls the creation back nor authorizes a second creation of the same identities. Confirm by injecting failure after work on one of two rows before commit, then separately losing the response after commit; compare the whole creation set and existing accounts in each case (C-5).

**State and gaps.** The authoritative user store owns durable user records, their canonical identities and scope. The eligible batch starts with distinct, available identities. Successful publication adds exactly that batch under normal account policies. Rejection leaves the prior state intact except for independent operations. Uniqueness is resolved at authoritative publication, including simultaneous ordinary user creation. Input correction, or a fresh submission following a confirmed zero-effect failure, is the recovery path. Created accounts use the ordinary user lifecycle. Open prerequisite for the product owner: determine the canonical identity, uniqueness scope, account defaults and any required invitations, activation, credentials, notifications or audit effects. Open feasibility prerequisite for the runtime owner: verify whole-batch publication, including any mandatory provisioning effects, inside the safe envelope. Any material conflict with ordinary provisioning or batch guarantees needs resolution before dependent work can proceed.

### R-4 — Report the outcome and end the attempt safely

**Basis and delta.** The dated incoming request, “Let admins upload a CSV to bulk-create users”; modeled with [Actors, channels, and state ownership](../GUIDES/behavioral-requirements.md#actors-channels-and-state-ownership) and [Service discovery verification](../GUIDES/service-discovery.md#verification). Preserve applicable user visibility and account audit policies; add private import state, truthful feedback and a recovery path. No runtime, history, retention policy or event destination has been observed. Transient import feedback is a proposed default. Implementation and operational checks are pending.

- **Show what the operation knows.** Positive: After submission the view indicates processing and prevents repeat submission in that view until the attempt settles or confirmation is lost. A confirmed success displays the number of newly created users; a confirmed rejection or failure states zero created and keeps actionable feedback available in the current view. Failure: On lost confirmation the view states that the result is unknown and directs the admin to check the authoritative user list or search in the target before deciding to submit again. Boundary: Upload receipt and elapsed time leave the attempt pending while confirmation is available; neither proves creation. A response for an abandoned view or different attempt cannot update the active attempt. Confirm through controlled response order, lost response, and independently inspected user state (C-2, C-5).
- **Expose only necessary import information.** Positive: The authorized initiating admin sees the selected file in their own view and receives record/column diagnostics and counts as applicable; created account values appear through normal authorized user management. Failure: Unrelated clients and revoked actors receive no import data, and diagnostics do not echo raw rows, rejected field values or secrets. Boundary: Discard temporary processing data when the operation settles or is terminated; clear local selection and feedback on discard, departure or access loss in the client. No durable raw upload, import history or cross-client drafts are required. Confirm with independent sessions, a synthetic marker in a rejected value, and inspection of accessible responses, retained state and operational destinations (C-1, C-7).
- **Provide safe operational evidence.** Positive: The system's owned operational surface can distinguish confirmed creations and their count, input/authorization rejections, and operational failures, using sanitized attempt references and outcome categories. Failure: Failure to emit an optional operational signal cannot turn a confirmed write into a reported rejection or trigger a repeated creation. Boundary: Existing mandatory account auditing, if applicable, follows its authoritative policy and is resolved with the publication rules in R-3. Confirm through the actual authorized event destination, exercise a destination failure, and verify account effects, filtering and absence of raw CSV, filenames and row values (C-7).

**State and gaps.** The initiating view owns selection and display state; the import authority owns transient processing and the authoritative outcome. A disconnected or superseded view cannot control a submitted operation. Recovery after loss of confirmation uses authorized user management. Two views may submit independently under R-3 and may only display their own attempt's feedback. Sanitized operational metadata follows applicable retention, removal and reader policy. Runtime owner and privacy/operations owner must establish termination and temporary-data cleanup behavior, quota enforcement, the event destination and retention/access controls. Product owner must identify the authoritative way for admins to check created identities, including any normal visibility delay. These gaps hold only the affected recovery, cleanup and operational verification open.

### States and transitions

The admin's transient view starts empty and can hold a selection, show a pending attempt, or display confirmed success, confirmed zero-effect failure/rejection or an unknown result. The operation starts when submission reaches its authority, processes under a current grant and ends with confirmed rejection/failure or committed creation. Loss of confirmation is a view state; it does not imply the operation has ended. The persistent user set changes only on publication and through independently authorized account actions. The individual state owners and deletion conditions are in R-1 through R-4.

## Submission

**summary**

The spec defines authorized CSV intake, account creation and admin feedback. The semantic walkthrough checked illustrative cases against the written guards and recomputed their outcomes. Product implementation and all target checks remain pending.

- R-2 default, UTF-8 comma-separated CSV with the quoting, header and record rules specified in its acceptance line. The request names CSV without a dialect or producer contract. This default covers common spreadsheet interchange and makes deliberate parsing outcomes checkable. Alternatives include a producer-specific dialect and auto-detection. Revalidate against actual admin export files and any applicable existing input contract before binding the parser.
- R-3 default, atomic publication. A reversible specification choice before implementation, grounded in the create-only request and the need to avoid silent partial outcomes and ambiguous correction after rejection. An alternative is per-row commit with explicit partial results and retry rules. Revalidate against authoritative write limits and required provisioning effects before committing the contract or its implementation.
- R-4 default, transient private attempt state and recovery through normal user lookup. The request needs immediate feedback and gives no basis for durable uploads or import history. An alternative is a durable restricted status record if the target's ordinary lifecycle makes reliable confirmation and recovery impractical. Revalidate against actual processing duration, client disconnect behavior, access policy and authoritative lookup.
- Open bounds under R-2 and R-4. The standalone evidence supplies neither a platform ceiling nor a measured workload from which to choose a safe limit. No numeric default is selected. Validate an effective byte ceiling against actual ingress, execution and temporary resource capacity. Establish a separate record/work bound only if independently necessary.
