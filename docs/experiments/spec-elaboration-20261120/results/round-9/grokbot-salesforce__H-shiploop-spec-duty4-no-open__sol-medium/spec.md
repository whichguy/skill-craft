# Grok Bot for Salesforce

## Scope and basis

On 2026-11-21 the user asked, “Create a Grok bot in a Salesforce development org.” The requested outcomes are a usable entry inside the designated Salesforce development org (R-1, clauses A–B) and a bot that answers a submitted prompt using xAI Grok (R-2, clause C). R-3 covers isolation and data handling needed to use those outcomes. This standalone run has no earlier specification, selected baseline, discovery, research handoff, or repository. Public documentation below establishes available mechanisms and provider contracts. Org state, permissions and provider entitlement are unobserved. There is no reference bot to match. “Grok” identifies the model provider for a Salesforce-hosted experience. The requested scope does not include parity with consumer Grok, production, a public channel, Salesforce record access or actions, attachments, search, or saved conversations.

New sends and view exit supersede old feedback as applicable. No callback, queue, offline submission or automatic retry is required. Separate views have independent state and the provider's current limits apply across them.

**Domain and open prerequisites.** The request leaves model variant, conversation memory, prompt/output budgets and UX of errors unstated. Each send is independent, with no promised answer wording, factual accuracy, response time from xAI, or use of live search or business data. The delivery operator owns the live integration check at release-verify, with provider administration supplied before release. **Pending.** Implementation, boundary cases and live inference are pending. The implementation owner owns controlled checks at system-test. Provider availability and live permission to call it are unverified.

## Non-functional requirements

- **Interface quality and appearance.** The Lightning shell keeps the org's established conventions. Where the bot's own surface has room to choose, its reference is light Google Gemini using Material 3 Expressive principles. Start light and provide a dark option for the bot surface, both with a consistent spacing and type scale, tonal surfaces and a single icon set. The conversation is the visual focus, with the labeled composer and primary **Send** action easy to find. Design the empty state, waiting state, response and persistent inline error with appropriate recovery. Keep keyboard focus visible, preserve reading and focus order as the response changes, announce status accessibly, and use motion only to clarify a change with an equivalent reduced-motion presentation. Confirm theme palettes, focus visibility, keyboard use, status announcement and WCAG AA text/non-text contrast in both themes. In a 320 CSS px wide bot area and a 1,280 CSS px wide browser with the Lightning shell, confirm accessible controls, wrapping of an unbroken answer and no bot-caused horizontal overflow. ## Submission

**summary**

The spec defines the Salesforce entry, real Grok exchange and isolated text lifecycle. A Lightning text bot in one designated development org is the proposed scope. The concrete org and runtime evidence are open. Independent state, validation and response-mapping design can proceed without them. The requester/org owner must designate the org and effective provisioning and test identities before target work. The xAI team owner must supply a usable scoped inference binding and confirm entitlement, capacity and effective retention before live use. No material conflict was found in the supplied intent. New baseline, scope or platform findings go through the existing spec correction route before dependent work and invalidate stale checks. Any required person-only observation remains unverified with its owner and due phase above.

Assumptions and revalidation conditions:

- R-1. Use one existing development org's Lightning shell and existing invited Salesforce users with a dedicated grant. An existing app placement or a dedicated app are alternatives. Revalidate placement, names, visual precedence and supported version when inspecting the designated org. A separate app adds administration without supplying a new requested outcome.
- R-2. Single-turn text, one pending attempt per open view and explicit retry are reversible defaults. They preserve prompt/answer association and avoid unrequested context and accidental repeat charges. Alternatives are multi-turn context, overlapping sends in a single view or queued retries. Revisit with evidence of a required workflow, sustained workload or a changed execution boundary.
- R-2.A. Default 8,192 UTF-8 bytes bounds one billable prompt while allowing multiline development inputs. It leaves room for escaping and transport under the documented Apex HTTP/heap envelope and is well below the selected model's documented context capacity. A character limit is less precise for serialized size. A tokenizer-based or larger budget could accommodate document-scale inputs. Revalidate with actual serialization and org heap checks and any documented workload that needs larger inputs.
- R-2.C. Default 1,024 visible output tokens bounds provider usage and keeps the answer small relative to the Apex envelope. Alternatives are the much larger provider default or a different cap sized for a known use case. Revalidate for the enabled model, real target payload, response completeness and intended answer length.
- R-2.D. Default 60 seconds gives short non-streamed development prompts more room than Apex's 10-second default, within its 120-second cumulative limit. Shorter waiting, the platform maximum, or a streaming design are alternatives. Revalidate with a bounded synthetic target run and observed timeouts before changing the default or moving to a different transport. The service may continue processing after the UI deadline.
- R-2 and R-3. Use ephemeral view content, synthetic data, and an administrator-managed development provider binding. No product history is needed. Existing provider audit retention is assumed to follow the documented ordinary setting until the team owner confirms the actual policy. Saved state, additional user identities and team-wide ZDR are alternatives that require a distinct use case or existing policy. Revalidate when authorized data classification, team settings or scope changes.
- R-2 provider selection. Architecture records a reversible documented Grok text model default. Revalidate it against enabled team models, the current model contract and measured response length/latency before live use, and again on entitlement or model changes.

**primary**

- R-1 — An authorized consumer can open and use the Grok Bot entry inside the designated Salesforce development org.
- R-2 — The bot submits the consumer's prompt and displays a genuine Grok text answer.

At product-acceptance, either primary requirement may remain unverified on its final surface only with a passed lower-layer test of the applicable behavior. No such pass exists in this run. Live verification of the designated org and actual xAI inference remains due at release-verify.
