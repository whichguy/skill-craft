# Grok Bot for Salesforce

An authorized Salesforce user opens Grok Bot inside an identified development org, sends a text message, and sees a reply from Grok. Conversation context lasts only while that chat is open. The bot does not read or change Salesforce business records.

**Request source** — User message, “The incoming request”, 2026-11-21 in the supplied workspace context: “Create a Grok bot in a Salesforce development org.” “In a Salesforce development org” maps to R-1 A–B. “Create a Grok bot” maps to R-2 A and C, supported by R-2 B and D and the scope defaults in R-3 and R-4.

**Baseline and reference** — The standalone brief supplies no prior spec, selected baseline, repository, discovery result, research result, or observed org. Existing org metadata, users and behavior remain unknown. Salesforce documentation describes supported navigation and access, and xAI documentation describes the inference contract. The proposed behavior matches Salesforce's signed-in entry and access model (R-1 A–B) and xAI's submitted text to completed model reply interaction (R-2 A and C). In-org chat uses temporary local context (R-3 A). The public [Grok Bot overview](https://docs.x.ai/grok-bot/overview) describes a separate product with broader task automation and other channels. Product parity with that offering was unspecified. The working assumption is a new Salesforce-hosted conversational bot powered by Grok; if the branded service itself is required, revise the integration scope before committing to the provider contract. No product or org observations were obtained in this stage.

**State and service contract.** Salesforce is authoritative for org identity, deployed metadata, authenticated user and effective permissions. Actors are the org owner, delegated deployer, access administrator, designated consumer and restricted comparison user. Initially, capture the intended org ID, release/edition, relevant metadata and grants through authorized reads. Afterward, only the agreed bot metadata/configuration and explicit assignments differ. Reconcile drift before applying changes and confirm owned resources by read-back. A stale client cannot confer send authority. Activation and removal are separate authorized changes. For failed activation, read deployment status, affected metadata and effective grants before any retry or compensating change. On retirement the responsible admin withdraws bot access, retires its integration credential under R-4 and removes only bot-owned resources if authorized. No Salesforce business-record read or write is in scope, so record sharing, object CRUD and field permissions are inapplicable to chat data access. Deployment status and permission read-back supply administrative evidence. Login monitoring is Salesforce-owned. No sync cursor, subscription or bot-owned login event is needed.

Due before org-dependent preparation or mutation. Exact org ID, revision binding, supported API version and real navigation path remain open. No broad grants or production rollout are specified.

### R-2 — Send a message and receive an actual Grok reply

**Basis and delta.** Request source, “The incoming request”, 2026-11-21, “Create a Grok bot”. Add text submission, truthful progress and a Grok-generated reply. No prior bot behavior is established. [xAI inference, Responses](https://docs.x.ai/developers/rest-api-reference/inference/responses) and [Debugging Errors](https://docs.x.ai/developers/debugging) describe possible provider outcomes. Live model access, actual thresholds and target runtime remain unverified. Implementation and checks below are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| A. Real round trip | An authorized submission reaches xAI on the configured text-capable Grok model and the chat shows the submitted message and the reply text returned for that operation. | A rejected, malformed, incomplete or empty provider result cannot appear as a successful Grok reply. | Provider wording can vary. Model identity and response provenance, with actual returned text, determine success. | In the target development org as the intended user, send the synthetic prompts in “Acceptance walkthrough”. Match the displayed replies to the corresponding successful live provider responses and model using approved, redacted operation evidence. A dummy answer or doubles cannot satisfy this check. |
| B. Validate before sending | A nonblank draft within the accepted input and context budget can start a request when idle. | Empty, whitespace-only or over-budget input starts no provider call. Preserve the draft and explain validation on the composer. | Accept exactly the configured limit under a documented counting rule and reject the first value above it. Do not silently clip user input or retained context. | Browser and server checks of empty and whitespace inputs and both budget edges, including direct submission that bypasses composer checks. Check outbound count and exact accepted payload. |
| C. Resolve the active request | Show the pending message and an accessible progress status as soon as a valid send starts. When the latest active request returns a completed nonempty reply, commit the pair once and announce completion. | For rate limits, credentials/configuration error, upstream outage, unavailable response, timeout or malformed/incomplete result, remove pending state, keep prior pairs, restore the draft and show an actionable, sanitized message. | An unfinished request or client timeout provides no delivery guarantee. No automatic retry or duplicate send while pending. A user-initiated retry is a new request and may incur a new charge. | Chat and provider adapter. Controlled delayed, distinct successes and failure fixtures verify displayed text, status, submitted prompts and call count. Check credential failure, 429, 5xx, network failure, timeout, invalid body and incomplete/empty output. |
| D. Isolate late results | An active view may change only on a completion for its own current operation. | Ignore late or duplicate completion after settlement and completion after a view is left, timed out or replaced. | Different chat views may send independently. While a send is pending, Send, composer edits and Clear chat are unavailable in that view. | Multiple browser views and controlled responses. Check old results never add text or overwrite draft, status or errors in a later view or turn. |

**State and service contract.** The consumer's chat view owns the draft and per-view pending/failed status. On submit it keeps the draft associated with the accepted operation until success or failure. A successful result appends exactly one user/reply pair and empties the composer. A failed result adds no pair, restores exactly the original draft and offers correction, retry, reset or admin action as appropriate. The failure remains visible until edit, resend, reset or departure. Only the browser view that initiated the send can observe its result. The server and provider temporarily process the authorized input. xAI is authoritative for availability, model access, limits and each generated response. Check Salesforce access at every send and use the configured provider authorization at request time. No cached replies, durable queue, provider continuity ID, subscription, cursor or incremental synchronization. Pending means waiting for a matching response, with a finite wait and no background responsibility for the chat. Provider processing can outlive abandonment and can incur cost. See R-4 for event coverage and lifecycle, and Non-functional requirements for limits.

**Open gaps.** The integration owner must confirm an approved Grok model, API entitlement, transport compatibility, quota, input/output budgets, counting rule and timeout on the selected target before finalizing dependent limits and live verification. The requester/integration owner must resolve the branded-product interpretation only if evidence shows that product is intended. Attachments, voice, search tools, external messaging, autonomous actions, record grounding, business instructions and model correctness guarantees were unspecified and are outside the default scope.

### R-3 — Keep conversation context private and temporary

**Basis and delta.** Request source, “The incoming request”, 2026-11-21, “bot”, interpreted as a conversation with temporary follow-up context. Add isolated, clearable chat state. Preserve Salesforce's existing data and sharing. No prior chat state or persistence was supplied. [xAI Generate Text](https://docs.x.ai/developers/model-capabilities/text/generate-text), “Disable storing previous request/response on server”, describes the provider option that supports this premise. The client and deployed lifecycle are unverified. Implementation and checks below are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| A. Carry successful context | A follow-up in the same open chat submits its draft plus earlier completed user/reply pairs in order. | Failed and abandoned attempts never enter later context. | A fresh view begins with no prior context. A context-limit rejection lets the user clear chat or shorten the draft where that fits the budget. | Controlled provider request inspection plus the rendered transcript. Verify the exact ordered messages across success, failure, follow-up and reset using the walkthrough. |
| B. End local state | Clear chat when idle removes displayed pairs, draft, error and context. Leaving the chat, refresh, sign-out or identity change ends that view's state. | No other user or separately opened view receives the prior state, and no late completion restores cleared or ended state. | Clear chat removes local content. It makes no claim to erase a provider-held copy. | Browser checks with independent views, reload, clear and a changed user, paired with request inspection. Verify the browser and org contain no bot-managed persisted transcripts or drafts. |

**State assessment.** The chat view begins empty and owns completed pairs and draft in session memory within that view. Only that view's current user reads the rendered copy. State ends on clear or view destruction as defined above. Appearance selection is view-local and ends when leaving the view. Separate tabs and windows never merge; only one send can modify a view at a time. Server processing is request-scoped. No conversation records, browser durable storage, shared transcripts, saved preferences, export or restored session. This state model depends on the view lifecycle and bounded payload behavior being verified under R-2 and R-3. Exact context capacity is the R-2 budget gap.

### R-4 — Protect secrets and disclose data handling

**Basis and delta.** Request source, “The incoming request”, 2026-11-21, “Grok bot in a Salesforce development org”, which entails an authenticated third-party boundary under the selected interpretation. Add protected integration access, minimal payload and content-free diagnostics. Preserve existing org records and unrelated credentials. [xAI API Security](https://docs.x.ai/developers/faq/security), “Does SpaceXSI train on customers' API requests?” and “What is Zero Data Retention (ZDR)?”, and [Salesforce Named Credentials](https://developer.salesforce.com/docs/platform/named-credentials/guide/get-started.html) describe capability and provider policy. Team policy, org setup and logging paths remain unverified. Implementation and checks below are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| A. Keep credentials server-side | A permitted Salesforce user sends without seeing or handling the key; the integration administrator can rotate or revoke the key through approved administrative channels. | A missing, disabled or rejected credential produces an actionable setup error with no raw error, key or headers on the client. | No provider credential in product source, browser artifacts, chat display, app-owned logs or handoff. Revocation governs subsequent calls once effective at the authority. | Admin configuration read-back of non-secret metadata and live positive/negative invocation. | B. The provider receives the permitted chat text and required request controls. | Do not activate live sends until an owner confirms the provider team, retention and permitted data class. | No Salesforce record lookup, Salesforce user identifiers or attachments in the inference payload. No free-text classification guarantee. | Chat disclosure, controlled outbound contract inspection and integration-owner confirmation of the selected team's policy before activation. |
| C. Diagnose without content | Authorized operators can distinguish successful completion, provider rejection by safe category, timeout and invalid response using a safe operation reference and outcome. | Diagnostic failure cannot turn a real reply into a failed chat or expose provider details. **State and data assessment.** The integration administrator owns the secret and non-secret route/model configuration scoped to this bot and target org. The approved server-side facility holds the secret, and the authorized runtime can use it for the designated provider route. Provision separately from deployable configuration. Before activation, verify access and policy with a synthetic request. After rotation, compare a new authorized send with the retired credential's revoked state using non-secret admin evidence; after retirement, remove the credential and revoke it at the provider. A replacement or failed setup must not silently use another credential or model. Provider retention is distinct from the bot's local lifetime. xAI documents default audit retention of 30 days and a team-level zero-data-retention option; turning off retrievable Responses storage does not prove zero audit retention. Approved operators see only safe diagnostics, retained and removed according to approved org facilities. No product-owned content store exists. Arbitrary user-entered text could contain personal or confidential information, so this dev use is limited to synthetic/non-sensitive prompts and makes no detection promise.

**Open gaps.** The provider team owner must provision authorized inference access through the org administrator and confirm billing, data class, retention, and any regional or zero-retention requirement before activation. The org owner must confirm safe diagnostic visibility and platform retention/removal before that path is accepted. No credential contents or account session information are needed in the specification.

## Non-functional requirements

- **Polished Lightning chat (R-1 through R-3).** Follow the UI guide's light Google Gemini reference and Material 3 Expressive starting point for airy composition, tonal rounded surfaces and visible hierarchy within Salesforce conventions. Start light with a dark option for the bot surface, subject to the documented precedence of the target shell's appearance policy. Use one spacing and type scale, a consistent light/dark palette and one icon set. The conversation is the focal point with a readable transcript, visually distinct statuses, and a reachable composer. Design the empty, loading, success and persistent error states. Establish accessible control names, visible focus, keyboard-only operation, status announcements without stealing focus and WCAG AA contrast for text and applicable controls. Motion only clarifies change and honors reduced motion. Verify both appearances in the target Lightning shell at narrow and wide widths with no horizontal overflow, including wrapped long unbroken text, keyboard focus, zoom, status announcements and reduced motion. The shell's actual theme and supported browser/viewport matrix need target confirmation by the release owner. [UI visual direction](../GUIDES/platforms/ui.md#light-expressive-starting-point) · [Google Material design research](https://design.google/library/expressive-material-design-google-research) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **Responsiveness, resource limits and cost (R-2 and R-3).** One unsettled send per live view and at most one outbound inference invocation per accepted send. A finite wait ends in success or recoverable failure, including a lost connection. Validate against Salesforce transaction/callout time and payload limits and the selected model's input, output and rate limits. Observe pending state, terminal timeout and exact outbound counts with controlled completion. The provider account's quota/tier, affordable development workload, selected timeout and input/context/output bounds remain open with the integration owner before load-dependent work and activation. No latency SLA, multi-user throughput target or spend figure was requested. [Salesforce callout limits](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-callouts-timeouts.html) · [xAI rate limits](https://docs.x.ai/developers/rate-limits)
- **Isolation, durability and recovery (R-1 through R-4).** Failed, superseded and disconnected work cannot alter another user's view or create Salesforce record changes. Show committed output only after a valid result. Check through negative authorization, delayed results, refresh and failed setup. Availability while offline, durable recovery and transcript migrations are excluded by the temporary interactive scope.
- **Privacy and operability (R-1 and R-4).** Verify secret-free artifacts and operator evidence, explicit authorized grants, redacted diagnostics and reconciled release state. Organization-specific retention, external processing terms and data residency are open before activation. Production compliance certification and production availability are outside this development scope.
