# Grok Bot for Salesforce architecture

These decisions describe the standalone specification's working design. Target-specific choices remain conditional on the corresponding requirements' open prerequisites.

## Decisions

### AD-1 — Salesforce-native consumer entry and scoped deployment

**Decision.** Use a Lightning Web Component in an explicitly deployed Custom Tab, visible through agreed Lightning navigation. Prefer the existing authorized Lightning app shell. Add a dedicated app only if target inventory shows that a scoped usable entry cannot be delivered in an existing shell and the org owner authorizes it. The component uses the `lightning__Tab` target and the real tab has a `standard__navItemPage` reference keyed by its API name. Bind and record the generated authenticated direct route after the namespace and tab name are verified. The visible label is **Grok Bot**.

**Rationale and verification.** A tab preserves signed-in use in Salesforce and lets authorized release staff bind the artifact and route to the same org. A separately hosted app would introduce another runtime and entry boundary. A component target makes the component eligible for a custom tab; the tab metadata and visibility establish the actual consumer entry. Inventory the authorized org for components, apps, tabs, Apex classes, credential metadata and permission sets before naming or deploying. Pin versions supported by that org and verify the actual app/tab route and revision using R-1. Use additive metadata and scoped permission sets for access. Match target, candidate and terminal result. Request supported rollback-on-error explicitly, read back after failure/partial/unknown status, and keep grants and secret provisioning separately authorized and verified. Separate post-commit failures from failures rolled back by the metadata operation.

### AD-2 — Server-mediated Grok inference

**Decision.** Use an imperative, non-cacheable Lightning-to-Apex request for each accepted send. Apex is the server-side gate and adapter. Restrict access to the Apex entry and External Credential principal with scoped grants. Verify effective access server-side per new invocation. Validate the bounded text payload before callout. Use an enhanced Salesforce Named Credential over HTTPS with a Custom External Credential and a named principal scoped to this bot's inference key. Configure the provider's Bearer authentication header through the platform's credential facilities. Provision the secret separately via authorized admin setup, with the key scoped to the chosen endpoint and model where the provider supports it. Browser-to-provider calls would expose a secret or require a separate user authorization model. No public Apex REST endpoint or separate service is needed.

Use the xAI Responses API, `POST https://api.x.ai/v1/responses`, with the approved explicit model ID, `store: false`, no streaming, no tools or previous response identifier, and a configured output budget. Send ordered text inputs with user and assistant roles from the current view. There is no trusted Salesforce record context in the request. Server-side validation restricts roles and payload structure, and a user-supplied change to local conversation text is treated as that user's input. The endpoint, model, retention setting and credential are server-controlled. For a successful response require a valid completed result from the approved model identifier or its verified resolved identity, with nonblank assistant output text. Read completed assistant output-text parts in provider order and preserve their text. Other item types do not become chat output. Map incomplete, unreadable, unsuccessful or empty results to a safe failure category. An unsuccessful send can still have reached xAI. Avoid retries and reply caching.

**Rationale and verification.** The Responses API is the provider's recommended interface for new integrations. Salesforce documents server-side callouts with encrypted credential storage and permission mapping. xAI documents Bearer authorization, the Responses schema and model discovery. Docs establish a feasible route. Verify the authorized principal, model and API behavior through an approved synthetic request, and test denied invocation in the target. A server transaction allows one inference callout per send. Salesforce documents a maximum of 100 callouts and 120 seconds cumulative callout time per transaction, and a synchronous maximum request or response size of 6 MB with heap use also accounted for. Those are ceilings. The implementation must choose lower operating limits with heap/serialization headroom, verify the target's concurrent-callout limit and provider rate/context limits, and measure with authorized synthetic fixtures. A browser timeout additionally ends the current UI operation when an invocation never returns. Confirm actual model/region, credential capability, payload counting and both timeout values before the dependent checks. In isolated verification, record actual provider outcome and model and compare synthetic output at the boundary through an approved, restricted observation with no durable prompt/response logs. The operational diagnostic record needs only the opaque operation reference and safe outcome/category.

### AD-3 — View-local state and accessible Lightning presentation

**Decision.** Keep drafts, completed turns, appearance selection and pending state in the current component's memory. Identify sends with a view generation and operation identity. Use component lifecycle cleanup and verify whether the actual Lightning container retains views across navigation, especially any console workspace behavior. Explicitly invalidate the old view when it ends. Use the existing signed-in Salesforce shell, accessible native or Salesforce Lightning Design System primitives and one SLDS icon family. The composer and transcript use a scoped layout and consistent appearance tokens for the chat itself. Use semantic text rendering, with wrapping for long strings. Avoid rendering provider output as HTML or actionable instructions.

**Interaction and skin.** Center the conversation and composer in an airy, tonal panel with one restrained emphasis on Send and a legible per-turn pending cue. Use Salesforce typography and resulting shell conventions with a light bot appearance and a dark option under the target's appearance policy. Use restrained rounding and consistent spacing and hierarchy. Render the progress and failure states beside the relevant composer/turn, retain input on failure and announce meaningful updates to assistive technology. When space narrows, keep reading order and the composer accessible without horizontal scrolling. Respect text sizing, visible focus and reduced motion. Choose actual scales, colors, breakpoints and supported primitives during planning against the selected Lightning theme. The UI visual-direction guide supplies the starting point; no dedicated frontend-design skill or existing implementation was supplied.

**Rationale and verification.** Native primitives and scoped styling keep a small surface within the Lightning shell. A custom toolkit would add compatibility and maintenance work for little expected gain here. A bounded target check should confirm navigation teardown or logical reset, rendered light/dark variants, and the accessibility of the selected controls under both variants. Verify state isolation and response ordering independently of animation completion. R-2, R-3 and the non-functional requirements supply the consumer observations.
