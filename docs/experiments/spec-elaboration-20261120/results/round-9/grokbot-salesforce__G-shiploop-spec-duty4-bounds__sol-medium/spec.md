# Salesforce Grok Bot

## Basis and scope

The 2026-11-21 request under “The incoming request” says “Create a Grok bot in a Salesforce development org.” The delivery outcome is a bot an authorized user can open and use inside the designated development org. “Grok” is interpreted as a genuine reply from the xAI Grok inference service. The first delivery is a text exchange inside Salesforce for existing org users. The application has one working exchange per open page and sends each prompt independently. The request supplies no domain workflow, reference product for parity, or required Salesforce business data. No earlier spec, repository, discovery or research result, or selected baseline was provided. Public platform docs establish available capabilities. The actual org and provider team have yet to be inspected.

| Requested outcome | Consumer acceptance |
| --- | --- |
| Create it in a Salesforce development org | R-1.a requires the installed, reachable bot in the identified org. R-1.b and R-1.c govern access and containment. |
| Create a Grok bot | R-2.a requires a real Grok exchange from that entry. R-2.b, R-2.c, R-3 and R-4 bound input, recovery and data handling. |

## Requirements

### R-1 — Open the bot in the designated Salesforce development org

**Basis and delta.** “in a Salesforce development org” in the 2026-11-21 request, “The incoming request.” No preserved contract was provided. Add an in-org entry and bounded access to it. [S1](#source-notes) establishes the platform paths. Org identity, entitlement, deployment, and browser checks are pending.

- **R-1.a** — **Positive** — In the designated development org, an assigned user can open the deployed **Grok Bot** entry in Lightning Experience and reach a working prompt composer. **Failure** — incomplete installation or activation leaves org delivery incomplete even if deployment reports success. **Boundary** — only the identified development org is in scope. **Surface and confirmation** — observe org identity and deployed revision, then navigate by the launcher's **Grok Bot** entry in that org as the assigned user. A preview, screenshot, or bare component cannot satisfy C-1.
- **R-1.b** — **Positive** — Salesforce checks the current existing user's grant on each new submission and allows an assigned user with an active session. **Failure** — a signed-out user encounters Salesforce sign-in, and a signed-in, unassigned or revoked user is denied access to sending, including via a stale open page or a direct submission attempt. No provider request or reply occurs on denial. **Boundary** — Salesforce authorization applies when a new send is admitted. A later revocation does not recall a request already dispatched or erase content that the browser already received. **Surface and confirmation** — clean browser sessions and a direct invocation at the deployed Salesforce boundary, with dispatch evidence for the granted control and zero dispatch on denial (C-2).
- **R-1.c** — **Positive** — the org administrator installs and activates the bot and grants access only to designated existing users. **Failure** — if setup is partial, record the completed effects, withhold user activation or withdraw it, and reconcile metadata and access before resuming. **Boundary** — on a naming conflict, preserve the existing occupant and resolve the target asset before deploying. **Surface and confirmation** — capture scoped before/after metadata and access readback, terminal deploy status plus revision/target evidence, and verify the affected users' entry visibility and ability to invoke it (C-1, C-2). Check both intended changes and preservation of colliding or unrelated assets.

**State and data.** The affected resources are the bot's deployable assets, entry and access grants in the designated org. The org administrator owns changes, and existing target Lightning users consume the entry. Begin with a readback of relevant metadata and permissions. After setup, the installed revision, active entry and assigned access must agree, and the scoped change preserves existing org assets and records. Run one install/configuration change at a time for the bot. After an interrupted or failed operation, read back actual effects before retrying. To back out, remove the bot-specific grants and entry and revert only the bot's changes using the pre-change inventory. No Salesforce record import, object/field creation, record sharing changes, or production deployment is in scope.

**Open gaps.** The user or org owner must identify the exact development org and designate installer, allowed user, and acceptance observer (including a denied-user role). Confirm the edition, installed metadata, license and supported Lightning runtime before target-specific planning. Deployment, entry activation and assignment are separate actions under org authority. This blocks target selection, live mutations and C-1/C-2, while component behavior and synthetic verification design can proceed.

### R-2 — Submit a text prompt and see a Grok reply

**Basis and delta.** “Create a Grok bot” in the 2026-11-21 request, “The incoming request.” No preserved contract was provided. Add an interactive prompt-to-reply surface. See [S2–S4](#source-notes) for the inference contract and runtime ceilings. Model entitlement, usable payload bounds, and live and lower-layer verification are pending.

- **R-2.a** — **Positive** — for each accepted send, submit the user's prompt to the configured Grok model and present the corresponding completed nonempty assistant text, in provider order, as inert text labeled **Grok** next to the submitted prompt. **Failure** — a service or parsing failure follows R-3.b. **Boundary** — a response must belong to that send and the current page instance. Intermediate status, partial text and provider metadata do not meet the completed-answer condition. **Surface and confirmation** — from the deployed entry, send two different prompts and correlate each submission with an independently observed response from the configured Grok route. Assert the rendered text matches that response and check distinct synthetic responses for echo, fixed-reply and stale-response substitutions (C-3, C-4).
- **R-2.b** — **Positive** — accept nonblank text, preserving the submitted characters, including non-ASCII text and newlines. **Failure** — empty or whitespace-only text gets a prompt-required validation cue and sends zero requests. **Boundary** — accept text at the effective input maximum when the other validations pass. Above it, keep the text editable, give a size validation cue and send zero requests. If the provider rejects an admitted prompt for its context limit, show a shorten-and-resubmit error with the original prompt available. A draft rejected locally does not replace an existing completed exchange. **Surface and confirmation** — observe composer feedback and callout counts at the browser and Salesforce submission boundaries, including direct calls and the exact below/at/above cases after the bound is established (C-4, C-7).
- **R-2.c** — **Positive** — a completed usable reply at the effective generation limit is displayed as returned. **Failure** — when the provider reports an incomplete reply due to its limit or Salesforce cannot accept/process the response within its envelope, end pending state and show a size/incomplete failure with a path to submit a shorter request. **Boundary** — a reply that would require more than the effective budget cannot be presented as complete using truncated content. **Surface and confirmation** — compare controlled completed and incomplete envelopes and exercise the effective boundary through the selected org route (C-4, C-7).

**State and data.** The user owns the draft. Only the submitting user's page holds the visible prompt/reply, and only an accepted prompt crosses the provider boundary. Before admission, there is a draft and zero provider effects. On completion, the visible reply belongs to the admitted prompt. The recovery and end-of-life rules are in R-3/R-4. Simultaneous page instances have distinct state and no shared draft or reply. Conversation memory, CRM grounding, attachments, voice, tools/actions, guaranteed factual accuracy, and a required Grok persona are outside the specified text exchange. The request supplies no model preference or maximum prompt/answer size.

**Open gaps.** The integration engineer and the org and xAI team owners must establish the technical prerequisites before freezing the affected payload and provider design. Establish the entitled text model, its input/context and output envelope, useful development prompt/answer size and serialized overhead/heap headroom in the selected org. Set the effective input and generation bounds from that evidence. A platform ceiling alone gives no safe acceptance limit for the combined serialized request, response and parsing copies. The selected bounds, their units and concrete boundary fixtures gate the size-sensitive work. Prompt validation and response mapping for representative small messages can proceed independently.

### R-3 — Show pending, completion and recovery accurately

**Basis and delta.** “Create a Grok bot” in the 2026-11-21 request, “The incoming request.” No preserved behavior. Add truthful waiting and recoverable failure to the text exchange. [S2–S4](#source-notes) document the upstream behavior and timeout envelope. Runtime pending, timeout and recovery checks are pending.

- **R-3.a** — **Positive** — an accepted send displays the submitted prompt and an accessible waiting status until that send completes or fails. **Failure** — losing the connection yields a visible failure when the page can observe it. A page the user leaves has no further display obligation. **Boundary** — **default** of one active send per page instance. While waiting, a second activation of Send starts zero additional provider calls and there is no queued send. At terminal success or failure, sending is available again. **Surface and confirmation** — hold a controlled response and attempt Send again, then release it and verify the state, request count and matching output (C-5).
- **R-3.b** — **Positive** — after failure the authorized user can submit again explicitly with the failed prompt available to edit. **Failure** — show a persistent, safe explanation and next action for each observable class: access denied, integration unavailable or misconfigured (missing or rejected credential, model unavailable), rate limited, provider or network unavailable, timeout, input too large, or unusable response. Preserve the failed prompt and show zero Grok replies for that attempt. **Boundary** — **default** of zero automatic retries. For access or setup errors direct the user to the org administrator. For quota rejection suggest waiting. For transient service, network or timeout failure offer explicit resubmission. For oversize or budget exhaustion suggest shortening the prompt. For an unusable response explain that Grok did not return a usable answer and offer another send. A timeout or lost response can follow provider processing, so a deliberate resend may incur another provider operation. **Surface and confirmation** — controlled failure inputs, composer feedback, redacted diagnostic class and outbound request count, plus a successful explicit recovery (C-4, C-5, C-8).
- **R-3.c** — **Positive** — if the platform delivers a valid completion within its wait window, show the reply. **Failure** — on a callout timeout, leave waiting and show a retryable timeout with no Grok reply. **Boundary** — **default** callout window is Salesforce's 10 seconds, measured at the downstream call. At the cutoff the platform outcome decides completion versus timeout. Beyond it a late provider reply cannot update the attempt. This is a callout wait bound. **Surface and confirmation** — on the selected Salesforce runtime observe a controlled immediate response, caller-directed timeout and the late downstream completion; correlate all occurrences with the attempt (C-8).

**State and data.** The page owns the pending status, submitted prompt and the slot for a terminal outcome. The server owns the authorization and status of the call it initiates. One admission supersedes the previous visible exchange. Connection loss can leave provider outcome unknown; retry begins a new authorized attempt and needs no rollback of Salesforce records. Correlate completion to the attempt and page instance to suppress late delivery after failure, navigation or supersession. There is no promised remote cancellation, durable queue, background completion, SSE, polling, or offline resumption for this interactive exchange.

**Open gap.** The integration engineer must revalidate the 10-second default against a real authorized selected-model sample in the development org before live readiness. No user-specified latency, throughput or retry schedule is available. This leaves live suitability and C-8's target observation open, while controlled waiting/error handling can proceed.

The actual team policy, logging, isolation and credential setup are unverified.

- **R-4.a** — **Positive** — the page shows the submitted prompt, matched reply and safe feedback only to the submitting session/page. Before sending, disclose that prompt text goes to xAI, display the verified team retention policy and instruct users to use synthetic development text. **Failure** — when the team policy or approval for that data transfer is missing, keep live sending disabled until setup is verified. **Boundary** — the product sends the current prompt and required inference parameters only. No earlier turn, Salesforce records, Salesforce user identifiers or browser session tokens accompany the prompt. **Surface and confirmation** — inspect the deployed disclosure and controlled outbound payload for both sample submits, including a cross-user/session isolation check (C-3, C-4, C-6).
- **R-4.b** — **Positive** — an authorized admin can provision, rotate and remove the inference credential through protected org configuration. The provider authenticates the server-side call. **Failure** — an unavailable or revoked credential follows R-3.b without disclosing the secret, authentication headers, upstream body, or stack trace. **Boundary** — the key stays off the browser, deployable source, application logs and handoff output. - **R-4.c** — **Positive** — a fresh page begins empty. While open, the page keeps only its current draft and exchange state. **Failure** — any callback arriving after navigation, reload, logout or identity change has no visible effect on the replacement page. **Boundary** — the application creates no saved transcript, storage-backed draft or provider history to retrieve; page state is discarded when the page instance ends. Provider audit retention follows the verified team policy, separately from page lifetime. **Surface and confirmation** — observe fresh/reloaded and separate signed-in pages, inspect browser storage and Salesforce persistence, and exercise delayed completion with an intervening navigation (C-5, C-6).
