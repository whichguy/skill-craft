# User Administration

## Scope and sources

The source of user intent is the 2026-11-21 incoming request, § “The incoming request”: “Let admins upload a CSV to bulk-create users.” This adds a one-file import to user administration. Product defaults below resolve details the request leaves unspecified. The change covers creating ordinary user accounts in the administrator’s authorized scope. Updating or deleting users, choosing roles, importing credentials and adding an invitation workflow are outside this change. Ordinary account creation and its established lifecycle continue to apply.

This standalone stage has no earlier spec, repository, research, discovery, selected baseline or reference product. There are no observed product behaviors or preserved requirement IDs to reconcile. References to existing account or authorization rules are preservation conditions to check on the eventual target, rather than claims that a particular rule or service was observed. No parity comparison applies. Implementation and product checks are pending throughout.

## Requirements

### R-1 — Give authorized admins an upload entry point

**Basis and delta.** 2026-11-21 incoming request, § “The incoming request,” “Let admins upload a CSV.” Add a file selection and submit action within user administration. Preserve the product’s administrator authorization and account-management scope wherever established. The source establishes the actor, but contains no role inventory or runtime access evidence. Implementation and checks pending.

- **Authority.** Positive — An authenticated admin with user-create authority in the active scope can open the entry point, submit, and see their own attempt’s results while authorized. Failure — A signed-out caller, non-admin, or admin acting outside their authorized scope cannot submit or read protected results, including via a direct call. A denial discloses no user existence, imported data, or outcome counts and makes no account changes. Boundary — Recheck current authority at submission, at each creation decision, and before serving results. Revocation prevents later creates and disclosure, while accounts already committed remain. Clear visible import state when the client learns of revocation, logout or account/scope switch. Surface — User administration and its import boundary. Confirm — Exercise entry, direct submission and result delivery as the authorized and denied identities and revoke between two creates. Compare the directory before and after.
- **Selection.** Positive — Show format and current upload limit before submission. The admin selects one local CSV, sees its file name, and explicitly submits. Failure — With no file selected, submission is unavailable and guidance describes how to select one. Boundary — Replacing or clearing a selection before submission changes or discards only the draft. Selecting alone creates zero users. Surface — Upload UI. Confirm — Select and clear the sample in W-1 before submitting it. Inspect accessible controls and verify the directory remains unchanged until submit.

**State, data and omitted rules.** The target is the admin’s current authorized directory or account namespace. The authority derives scope from the authenticated context. A CSV or client-provided scope cannot confer authority or select an unauthorized target. The user’s chosen file stays in their current page’s transient draft until submission. Only that admin context can see the selection and current result. Navigation, context change or explicit reset clears the draft. Recovery is to select the file again in an authorized context. No changes to identity, authentication or sharing policy are needed.

**Target prerequisite.** The product owner or integration owner establishes the target and documents actual administrator roles, scope, creation and revocation semantics before target binding. This is unverified in this stage. The default requires an admin with ordinary user-create permission. The entry, denial and scoping contracts can be specified independently of target binding.

### R-2 — Accept and validate one CSV before creating accounts

**Basis and delta.** 2026-11-21 incoming request, § “The incoming request,” “upload a CSV.” Add a documented import format and preflight validation. Preserve ordinary field validation at creation. The request supplies no dialect, schema or capacity and no parser or host was observed. Implementation and checks pending.

- **Format.** Positive — The default format is UTF-8, optionally with one leading UTF-8 BOM, with one header field `email` and one email field per data record. Recognize commas as field separators and LF or CRLF as record separators outside quoted fields. A quoted field begins with a double quote, uses doubled quotes for a literal quote, and ends before a separator or EOF. A newline in quotes belongs to that field. A bare quote in an unquoted field is invalid. Accept a final record without a trailing newline. The header value after CSV decoding is exactly `email`. Failure — Reject the whole file before any creates for unreadable input, invalid UTF-8, malformed quoting, unsupported or missing headers, extra header columns, or zero data records. Give a file-level reason. Boundary — Ignore physically blank records outside quotes after the header. A quoted empty field is a data row with a missing email. A parseable data row with the wrong number of fields is a row rejection under R-3. Surface — Format guidance and the authoritative import response. Confirm — Compare W-1 and W-2 with directory read-back, including an earlier valid row followed by a malformed record.
- **Admission limit.** Positive — Admit otherwise eligible files at or below the advertised maximum raw CSV bytes. The default maximum is the largest validated whole-byte budget at or below the target’s safe end-to-end budget for ingress, full-file validation, creation and result delivery, taking the most restrictive applicable capacity into account. Failure — Above that effective maximum, show the maximum and how to split or reduce the file. Reject before any creates. If a safe budget has yet to be validated for a deployment, upload is unavailable with an explanatory state. Boundary — The maximum is inclusive. Apply it to the file bytes before decoding, including BOM and line endings, independently of client metadata. Surface — Upload UI and authoritative import admission. Confirm — Check W-3 at, below and above the effective limit and perform the same boundary check at the actual deployed ingress.

**State, data and omitted rules.** Before admission no server-side import state or account effect is required. During the request the import authority may hold the raw bytes, parsed records and minimum working data needed for validation and processing. Only the import operation uses that data. Raw files and records are discarded when the request terminates, including validation rejection or interruption. The selected file remains under the admin’s control on their device. Size is bounded for safety. The request supplies no separate row quota, throughput goal or format variants. Admission must constrain worst-case record density and result representation within the validated budget.

**Target prerequisite.** Integration owner measures the chosen runtime’s safe budget and verifies user-facing rejection at actual ingress before enabling upload. Unverified here. Format, byte-count semantics and rejection behavior are independent of that measurement.

### R-3 — Create ordinary users from eligible CSV rows

**Basis and delta.** 2026-11-21 incoming request, § “The incoming request,” “bulk-create users.” Add creation of multiple eligible accounts from one submitted file. Preserve ordinary user creation validation, uniqueness, authorization, role, account lifecycle and side effects wherever established. No account schema, identity policy or downstream system was observed. Implementation and checks pending.

- **Creation.** Positive — After whole-file preflight, handle eligible records in file order. Each eligible row for a new identity creates one ordinary user account in the authorized directory. Count a row as created only after authoritative confirmation of account creation. Failure — An ordinary validation denial or a row with missing, invalid, or extra fields yields a row-specific reason with zero account effects for that row. Other valid rows continue. Boundary — The default is independent commitment per row, including for a file containing a single valid row. Apply the ordinary user-create path to decoded email, trimming leading and trailing spaces and tabs. Use ordinary identity normalization and validation when established. The fallback for the spec model is a case-insensitive email key within the account namespace. Surface — Admin’s import result and authoritative directory. Confirm — For W-1, compare exact outcomes to read-back of each named identity and ordinary account role. Verify the existing record is unchanged and that successful rows after rejected rows are present.
- **Conflicts and retries.** Positive — A previously unclaimed identity is eligible for a create, including on resubmission after a prior attempt failed before commitment. Failure — An existing identity or one created by an earlier row receives an already-exists outcome and does not change the existing account or repeat its creation side effects. Boundary — For concurrent imports or ordinary creates targeting the same identity, the directory admits at most one creation. The other attempt reports already exists once the conflict is confirmed. Enforce the invariant at creation, including when earlier eligibility checks saw the identity as free. Surface — Import results, ordinary creation result where applicable, and directory. Confirm — W-1 and W-4 require exact result categories, record counts, scope and preservation of the winning record.
- **Interrupted writes.** Positive — Confirmed creates remain available through normal user administration when processing stops. Failure — For a system failure whose write outcome cannot be established, stop before the next row and distinguish the unconfirmed row from rows definitely unprocessed. If authority cannot be checked or is revoked, stop new writes and withhold protected results per R-1. Boundary — When a caller loses the response, treat the attempt as unconfirmed from that caller’s view. Authorized resubmission resolves each supplied identity against current directory state and cannot create a duplicate. Surface — Import response where deliverable and directory read-back. Confirm — W-4 checks response loss after a commit and an indeterminate write, including the set of identities present and absent before retry.

**State, data and omitted rules.** The account directory owns the durable user and role assignment. The target identity is the ordinary uniqueness key inside its authoritative namespace. Before each create the identity is either present or eligible for creation. After a successful write exactly one ordinary account occupies the key. Rejections preserve the prior account set and privileges. Irreversible completed creates survive interruption. Existing authorized account lifecycle rules own subsequent reads, retention and deletion. The import does not broaden access to directory data. Email-only input, ordinary non-admin role and independent row outcomes are defaults for the unspecified schema, onboarding and partial success rules.

**Target prerequisite.** Integration owner binds the contract to ordinary creation and proves scope, key equivalence, authoritative confirmation and race safety before implementing dependent writes. Check for required account fields and ordinary create side effects, including any downstream provisioning. If an observed product policy conflicts with the email-only default or changes the authority or outcome, reconcile the affected contract before those writes. No such conflict is evidenced here.

### R-4 — Explain completion, failures and recovery

**Basis and delta.** 2026-11-21 incoming request, § “The incoming request,” “bulk-create users.” Add truthful status and actionable outcomes for the submitting admin. Preserve ordinary user-management visibility and access. The request provides no status, history or retention mechanism. Implementation and checks pending.

- **Pending and completion.** Positive — On submit, show an accessible pending state through validation and processing. When the authority returns a completed result, show counts for created, rejected and already exists, and the logical record number and reason for each non-created row in file order. Count the header as record 1, exclude physically blank records, and count a multi-line quoted field as part of one record. Failure — A file rejection displays its file-level reason. On an interruption with an authoritative partial response and sufficient authority, show confirmed dispositions plus separate unconfirmed and unprocessed counts and affected record numbers. If the response is lost or the target’s request deadline is reached without confirmation, show that outcomes could not be confirmed and explain checking the directory or resubmitting. Boundary — A completed result must reconcile its three counts to all data records, even when zero are created. Pending, request receipt and connection loss never imply creation or full failure. Surface — Status and results in user administration. Confirm — In W-1, W-2 and W-4, observe reported counts and record numbers against the original file and directory read-back, including the all-rejected variant.
- **Recovery and isolation.** Positive — After rejection or interruption, an authorized admin can choose a corrected file or resubmit and receive a result for that attempt. Failure — A delayed response from a prior attempt or context cannot replace a newer draft or result, or reveal information after a context change. Boundary — The upload action cannot submit twice while its current request is pending. Other sessions can still submit under R-3. Leaving the view drops the local draft and result and does not undo writes or promise cancellation. Surface — Upload UI across replies and context changes. Confirm — Hold a response, switch contexts, then release it. Return as the authorized admin and resubmit as in W-4. Observe the new attempt’s result and compare the directory.

**State, data and omitted rules.** Default completion belongs to the submitted request and its current UI view. Status is transient. The UI keeps a current result only until replacement, reset, exit or context loss. The product retains no import history, file, or per-attempt retrieval record for this feature. Row diagnostics use logical record number and allowlisted reason without echoing field values or file contents. The result is accessible only to the currently authorized submitting context. Directory lookup remains subject to normal access. The request leaves background completion, cancellation, history and notifications unspecified.

### R-5 — Minimize import data exposure and record owned outcomes

**Basis and delta.** 2026-11-21 incoming request, § “The incoming request,” “admins upload a CSV to bulk-create users.” Add operation evidence for privileged account creation and minimize incidental retention of the upload. Preserve ordinary account audit, authorized access and retention policies where established. This stage has no evidence of runtime event coverage or a logging destination. Implementation and checks pending.

- **Data exposure.** Positive — Authorized admins see filename locally and record-number diagnostics in the results. Authorized directory readers can see newly created accounts through normal user administration. Failure — Uploaded fields, CSV bytes, filenames, credentials and raw diagnostics are excluded from logs and telemetry. None are copied into retained import storage. Boundary — Persistent account fields and ordinary account audit governed by the target’s existing policy remain subject to that policy. Surface — Upload view, directory and application observability. Confirm — Use a distinct harmless marker in an invalid extra field, inspect results and retained data in W-5 after a completed import and a rejection, and search the target’s approved import logging destination for the marker and uploaded email addresses.
- **Owned events.** Positive — The import boundary accounts for submitted operation outcomes, including denial, file rejection, completed counts and interrupted processing where observable. Use a protected existing operational or audit destination and its retention policy where applicable. Include a safe operation correlation reference, outcome, applicable counts, and the authorized scope and actor reference when allowed by policy. Failure — A diagnostic delivery failure cannot turn a committed create into a rejected row or obscure the underlying business error in a deliverable response. Boundary — Reuse sufficient ordinary account-creation and authentication events. Import events report the distinct batch outcome. Surface — Approved event reader and import result. Confirm — Use W-5 to compare actual event records for one completed, one rejected and one denied attempt, including redaction and correlation. Simulate an unavailable diagnostic destination and reconcile the visible outcome with the directory.

**State, data and omitted rules.** The product’s import authority owns the aggregate outcome event. Access is limited to approved operational or audit readers. Use the destination’s applicable retention and purge schedule. Where no suitable policy is established, retain no new import telemetry containing actor or scope identifiers until the target owner establishes the policy. The application retains created account data only through ordinary user records. This request introduces no credentials and needs no new data export.

**Target prerequisite.** Integration owner verifies authoritative event ownership, safe retrieval, retention/purge and existing event coverage before wiring or validating import events. Extend owned coverage only for missing import outcomes. Any mandatory audit failure rule discovered on the target must be reconciled before enabling dependent writes. Privacy behavior can be specified independently of that destination.

## Model walks and evidence

Flow and transition locators describe product behavior. W-1 through W-5 below are specification walkthroughs, with prospective confirmation surfaces identified in the requirements. The independent walk recomputes state from inputs, guards and directory invariants. Runtime fixtures and product execution remain pending.

| Flow | Ordered actions and transitions |
| --- | --- |
| F-1 — Submit an import (R-1, R-2, R-4) | Authorize admin and show guidance → T-1 select or replace a local draft → T-2 explicitly submit and recheck authority → pending → preflight. Denied, invalid or over-limit attempts create nothing. An admitted file enters F-2. |
| F-2 — Create and report (R-1, R-3, R-4, R-5) | T-3 evaluate each row with current authority, validate content and conditionally create at the directory boundary → T-4 classify confirmed outcomes and serve a terminal result only under current authority → T-5 clear transient state on exit, replacement or context loss. A preflight failure goes straight to eligible file-error feedback. A system interruption stops further rows. Emit the observable owned outcome and release request data at termination. |
| F-3 — Retry or compete (R-1, R-3, R-4) | Authorized admin checks the directory or starts a fresh F-1 after interruption. A second authorized actor may independently start F-1 or ordinary creation. T-3 arbitrates identity at the current authoritative write, followed by T-4 or unconfirmed feedback if delivery fails. |

**Common modeled start.** Each numbered walk starts with fresh fixtures. Directory `D1` contains one ordinary user `U-7` with email `taken@example.test` and display name `Original`. Signed-in actors `A1` and `A2` have admin user-create and read authority in `D1`. Signed-in actor `N1` is a non-admin in `D1`. Actor `A2` has no authority in directory `D2`, which starts empty. All other named email addresses are absent in `D1`. The walkthrough uses the fallback identity key and accepts the sample `example.test` addresses as ordinary valid email input. The real authorized sandbox and its fixture identity rules require establishment before product verification. CSV byte literals below use `\n` for one LF and `\r\n` for CRLF, with quotes representing literal bytes inside the file. Assume a sufficient validated upload budget except in W-3.

- **W-1 — Mixed file and authority (F-1, F-2).** Use `team.csv` with `email\n"ada@example.test"\ntaken@example.test\nADA@example.test\n""\n\nben@example.test`. By R-1/T-1 selection and clearing leave `{taken}`. Select again and submit under `A1` (R-1/T-2). R-2 admits the header and six physical lines after it, including one blank line skipped. R-3/T-3 creates Ada at logical record 2, finds `U-7` at record 3, finds the new Ada identity again at record 4, rejects the missing email at record 5 and creates Ben at record 6. At T-4, R-4 therefore yields 2 created, 2 already exists, 1 rejected, with reasons at 3, 4 and 5. Directory equals `{taken, ada, ben}`, with `U-7` still named `Original`. Independently reset and submit `email\n""` as `A1`. Record 2 is rejected, so counts are 0 created, 0 already exists, 1 rejected, and directory stays `{taken}`. Independently reset and attempt direct submission of `team.csv` as `N1`. R-1 stops at T-2, so directory stays `{taken}` and neither counts nor row diagnostics are visible. The same T-2 denial applies to an unsigned caller and to `A2` trying to target `D2`. Both directories retain their starting records in those fresh runs.
- **W-2 — File failure precedes all creation (F-1, F-2).** As `A1` select and submit `broken.csv` with `email\nada@example.test\n"unfinished@example.test`. R-1 allows T-2. R-2 reaches an unclosed quote at EOF in preflight, so it returns a malformed CSV reason and never enters T-3. `ada@example.test` stays absent. Separately, reset and use `header.csv` with `email\r\n`, which R-2 rejects for zero data records. Reset and use `foreign.csv` with `email,role\nada@example.test,admin`, which R-2 rejects for unsupported header columns. Both leave `{taken}`. Reset and use `utf8.csv` with hexadecimal bytes `EF BB BF 65 6D 61 69 6C 0D 0A` followed by ASCII `ada@example.test` and EOF. R-2 consumes the BOM, header and delimiter before admitting the final data record. R-3 creates only Ada, yielding counts 1/0/0 in created/already-exists/rejected order and directory `{taken, ada}`. Reset and submit hexadecimal `65 6D 61 69 6C 0A FF` as `invalid.csv`. R-2 rejects at the invalid UTF-8 byte before T-3, leaving `{taken}`. In another fresh run submit `email\n"ada@\nexample.test"\nada@example.test,admin\nben@example.test`. R-2 admits three logical data records. R-3 rejects record 2 for an invalid email containing LF and record 3 for extra fields, then creates Ben at record 4. Counts are 1/0/2 and directory is `{taken, ben}`.
- **W-3 — Inclusive byte oracle (F-1, R-2).** Use a specification fixture with a declared 24-byte budget solely to calculate the boundary. In three fresh starts, as `A1` submit `bounds.csv` with `email\nada@example.test`, then the same bytes with one final LF, then the same bytes with one final CRLF. The header with LF is 6 bytes and the email is 16 bytes, giving respectively 22, 23 and 24 bytes. All admit and each isolated run adds only Ada. In a fourth fresh start, append an additional LF to the CRLF variant, giving 25 bytes. R-2 denies admission before R-3 even though the added separator would otherwise be ignored. Directory remains `{taken}`. At the actual target use valid fixtures of exactly maximum minus one, maximum, and maximum plus one bytes, holding logical records constant whenever possible. **NOT-REPLAYED: no deployed target or effective budget is available for the actual ingress check.** Integration owner verifies this before enablement.
- **W-4 — Race, interruption and revocation (F-2, F-3).** With both admins authorized, each submits `race.csv` containing `email\nada@example.test`. Hold both after preflight and let `A1` commit first at R-3/T-3. Let `A2` reach its creation decision next. One record exists, `A1` receives one created and `A2` one already exists. Independently reset. As `A1` submit `retry.csv` containing `email\nada@example.test\nben@example.test\ncy@example.test`. Allow Ada to commit, then make Ben’s authoritative write fail before commitment with its outcome unavailable to the importer. R-3 stops before Cy. With the reply delivered, R-4 shows record 2 created, record 3 unconfirmed and record 4 unprocessed. With the reply dropped at the same state, the client reports an unconfirmed attempt and cannot infer those counts. In both versions read-back shows `{taken, ada}`. After the failed attempt terminates, resubmit as `A1`: record 2 already exists, records 3 and 4 create, terminal counts are 2 created, 1 already exists, 0 rejected, and directory is `{taken, ada, ben, cy}`. Independently reset and start the same file as `A1`. Revoke `A1` just after Ada commits and before Ben’s creation decision. By R-1/R-3 no further create or protected result is permitted. `A2` can read `{taken, ada}`. A response held from the prior context cannot be displayed after context loss under R-4/T-5. To model actual late delivery, reset, submit `race.csv` as `A1`, let Ada commit, and hold the authorized completed reply in transit. Switch to `N1` before releasing it. R-4 drops the late reply, so `N1` sees no selection or result. Sign back in as `A1`, select and submit `race.csv` again. R-1 admits it and R-3 reports 0 created, 1 already exists, 0 rejected. The directory remains `{taken, ada}`.
- **W-5 — Diagnostics and cleanup (F-1, F-2).** As `A1` submit `privacy.csv` with `email\nada@example.test,PRIVATE-MARKER-501\nben@example.test`. R-2 admits the structure. R-3 rejects record 2 for extra fields and creates Ben. R-4 shows 1 created, 0 already exists, 1 rejected and identifies record 2 by reason only. R-5 permits one completed batch outcome with those counts and excludes the marker, filename and input addresses from import telemetry. T-5 clears the view on exit and the request data is discarded at completion. Directory is `{taken, ben}`. In separate fresh starts, reuse `broken.csv` as `A1` and attempt `privacy.csv` as `N1`. The model derives a file rejection and a denial respectively, each with no writes and no imported data in diagnostics. In a fresh successful run with the diagnostics destination unavailable, the committed Ben record and business result remain the same. **NOT-REPLAYED: actual diagnostics access, sink fault injection and inspection of deployed retention are unavailable without a selected target.** Integration owner verifies these at system test.

## Submission

**summary**

- The spec defines a scoped admin CSV upload, authoritative user creation and an observable outcome with safe retry. The request provides no accepted baseline or reference product. No material conflict is evidenced and no user-only product decision is needed to state the modeled behavior.
- R-1 assumption — Place the feature in user administration and use current admin plus ordinary user-create authority. This follows the named actor and mutation. A separate admin role or separate surface would add policy or interaction. Revalidate at the target’s first role and UI inventory.
- R-2 assumption — Default to a UTF-8, comma-separated, email-only file contract. It provides an interoperable minimal identity input. Additional fields or dialects would need evidence of supported producers or ordinary creation requirements. Revalidate with the first actual schema and input inventory.
- R-2 assumption — Use the validated, runtime-derived inclusive byte ceiling as the default admission limit. No numeric deployment value is evidenced. The 24-byte walkthrough budget is a fixture value. This bound protects validation, creation and feedback from unbounded input. Alternatives are an arbitrary fixed cap, an additional row cap, or an unbounded file. Revalidate the effective value on ingress, execution, resource, response-size or account-write cost changes. Only runtime binding and live boundary verification depend on that value.
- R-3 assumption — Use ordinary non-admin account creation, with case-insensitive email identity as the standalone fallback. Independently commit eligible rows after full-file structural validation and report conflicts without overwriting. This allows mixed files and safe replay without imposing elevated roles or an all-or-nothing account batch. Alternatives include atomic batch rejection, importing more account fields or identity mapping selected by another system. Revalidate against real account rules and side effects before binding writes.
- R-4 assumption — Use request-scoped outcomes and directory read-back for recovery. The request requires submission and creation; a retained result inbox or background processing would add a lifecycle. Revalidate if the chosen runtime cannot confirm the required outcomes inside its validated admission budget or if a later request calls for resumable work.
- R-5 assumption — Keep only ordinary account data and minimum approved diagnostics beyond the current request and view. Raw import history or a separate audit destination would add retention and exposure. Revalidate on target privacy, retention and observability inventory.
- Open prerequisites apply to the missing target binding, runtime budget, account and permission integration, and approved operator evidence described under the affected requirements. Independent format, state and interaction work can proceed. Product verification has no execution evidence from this stage.

**primary**

- R-1 — The admin has the authorized upload entry point.
- R-2 — The product accepts a CSV through that upload entry point.
- R-3 — One submission creates multiple eligible user accounts.

Product acceptance may leave one primary requirement unverified only with a passed lower-layer test for that requirement. No such pass exists here.
