# User Administration

## Scope and evidence basis

**Request (2026-11-21, “The incoming request”)** — “Let admins upload a CSV to bulk-create users.” The product name is unspecified. User Administration names the product area. The intended consumer is an authorized administrator working in the product's user administration surface.

**Observed inputs.** The standalone stage supplies the request and guides. There is no prior spec, repository, discovery or research result, selected baseline, or reference system. Existing account rules, interaction surfaces, and runtime capabilities are unobserved. No parity claim is made.

**Proposed product decisions.** Use one CSV, standard create-user rules, an all-or-nothing batch, and an outcome recoverable for the same submission. This bounds a bulk-create operation without adding a user-edit workflow, provisioning integration, or shared import history. Existing role, identity, create-user, navigation and design conventions must be preserved where confirmed. The defaults and dependent gaps are recorded below.

## Requirements

### R-1 — Admin access and CSV upload

**Basis and delta.** Request (2026-11-21), “The incoming request,” specifically “Let admins upload a CSV.” Add an import entry to user administration. Preserve the product's established permission and scope rules for creating users. Those rules and the target UI are unobserved. Implementation and checks are pending.

| Acceptance and transition | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| Access (F-1, T-1) | A signed-in admin with create-user authority in the selected scope can open the import and submit there. | Signed-out users and users without that authority cannot submit, including through a direct invocation. Denial reveals no protected import or account information and causes no user creation. | Authority is checked for the trusted target scope on submission, at the final create decision, and on each result read. Revocation effective before that decision prevents creation. Revocation afterward prevents further protected result reads. | Admin UI and authoritative operation. Compare allowed, denied, cross-scope and revoked principals, inspect protected responses, and read authorized account state before and after. |
| File selection (F-1, T-2) | The UI publishes the supported format, column rules and operative limits before submission. An admin can select one local file, see its name, replace or clear it, and deliberately submit. | If there is no selection or the file cannot be read, explain the issue and allow a new selection. | Merely selecting, replacing or clearing a file causes no user creation. Each explicit submission uses one file and the scope displayed at submission. | Rendered admin UI and authorized account listing. Select and replace a file, clear it, then submit the final selection and check the input associated with the result. |

**State and data.** The admin owns the local file and its selection. The private import view holds the selection and current feedback under the active principal and scope. A newer selection replaces the draft. Leaving before submission, clearing the file, signing out or switching scope discards the view's selection and feedback. Cleanup applies to product-held copies, while the admin's original local file remains theirs. No draft or raw file content goes to a shared client or durable client storage. Selected file size is subject to the confirmed upload cap.

**Open gap.** The product owner and identity owner must identify the admin entry point, authority and scope (including whether the product has tenants) before permission wiring and target UI verification. The permission rule applies even if the only scope is the whole product.

### R-2 — Validate the CSV and explain corrections

**Basis and delta.** Request (2026-11-21), “The incoming request,” specifically “a CSV to bulk-create users.” Add a publishable input contract and validation feedback. Preserve field validation, required attributes, defaults and uniqueness semantics of standard user creation once established. There is no observed account schema or file policy. Implementation and checks are pending.

| Acceptance and transition | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| File contract (F-1/F-2, T-3) | Accept UTF-8 comma-delimited records with a header, LF or CRLF separators, optional initial UTF-8 BOM, an optional final line ending, quoted commas and line breaks, and doubled quotes inside quoted cells. Match the exact published header names in any order. Require each mandatory header once and permit each supported optional header at most once. | Reject undecodable or malformed CSV, missing, unknown or repeated headers, and files above the published size or record limit. Give a file-level reason when a record cannot be located reliably. | A header and one data record suffice. An empty file or header-only file is rejected. A completely blank record between line endings is ignored outside quotes. For each confirmed cap, the cap itself does not cause rejection and the first value above it does. | Import form and operation result. Send concrete valid and invalid file bytes through the upload boundary, including bytes untrusted clients send without UI checks. Read back that rejected files create zero accounts. |
| Row and identity validation (F-2, T-3) | A data record has the header's cell count and passes standard create-user field and identity validation. | Reject the batch on a wrong cell count, missing or invalid required values, duplicate canonical identity in the same CSV or any identity conflicting in the authoritative uniqueness domain. Report the corrections found across parseable rows within the agreed limits, with offending fields when known. For file duplicates, flag each participating row. For existing identity conflicts, disclose only the submitted row and the conflict category. | Row locations are 1-based physical start lines, with the header on line 1. Embedded line breaks and ignored blank lines still advance line numbering. Two raw values treated as the same identity by standard creation conflict even if spelled differently. | Import result and authorized user view. Compare malformed, invalid, valid-neighbor and duplicate fixtures, check exact locations and reasons, and verify that all pre-existing users and their attributes survive a rejected batch. |

**State and data.** Uploaded bytes and decoded values are transient within the authorized operation. The file is treated as data, and feedback uses row positions, supported field names and reason codes or safe text. Do not echo raw cells, arbitrary headers, filenames or parser internals in diagnostics. Release product-held bytes when validation/creation no longer needs them, including failure or abandoned processing. Capture only the minimum outcome information described in R-4.

**Open gap.** The product and identity owners must confirm exact supported headers and required fields, treatment of blank optional values, canonical identity and uniqueness scope, and applicable field-level validation and defaults before publishing the schema. Runtime owners must establish the limits in Non-functional requirements before supporting production uploads.

### R-3 — Create the batch as standard users

**Basis and delta.** Request (2026-11-21), “The incoming request,” specifically “bulk-create users.” Add multi-user creation. Preserve established standard-create attributes, lifecycle and permission constraints, and all prior user records. The authority's create contract and capabilities are unavailable. Implementation and checks are pending.

| Acceptance and transition | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| Commit (F-1/F-2, T-4) | For an authorized valid submission, create one standard user per accepted record in the authorized scope and report success only after all requested users are committed. A fresh authorized user lookup can then find each target with its expected attributes and standard creation defaults. | Validation or known pre-commit failure leaves zero users from this submission and triggers no user-creation side effects. Show the reason and an applicable next action. | Existing users retain their prior IDs, fields and privileges. The CSV cannot set privileges or credentials. Any established account lifecycle effects must follow ordinary creation under its confirmed contract. | Completion view and authoritative user lookup. Compare named target identities and stored attributes against the CSV and the standard-create baseline, and independently check prior records and relevant side effects with a failure at the commit boundary. |
| Concurrent creation (F-2, T-5) | Concurrent nonconflicting creates can both succeed. | At the authoritative create decision, an identity conflict rejects the losing batch in full, including its otherwise valid rows. | Conflicts include overlapping imports and standard individual creation in the same uniqueness domain. A valid earlier lookup does not reserve an identity. | Result views and authoritative user lookup. Control ordering after validation, let one operation win, and check winner attributes, losing-row absence and exact counts. |

**State and data.** The existing account authority owns durable user records and the identity uniqueness domain. Before commit, imported users are absent. After a confirmed commit, all are present under that authority, with ordinary user IDs, scope, read policy, retention and deletion lifecycle. For definitive failure, the batch contributes no records or effects. An import never compensates by deleting an unrelated or pre-existing user. A lost response follows R-4.

**Open gap.** The identity and runtime owners must establish the actual write authority, standard account status/role and lifecycle effects, including any external identity provisioning or notifications, and demonstrate whether the chosen all-or-nothing contract is feasible across required effects. The platform's commit, authorization and uniqueness boundaries are unobserved. An incompatible authority or side-effect contract requires a revised product decision before dependent writes are ready.

### R-4 — Report outcomes, recover interrupted submissions, and protect import data

**Basis and delta.** Request (2026-11-21), “The incoming request,” specifically “upload … to bulk-create users,” plus standalone stage duties 7–9. Add truthful outcome feedback and safe recovery for that submission. Preserve ordinary account read authorization and existing privacy and audit policies once located. No existing result, retention, or audit facility was available to inspect. Implementation and checks are pending.

| Acceptance and transition | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| Outcome (F-1/F-3, T-6) | Show processing after submission and a confirmed created count on success. A rejected batch displays zero created, a reason and the next action. Announce meaningful state changes accessibly. | On a connection loss or unknown result, show an unconfirmed outcome with a way to recheck. Do not display either success or zero created until authoritative resolution. | A late response for a superseded view, principal or scope does not update the current UI. Leaving the view after submission does not cancel or roll back a commit. | Rendered UI and authorized operation result. Hold, lose and release responses around commit. Observe status text and announcements, compare the count to durable account state, and switch scope before delivery of a delayed response. |
| Recovery (F-3, T-7) | Within result retention the submitting admin, while still authorized in the original scope, can recover the result for the same submission after interruption or restart. Repeating the same submission identity with the same input converges on one authoritative outcome and creates at most one batch. | Reject reuse of the same submission identity for different input. Deny lookups by other principals, scopes or revoked actors. If the result can no longer be established after expiry, show that limitation and direct the admin to verify the intended identities before a new submission. | Repeated delivery while processing cannot authorize a second commit. Interruption before a commit decision can recover to a definitive zero-write failure, or complete once under current authority. Interruption after commit recovers the same success without re-creation. A rejected file can be corrected and sent as a fresh submission. | Result-recovery interaction, authoritative operation and user records. Interrupt before and after commit, repeat the original and a modified input with the same identity, and compare results and user IDs. Exercise retention expiry and replay after expiry with no new writes under the expired identity. |
| Audit and redaction (F-1–F-3, T-8) | Authorized operators can trace submission outcomes, access denials and recovery by a safe correlation value, actor, scope where safely known, and outcome. Record counts only for resolved outcomes. | Upload bytes, raw cells, filenames, secrets and session material never appear in logs or telemetry. Audit delivery failure is surfaced through the existing operational failure route and cannot turn a failed create into a success or erase a committed outcome. | Retried delivery can be correlated to the original submission. The application owns import events and reuses ordinary user-lifecycle and authentication coverage where adequate. | Authorized operational view or audit sink. Exercise success, rejection, denied access, retry and sink failure. Retrieve and correlate events, then inspect captured output for seeded sensitive values and structural redaction. |

**State and data.** The processing authority owns pending work and resolves each submission once, even if the initiating view disconnects. The account and outcome decisions must remain consistent through failure. The minimum recovery result consists of an opaque submission identity, actor and scope binding, same-input comparison information, status, counts and safe correction details. It is readable by its still-authorized submitter, with sanitized audit information separately available under operational policy. The admin view may carry a non-authorizing reference for recheck, cleared on sign-out or scope change. No new shared history or raw CSV archive is required. Expire and remove recovery metadata and product-held references under the confirmed result policy. Expired references must be rejected for execution. Audit data follows the existing destination's access and deletion policy. Closing a page ends presentation state while an operation already received by the authority settles independently.

**Open gap.** Runtime and privacy owners must confirm restart and recovery support, the recovery entry point and retention duration, purge behavior, and audit destination/retention before those features or verification can be finalized. Operations must confirm an audit failure policy compatible with the commit contract. Confirm the existing UI and usable narrow/wide environments before visual acceptance.

**Lifecycle boundaries.** An active submission can settle as committed or rejected. Either outcome is terminal for that submission. Unconfirmed is a view state while the authority's outcome is unknown to the admin. A definitive rejection allows a fresh submission, and an expired identity can no longer start work. Cancellation after submission, deletion of completed imports from the UI, and account migrations are inapplicable to this create-only flow. Account deletion remains governed by the standard lifecycle.

## Non-functional requirements

- **UI quality and visual direction.** Basis is stage duty 6 and the UI guide's Light expressive starting point. Inspect the product's current components and tokens first. For a new graphical surface use light Google Gemini as the visual reference through Material 3 Expressive principles. Start with a luminous light canvas, rounded tonal surfaces, clear type hierarchy and a restrained accent for the file selection and next action. A new web UI starts light with a dark option, subject to product identity, explicit visual constraints and platform appearance conventions. Use one icon set, consistent typography and spacing scales, and a palette for both themes. Give the file picker and its state the strongest visual weight, with format guidance close to selection and a persistent, readable result region. Provide designed empty, file-selected, processing, rejected, unconfirmed and successful states. Protected errors use text and stay available while action is needed. Verify narrow and wide supported layouts without horizontal overflow, including long filenames and messages. Verify keyboard file selection, submission and recovery, visible focus, status announcements, WCAG AA text and non-text contrast, and reduced-motion behavior. Motion may clarify a state change and must have a reduced-motion equivalent. Confirm in the rendered interface in both themes with keyboard, assistive technology, contrast measurements and visual inspection. Concrete treatment and components depend on the product design system. [UI guide](../GUIDES/platforms/ui.md#light-expressive-starting-point), [Google Design](https://design.google/library/gemini-ai-visual-design), [WCAG 2.2](https://www.w3.org/TR/WCAG22/).
- **Capacity, time and cost.** Basis is R-2 and R-4. Establish file bytes, data rows, processing and recovery lifetimes, and concurrency limits for the supported workload from the selected runtime's hard caps and a representative bounded probe. Set product limits within the confirmed hard platform limits, publish the effective upload limits, and reject overflow with no writes. Check at and immediately above each published cap and exercise contention on shared identities separately from independent imports. Record any time budgets and production workload evidence before finalizing dependent processing and recovery. No response-time SLA, throughput number or cost ceiling was supplied.
- **Integrity, privacy and recovery.** Basis is R-1–R-4. Exercise stale authority, interrupted processing, pre-commit failure, lost confirmation, replay, expiry and purge under the actual runtime. Validate account invariants through authoritative reads. Verify that protected payloads appear only within the authorized processing boundary and that audit and operator access obey the retention and visibility contract. No availability target or regulated retention period is established.
- **Compatibility and operability.** Basis is the request's additive scope and R-3. Confirm ordinary user creation and lookup still work under the supported clients and record lifecycle, with existing records and policies preserved. An account migration, a new public API and standalone import history are outside the requested scope. Concrete framework, storage and execution choices remain pending platform evidence.

## Behavior flows and replay evidence

| Flow | Sequence and state changes |
| --- | --- |
| F-1 — Submit a valid CSV | An authorized admin opens the import (T-1), selects one file and submits (T-2). The operation validates (T-3), checks live authorization and conflicts at the create decision (T-4/T-5), then returns the committed count (T-6). The admin sees the new users on an authorized read. Import outcome is auditable (T-8). |
| F-2 — Denial, correction or conflict | Access denial (T-1) stops protected actions. A file/row error (T-3), known write failure (T-4), or losing a conflict (T-5) returns a definitive rejection with zero creations by the batch (T-6/T-8). An authorized admin can submit a corrected file as a new attempt (T-2). |
| F-3 — Interrupted submission | An in-flight response becomes unavailable (T-6). The still-authorized submitter rechecks the same submission (T-1/T-7). The authority returns pending or a definitive outcome as appropriate. Once the outcome expires, recovery reports expiry and the admin checks user state before deciding on a new attempt (T-6/T-8). |

**Manual specification replay, 2026-11-21.** Independently walked the following actions from their stated prerequisites using the named rules. Expected outcomes below are derived on paper. The example model assumes an isolated scope `example-org`, an admin `admin-example` with import, standard create and user-read authority, an ordinary member `member-example`, an authorized operator `ops-example` with audit read access, and a separate user-read principal `reader-example` for the revocation case. For these fixtures only, the published columns are `email,name`, both required. The fixture accepts a nonempty name containing a comma or line break. Canonical identity is the lowercased email within the scope. The pre-existing record is `user-98`, `existing@example.test`, name `Existing User`. Other fixture identities are absent at the start of each case. Files use UTF-8 with LF, including a final LF, and are within the assumed limits unless stated. Submission names below are fixture references. The real mapped identities, schema, limits, and setup are open prerequisites under the respective requirements.

- **F-1, valid batch `import-101`.** The admin opens the import under T-1, then selects and submits `people.csv` under T-2. Its contents, with line breaks represented by `\n`, are `email,name\nada@example.test,"Ada, Sr."\nlin@example.test,Lin\n`. T-3 yields two valid records with distinct identities. T-4 commits both and T-6 reports 2 created. Independent account read-back must find `ada@example.test` named `Ada, Sr.` and `lin@example.test` named `Lin`, with distinct newly assigned IDs. `user-98` remains the same record. The fixture scope therefore contains three users. T-8 lets the authorized operator correlate completion with count 2 without either email in the event.
- **F-2, invalid file `import-102` and correction `import-103`.** Under T-1/T-2 submit `repair.csv` with `email,name\nada@example.test,Ada\nADA@example.test,Other Ada\nexisting@example.test,Overwrite\nlin@example.test,Lin\n`. T-3 flags lines 2 and 3 as same-file identity conflicts and line 4 as an existing identity conflict. T-6 reports 0. An authorized read finds only `user-98` with its original name. The admin can replace the file and make a fresh submission under T-2, using `email,name\nada@example.test,Ada\nlin@example.test,Lin\n`. T-3/T-4 now permit both writes. T-6 reports 2, and an authorized read finds the named Ada and Lin records as well as unchanged `user-98`.
- **F-2, denied submit.** `member-example` tries to submit the same valid content to the import invocation path in `example-org`. T-1 rejects before creation or disclosure. The member observes denial and the authorized admin's separate read still finds only `user-98`.
- **F-2, physical record locations `import-107`.** Under T-1/T-2 submit `lines.csv` with `email,name\nada@example.test,"Ada\nSr."\n\nlin@example.test,\n`. T-3 consumes lines 2 and 3 as one valid record and skips physical line 4. Lin's record starts on line 5 and lacks a required name. T-6 reports line 5 and field `name`, with zero created. An authorized read still finds only `user-98`.
- **F-2, conflict after validation `import-104`.** Submit the original `people.csv` through T-1/T-2. With T-3 complete and before the batch's create decision, the same authorized admin uses the standard create surface to create `ada@example.test` as `Manual Ada`. T-5 makes the already committed individual create the winner and rejects the import in full. T-6 shows 0 created by import. The independent lookup must show `Manual Ada` and `user-98`, with no `lin@example.test`. Reaching this order in a real test requires control of the create boundary and an accessible standard-create surface.
- **F-3, lost confirmation `import-105`.** T-1–T-4 admit and commit the original `people.csv` before the confirmation is lost. Under T-6 the admin sees an unconfirmed outcome. Still authorized and within retention, the admin rechecks `import-105` under T-7 and recovers 2 created. Repeating that identity and the original input leaves both committed user IDs unchanged. Reusing the identity with `email,name\nlin@example.test,Lin\n` is rejected under T-7. The final independent read still shows two new records with original attributes plus `user-98`.
- **F-3, revocation before create `import-106`.** Begin the same valid upload with T-1 authority. After T-3 and before the T-4 create decision, assume the product's authorized access owner revokes the admin's create permission. T-1 denies the write and subsequent protected result lookup. Only `user-98` remains, observable by `reader-example` under the unchanged user-read grant. Actual revocation and observation procedures require the product access model.

## Submission

**summary** — Defined admin-only CSV upload and verified-on-commit bulk creation as a proposed specification. Assumptions are a single-file admin UI, the documented CSV profile, standard account creation rules, rejection of the entire batch on any validation or identity conflict, and recoverable authoritative results scoped to the original submission. Proposed visuals follow the existing product identity where available. The account schema, target authority and UI, platform bounds, recovery retention and audit contract remain open. No conflict is established by the supplied evidence. Compatibility of atomic creation with any required external lifecycle effects remains open and gates dependent writes. Independent format and interaction specification work can proceed. The flow examples were walked against the written rules. Product behavior and all checks remain unverified.

**primary** — R-1 (admins can upload a CSV) and R-3 (the submission bulk-creates users). Product acceptance may accept one primary requirement left unverified only with a passed lower-layer test for that requirement. No such pass exists here.
