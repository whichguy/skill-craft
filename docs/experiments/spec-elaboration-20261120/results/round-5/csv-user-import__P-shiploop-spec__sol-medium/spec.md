# User Administration

## Scope and evidence

The 2026-11-20 request, under “The incoming request,” is the product authority: “Let admins upload a CSV to bulk-create users.” An authorized admin submits one file for one managed user scope and can verify that the resulting users exist in that scope. Access, upload and creation trace to the primary requirements below. Feedback and recovery make those outcomes observable. Scope excludes updating or deleting users, importing passwords or privileged roles, and scheduled or unattended imports.

The request and the ShipLoop guides were inspected. This standalone stage has no earlier spec, discovery or research result, selected baseline, repository, deployed target or reference product. Existing admin permissions, account rules, workflows, visual identity and runtime capabilities are unknown. The contracts below preserve the applicable rules once identified. Product defaults are assumptions recorded in Submission. The worked cases use synthetic data and are evidence of a specification walkthrough only. Later discoveries that contradict a material assumption go through ShipLoop's existing correction or incomplete route with the affected clauses, original basis and new evidence. Preserve unrelated clauses and invalidate affected checks.

## Requirements

### R-1 — Authorize the admin for the target scope

**Basis and delta.** 2026-11-20, “The incoming request,” “Let admins.” Adds an admin import action. Preserves ordinary user-creation authority and scope isolation. See also [current-system baseline handoff](../GUIDES/current-system-baseline.md#planning-and-review-handoff) and [service verification](../GUIDES/service-discovery.md#verification). No authority mapping or existing workflow was observed. Implementation and target checks are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| R-1.a | A signed-in admin with current user-create authority for the managed scope can open and submit the import. | An unsigned caller or signed-in non-admin cannot use the action, receive validation results or create users even through direct submission. | An admin for only another scope has the same restriction for the requested scope. | Admin UI, receiving boundary and authoritative user read. Exercise permitted and denied identities against the same input and compare both scopes before and after. |
| R-1.b | The authority at the point of protected processing and final commit governs the operation. | Revocation effective before commit prevents every write in the batch. When authority cannot be established, deny processing or commit. | Revocation following commit preserves the committed users. Access to any subsequent protected result requires current authority and the originating admin and scope. | Receiving boundary, delayed-response UI and authoritative users. Change the grant before commit and after commit but before result access, and verify the denied surface and user state. |

**State and recovery.** The product's identity and authorization owner governs the signed-in actor, their user-create grant and the managed scope. Derive and validate the scope from authenticated context and current authorization. File contents and client state grant no authority. The write and any result disclosure obey effective policy at their respective boundaries. A denied admin can try again through the normal flow after permission is restored. On account or scope switch, clear the old import view and suppress its pending responses. An existing grant writer and access-management policy own revocation and session lifecycle.

**Open gap.** Identify the actual admin permission, scope boundary, supported way to enforce revocation at commit and result release, and authorized identities for verification. Product/identity owner resolves the role and scope during discovery or initial planning. Integration verifies enforcement on the real boundary. These gaps gate live access and mutation, while CSV examples can be specified independently.

### R-2 — Upload and validate one CSV

**Basis and delta.** 2026-11-20, “The incoming request,” “upload a CSV.” Adds a file picker, supported-format instructions and validation. Preserves ordinary rules for admissible user data. See [behavior model](../GUIDES/behavioral-requirements.md#behavior-model) and the input contract below. No user schema, upload mechanism or quotas were observed. Implementation and checks are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| R-2.a | The admin can select one file and explicitly submit it from user administration. Selection displays the filename and allows replacement or clearing before submission. | A read or transport failure with a known unreceived submission shows how to select or submit again. | No selection leaves submission unavailable. Replacing the file submits only the latest selection. Selection or clearing alone creates zero users. | Admin UI and receiving boundary. Use keyboard and pointer paths, select and replace distinguishable files, inspect the actual submitted bytes and read authoritative users. |
| R-2.b | The service understands the CSV format and validates the required headers, record shape and each value before changing users. | Unreadable encoding, malformed quoting, missing, repeated or unsupported headers, wrong field count, invalid required value or an exceeded limit reject the batch. Provide a file-level reason or a logical record number and field when attributable. | A header with zero data records is rejected. A single permitted record is accepted. A file exactly at each published maximum is eligible, and the next byte or logical record is rejected when the other limit is satisfied. | Admin result and receiving boundary. Use byte-specific fixtures and independently read users after each rejection. Verify ordinals and reasons against the submitted payload. |

**Input contract default.** One UTF-8 comma-delimited file with optional leading UTF-8 BOM, a required header, and LF or CRLF record endings, with or without a final line ending. Double quotes delimit fields and a doubled quote escapes a quote. A quoted record spanning lines has one logical record number. Header comparison is exact and case-sensitive, with each supported header appearing once and all required headers present. A physical blank data line is an empty record and fails required-value validation. A final record terminator alone does not add a record. Use headers to map values and enforce content validation regardless of extension or media-type claim. Number the header as logical record 1. File-format errors with no reliable record location get a file-level diagnostic. Show the supported headers, limits and accepted format before submit. Default to a required `email` column when ordinary creation supports it as sufficient input. Additional required supported fields, identity normalization, field constraints and defaults follow confirmed account rules. Reject unsupported columns, including credentials or privileged role inputs.

**State and recovery.** The initiating admin's active view holds the selected file reference and filename locally until clear, replacement, submission completion, navigation away, logout or scope switch. The admin selects the next file for correction. The import authority reads the upload only for the active attempt within the authorized scope. Release raw bytes and parsed input at the terminal outcome or attempt expiry, apart from values required in created accounts. Keep them out of ordinary history, logs and other clients. Bound incoming bytes, record count and active processing to the documented runtime limits. Superseded local selections cannot replace an already submitted file or receive its status in a new scope.

**Open gap.** Product owner confirms the schema, instructions and accepted ordinary field values. Runtime owner sets and verifies byte, record and field limits, request expiry and cleanup against the selected runtime before dependent planning. The real upload contract and maximum-bound checks remain unready. Fixture-based format work can proceed under the stated input assumptions.

### R-3 — Commit new users as a batch

**Basis and delta.** 2026-11-20, “The incoming request,” “bulk-create users.” Adds one submission that creates multiple ordinary user records in the managed scope. Preserves ordinary source-of-truth identity rules, fields, permissions and account lifecycle. See [state and data assessment](../GUIDES/requirements-definition.md#state-and-data-change-assessment) and [service verification](../GUIDES/service-discovery.md#verification). No actual account store, dependencies, effects or failure boundaries were observed. Implementation and checks are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| R-3.a | A valid batch commits one new ordinary user for each data record with the submitted supported values and ordinary defaults. All can be retrieved through normal authorized user management after confirmation. | Invocation that fails definitively before commit leaves zero created records and produces no account lifecycle effects for the failed batch. | The batch changes only the intended scope and submitted identities. A one-record batch has the same semantics. | Successful import result and ordinary authoritative user management. Compare exact identities, fields, role/status and neighboring records before and after. Inject a failure between staging two records and final commit and check both state and applicable effects. |
| R-3.b | Conflict-free rows can be committed together by an authorized admin. | A duplicate within the file or an identity already reserved by ordinary account policy rejects the entire batch. Report affected input record numbers where known, with no private details about other users or scopes. | If competing writes claim the same identity, at most one can commit it. A losing batch leaves zero new users even if some of its rows were otherwise valid. Replaying a committed file creates zero additional users and updates none. | Import result and authoritative user gathering across relevant writers. Race imports and ordinary creation, replay a committed file, and verify exact final records plus the loser’s disjoint identities. |

**State and recovery.** The existing user authority owns the targeted account records and the ordinary uniqueness domain, which may extend beyond the admin's read scope. Before commit all candidate identities must be available under that policy. After commit the complete accepted set is authoritative, with uniqueness and scope boundaries intact. Conflicts with another admin or ordinary writer resolve at the final authoritative write. An initial validation result cannot reserve an identity. Rejection rolls back the full batch. Committed users follow the ordinary account retention, deletion and recovery lifecycle. An admin with a definitive rejection may correct the source file and submit anew. An unconfirmed outcome follows R-4.

**Open gap.** Confirm the identity key and uniqueness scope, normalization, default non-privileged access, activation and invitation behavior, any effects of ordinary creation and their recovery rules, and the capability for a batch commit across actual writers. Product owner and runtime owner resolve these before dependent design. An external account dependency or an ordinary mandatory effect that cannot coexist with the batch guarantee would require explicit reconciliation through the correction route. No new invitation, credential or privilege policy is authorized here.

### R-4 — Report the outcome and recover from interruption

**Basis and delta.** 2026-11-20, “The incoming request,” “upload a CSV to bulk-create users,” implies an admin-visible distinction between sending a file and creating its users. Adds import feedback and correction. Preserves ordinary authorized reads and recovery paths. See [interaction design](../GUIDES/behavioral-requirements.md#actors-channels-and-state-ownership) and [service verification](../GUIDES/service-discovery.md#verification). No interface or runtime execution/diagnostics facilities were observed. Implementation and checks are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| R-4.a | Show processing while the operation is outstanding and show the created count only on authoritative commit confirmation for the active attempt. | A definite rejection reports no users created and gives an actionable file, record or operational reason. Retain the message in the active view until dismissed, replaced by a new attempt or the view ends. | Repeated submit while that view's attempt is pending does not start a second attempt. Late results cannot overwrite a newer attempt or another session or scope. | Admin UI and receiving boundary. Control timing, compare visible counts with committed identities, inspect submission count and exercise a late result after leaving or switching. |
| R-4.b | A still-authorized admin can reconcile an unconfirmed outcome through ordinary user management and can retry with source rows known to be absent. | Loss of confirmation shows that the outcome is unknown and directs the admin to check users before submitting again. Never report zero or success without the corresponding authoritative result. | A reconnect or reload alone provides no retrospective confirmation. An overlapping retry is still subject to the authoritative conflict invariant in R-3.b. | Admin UI and authoritative read. Lose the response before or after commit, recover via a fresh read, and verify that retry and late responses cannot produce duplicate users or false confirmation. |
| R-4.c | The application owner can distinguish submission rejection, commit and known execution failure through authorized operational evidence with safe correlation. | Loss of diagnostic delivery cannot turn an actual commit into a reported rejection or mask the original business failure. | CSV content, filenames, raw user fields and credentials do not appear in diagnostic events, including on errors. Access-denied diagnostics do not disclose target data to the caller. | Existing owned diagnostic destination if available. Retrieve outcomes with approved operator authority, use synthetic sentinel values to inspect redaction and exercise sink failure. |

**State and recovery.** The user authority owns the commitment decision. The view owns transient empty, selected, pending, rejected, confirmed and outcome-unknown presentation. Allow reads only for the originating authorized admin in the active scope. A response belongs to that attempt and authorization context. Clear result details on logout, scope switch and view teardown. The outcome view shows counts, logical record numbers and safe reasons. Ordinary user management remains the authorized place to inspect account data. No new import history, job continuation promise, cancellation after submit or external notification channel is in scope. Leaving or closing the view does not establish cancellation. The application operations owner controls diagnostic access and purges metadata under the verified existing retention policy. Relevant metadata is limited to safe correlation, outcome, safe reason category, timing and any permitted aggregate count. No raw personal data is needed for diagnostics.

**Open gap.** Confirm the actual normal user read, consistency at read-back, supported attempt expiry and cleanup on interruption, log ownership/coverage, safe retrieval and retention. The application owner checks those during planning. The integration and operations owners verify recovery and event behavior on the selected target. Provider-owned event coverage stays unverified pending the selected destination and authorized operator.

| Flow | Order and observation |

| F-1 — Submit and confirm (R-1–R-4) | Current authorized admin opens user management, selects a file, submits, and sees processing. The authority checks current permission and validates the file. The admin reads the created users through ordinary user management. |
