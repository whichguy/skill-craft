# Grok Bot for Salesforce

## Scope and baseline

The source of product intent is the 2026-11-20 incoming request, “Create a Grok bot in a Salesforce development org.” The two direct outcomes are a usable bot entry in the intended development org and a user receiving a real Grok reply there. Authorized Salesforce users, the Salesforce administrator and the xAI team owner are the actors. The working scope is private, interactive text Q&A with one independent question per turn. CRM grounding and actions, attachments, public channels, saved or shared conversations, automated work and production rollout have no basis in the request. Grok denotes the provider/model, with no parity obligation to the public Grok app.

This is the first specification supplied to this standalone stage. No prior spec, discovery, research result or selected baseline was supplied. Target org assets, settings, roles and existing behavior are unknown. The source observations below establish documented capabilities, while the audiences, interaction rules and delivery defaults are proposed product decisions. Preserving unrelated org configuration and data applies even if later inspection finds an existing bot or a naming collision.

**Provider-boundary contract.** Salesforce authorizes admission and controls the approved endpoint/model configuration. xAI authorizes execution with the current team credential and is authoritative for model output, entitlement and throttling. Every admitted send starts fresh. No bot answer cache, retrieval of past answers or incremental sync. Completion means a terminal successful answer with nonblank user-facing text, consumed by the originating view. A failed or interrupted call may already have reached xAI. The provider key can be revoked or rotated by its owner, with new calls subject to the provider's effective configuration. No durable completion or webhook lifecycle applies to a foreground turn.

**State and recovery.** The Salesforce admin owns the selected endpoint and model configuration, which users cannot edit from the bot. The provider team owns key entitlement, quota and revocation. The approved configuration is the invariant from setup through verified operation. Conflicting admin changes require read-back and reconciliation before reopening use. Existing authorized provider/account state is read where needed, with no provider account or billing mutation by the bot. A retired key is disabled or revoked by its owner after replacement is validated, or immediately if compromised. On a configuration mismatch, keep the bot unavailable until the correct target and model are confirmed.

**Open gaps.** The requester/provider owner identifies the xAI team and admissible synthetic-only data policy, confirms billing or available credits, model entitlement and limits, and provisions the secret through the approved admin path. The implementation owner confirms the model, selected endpoint, timeout and safe size limits before enabling live use. The release and provider owners also confirm an authorized observation path that independently ties each live browser send to its upstream model and answer. Provider-side synthetic request logging, where permitted and available, is one candidate. If no permitted route proves that connection, C-05 remains unverified. These gaps gate live inference or its verification as applicable. Controlled reply handling can proceed with synthetic fixtures.

They add an ephemeral composer and answer view with no existing behavior to migrate. [G2], [S4] and [X1] support the interaction and completion design. Timing, host lifecycle and browser behavior are unobserved. Implementation and browser checks are pending.

| Case | Positive | Failure | Boundary | Consumer surface and confirmation |

An over-limit input gives a length error without contacting xAI. | Validate at the server boundary too. At the selected input cap, admit otherwise-valid text. At one unit above, reject without sending. A rejected local validation keeps the draft and any previous completed pair. | Exercise the composer with keyboard and pointer and call the server entry with invalid input as an assigned user. | C-09 | Clear empties the idle view. Reloading, leaving the bot view or signing out and returning starts a fresh view. **State and interaction.** The signed-in view owns the draft, submitted text, current answer or error, pending attempt identity and theme choice. Only that view receives its text/state. Idle blank is initial, pending owns a frozen prompt, success owns one question/answer pair and an empty composer, and failure owns an editable prompt and recovery message. Idle invalid input can show validation alongside a previous result. The first matching terminal result wins; ignored completions cannot resurrect a cleared or closed view. Clear resets content, while reload or departure removes all view state. Browser state is transient and bounded to one draft/turn, one pending attempt and one displayed outcome. The browser calls Salesforce asynchronously from the user's point of view. An accepted submission signals waiting, and a matching terminal result changes the visible status. Preserve keyboard position or return it to the composer if the focused control becomes unavailable and the user has stayed in the bot controls.

**Open gaps.** The implementation owner determines the input unit and limit, output limit, request timeout and capped fixture values against Salesforce and selected xAI limits before limit-dependent implementation and system-test. The org browser verifier confirms view teardown, re-entry and focus on the selected Lightning shell. The interaction model and cases independent of the limits can proceed.

**State ownership and retention.** Salesforce owns the protected credential and durable non-secret feature metadata/configuration. An authorized administrator manages them. The bot client receives neither credential values nor raw upstream response data. Remove feature-owned credential/configuration on decommission and disable the provider key. Prompts exist in the active view, request-processing memory and the provider boundary. Owner-visible local content is dropped on clear or view exit and excludes application persistence and logs. The provider's response retrieval/history must be off. xAI's documented default audit retention is 30 days with automatic deletion. Actual team terms or settings can differ, including zero data retention. Local Clear has no effect on provider audit retention. No app-sent persistent user identifier is needed for the synthetic development turn.

**Owned observation.** The bot reports submission outcomes in the active view, and the owner of the integration may use Salesforce/xAI administrative facilities within their access. Salesforce owns sign-in events and deployment status, xAI owns infrastructure response and key/team events. During target readiness, admins confirm available authorized event coverage and retention with a synthetic login/outcome/configuration check and redacted evidence. The bot has no independent notification, event stream, log sink or durable audit obligation.

**Open gaps.** Before live use, the org and xAI admins confirm that the selected org and team accept synthetic prompts, confirm actual provider retention and relevant diagnostics/access settings, and provide a sanitized configuration observation. If provider policy or required telemetry implies broader payload, persistent identity or retention, the affected live path stays unready pending the requester's decision. Synthetic UI and controlled boundary work can proceed.

## Non-functional requirements

- **Interaction and visual quality (R-4, C-12).** Start light and offer a dark option scoped to the bot. Use the light Google Gemini visual direction with Material 3 Expressive principles as a reference for airy composition, tonal rounded surfaces and purposeful motion, within Salesforce Lightning conventions. Give the question, legible answer and primary Send action a clear hierarchy. Use one icon set, consistent spacing and type scales, and semantically consistent palettes across both themes. Design the empty, pending, answer and persistent error states together. A distinct, calm status area next to the composer communicates progress and recovery. Switching themes keeps the active turn and draft. Scope changes to the bot surface. Inspect the rendered states in both themes in a real Lightning browser. [G2], [S5], [U1]
- **Access and reflow (R-4, C-12).** Visible and unobscured keyboard focus, accessible names and status announcements, WCAG 2.2 AA contrast (4.5:1 for normal text, 3:1 for large text and required non-text indicators), and motion only to explain changes with reduced-motion support. Verify at 320 CSS pixels of available bot content width and a 1280 CSS pixel wide layout, with no horizontal overflow or loss of actions in the bot area, including a long unbroken answer. Test keyboard and screen-reader status, contrast, both appearances and reduced motion. Confirm host feasibility at the narrow width during target UI readiness. [U2]
- **Capacity and failure containment (R-3/R-4, C-06–C-09).** Only one call per admitted send and one pending turn per view. Use finite timeout and bounded input/output sizing with serialization and temporary-memory headroom under Salesforce and model limits. The Salesforce synchronous ceilings include 100 callouts and 120 seconds cumulative callout timeout per transaction, with a 6 MB callout payload limit that also counts towards heap. These are ceiling evidence. Selected prompt and output limits, timeout, expected concurrent load and any spend ceiling remain unresolved with the implementation owner and provider owner before live enablement. Verify maximum accepted and first rejected input, largest configured response, delayed failure, count of attempts and provider throttling. No throughput, availability or latency SLA was requested. [S6], [X1]–[X3]
- **Security, privacy and operability (R-1/R-2/R-5, C-01–C-04, C-10/C-11).** Verify against assigned and unassigned users, controlled revocation and credential failures, and the recorded candidate/target. Confirm that client/network output and application diagnostics contain no secrets or transcript persistence and that rollback withdraws feature access and preserves unrelated org state. This development scope uses synthetic data. No production compliance, migration, backup, mobile-native or cross-browser support promise is inferred. [S1]–[S3], [X4]
