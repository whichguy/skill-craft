# Grok Bot for Salesforce Architecture

## Decisions

These decisions are the starting architecture for the standalone spec. Tenant-specific bindings and live feasibility checks remain open in [the product specification](spec.md).

### AD-1 Use a Lightning custom tab and native Salesforce delivery

Build the bot as a Lightning Web Component exposed as a custom tab. Deliver the tab metadata and make the tab reachable in the selected existing Lightning app. Use supported Lightning navigation. After org binding, choose collision-free API names and record the actual tab API name and generated entry path. The target org determines the supported metadata API version and deployment checks.

Deploy the feature-owned Salesforce metadata with rollback on deployment error. Verify terminal success and candidate identity separately from secret provisioning and access activation. Grant access only to the intended users after the setup checks, using a feature-scoped permission set. A failed assignment or credential configuration is reconciled separately from metadata deployment. The release owner can withdraw the feature grant and reconcile the scoped metadata delta if containment is needed. Salesforce owns deployment progress and final status.

This is a lower-overhead fit for an authenticated feature in the existing shell than maintaining a separate app surface or external host. The selected app, supported version, naming and effective navigation/permission setup must be confirmed in the actual org. [Custom tabs and navigation](https://developer.salesforce.com/docs/platform/lwc/guide/use-config-custom-tab.html), [Deployment status](https://developer.salesforce.com/docs/platform/api-metadata/references/file-based-calls/meta-checkdeploystatus.html), [Deployment result](https://developer.salesforce.com/docs/platform/api-metadata/references/result-objects/meta-deployresult.html)

### AD-2 Authorize and call the provider from Salesforce

The component uses a non-cacheable imperative Apex entry point. Grant only intended users access to the Apex class and the External Credential principal through the feature permission set, including the necessary User External Credentials object permissions where applicable. Backend validation and the platform grants guard the provider boundary on each invocation. This path has no CRM object reads, CRUD, field-level data handling or record-sharing dependencies.

Use a modern Named Credential targeting the approved xAI HTTPS base URL and a Custom authentication External Credential with a named principal. An admin populates the encrypted principal parameter through Salesforce Setup. Use a custom Authorization header with the Bearer scheme and a reference to the credential parameter, with generated authorization disabled and header formulas enabled. Ship credential metadata without the secret. The endpoint is deployment configuration and the model is server-owned non-secret configuration. The browser has no role in selecting them. This uses Salesforce's protected callout path and avoids a separate gateway or key store. The org administrator and provider owner verify principal setup, actual outbound auth and rotation on the selected route using sanitized observations. [Salesforce custom authentication](https://help.salesforce.com/s/articleView?id=sf.nc_custom_headers_and_api_keys.htm&language=en_US&type=5), [Apex security](https://developer.salesforce.com/docs/platform/lwc/guide/apex-security.html), [Imperative call](https://developer.salesforce.com/docs/platform/lwc/guide/apex-call-imperative.html)

### AD-3 Use a foreground xAI Responses request

Use HTTPS POST to `/v1/responses` with JSON containing the configured Grok model and current text input, explicit `store: false` and an output cap. Use the non-streaming create-response path and omit tools, prior response IDs and provider-side conversation state. Omit fixed instructions initially. Before activation, verify that the selected team key and model support this path, and confirm request/response size, model output, timing and token constraints against the actual constraints of that route.

A single Apex callout is sufficient for the foreground interaction. A successful HTTP status also needs a valid completed provider response. Project nonblank assistant `output_text` from response message items in provider order. Discard reasoning and other provider metadata in the consumer response. Map failures to safe product outcomes before returning to the component. Treat an incomplete or pending provider response as a failure for this path. The client ties a completion to its live view and attempt. The stateless foreground design has no worker, broker or persisted operation record. Confirm the user-visible deadline and payload limits in the target before enabling the path. [Responses contract](https://docs.x.ai/developers/rest-api-reference/inference/responses), [Storage control](https://docs.x.ai/developers/model-capabilities/text/generate-text#disable-storing-previous-requestresponse-on-server), [Output cap](https://docs.x.ai/developers/model-capabilities/text/best-practices#output-length), [Apex governors](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-gov-limits.html)

### AD-4 Use Lightning design conventions with a scoped visual system

Start with Salesforce base controls and supported Lightning Design System conventions. The app surface gives primary weight to the composer and reply, with a nearby stable status region. Use one native icon family, scoped styles and semantic state colors across the light and dark appearances. Use the spec's light Gemini and Material 3 Expressive direction for typography hierarchy, tonal surfaces and considered transitions. Establish the org's SLDS theme before relying on styling hooks. Confirm actual control styling, responsive space, keyboard focus and theme contrast in the real shell. Keep styling and state within the bot component. Use its lifecycle and originating-attempt tracking to drop abandoned results. Verify how the selected shell handles navigation, including a shell that keeps components mounted across navigation.

Reusing native controls minimizes theme, navigation and accessibility integration costs. Scoped styling can fill visible gaps where the supported Lightning primitives permit it. The plan chooses concrete tokens and responsive treatments after the target check. A new UI library or separate host would add packaging and theme risk without a demonstrated capability gap.
