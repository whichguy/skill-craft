## Use cases

### U-1: A Salesforce user asks Grok a question to get a reply
Flow: Sign in to the Salesforce development org, open the bot, enter a question, submit it, and see the resulting Grok reply. If the bot is unavailable, see that outcome.
Source: request

### U-2: A returning user asks another question to get another reply
Flow: Submit another question after a prior result, reopen the bot, or use two open views. Each view shows its own outcome. A second send in a pending view is refused.
Source: implied: A bot is used more than once

### U-3: A Salesforce user submits text at the input boundaries to learn what the bot accepts
Flow: Try a blank draft, a nonblank draft of exactly 4,000 Unicode code points, and one of 4,001. The boundary draft passes input validation. The blank and oversized drafts produce validation outcomes.
Source: implied: A bot that accepts questions has input boundaries

### U-4: A Salesforce user encounters a failed request and tries again
Flow: Submit a question while Grok is unavailable or a limit prevents completion. See the failed outcome, or a timeout if the call stalls, and choose whether to retry.
Source: implied: A bot that relies on Grok must handle failed calls

### U-5: A Salesforce user without bot access attempts to use it
Flow: Open the entry point or try a direct invocation while signed out or signed in without bot access. See a refusal. If access is lost during a send, the answer cannot be delivered while access is invalid.
Source: implied: The bot lives inside a Salesforce development org

### U-6: A Salesforce operator sets up the bot for its first use
Flow: Confirm the intended development org, configure the Grok connection, grant bot access, enable service, and verify a reply with an authorized account. Missing settings prevent activation.
Source: implied: The bot must be set up in the development org

### U-7: A Salesforce operator checks or pauses service
Flow: Inspect whether service is enabled or disabled. Pause service and see a later send refused. A request already pending can finish. Enable service again when ready.
Source: implied: A live provider connection needs an operational stop

### U-8: A Salesforce operator restores service after a dependency failure
Flow: Find a recent request by its correlation reference, inspect its outcome category, correct saved settings or wait for service to recover, and verify with a new request. A failed replacement leaves the last saved settings in effect.
Source: implied: The bot depends on Salesforce and Grok being available

### U-9: A Salesforce operator introduces the bot into an org with existing data
Flow: Introduce the bot into the development org, then check that existing records and workflows remain usable. If setup fails, check that existing work can continue.
Source: implied: A development org may already contain data and automation

### U-10: A Salesforce operator returns the org to its previous release
Flow: Pause the bot, restore the prior release or remove the first release, and verify the resulting service state. If restoration fails, keep the bot out of service while recovering.
Source: implied: The development change may need to be reversed

Source: choice: U-4 avoids asking users to repair an integration they do not control

### C-106: Give the user the admitted send's correlation reference
Observable: When the bot returns a terminal result for an admitted request to an authorized view, the user can see the request reference
Source: choice: U-8 needs the user to be able to identify the affected request without sharing the question

### C-107: Expose only the enumerated fields for each diagnostic entry
Observable: For each diagnostic entry an operator can see the correlation reference, send time, elapsed time, model ID used, and outcome category. The fields exclude user identifiers, cost, token usage, HTTP bodies, and provider request identifiers because these are unnecessary for first-line triage
Source: choice: U-8 needs a minimal support record

### C-108: Categorize every processed send for operator triage
Observable: The diagnostic entry has one category from this closed list: success, output limit, credential or permission, model unavailable, billing or entitlement, rate limit, timeout, transport failure, invalid provider response, provider rejection, provider unavailable, Salesforce failure, access lost, or release withdrawn. If an upstream rejection is ambiguous it falls under provider rejection. Input validation, authorization failures before admission, disabled-service refusals, and duplicate deliveries are outside this diagnostic list because they did not enter processing
Source: choice: U-8 needs useful category coverage without revealing raw dependency messages. [xAI errors](https://docs.x.ai/developers/debugging)

### C-109: Bound the history visible to operators
Observable: Operators can look up at most the 100 most recently completed recorded sends less than 24 hours old, measured from terminal completion
Source: choice: U-8 needs recent diagnosis without indefinite retention

### C-110: Keep one recent turn visible in a bot view
Observable: A fresh view has no turn. A submitted turn shows its own question and state, and a later accepted turn replaces it. A rejected draft does not replace the prior accepted turn
Source: choice: U-2 needs the latest exchange without implying a transcript or an unbounded client history

### C-111: End browser-visible bot state when an access loss is detected
Observable: When the view learns of sign-out, Salesforce session expiration, or bot-access revocation, it removes the draft, prior displayed turn, and pending question from the view
Source: choice: U-5 needs temporary content to stop appearing after access denial

### C-112: Limit user controls to drafting and submitting questions
Observable: The user can edit a text draft, submit it, and deliberately resubmit after failure. View closure uses normal Salesforce navigation. Provider cancellation, transcript management, model selection, file upload, and tool controls are out of scope for U-1
Source: choice: U-2 needs a minimal standalone question surface

### C-113: Allow operators to inspect who has the bot-use grant
Observable: An operator can check whether a specified Salesforce user currently has bot-use access
Source: choice: U-6 needs a way to verify the result of granting or revoking access

### C-114: Keep provider selection under operator control
Observable: An ordinary caller cannot set or override the destination, stored credential, or model at send time
Source: choice: U-5 needs a direct invocation to have the same authority as the UI

### C-115: Erase the bot's development credential on removal of a first installation
Observable: Once first-install rollback succeeds, the removed bot has no configured key available to use in that org
Source: choice: U-10 needs a first-install rollback to remove its integration access without revoking an independently managed xAI team key

### C-116: Preserve existing bot-use grants when restoring a prior bot release
Observable: After rollback to a prior release, users retain the bot-use grants effective immediately before rollback
Source: choice: U-10 avoids unintentionally granting access that an operator previously revoked

### C-117: Default to a new Developer Edition org only when no authorized development org is designated
Observable: A requester-supplied development org is the only target when one is designated. Otherwise the operator can use a newly provisioned Developer Edition org authorized for this delivery
Source: choice: U-6 needs a usable default without assuming access to an existing org or a Dev Hub

### C-118: Refuse activation outside the designated org
Observable: An attempt to enable the bot in any other org leaves service disabled there
Source: choice: U-6 prevents sending development data or causing charges from an unintended org

### C-119: Limit bot operator controls to org setup and service operation
Observable: A designated operator can see the target org, inspect service state and current model, check credential presence, replace the credential, select the model, enable or pause service, inspect or change a user's bot grant, and look up recent request diagnostics. Provider billing, provider key issuance or revocation, and Salesforce deployment or rollback use their respective administration surfaces
Source: choice: U-6 through U-10 need a complete operator control inventory without duplicating provider or deployment tooling

### C-120: Require an authorized Salesforce administrator to establish bot operators
Observable: A first installation has no self-assignment path for ordinary users. A Salesforce administrator authorized to manage access can designate an operator
Source: choice: U-6 needs a first authorized operator without letting bot users grant administrative access to themselves

### C-121: Report a refused setup change
Observable: An operator whose enable, pause, grant, revoke, or connection edit fails sees that the requested change did not take effect
Source: choice: U-6 and U-7 need to distinguish a failed write from success

### C-122: Leave the effective bot-use state unchanged by repeated grants or revocations
Observable: Granting an already-held bot-use grant leaves it granted. Revoking an absent grant leaves it absent
Source: choice: U-5 requires safe retries of access changes after an uncertain administrative response

### C-123: Leave the effective service state unchanged by repeated enable or pause actions
Observable: Pausing an already disabled bot leaves it disabled. Enabling an already enabled bot leaves it enabled if prerequisites still hold
Source: choice: U-7 needs safe retries of service controls

### C-124: Preserve the last saved settings during an ordinary pause
Observable: After pause, the operator can still see the model and credential presence needed for re-enabling
Source: choice: U-7 is a service stop rather than a configuration removal

### C-125: Return an acknowledgement for a duplicate delivery without disturbing the original send
Observable: A repeated delivery of an admitted send identity receives a duplicate outcome if no higher-priority refusal applies. The original question, pending indicator, or terminal outcome stays associated with the original send
Source: choice: U-1 needs duplicate deliveries to be visible to the caller without manufacturing a second turn

### C-126: Keep the send deadline fixed after submission
Observable: Refresh, retry of transport delivery, browser reconnection, and clock changes do not extend an existing send's 60-second user deadline
Source: choice: U-4 needs one bounded wait for one logical send

### C-127: Assign an opaque correlation reference at admission
Observable: Each admitted send has a distinct reference independent of prompt text and user identity. The reference can be shown with a client-side timeout if the view received it before losing contact
Source: choice: U-8 needs correlation even for failures that occur after admission

### C-128: Record at most one terminal diagnostic for an admitted send
Observable: Multiple outcomes for the same reference never produce multiple terminal entries. A provider result received after the service deadline cannot replace the timeout entry
Source: choice: U-8 needs diagnostic counts to represent distinct sends

### C-129: Keep a provider outcome diagnosable after view closure
Observable: A closed or reloaded view does not prevent the service from recording the eventual outcome in operator diagnostics if the request was already admitted
Source: choice: U-8 needs operations to observe provider work even when the user stops waiting

### C-130: Report a withdrawn release to a still-open affected view
Observable: A view with a request pending when rollback starts shows an unavailable outcome once it detects withdrawal, or times out at the usual deadline if it receives no update
Source: choice: U-10 needs a terminal user outcome when an earlier version's answer is discarded

### C-131: Preserve the last saved org connection settings when restoring a prior bot release
Observable: After rollback to a prior bot version, the operator can see the last saved model and credential presence, subject to the restored version accepting them. If it cannot use those settings, the bot stays disabled until the operator supplies usable settings
Source: choice: U-10 avoids reviving older provider settings or bypassing a rotated key

### C-132: Remove bot diagnostics during first-install removal
Observable: After first-install removal, its diagnostic history is no longer retrievable in the org
Source: choice: U-10 needs clean reversal of the bot's optional operational data

### C-133: Accept inference only over authenticated HTTPS to xAI
Observable: If the provider connection cannot establish a valid HTTPS connection to the configured xAI service, the send fails and no prompt is sent over an insecure connection
Source: choice: U-1 needs transport protection for the question and xAI credential

### C-134: Reject text that cannot be represented as Unicode scalar values
Observable: An invocation carrying an unpaired surrogate returns an invalid text value outcome without sending a substituted question to the provider
Source: choice: U-3 needs exact text preservation at the Unicode boundary

### C-135: Treat a stale or wrong-scope send identity as invalid
Observable: An expired identity, an identity belonging to a different user or view, or a missing or malformed identity receives the invalid-send-identity outcome if the caller can reach identity validation
Source: choice: U-3 and U-5 need explicit behavior when the direct caller cannot present a valid send

### C-136: Confirm when an xAI answer declines the user's request
Observable: A usable finished Grok refusal is displayed as Grok's answer. A provider-level rejection with no completed answer follows the failure path
Source: choice: U-4 distinguishes model responses from failed requests

### C-137: Give a generic explanation for remaining provider failures
Observable: A provider rejection or invalid provider response that has no more specific feedback tells the user that the bot could not obtain a usable answer
Source: choice: U-4 needs feedback even when the provider supplies no safe or actionable detail

### C-138: Use xAI's status classes when classifying an unambiguous provider failure
Observable: HTTP 401 is a credential failure, HTTP 429 is a rate limit, and HTTP 5xx is provider unavailable. An explicitly identified access, billing, or model error uses its own category. An ambiguous 4xx uses provider rejection
Source: choice: U-8 needs consistent classification from xAI's standard responses. [xAI errors](https://docs.x.ai/developers/debugging)

### C-139: Let an operator retrieve a recent diagnostic by its reference
Observable: An authorized operator who looks up a known reference sees its entry if present. An unknown, removed, or unrecorded reference produces a no-entry outcome
Source: choice: U-8 must handle missing diagnostics after expiration or a Salesforce outage

### C-140: Do not let a client timeout substitute for an unavailable service diagnostic
Observable: If the view times out before hearing from Salesforce but the service completes by its own deadline, the operator can see the service's own outcome when recorded. The view still shows its timeout
Source: choice: U-8 needs to distinguish lost delivery from failure to obtain an answer

### C-141: Apply elapsed deadlines when a suspended view resumes
Observable: If a view wakes after its 60-second deadline with no terminal outcome accepted before that deadline, it shows timeout before accepting another send
Source: choice: U-4 needs background tabs to respect the same deadline despite browser suspension

### C-142: Start with no bot-use grants on first installation
Observable: Before the operator grants access, ordinary users cannot submit a Grok question through the new bot
Source: choice: U-6 needs deliberate development-org access assignment

### C-143: Identify where a requester can open the delivered bot
Observable: The requester receives the designated org ID and the in-org navigation needed to find the deployed bot
Source: choice: U-1 needs a verifiable handoff without fixing a product label or route

### C-144: Keep provider conversation history disabled
Observable: The bot cannot fetch or continue a stored xAI conversation from an earlier send. Provider audit retention remains subject to xAI's separate terms
Source: choice: U-2 needs standalone turns without using provider-stored conversation history. [xAI API Security](https://docs.x.ai/developers/faq/security)

### C-145: Keep Salesforce identity out of xAI inference requests
Observable: For an ordinary send, xAI receives the submitted question, selected model and generation controls, and the xAI credential needed for inference. The bot adds no Salesforce user ID, org ID, session token, record data, or diagnostic reference. Values the user types into the question remain part of the submitted text
Source: choice: U-1 and U-5 need only the data necessary to obtain the chosen model's answer

### C-146: Keep question drafts editable after input validation fails
Observable: After a blank, invalid, or oversized draft is refused, the user can correct the draft in the original view without opening a new one
Source: choice: U-3 needs a correction path within the normal interaction

### C-147: Distinguish service enablement from successful live verification
Observable: With a populated but revoked xAI key, the operator can see enabled local service state while a real verification send fails
Source: choice: U-6 needs a visible distinction between operator intent and dependency readiness

### C-148: End delivery eligibility for a send cleared after access loss
Observable: If a view clears a pending send because it detects sign-out, expiration, or revocation, signing in again or regaining the grant does not make that send's late reply appear
Source: choice: U-5 requires restored access to begin a fresh interaction

### C-149: Treat a partial answer as eligible for deliberate resubmission
Observable: After an answer ends at the output limit, the user can submit the question again by an explicit action
Source: choice: U-4 needs recovery from a short response without continuing an earlier provider conversation

### C-150: Keep a required change attributable to the designated org
Observable: If target-org access or xAI provisioning is missing, the operator can tell which prerequisite remains unavailable from setup or the verification outcome
Source: choice: U-6 needs to distinguish an org provisioning blocker from a Grok configuration blocker
