# Grok Bot for Salesforce

**Request — 2026-11-21.** “Create a Grok bot in a Salesforce development org.”

The direct outcomes are a bot accessible inside the designated Salesforce development org and a user-facing reply generated by Grok. This specification interprets “bot” as an interactive text prompt and reply for an existing authorized Salesforce user. The request names no existing interface to reproduce. The Salesforce and xAI references establish platform and provider contracts. They establish neither a selected org's configuration nor a parity target for the Grok consumer apps.

The standalone intake supplied no earlier spec, repository, discovery or research result, or selected baseline. There are no earlier clauses to reconcile. The scope is one development org. Implementation, access changes, and checks against a deployed bot are pending.

## Requirements

### R-1 — Open the bot in the development org

**Basis and change.** 2026-11-21 request, “in a Salesforce development org.” Establishes an in-org entry and access contract. Preserved behavior: no prior bot contract supplied. Salesforce page activation and authorization are documented in S1 and S2. The org and its current access state were not inspected. Deployment, permission setup, and role-based read-back remain pending.

- **Entry (C-1).** Positive: an approved, signed-in user can reach **Grok Bot** from Salesforce navigation in the designated development org and see an empty prompt composer and Send control. Failure: an unapproved or signed-out user following the entry URL gets a platform sign-in or access denial, with no usable bot controls. Boundary: the approving scope is the identified development org and named existing users. Confirm in the deployed org under both roles and a signed-out browser, using the org identity, deployment identity and actual navigation recorded at handoff.
- **Execution authority (C-2).** Positive: a user with the approved execution grant can submit from the entry. Failure: a denied caller cannot cause provider egress even through a direct request to the bot operation. Boundary: once Salesforce makes revocation effective, a subsequent request from an already-open page is denied. A previously accepted request may finish in its original live view. Granting or seeing the navigation entry alone conveys no execution authority. Confirm through the deployed Salesforce execution boundary and a safe egress observation before and after revoking the test user's effective grant.

**Domain rules left out.** Production distribution, public or guest access, new Salesforce accounts, distribution to all org users, and a mandatory Salesforce mobile app surface.

**State and data.** Salesforce owns bot entry/configuration and access assignments, operated on by the authorized org administrator. Before applying changes, identify the org ID and instance, compare intended metadata and assignments to current state, and resolve naming or permission collisions. Afterward the same org exposes the intended revision and permissions only to the approved audience. Unrelated metadata and effective grants must survive. If deploy or activation succeeds only in part, keep consumer access disabled or withdraw only the new access, inspect terminal status and read back metadata before retrying or restoring the scoped prior state. Salesforce record sharing, object permissions and field permissions are inapplicable to bot data access because the bot reads and writes no business records. Confirm with metadata and role-specific browser evidence.

**Open gaps.** The requester or org owner must identify the development org and approved consumer and deployer identities, and authorize the actual deploy and access changes before those operations. The org administrator must resolve navigation, names, org version/theme and permissions from the target at release readiness. The deployment, effective grants, and consumer journey are unverified. A person-only login or verification, if required, belongs to the org owner and is due at the gate it enables or at handoff for a consumer observation.

### R-2 — Send a text prompt and receive a Grok reply

**Basis and change.** 2026-11-21 request, “Create a Grok bot.” Establishes prompt validation, live Grok inference and truthful user-facing completion. Preserved behavior: no prior bot contract supplied. X1–X4 describe the provider interaction and error classes. S3 describes the Salesforce envelope. The target provider account, model access and observed latency are unknown. Integration and verification remain pending.

- **Submit and display (C-3, C-4).** Positive: Send on a permitted, ready view with valid text and configured credentials starts a live Grok request for that text. The view announces that it is waiting. An on-time, completed usable assistant reply appears as text in that view and Send becomes available for the next prompt. Failure: a malformed, empty, incomplete or nonterminal provider result produces a visible failure and conveys no completed reply. Boundary: a send that passes the server-side guards has one outbound attempt and each view has a single active submission (**default**). Repeat activation while pending makes no second request. A new explicit Send after completion is a fresh request. Confirm pending state with a held response, exact request-to-reply binding with distinct controlled inputs and returned texts, and provider identity with an authorized real call from the deployed org.
- **Input validation (C-5, C-10).** Positive: non-whitespace text within the effective size envelope is sent intact. Failure: empty or whitespace-only text is rejected with guidance and zero egress, including at the server boundary. Boundary: at the inclusive effective prompt limit, a valid prompt can be sent. Beyond it, Send reports that the prompt must be shortened, keeps the editable draft, and makes zero calls. No silent truncation. Check both composer and server request boundary, including encoded bytes and model context allowance for the full request.
- **Response and time bounds (C-6, C-10).** Positive: an otherwise usable completed answer at the inclusive output cap, received before the deadline, displays normally. Failure: a request exceeding the deadline, including a disconnected request that cannot complete, leaves pending with a timeout or connection message and retains the prompt for an explicit retry if the view is still open. Boundary: completion observed at or after the deadline cannot change the terminal outcome. An over-cap answer or provider-reported truncation produces an actionable incomplete-answer message and no partial answer presented as complete. Confirm with a controlled clock and provider outcomes around the effective limits, then validate the envelope against the actual org and model.
- **Provider rejection and recovery (C-6).** Positive: following an error, the user can edit the retained draft and send again when the cause permits. Failure: missing or rejected provider credentials, or model access failure, directs the user to the org administrator. Rate or quota rejection tells the user to try later or contact the administrator if it persists. A provider outage or unusable response reports the failure and permits a manual retry. Boundary: unconfigured credentials prevent outbound egress. Every failed submission ends the pending state and generates zero automatic retries. A manual retry may be processed or billed as a fresh request even if the earlier attempt timed out locally. Confirm terminal UI, draft, attempt count and secret-free error content on controlled outcomes.

**Domain rules left out.** The request leaves model tier, persona, locale, accuracy commitments and usage budget unspecified. Scope is text prompt/reply. Record access, attachments, tools, external actions, background completion, streaming and consumer Grok feature parity are outside this flow.

**State and data.** The submitting browser view owns draft, pending and current outcome. The server request holds only the active prompt/result and its routing context. xAI owns model execution and the returned status. Before an accepted send the view has no pending request. Sending snapshots the draft, clears the previous outcome, and locks that view's submission until terminal. Success clears the draft and displays the returned answer. Failure keeps the draft and displays the current error. Closing, reloading or signing out abandons the view under R-3. Provider work already sent may complete or be billed after abandonment. There is no compensating business-data write or automatic retry. The server and the browser must enforce bounded work as described here and in Non-functional requirements.

**Open gaps.** The provider account owner must authorize development usage and confirm available model, billing and quotas before live calls. Use the authorized account's eligible model inventory and target-org measurements to close the effective input byte/context ceiling, output cap and deadlines. The published platform ceilings and provider defaults do not establish safe working limits for the full encoded and decoded request, or representative Grok latency. The implementation owner is responsible for this evidence before freezing the size/timing-dependent contract, and the release verifier owns the real org-to-Grok case at consumer verification. These cases are unverified. Other UI and failure contracts can proceed independently.

### R-3 — Isolate prompt, answer and credential data

**Basis and change.** 2026-11-21 request, “Grok bot in a Salesforce development org.” Defines the privacy and lifecycle boundaries needed for that external interaction. Preserved behavior: no prior bot contract supplied. S2 and X1/X3 document credential and provider retention mechanics. No org logging configuration or provider account policy was inspected. Data boundary checks and provisioning remain pending.

- **View lifecycle (C-7).** Positive: the initiating live view shows its own draft, status and returned text. Failure: another view or user cannot read that interaction through the bot. Boundary: each view operates independently. A later accepted send replaces its current result and is independent of earlier text (**default**). Reload, leaving the page or sign-out discards the local prompt, answer and pending state (**default**). Late completion cannot repopulate a discarded or superseded view. Confirm with two signed-in browser contexts and a held reply released after a reload.
- **Prompt disclosure and retention (C-8).** Positive: before Send, the composer tells users that their entered text goes to Grok and instructs them to use approved development data. The outbound request includes the explicitly submitted prompt and inference configuration. Failure: payload, reply, raw provider errors and user details are excluded from bot logs and other users' clients. Boundary: the bot uses ephemeral draft and result state only, with no org records, browser storage, saved history, Salesforce record context or provider conversation storage. Provider audit handling still applies. Confirm with browser and server storage checks and a redacted outbound observation that can distinguish the prompt from unrelated Salesforce context.
- **Credential protection (C-9).** Positive: the approved org integration identity authenticates to Grok using a server-side secret under the administrator's control. Failure: browser responses/resources, logs, deployable source/configuration and user messages reveal no key. Missing or revoked credentials fail safely under R-2. Boundary: the credential lasts until rotation or removal. The administrator can replace the org's reference and revoke the old key at xAI. Subsequent attempts use the current configured key or fail closed. Confirm with sanitized configuration/egress observations and an authorized rotation or revoked-key case isolated to a development credential.

**Domain rules left out.** Shared conversations, durable transcripts, accounts at xAI for individual Salesforce consumers, and ingestion of customer records or regulated data. Free text may contain personal or secret data typed by a user. The notice and intended data scope do not assert automatic detection or filtering.

**State and data.** The view keeps its owner's text in memory for the interaction and clears it under the rules above. The Salesforce runtime handles it for the request and releases it at transaction end. The integration is provisioned in the target org by its administrator with a key managed by the approved xAI account owner. Two configuration edits must be serialized by that administrator and read back before use. Retire the prior key in the provider account and remove obsolete org credential material. The app asks for no provider-retrievable conversation state. xAI documents 30-day audit retention by default and an account-specific Zero Data Retention option. The bot neither controls nor promises deletion of provider audit copies on view close. No transcript or secret is deliberately retained in app diagnostics. Runtime debug settings and account-specific data handling require confirmation before live use. Check actual behavior with synthetic content and redacted evidence.

**Open gaps.** Before using the live route, the org and provider owners must confirm applicable retention, permitted development data, credential provisioning/rotation authority and any diagnostic exposure. If their policy forbids the documented provider processing or retention, the live route is unready until they resolve it. Pending that confirmation, design and controlled checks use synthetic inputs. The live data and credential checks are unverified, owned by the release verifier with org/provider owner help, and due before live data use or at the release consumer gate, as applicable.

## Non-functional requirements

- **Interface quality (R-1–R-3, C-11).** Use the guide's light Google Gemini reference and Material 3 Expressive principles for the starting appearance. Within Salesforce conventions, start with an airy light canvas, softly rounded tonal surfaces, a clear prompt/reply hierarchy and restrained accent on Send. Provide a dark option scoped to the bot, with the appearance choice held in the view unless an applicable host appearance policy governs it. The composer, primary action, status area, reply and error recovery use consistent spacing and type scales, coordinated light and dark palettes and a single icon set. Empty, loading and error states each have a deliberate composition. The reply is the reading focus when present, and the composer and recovery action remain easy to find. Exact visual treatment is pending design in the target theme. Sources [G1](GUIDES/platforms/ui.md#light-expressive-starting-point), [S4](#sources), [V1](#sources).
- **Accessibility and adaptive layout (R-1–R-3, C-11).** On the rendered Salesforce page, verify the bot region at 320 and 1280 CSS pixels, with a long unbroken reply, in both themes. Controls and text must remain usable and readable without bot-generated horizontal overflow. Verify visible keyboard focus, accessible names, keyboard Send and recovery, screen-reader announcements of pending and terminal states, and WCAG AA text and control contrast. Motion is allowed only when it clarifies a change. With reduced motion, status and progress remain understandable without the movement. The 320 CSS pixel check follows WCAG reflow. A native app or a specific unsupported host form factor is outside the scope. Sources [V2](#sources), [S4](#sources).
- **Capacity and performance (R-2, C-10).** Under the chosen model and development-org configuration, exercise the largest admitted encoded prompt and capped response, including serialization, parsing and presentation. Verify the working set stays inside applicable request/response, heap, context and time ceilings, and that quota contention produces a recoverable failure. One inference attempt per accepted send bounds ordinary per-send consumption. The effective payload and timing limits are open under R-2. The Salesforce and provider hard limits are feasibility constraints. There is no workload evidence or requirement for a latency SLA, org-wide traffic quota, per-user daily allowance, or spend target. Sources [S3](#sources), [X2](#sources), [X4](#sources).
- **Confidentiality and reliability (R-1–R-3, C-2, C-6–C-9).** On approved development access and synthetic content, verify denied egress, redaction, bounded pending state, view isolation and fresh authorization on subsequent requests. Check the lifecycle under failure and page exit. Recovery is local edit/resubmit or administrator repair. Durable recovery, persistent telemetry, and cross-org availability objectives are excluded because the app holds no durable conversation or shared workload. Sources [S2](#sources), [X3](#sources).

## Submission

**summary**

- Specified opening Grok Bot in a designated Salesforce development org and submitting a text prompt to Grok with the reply displayed in the same view. Captured access control, failures, data lifecycle and appearance criteria. The approved target, authorized identities, provider access and retention policy, and effective payload and completion limits are open as recorded under their requirements. There is no evidenced requirement conflict. A provider retention restriction conflicting with the live route keeps that route unready. Work independent of those gaps can proceed.
- **R-1 assumption.** Use a signed-in Salesforce navigation entry named Grok Bot for an explicitly granted audience using existing identities. Basis is the request's in-org scope and the platform's navigation and access model. Alternatives include a record-page placement or org-wide visibility. Revalidate with the org owner if there is an established bot entry, host convention or intended audience.
- **R-2 default.** One pending submission per open view and one provider attempt per accepted send, with explicit retry. Basis is one visible result per view, clear reply ownership and the possibility of billable duplicate execution under provider/runtime limits. Alternatives are overlapping submissions, a queue or automatic retries. Revalidate if the user asks for parallel work or retry policy and the selected provider and org limits support it. Input, output and time values remain open because the sources establish only platform ceilings and generic provider guidance.
- **R-3 default.** Independent turns with only the active view's draft and outcome retained in memory, discarded on view exit and with provider conversation storage disabled. Basis is the one-user text flow and the absence of a specified memory or sharing requirement. Alternatives include per-view multi-turn context or saved history with a retention policy. Revalidate if conversation recall is requested or applicable policy changes. Start the bot view light with a view-local dark option, per the visual guide and subject to the established Salesforce theme. An inherited appearance policy or user preference for persistent theme would prompt revalidation.

**primary** — R-1, R-2. Product acceptance can leave at most one of these unverified and only with a passed lower-layer test for it. That evidence does not itself verify the deployed journey. No product checks have run in this standalone stage.
