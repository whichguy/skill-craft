# Grok Bot Architecture

## Decisions

### AD-1 — Salesforce-hosted bot page

Use a Lightning Web Component on an activated Lightning App Page in the approved development org. Use a navigation entry in an approved Lightning app and narrowly scoped permission assignments for existing Salesforce identities. The app, page metadata names, supported API version, org theme and form factors depend on target inventory. Confirm the rendered entry and permissions with a permitted and an unpermitted identity. Preserve unrelated navigation and assignments.

An existing approved Lightning app avoids creating another app. An external site would add a hosting and sign-in boundary. An Agentforce implementation depends on an entitlement and an agent workflow that the request does not specify. For the proposed page, start with supported Salesforce controls and theme hooks. Evaluate the rendered controls and component-scoped light/dark tokens in the actual Lightning theme before selecting concrete styling.

### AD-2 — Server-side text inference

Use an imperative Salesforce page-to-Apex request and one foreground HTTPS callout per submission that passes the server-side guards, to the xAI Responses API at `https://api.x.ai/v1/responses`. Store the API key as an encrypted credential parameter on a Custom authentication named principal in an External Credential. Link it to a Named Credential and use a formula-backed `Authorization: Bearer …` header. Provision the secret separately from deployable metadata. Grant access to the Apex entry point and principal only to the approved existing users. Validate the input server-side before egress. Verify the actual custom header configuration by an authorized inference check with secret-free evidence.

Use the selected text Grok model with the submitted prompt as its text input, `store: false`, non-streaming foreground completion, and no conversation ID or tools. Use the completed assistant message's text. Treat an incomplete result as failure. Revalidate the precise request and response contract against the selected model. Size the request, answer and decoded working set inside the Salesforce envelope and model limits. Browser page memory holds the visible interaction. A server transaction handles one request and releases its working state at completion. The org and provider own their respective authorization and configuration. The operative limits and model remain open in the specification.

The browser-direct alternative would expose the integration credential to the client. A durable job or deferred polling would require result ownership and cleanup, including an agreement about provider storage. Reconsider the foreground route if measured inference cannot fit the org and browser deadlines. Reconcile any change that affects the consumer contract before dependent work proceeds.
