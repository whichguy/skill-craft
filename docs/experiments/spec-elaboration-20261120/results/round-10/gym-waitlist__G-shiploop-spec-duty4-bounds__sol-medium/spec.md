# Class Booking App

## Basis and scope

**Request source**, 2026-11-21, “The incoming request” in “Specify: ShipLoop's spec stage, run on its own”:

> Add a waitlist to our class booking app so full classes don't turn people away.

**Evidence available.** The request identifies an existing class booking app and full classes as the problem. The standalone stage provides no earlier specification, repository, discovery, research, selected baseline, or reference product. No product surface was inspected. Normal booking, capacity, eligibility, and class lifecycle rules are preservation obligations. Their details are unknown. Waiting without a confirmed place, reconsideration when a place opens, and the supporting member controls below are inferences from the request. No parity claim is made.

**Outcome trace.** “Full classes don't turn people away” maps to R-1 (join and confirm enrollment). “Add a waitlist” maps to R-1 (record demand) and R-2 (give waiting members a route to a newly available place). R-3 supports both outcomes by keeping member intent and status accurate. The scope is the existing class booking journey for a single class occurrence at a time.

## Requirements

Add a way for an eligible member to join the waitlist for a full, otherwise bookable occurrence. Existing screens, identities, eligibility conditions, and booking results are unobserved. With an uncertain response, the member reads back current status and can safely retry the same intent under R-3. Occupancy and availability are sourced from the existing booking authority.

If required, the ceiling is governed by TC-12. Membership tiers and eligibility exceptions come from the existing booking policy.

**State, authority and recovery.** Targets are the occurrence's capacity, active entries for that occurrence, and the relevant member's existing booking identity. Only the booking authority confirms a place. Before allocation, a place must be bookable by the policy and the entry must still be active and currently eligible. After successful conversion there is one confirmed booking for the pair and no active entry. Coordinate mutations across all writers of confirmed occupancy and active eligibility. Repeated, delayed, and simultaneous inputs must converge to the same valid outcome for a given committed change. If processing continues after the initiating response, the app owns recovery without depending on the member keeping the view open. The recovered outcome is subject to current capacity and authorization. A successful withdrawal before allocation makes that enrollment ineligible, while an already committed booking remains subject to ordinary cancellation rules.

**Open gaps and domain bounds.** Product owner decision before dependent allocation design and verification: who gets the next opportunity, including ties and ordinary-booking competition, and whether the member must actively claim or may agree to automatic booking. If the chosen model reserves a place for a claim, a finite claim deadline is required to release an unclaimed place. The value and any earlier effective booking close are open. TC-13 defines the observable boundary if reservations apply. The request supplies no basis for a duration. A mode without reservations needs no claim deadline. Discovery must establish which existing events actually reopen capacity, current consent/payment effects, current booking deadlines, and every competing capacity writer before verifying exact outcomes. External notification channels, visible queue position, staff overrides, and new booking or billing policies are outside the specified delta.

**State, privacy and lifecycle.** The app owns active enrollment keyed to the booking identity and occurrence. The member application receives only the current authorized member's status and class information already permitted by booking. Client presentation state lives in the current interaction and is discarded on navigation or identity change. Temporary request context never confers booking or membership authority. The actual membership survives interruption and is read back under current authorization. No new identity or contact data is needed. ## Behavior model

Within the app, a member uses the existing booking view to request a change and read authoritative status. Capacity and lifecycle changes originate with the existing booking authority. Waiting, confirmed booking, and a pending UI action are distinct facts. An ended enrollment has no allocation rights. A later join is a fresh enrollment subject to R-1.

| Flow | Transition, guard and effect | Recovery and mapped cases |
| --- | --- | --- |
| F-1 / R-1 | **T-1** Join. For an authorized, eligible, unbooked member in an open full occurrence, absent active entry → active. **T-2** Repeat join resolves to the existing active entry. If guard fails or an ordinary booking choice is available under R-1 and R-2, leave state intact and return the authorized current outcome. | Read back after an uncertain result. TC-1–TC-4, TC-10, TC-12. |
| F-2 / R-2 | **T-3** Existing authority makes capacity bookable. Recheck lifecycle and eligibility, then apply the selected allocation policy. Details beyond these guards are open. **T-4** Valid allocation commits booking and ends the active entry. If any guard fails, leave booking unaffected by that attempt and recover from authoritative status. | Read back a committed booking or reconcile live state before retry. TC-5–TC-7, TC-13 if applicable. |
| F-3 / R-3 | **T-5** Authorized leave ends the targeted active enrollment, or returns its current result if already ended. An existing booking is handled by ordinary cancellation. **T-6** Closure or cancellation ends allocation rights. **T-7** The authorized member reads current state, or receives an access/unavailable result. **T-8** Retention expiry removes or de-identifies data in the applicable scope. | Suppress stale results and recover from fresh status. Cleanup failure follows TC-11. TC-8–TC-11. |

## Service boundaries

- **Member interaction ↔ booking application**, R-1 and R-3. Every protected read and change uses current booking authority. Cached display may be stale and gives no permission to write or show protected data after revocation. Read back the affected occurrence and own status after uncertain outcomes while leaving unrelated occurrences and identities untouched. A delivery acknowledgment proves receipt only. Success requires authoritative confirmation. An older result cannot replace newer confirmed state or cross identity scope. Incremental event cursors and live connections are inapplicable to the specified request/response and status-read contract.
- **Booking capacity and lifecycle ↔ waitlist behavior**, R-2 and R-3. Existing booking authority owns occupancy and lifecycle, and the waitlist evaluates latest applicable values before allocation. Each change applies to the affected occurrence and member scope. Delayed information cannot reinstate an ended entry or consume capacity that is gone. If actual completion is asynchronous, the runtime owner must identify the authorized processor, how responsibility survives interruption, and how abandoned work is reconciled before accepting that design. No external notification service boundary is established.
- **Owned event coverage.** The booking application owns observable join, withdrawal, guarded rejection, allocation outcome, retry/recovery, and cleanup failure where those actions apply. Reuse adequate coverage in the actual application. At system verification, retrieve events for a scoped fixture through the existing authorized operational surface, reconcile them to authoritative outcomes, and check redaction and that an ordinary diagnostic sink failure does not masquerade as booking failure or success. Existing destination, access, required audit policy, and retention are unresolved. Provider login events are outside this feature's ownership.

## Submission

**summary**

The spec defines entry for a full class, use of newly available capacity, and private status, withdrawal, and recovery. The entry/status rules can be reviewed independently of the allocation choice. Actual integration depends on access to the booking baseline. Allocation, its exact oracle, and any reserved-claim timing remain open pending product policy and runtime evidence. Retention and any runtime-driven enrollment ceiling also remain open. No material conflict is evidenced in the supplied sources.

- **R-1 default assumption.** One active entry per booking identity per occurrence. A waitlist represents a member's intent to attend an occurrence, and retries or two devices cannot multiply that intent. Multiple independent entries would require an established multi-place or group-booking contract. Revalidate against the actual booking identity and any existing group or multi-seat rules before implementation. The alternative is one active entry per distinct authorized attendee or reserved party, if existing policy and identity support it.
- **R-3 interaction assumption.** Expose status and withdrawal in the existing class booking journey, with durable authority on the app side and no dependency on an external notification channel for reading the result. Basis is the existing booking app named in the request and the need to recover interrupted interactions. A separate member bookings view may be more appropriate if that is where existing own-booking actions live. Revalidate when the product surfaces and any chosen time-sensitive allocation mode are known.
- **Verification disposition.** Implementation and every product check are pending. In a later delivery run, the application owner supplies the existing workflow, authorization, and fixture route before dependent planning. The test owner verifies authority and concurrency at system-test and the member journey at product-acceptance. If a required check is person-only after access discovery, the named application operator owns it, due at handoff or the earlier stage whose external effect it gates, and it remains unverified until observed. Product-acceptance may accept one unverified primary requirement only with a passed lower-layer test for it. There is no such result here. If observed behavior contradicts an assumption, record the evidence in the project knowledge checkpoint and use the existing spec correction and, where applicable, add-work route before changing dependent acceptance.
