# User Administration

## Scope and basis

**Request, 2026-11-21, “The incoming request”** — “Let admins upload a CSV to bulk-create users.”

Admins submit one CSV and can tell whether it produced usable user records in the administration scope where they are authorized to create users. Bulk import adds a creation path. Updates, deletion, new role-grant powers, automated imports, and a saved import-history feature are outside the request.

The request and the standalone stage instructions are the product sources supplied. The guides inform modeling and verification. No prior specification, selected baseline, discovery or research result, repository, reference system, or deployed target was supplied. Existing behavior, including identity rules and creation side effects, remains unobserved. The preservation clauses below bind the feature to the applicable product contracts once identified. Confirmation applies to the affected work only.

## Flows and state transitions

- **F-1, submit and create (R-1 through R-4).** An authorized admin selects a local file, submits it and waits for the outcome. The intake boundary admits the file, the user authority processes its rows, and the admin sees the actual result. File rejection starts no writes. Row rejection leaves earlier commits intact.
- **F-2, reconcile and retry (R-1, R-3, R-4).** When the original outcome is unavailable, a currently authorized admin reads ordinary user records and can submit a new attempt. The authority applies uniqueness even if the first attempt is still resolving. A stale or revoked context receives no protected result.

## Non-functional requirements

- **Interface and accessibility.** Apply to the admin entry, file control, submission and outcome views. Use a consistent visual system with coherent spacing and type scales, a light and dark palette, and one icon set. Design the empty, selected, pending, full-success, mixed and error states. Keep the upload and primary action prominent and the row outcomes readable and actionable. At narrow and wide supported widths, long filenames and outcomes wrap without horizontal overflow. File selection, submission, error recovery and outcome inspection work by keyboard, with visible focus and accessible status announcements. Meet WCAG AA contrast in both themes. Motion clarifies state changes and honors reduced motion. Inspect the rendered states at the supported narrow and wide viewport sizes, traverse by keyboard, check contrast, use assistive technology for status and labels, and exercise the reduced-motion preference. The supported viewport and browser matrix awaits the product baseline. Until then the existing admin identity and components take precedence for typography, spacing, color and appearance. Where a new graphical UI needs an otherwise unspecified visual direction, use the guide's light Google Gemini reference via Material 3 Expressive principles, with airy spacing, layered tonal surfaces, a clear type hierarchy and a focused upload action. A new web UI starts light with a dark option absent a governing appearance policy. The concrete treatment belongs to planning.
- **Capacity and responsiveness.** Under the approved intake workload, keep the file and processing state legible and give a bounded rejection for oversized inputs under R-2. Verify intake and concurrent writes on the actual runtime, including any host rejection path. Limits and expected seasonal or peak bulk workload are open under R-2. No latency, throughput or availability target was supplied. An independent service-level target requires an operating workload and owning service.
- **Integrity and recovery.** Exercise concurrency, loss of acknowledgment, service interruption and revocation against the actual write authority. Inspect resulting records and ordinary effects as well as the import result. Pending work never appears as confirmed, known commits survive view loss according to ordinary durability, and a retry preserves uniqueness. Actual deployment and recovery capabilities remain open under R-3 and R-4.
- **Privacy and operability.** In normal and failing attempts inspect response access, local cleanup, service retention and approved diagnostic destinations. Only authorized recipients see their attempt data, and operational metadata excludes raw input and personal field values. Test with synthetic input. Runtime retention, audit obligations and applicable compliance evidence are pending under R-2 and R-4. Existing account policy governs durable records.

## Submission

### summary

Specified admin-only CSV upload and bulk account creation with policy-preserving validation, authoritative writes, truthful results and a recovery path. The stage deliverable is complete. The existing product's authority and scope rules, user schema and identity, creation effects, runtime limits, privacy and audit policies, and actual consumer surfaces remain open prerequisites where identified. No material conflict with a supplied product contract was observed. Any conflict discovered with a provisional rule is open for the product owner before dependent implementation. Use the existing spec correction or revision route and reconcile affected checks and future work if evidence changes the contract. Keep independently definable work moving.

Assumptions and revalidation:

- **R-2** — Default CSV profile is UTF-8 with one header row, comma delimiters, double quoting with doubled escapes, and LF or CRLF records. Use the common spreadsheet-style CSV shape to give admins a deterministic input contract without imposing a product schema. Alternatives include positional fields, a locale-specific delimiter, other encodings, or an existing product export format. Confirm against supported source files and established interchange conventions before finalizing intake. No capacity value is assumed because the target limits, workload and file envelope are unavailable.
- **R-3** — Default independent row outcomes after successful file-level intake, with file-order within-file conflicts and authoritative uniqueness across writers. This lets admins keep confirmed creations and correct specific rows while preserving existing accounts. Alternatives are rolling back the whole batch, rejecting all duplicate occurrences, or accepting a different published ordering. Confirm against product policy, creation side effects and the authority's supported consistency and recovery before implementing. Rejecting a malformed or oversized file before writes allows correction without guessing which records were processed.
- **R-4** — Default results live in the initiating view and no durable background completion is promised. This gives an authorized admin immediate feedback and ordinary user read-back after interruption, with minimal retention of uploaded personal data. An existing durable work and result facility is an alternative if the approved workload cannot complete within the target interaction or policy requires later retrieval. Revalidate after runtime and workload confirmation and before promising background completion or retained results.

Unverified obligations:

- Product owner supplies the governing permission and creation rules, CSV schema or conventions, and applicable retention or audit policy before dependent planning or implementation. Engineering confirms the runtime, write/read-back contract, effective limits, failure boundaries and ability to stage controlled checks before accepting those designs. The product operator confirms access, event coverage, retention and retrieval in the operational environment before the corresponding verification.
- Implementation and all product checks are pending. The verification owner owes the real-boundary checks at system test and the admin-facing outcomes at product acceptance. If later discovery and test strategy establish that a required check is person-only, record the specific owner and phase under the unverified policy, normally handoff or the phase whose external effect it gates. At product acceptance, at most one primary outcome may remain unverified, and only with a passed lower-layer test for that requirement. No such pass exists here.
