# User Administration

## Scope and source

**Incoming request, 2026-11-21, “The incoming request”** — “Let admins upload a CSV to bulk-create users.”

An authorized admin submits one CSV in their managed scope and can tell which rows created ordinary users. The created users are available through ordinary authorized user management. Editing or deleting accounts, granting roles, setting passwords through the file, changing invitation or activation policy, and importing outside the authorized scope are outside this change.

The standalone instructions establish that there is no earlier spec, discovery/research result, selected baseline, or product repository. There is no observed existing product behavior or parity target. Ordinary account behavior below means policy to preserve wherever the target product supplies it. The synthetic fixtures supply their own initial conditions. Product defaults for unspecified behavior are summarized under Submission.

## Submission

### summary

The specification defines current-admin upload and create-only bulk processing with traceable row outcomes and safe reconciliation. Independent interaction, format and result design can proceed. Runtime integration and actual verification depend on the entitlement, account authority, directory, quotas and UI and diagnostics surfaces. No parity target or material conflict was evidenced. If later sources contradict a clause, record its source and scope, invalidate affected evidence and use the existing correction route. Obtain product-owner direction if a correction would alter approved intent.

| Requirement | Default or assumption, basis, alternatives and revalidation |
| --- | --- |
| R-1 | Place import in account management and use the admin’s authorized current scope. This follows the actor and task named in the request and minimizes privilege changes. Alternatives are a separate admin entry or a product-defined global scope. Revalidate against actual navigation, grants and scope semantics. |
| R-2 | Use UTF-8 comma-separated input with `email` and optional `name`. This is a small reversible schema for ordinary creation fixtures. Alternatives are the established account schema, mapped headers or additional encodings. Revalidate against the actual create contract and representative admin files. |
| R-2 | **65,536 bytes inclusive** is a provisional functional default. Unbounded admission would permit uncontrolled input processing. The ceiling bounds the submitted bytes while allowing a meaningful batch of short account rows. No target workload or applicable runtime limits were supplied. Alternatives include a lower ingress-safe cap, a larger validated limit or a separate row bound if downstream capacity requires it. Before fixing the effective cap, check payload overhead, runtime resource and execution limits, downstream creation quotas and representative files. Any replacement must fit verified limits and keep at-limit and over-limit checks. |
| R-3 | Use partial success, first field-valid occurrence eligible, create-only conflict handling, and trim plus ASCII case-folding for the default email comparison. These choices preserve existing accounts and let eligible independent rows progress. Alternatives include all-or-nothing creation, rejecting every occurrence of an in-file duplicate or using the actual ordinary identity key. Revalidate with normal identity, validation, ordinary effects and uniqueness policy. |

Revalidate against deployed execution, support expectations and product retention obligations. |
| R-4 | Use the established account-management visual system where available and the local light expressive starting point for gaps. Start light with a dark option for a new web surface. Revalidate against actual product identity, controls, supported viewports and appearance policy. |
