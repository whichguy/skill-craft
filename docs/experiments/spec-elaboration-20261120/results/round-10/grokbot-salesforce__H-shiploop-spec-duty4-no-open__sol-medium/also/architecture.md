# Grok Bot for Salesforce architecture

This record describes implementation premises for the behavior in [spec.md](spec.md). The choices are provisional where the development org or provider account must be verified. No implementation, deployment or account inspection occurred during specification.

## Decisions

### AD-1 — Use a Salesforce-native Lightning workspace

Use a Lightning web component on a Lightning component custom tab in Lightning Experience. Plan an explicit tab metadata entry and scoped visibility reachable via App Launcher’s All Items. A component’s tab target only makes it eligible for use as a tab. Prefer a standalone tab over changing existing app navigation. A dedicated Lightning app or an existing app placement can be evaluated if the actual org makes All Items unsuitable for the intended user. An external web app adds hosting, session and deployment work for a single in-org workspace.

The display label is **Grok Bot**. Select org-unique bundle, tab, Apex and configuration API names after a scoped metadata inventory. The specific route, metadata API version, feature visibility and browser compatibility remain pending until the development org is identified. Read back the entry independently of deployment status, then prove the intended user can use it on the intended revision. [Salesforce custom tab configuration](https://developer.salesforce.com/docs/platform/lwc/guide/use-config-custom-tab-lex.html) · [Salesforce platform guide](../GUIDES/platforms/salesforce.md#service-discovery)

### AD-2 — Keep invocation and provider authentication in Salesforce

Use an imperative, non-cacheable Apex invocation and a server-side HTTPS callout. Validate input and effective access before sending. Use scoped platform grants for tab visibility, Apex class access and External Credential principal access. Where a separate feature entitlement is needed, enforce it on the server. Client-side visibility is a presentation aid. Do not use an authenticated browser session as evidence of Apex or external principal authorization. The product has no record CRUD or field access to authorize.

Use a modern Named Credential for the fixed xAI endpoint and an External Credential with custom authentication and a development-only named principal. Map allowed Salesforce users to that principal and configure its bearer header from a protected credential parameter. Authorized account owners handle secret setup and rotation through supported administration. The deployment artifacts carry only non-secret configuration and references. Confirm the actual org’s API support, authorized provisioning path and usable caller permissions by scoped inspection and an allowed/denied callout probe. A browser-direct request would expose integration authentication. A separate middleware service would add identity, hosting and retention with no established need.

Use one request/response callout per send and no server-side work queue. The client handles the asynchronous invocation result for its active attempt only. A 30-second configured callout is within the documented 120-second transaction ceiling. The 16,384-byte prompt bound and bounded output leave margin below the documented 6 MB synchronous callout and heap ceilings for ordinary payloads. Validate serialized input, actual provider envelopes and parsing heap in the target. Developer Edition’s edition-specific concurrent external-callout limit matters if that is the selected edition. A continuation is a later option if measured org behavior warrants revisiting the one-callout design. [Imperative Apex](https://developer.salesforce.com/docs/platform/lwc/guide/apex-call-imperative) · [Secure Apex](https://developer.salesforce.com/docs/platform/lwc/guide/apex-security.html) · [Named Credentials](https://developer.salesforce.com/docs/platform/named-credentials/guide/get-started.html) · [External Credential metadata](https://developer.salesforce.com/docs/platform/api-metadata/references/meta-types/metadata-externalcredential.html) · [Salesforce callout limits](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-callouts-timeouts.html) · [Salesforce governors](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-gov-limits.html)

### AD-3 — Use stateless Grok inference and explicitly map completion

Use xAI’s HTTPS Responses API at `api.x.ai`, with the documented `POST /v1/responses` operation. Candidate model `grok-4.3` with reasoning effort `none` is documented and fits short interactive text exchanges. Check actual model availability, cost, latency and limits in the authorized development team before using it. Model choice remains server-owned configuration. Prefer an explicitly supported model over retired aliases or a moving latest alias. Responses is the provider’s recommended API for new integrations.

Send one text input with `store: false`, `stream: false`, `max_output_tokens: 512` and no tools, prior response identifier or history. Consume completed assistant message text entries in response order. Accept only completed responses with nonblank answer text. Ignore non-answer metadata. Map incomplete length-limited completion distinctly from malformed, empty, refused or other incomplete content. Validate the actual length-limit signal during the bounded provider check. Keep parsing and UI message categories separate from raw provider errors. A non-storing request disables later retrieval through the application path. Standard provider safety retention is a separate account property. Confirm that setting with the team owner before transmitting any test fixture. [Inference authentication](https://docs.x.ai/developers/rest-api-reference/inference) · [Responses API](https://docs.x.ai/developers/rest-api-reference/inference/responses) · [Grok 4.3](https://docs.x.ai/developers/models/grok-4.3) · [Best practices](https://docs.x.ai/developers/model-capabilities/text/best-practices) · [Retired model redirects](https://docs.x.ai/developers/migration/may-15-retirement) · [Provider retention](https://docs.x.ai/developers/faq/security)

### AD-4 — Keep workspace data ephemeral and reuse host diagnostics

Keep the current draft, reply, appearance and per-view attempt identity in component memory. Keep Salesforce execution data request-scoped. Guard result delivery by workspace lifetime and matching attempt ownership. Check navigation/reload and session changes in the actual Lightning container. The product has no objects, browser durable storage, result cache or cross-user subscriptions. Add those only if a distinct approved behavior needs them.

Prefer the target’s existing authorized diagnostic facility for safe attempt results. Have the org operator verify the available destination, access, retention and host-owned login and administration coverage. Where the existing facility cannot meet the contract, resolve the scoped logging design before relying on that operability check. No new logging service is selected. Platform logging is not a place to enable or collect raw request, credential or response diagnostics. [Interaction ownership guide](../GUIDES/behavioral-requirements.md#actors-channels-and-state-ownership) · [Service observability guide](../GUIDES/service-discovery.md#observability-coverage)

### AD-5 — Use Lightning primitives and a scoped expressive appearance

Start with accessible Lightning primitives and one compatible icon family, supported by scoped layout and palette tokens for the bot workspace. Use an expressive, softly rounded answer surface and a clearly grouped composer. Keep status feedback adjacent to the prompt/answer flow. Preserve Salesforce navigation, form conventions and host chrome. The named reference is light Google Gemini via Material 3 Expressive, using emphasis and containment to make the primary action obvious. Start light with a workspace-local dark option. The concrete treatment, tokens, rendered states and keyboard/focus details belong in the later plan.

A third-party component package adds compatibility and maintenance work for few controls. A scoped treatment using platform primitives is the lower-effort choice if the selected org’s theme supports the required visual states. Confirm component theming, contrast, focus treatment, overflow, reduced motion and CSP compatibility in the rendered target. No optional frontend-design skill was available in the supplied catalog. The local UI guidance supplies the design profile. [ShipLoop visual direction](../GUIDES/platforms/ui.md#light-expressive-starting-point) · [Material 3 Expressive research](https://design.google/library/expressive-material-design-google-research) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/)

### AD-6 — Reconcile actual metadata before activation

Use the target’s supported Salesforce metadata deployment and status/read-back surfaces, with rollback on metadata errors and separately reconciled org-only configuration and assignments. Metadata status is asynchronous. The job identity tracks monitoring while deployed revision is confirmed through independent scoped metadata read-back against a candidate-derived fingerprint. Pick the manifest and normalization rules once the target API and artifacts are known. Stop on collision or ambiguous state before changing unrelated resources. Check current configuration and active grants after terminal deployment. A successful metadata rollback does not prove a separate configuration or grant was undone. Use the pre-change snapshot and admin authority for containment/recovery.
