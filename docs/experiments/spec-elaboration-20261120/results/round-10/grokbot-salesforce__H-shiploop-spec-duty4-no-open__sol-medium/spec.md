# Grok Bot for Salesforce

Source S0 is the user’s request dated 2026-11-21, “Create a Grok bot in a Salesforce development org.” This is the initial specification. The standalone stage supplied no prior requirements, discovery, research result or selected baseline. Public documentation establishes supported options and provider contracts. The target org’s existing metadata, identities and behavior are unknown. Where the request leaves product rules unstated, this spec uses the reversible defaults recorded in [Submission](#submission).

## Requirements

### R-1 — Reach the bot in the development org

**Basis and change.** S0, “Create … in a Salesforce development org,” is the basis for an in-org consumer entry backed by the delivered candidate. [SF1](#sources) describes supported navigation, [SF4](#sources) describes deploy status, and the [baseline guide](../GUIDES/current-system-baseline.md#planning-and-review-handoff) governs preservation. There are no previous bot clauses to carry forward. Preserve unrelated org metadata, permissions and business data. Implementation and checks C1–C2 are pending.

- **R-1.a / C1.** Positive — an assigned, signed-in Salesforce user finds **Grok Bot** via the org’s App Launcher and opens a workspace with an enabled **Prompt** composer and availability to **Send** valid text. Failure — a missing item, dead route, sign-in page, wrong org, or title-only workspace fails. Boundary — the consumer is a regular assigned user in the identified development org. Confirm in Lightning Experience under that user, record the non-secret entry route and org identity, and exercise a send under R-2.
- **R-1.b / C2.** Positive — the bot revision intended for delivery reaches a terminal successful deployment in that org, its entry and scoped access are effective, and unrelated state matches the recorded pre-change baseline. Failure — partial or failed deployment, missing access, unknown revision or a different revision leaves delivery incomplete. Boundary — accepted or finalizing status is pending, even if a bot with the same name is already present. Confirm with the deployment receipt and revision-sensitive metadata/configuration read-back tied to C1. Qualify the identity check against the intended revision and a known different candidate in an authorized isolated context.

**State and domain rules.** The Salesforce admin owns org metadata, feature visibility and user assignments. Admin and tester access are distinct from the consumer’s runtime access. Before any write, bind the intended org, effective roles, candidate identity, pre-existing bot-related components and access, and unrelated state in the touched scope. Afterward, only the bot’s scoped resources and named assignments have changed. Resolve name collisions before deployment. Reconcile current state before retrying a partially successful release or one with an unknown outcome. Contain access by withdrawing only feature-owned grants where authorized, then restore or remove only feature-owned metadata/configuration using the recorded pre-change state. Verify containment and restored state by read-back. There is no business data migration, production rollout, or additional channel in S0.

**Open gap.** The user or authorized org owner supplies the unique development org identity, scoped deploy/configuration authority and existing consumer identities. Preparation owner confirms the edition, release, names, effective permissions and consumer access in that org. Resolve target ambiguity with the user if it remains after identification. These gaps gate org-specific work, deployment and C1–C2, while independent UI and contract design can proceed. If no authorized browser route exists once target access is assessed, the intended user owns the open consumer check at release verification, reported unverified under the stage readiness policy.

### R-2 — Submit a prompt and see Grok’s reply

**Basis and change.** S0, “Create a Grok bot,” implies a real Grok-generated answer to user input. [XA1–XA3](#sources) document API behavior and model capability, without establishing the selected account’s access or live output. No prior behavior is available to preserve. Add one text prompt and one answer per exchange. Implementation and checks C3–C6 are pending.

- **R-2.a / C3.** Positive — **Send** submits the current valid prompt once and the workspace displays the completed, nonblank answer text returned by Grok for that submission, labeled **Grok**. Failure — missing usable text, malformed or nonterminal provider output, or a response associated with another submission produces no answer and follows R-3. Boundary — each exchange sends only its own prompt and starts fresh, including a second send from the same workspace. Confirm with two different prompt/answer pairs at the service boundary and in the rendered workspace. The live case must bind both successful calls to the authorized Grok route and compare the rendered answers to the respective returned text.
- **R-2.b / C4.** Positive — a nonblank prompt within the effective limit is sent with its text intact. Failure — missing, empty, or Unicode White_Space-only input shows “Enter a prompt.” and incurs zero provider requests. Boundary — the **default** is 16,384 UTF-8 bytes inclusive, measured on the submitted text before transport encoding. At 16,384 bytes the send is allowed; from 16,385 bytes it is rejected with “Prompt exceeds 16,384 UTF-8 bytes.” and editable original text at the default. Confirm rendered validation and independent service-side enforcement with the inputs in C4.
- **R-2.c / C5.** Positive — completed answer text is readable, selectable and displayed literally, with line breaks. Failure — text resembling markup or an instruction remains text and causes no rendering of active content, navigation, record change or action. Boundary — n/a: output size and incomplete output are covered in R-2.d. Confirm with literal output and verify absence of parsed markup/actions.
- **R-2.d / C6.** Positive — complete nonblank text returned within the selected output allowance renders in full. Failure — when generation ends incomplete at the allowance, show that the answer reached its length limit and suggest a shorter requested answer. Preserve the prompt for editing and display no partial answer as success. Boundary — the **default** provider allowance is 512 visible output tokens. A completed answer at the allowance still renders; a continuation beyond it is not requested. Confirm at the provider adapter and workspace using the complete/incomplete controls in C6.

**State and domain rules.** The current prompt snapshot and corresponding reply are the only exchange data. The initiating user owns the draft and display; Salesforce processes the submitted snapshot transiently, and Grok owns generation. Neither prior prompts, earlier answers, CRM data, nor attachments enter a later request. Single-turn text Q&A is the scope default. Provider persona settings, guaranteed factual accuracy, streaming, tools, browsing, CRM actions and parity with consumer Grok apps are outside this contract. Platform-native navigation and documented Grok response semantics are the only external reference behaviors. Verify retention separately in R-4.

**Open gap.** The provider account owner supplies an authorized development team/key, permitted Grok model, funding/quota and applicable data-use policy. Integration owner verifies the team/model/route association and a bounded live call before relying on it. This gates live inference and C3’s live case, while simulated behavior and UI work can proceed.

### R-3 — Wait, recover and avoid duplicate sends

**Basis and change.** S0, “bot,” requires an observable outcome when external generation fails or stalls. [SF2](#sources), [XA1](#sources) and [XA4](#sources) describe applicable callout limits, provider completion and errors. No previous interaction rules were supplied. Add pending feedback and recovery. Implementation and checks C7–C9 are pending.

- **R-3.a / C7.** Positive — when a valid send starts, show a screen-reader-announced **Waiting for Grok** state, snapshot the prompt, clear any previous answer/error, and make the composer read-only and sending unavailable until the active attempt settles. Arrival of that attempt’s completed answer returns the composer to ready. Failure — repeated clicks or keyboard activation while pending have no effect and create no extra request. Boundary — the **default** is one active send per workspace instance; another instance has independent state, subject to org and provider limits. Confirm with a held reply and counted invocations in one and two views.
- **R-3.b / C8.** Positive — after a failure, release pending state, retain the exact editable prompt and allow a fresh explicit send. Failure — distinguish provider throttling (“Grok is busy. Try again later.”), provider authentication/configuration (“Grok is unavailable. Contact your Salesforce admin.”), unsafe/missing/unfinished reply (“Grok couldn’t return an answer. Try again.”), and timeout (“Grok took too long. Try again.”). Other transport/provider failures show “Grok is unavailable. Try again.” Salesforce permission denial follows R-4; answer length follows R-2.d. Raw diagnostics stay off the screen. Boundary — the **default** upstream callout timeout is 30 seconds from callout start. A completed reply that wins the transport deadline can succeed; at the deadline with no completed transport result, or if it arrives later, the attempt times out. This is an upstream deadline, not a browser response SLA. There is no automatic retry. A fresh send after an unknown outcome may incur another provider charge. Confirm with controlled outcomes and the recovery sequence in C8.
- **R-3.c / C9.** Positive — reloading the workspace creates a clean composer and result area. It gives the user a recovery path if a broken client connection leaves the call unresolved. Failure — a completion from a destroyed workspace or previous login cannot populate a new workspace. Boundary — a reload or sign-out ends local observation; an already sent provider request may still finish and incur usage. Confirm with a held reply across reload and with a different authenticated user in a separate browser context.

**State and domain rules.** Before each accepted send there is either an empty workspace, a draft, a prior answer or a recoverable error. While pending, only its matching completion can leave that state. The same view resolves simultaneous activation by giving the first accepted send ownership until it settles. A later view can have work of its own. There is no shared queue, exactly-once claim, background delivery, remote cancellation or deferred retrieval. Known pending work ends at a terminal reply/failure or local teardown; authorization and retention follow R-4.

**Open gap.** Provider latency and error behavior in the selected org/team remain unmeasured. Integration owner confirms timeout handling, real short-prompt viability and dependency availability before live verification. Contract and controlled feedback checks can proceed independently.

### R-4 — Enforce org access and limit data exposure

**Basis and change.** S0, “in a Salesforce development org,” and the service boundary implicit in “Grok” are the basis for using org access and protecting prompt traffic and the provider credential. [SF3](#sources), [XA1](#sources), [XA2](#sources) and [XA5](#sources) describe authority, authentication and provider storage. The actual org and provider policies are unknown. Preserve existing Salesforce permissions and data outside scoped feature access. Add assigned-user access, ephemeral exchange data and safe handling. Implementation and checks C10–C12 are pending.

- **R-4.a / C10.** Positive — a signed-in, assigned user can invoke the bot using the enabled development integration. Failure — unassigned, unauthenticated, or effectively revoked users cannot initiate a chargeable provider call, including through a direct invocation or stale open page. Show a safe access-denied outcome or the host sign-in gate. Boundary — enforce the authorization effective in Salesforce at each new submission. An already authorized request may finish in its original still-active view after grant removal; a new identity/view cannot receive that result. Confirm with allowed, denied and post-revocation identities at the consumer and server boundaries, counting outbound calls.
- **R-4.b / C11.** Positive — the workspace discloses before **Send** that text goes to the Grok provider, and directs users to enter synthetic development data only. On a successful request, only the explicitly submitted text and necessary inference parameters cross the provider boundary. Failure — Salesforce business records, record identifiers or user identifiers gathered by the bot, provider secrets, session material and raw service errors are absent from the consumer response, application diagnostics and unintended destinations. Boundary — the composer accepts free text; this restricted development scope relies on the user for input selection and does not classify arbitrary free text. Confirm with the synthetic sentinels in C11, a redacted endpoint inspection and before/after CRM checks.
- **R-4.c / C12.** Positive — only the initiating user’s active workspace displays exchange content. The bot owns no durable history or retrievable provider-side response object for the request. Failure — a fresh/reloaded workspace or another user cannot retrieve the exchange from the bot. Boundary — workspace teardown discards local content; provider safety retention is governed separately by the actual account policy. Confirm with two browser contexts, storage/diagnostics inspections, a provider request retention setting check and documented account-policy evidence.

## Behavior model

### UI premises

- **Components.** Workspace heading and data-use notice, labeled multiline **Prompt** composer, **Send** and appearance controls, answer region, and inline status/error area. Controls expose keyboard and pointer equivalents. Long plain text wraps. The appearance control stays reachable during inference.
- **Interaction.** Typing changes a draft. **Send** owns the visual progress state until a matching reply/failure, with no speculative answer. Preserve visible focus or place it at a usable related control if its target becomes unavailable. Announce waiting, failure and completion, and keep the error present until the next attempt or teardown. The pending state explains that a refresh clears the workspace. Reload and new sign-in start clean.
- **Skin.** Adapt expressive color, shape and containment to make the prompt and answer the main activity. Use a light tonal surface, restrained accent, distinct error and focus treatments, disciplined spacing and type hierarchy, and an equivalent dark palette. Salesforce shell conventions govern navigation. Precise treatment is a later design choice.

### Flows and transitions

- **F-1 / R-1, R-4.** The authorized org operator identifies the target and baseline, deploys the scoped candidate and reads terminal status, then applies/reads back scoped configuration and grants under T-1. The assigned consumer opens **Grok Bot** via App Launcher under T-2. A second identity lacks effective access. No org write occurs while the target or authority is indeterminate.
- **F-2 / R-2, R-3, R-4.** In a fresh or settled workspace, a consumer submits a prompt under T-3. Salesforce checks authority and input, then calls Grok. The UI receives an eventual result under T-4 or T-5. Repeated activation while waiting follows T-6. A failed attempt permits editing and sending again through T-3.
- **F-3 / R-3, R-4.** Reload or logout retires local state and discards stale completion under T-7. An admin may remove access under T-8; an already open page cannot confer future callout authority.

### Replay review

Specification review on 2026-11-21 walked the defined guards and observers. A desk walk checks reachability and expected outcomes from the contract. A local documentation audit checked the requirement/case references, local links and UTF-8 fixture calculations. Actual product, target and controlled fixture executions remain unverified.

- **C1–C2.** T-1 requires the bound dev org, scoped operator and pre-change snapshot. Candidate-A’s terminal success plus matching read-back permits T-2 with the separately assigned user. Pending/partial/failed status yields zero delivery completions and Candidate-B identity fails even with a matching label. **NOT-REPLAYED: no bound org, candidates, deployment evidence or consumer route.**
- **C3–C6.** T-3 allows P1, T-4 associates Cedar-317 with P1 and releases P2 for the next T-3. T-4 then replaces the result with Maple-842, with two sends and no carryover. ASCII boundary sizes are 16,384 and 16,385 bytes; U+00E9 takes two UTF-8 bytes, yielding 16,384 and 16,386 bytes. Blank or over-limit input never reaches Grok. ### summary

The standalone specification defines a reachable Salesforce Grok workspace and real Grok prompt/reply behavior. It records controls for authorization, validation, recovery, privacy and interface quality. Public documentation informed feasibility. Actual target state, configuration and behavior remain unverified. Spec definition is complete for the described scope. The org binding/authority, provider setup/retention and authorized verification surfaces listed under the affected requirements remain open and gate their dependent work. There is no evidenced requirement conflict. An actual policy conflict on provider transfer or retention would keep live inference unready until resolved.

**Assumptions and revalidation**

- **R-1 and interface quality.** Assigned internal Salesforce users, a single dedicated workspace under **Grok Bot**, and an online browser are the defaults for “in a Salesforce development org.” An existing app placement or other intended channel could replace the entry model if the target/user establishes it. Start light with an in-workspace dark option from the visual direction guide. Revalidate against org conventions and target browser capabilities. No org, person, alias or grant was assumed.
- **R-2.** Default to standalone plain-text exchanges and one current answer. Conversation context and persistent transcripts were alternatives. The request establishes no need for them and omitting them limits transfer and retention. Revalidate if the user specifies follow-ups or history.
- **R-2.b.** Default 16,384 UTF-8 input bytes keeps one text prompt and its serialization well below Salesforce’s synchronous callout/heap limits and small relative to the candidate model context. The quota protects the service from oversized arbitrary input. Alternatives include a smaller short-prompt cap or a provider token-aware validator. Revalidate with the actual transport, boundary Unicode/escaping and representative dev prompts before release.
- **R-2.d.** Default 512 visible output tokens is a bounded short-answer budget under the provider’s documented output-control mechanism. It limits response size, time and cost for dev use. A smaller cap or a larger budget for longer answers is reversible. Confirm the selected model’s actual cutoff semantics, response footprint and usefulness for representative questions.
- **R-3.** Default one pending send per workspace with explicit manual retry. Queued overlapping sends and automatic retry add duplicate-cost and stale-result risks for this scope. Revalidate if an actual concurrent-workflow requirement or provider idempotency contract is introduced.
- **R-3.b.** Default 30-second outbound timeout allows more than Salesforce’s 10-second default while staying within the 120-second callout ceiling. Shorter waits favor fast recovery; longer waits may accommodate the chosen model but cost user time. Revalidate against actual dev-org short-prompt measurements and transport deadline behavior before live acceptance.
- **R-4.** Default to synthetic development data, current Salesforce access, ephemeral workspace state, no retrievable history, and no additional identity. Provider standard auditing and account-level Zero Data Retention are different account choices. Revalidate with the authorized org/provider owners when the actual policy and team are identified. No retention terms are presumed accepted for an unidentified account.

For later discoveries, preserve scope and record evidence against affected clauses. Use the existing review/correction route for incompatible intent or authority, and carry new prerequisites forward before affected future work. Pending acceptance only becomes verified from corresponding observations.
