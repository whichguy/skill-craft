# Grok Bot for Salesforce Architecture

## Decisions

These decisions define the starting design for the specification. Target-specific dependencies remain subject to the gaps recorded in [spec.md](spec.md#requirements).

### AD-1 · Salesforce-native entry and authorization

Use a Lightning Web Component in a Lightning component tab and place that tab in one operator-approved Lightning app. Prefer an existing suitable development app when its owner approves the navigation change. Use a dedicated app only if the baseline shows that adding to an existing app would disturb an unrelated audience or configuration. Supply the tab and navigation as scoped metadata. The component's tab target only makes it eligible for a tab. Verify the tab, app navigation, direct entry and effective visibility with the designated role. Confirm the actual org ID, metadata API version, runtime edition and candidate API-name availability before fixing target identifiers.

Use a narrowly assigned permission set for entry visibility, Apex class access, bot custom permission and access to the one external credential principal. Use an imperative, non-cacheable Apex action with an explicit check of the current user's bot permission before validation and any network request. Native authentication, class access and principal permissions remain independent enforcement points. CRM row sharing, object CRUD and field permissions are inapplicable to bot data processing because the action neither reads nor mutates CRM records. Keep metadata deployment, secret provisioning and consumer grants separately authorized. Require successful terminal Salesforce status and matching metadata read-back before activation. [Spec R-1 and R-2](spec.md#requirements), [Salesforce S1–S3](spec.md#salesforce-sources).

### AD-2 · Direct, stateless Grok Responses API integration

Use a synchronous Salesforce server callout for one foreground `POST https://api.x.ai/v1/responses` per accepted submission. A modern Named Credential points to the approved inference endpoint and an External Credential with Custom authentication and a named principal provides the bearer header from a protected parameter. Enable header formulas and disable the generated authorization header when using the custom header. The custodian sets the secret through an authorized Salesforce setup surface; it is excluded from deployable metadata. Use a dedicated development inference key and verify availability of the configured approved model under that key. The team owner selects the model, confirms quota and approves the provider policy. Pin the available model and document a resolved canonical ID if the selected identifier is an alias. No automatic fallback.

Send the validated current text as `input` with the server-selected `model`, `store: false` and non-streaming behavior. Set a verified output-token cap. Omit tools, previous responses, attachments and user metadata. API success requires a completed response containing usable assistant output text for the configured or evidenced resolved model. Read ordered assistant message `output_text` parts and discard all other provider fields from consumer output. Classification covers transport/timeout, authorization/model/configuration rejection, rate-limit response and remaining provider/completion failures. Retain safe diagnostic categories and an opaque attempt reference in the approved scoped diagnostic surface. No browser-side provider credential, background processor or separate service is needed for these interactions.

Validate the selected model's serialization, content bounds and timeout in the org. Salesforce documents a cumulative callout deadline ceiling of 120 seconds, a per-transaction callout count ceiling of 100 and a synchronous request/response size ceiling of 6 MB that also counts toward heap. The configured timeout and payload budget must leave headroom inside these limits and the provider's own limits. Confirm Edition-specific concurrency, actual team rate limits and usage allowances before activation. Documented endpoint capabilities provide design evidence. The org callout, team configuration and selected model still require integration and release verification. [Spec R-2, R-3 and non-functional requirements](spec.md#non-functional-requirements), [Salesforce S2/S5](spec.md#salesforce-sources), [Grok X1–X4](spec.md#grok-sources).

### AD-3 · Lightning conversation panel with ephemeral state

Use accessible Lightning primitives and one Salesforce icon family where they satisfy the interaction contract. Use scoped styles for the bot's typography, spacing, semantic colors and appearance toggle. Preserve the surrounding Salesforce shell. The visual direction is the light Google Gemini reference interpreted through Material 3 Expressive principles, with generous spacing, a rounded answer panel, readable question/answer hierarchy and a clear composer as the main action. The starting appearance is light with a bot-panel dark option. Confirm the target's SLDS version and theming constraints before choosing concrete tokens and controls. A parallel toolkit would add theming and compatibility work without a demonstrated gap. The local UI and actor/state guides inform the direction; the selected target will determine the concrete treatment.

Use one multiline composer, Send, Clear, a latest-answer region and an inline status/error region. Keep the status independently perceivable during an asynchronous send. The originating component holds the draft, local appearance and per-attempt display eligibility in memory. Scope callbacks to that view and discard invalidated content on Clear or disposal. A reconnected browser starts empty. Verify lifecycle events and theme contrast in the real Lightning host, including any host behavior that retains a mounted view.
