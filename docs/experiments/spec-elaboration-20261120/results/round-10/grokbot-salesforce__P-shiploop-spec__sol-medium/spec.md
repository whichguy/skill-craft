# Grok Bot for Salesforce

## Scope and basis

**Request, 2026-11-21** · “Create a Grok bot in a Salesforce development org.”

The intended outcome is a bot an authorized user can open in the designated Salesforce development org and use to send an independent text prompt to Grok and read its reply there. The initial audience is designated internal development-org users with existing Salesforce accounts. This is an additive feature. The standalone stage supplied no prior spec, repository, selected baseline, discovery results or target-org observations. Existing org resources and policies may be present and must be preserved. Public documentation establishes platform capabilities and constraints, with evidence limits recorded below. No external product is a parity reference. The Grok API is an integration contract and the visual reference informs appearance.

**State and service boundary.** Salesforce authorizes each send under R-1. The Grok team authorizes the server's inference identity and the enabled model. Acknowledgment, HTTP success without usable completed text, timeout and disconnection do not establish a delivered reply. The provider may count or bill accepted work even if the caller sees no reply. Salesforce holds prompt and reply data in request scope and performs zero bot-related CRM record operations. There is no durable bot job, callback, polling, replay or incremental result sync because each prompt is independent. Credential lifecycle, user-visible state and owned diagnostics are under R-3.

The request leaves model variant, history, tools and record access unspecified. This release is text only and gives Grok no browsing, CRM reads or writes, autonomous actions, or agents that run in the background.

## Flows and transitions

The browser's request is asynchronous from the user's perspective. A single send resolves into a reply, an error or locally discarded content. The only durable asynchronous operation in this scope is Salesforce metadata deployment.

| Flow | Actors, order and outcome |
| --- | --- |
| F-1 · Provision and open (R-1, R-3) | The authorized operator confirms target and scoped before-state, then submits the identified candidate to Salesforce (T-1). On successful status and read-back, the administrator configures the approved connection and assigns only the named user's access (T-2). The existing Salesforce user signs in and opens **Grok Bot** (T-3). |
| F-2 · Ask and answer (R-1, R-2, R-3) | The user enters text and selects Send. The server checks current access, then input (T-4). It submits the approved prompt to Grok (T-5). Grok responds to Salesforce; Salesforce returns a sanitized reply or outcome to the originating view (T-6 or T-7). The user can edit and deliberately submit another prompt once ready. |
| F-3 · Clear or leave (R-2, R-3) | The user clears the view or the view/session ends (T-8). An already-sent inference may finish at Grok. That result can only release the gate for a cleared, still-open view. |
| F-4 · Maintain access and service (R-1, R-3) | The authorized admin rechecks scoped state, revokes a grant or replaces an unusable credential (T-9). New sends use the effective state. The operator distinguishes failure and recovery using sanitized evidence (T-10). |
