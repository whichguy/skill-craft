# Grok Bot for Salesforce

## Basis and scope

On 2026-11-21 the user wrote “Create a Grok bot in a Salesforce development org.” The source locator is the request’s **The incoming request** section. Its two direct outcomes are a bot available inside the intended Salesforce development org ([R-1](#r-1--open-the-bot-in-the-development-org)) and a user receiving a real Grok-generated answer there ([R-2](#r-2--get-a-grok-answer)). The standalone-stage instructions establish that no prior spec, research/discovery result, repository or selected baseline exists. The target org’s contents and behavior are unknown. The proposed addition preserves unrelated org configuration and business data.

The working interpretation is an internal, single-turn, text question-and-answer interface for existing Salesforce users. The xAI API is the provider contract. The public Grok application and xAI’s separately branded Grok Bot are outside the scope of parity. Supporting default rules appear under their affected requirements and in the submission. Each acceptance line is a future verification obligation.

## Requirements

### R-1 — Open the bot in the development org

**Basis and change.** “Create a Grok bot in a Salesforce development org” (2026-11-21, **The incoming request**), specifically “in a Salesforce development org.” Adds a navigable Grok Bot entry in one identified non-production org and preserves unrelated setup, access and data. Source sections S1 and S5 document the platform entry and setup evidence. They establish capability only. Implementation, deployment, activation/access assignment and checks are pending.

- **C-01 — Consumer entry.** Positive: From Lightning Experience App Launcher → **Grok Bot** → **Grok Bot** navigation item, the designated authorized user reaches a page whose heading is **Grok Bot**, with a **Message** field and **Send** button usable without administrator rights. Failure: A login page, missing or inactive entry, or a page lacking the composer fails this check. Boundary: the rendered page and candidate deployment must belong to the identified development org. **Surface/check:** Release verification in an authenticated browser under the consumer identity, correlated to the deployed revision, target org ID and terminal release/read-back evidence.
- **C-02 — Targeted setup.** Positive: reconcile the planned feature resources with org metadata before applying changes and verify the intended bot and its access configuration afterward. Failure: a wrong target, name collision, unconfirmed write or partial activation prevents reporting the bot as available. Boundary: deployment, visibility/access assignment and credential readiness have separate evidence, with business records and unrelated metadata outside the write set. **Surface/check:** Compare authorized before/after org metadata, assignment and Setup Audit Trail evidence to the candidate’s planned feature inventory, plus C-01. Deployment submission alone cannot satisfy this line.

**State and service boundary.** The org administrator owns the feature metadata, navigation, grants and authorized recovery in the selected development org. The precondition is a verified org identity and a supported deploy route with a collision-free feature delta or a specifically reconciled prior bot installation. In the expected after state only feature-owned resources and designated grants have changed. Re-read actual state before reapplying a failed or uncertain setup step. On partial activation the administrator withdraws affected feature visibility/grants and reconciles only feature-owned resources before reopening. Rollback cannot recall a request already sent to xAI. Salesforce is the live authority for deployment status, navigation and grants. Read current metadata and assignments before changes and read back terminal deployment plus effective access afterward. App-level sync, cache and metadata event consumers are inapplicable because this is a scoped setup change with authoritative read-back. Salesforce owns setup event coverage (S5).

**Domain rule left open by the request.** The development target and designated operator/users are supplied by the owner. Default entry is Lightning Experience in a dedicated internal app, with native mobile excluded from this delivery.

**Open gaps.** The Salesforce owner must identify the org ID, the deployment/setup authority and existing authorized and denied consumer identities by prepare, and authorize actual writes and access grants by release-check. The delivery operator must confirm the supported platform/API version, org theme and feature metadata names against the actual target before dependent configuration. Until then, target-specific deployment, access and browser verification are unready. Isolated product work can proceed.

### R-2 — Get a Grok answer

**Basis and change.** “Create a Grok bot in a Salesforce development org” (2026-11-21, **The incoming request**), specifically “Grok bot.” Adds real text generation for one submitted question. Preserves unrelated org data and workflows. Source sections X1–X4 and S3 describe the documented provider and runtime contract. The pinned-model request and response, key scope, quota and retention for the eventual account are unobserved. Implementation, service-contract checks and real-boundary verification are pending.

- **C-03 — Real result.** Positive: one valid admitted Send submits the normalized question to xAI and displays the completed Grok assistant text in provider order, joining multiple text parts with one newline, alongside the submitted question. Failure: acknowledgment, loading text, a canned answer, a refusal, reasoning metadata, partial content or a fallback model cannot satisfy this line. Boundary: send one fresh question per request, with no previous answer, client identity or Salesforce data attached, and make one provider attempt per accepted submission. **Surface/check:** At release-verify exercise both live samples in **Replay and evidence** from the actual org and designated role. Match the rendered answer against the independently observed same-attempt provider result and verify the normalized outbound input and selected model with approved sanitized evidence. Separately vary the request and provider result at the isolated adapter-to-UI boundary before product-acceptance.
- **C-04 — Failure is visible and recoverable.** Positive: a failed attempt leaves an editable question, a usable Send action when local access is available, and a persistent inline status until edit, valid resubmission, Clear or view end. Failure classes and messages are below. Boundary: a provider output cap reached with an incomplete response yields the incomplete status, with zero partial answer displayed. A completion exactly at the presentation deadline is late. No automatic retry, fallback or success placeholder. **Surface/check:** Inject each failure group at the Salesforce/provider or browser/server boundary as appropriate, verify the visible category and draft, no assistant answer or payload leak, and zero additional attempts until a user explicitly submits again. Where setup can be corrected in an approved test target, validate manual recovery against the same target.

| Distinct failure group | Visible result and action |
| --- | --- |
| Provider key missing, rejected or unauthorized, selected model unavailable, or known provider billing failure | “Grok is unavailable. Contact your Salesforce administrator.” Administrator checks feature configuration and xAI model/credit access. |
| Provider rate or quota limit | “Grok is busy. Wait and send again.” Resending is manual and can fail again until the provider permits it. |
| Timeout, no transport, upstream 5xx or platform invocation failure without a known more specific classification | “No reply received. Send again.” An upstream attempt may already have run and may incur cost. |
| Confirmed content refusal, or explicit incomplete provider result | “Grok couldn’t complete this reply. Revise or shorten your message and send again.” No partial reply. |
| Other upstream rejection, malformed or empty success, unexpected/nonfinal status, or protocol mismatch | “Grok couldn’t return a reply. Try again or contact your Salesforce administrator.” No raw error or response body. |
| Local entitlement missing or Salesforce session expired when submitting | The R-4 authorization or sign-in outcome takes precedence. No provider request for a denied submission. |

**State and service boundary.** xAI is authoritative for its key/model entitlement, rate/billing rules and result. Each call uses current entitlement at dispatch without application cache, stored response ID, provider conversation, job, replay queue or polling. Salesforce owns a transient request and normalized result/error in the user’s invocation. Only response content required by the product returns to that invocation. xAI may have processed an uncertain attempt even after the browser stops waiting. The key owner restores credential/model/quota readiness, and manual Send creates a new attempt. No incremental data feed, webhook, completion notification or separately durable job applies to a single foreground response. The app owns visible pending/success/failure status and coarse error classification only. Salesforce owns platform invocation/failure telemetry and xAI owns provider-side usage/authentication events where available. Provider event coverage and authorized retrieval for this team remain unverified. Authoritative login coverage is described under R-4.

**Domain rules left open by the request.** Use a single text question with a complete text result. Images, voice, live search/tools, Salesforce actions and factual accuracy guarantees are outside scope. The selected model has a documented 1,000,000-token context window (X2). The application sends one bounded question, requests at most 512 visible output tokens, and asks the provider for a fresh non-stored response. A complete reply at the cap can display. A provider input/context rejection yields the generic upstream rejection, and never silently truncates the question. The consumer stops waiting at 30,000 ms from valid Send, with a deadline decision on the first runnable UI callback at or after that point. This is a presentation rule. R-5 defines stale-result handling.

**Open gaps.** The xAI owner must supply an approved developer team with model entitlement, funded usage and a team-controlled credential by release-check, and confirm its rate/usage constraints and retention terms. The Salesforce admin must authorize the outbound data boundary and provision access before live invocation. The delivery verifier owns the lowest feasible live probe by release-check and the consumer-path check at release-verify. Confirm provider response/error mapping and obtain a permitted, same-attempt source of reply evidence without recording sensitive data. Until then live readiness and real generation remain unverified. Isolated mapping and consumer behavior can proceed.

### R-3 — Validate a text question

**Basis and change.** “Create a Grok bot in a Salesforce development org” (2026-11-21, **The incoming request**) plus the recorded input default. Adds a bounded question composer and authoritative validation. Preserves business data and access. Source sections X1, X2 and S3 describe the text input and outer limits. They do not choose the composer boundary. Application validation and boundary checks are pending.

- **C-05 — Admission and exact limit.** Positive: send a well-formed Unicode text value after trimming only the whitespace code points listed below from both ends. Preserve interior text and line breaks as received by the composer. Failure: reject missing/null, non-text, ill-formed Unicode, empty and whitespace-only input with “Enter a message as text.” Reject over-limit input with “Use 4,000 characters or fewer.” Leave the draft available for correction and send no provider request. Boundary: 1 through 4,000 UTF-16 code units inclusive after trim, including paired supplementary characters counted as two, with no silent truncation. **Surface/check:** Exercise the composer and an authorized invocation with validation inputs from C-05 in **Replay and evidence**. Independently inspect normalized inputs and count actual dispatches. Local access denial under R-4 precedes admission at the server.

**State and rules.** The browser owns the draft and rejects locally invalid input before opening a pending attempt. The server independently makes the authoritative admission decision. An invalid Send changes only the cue and leaves a prior completed answer, if present, intact. A valid Send hands off to R-5. Attachments and non-text prompt modes are outside scope. Trim U+0009–000D, U+0020, U+0085, U+00A0, U+1680, U+2000–200A, U+2028, U+2029, U+202F, U+205F and U+3000 from the edges. The length count is deterministic across client and server. The user can edit a multiline draft using standard text controls. No extra rule for languages or topic-specific content.
