# User Administration Specification

## Scope and evidence

The product name is unavailable. **User Administration** names the product area covered by this specification.

**Observed source.** The incoming request, 2026-11-21, under “The incoming request”: “Let admins upload a CSV to bulk-create users.” It establishes the actor, input and create outcome. The standalone stage supplies no earlier specification, discovery, research, selected baseline, repository, reference system or target runtime. There are no earlier IDs to carry forward. No existing behavior, technical capability or parity has been observed.

**Inferred behavior.** Import is a create-only entry into the authoritative user directory. The requirements preserve applicable single-user creation rules, directory access and existing user records. Proposed product defaults below make the flow checkable and are subject to the listed prerequisites. The examples use a provisional fixture contract, with an email-only header, ASCII address matching after trimming and case folding, and ordinary non-admin accounts. These are assumptions about a workable starting contract. The actual creation and identity rules must come from the product authority.

## Requirements

Each acceptance line identifies its positive, failure and boundary expectations, then its required observation and planned confirmation. The case keys link to the specification walkthroughs. Implementation and runtime verification are pending for every requirement.

### R-1 Admin access and scope

**Basis and delta.** Incoming request, 2026-11-21, “Let admins upload a CSV to bulk-create users” (“The incoming request”; “admins”). Preserve applicable user-administration rights. Add gated entry, submission and result access. The role and scope model is unobserved. Confirm it before wiring access and verify on the UI and authoritative operation boundary.

- **C1 / Access.** **Positive:** An authorized user administrator can open the import in their permitted directory and submit a file. **Failure:** Signed-out users, non-admins and admins outside the target scope cannot submit or get protected import data, including by going directly to the operation boundary. **Boundary:** Another admin in the same scope cannot retrieve an attempt owned by the submitter through this feature. **Surface and confirmation:** Exercise entry, direct submission and result lookup with the identities in C1; inspect the authoritative directory for zero writes on denied submissions.
- **C2 / Revocation.** **Positive:** The authority uses current permission for the create decision and before releasing protected results. **Failure:** Revocation ordered before the write decision prevents any create. **Boundary:** Revocation ordered after commit leaves created accounts in place, denies later result reads and clears the import view when the client learns of the change. A response from an old session or scope cannot populate its replacement. **Surface and confirmation:** Control both orderings at the authority, then read back the directory and attempt result lookup through the revoked session.

**State and service boundary.** The product's authorization authority owns identity, role and permitted directory. The attempt binds to the authenticated submitter and verified target scope. The upload conveys proposed users only. A filename, CSV field or client-supplied scope cannot grant permission. A stale view may display an entry point until revalidation, but it confers no write or result access. If current authority cannot be established, the operation fails closed. The feature does not alter memberships or permissions.

**Open gap.** The product owner and planning owner must identify the real admin permission, scope boundaries, revocation semantics and test identities before access integration. Verify that authority changes and account writes can honor the ordering in C2. The direct denial contract is independent of the final role names.

### R-2 CSV intake and validation

**Basis and delta.** Incoming request, 2026-11-21, “Let admins upload a CSV to bulk-create users” (“The incoming request”; “upload a CSV”). Preserve applicable field validation. Add file selection and full-file validation before any create. No existing import format, user schema or upload capacity was supplied. Verify against the real schema and chosen runtime before fixing the public format or limits.

**Proposed file contract.** One UTF-8, comma-delimited file per submission, with an optional UTF-8 BOM, LF or CRLF record endings, and a final newline allowed. The first record is a header. The provisional header is exactly `email`, case-sensitive. Quoted fields are parsed as fields, including commas within quotes and doubled quotes as a literal quote. The parsed value then goes through the user field rules. Ignore records with zero content after the header. A whitespace-only or quoted empty value still goes through field validation. At least one data record is required. Row references are one-based logical record numbers including the header and any ignored empty records. The upload content determines validity.

- **C3 / File and shape.** **Positive:** A correctly shaped file reaches row validation. **Failure:** Reject unreadable or invalid UTF-8, malformed quoting, missing or unsupported headers and incorrect field counts before any create. Identify the file or first reliably identified bad record and give a correction. **Boundary:** Empty and header-only files create zero users. BOM, CRLF, a quoted field and a final newline are accepted under the proposed contract. **Surface and confirmation:** Submit the named files in C3 through the import boundary. Assert the failure category or expected parsed identity and inspect the directory after each submission.
- **C4 / Values and privileges.** **Positive:** Eligible rows supply only the supported creation fields. **Failure:** A missing required value or value rejected by the account rules is reported with row number, field and correction. Attempts to supply a role, scope or credential column are rejected as unsupported input. **Boundary:** A quoting-valid field may still be invalid as an account value. **Surface and confirmation:** Inspect row errors and authoritative records using C4, including role and scope on a valid created account.
- **C5 / Capacity.** **Positive:** A valid file at each confirmed supported limit can be submitted when all other limits allow it. **Failure:** An oversized or over-row-limit file receives a useful limit message and writes zero users. **Boundary:** Compare each confirmed limit and the first rejected value above it. **Surface and confirmation:** Inspect upload and response behavior on the target runtime, including its outer upload boundary, and read back the directory.

**State and data.** The submitting admin owns the file in their local filesystem. Selection is a transient draft in their active admin view. The product processes a transient copy under the submitting identity and directory context. Selecting, replacing or clearing the draft never creates users. Replace or clear is available before submission. Once sent, the attempt is bound to that submission's input. The product discards the raw copy and parsed working data once processing finishes or is abandoned. No product copy is available to other clients, in upload history, or in diagnostic logs. The admin's original local file remains under their control.

**Open gaps.** The planning owner must confirm create fields, allowed defaults and field validation with the account owner; the product owner must resolve any necessary schema or format differences. Before upload integration, determine byte, row and processing quotas from the target runtime and operating workload, accounting for any upstream limit. Confirm cleanup on rejection and interruption. C5 remains open until limit values and a reachable target exist.

### R-3 Create the batch and protect user records

**Basis and delta.** Incoming request, 2026-11-21, “Let admins upload a CSV to bulk-create users” (“The incoming request”; “bulk-create users”). Preserve single-user rules for identity, uniqueness, permissions, account lifecycle and any mandatory creation effects. Add one explicit submission that creates the batch. Atomic batch and reject-on-duplicate are proposed product defaults for predictable correction. Actual identity rules and write capabilities were not supplied. Implement and verify at the directory authority.

- **C6 / Create and read back.** **Positive:** Submitting an eligible batch creates one durable account for each row, and authorized reads begun after success can see the created accounts through normal user administration. **Failure:** If the batch cannot complete, create zero accounts from it and preserve existing account contents. **Boundary:** One eligible row is a valid batch. **Surface and confirmation:** Read the authoritative directory before and after both the multi-row and one-row cases. Compare actual identity, scope and ordinary account privileges. For the fault case, demonstrate the failure after the first proposed write and confirm zero committed accounts from the batch.
- **C7 / Duplicates and competing creates.** **Positive:** Distinct, eligible identities can be created together. **Failure:** Any collision within the CSV or with an existing identity rejects the whole batch. Report the implicated rows where disclosure is allowed, and preserve existing accounts. Use a generic conflict for identities the admin cannot inspect. **Boundary:** Overlapping imports or a concurrent ordinary create are ordered at the identity authority. At most one creates a shared identity, and a losing import creates none of its other rows. **Surface and confirmation:** Compare authoritative identity sets and existing account attributes after within-file, existing-account and competing-create cases.
- **C8 / Correction and ambiguous completion.** **Positive:** After a definitive rejection, the admin can correct the file and make a new submission. **Failure:** A lost or delayed acknowledgment yields an unconfirmed state until the same attempt can be reconciled. Repeating that attempt with the same content returns its pending or terminal state without a second write. Reuse with different content is rejected. **Boundary:** If an unconfirmed attempt expires or reconciliation is unavailable, the UI makes the uncertainty explicit and directs the admin to check the authorized directory. An expired or unverifiable retry cannot start a new create. A fresh submission requires deliberate action and normal duplicate checks. **Surface and confirmation:** Interrupt delivery after commit, repeat the original intent, then compare the authoritative accounts and receipt. Repeat after expiry and with altered content.

**State and service boundary.** The user directory is the write and read-back authority. Before commit all rows must be eligible under current account rules and uniqueness in the directory's actual identity namespace. On commit only the eligible batch accounts are added. Existing accounts and unrelated changes are preserved. Concurrent decisions use current account state; a previous validation result cannot override a newer account or permission change. Import recovery reconciles with the authoritative outcome before allowing the original attempt to run again. A failure with an unknown write result cannot be displayed as a definitive rejection.

**Domain limits and open gaps.** Updates, merges, role assignment, password import, and a new activation or invitation workflow are outside scope. Which existing activation, notification, billing, audit or other effects a normal create triggers is unknown. The account owner must confirm identity normalization, uniqueness scope including inactive accounts, and default privileges. Before write and recovery integration, the planning owner must establish that the selected authority supports the proposed atomic outcome, mandatory effects and outcome reconciliation, including interruptions. Any mismatch goes through scope correction before dependent work. Never guess which accounts to delete after an uncertain result.

### R-4 Import feedback and result lifecycle

**Basis and delta.** Incoming request, 2026-11-21, “Let admins upload a CSV to bulk-create users” (“The incoming request”; “upload” and “create”), with consumer feedback inferred so an admin can tell what happened. Preserve normal directory visibility rules. Add an admin import view and truthful progress and results. The established UI, operational controls and retention policy are unobserved. Implement and verify with the applicable product conventions.

- **C9 / Submit and feedback.** **Positive:** The import view shows format requirements, selected file and an explicit **Import users** action. It shows in-progress status after submission and confirms the actual created count only after authoritative commit. **Failure:** Rejection shows zero created with actionable file or row errors. An ambiguous completion says the result is unconfirmed and provides the recovery in C8. **Boundary:** Before file selection, submission is unavailable. Rapid repeated activation for the same pending intent cannot launch another batch. **Surface and confirmation:** Observe the authorized UI with responses held pending and then released as committed, rejected or unconfirmed. Compare displayed outcome and count with authoritative state.
- **C10 / Result isolation and cleanup.** **Positive:** Only the authorized initiator can recover their attempt during its recovery window. Authorized operators can investigate the attempt by safe correlation. **Failure:** On sign-out, scope change or loss of permission, discard the client's protected import state and deny protected reads. **Boundary:** At expiry, the receipt is no longer available or eligible to create; it contains no raw rows or credentials during its lifetime. **Surface and confirmation:** Inspect the UI, operation response and permitted diagnostics across loss of authority and expiry, including a late response. Check transient and retained data for prohibited payloads.

**Interaction and lifecycle.**

| State or resource | Owner, readers and lifetime |
| --- | --- |
| File draft and displayed status | Active admin view, visible to its authorized operator. Clear on exit, logout or scope change. Ignore results for a superseded view, account or scope. Dismissing the view does not cancel an already submitted write. |
| Attempt and receipt | Product import operation under authenticated actor and target. Show pending, committed, rejected or unconfirmed as appropriate. The product correlates retry to the original intent and retains only the protected binding, outcome, counts and safe row references/reasons necessary for recovery. The operation needs recoverable evidence of commit before reporting success, including after an interrupted response. Expire and remove receipt data under the approved recovery policy. |
| Created accounts | Authoritative directory, visible under existing directory policy. They persist as ordinary accounts and follow existing account lifecycle and deletion rules. |
| Operational outcomes | The import operation owns distinct outcomes for denied submission, validation rejection, committed creation, clean write failure and unresolved/reconciled completion. Authorized operators can identify them by opaque correlation, outcome and counts where appropriate. Reuse adequate existing coverage. Omit raw CSV, filenames, personal row values and secrets. Verify coverage and redaction at the actual destination. A diagnostic failure cannot relabel the business result; any mandatory audit dependency must be settled before writes. |

**Service boundary.** The admin view submits a file and receives progress or outcome. In-progress feedback is provisional. The operation authority owns any processing that survives view exit and any resumption or reconciliation covered by the final design. No additional provider boundary is established. Separate subscriptions, notifications, incremental event cursors and a cached directory projection are inapplicable because this contract requires one batch result and authoritative read-back. Provider login instrumentation is outside the import scope.

**Open gaps.** The planning owner must confirm the real admin entry point, product UI components, supported response/recovery channel, runtime execution and storage quotas, and ability to recover authoritative outcomes. The product and operations owners must confirm receipt and diagnostics retention, deletion, operator access and audit failure policy before affected integration. Confirm the smallest useful recovery window consistent with applicable retention. Browser draft and result states can be designed without settling those values.

## Non-functional requirements

- **Capacity and compatibility (R-2, R-3, R-4).** The runtime and workload are unresolved. Before selecting supported byte, row, request-time, working-storage or retained-state limits, establish the platform's hard constraints, including concurrent import demand. Verify acceptance at the supported bounds, fail-safe rejection above each hard-facing bound, and truthful pending feedback under a controlled delay. No latency, throughput, availability or cost target is established by the request.
- **Integrity and privacy (R-1 through R-4).** Under stale authority, overlapping writes, a lost response and interrupted processing, confirm the directory, result surface and operational records satisfy C2 and C6–C10. Verify purging for rejection, success, abandonment and expiry using the real storage and operational controls. Numeric retention, platform recovery capability and applicable compliance rules are unresolved.
- **Designed admin interface (R-2, R-4).** Use the visual reference in [Light expressive starting point](GUIDES/platforms/ui.md#light-expressive-starting-point). For the assumed web surface, start light with a dark option. Inherit established identity and platform conventions when available. Where choices are open, use the light Google Gemini look as a reference with Material 3 Expressive principles: airy composition, softly rounded tonal surfaces, clear type hierarchy and a restrained accent that gives the file selection and primary action prominence. The plan chooses the concrete treatment.
- **Rendered acceptance (R-4).** Review empty, selected-file, loading, success, rejection and unconfirmed states in both themes. Verify consistent spacing and type scales, a cohesive palette, one icon set, visible keyboard focus and WCAG AA contrast. At supported narrow and wide widths, the action and errors remain readable and reachable without horizontal overflow. Use motion only to explain changes and honor reduced motion. Verify keyboard and touch selection, submission and recovery. A controlled delay and response must produce accessible status changes without unexpected focus shifts. Use browser rendering, keyboard and assistive-technology checks, contrast measurements and reduced-motion checks. Supported browsers and viewport range must be set from the product surface.
- **Support scope (R-4).** Confirm owned operational outcomes, safe diagnostic retrieval and redaction with authorized operators. Bulk account edits, downloadable error reports, progress notifications and permanent import history are excluded because the requested upload and outcome can be handled in the import view and normal directory.

## Behavior model

| Flow | Actor, ordered actions and outcome |
| --- | --- |
| F-1 Start and validate | Admin enters the authorized scope (T-1), selects one file and explicitly submits it (T-2). The operation validates the immutable submission (T-3). An invalid file ends with a correction and zero writes. |
| F-2 Commit and observe | For an eligible file, the operation asks the user directory to make the create decision (T-4). The directory commits or definitively rejects. The authorized admin receives that outcome and can read created accounts after commit (T-5). |
| F-3 Correct or recover | A definitive rejection permits correction and a new submission (T-2). An interrupted response leaves the outcome unconfirmed. The admin checks the original attempt (T-6). Revocation and expiry can deny further access (T-7). |

| Transition | Guard, effect and acceptance case |
| --- | --- |
| T-1 / R-1 | Identify actor and scope from current authority. Admit an authorized admin to the empty view. Deny unauthorized entry, direct submission or result lookup without exposing protected data (C1). |
| T-2 / R-2, R-4 | In an authorized view with a draft, explicit submission fixes the input for this attempt and displays pending. Before submission, replacement affects only the draft. No file or repeated activation while pending cannot initiate another batch (C3, C9). |
| T-3 / R-2 | Validate shape, scope-independent field rules and confirmed limits before mutation. The eligible batch advances. Errors terminate the attempt with zero writes and correction details (C3–C5). |
| T-4 / R-1, R-3 | Recheck authority and authoritative identity eligibility at the write decision. A valid, authorized batch commits together. A precommit conflict, revocation or clean failure creates none. An ambiguous reply goes to reconciliation (C2, C6–C8). |
| T-5 / R-3, R-4 | Release final outcome only to the current authorized initiator. Committed receipt counts agree with actual writes. A definitive rejection shows zero created. Pending or missing evidence cannot produce a success message (C6, C9). |
| T-6 / R-3, R-4 | Under current authority, recover a still-valid same-intent attempt. Pending stays pending, a known terminal result is returned, and an unverifiable result stays unconfirmed. Changed or expired retry input cannot produce a write (C8, C10). |
| T-7 / R-1, R-4 | On view exit, session or scope change, or expiry, clear the applicable draft or result state and refuse stale result access. No cancellation or rollback of an already submitted write is implied. Apply the T-4 ordering if revocation races with commit (C2, C10). |

## Acceptance walkthrough evidence

The following are manual spec-level walks using the independent expected directory changes, current authority guards and result transitions above. Each case starts afresh unless its sequence says otherwise. These are conditional walks in a synthetic model. The ability to provision the starting identities and directory in a real product is **NOT-REPLAYED: no target, runtime or fixture authority was supplied**. The future product-acceptance owner verifies the normal admin journey and directory read-back. The system-test owner verifies direct access, ordering, fault recovery, cleanup and operational event coverage at the actual boundaries. The product-acceptance owner also verifies rendered quality, using the supported browsers and widths once confirmed. No executable product verification occurred.

**Fixtures.** Directory **North** has admin **Avery**, admin **Morgan**, non-admin **Blair**, and ordinary account `owner@example.test`. **Casey** administers **South** only. All other example addresses begin absent in North. Assume an authorized fixture owner can create these starting conditions and revoke Avery's North admin rights without deleting accounts. The baseline file **pair.csv** has bytes `email\nada@example.test\nlee@example.test\n`, where escapes denote literal line breaks. **one.csv** is `email\nada@example.test\n`. Fixtures use the provisional schema and identity contract from the scope section.

| Case | Manual walk and recomputed oracle |
| --- | --- |
| C1 | Apply T-1 to Avery, Blair, Casey and a signed-out client targeting North. Only Avery among these four can reach T-2. Submit `one.csv` directly as each denied actor; North stays at its starting accounts. Let Avery submit `one.csv` and record its attempt reference. Under T-5, Morgan can read Ada in the ordinary directory but cannot retrieve Avery's receipt even when given its reference. |
| C2 | Avery submits `pair.csv` through T-1–T-3. With the eligible batch paused before T-4, revoke Avery, then allow the write decision. North gains neither Ada nor Lee. T-3 rejects each, with North unchanged. With bytes `EF BB BF` followed by `email\r\n"ada@example.test"\r\n`, T-3 yields Ada and T-4 creates exactly Ada. |

## Submission

**summary**

- Defined the admin CSV upload and bulk-create contract, including authorization, input validation, conflict handling, correction and outcome feedback.
- Assumptions are an admin web surface, one UTF-8 CSV per submission, the provisional email-only fixture format and identity rules, a create-only atomic batch with duplicate rejection, and an initiator-only result with bounded recovery. These fill open choices for the specification and do not establish existing product policy.
- Open prerequisites are the actual user schema and identity namespace, admin scope and revocation ordering, compatible creation effects and recovery, runtime quotas, UI conventions, and retention and audit policy. No material conflict was observed. A conflict with required single-user effects or the authority's capabilities would keep dependent work unready and require correction through the existing review route. Independent spec and interaction work can proceed. Runtime checks are unverified and remain due at their assigned boundaries. No person-only check has been established.

**primary**

- R-1 / C1 — authorized administrators can reach and submit the import.
- R-2 / C3 — the import accepts a supported CSV and interprets its records.
- R-3 / C6 — one submission creates multiple usable directory records.

At product-acceptance, at most one primary requirement can remain unverified, and only with a passed lower-layer test covering that requirement. No such test result is available for this standalone stage.
