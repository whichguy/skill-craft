# User Administration Specification

## Scope and basis

The 2026-11-21 incoming request, under **The incoming request**, is “Let admins upload a CSV to bulk-create users.” It authorizes an admin-facing import into the product's user records. The stage instructions under **The stage** govern acceptance and evidence. This workspace supplies no prior spec, discovery, research, selected baseline, reference system, or runtime. Existing product behavior and policy remain unknown. Preservation statements describe the intended relationship to the ordinary user workflow and require the checks listed below.

The product default is a create-only, all-or-nothing batch in the currently authorized user scope. The import adds no account roles, upload history, or sharing surface. Ordinary user creation remains the authority for the account fields and lifecycle it actually supports.

## Requirements

### R-1 Admin access to CSV import

**Basis and delta.** The 2026-11-21 request “Let admins upload a CSV to bulk-create users” (**The incoming request**, “Let admins”) adds import to authorized user administration. It preserves ordinary sign-in, administrative scope, and user visibility rules. **Evidence and pending work.** The request identifies the actor. Permission names, scope boundaries, and current access behavior were unavailable. Implement the entry and authority checks and verify the following clauses on the real admin and mutation surfaces.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| Entry | A signed-in admin currently authorized to create users in the active scope can open **Import users** from user administration. | A signed-out, expired-session, or signed-in non-admin actor sees no usable import action. A direct attempt is denied without exposing file or user information. | Admin authority in a different scope conveys no access to the active scope. A global deployment applies the same rule to its user directory. | Admin UI and actual upload boundary. Compare the authorized, signed-out, expired, non-admin, and wrong-scope identities in C1. Verify there are no writes on denial. |
| Mutation authority | The user authority validates admin create permission at submission and still requires it at the commit boundary. | Revocation or session expiry effective before commit rejects creation. Reject a submitted scope the actor lacks authority over, even if the interface cached prior permission. | A write committed before revocation remains committed. Subsequent requests and delivery of any pending result require current access. | Exercise the actual authorization and account boundaries in C1 and C6. Confirm account state from an independently authorized observer. |

**State and service contract.** The affected resources are the actor's existing session, create grant, and active user scope. The existing identity and permission authority owns these records. The import reads the current grant and writes no access assignment. The UI may reflect the last known grant, while the mutation and response use the authority's current decision. A committed batch and a revocation must have a determinate order. On denial with an available interface, clear import state and direct the actor to the existing sign-in or access flow as applicable.

**Domain rules and open gap.** The request leaves scope derivation, exact admin entitlement, expiry and revocation semantics, and the ordering guarantee open. The defaults are to require both admin status and existing create authority in the active scope, with fresh permission at commit. The product/identity owner must identify the actual actors and provide authorized scope and revocation controls before the affected integration is planned and verified. A person with access owns the check at the boundary it gates if this authority cannot be accessed by the run. CSV format work can proceed independently.

### R-2 CSV selection, submission, and validation

**Basis and delta.** The 2026-11-21 request “Let admins upload a CSV to bulk-create users” (**The incoming request**, “upload a CSV”) adds a file selection and upload path. It preserves the ordinary create path's field validation for fields it owns. **Evidence and pending work.** Format and application input limits below are defaults supplied by this spec. The ordinary account field contract and platform envelope were unavailable. Implement and verify file and field handling on the admin upload and authoritative validation surfaces.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| Select and submit | The import offers a labeled file chooser, format instructions with the C2 example CSV, and an explicit **Create users** action. Selecting or replacing a file alone writes no users. | Without a file the action is unavailable. If file selection or transfer fails, show a recoverable error. Apply R-4 if the service disposition is unknown. | One file is selected per submission. Before submission, removing or replacing it discards the old selection and clears that selection's errors. | Admin UI and actual upload boundary. Follow C2 and verify that only explicit submission reaches account creation. |
| Parse file and schema | Accept comma-delimited, valid UTF-8 CSV with an optional initial UTF-8 BOM, LF or CRLF line endings, and optional final line ending. The first record is the header. It contains `email` exactly once and may include `name` exactly once, in either order. Header names are case-sensitive and literal after CSV decoding. Support quoted fields, commas and line breaks inside quotes, and doubled quotes inside quoted fields. | Reject an empty or undecodable file, malformed quoting, missing or repeated header, unknown column, or a nonblank record with a different field count from the header. Show a diagnosable file error or logical row error with zero users created. | Ignore empty physical lines after the header outside quotes. A whitespace-only line or explicit empty field is a data record. Filename suffix and declared media type do not determine CSV validity. Compressed files, other encodings or delimiters, and spreadsheets are outside the CSV contract. | Upload boundary and admin error display. Compare the valid and invalid C3 fixtures and independently inspect user state. |
| Apply file limit | A valid CSV of up to **1,048,576 bytes (1 MiB)**, inclusive, is eligible for processing. Count all original file bytes including any BOM, line breaks, and ignored lines. | Reject a file of 1,048,577 bytes or more and report the file-size limit. No users are created. | This is a limit on the file's bytes. Transport overhead does not count. The exact-at-limit file remains eligible. | Upload the exact adjacent files in C4 through the actual boundary. Verify acceptance at the limit and the specific size error immediately above. |
| Apply record limit | A valid CSV with **1 to 1,000 logical data records**, inclusive, is eligible for creation. Count nonempty records following the header, including records later rejected for field validation. | Reject zero data records with a no-users-to-import error. Reject 1,001 or more data records with a row-limit error. No users are created in either case. | Header, skipped empty lines, and embedded quoted line breaks do not add to the count. A single valid record is allowed. | Compare counts and user effects in C3 and C4. Verify that the file and row limits fail independently. |
| Validate account fields | Trim surrounding spaces and tabs from decoded field values. Validate `email` and a supplied nonblank `name` under ordinary account creation rules. Send a missing or blank `name` through the ordinary omitted-name behavior. | A missing or blank email, invalid email, or rejected account field produces a row-level reason and zero users created. A record with the wrong field count follows the schema rule. | Use 1-based logical CSV row numbers with the header at row 1. Skipped empty lines consume no row number. A quoted value spanning lines still has one row number. Credential, role and scope columns are unknown columns and cause rejection even when blank. | At the UI and authority, use C3 and C5 to check the reported row and reason, and absence of writes. Confirm the production field rules using ordinary account creation before treating the default schema as compatible. |

For overlapping errors, check the file byte limit first, then decoding and CSV structure (report the first structural error in file order), then the record limit, then field validation, then conflict validation. Within the first failing row-validation stage, report the lowest affected logical row with its reason. R-3 describes conflict attribution.

**State and data.** The initiating admin owns the selected file reference while the import is open. Only that client context uses the selection and can replace it before submission. File bytes go only to the authorized import boundary. The application holds uploaded bytes and parsed row values only as long as needed for that attempt, including abort or failure cleanup. The application neither stores a durable upload copy nor includes filenames, raw rows or field values in logs. The initiator's own UI may show the selected filename and safe row-number diagnostics. There is no saved draft or rejected-row export. Clearing, replacing, or leaving the import removes the selection from the application UI and releases its reference without deleting the admin's local file. Submission freezes the selected file for that attempt.

**Domain rules and open gaps.** The request omits CSV dialect, field names, encoding, cardinality and file bounds. The stated defaults support ordinary small administrative batches and a narrow field contract that does not let the file assign access. The product/identity owner must confirm that email and optional name can provision an ordinary account without other required fields and identify the actual syntax, length and omitted-value behavior. The runtime owner must verify deployed request, buffering, execution and response limits before committing to the default envelope. Document the exact target and primary documentation or probe result. These gaps affect account-field integration and deployed capacity, while format modeling and size/row boundary checks can proceed independently.

### R-3 Create the complete batch exactly once per account identity

**Basis and delta.** The 2026-11-21 request “Let admins upload a CSV to bulk-create users” (**The incoming request**, “bulk-create users”) adds creation of multiple ordinary users in one authorized submission. Existing user and access records and the ordinary account lifecycle are to be preserved. **Evidence and pending work.** All-or-nothing behavior, duplicate outcomes, and the default comparison below are spec decisions. The actual account identity, capability for atomic publication, and provisioning behavior were unavailable. Implement and verify the creation and conflict rules against the real authority and normal user administration view.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| Persist new users | When every row is valid, every identity is available, and permission is current, one submission makes the entire batch durable as ordinary users in the active scope. Success includes the exact committed count. A fresh, authorized user listing or lookup shows each expected account and supported name. | An authoritative rejection before publication leaves zero users from that attempt. An unexpected write failure may be reported as a known failure only after the authority establishes zero published users. If disposition is indeterminate, apply R-4. | The smallest allowed batch creates one. A valid 1,000-row batch creates 1,000. Preserve pre-existing users, their IDs, fields, and access. Raw input cannot assign passwords, privileges, or scope. | At the real mutation and user-read surfaces, compare the pre/post identity set, values, and count for C2, C4 and C7. Inject a failure after the first candidate write and verify zero durable records from the batch. |
| Reject duplicate identities | A batch of distinct, available identities is eligible to commit. The default key for the supported ASCII sample addresses is email after trimming and case-insensitive comparison, within the authority's actual uniqueness scope. | A repeated key in the CSV or a key already reserved by the authority at the commit boundary rejects the whole batch. Report the later logical row for a repeat and the matching row for an existing-account conflict, without revealing account data or whether the conflict is outside the visible scope. Within one row, prefer the in-file repeat reason over existing-account conflict. | Active accounts and any disabled, pending, or deleted identities the authority still reserves conflict. A genuinely released identity is eligible. Other scopes are relevant only where the authority uses a shared key. Retrying an unchanged committed file yields conflicts with zero extra users. | C5 and C7 compare exact row attribution and the authoritative user set, including existing ID and fields. Add the actual reserved-state and uniqueness-scope cases once established. |
| Resolve simultaneous changes | Concurrent attempts with disjoint available keys can both commit. For overlapping keys, the first authoritative commit wins and the conflicting batch creates zero. Ordinary user creation competes under the same uniqueness rule. | A precheck that has become stale cannot authorize a conflicting write. A conflict discovered at commit still gets the safe conflict result. | The winner is determined at the authority, independent of upload order and UI timing. A repeated submit while pending is suppressed in the initiating interface; overlap through another tab or actor still follows the same account rule. | At the real authority, use C7 with controlled commit order and verify both actors' results plus the user set. |

**State and service contract.** The target is the product user authority's account collection and identity reservations for the authorized scope. The authority owns IDs, account fields, grants, and durable reads. Authorized admins see only what normal user administration allows. Import adds only the batch's new ordinary users. It uses current grants and uniqueness data at the write boundary and never replaces a cached snapshot of account state. A batch moves from candidate values to either the entire durable set or no durable users from that attempt. An interrupted response does not determine which happened. Ordinary account lifecycle rules apply to committed records, including their normal retention and removal. Import does not create additional durable row data or provide undo or bulk deletion. Recovery is whole-batch rejection before publication, or ordinary lifecycle management after confirmed publication. Use authoritative readback for reconciliation.

**Domain rules and open gaps.** Confirm the exact uniqueness key and scope, reserved states, ordinary role/status, required provisioning and side effects, and whether the real authority can satisfy atomicity and live permission ordering. The default is ordinary non-privileged provisioning with no import-specific invitations or credentials. The product/identity and runtime owners must resolve those gaps before dependent implementation. If mandatory provisioning exposes partial accounts or effects that the authority cannot make consistent with the batch promise, record the conflict and obtain a supported design or product decision through the correction route. Reconfirm synthetic email and name fixtures against the production contract. Third-party provisioning is unverified and no separate integration is assumed.

### R-4 Report import status and support safe recovery

**Basis and delta.** The 2026-11-21 request “Let admins upload a CSV to bulk-create users” (**The incoming request**, upload and creation outcome) implies feedback that lets the admin tell whether users were created and act on errors. This adds attempt status while preserving normal permissions and the normal user view as the durable source. **Evidence and pending work.** The interaction and data lifetime are spec defaults. There was no consumer interface, telemetry sink, or runtime to inspect. Implement and verify the feedback and recovery on the real UI and check event coverage at the actual owned boundary.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| Pending and completion | After submission, show and announce pending status until there is an authoritative result or the interface loses the ability to know it. A confirmed success shows the created count and a way to open the user list. | A known rejection shows zero created and the authorized diagnostic, with a clear way to select a corrected file and submit again. A transfer interruption, timeout or lost response with unknown disposition says it could not confirm the result and directs the admin to the authorized user list before a manual retry. | Upload receipt and elapsed time never display success. There is no automatic retry. A response from an earlier attempt or session cannot overwrite a newer selection, outcome, or access state. | In C2, C5, C6 and C8, control response timing and access and compare UI/status announcements to independent authoritative account observations. |
| End or resume interaction | A result can be read in the initiating authorized import context until it is replaced, cleared, or the context ends. After an unknown result, an authorized admin can reopen ordinary user administration, look up expected accounts, then manually submit a file for remaining accounts if appropriate. | Closing the UI, losing access, or disconnecting does not promise cancellation or rollback. A client that changed identity or active scope receives no old result. | Pending work may commit within the original authority operation if it still meets R-1 and R-3. No durable import job, resumable upload, or cross-session result is offered. Presence of a user proves that account exists, including when another actor could have created it. | C6 and C8 observe the same and replacement contexts and authoritative reads after a lost response. Confirm retries obey R-3. |
| Observe owned outcomes safely | The responsible application boundary provides a safe correlation ID, outcome category and created count for known outcomes, and a safe reason category for rejection or interruption when observed. Reuse adequate authoritative coverage. | When a completion is unavailable, diagnostics do not assert that creation happened. A diagnostic sink failure does not alter the account result or mask the original business failure. Preserve any separately mandated audit obligation as an open compatibility question. | Categories distinguish confirmed commit, validation or conflict rejection, authorization denial, and observed interruptions or internal failures. Omit the file, filename, email, name, other row data, credentials and tokens. No duplicate provider-owned event is required. | Authorized operational retrieval and redaction check in C8. Compare categories and counts to actual outcomes and exercise sink failure. Verify normal account lifecycle audit coverage where it applies. |

**State, UI, and service contract.** The initiating UI owns empty, file-selected, pending, success, rejected and unknown presentation states. The application authority owns the disposition of the original operation. Only the initiating context with live access receives its result. Keep the UI result in that context and discard it on replacement, clear, exit, or loss of access. An administrative client sends a submission and receives the disposition or reports uncertainty. There is no subscription, incremental import-result feed, or cross-session cache to refresh for this one-shot operation. Refresh ordinary authoritative user reads for recovery. No new remote service, webhook or background queue is required by this behavior.

The file chooser and format example explain the input. The primary action communicates when creation begins and is unavailable while pending. Pending and result regions announce status, preserve usable keyboard focus and keep recovery actions visible. Show error reasons with row numbers where applicable. Keep the same visual hierarchy between empty, selected, pending and result states, with the appearance criteria below.

Authorized operators alone read safe diagnostics. Reuse the product's access, retention and purge policy for those events. Product accounts stay under their ordinary retention policy. In-flight data is bounded by R-2 per attempt and import UI state by one selection and one active submit per context. Bulk concurrency, operational log quotas, hosting limits and their runtime enforcement remain to be established.

**Domain rules and open gaps.** The request leaves disconnect behavior, attempt history, audit and result retention open. The default is an attempt-scoped result, manual recovery through the user directory, and reuse of current diagnostic capabilities. Runtime/operations owners must establish timeout behavior, cleanup on abrupt termination, diagnostic coverage, retention/purge and authorized retrieval on the chosen runtime before related integration and verification. If existing events omit an observable owned outcome, add coverage at the owner boundary and verify safe retrieval there. A mandatory audit gate that conflicts with the ordinary diagnostic-failure behavior must be resolved before dependent work. Pure presentation states can be specified independently.

Existing account/event retention and applicable compliance or deployment controls are unresolved and require the product/runtime owners' policies before release-dependent work.
