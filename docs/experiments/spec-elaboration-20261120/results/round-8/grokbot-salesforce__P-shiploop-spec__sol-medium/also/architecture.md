# Grok Bot for Salesforce architecture

## Decisions

### AD-1 — Salesforce-hosted Lightning entry and invocation

**Status.** Selected for the specification. Target binding and platform compatibility are pending under R-1.

Use a Lightning Web Component exposed through a Salesforce Lightning component tab. The tab and scoped visibility are deliverables separate from the component itself. Use an imperative, non-cacheable Apex operation called as the signed-in user for each Send. Give the dedicated access grant the tab visibility, Apex class access and required external credential principal access. Validate both effective entry and invocation permissions separately. Existing Salesforce identity controls remain authoritative, with no application login and no CRM data access. Use transient view memory with an attempt marker for late-result suppression. A server-side callout keeps provider authentication out of the browser and permits enforcing input checks and normalizing errors at the actual invocation boundary.

A separate hosted web app would add a deployment target and identity boundary. An Agentforce implementation could introduce additional org entitlement, configuration and assistant tooling prerequisites for the assumed plain-text use case. The native tab and explicit provider invocation are the working selection. The intended runtime entry is the Grok Bot custom tab in the App Launcher. The API name and URL are pending collision inspection in the actual org. The implementation owns the component, tab and access metadata and the invocation class. The operator reads back current org metadata, permissions, compatibility and edition before making any change, then verifies the approved revision and effective grants using the intended and denied identities. Revalidate this decision if the target or consumer surface changes. ### AD-2 — Direct, foreground xAI Responses request

**Status.** Selected provider route for the specification, conditional on the team's model, retention policy, callout limits and approved credential configuration (R-2 to R-4).

Use modern Salesforce Named Credentials and a Custom External Credential with a Named Principal to call the approved xAI endpoint over HTTPS. The principal holds an administrator-provisioned dedicated key for the approved team/model. The external credential custom header supplies Bearer authentication, with generated authorization disabled and header formulas enabled where required. Metadata carries references and safe configuration only. The runtime uses the Salesforce user's principal access. Salesforce controls that access, and xAI controls key and model eligibility. Keep endpoint and model selection under administrator control. No client-provided endpoint, model or credential is accepted.

Use one non-streaming POST to the xAI Responses operation per admitted prompt. The request supplies the selected model and the normalized single user input with `store: false`. It omits tools, prior-response identifiers and Salesforce identities. Raw response parsing checks successful HTTP completion, the completed response status and usable assistant message output text in provider order. It ignores reasoning, other output item types and raw errors. Configured limits and timeout must fit the selected model and the full Apex transaction, including request/response heap use. Verify that the team's selected API/model actually supports the necessary output controls and that legitimate sample questions complete inside the configured deadline. Provider audit retention is separate from response retrieval storage. Check team policy, including any zero-data-retention feature compatibility, before enabling the live route.

Apex initiates the call synchronously while the browser waits asynchronously. An abandoned view suppresses its late reply. It makes no cancellation claim about the provider. Use the real target route for verification and sanitize all evidence. Use the native org diagnostics surface if suitable. Verify coverage for platform admission outcomes, plus retrieval, redaction, retention and drop behavior for distinct app-observed outcomes. Select any extension only after checking the confirmed org's existing coverage. Revalidate on team, policy, endpoint, model, target edition or permission changes. ### AD-3 — Lightning design foundations with a distinct chat surface

**Status.** Selected starting direction. Concrete component, token and layout choices depend on the target org's design system and rendered checks.

Use documented Salesforce Lightning design conventions and accessible controls where they fit. Own the bot's responsive chat layout and themeable surfaces within the tab. Use the light Google Gemini reference through Material 3 Expressive for visual hierarchy, tonal grouping and generous, disciplined spacing. Start the bot in light mode with an accessible dark option, keeping presentation state in the active view. Keep Salesforce navigation and host theme outside the bot's theme control. Reusing native foundations lowers integration cost and retains control behavior. An additional UI framework would add styling and runtime compatibility work for a single focused screen. Plan and validate the bot's content layout, keyboard and status behavior, contrast in both themes and reduced motion in the actual supported host.
