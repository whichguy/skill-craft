# User Administration

## Scope and basis

**Request, 2026-11-21, “The incoming request”** — “Let admins upload a CSV to bulk-create users.”

The explicit outcome is an administrator uploading one CSV and creating multiple user accounts from it. The target is the administrator’s authorized user-management scope, whether the product has one directory or several. This spec uses “Users” for the normal user-management view and “Import users” for the import entry. They are logical surfaces pending discovery of the product UI.

The standalone stage supplied no prior accepted spec, repository, discovery or research result, selected baseline, target runtime, or reference system. Existing workflows, rules and capabilities are unknown. Preserve applicable user-creation and access policies when recovered. Product defaults below are proposals grounded in the request’s scope. A material conflict goes through the existing correction route before dependent work proceeds.

## Requirements

### R-1 Admin access and CSV submission

**Basis and delta.** Request, 2026-11-21, “The incoming request” (“Let admins upload a CSV”). Add an import action in user management. Preserve the product’s current authorization and scope rules for user creation. The target authorization contract and UI have not been inspected. Implementation and checks A1–A3 are pending.

| Clause | Positive expectation | Failure expectation | Boundary expectation | Observable surface and confirmation |
| --- | --- | --- | --- | --- |
| A1. Reach the import | An authenticated administrator permitted to create users in the target scope can open **Import users** in **Users**. | A non-admin, signed-out caller, or administrator without create authority in that scope cannot use the import UI or submit directly to its backing operation. A denial reveals no file, row, user-existence or result details and causes no user changes. | Authorization follows the trusted actor and target scope even when a caller supplies a different scope or reuses a previously open view. | Users and the actual submission boundary. Check allowed and denied callers, including a scoped admin targeting another scope, and read the directory independently. C1, C7. |
| A2. Choose and submit | The admin can select one file, see its filename locally, replace or clear the selection, and submit the selected file with **Import users**. The view explains the accepted columns before submission. | Submitting with no selection is unavailable and causes no write. | Choosing, replacing, clearing or leaving before submission changes only the local draft. A second activation while the view is pending sends no new intent. | Import view and submission boundary. Observe the draft, count submitted intents, and compare directory contents. C1, C2. |
| A3. Enforce current authority | The operation checks the actor and scope before accepting the submission and requires authority at the point the batch commits. | If authority is revoked before commit, or the authority cannot establish access, no users are written. The screen loses access to protected import data when it learns access is gone. | Revocation after commit leaves committed accounts in place. **State and data.** The admin owns the draft in the current UI context. It contains a single file reference and local filename. Selecting a new file replaces the prior draft. Clear, exit, reload, sign-out, scope change or known access loss discards it. The admin’s original local file remains under their control. The product’s authorization owner controls the authenticated principal and authorized scope. The importer only reads authorization state. The imported row or a scope supplied by a client cannot grant access.

**Open gaps.** The product owner must identify who qualifies as an admin with create authority, how scope is derived, and whether an import permission already exists. The environment owner must establish how the actual auth boundary orders revocation with a write and protects result reads. Admin UI integration and live security checks depend on these findings. The product and environment owners must also confirm the supported browser/device matrix and representative wide layout before UI verification. The standalone definitions of a draft and of denied outcomes can proceed.

### R-2 CSV interpretation and validation

**Basis and delta.** Request, 2026-11-21, “The incoming request” (“upload a CSV”). Add a documented file contract and validate the full file before creation. Preserve normal user field validation. The provisional input is an email-only file for ordinary accounts. There is no observed product schema or deployed file envelope. Implementation and checks A4–A6 are pending.

| Clause | Positive expectation | Failure expectation | Boundary expectation | Observable surface and confirmation |
| --- | --- | --- | --- | --- |
| A4. Decode and parse | Read the file as UTF-8 comma-separated text. Accept an optional initial UTF-8 BOM, LF or CRLF record endings, and an optional final record ending. Quoted fields support commas, doubled quotes and embedded record endings. | Reject undecodable bytes, invalid CSV quoting or an unreadable upload as a file error with zero writes. A filename alone cannot validate content. | Ignore completely empty records outside quotes. Whitespace-only and quoted-empty records are evaluated as data. Number logical records from the header as row 1. Count subsequent empty records in row numbers, even though they produce no data rows. | Upload boundary and Import users. Send exact valid and invalid byte sequences. Check parse outcome, logical row positions and no writes on error. C2, C3. |
| A5. Require the supported schema | The first nonempty record is a single header with the exact value `email` after CSV decoding. Each data row must have one nonempty value satisfying normal account email rules. Each field is treated as data. | Reject a missing or wrong header or a header with repeated or extra columns as a file error. A wrong-width data record, missing or invalid email produces a row error. Password, credential, role and scope columns are unsupported by this file contract. | A zero-byte file reports an empty file, an empty-record-only file reports a missing header, and a header-only file reports no data rows. Each creates zero users. One valid data row is allowed. | File guidance, import result and real validation boundary. Observe the exact data rows accepted or flagged, and inspect the directory for the rejected fixtures. C2, C3. |
| A6. Enforce the supported file envelope | A file within the confirmed byte and data-row caps can be processed if all other checks pass. | If either cap is exceeded, provide a file-limit error with zero writes. Processing stays within the safe envelope even if the caller supplies no reliable size metadata. | Each cap is inclusive. Byte size refers to the supplied file bytes. The row cap counts nonempty logical data records, including rows that would fail field validation. | Import guidance and real upload boundary. Check at and one above each published limit, varying one dimension at a time. C10. |

**State and data.** The file bytes, decoded fields and error locations are transient submission input owned by the import operation while processing the admin’s selected file. They can be read by authorized import processing only and are released on completion, rejection or operation expiry. The admin gets file-level reasons or row numbers and allowed reason text. Raw cell contents and unrelated user records stay off the result and out of logs. Upload validation writes no account records. If parsing fails, any buffered rows are discarded. An error in the file structure takes precedence over row diagnostics if record boundaries cannot be established.

**Open gaps.** The product owner must confirm required fields and the existing email acceptance and canonicalization rules, including any product-specific normalization. Default to the single `email` column and existing account rules. If user creation requires additional input with no safe existing default, the schema must be reconciled before the affected create behavior can be planned. The environment owner must confirm supportable caps, time and resource budgets, where transient buffers or spools reside, and the enforceable cleanup boundary. Encoding and CSV syntax can be specified independently.

### R-3 Create users as one batch

**Basis and delta.** Request, 2026-11-21, “The incoming request” (“bulk-create users”). Add creation of one ordinary account per eligible data row in the authorized directory. Preserve the product’s account identity, uniqueness, privileges and onboarding semantics. Atomic completion and create-only behavior are proposed product defaults for straightforward correction and retry. The directory, normal account creation and provisioning contracts have not been inspected. Implementation and checks A7–A9 are pending.

| Clause | Positive expectation | Failure expectation | Boundary expectation | Observable surface and confirmation |
| --- | --- | --- | --- | --- |
| A7. Commit and expose the users | A valid, authorized batch commits one durable user per row under distinct product-issued user IDs. The intended identities and ordinary account privileges appear through the normal user-management read path after a fresh read. | Any invalid row, conflict, lost authority before commit, or definite failure before a successful batch commit rejects the whole batch. No user from that batch is left created and no creation side effects are issued for a rejected batch. | One valid row works. Existing users, permissions and accounts outside the batch are unaffected by bulk create. Report success only after the authoritative write is confirmed. | Import result and independent read of the target directory. Compare before and after by identity, count, privilege and an unrelated sentinel account. C1, C2, C4, C8. |
| A8. Reject duplicate identities | Distinct eligible identities can be created together. Identity equivalence and uniqueness scope use the normal user-creation policy. | A duplicate within the file or a collision at creation time rejects the whole batch. Report a safe row reason without returning another account’s identity or details. | Flag all rows in an in-file duplicate group. For directory collisions, use the generic row reason **Account cannot be created for this row** regardless of where a conflicting record resides. The product owner must confirm whether its existing privacy rules require a less specific result. Resubmitting a committed file against those same identities creates no additional users and leaves original IDs intact. | Import result and authoritative directory. Compare duplicate, existing, replay and nearby distinct identities against known fixtures. C4, C5. |
| A9. Resolve simultaneous changes | Concurrent submissions whose identities are disjoint can each succeed under healthy conditions and within the supported resource envelope. | When two valid batches contend for the same absent identity, at most one can create it. With both otherwise eligible and a healthy write path, one commits and the other rejects on conflict. | The same uniqueness rule applies to simultaneous ordinary user creation. A losing batch contributes none of its otherwise eligible rows. | Real shared write boundary. Arrange overlapping submissions, inspect outcomes and read back winner, shared and loser-only identities. C6. |

**State and data.** The directory owner controls persistent user records and authoritative identity mapping. The target identities are the covered file rows under normal product normalization and uniqueness scope. Before a successful commit each identity is absent from that scope; afterward exactly one ordinary account exists for each row. The batch has no effect on unrelated accounts. A failed write requires no partial user footprint. A correction is a full resubmission from a fresh validation state. New accounts follow the product’s standard read permissions, retention, deletion and access lifecycle. The CSV adds no way to supply or read passwords, secrets or elevated privileges.

**Open gaps.** The directory and product owners must confirm canonical identity, uniqueness scope, permitted conflict disclosure, required user status, default entitlements, and standard activation, invitations or other creation side effects. The environment owner must demonstrate that the real write path can prevent partial account creation and order uniqueness and authorization at commit, including collisions with ordinary creation. If onboarding triggers external effects, confirm their timing and recovery before promising the same behavior for bulk input. Atomicity versus a non-atomic directory is a potential conflict, with bulk-write planning held until confirmed or explicitly revised. CSV grammar and submission surface definition can proceed independently.

### R-4 Import feedback, privacy and recovery

**Basis and delta.** Request, 2026-11-21, “The incoming request” (“bulk-create users”). Add truthful feedback so the admin can tell whether accounts were created and recover from a failed or interrupted submission. Reuse applicable privacy, session and audit policies. No existing log, UI or target recovery behavior was observed. Implementation and checks A10–A13 are pending.

| Clause | Positive expectation | Failure expectation | Boundary expectation | Observable surface and confirmation |
| --- | --- | --- | --- | --- |
| A10. Show the operation result | Show a pending state while waiting for an authoritative outcome. On confirmed success, show the exact created count and a way back to Users. | A definitive rejection shows zero created and a file-level reason or actionable row numbers and reasons, as applicable. Keep the error and correction action visible until the admin clears, replaces or leaves. If current authorization cannot be established at disclosure, show a generic access state. | Pending and confirmation are distinct. A corrected submission replaces the prior outcome and stale updates cannot overwrite the active view or a newer submission. | Import UI and status announcement. Delay, fail, and complete real submissions and compare the message to the account read-back for the same attempt. C1, C2, C7, C8, C9. |
| A11. Recover after interruption | If delivery of the outcome is uncertain, show **Outcome unknown** while the admin remains in the view. Direct the admin to recheck the intended identities in Users and permit explicit resubmission under normal authority. | A lost response or deadline after submission shows neither success nor confirmed failure unless the authoritative outcome is known. There is no automatic retry. | Losing the view does not undo a commit. Reopening starts with an empty draft. Presence in Users establishes current existence only. A corrected attempt or repeat is evaluated on its own and does not retroactively prove who created accounts in the old attempt. | Import UI, return to Users and real write boundary. Lose the response on both sides of commit and compare the fresh directory and retry results. C9. |
| A12. Limit import data exposure | Only the submitting admin in the authorized current context can see its draft and feedback. Account emails appear on normal authorized user surfaces after creation. | No raw upload, cell contents, filename, credentials or session material in server logs, shared error feedback, or durable import history. Sign-out, scope change, or detected access loss clears the protected view. | Draft and result are view-local. Imported account records have the normal lifetime and read rules. Cleanup is governed by the confirmed execution envelope. | Separate authorized and unauthorized contexts, runtime storage inspection and log retrieval. Trace a synthetic filename and email through success, failure and cleanup. C7, C11. |
| A13. Cover owned operational events | Operators authorized by product policy can retrieve an import completion, rejection, operational failure or access denial signal from existing owned instrumentation where available, with a safe correlation reference and outcome class. | Diagnostic sink failure preserves the authoritative outcome and consumer error. A later-discovered mandatory audit rule takes precedence and needs reconciliation before acceptance. | Capture both successful and failed import outcomes without copying underlying login events. A confirmed creation count may be logged if permitted. | Authorized operational destination and real submission boundary. Inspect event ownership, redaction, retrieval, and behavior with the destination unavailable. C11. |

**State and data.** The current authorized admin view owns transient selection, pending indicator and last outcome. The processing authority owns the in-flight attempt and its outcome while it is returnable to that view. Each view displays results only for its active submission and authorized context. Separate views do not share drafts or results. Exit, context loss and replacement discard the UI result. An interrupted operation may already have committed or may terminate without writes. The contract supplies no independent background completion guarantee, persistent import history, or status-sharing channel. The product’s existing operations owner controls redacted event records and their access and disposal policies.

**Open gaps.** The environment owner must validate runtime deadline/disconnect behavior, cleanup of abandoned request data and whether safe direct completion fits the file envelope. The operations owner must identify the existing event source and destination, retrieval rights, retention and purge rules, any mandatory audit behavior, and where a safe gap must be filled. These affect recovery, redaction and operability verification. A person-only check, if required after actual access discovery, stays an unverified item for the applicable product or operations owner at handoff or the stage whose effect it gates.

## Behavior model

| Flow | Ordered interactions and outcome |
| --- | --- |
| F-1, submit and create (R-1–R-4) | Admin enters Users, opens Import users, selects one file (T-1), and submits (T-2). The import authority checks input (T-3), current permission and uniqueness and then commits (T-4). The UI shows the confirmed count (T-6). The admin reads Users to see the new accounts. |
| F-2, reject and correct (R-1–R-4) | The authority denies access or rejects a file, row, conflict, or write (T-3 or T-5). If disclosure is still authorized, the UI shows the actionable rejection (T-6). The admin can replace or clear the draft and start a new attempt (T-1, T-2). |
| F-3, reconcile uncertainty (R-3, R-4) | A pending attempt loses its confirmed response (T-7). The admin reads Users under current authority and can explicitly resubmit (T-1, T-2, T-4/T-5). A stale or unauthorized result cannot change the active view (T-8). |

| Transition | Owner and before → after | Guard, effect, failure and confirmation |
| --- | --- | --- |
| T-1 / F-1–F-3 / R-1, R-4 | View, empty/selected/settled → selected or empty | The authorized admin chooses, replaces or clears one file, or leaves the draft. Prior feedback clears on replacement or exit. No submission or directory changes. C1, C2, C9. |
| T-2 / F-1–F-3 / R-1, R-4 | View and operation, selected → pending; incoming → validating or denied | Explicit submit with a selection starts an attempt, subject to admission authorization. An empty draft or duplicate activation of a pending view produces no new intent. An unauthorized caller receives only denial. Admission and pending do not imply commit. C1, C7. |
| T-3 / F-1, F-2 / R-2 | Operation, validating → eligible or definitively rejected | Apply the file envelope, decoding, grammar, schema and row checks. When structure is intact, return row diagnostics for invalid data. File- or row-level rejection produces zero writes. C2, C3, C10. |
| T-4 / F-1, F-3 / R-1, R-3 | Authority and directory, eligible and identities absent → committed and identities present | Current authority and all identities’ unique availability must hold at the batch commit. The intended records become durable together and the authoritative outcome carries the exact count. C1, C5, C6. |
| T-5 / F-2, F-3 / R-1, R-3 | Authority and directory, eligible → rejected, no batch effects | A precommit revocation, conflict or definite write failure aborts the batch. The winner in a collision can complete. A service failure with uncertain commit proceeds to T-7 for the viewer. C4, C6–C9. |
| T-6 / F-1, F-2 / R-4 | View, pending → settled | The active view with current authorization receives a confirmed success or definitive failure. Show count or actionable error, according to that outcome, with a persistent status. C1, C2, C8. |
| T-7 / F-3 / R-4 | View, pending → outcome unknown or empty on exit | No confirmed response is available by the applicable deadline or after loss of the view. No rollback is inferred. Before explicit retry the admin can check Users, and reopening restores no import data. C9. |
| T-8 / F-1–F-3 / R-1, R-4 | View, any state → cleared on context loss, otherwise unchanged for stale delivery | Discard late or superseded updates. At result disclosure enforce current access. If disclosure is denied, clear protected feedback and selection once the view learns about the loss. A committed account is unaffected. C7, C9, C11. |

A selected draft can be canceled by clearing it or leaving. Once submitted, there is no cancel or undo action in this scope. Automatic resumption, account updates, deletions, scheduled imports, and a new invitation or notification channel are outside the requested create workflow. Existing onboarding behavior remains subject to R-3.
