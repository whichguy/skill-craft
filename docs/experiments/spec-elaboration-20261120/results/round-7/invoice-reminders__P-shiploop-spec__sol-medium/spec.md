# Invoicing

## Source and scope

The user request dated 2026-11-21, under “The incoming request,” is “Set up automatic reminders for unpaid invoices.” This defines the outcome. The timing, email channel and activation rules below are proposed defaults for choices the request leaves open.

This standalone stage has the request and the ShipLoop guides. There is no prior spec, selected baseline, repository, discovery or research result, reference product, or selected runtime. The flows below describe intended behavior. Existing product behavior, roles, integrations, data and available verification surfaces are unknown. Preserve the existing invoice, payment, access and contact workflows once discovered. The requested change adds scheduled communications and the state needed to control and recover them. Invoice creation, collections escalation, and changes to payment processing are outside this request.

## Requirements

### R-1 Enable automatic reminders for a billing account

**Basis and delta.** The 2026-11-21 request, “The incoming request” (“Set up automatic reminders”), calls for an account to use reminders without a person triggering each send. Add scoped activation and a way to stop future sends. Preserve the existing account and permission model. The account settings and authority source were unavailable for inspection. Implementation and TC-1 through TC-3 are pending.

- **A · Activation (TC-1).** Positive: an actor authorized to manage billing reminders can enable them for one billing account and read back the committed enabled state. The background runtime can act on that state with the actor signed out. Failure: invalid or uncommitted configuration returns a reason and leaves the previous effective state in force. Boundary: before the first enable the default is off. Repeating an enable while enabled retains the original activation time. **Surface and confirmation:** use the selected authorized configuration interface, read current state after sign-out and sign-in, and observe a scheduled outcome with the original session closed.
- **B · Account isolation (TC-2).** Positive: the authorized actor can read and set the state for their own account. Failure: a different account or a principal whose permission has been revoked receives an access denial without access to the other account's status or any change to either account. Boundary: permission revocation takes effect for subsequent configuration and status access, including requests from an already-open session. **Surface and confirmation:** use two accounts and revoke the actor's permission between authorized and denied requests at the configuration boundary.
- **C · Disable and resume (TC-3).** Positive: disabling stops initiations authorized after the disable commits. Re-enabling starts a new active interval and only considers future scheduled times. Failure: if the processor cannot establish the current effective setting it withholds dispatch. Boundary: an already initiated handoff may complete and must still be reconciled. **Surface and confirmation:** read back the state and compare handoff receipts when disable is ordered before or after dispatch authorization.

**State and flow (F-1, T-1 through T-3).** Account ID defines scope. The billing configuration authority owns the durable off/on state and the start time of the current enabled interval. An authorized billing actor submits enable or disable. The authority validates scope, commits, then confirms the effective state (T-1, TC-1/TC-3). Denied or invalid writes leave state and external effects untouched (T-2, TC-1/TC-2). Concurrent changes resolve in authoritative commit order. A retry or delayed request based on a superseded version must report a conflict or return the current state without undoing the newer change (T-3, TC-3). The runtime reads effective state and account scope independently of browser sessions. Revoking an individual admin's access ends that actor's access. The account-level setting remains effective until authorized disable or account closure. Account closure ends dispatch entitlement and removes the setting under the account deletion policy. If an invoice reminder is in flight, retain only the restricted reconciliation state needed by R-4.

**Domain rules and open gaps.** The default is off, with explicit account-scoped enable and disable through an authorized configuration surface. Neither the billing account model nor a roles/settings contract was supplied. Discovery/planning must identify the owners, confirm a configuration and read-back path and its conflict semantics, and establish an authorized isolated account. These prerequisites gate production setup and integration verification. Activation and access rules can be developed independently of provider selection.

### R-2 Identify unpaid invoices and stop when eligibility ends

**Basis and delta.** The 2026-11-21 request, “The incoming request” (“for unpaid invoices”), makes payable unpaid status the dispatch criterion. Add a reminder eligibility decision tied to current authoritative invoice state. Preserve invoice balances, due dates and payment decisions owned by the billing system. No status vocabulary, source freshness or consistency contract was supplied. Implementation and TC-4 through TC-6 are pending.

- **A · Payable balance (TC-4).** Positive: an issued, open, collectible invoice with a positive remaining balance and a valid due date can qualify in an active reminder window. A partially paid invoice qualifies on its remaining balance. Failure: a missing or inconsistent due date, balance, status or account association withholds the reminder and records a safe reason. Boundary: drafts, canceled or voided invoices, invoices held from collection, and invoices with zero or negative balance produce zero dispatch initiations. **Surface and confirmation:** compare the authoritative record with per-invoice outcome and dispatch evidence for a mixed set of invoices.
- **B · Current decision (TC-5).** Positive: each new handoff, including a retry known to be safe, is authorized using current eligibility, current account setting, window and recipient. Failure: if only stale discovery data is available or an authority cannot be reached, initiate no handoff. Boundary: a payment, void, collection hold, disable, or recipient revocation committed before dispatch authorization is effective for that authorization. Updates committed after initiation govern subsequent initiations. **Surface and confirmation:** place each update on both sides of the authorization point in an isolated billing account and inspect billing state and dispatch receipts.
- **C · Schedule identity (TC-6).** Positive: before each authorization, use the current due date and billing-account time zone. Failure: if either is invalid or missing, withhold dispatch and expose a safe reason. Boundary: changing either value moves only unconsumed positions. A position already recorded as accepted, expired or terminally closed stays consumed for that invoice, including after payment reversal or reopening. A reopened invoice can qualify for a current unconsumed position on the same terms as any other invoice. **Surface and confirmation:** edit a due date, change a time zone, and reopen an invoice in the selected billing source. Verify that future positions move and consumed positions produce zero additional handoffs.

**State and flow (F-2, T-4 and T-5).** The billing system owns account ID, invoice ID, due date, status, collection eligibility, currency and remaining balance. Its authorized actors can change these through existing workflows. The reminder processor reads the minimum account-scoped fields and leaves source records untouched. At a scheduled opportunity, use authoritative state to select a candidate (T-4, TC-4/TC-6), then re-evaluate at dispatch authorization (T-5, TC-5). The authorization point must order consequential committed changes against initiation. Candidate snapshots are transient and give no dispatch authority. A failed read leaves the candidate uninitiated and recoverable within its window. Billing records follow their owning system's access, corrections and lifecycle. Source deletion or closure makes them ineligible from that point on.

**Domain rules and open gaps.** Partially paid collectible invoices are included. Drafts, final closures and collection holds are excluded. The billing owner must map real status, dispute/hold, payment-reversal, balance and deletion semantics, time-zone source, and transactional ordering or equivalent authoritative behavior before billing integration. In particular, a stale replica or a late event cannot prove that a preceding payment was excluded. Whether invoicing treats pending payment as a collection hold is unresolved and gates that status mapping. The state guards and synthetic cases can be specified independently of it.

### R-3 Send a scheduled reminder to the current billing contact

**Basis and delta.** The 2026-11-21 request, “The incoming request” (“automatic reminders for unpaid invoices”), calls for delivery to the party who can act on the invoice. Add a recurring schedule and recipient-facing notice. Preserve existing billing-contact ownership and communication restrictions. Cadence, copy and email are provisional. No mail provider, approved sender, existing notice, or real recipient surface was supplied. Implementation and TC-7 through TC-9 are pending.

- **A · Schedule (TC-7).** Positive: while enabled, the processor automatically evaluates positions 1, 2 and 3 at 09:00 billing-account local time on calendar days 1, 7 and 14 after the invoice due date. It can initiate within the corresponding window. Failure: when the runtime resumes after an outage, it considers any still-open window and expires elapsed positions without sending them. Boundary: a window starts inclusively at its scheduled local time and ends at the first instant on a later local date, exclusively. Only positions with start times strictly after the current activation time qualify. If 09:00 occurs twice, use the first occurrence. If it is skipped, use the first later instant on the same date. A date with no remaining instant has no window. **Surface and confirmation:** drive clock and schedule through activation, the due date, window edges, a restart and applicable time-zone transitions. Observe handoff count and time without an active client.
- **B · Recipient selection (TC-8).** Positive: address the notice to the one currently designated, eligible billing email for that invoice's customer and account. Failure: missing, invalid, ambiguous or suppressed contact data withholds dispatch and exposes a safe reason. A corrected contact can qualify before the window closes. Boundary: a contact change before dispatch authorization selects the newly eligible recipient. Zero copies go to prior contacts, unrelated accounts or fallback addresses. **Surface and confirmation:** use two isolated mailboxes with the configured contact switched before authorization and compare each inbox with the account-scoped dispatch record.
- **C · Message (TC-9).** Positive: the intended recipient can identify the approved sender, invoice reference, due date and remaining balance with currency, and sees a request to pay using their established billing method. Failure: inability to establish required message fields withholds dispatch and records a safe reason. Boundary: include only this invoice's required details. Omit credentials, other invoice details and recipient lists. **Surface and confirmation:** inspect the actual message in an authorized test mailbox and compare its envelope and body to the invoice and current balance at authorization.

**State and flow (F-3, T-6 through T-8).** The autonomous processor wakes or resumes independently of a user session, uses the current schedule for unconsumed positions and selects an open position or records an elapsed one as expired (T-6, TC-7), resolves the current contact and message inputs, and defers if validation fails within the open window (T-7, TC-8/TC-9). The billing contact authority owns the contact address and permissions and can change or remove them through its existing workflow. On an authorized handoff, send only the intended email and keep the transport outcome under R-4 (T-8, TC-7 through TC-9). Before handoff, the address and composed body are held only for the immediate attempt. Discard them when the attempt returns or is abandoned. After handoff the provider and recipient mailbox own their respective message copies. Subsequent configuration and invoice updates cannot recall them.

**Domain rules and open gaps.** Cadence, local time, expiry and recipient rules are product defaults. Billing/product owners must establish any mandatory notice policy, address eligibility and suppression rules, approved sender, wording/localization needs and mail retention authority. Discovery/planning must select the existing contact and mail boundaries if available and prove access to a controlled receiving mailbox. These gaps gate actual dispatch and consumer verification. Schedule cases and copy checks against synthetic inputs can proceed before that. A customer preference center, escalation and attachments are excluded for this request.

### R-4 Recover dispatch safely and report what happened

**Basis and delta.** The 2026-11-21 request, “The incoming request” (“automatic reminders”), requires recurring execution to behave coherently on retries, overlaps and failures. Add per-reminder disposition and authorized outcome visibility. Preserve billing records and existing operational access controls. No provider completion, retry or operation-status capabilities were supplied. Implementation and TC-10 through TC-12 are pending.

- **A · Stable identity (TC-10).** Positive: one account, invoice and schedule position identifies a logical reminder across overlapping executions and restarts. A successful authorization reserves that position before attempting handoff. Failure: overlapping or stale workers cannot independently initiate a second handoff for that position or replace a newer disposition. Boundary: a definitively unsent attempt can be retried under the same position while its window and eligibility still hold. **Surface and confirmation:** force concurrent claims and interruption, compare authoritative dispositions and provider evidence, and count recipient messages.
- **B · Recovery and stop conditions (TC-11).** Positive: resolve known provider acceptance as accepted. On a confirmed transient failure with proof of no handoff, allow a controlled retry within the same window after rechecking R-1 through R-3. Failure: a permanent rejection closes the position as failed. An ambiguous response, or interruption after the reservation with no definitive outcome, becomes unknown. A reclaimed reservation grants the recovering worker no permission to submit. Reconcile through trustworthy provider evidence. Until resolved, withhold a fresh submission for that position and newer positions on that invoice. Boundary: expiry, loss of eligibility, or disable ends new submissions under that authorization. Reconciliation may still record the actual outcome of a handoff already initiated. Stale or repeated completion signals cannot reopen a closed position. **Surface and confirmation:** inject definitive rejection, timeout, accepted handoff with lost acknowledgment, interruption and duplicate or late completions at the delivery boundary. Compare provider records, account-scoped disposition and recipient message count.
- **C · Truthful outcome (TC-12).** Positive: authorized billing support can distinguish an active position awaiting a valid attempt, a reserved/in-flight attempt, provider acceptance, a confirmed delivery failure, an expired or closed position without acceptance, and an unknown result. Report acceptance as provider acceptance. Report a downstream failure when authoritative feedback is available. Failure: denied status reads expose no cross-account information. A diagnostic sink failure cannot authorize dispatch, undo committed work or convert a failure into success. Boundary: a provider acknowledgment alone makes no inbox-delivery claim. **Surface and confirmation:** compare authorized outcome reads, provider dispositions and the controlled inbox, inspect recorded fields, and force sink failure separately from dispatch failure.

**State and flow (F-4, T-9 through T-12).** The reminder runtime owns durable dispatch state scoped by billing account, invoice and position. Inputs for correlation are the logical position identity and the attempt or provider reference. A position can be open without a prior attempt. Reserve it with current authorization before transport (T-9, TC-10). Authorized automation completes it from trustworthy evidence (T-10, TC-10/TC-11). A definitive transient pre-acceptance failure can return it to open while the window is active. Ambiguity goes to unknown, with recovery owned by the processor and authorized billing support (T-11, TC-11). A confirmed unsent resolution re-enters the eligibility decision if the window remains open, otherwise it closes without acceptance. Accepted, expired and permanently failed positions are terminal for sending. An authoritative bounce after acceptance can refine the delivery outcome without allowing resend (T-12, TC-11/TC-12). Confirmed ineligibility at a particular evaluation prevents initiation then. A corrected condition can qualify before window expiry. Unknowns remain visibly actionable through reconciliation or source/account closure and the governing retention policy.

**Information lifecycle.** Only the scoped runtime and authorized billing support may access this outcome state. Recipient clients receive their email only. Retain the minimum position and outcome evidence needed to recover unknowns and prevent replay, including a minimal consumed-position marker while an invoice can regain eligibility. Remove temporary attempt input after use. Purge disposition and diagnostics at their policy-defined expiry. Resolve an overlap with an outstanding replay or reconciliation obligation before enabling the account. If deletion precedes the end of a replay window, prevent all future sends for the deleted target, including late work. Ordinary diagnostic records use restricted correlation identifiers, category, timestamp and reason codes. Omit email addresses, invoice contents, message bodies, credentials and raw provider payloads. Provider and mailbox retention remains an external lifecycle. The runtime must preserve status and replay protection through restarts and use bounded recovery under the selected runtime and provider quotas.

**Domain rules and open gaps.** Discovery/planning must establish an authorized status surface, recovery operator, trustworthy provider reconciliation and completion semantics, retry and reconciliation bounds, retention and deletion policy, usable scheduler/storage primitives and quotas. If the selected route cannot confirm an ambiguous outcome, it must preserve the unknown disposition and suppress fresh submissions as specified. The effect on subsequent positions makes that capability material for production readiness. Ownership, destination, retrieval and retention for operational evidence must be verified before real-boundary acceptance. State/identity cases can proceed with synthetic inputs.

## Submission

**summary**

- Specifies account-scoped activation, evaluation of unpaid collectible invoices, automatic email to the billing contact, and recovery and operational outcomes.
- Assumes default-off activation, one designated billing email, and three reminder opportunities at 09:00 billing-account local time on days 1, 7 and 14 after the due date. Each expires at local midnight, and enabling does not backfill elapsed or already-started windows. These are unattended product defaults.
- The actual billing authority, ordered eligibility check, configuration and status surfaces, delivery route, recovery capabilities, approval to activate, quota and retention limits remain open for the affected integration and release work. No material conflict was identified in the supplied request and guides. Independent eligibility, scheduling and state checks can be planned. The fixture was walked against the written rules. Product execution and real delivery remain unverified. If a retention rule cuts short replay protection, or the chosen billing source cannot order updates against dispatch, resolve that conflict before enabling affected accounts.

**primary**

- R-1 — activate independent automatic processing.
- R-2 — restrict reminders to currently unpaid, eligible invoices.
- R-3 — deliver automatic reminders to the responsible billing contact.

At product acceptance, at most one primary requirement may remain unverified, and only with a passed lower-layer test for that requirement. No such pass is claimed here.
