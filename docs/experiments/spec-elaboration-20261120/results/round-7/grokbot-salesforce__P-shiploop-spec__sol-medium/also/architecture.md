# Grok Bot for Salesforce architecture

These decisions describe the default implementation direction for the 2026-11-21 request. Pending target checks qualify their applicability.

## Decisions

### AD-1 — Lightning entry and authenticated Apex boundary

**Decision.** Expose a Lightning Web Component (LWC) through a Salesforce custom tab labeled **Grok Bot**. Put it in an existing suitable Lightning app's navigation when the org owner approves that placement, and supply the authenticated feature link. Reserve candidate names only after inspecting the selected org's component, tab and app metadata. The component uses a non-cacheable imperative call to an `@AuraEnabled` Apex operation in the same deployment. Keep the tab access, Apex class permission and external credential principal mapping in a dedicated least-privilege permission set. Require the platform's current effective grants server-side, including principal access at callout. Set sharing explicitly and perform no business-record queries or writes.

**Rationale and alternatives.** A feature tab gives a stable consumer entry in the signed-in org. Reusing an in-org shell keeps the scope smaller than a new app. A separate Salesforce app remains conditional on an entry need demonstrated by the target org inventory. A browser-to-provider call would put credential custody and spending controls outside the Salesforce server boundary.

**Evidence and revalidation.** Salesforce documents the distinction between component eligibility and a created custom tab, imperative server invocation and the Apex class access gate. Confirm actual app/tab placement, exposure, API version compatibility, effective user permissions and the supported deployment route against the authorized dev org. Use scoped metadata read-back and a terminal deployment receipt tied to the candidate revision before browser verification. A staged or asynchronous deployment acknowledgment is provisional. Release ownership, metadata authority and grant assignment are separate from consumer authority. [Custom tabs](https://developer.salesforce.com/docs/platform/lwc/guide/use-config-custom-tab), [imperative Apex](https://developer.salesforce.com/docs/platform/lwc/guide/apex-call-imperative.html), [Apex security](https://developer.salesforce.com/docs/platform/lwc/guide/apex-security.html), [deployment reporting](https://developer.salesforce.com/docs/platform/salesforce-cli-reference/guide/cli_reference_project_deploy_report.html).

### AD-2 — Server-side Grok call and credential custody

**Decision.** Use a server-side HTTPS call to the xAI Responses API, `POST https://api.x.ai/v1/responses`, with a server-selected eligible Grok text model. Prefer an entitled low-latency text model suited to direct question and answer. Use an enhanced Salesforce Named Credential linked to a Custom External Credential with a named principal. The org admin provisions the API key as an encrypted principal parameter and configures the bearer authorization header through the credential definition. Store only non-secret routing and model/budget settings in deployable configuration. The browser may supply prompt/history and a local correlation identity, within the validated schema. Endpoint, credential and model selection are controlled on the server.

**Contract.** The one-request exchange uses ordered `user` and `assistant` text in `input` plus model and budget controls. Set `store: false`, use non-streaming foreground inference without tools, and omit continuation IDs. Require a successful HTTP response whose body has completed status, no provider error, and nonblank assistant `output_text` from completed message items. Read text parts in order, excluding other item types and raw provider metadata. An incompatible response, nonterminal/incomplete status or missing usable text follows the safe R-3 failure path. Use controlled fixtures that vary model output and failure shape, and retain an authorized redacted receipt for the real exchange. Acknowledgments and a title rendered in the browser supply no inference evidence.

**Rationale and alternatives.** The documented provider interface supports text generation and stateless calls. Keeping just visible text context fits this short chat and avoids storing or replaying tool or reasoning artifacts. Provider-managed continuation, streaming, a gateway and durable worker state would add lifecycle or hosting commitments. Reopen this decision if the entitled model, required team policy or deadline cannot support the direct path. Local budgets must fit the selected model's context and output, the target's Apex heap and callout envelope, and the verified team limits. Set a bounded client recovery deadline and provider callout budget together. Revalidate model entitlement, target permissions, data policy, rate limits and configuration read-back before live use. Verify the state's actual retention behavior with the team operator. [Inference API authentication](https://docs.x.ai/developers/rest-api-reference/inference), [Responses API](https://docs.x.ai/developers/rest-api-reference/inference/responses), [Generate Text](https://docs.x.ai/developers/model-capabilities/text/generate-text), [xAI retention](https://docs.x.ai/developers/faq/security), [Named Credentials glossary](https://developer.salesforce.com/docs/platform/named-credentials/references/named-credentials-reference/nc-glossary.html), [custom OAuth-independent API key header setup](https://help.salesforce.com/s/articleView?id=sf.nc_custom_headers_and_api_keys.htm&language=en_US&type=5), [Apex governor limits](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-gov-limits.html).

### AD-3 — View-owned state and Lightning-compatible visual system

**Decision.** Keep draft, completed turns, in-flight view identity and appearance choice in component memory. Mask pending duplicate UI activations and associate each promise with the active view and attempt so late results cannot rehydrate conversation state. Use the existing Salesforce shell and design system for semantics, available controls, tokens and icons. Compose a scoped chat surface with dedicated transcript, composer and persistent status regions. Adopt a local light and dark palette where needed. Confirm actual theme compatibility before relying on component-level hooks. The plan selects the exact tokens, component treatments and focus behavior from the R-1–R-3 interface criteria.

**Rationale and alternatives.** A Lightning-native layout gives the most direct org entry and keeps typography and navigation familiar. Reusable controls and scoped styles are a smaller change than adding a second UI framework. A component whose native styling cannot maintain contrast in the scoped dark theme needs an accessible compatible treatment within the same system. Verify empty, pending, error and populated states at narrow and wide widths in the deployed shell. The design borrows airy hierarchy and tonal surfaces from Gemini and Material 3 Expressive and retains the product's own identity. Salesforce's styling hooks documentation distinguishes global tokens from component hooks and explains current theme limitations. [Salesforce styling hooks](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-css-custom-properties), [light expressive starting point](../GUIDES/platforms/ui.md#light-expressive-starting-point), [Gemini design](https://design.google/library/gemini-ai-visual-design), [Material 3 Expressive](https://design.google/library/expressive-material-design-google-research), [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

### AD-4 — Existing diagnostic surfaces

**Decision.** Reuse Salesforce-owned authentication and access evidence where available, supplemented by application outcomes recorded in an existing restricted diagnostic surface. The first candidate for on-demand dev-org diagnostics is Salesforce Debug Logs with appropriate trace filters and retention settings. Emit sanitized categories, elapsed time and opaque attempt correlation at the app's boundary. A platform-level rejection can prevent app execution, so consult native evidence for platform-denied requests. Retrieve outcome evidence through authorized roles. Suppress body and secret logging throughout the application path. A diagnostic failure must leave the send's outcome intact.

**Evidence and open applicability.** Salesforce documents filters, access, finite retention and truncation limits for debug logs. Candidate suitability depends on safe live settings, the ability to distinguish relevant outcomes without recording input or auth material, and approved operator access. Verify with synthetic outcomes under the actual configured filters. If it fails these checks, the diagnostic portion stays open until the org operator identifies an approved existing destination. No new log store is selected. [Salesforce Debug Logs](https://help.salesforce.com/s/articleView?id=sf.code_viewing_log_details.htm&type=5), [service observability guidance](../GUIDES/service-discovery.md#observability-coverage).
