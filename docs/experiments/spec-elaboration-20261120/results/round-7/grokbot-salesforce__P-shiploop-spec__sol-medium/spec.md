# Grok Bot for Salesforce

A Salesforce user can open Grok Bot inside an identified development org and exchange text messages with Grok. The initial scope is an internal chat for synthetic, non-sensitive development prompts.

## Basis and scope

The user request dated **2026-11-21**, under **The incoming request**, is “Create a Grok bot in a Salesforce development org.” “In a Salesforce development org” maps to deployed, authenticated consumer entry in R-1 (C-01). “Create a Grok bot” maps to a live Grok-backed exchange in R-2 (C-03), with session context, recovery and data protections defined in R-2 through R-4.

The standalone-stage instructions state that there is no prior specification, repository, discovery or research result, selected baseline, or callback. There are no previously accepted requirements or verified bot behaviors to preserve. Existing target-org state is unknown. The default interpretation is a private, text-only chat for users of the development org. No Salesforce record grounding or actions, external messaging channel, voice, files, web-search tools, durable history, or public Grok client parity are specified. xAI is the model provider and its API documentation supplies the integration contract. No other product is the behavioral reference.

Sources below were inspected on 2026-11-21. They establish documented capabilities. They supply no observations of the selected org, its grants, or the provider account.

The live application/error mapping is unobserved. Pending implementation and controlled browser and server fault checks.

| Case | Positive expectation | Failure expectation | Boundary expectation | Surface and confirmation |
| --- | --- | --- | --- | --- |
| C-06 | The active send shows a waiting status until settlement. After success the composer becomes usable for the next turn. | A second activation during the pending send leaves the existing attempt and message intact and creates no extra dispatch. | One outstanding attempt per active view. Independent views are isolated and may send within shared upstream quotas. | Browser with a held reply and independent invocation/callout counts. Exercise mouse and keyboard activation. |
| C-07 | On a retryable failure, preserve the submitted prompt and completed pairs. **Retry** resubmits that prompt once with the same completed context and reuses its visible message. | A timeout, network loss, throttle, upstream service failure or unusable response shows a persistent, sanitized error with Retry available. Invalid or missing configuration shows a contact-admin action. Expired Salesforce sessions prompt sign-in. An authenticated access denial directs the user to the administrator. No automatic retry and no fabricated reply. | An ambiguous call may have reached xAI and consumed quota. Manual retry is a new upstream attempt. | C-08 | **Clear conversation**, available when settled, removes draft, messages and failure state in that view. No user sees another user's draft, result or operation status. | Browser with separate view/user contexts, held response and lifecycle events. Compare visible history, next request and browser persistence surfaces. |

**Affected resources and state.** The active view owns presentation state and a transient attempt identity. An accepted send snapshots its input, locks the composer and shows pending feedback. Success appends only the matching reply. Failure retains one failed user message, offers recovery and unlocks composition. A fresh valid send from failure replaces that unfinished turn; a completed turn is immutable until cleared. A pending clear or duplicate activation changes no state. Reopen creates fresh view state; a stale callback cannot mutate it. Recovery uses a user-initiated new attempt or a new empty view. The service holds no lookup record, resumable job or server transcript.

**Open gap.** The integration owner must establish the supported attempt deadline and overload behavior on the chosen model and target runtime before live readiness. Pending feedback ends on an observed terminal outcome or the confirmed deadline. No retry schedule, cross-device recovery or model execution after the user leaves is promised.

### R-4 — Protect prompt data and provider access

**Basis, change and evidence.** Decision on external data and access under the 2026-11-21 request, “Grok bot in a Salesforce development org,” and the interaction and service guides. Introduces a governed provider call while preserving existing Salesforce identity and record access. Salesforce's [credential glossary](https://developer.salesforce.com/docs/platform/named-credentials/references/named-credentials-reference/nc-glossary.html) and [API key custody guidance](https://help.salesforce.com/s/articleView?id=sf.nc_custom_headers_and_api_keys.htm&language=en_US&type=5), and xAI's [API security and retention FAQ](https://docs.x.ai/developers/faq/security) document the available controls. Effective configuration, external-processing approval and live redaction behavior are unknown. Pending operating approval, configuration and boundary checks.

| Case | Positive expectation | Failure expectation | Boundary expectation | Surface and confirmation |
| --- | --- | --- | --- | --- |
| C-09 | Before Send, the bot tells the user that chat text is sent to xAI and instructs them to use synthetic, non-sensitive content. The provider receives only the submitted text and permitted in-view context plus model/request controls. | Missing provider setup or denied principal access fails safely. The browser sees no key, raw provider error, native stack trace or credential detail. | The bot does not automatically add Salesforce user identifiers, CRM fields, or secrets to the request. | C-10 | An authorized operator can distinguish a successful completion, local rejection, access/configuration failure, timeout, throttling and upstream failure using outcome-only diagnostics and native platform evidence for denials before the bot runs. | A diagnostic delivery failure cannot convert a legitimate reply into a resend or falsely report model success. Unauthorized users cannot retrieve diagnostics. | App-owned diagnostic fields are limited to sanitized outcome, elapsed time and opaque correlation, without prompts, reply bodies, credentials or session values. | Existing operator diagnostic surface under its assigned role, using synthetic outcomes, redaction checks and a simulated unavailable sink. |

**Affected resources and state.** Salesforce owns org authentication, the provider credential binding and access assignments. The org admin manages configuration and least-privilege runtime use. The xAI owner restricts, rotates and revokes the development credential and governs team quota and retention. The underlying secret is entered only via approved administrative credential setup, stored in protected server-side custody and removed on rotation or teardown. The browser and product source, logs and handoff never contain credential values. Prompt and reply text are displayed only to the current user and held in active view memory plus request processing. The bot neither stores them durably nor writes them to intentional diagnostics. xAI documents a default 30-day audit retention and separate team-level Zero Data Retention. Disabling response retrieval storage does not establish Zero Data Retention. The bot has no provider-side delete promise. Application-level exclusion of sensitive content relies on the disclosed development-use boundary, with no claim of automated detection.

**Open gaps and scope limits.** The org/data owner and xAI owner must approve transfer of synthetic prompts and confirm the team retention setting before any live request. The org operator must confirm the diagnostic destination, access, retention and deletion settings and verify no capture of body/secret values with the intended runtime settings before live readiness. Exact ownership assignments, credential/key scope and org/provider handling of platform-level logs require confirmation. A stricter retention mandate would hold live use pending a supported route and revalidation. The admin owns any person-only setup at release and its verification evidence at release-verify. No production data policy, archive, audit service or provider admin interface is included.
