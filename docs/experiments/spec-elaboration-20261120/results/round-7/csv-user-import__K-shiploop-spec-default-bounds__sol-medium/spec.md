# User Administration

## Scope and source

On 2026-11-21 the user requested “Let admins upload a CSV to bulk-create users.” The source locator is the standalone ShipLoop prompt, **The incoming request**. The feature starts in user administration and ends with new user records and truthful feedback to the submitting admin. Account updates, role changes, and user deletion are outside this feature.

The standalone workspace supplies that request and process guides. There is no prior spec, repository, discovery or research result, selected baseline, or reference-system parity obligation. Existing product behavior is unknown. Where this spec refers to existing rules, it records a preservation obligation and the prerequisite for establishing those rules. Product defaults are identified in the submission.

## Requirements

### R-1 — Admin access and CSV submission

**Basis and delta.** The 2026-11-21 request, **The incoming request** (“Let admins upload a CSV”), adds an admin-facing import action. Preserve current user-administration access and target scope wherever they already exist. The prompt identifies admins but provides no role matrix, scope model, or UI baseline. Implementation and consumer checks are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| Open import | A signed-in admin with user-create authority in the selected directory can open **Import users** from user administration. The form shows the supported column, file bounds, and what submission does. | A signed-out actor, signed-in non-admin, or admin without user-create authority for the target cannot reach an operable import, including by direct navigation. Denial follows the established sign-in or access-denied behavior. | An admin authorized for one directory gains no access to another through import. In a single-directory product, the directory is implicit. | User administration and actual import entry. Exercise the allowed, signed-out, non-admin and wrong-target paths. |
| Select and submit | The admin can choose or replace one local file and explicitly import the selected file. Selection or replacement alone creates zero users. | With no file selected there is no submission and the UI explains what to select. **Open gap.** Product owner and integration lead must identify the user-administration entry, actual admin/create permissions and scope, and the enforcement point that can order revocation against writes and result reads. Resolve before integrating access or writes. File rules and isolated interaction design can proceed.

### R-2 — File contract and validation

**Basis and delta.** The 2026-11-21 request, **The incoming request** (“upload a CSV”), adds file admission and per-record validation. Preserve existing user-create field and identity rules when established. The prompt provides no schema, CSV dialect or workload baseline. The format and bounds below are product defaults. Implementation and checks are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| File admission | Admit UTF-8 CSV content within both inclusive caps and with the supported header and record syntax. | Invalid UTF-8, invalid CSV quoting, unsupported header, unreadable content, or exceeding a cap rejects the entire file before any user write. Show the failing category and the applicable limit or expected format. | At most 262,144 file bytes (256 KiB) and 500 data records. Count bytes of the original file including BOM and line endings. Exclude the header and empty physical lines from the record count. Exactly either cap is allowed if all other checks pass. | Upload result and directory. Probe the size and row edges, and put a valid row before malformed quoting to prove that admission precedes writes. |
| Header and empty input | The first record, after an optional UTF-8 BOM, decodes to the single case-sensitive field `email`. | Zero bytes, BOM only, header only or only empty physical lines after the header yields “No data rows” for an empty file or valid header. Any other header, including a blank record before the header, yields “Expected one column named email.” Both outcomes create zero users. | A final newline adds no record. Space-only data lines and quoted empty fields count as data records and are subject to row validation. | Form and directory. Submit the distinct empty and unsupported-header inputs and verify diagnostics and zero writes. |
| Row validation | For an admitted file, validate each record against the field contract and ordinary account-create rules before trying to create that row. | A missing or invalid address or a record with other than one field is a row error. Report its source line and reason. An invalid row does not prevent other eligible rows from being tried. | Report the 1-based physical line on which each record starts, including both the header and intervening empty lines in numbering. Quoted newlines within a record advance line numbering but are part of that field. A row containing a line break in its email is invalid. | Import results and directory. Compare exact row outcomes and names of created accounts with a mixed file. |

**Input profile.** A comma separates fields. LF and CRLF delimit records outside quoted fields, with or without a final terminator. Quotes can enclose a full field, and doubled quotes within a quoted field decode to one quote. After a closing quote only a delimiter, a record end, or end of file is valid. A quote in an unquoted field, a bare CR outside quotes, or an unclosed quote is a file error. Empty physical lines after the header and outside quoted fields are ignored. A data row with two fields, even if one is empty, is invalid. Parse content regardless of filename extension or browser-reported media type.

For email, trim leading and trailing ASCII spaces and tabs. The established account validator and identity key govern if available. The standalone default accepts an ASCII dot-separated local part made of nonempty atoms of letters, digits or conventional unquoted email symbols (`!#$%&'*+-/=?^_` plus backtick and `{|}~`), one `@`, and at least two nonempty domain labels made of ASCII letters, digits or interior hyphens. Empty input, embedded whitespace, quoting within an address, display names and non-ASCII addresses fail this default. The standalone identity key lowercases the trimmed address. The product account input may retain the trimmed spelling under its regular rules.

**State, exclusions and recovery.** The product receives only enough transient file state to admit and process the selected submission. File rejection clears received data without writing accounts. The admin can correct the source file and submit a new attempt. No header mapping, alternative delimiters, spreadsheet support, or import of permission, password or profile columns.

**Open gap.** The integration lead must verify the supported account schema and validation/normalization rules and obtain primary documentation or suitable boundary probes for upload and execution quotas. This gates integration of the file cap and account-specific checks. If a hard limit cannot accommodate the stated cap including transport overhead, reconcile the cap through spec correction before affected work. No platform capacity is claimed here.

### R-3 — Create eligible users and protect existing accounts

**Basis and delta.** The 2026-11-21 request, **The incoming request** (“bulk-create users”), adds create-only processing for eligible rows. Preserve ordinary user identity, uniqueness, creation defaults and mandatory account controls. The prompt supplies no account model or onboarding policy. Implementation and checks are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| Create multiple users | After file admission, process data records in source order. Each eligible row commits one account through the product’s regular user-create behavior, in the authorized directory, with the product’s normal least-privilege role and initial account state. A committed row is visible in the authoritative directory under its email identity. | A definite row-local validation, policy or write rejection leaves no partial account for that row and permits later eligible rows to proceed. A directory-wide failure or indeterminate write stops further row attempts and follows R-4. | A valid one-row file can create one user. A mixed valid and invalid file can create a subset. An admitted file with no eligible rows creates zero. Account creation is atomic at the row boundary, and previously committed rows stay committed. | Admin result and fresh directory read. Compare pre/post identity sets, the created users’ default roles and initial states, and exact row outcomes. Inject a definite row rejection between valid rows. |
| Duplicate within the file | Attempt creation at most once for each row and consider a first field-valid occurrence before later occurrences of its identity key. | After the first field-valid occurrence, later field-valid rows with that key are marked **Skipped** with “Duplicate in this file,” even if the first occurrence has a known write rejection. | Rows already rejected by field validation do not reserve a key. Under the fallback key, case and trimmed outer whitespace do not create a new identity. | Result and directory. Use differently cased and spaced copies, exercise a rejected first write, and verify at most one created account per key. |
| Existing match and concurrent creation | An unused identity can be created subject to the same uniqueness rule as ordinary user creation. | A match in any identity-reserving state is **Skipped** with “Email unavailable.” A concurrent uniqueness conflict has the same outcome. Do not expose the matching account, its scope or its state. | Active, inactive/disabled and pending accounts are treated alike if they reserve the key. Deleted accounts follow ordinary key release rules. If two otherwise valid writers race for an unused key, one may commit and the other skips. An already existing record stays as it was. | Result plus authoritative pre/post records. Exercise collisions with existing accounts, another import and ordinary creation. Verify uniqueness and compare pre-existing record identity, role and state. |

**Affected resource and invariants.** The directory is the authoritative owner of accounts. The actor selects the directory as allowed by R-1. Each candidate is identified by the ordinary account identity key in the product’s uniqueness scope, with the R-2 fallback used in the standalone model. Before creation the key must be available, and after a reported creation exactly one complete account occupies it. Import does not update or reactivate existing records. Committed accounts are readable under ordinary directory rules and follow the ordinary account lifecycle. Local draft/result cleanup does not delete them.

**Domain exclusions and open gap.** CSV cannot grant elevated roles or set credentials. Default to the ordinary account-creation side effects, with no extra import-specific invitations or login provisioning. The product owner and account integration lead must establish the mandatory account fields, default role and initial state, identity-reserving states, uniqueness scope, onboarding side effects and whether those effects can satisfy the row contract. If the account contract requires data unavailable from an email-only file or cannot provide a safe create-only operation, integration is unready until the affected spec is reconciled.

### R-4 — Results, interrupted attempts and import data lifetime

**Basis and delta.** The 2026-11-21 request, **The incoming request** (“upload a CSV to bulk-create users”), implies an outcome the admin can act on. Add attempt feedback and safe resubmission while preserving ordinary account lifetime and access. The prompt provides no delivery, background-processing, retention or audit contract. The current-view lifetime and retry behavior below are defaults. Implementation and checks are pending.

| Acceptance | Positive | Failure | Boundary | Consumer surface and confirmation |
| --- | --- | --- | --- | --- |
| Show processing and confirmed outcomes | After submission show **Processing** while the outcome is pending. On confirmed completion show **Created**, **Skipped** and **Failed** counts and source lines and reasons for skipped and failed records in source order. Counts sum to the admitted row count. Direct the admin to the refreshed user directory. | For file rejection show a file-level reason and zero created. For a completed attempt with errors or zero creations, make the actual counts and remediation visible. Never use an elapsed timer or receipt of the upload as proof of creation. | Full success, mixed results and no created rows have distinct truthful feedback. Only committed accounts count as created. | Admin view, accessible status output and directory. Hold a response pending, then reconcile the result against actual writes and exact diagnostics. |
| Recover from interruption | After an interrupted attempt, guide the still-authorized admin to refresh the directory, correct the file if necessary and explicitly resubmit. The new submission uses current authorization and uniqueness. | On disconnect or lost/indeterminate completion, show that the outcome is unconfirmed once the view detects the failure. When an abort is confirmed and the authority can still return results, show known row outcomes separately from any indeterminate or unattempted records. Do not automatically retry the batch or report a fabricated final total. | Work may have committed before the interruption. A known abort starts no further rows. Client disconnect alone gives no cancellation guarantee. A new attempt cannot create a second account for an already committed key, even if the first attempt is still resolving. | Admin view, actual write boundary and directory. Force a lost result after one committed row and before the next row starts, then verify a fresh submission and the actual account set. Also exercise failure before any commit. |
| Limit disclosure and lifetime | Show a submitter their own current attempt’s result only while authorized for its target. Use source row numbers and reason categories. Show created email addresses through ordinary directory access. | Do not expose raw CSV cells, email values, files or filenames in import results, routine telemetry or diagnostic logs. Do not return another admin’s attempt details or data from another target. | Closing or replacing the attempt, changing scope or losing access discards its view state. A pending operation can hold transient input until it completes or aborts, then releases it. A late result must not attach to another attempt or view. | Two admin sessions, UI, product storage and authorized log view. Exercise completion, rejection, disconnect, navigation and revocation and inspect for persisted upload data and cross-session disclosures. |

**State and lifecycle.** The admin keeps the original file locally. The import view owns the selected file reference, pending indicator and result while that attempt is current. File content, transient identity keys and row outcomes in processing belong to the product authority and are scoped to the submitting identity and directory. Release the local file reference after completion or dismissal and release processing data on rejection, completion or abort. Authorized results live only in the active view. Reloading can lose feedback and the directory remains the account authority. There is no persistent import history, resumable job, shared result, cancellation control or promised completion after leaving. The 262,144-byte and 500-record caps bound an attempt’s inputs and displayed row diagnostics. Platform execution, concurrent workload and retention constraints remain the unresolved items below.

**Open gap.** The integration lead must verify the host’s request lifetime, failure signals, result delivery, cleanup and diagnostic logging paths before wiring interruption or claiming safe cleanup. The product owner must identify any existing mandatory account audit obligations and retention. Preserve those obligations through ordinary user creation and reconcile any conflict with import-data minimization before affected integration.

## Service boundary contracts

| Concern | Contract and check |
| --- | --- |
| Current authority and freshness | The admin interaction sends the selected CSV and intended scope to the product’s user-creation authority. The authority derives the actor from current authentication. A displayed form or prior permission is insufficient for a write or private result. Check stale access, direct invocation and fresh directory reads on the actual integration boundary under R-1 and R-3. |
| Incremental state | Each write adds only the eligible identity in the selected scope. Unrelated edits and existing accounts are preserved. Check overlapping import and ordinary-create operations and compare records under R-3. |
| Completion and recovery | The submission remains pending until the authority returns a confirmed result or the view detects failure. Only committed writes count. Recover through an authorized directory read and explicit resubmission under R-4. Check interruptions at the write and result boundary independently. |
| Owned event coverage | Preserve required ordinary account audit coverage for each committed creation. Where the product records import diagnostics, correlate with a non-personal attempt reference and distinguish rejected, completed and aborted outcomes without raw inputs. A lost response alone does not establish an abort. Confirm the actual owned events and their redaction at the authorized destination. |
| Inapplicable | No independent external service, subscription, incremental synchronization cursor or durable completion notification is required by this feature. |

The administrator-to-product boundary and the logical account authority above define observables. A separate account service exists only if product evidence establishes one. The actual invocation and enforcement contracts are open under R-1, R-3 and R-4.

## Interaction model and coverage

The admin controls a file picker and primary **Import users** action. Format and limits stay visible before submission. The result component keeps counts and actionable diagnostics readable, including with keyboard and touch. Keep focus stable while processing, announce status changes without relying on animation or toasts, and keep a completed error or recovery action available while the attempt is current. The normal directory is the consumer read surface for created accounts. The visual premise is in [Non-functional requirements](#non-functional-requirements).

These are behavioral flow and transition locators. Acceptance criteria remain under their requirement IDs.

| Flow and transition | Trigger, guard and state change | Observable result and case |
| --- | --- | --- |
| F-1 / T-1 — Enter and select (R-1) | Current allowed admin opens the import and selects, replaces or clears a file. The view goes from empty to selected, or back to empty. Forbidden actors cannot start a draft through this surface. | No domain write. See **Access and selection**. |
| F-1 / T-2 — Submit and admit (R-1, R-2, R-4) | A selected file and current permission allow explicit submission. The view is pending. The authority rejects a bad file before entering row processing or admits it once file checks pass. A second action in the same pending view cannot start a new submission. | Pending or file-level error. See **File admission** and **Exact caps**. |
| F-2 / T-3 — Process rows (R-1, R-2, R-3) | For each admitted row in source order, evaluate row validity, within-file identity, current authority and the ordinary uniqueness and write rules. A definitive row outcome advances the attempt. Directory-wide or indeterminate write failure stops it. | The account is durably created, the row is skipped, or the row fails without a partial account. See **Mixed rows and duplicate write** and **Concurrent create**. |
| F-2 / T-4 — Finish (R-1, R-4) | All rows resolved, or execution definitively halted. Release input. Deliver only to the still-authorized initiating view for its current attempt. | Confirmed counts, or known and unresolved outcomes kept distinct. See **Mixed rows and duplicate write** and **Interruption and retry**. |
| F-3 / T-5 — Lose access or response (R-1, R-3, R-4) | Effective revocation stops further commits and result disclosure. Client-detected response loss moves the active view from pending to unconfirmed. Scope/identity change or dismissal clears view state. Previously committed accounts remain. | No stale success or unauthorized disclosure. See **Interruption and retry** and **Revocation and isolation**. |
| F-3 / T-6 — Retry explicitly (R-1 through R-4) | A currently authorized admin can use a fresh directory read, then submit a selected file as a new attempt under T-2. A closed or superseded view cannot receive late feedback. | Newly eligible rows may commit. Previously committed keys remain unique. See **Interruption and retry**. |

## Replay evidence and verification status

The following are specification walkthroughs. Each begins with a fresh isolated directory `D` and a signed-in admin `A` who can create users in `D`, unless a case says otherwise. Only the named fixture identities are compared in directory reads. Independent expected results were derived by applying the named guards and counting writes and diagnostics. `LF`, `CR`, `BOM` and `0xFF` denote literal bytes. In inline file descriptions, `\n` and `\r` denote LF and CR, respectively. All filenames below are local synthetic fixtures.

**Access and selection (R-1, F-1 / T-1–T-2).** As A, open Import users and select `first.csv` containing `email\nfirst@example.test\n`. Replace it with `second.csv` containing `email\nsecond@example.test\n`, clear it, then select `second.csv` again and submit. T-1 grants selection, replacement and clearing but no writes. T-2 permits only the final selected file to proceed and disallows a second submit while pending. After T-3 and T-4, the result has one created row and a fresh directory read contains only `second@example.test` of those two keys. In separate attempts, use signed-out access, non-admin `M`, and admin `B` who can create only in directory `E`, including direct navigation and direct submission to D. R-1 denies all three and D receives zero writes. For unreadable input use a selected `second.csv` whose read is denied before upload. The form reports unreadable input and D receives zero writes.

**File admission (R-2, F-1 / T-2).** As A submit each of these independently with an empty fixture directory. For each table row, R-1 allows submission and R-2 determines whether T-3 can run. The table records the resulting independent oracle.

| Exact content or construction | Recomputed admission and outcome |
| --- | --- |
| Zero bytes, BOM alone, `email`, and `email\n\n` | Each has no data rows and creates zero. |
| `Email\na@example.test\n`, `email,role\na@example.test,admin\n`, and `\nemail\na@example.test\n` | Each has an unsupported header and creates zero. |
| `email\na@example.test\n"bad\n`, `email\na@example.test\n"bad"x\n`, `email\na@example.test\nb"ad\n`, and `email\ra@example.test\n` | Each is a file syntax rejection and creates zero. In the first three cases the apparently valid first row cannot commit before full admission. |
| ASCII bytes for `email\na@example.test\n` followed by byte `0xFF` | Invalid UTF-8 rejects the file before any write. |
| BOM followed by `"email"\r\n"a@example.test"` | One valid row at line 2. The result is one created and D contains `a@example.test`. |
| `email\n"a""b@example.test"\n"x\ny@example.test"\n\n"b@example.test"\n` | Correct CSV syntax. Lines 2 and 3 fail email validation and line 6 creates `b@example.test`. The result is one created, zero skipped and two failed. |

**Exact caps (R-2, F-1 / T-2, F-2 / T-3–T-4).** As A submit each construction separately to an empty fixture directory. For bytes, concatenate ASCII `email\n`, a run of ASCII spaces, and ASCII `a@example.test\n`. The fixed pieces total 21 bytes. A run of 262,122 spaces yields 262,143 bytes, 262,123 yields 262,144, and 262,124 yields 262,145. R-2 passes the first two, trims the spaces, and permits one user per run. It rejects the third before any writes. For rows, concatenate `email\n` and one line `uNNN@example.test\n` per integer starting at 1, with exactly three decimal digits and leading zeroes. End separately at 499, 500 and 501. Each line is 18 bytes, so all three files are below the byte cap. The first two produce exactly their specified identity sets and 499 or 500 creations. The third rejects the whole file, leaving the directory empty. Admission and counts must both be observed, including the last permitted identity at each passing boundary.

**Mixed rows and duplicate write (R-2 through R-4, F-2 / T-3–T-4).** Seed `held@example.test` as disabled in D, reserving its identity. As A submit the following LF-terminated lines in listed order. R-2 admits the file because the delimiter and quoting syntax is valid, then rejects invalid record shape or email at the row boundary. R-3 reserves a key at its eligible first occurrence, checks uniqueness, and permits unrelated eligible later rows.

| Physical line | Contents | Recomputed row outcome |
| --- | --- | --- |
| 1 | `email` | Header |
| 2 | `one@example.test` | Created |
| 3 | `bad` | Failed, invalid email |
| 4 | ` held@example.test ` | Skipped, email unavailable |
| 5 | `" ONE@example.test "` | Skipped, duplicate in this file |
| 6 | Empty line | Ignored |
| 7 | `two@example.test` | Created |
| 8 | `extra@example.test,admin` | Failed, wrong number of fields |
| 9 | `""` | Failed, missing email |

After completing T-4, A sees 2 created, 2 skipped and 3 failed with diagnostics for lines 3, 4, 5, 8 and 9. The directory has new identities `one@example.test` and `two@example.test`. The seeded account retains its prior record and disabled state. Repeat the collision through R-3 with the seed active and pending, provided those states reserve keys, and expect the same skip. For the no-eligible alternative submit `email\nbad\n""\n` to an empty fixture directory and derive 0 created, 0 skipped and 2 failed. To check duplicate handling after a known write rejection, submit `email\none@example.test\n ONE@example.test \ntwo@example.test\n` with a definite row-local write rejection at line 2. Line 2 fails, line 3 skips, and line 4 creates `two@example.test`. The counts are 1 created, 1 skipped and 1 failed, and `one@example.test` is absent.

**Concurrent create (R-3, F-2 / T-3).** Start with `race@example.test` unused. Let two authorized views submit `email\nrace@example.test\n`. In a controlled ordering, let the first write commit before the second tries to commit. R-3 allows the first write and denies the second as a uniqueness conflict. The first shows one creation, the second one skip with “Email unavailable,” and the directory contains exactly one account for that key. Repeat with the first writer using ordinary creation and the import as second writer. The import again skips, and the ordinary account record is unchanged. In the reverse ordering the import creates one and the ordinary request receives its existing conflict outcome.

**Interruption and retry (R-3, R-4, F-2 / T-3–T-4, F-3 / T-5–T-6).** As A submit `email\none@example.test\ntwo@example.test\n`. Force execution to stop after line 2 commits and before line 3 starts, and lose the result on the return path. R-3 permits the first commit; there is no trigger permitting the next row after execution stops. On detecting loss R-4 requires unconfirmed feedback. A can read D while still authorized and observes only `one@example.test`. A may reselect and explicitly resubmit the same file under T-6. The first key now skips through uniqueness and the second creates, for 1 created, 1 skipped and 0 failed. D then holds both keys exactly once. In a separate fresh run, stop before the first commit and lose the response. The first directory read finds neither key and resubmission creates both. In a separate fresh run, submit `email\none@example.test\ntwo@example.test\nthree@example.test\n`. After line 2 commits, let the line 3 write commit but make its acknowledgment unavailable to the import authority, and deliver the confirmed abort to A. Under R-3 the indeterminate write stops the attempt before line 4. A sees line 2 created, line 3 indeterminate and line 4 unattempted. The fresh directory holds `one@example.test` and `two@example.test` only. The indeterminate write is not counted as a confirmed creation.

**Revocation and isolation (R-1, R-4, F-2 / T-3–T-4, F-3 / T-5).** As A submit `email\none@example.test\ntwo@example.test\n`. After line 2 commits but before line 3 may commit, the fixture permission authority makes A’s loss of access effective and the view learns of it. R-1 forbids further writes and private result disclosure. A sees loss of access and no row details. Authorized fixture admin `C`, who can still read D, sees only `one@example.test` and cannot read A’s attempt result. Separately, let A submit with stable access, dismiss the pending view, reopen and select `other.csv` containing `email\nother@example.test\n` without submitting it, then deliver the earlier result. T-5 discarded the old state and T-1 permits a new draft, so the old result changes neither the new selection nor its pending state. `other@example.test` is absent. After the original execution ends, inspect authorized storage and logs for the original bytes and unique fixture addresses and filename. Ordinary directory records for committed accounts are the expected personal-data exception, and applicable ordinary account audit coverage must be reconciled under R-4.

**Evidence limits and owners.** The walks above recompute the specified outcomes using synthetic start conditions and controlled failure orderings. No prior accepted cases or runtime commands exist to reconcile. NOT-REPLAYED: the real admin entry, account/authorization fixtures, concurrency and interruption controls, storage/log access, and target runtime are unavailable. The product owner and integration lead own establishing those prerequisites before affected work. All consumer, authority, runtime-limit and rendered checks are pending. A future implementer owns lower-layer checks at the implementation/test phase and the acceptance reviewer owns the actual consumer checks at system test/product acceptance. Assumed a user-admin import surface, one UTF-8 email-only CSV per attempt, inclusive caps of 262,144 bytes and 500 data records to bound an interactive import, and the stated fallback email grammar and case-insensitive identity. Assumed partial success after whole-file admission, no updates on collisions, ordinary least-privilege account defaults and ordinary creation side effects, explicit retry, and current-view feedback without import history. For a new web surface, assumed a light-first appearance with a dark option subject to product identity and platform conventions. Open for affected work are actual authorization and directory scope, mandatory creation fields and account lifecycle rules, runtime quotas and interruption controls, audit and retention requirements, and supported UI widths and identity. No known material conflict has been established. If the account or runtime contracts conflict with the defaults, reconcile the affected requirements through the existing spec correction route before that work proceeds. Independent file-model and interaction work can proceed. Walkthroughs define oracles. Product implementation and verification remain pending.
