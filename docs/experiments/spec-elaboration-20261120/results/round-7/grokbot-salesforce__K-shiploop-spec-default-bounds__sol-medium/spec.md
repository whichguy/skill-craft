# Grok Bot for Salesforce

## Scope and basis

On 2026-11-21 the user asked, “Create a Grok bot in a Salesforce development org.” “In a Salesforce development org” maps to opening and using the bot as an authenticated user in the selected development org (R-1, entry and access). “Grok bot” maps to sending a prompt and receiving a reply generated by xAI Grok (R-2, send and reply). R-3 and R-4 specify the default conversation lifecycle and the safeguards for that interaction. The chat is a development-org tool for authorized internal users and synthetic inputs.

This is the first specification. The standalone stage supplies no prior spec, discovery, research result or selected baseline. Existing org features, grants and naming collisions are unknown. The before state in the controlled cases is a fixture, never an observation of the intended org. The Grok API is a dependency. The product does not target parity with grok.com, X or a reference Salesforce bot.

- **Privacy and integrity (R-1–R-4).** With synthetic data, verify a denied Send causes zero provider calls, a stale completion cannot publish, and successful and failed attempts emit no application-owned payload logs or durable transcript. - **Compatibility and recovery (R-1, R-2, R-4).** Verify in the selected Lightning development org using an org-supported metadata version, identified internal roles and current Grok model entitlement. ## Specification evidence and remaining verification

- **Specification walk, validation and duplicate.** Apply R-2 Validate before Send, with Ava's R-1 grants. Trim the prescribed whitespace, then count scalar values. All-whitespace becomes zero, spaced `x` becomes one, the two rocket inputs are 2,000 and 2,001 respectively. T-2 admits only the middle valid cases. In Reply and duplicate, during the pending interval T-2 rejects the repeat, leaving a single request. At 1,000 ms T-3 may move it to completed and the Reply clause gives the literal expected result. A UI observer can count the reply while the controlled boundary counts calls.
- **Specification walk, deadline and recovery.** Start with the completed first pair via T-3. The second Send is admitted by T-2. Comparing elapsed time to the R-2 boundary gives 39,999 < 40,000 and 40,000 ≥ 40,000. The former may commit the supplied reply through T-3. The latter goes through T-4, preserving exactly the first pair and restoring the draft. T-2 can then admit the deliberate retry, and a timely T-3 outcome adds exactly one pair with `Recovered.`. The 39,999 ms case exercises the view callback independently of the shorter Salesforce outbound wait.
- **Specification walk, context and clearing.** Starting from zero with Ava authorized, T-2 then T-3/T-5 for 1–4 yields pairs 1–4. On success 5, T-5 removes pair 1, so Send 6 carries eight history messages plus the new user prompt. T-6 clears the window and invalidates attempt 6. R-3 allows T-2 for `Fresh?` immediately with only that prompt. The old event cannot pass T-3 or T-4's current-attempt guard. A timely new success gives one completed pair. Access for Ben in this isolation case requires the admin's explicit fixture grant from R-1, separate from the denial case.
- **Specification walk, errors.** Once T-3 establishes the first pair, Salesforce authorization denial leaves zero outbound requests. For the other dispatched alternatives, T-4 maps each failed current attempt to the corresponding R-2 message, retains the first pair and adds no second pair. A missing configuration may fail before dispatch. An already-reported denial or failure does not start a background retry.
- **Specification walk, themes and privacy.** With an empty authorized view, changing appearance does not alter Send admission. T-2 produces the waiting state after the labeled action, T-3 yields one completed pair with the 160-character reply, and T-4 maps the independent 503 attempt to inline failure with the draft restored.
