# Grok Bot for Salesforce architecture

These decisions are proposed for the spec. Product behavior and readiness gaps are in [spec.md](spec.md). Primary documentation supports the mechanisms. The actual org, runtime API version, browser permissions and xAI team configuration remain unverified. The spec stage has no deploy or runtime result.

## Decisions

### AD-1 Use a Lightning Web Component tab in the development org

Serve Grok Bot as an LWC in the existing authenticated Lightning Experience shell with an actual CustomTab metadata entry. Use Salesforce Navigation Item Page navigation and verify the resulting route after redirects. A component's `lightning__Tab` exposure alone only makes it eligible for a tab. Prefer the existing App Launcher and an additive tab to a new app or external site, which would add navigation or hosting without a separate product need.

Candidate identifiers for a collision-free, unnamespaced development org are LWC `grokBot`, tab `Grok_Bot` and tab label `Grok Bot`. The expected feature path in that configuration is `/lightning/n/Grok_Bot`, relative to the approved org's domain. An authorized metadata inventory must settle names and supported API version first. Observe and record the actual deployed navigation URL and revision independently of the org home page and of the tab metadata's presence. If names differ, update the affected case inputs before replay. Deployment, credential setup and permission assignments are separate external operations and need their own authorized actors and read-back.

**Evidence and limit.** Covers R-1. The target's actual shell, visibility, navigation and available runtime version require a probe as the intended user. [Configure Custom Tabs](https://developer.salesforce.com/docs/platform/lwc/guide/use-config-custom-tab.html), [CustomTab metadata](https://developer.salesforce.com/docs/platform/api-metadata/references/meta-types/metadata-customtab.html), [PageReference Types, Navigation Item Page](https://developer.salesforce.com/docs/platform/lwc/guide/reference-page-reference-type.html), [Salesforce platform guide, Service discovery](../GUIDES/platforms/salesforce.md#service-discovery).

### AD-2 Keep authority and external transport in Salesforce

Use an imperative, non-cacheable LWC invocation of a narrow Apex method. Use current authenticated class access and an explicit feature permission at the method boundary. Use an extensible Named Credential at `https://api.x.ai` and an External Credential with Custom authentication. Grant principal access and the necessary User External Credential permissions only to enabled consumers. The shared named principal uses a dedicated development inference key. Salesforce supplies the custom Authorization header with the Bearer scheme by resolving the protected credential parameter at callout time. Disable the standard generated header to avoid a conflicting header. Keep credential values out of code, UI, payload diagnostics and metadata artifacts. Use permission sets for entry/class/feature and for outbound principal access so they can be revoked independently.

Use one callout per admitted invocation with R-2's timeout. Enforce the bounded prompt and history contract at the server boundary because client-side state is caller input. The application treats chat history only as text for inference. The method has no CRM object queries, sharing dependencies, FLS dependencies, DML or record permissions. There is no separate identity pool, middleware, worker or direct browser-to-xAI connection. This keeps the development setup within the existing trust boundary and preserves Salesforce's ownership of Access, even if the workstation goes offline.

**Evidence and limit.** Covers R-1, R-2 and R-4. Salesforce documents 100 callouts per transaction, 120 seconds cumulative timeout and a 6 MB synchronous request/response limit that counts toward heap. Salesforce also documents up to 20 concurrent external callouts for Developer Edition. At that ceiling remaining platform gates still apply. Excess capacity follows R-2 unavailable feedback or the view deadline. Confirm actual feature/principal grants and denial normalization in the chosen org with its supported metadata/API version. [Call Apex Methods Imperatively](https://developer.salesforce.com/docs/platform/lwc/guide/apex-call-imperative.html), [Secure Apex Classes](https://developer.salesforce.com/docs/platform/lwc/guide/apex-security.html), [FeatureManagement.checkPermission](https://developer.salesforce.com/docs/platform/apex-ref/references/apex-ref/apex-class-system-featuremanagement.html), [Governor limits](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-gov-limits.html), [Callout limits](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-callouts-timeouts.html), [PermissionSet metadata](https://developer.salesforce.com/docs/platform/api-metadata/references/meta-types/metadata-permissionset.html), [Use API Keys in Custom Headers](https://help.salesforce.com/s/articleView?id=sf.nc_custom_headers_and_api_keys.htm&language=en_US&type=5), [xAI API overview](https://docs.x.ai/developers/rest-api-reference/inference).

### AD-3 Use stateless Grok Responses

The xAI operation is `POST /v1/responses` with JSON and the org-managed authorization header. Select `grok-4.3` as the proposed development default for text and configurable reasoning, pending team entitlement. Use `reasoning.effort` of `none` for this bounded synthetic text chat and `max_output_tokens` of 1,024. Send compact text messages with alternating user/assistant roles for retained pairs, then the new user prompt. Set `store` and `stream` to false. Omit continuation IDs, tools, metadata and user identifiers. The model's documented context window is 1,000,000 tokens. R-2 and R-3's text bounds keep normal requests small. Keep the provider's default rejection of context overflow rather than accepting provider-side history truncation. The app owns its window.

Consider direct terminal replies versus streamed or deferred work. A terminal reply gives the UI a single settlement and Salesforce one outbound call. Streaming, provider history retrieval and model fallback would change failure, retention or acceptance behavior without serving a required outcome. Retrieve only assistant `output_text` parts from a completed response, preserving part order and separating parts with a newline. Reject inconsistent or unusable terminal data. Normalize transport, explicit refusal and error groups according to R-2. The provider documentation establishes completion and incomplete status. Verify the wire shape of refusal and incomplete details before depending on a subtype; an unrecognized subtype takes the generic unusable-result path. Verify that the selected account supports the request fields and returns the contracted shape with a synthetic prompt. A different model or changed retention policy calls for spec/architecture reconciliation before live use.

No model reasoning artifacts are retained or forwarded. The four displayed text pairs are the only continuation context. The provider's audit policy and prompt cache are independent of the request storage switch. The API team owner confirms actual policy and entitlement in the selected team. Use limited, sanitized synthetic response evidence for proof of provider identity and completion.

**Evidence and limit.** Covers R-2–R-4. Controlled responses can exercise shape, errors and ordering. Only the authorized real call can prove real integration. [Responses, Create new response](https://docs.x.ai/developers/rest-api-reference/inference/responses#create-new-response), [Grok 4.3, context and reasoning options](https://docs.x.ai/developers/models/grok-4.3), [Reasoning, reasoning effort](https://docs.x.ai/developers/model-capabilities/text/reasoning), [Best Practices, stateless Responses and output cap](https://docs.x.ai/developers/model-capabilities/text/best-practices), [Debugging Errors](https://docs.x.ai/developers/debugging), [Rate Limits](https://docs.x.ai/developers/rate-limits), [API Security](https://docs.x.ai/developers/faq/security).

### AD-4 Keep chat state in the view and style it within Salesforce

Keep the draft, current request identity, completed pairs, appearance and error as LWC instance state. Correlate completion to both the current conversation and attempt, including after reset, reconnection and view deadline. Use no persistent client store, shared memory cache, custom object or background job. This is smaller than a durable store and removes a cross-user synchronization and retention obligation. Controlled time and completion tests distinguish pending, completed, failed and invalidated attempts.

Use Salesforce Lightning Design System controls and icons where they meet accessibility and theme needs, with scoped bot tokens for the chat surfaces. Give the transcript and multiline composer most of the page, with a compact title and controls for New chat and appearance. Enter in the textarea inserts a newline. Send and New chat are labeled focusable actions. Use a live waiting/outcome status and persistent inline recovery guidance, preserve focus on settlement and return it to the composer on New chat. Use an integrated waiting indicator and a tonal highlight for the arriving reply only as meaningful state cues. Under reduced motion use static cues. Keep the Salesforce shell's identity and start the bot light with a dark option. For the bot surface, use the UI guide's light Gemini and Material 3 Expressive direction for spacing, hierarchy and tonal shapes. The existing Salesforce base primitives plus a scoped palette and chat composition are smaller to maintain than importing another UI framework. Check both palettes and the actual deployed control rendering before finalizing the treatment. If primitives prevent contrast or focus compliance, evolve just the affected controls using accessible native elements and the same visual system. The plan defines exact type, color, spacing and shapes.

**Evidence and limit.** Covers R-1–R-3. Available local design guidance is the UI guide's named section and the session's frontend design instructions. A separate frontend-design skill was not available in the session catalog. The Salesforce platform guide, Lightning icon reference and published visual guidance inform the choice. Target shell, controls and colors have no rendered evidence yet.
