# User Administration

## Scope and source

**Request, 2026-11-21, “The incoming request”** — “Let admins upload a CSV to bulk-create users.”

The requested outcome is a signed-in administrator submitting one CSV and seeing its users created in the intended user directory. The stage packet supplies the request and authoring rules. The workspace supplies guidance only. There is no accepted product baseline, product repository, discovery or research result, selected reference system, or prior requirement or check to reconcile. Existing product behavior is unknown. Reuse of the product's normal admin scope, account rules and directory is a proposed constraint to confirm when those contracts are available. No product implementation or checks have run.

## Requirements

Each acceptance line specifies its positive, failure and boundary expectations and the observation required. Acceptance IDs are clause locators within their parent requirement. Flow and transition IDs below describe product behavior.

### R-1 — Limit import to administrators in the authorized scope

**Basis and delta.** Request, 2026-11-21, “The incoming request,” “Let admins upload.” Adds an import action and enforces admin authority for it. Proposed preservation is the existing sign-in, role and user-creation scope. Evidence is request intent only. Role names, directory scope and enforcement points are unknown. Implementation and the A/B checks are pending.

- **A. Entry and submission.** Positive — a signed-in administrator authorized to create users in the selected directory can open the upload action and submit there. Failure — hide the entry from a signed-out caller, signed-in non-admin, admin lacking create authority in the selected directory, or caller whose authority cannot be verified. Deny direct requests from each of those callers before CSV processing or effects. Unauthorized responses disclose no file, identities, duplicate findings, operation existence or row counts. Boundary — scope and actor come from verified product context. A caller-supplied directory or admin claim cannot widen them. **Surface/check** — open the admin UI as an authorized admin, try both navigation and direct submission as each denied caller, and inspect the target directory and attempt records for zero changes.
- **B. Revocation and isolation.** Positive — the submitting admin with current create authority in the original scope can obtain their operation status and authorized diagnostics. Failure — deny those reads after role revocation, session expiry or account/scope switch, and deny another admin access to the submitter's operation. Boundary — authorize again at commit. A revocation effective before commit prevents all account writes. A revocation effective after commit leaves the committed batch intact and denies subsequent import-status reads. If ordering cannot be established, creation fails closed. **Surface/check** — control revocation before and after the commit boundary, record ordering, inspect account state independently and attempt status retrieval as the submitter and as the other admin.

**State and open gaps.** Admin identity and create grants belong to the product's authority source. Import reads them and changes no grants. The owner of the product authority contract must confirm the principal and directory identifiers, cross-directory semantics, and how current authorization can be enforced against commit and result disclosure before authority integration. The sign-in mechanism, grant administration and delegation policy are outside the requested change. Verify against the actual authority and account writer. If either is unavailable, block only binding and verification that depend on it.

### R-2 — Accept a CSV and identify input problems before creating users

**Basis and delta.** Request, 2026-11-21, “The incoming request,” “upload a CSV.” Adds an upload and validation contract. Proposed preservation is the product's normal required fields and value validation. Evidence supplies no CSV dialect, field list or operating limits. The dialect below is a proposed default. Implementation and the A–C checks are pending.

- **A. Select and submit.** Positive — the admin surface shows required and optional headers, accepted file format and active limits. It lets the admin select one file, see the selection and submit explicitly. Failure — missing selection or a transfer known to have ended before acceptance gives a corrective message and creates zero users. An ambiguous transfer follows R-4. Boundary — replacing or clearing an unsubmitted file discards the old selection and diagnostics. Selection alone creates nothing. **Surface/check** — observe the selection, replacement, clear and submit controls in the admin UI and inspect account state before submission and after a confirmed incomplete transfer.
- **B. File structure.** Positive — accept UTF-8 text with an optional initial UTF-8 BOM, comma-separated columns, LF or CRLF record separators, an optional final record terminator, header row first, and double-quoted fields with doubled quotes for literal quotes. A quoted newline stays within one field. Allow columns in any order. Failure — reject undecodable input, missing or malformed header, duplicate or unknown header, missing required header, unmatched quotes, ragged rows, or a document with zero data records. Report the file reason and, when identifiable, the logical record position. Boundary — header names match the published spelling after removing an initial BOM. A terminal line ending adds no blank record. An empty record within the file is rejected, even with a one-column schema. A single well-formed data record is eligible. File content determines validity, regardless of suffix or reported media type. **Surface/check** — submit exact byte fixtures for the listed groups and assert both the diagnostic category and absence of writes for rejected files. Confirm a quoted line break does not shift subsequent record numbering.
- **C. Row values and size.** Positive — validate every structurally valid record under normal account creation rules and report invalid records by one-based logical record number, with header as record 1, field and corrective reason. Failure — one or more invalid values reject the batch and create zero users. Exceeding any published input bound rejects the batch with the breached limit and creates zero users. Boundary — a valid file at each inclusive maximum is eligible, a file one unit beyond is rejected, and a blank field follows the normal required/optional rule for that field. **Surface/check** — compare valid and invalid single-create and import fixtures for the same values, and exercise each size boundary with the other limits held below their maxima. Inspect the result and directory state.

**State and open gaps.** The initiating admin owns one draft in the active import view. The file and selection state are cleared on replacement, successful result, navigation away, or loss of the owning session/scope. On definitive rejection in the same view, the admin may replace the file and resubmit. The admin surface shows the local filename and actionable reason/position, without echoing submitted field values in diagnostics. Application-side upload/parsed values are scoped to verification and the in-flight attempt and discarded at termination, including rejection or abandoned transfer. Neither the raw file nor parsed rows belong in ordinary logs or persistent import history. Normal created user records follow R-3. Product/account owner must confirm the actual headers, canonicalization, required/defaulted values and normal validators. The minimal provisional contract is a single required `email` header if email-only creation is supported. Extra fields are accepted only when published and allowed by ordinary create rules. CSV-supplied roles, passwords, cross-directory placement and arbitrary attributes are excluded. Runtime owner must establish inclusive byte, data-record and field-size limits, and any structural limits implicit in the schema before publishing limits or enabling uploads. A fixture below the agreed limits can be specified independently.

### R-3 — Create the batch in the authoritative user directory

**Basis and delta.** Request, 2026-11-21, “The incoming request,” “bulk-create users.” Adds one create-only batch action. Proposed preservation is the ordinary account record, canonical identity, default access and account readiness rules, plus all pre-existing accounts and unrelated state. The request does not settle duplicate, partial-success or onboarding policy. All-or-nothing and reject-on-conflict are defaults chosen to make correction and retry predictable. Implementation and the A–C checks are pending.

- **A. Commit.** Positive — for an authorized, valid batch with distinct, available canonical identities, create one ordinary user for each data record in the selected directory and publish completion only after all are durable. Failure — definitive validation, authorization or persistence rejection before commitment leaves zero users from that operation and zero activation or provisioning effects from its rows. Boundary — apply the same non-elevated default access and account lifecycle as ordinary creation. Submitters cannot use CSV to choose privileges. Existing records and other directories are unaffected by the import. **Surface/check** — compare actual before/after directory reads by canonical identity, verify persisted fields and default privileges, and induce a late write failure after preparation. Compare both directory and consequential account-creation effects to the baseline.
- **B. Duplicate and existing identities.** Positive — a batch of distinct available canonical identities proceeds. Failure — any duplicate canonical identity within the file, or any existing identity that conflicts under the ordinary account rules, rejects the entire batch and identifies the conflicting record positions and reason without disclosing other records or scopes. Boundary — equivalence and uniqueness scope match the account authority, including any normalization and reserved lifecycle states. Two rows for the same canonical identity conflict even when their non-key values differ. **Surface/check** — supply exact repeated and canonically equivalent identity fixtures and a file colliding with a pre-existing account. Assert the relevant record positions, the absence of otherwise-valid new rows, and unchanged pre-existing account fields.
- **C. Concurrent writers.** Positive — disjoint authorized batches with valid data and a healthy writer can both commit. Failure — when two otherwise eligible batches, or a batch and a normal create, compete for the same identity, at most one writer wins. A losing batch is rejected as a whole and reports a conflict. Boundary — evaluate the identity conflict at commitment, including after any earlier availability check. Only the winner can have durable new-account effects for the contested identity. **Surface/check** — coordinate overlapping writes at the real account boundary after validation and before commitment. Assert exact directory contents, loser-specific companion row absence, and both reported outcomes.

**State and open gaps.** The account authority owns durable users keyed by its canonical identity and uniqueness scope. Only actors permitted by normal creation may add them through import. Ordinary directory policy governs later reads, edits and deletion. From an initial snapshot plus any independently committed changes, a successful batch adds exactly its eligible identities and their ordinary create effects. A rejected batch contributes none. Recovery retains a committed batch and reconciles operation status under R-4. Deleting the batch, updating/merging or reactivating accounts, importing credentials, changing access, defining new invitation rules and migrating existing users are outside scope. The account owner must confirm uniqueness (including pending, suspended or deleted accounts), default access, create side effects and when a created account becomes usable. The runtime owner must demonstrate that authoritative writes and any required external effects can uphold the batch invariant and that the outcome is independently readable after interruption. If a required ordinary side effect or authorization rule conflicts with all-or-nothing, dependent creation work stays unready until that product contract is reconciled. No architecture or platform capability has been established here.

### R-4 — Report the actual outcome and support safe recovery

**Basis and delta.** Request, 2026-11-21, “The incoming request,” “upload a CSV to bulk-create users.” Adds status and feedback for that action so the admin can tell whether the intended accounts were created. Evidence gives no operation status, audit or retention contract. The behavior below is a proposed default. Implementation and the A–D checks are pending.

- **A. Pending and completed.** Positive — once submission begins, display understandable pending feedback and suppress a second submission for the same attempt. Display the confirmed created count only after durable commitment and give the admin a way to view the ordinary directory. Failure — definitive rejection displays zero created, the actionable reason and permitted correction. Boundary — transport acknowledgment means receipt only. Timeout or lost response after sending means “Outcome unknown” until reconciled. Display neither a success claim nor zero created while uncertain. Prevent a late response from changing a replacement view or another interaction's status. **Surface/check** — hold the account operation before commit and observe the UI, then release it. Repeat with lost response before and after commitment, and with a late response after leaving the view.
- **B. Recovery and replay.** Positive — before sending file data, make a reference available to the submitter for recovery even if the first upload response is lost. Bind it to that admin, directory and original submission. While the reference is recoverable, the authorized admin can resume status after reconnecting and receive the actual outcome. Concurrent or sequential replay of the same reference and unchanged submission yields the accepted attempt's pending or terminal result without extra effects. Failure — reject reference reuse with different content or by a different principal or scope. If status is unavailable or outside its recoverable lifetime, explicitly say the outcome cannot be confirmed and direct the admin to reconcile against the authoritative directory before submitting again. Boundary — interruption before durable acceptance with no committed effect can be retried with the original file and same reference. An interruption ending processing after acceptance with no commit resolves to rejection once non-commit is established. An interruption after commit recovers the committed result and count. Hold uncertainty until authoritative evidence establishes one terminal outcome. **Surface/check** — interrupt transfer and processing at these boundaries, restart the relevant runtime, recover under the original actor and compare status with independent read-back. Send simultaneous same-reference retries, then reuse it with changed content and a different identity. Check for one accepted attempt and verify exact directory effects.
- **C. Correction and cancellation.** Positive — after confirmed rejection, give the admin a way to replace or correct the file and submit a new attempt. Failure — once the file has been sent, leaving the view, reconnecting or closing the browser does not cancel or reverse a write. Boundary — clearing an unsent draft is local. No post-submit cancel or undo action is offered because completion may already be irrevocable. **Surface/check** — reject a batch, correct it and observe a distinct attempt commit. Leave the UI with an in-flight submission, then recover the actual outcome under R-1 and R-4B.
- **D. Minimal operational evidence.** Positive — record an operation-level outcome for each accepted attempt with reference, initiating admin identifier, authorized scope, outcome, and safe counts or error category. Record denied import requests as redacted access-denial events without CSV contents. Failure — an event-delivery failure must leave account state and attempt status truthful, avoid duplicate account effects and be detectable through the product's supported operational signal. Boundary — an unchanged replay adds no second terminal event for that outcome. Authorized operational staff can view these events through the ordinary restricted operational surface. CSV content, submitted field values, filename, passwords and credential/session material are excluded from events and logs. **Surface/check** — inspect restricted event outputs for committed, rejected, denied and recovered attempts, verify redaction with unique synthetic input markers and induce a sink failure where an independent sink exists.

**State and open gaps.** The import authority owns attempt state keyed by scope, initiator and attempt reference. It retains only the metadata needed for authorization, same-submission recognition, terminal outcome, count, and redacted diagnostics during the recovery window. No raw CSV or raw row data in the receipt or history. Pending inputs are short-lived as specified in R-2. If inputs are lost before commit, recovery can resolve to confirmed rejection once the authority rules out any competing delivery or write for that attempt. There is no promise to continue processing an interrupted transfer. The UI keeps the active reference with the current interaction and clears stale file data and results on actor/scope change. Recovery is limited to the submitter with current authority, and must be reachable without reliance on an open upload view. A status response can never reverse a terminal result. Attempt receipts and app-owned diagnostic copies expire and are removed under the approved policy. The recovery reference expires with the receipt and must never silently become executable as a new attempt. Ordinary account records and operational events follow their own approved lifecycle. No cross-admin sharing or permanent import-history UI is needed.

Before committing to recovery and operations integration, the runtime and privacy owners must confirm how the existing product can bind and recover attempts, retain a durable verdict consistent with account state, signal event failures and enforce cleanup. Set the recovery window, maximum unresolved duration/escalation point, cleanup deadline and operational event retention or locate their applicable existing policies. Exercise last recoverable and first expired states and interrupted cleanup. Age alone must never establish a verdict. The UI may distinguish pending, uncertain, rejected and complete before concrete persistence and durations are resolved.

## Service boundaries

These are logical authority boundaries. Actual routes, native facilities and remote dependencies are open. Verify the selected product surfaces and identities before dependent integration.

| Boundary | Contract and evidence |
| --- | --- |
| Admin UI → import authority | A submitted file requests one scoped operation. Returned status describes that attempt and is checked for current permission on every status read, including recovery. A late result for a prior attempt or actor cannot overwrite the visible current status. Incremental status may advance from pending/unknown to a terminal verdict, which stays final. Verify direct submission, status access, stale responses, interrupted recovery and result redaction under R-1/R-4. Owned acceptance/outcome events follow R-4D. |
| Import authority → product authorization and account authorities | Current scope and create permission gate admission and commitment. Revocation gates subsequent protected reads. On unavailable authority fail closed. Directory reads show authoritative committed effects. Only new identities change, and unrelated records and grants remain intact under concurrent writers. Recover ambiguous acknowledgments with authoritative verdict and directory evidence. Verify actual actor binding, revocation timing, atomicity, conflict scope and read-back. Ordinary creation side effects have an open discovery prerequisite under R-3. |
| Import authority → existing restricted operational surface, if separate | Use the existing event contract for the R-4D outcomes and detect delivery gaps or failure without changing the business verdict. Verify event scope, redaction, deduplication and sink-failure visibility at the selected boundary. No second telemetry service is required by the request. |

Cache invalidation, stream subscriptions and remote metadata synchronization are inapplicable to the proposed behavior because it relies on current authorities and attempt-scoped status. No external provider, public API, delivery notification, or asynchronous transport is selected. Runtime native facilities for active input, account writes, receipts and existing operational evidence remain selection prerequisites with the quotas below.

## Flows and transitions

- **F-1 — Successful import (R-1–R-4).** An authorized admin starts in the ordinary user administration context, selects a supported file, and submits it explicitly (T-1, T-2). Receipt and pending feedback precede validation and commitment (T-3, T-4). The admin observes the confirmed count, then opens the ordinary directory to see the new accounts.
- **F-2 — Refusal, rejection and correction (R-1–R-4).** A denied actor cannot start a protected attempt (T-2). File, row, identity or write problems reject an admitted attempt (T-3/T-4). A still-authorized admin can correct a rejected submission and start a distinct attempt (T-6).
- **F-3 — Lost response or interruption (R-1, R-3, R-4).** After submission, the client loses confirmation. The same currently authorized admin recovers by reference (T-5). Recover the actual terminal verdict, continue to show an uncertain outcome while the verdict is unavailable, or report expiration (T-7). Timeout and UI closure do not establish the directory outcome.

| Transition | Before, trigger and guard | After, effect and observation |
| --- | --- | --- |
| T-1 / F-1 / R-2A | An authorized admin selects one file from an empty state, or replaces or clears an unsent draft | Update or clear the local draft. The directory stays as it was. Leaving the view or losing the owning session clears the draft. |
| T-2 / F-1,F-2 / R-1A,R-4A–B | An admin submits a draft explicitly with verified authority and scope. Missing file, missing authority or interrupted transfer have separate guards | Authorized receipt leads to pending processing. A denied or missing-file request has no account effects. Transfer interruption leaves the client uncertain if it cannot establish delivery. |
| T-3 / F-1,F-2 / R-2B–C,R-3B | While pending, inspect the complete file, then row rules and identity groups | Invalid structure, rows or initial conflicts reject with actionable permitted reasons and no account effects. Valid input becomes eligible to commit. Account effects start at T-4. |
| T-4 / F-1,F-2 / R-1B,R-3A–C,R-4A,D | At commitment for an eligible attempt, verify current authority and identity availability | Either durable batch and successful outcome, or definite rejection with zero changes from the batch. Unavailable confirmation stays uncertain to the observer until T-5. |
| T-5 / F-3 / R-1B,R-4A–B,D | For pending, terminal or uncertain outcomes, require the same reference and current scope and authority | Recover pending or the actual terminal outcome. Restore the committed result after lost acknowledgment or the rejection after proven non-commit. Same-attempt replay adds no effects. Denied access reveals no status. |
| T-6 / F-2 / R-2A,R-4C | After definitive rejection, the authorized admin in the same view corrects or replaces the file and submits | New attempt enters through T-2 with a new reference. The original rejection remains terminal during its recovery window. |
| T-7 / F-3 / R-4B,D | Recovery window ends under the approved policy | Receipt and its app-owned diagnostic copies are removed within the cleanup bound. Lookup/replay reports unavailable without effects. Confirmed account state follows ordinary lifecycle. |

Pending and terminal outcomes belong to the import authority. An uncertain outcome belongs to the observer and can coexist with an authoritative commitment. A draft and its later attempts are separate from users, whose durable state is visible through the directory. Follow the R-4 recovery/escalation rule for unresolved operations, including near expiry. Ordinary account deletion and migrations do not form part of the import state machine.

## Non-functional requirements

- **Visual design and accessibility.** Use the [Light expressive starting point](GUIDES/platforms/ui.md#light-expressive-starting-point) with the light Google Gemini reference and Material 3 Expressive principles as the starting appearance for a new web surface. Start light with a dark option. Confirm and inherit established product identity and platform conventions when available. Give the file selection and main import action the strongest visual emphasis, with tonal rounded surfaces and a clearly grouped result area showing count or corrective actions. Use a consistent type and spacing scale, light/dark palette and one icon set. Design the empty, file-selected, in-progress, uncertain, error and success states. At representative narrow and wide supported widths, the page must fit without horizontal overflow and retain access to actions and errors. Support touch and keyboard selection, visible focus, WCAG AA contrast, readable announced status without moving focus on every update, and recovery feedback that remains available. Use motion only to clarify a change and honor reduced motion. Confirm in rendered browser checks for both themes, narrow and wide compositions, keyboard and assistive technology, and controlled async states. The project design system is an open input to the concrete treatment. The supplied UI and interaction guides are the available design guidance for this spec.
- **Workload and runtime fit.** Verify a representative typical file, each inclusive maximum and an over-limit input on the selected target with its real request, storage and execution limits. Also observe same-identity contention and disjoint simultaneous batches. Open bounds include request/file size, record and field maxima, simultaneous active work, resource/time ceiling, and acceptable upload-to-feedback and upload-to-verdict latency at the agreed workload. Runtime owner supplies evidenced platform limits and measurements. Product owner supplies any service targets. Set supported limits inside hard limits before release. The numeric bounds are open. The admin must get pending or actionable rejection when the runtime cannot safely admit work.
- **Integrity, reliability and privacy.** Under simultaneous writes, process failure, lost responses and role changes, observe the R-1/R-3/R-4 invariants at the real authority. Inspect the UI, restricted operator outputs and state lifecycle for redaction, authorization and expiry using synthetic data. Open bounds for receipt recovery, unresolved outcome escalation, pending input cleanup, event retention and deletion are in R-2/R-4. Confirm any existing data handling or compliance policy with its owner. Avoid asserting an availability or latency SLA from this spec.
- **Compatibility and operability.** Confirm the product's supported web/browser and account integration surfaces before integration. Exercise the published CSV rules across those surfaces without a specific spreadsheet application. Verify that diagnostics distinguish input, authority, conflict, write failure and uncertain outcome without disclosing other users. There is no new requirement for spreadsheet-specific formats, offline creation, deployment, cross-region support, backfill, or a separate service because the request names only interactive CSV import.
