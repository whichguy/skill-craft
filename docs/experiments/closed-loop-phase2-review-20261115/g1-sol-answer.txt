I did **not** verify a false QUIET from ordinary, completed harness artifacts. I did verify false cleanup evidence, which the orchestrator can accept for C5. The six stated decisions remain intact.

The changes below are ordered by priority.

1. **Verified bug — cleanup can acknowledge a worker that subsequently starts executing.**

   Concrete window: `worker_main` acquires its lock and reads `starting`, then pauses before saving its identity. Cleanup sees a live lock but `worker:null`; `kill_step` stops nothing, and `settle` writes `cancelled`. Cleanup returns `verified:true`. The paused worker then saves `running` and proceeds.

   My controlled witness returned verified cleanup over zero run folders, followed by worker execution and a final `published` record. The equivalent cancellation window exists in `step_cancel`.

   Require a durable cancellation handshake and synchronized transitions; a worker must recheck cancellation before execution. Test the interval **after lock acquisition but before identity publication**, rather than only established running workers. [facade.py — `worker_main`, `kill_step`, `step_cancel`, `cmd_cleanup`, `settle`](/private/tmp/g1-sol.tHD7YG/checkout/test/shiploop_e2e/adapter/facade.py). [Witness](/private/tmp/g1-parent-witness-rcdutfqs/results.json).

2. **Verified bug — failed process termination does not prevent verified cleanup.**

   `kill_step` returns group outcomes and session survivors, but `cmd_cleanup` and `settle` do not incorporate them into verification. With `group:"survived"` and a nonempty survivor list, my witness still received `verified:true` because lifecycle cleanup found no recorded run resources.

   This matters for reviewer, judge and improver sessions absent from the run lifecycle ledger. Require positive termination evidence before teardown and certification; preserve `protected`, unresolved identity and survivor outcomes as blockers. Add negative controls where termination leaves a survivor. [facade.py — `kill_step`, `stop_group`, `stop_processes`, `settle`, `lifecycle_cleanup`, `cmd_cleanup`](/private/tmp/g1-sol.tHD7YG/checkout/test/shiploop_e2e/adapter/facade.py). The false receipt is accepted by [closed_loop.py — `cmd_cleanup`, `check_c5`](/private/tmp/g1-sol.tHD7YG/checkout/skills/closed-loop/scripts/closed_loop.py).

3. **Verified bug — cleanup can overwrite a completed publication.**

   Unlike `step_cancel`, `cmd_cleanup` does not reload the step after stopping it. If the worker publishes while cleanup holds an earlier `running` record, cleanup subsequently saves that stale record as `cancelled`.

   Reproduced result: the tip advanced, but the durable record became `cancelled` with `iteration:null` and `prepared:null`. This separates the published candidate from its reported outcome and acceptance evidence.

   Serialize terminal transitions and reload under that synchronization before changing state. Add a barrier test where publication completes during cleanup’s kill operation. [facade.py — `cmd_cleanup`, `publish`, `step_cancel`](/private/tmp/g1-sol.tHD7YG/checkout/test/shiploop_e2e/adapter/facade.py). [Witness](/private/tmp/g1-parent-witness-rcdutfqs/results.json).

4. **Verified bug — per-worker locks do not enforce one step per workspace.**

   Two concurrent starts can both observe no record and no live worker before either writes its intent. With different keys, their locks are independent. A barrier witness accepted and launched both.

   They can then reposition X and remove each other’s worktrees through `restore_x`, `position`, `settle` and `remove_worktrees`. The existing duplicate-start test is sequential and misses this interval.

   Reserve the workspace atomically before admitting a step, including startup and pending publication. Test simultaneous starts with both identical and different keys. [facade.py — `step_start`, `live_keys`, `WorkerLock`, `restore_x`, `position`, `remove_worktrees`](/private/tmp/g1-sol.tHD7YG/checkout/test/shiploop_e2e/adapter/facade.py).

5. **Verified bug — owner decisions can invalidate pending publication.**

   A dead worker’s durable `prepared` record is excluded from `live_keys`. Consequently `cmd_decide` accepts an owner decision “between steps,” advancing T to a ledger-only D. Polling the completed step then rejects its intended T→T′ publication because D is neither endpoint.

   Reproduced using the real owner command and publication functions. The build token stayed unchanged. Reconcile prepared steps before admitting owner decisions, under the same workspace synchronization.

   The Git-object construction itself behaved correctly: original ledger mode, HEAD, index and working files were preserved; explicit identities were used; competing tip movement was refused by CAS. The defect is transaction admission. [facade.py — `cmd_decide`, `live_keys`, `advance`, `publish`](/private/tmp/g1-sol.tHD7YG/checkout/test/shiploop_e2e/adapter/facade.py). [Evidence](/tmp/g1-probes-owner-4woqs9ug/evidence.json).

6. **Verified bug — terminal start replay violates the orchestrator’s accepted replies.**

   Suppose the original launch response is lost, and the worker fails before replay. `step_start` returns the existing handle with `status:"failed"`. However, `apply_action(start)` accepts only `running` or `done`. It records another start failure instead of consuming the failed step and its reported consumption; three identical responses stop the campaign.

   Preserve idempotence while providing a response the orchestrator can register and subsequently poll, or explicitly support terminal replay in the orchestrator. Add lost-response tests ending in failure and cancellation. [facade.py — `step_start`, `advance`](/private/tmp/g1-sol.tHD7YG/checkout/test/shiploop_e2e/adapter/facade.py); [closed_loop.py — `apply_action`, `start_action`, launch intents](/private/tmp/g1-sol.tHD7YG/checkout/skills/closed-loop/scripts/closed_loop.py).

7. **Verified bugs — successful assessment retries are misread.**

Resolve authoritative final assessments per attempt, verify receipt identity, and test recovery separately from exhausted retries. 11. **Likely bug — absent leaders do not prove process-group ownership.**

    `stop_group` allows signaling when the recorded leader is absent. After the original group disappears, its number can eventually be reused; the replacement leader can also exit while leaving members.     Require verifiable surviving ownership rather than assuming uninterrupted group existence. Existing tests cover a reused **present** leader, zombies and protected ancestors, but not recycled groups with absent leaders.
