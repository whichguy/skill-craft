**Verified bug — cleanup still forgets detached survivors.** In my witness, the worker group stopped, while a separately grouped descendant resisted both signals. First cleanup correctly returned false and stored its PID. Second cleanup called `kill_step`, found the original group gone, replaced the receipt with `survivors=[]`, and returned **true while that descendant remained alive**. `kill_step` never revalidates previously recorded survivors after their parent group disappears. Storing only survivor PIDs also loses the start-time identity needed for safe later signaling. This reproduces the defect class behind request 1. [Cleanup witness](</private/tmp/g1e-publication-cleanup-n06hbahx/results.json>)

**Verified bug — terminalization can contradict an already-moved ref.** I injected `OSError(ENOSPC)` while saving `published`, after a real `update-ref`. Poll correctly recovered to `published/done`. Given the identical persisted `prepared` state, both `step_cancel` and `cmd_cleanup` instead settled it `cancelled`, reporting “its finished result was not published,” while the ref remained at its result. The finished iteration is then omitted from the reply although its changes are published. [Publication witness](</private/tmp/g1e-publication-cleanup-n06hbahx/results.json>)

There is also a normal completion race: cancellation of an already-published record returns `done`; [closed_loop.py — cmd_cancel](skills/closed-loop/scripts/closed_loop.py) accepts only `cancelled` and leaves the campaign step running. The replan fixes this mismatch only for unpublished prepared records. [Published-cancel witness](</private/tmp/g1e-publication-cleanup-n06hbahx/published-cancel.json>)

The locks and repeatable `publish` prevent competing publication or duplicate engine execution on the reviewed paths. Deliberately discarding an unpublished finished result is the owner’s accepted **judgement**; discarding its accounting after publication is a bug.

**Verified bugs — delegation does not establish epoch parity on every path.** `epoch_facts` catches `OSError`, `ValueError`, `KeyError`, `TypeError` and `SystemExit` around state/events; receipt reads catch `OSError`/`ValueError`. Other child failures become bridge failures, which `epoch_evidence` reports as unreadable. Ordinary torn ledgers, changed registrations, rewritten receipts and changed sealed runs therefore fail closed.

However:

- `epoch_evidence` treats an absent epoch as zero expected assessments without checking whether the cycle legitimately stopped before registration. A retained `DROP` result with missing epoch evidence can inherit complete exploration assessments and return `invalid=[]`.
- An **existing accepted epoch without a decision**, containing `not_launched`, `unknown_launch`, `recorded` and `reviewed` attempts, also becomes `expected=0,incomplete=0`. The bridge preserves those states; the facade discards them. The harness requests another launch, while facade review/judge facts can both say complete.
- `invocation_evidence` adds an incomplete **review** placeholder but no corresponding judge placeholder. An incomplete assessment caused by an invalid judge can consequently yield `judge.valid=true,complete=true`. This predates the diff; review failure still blocks QUIET.

These are verified fact defects, **not demonstrated whole-campaign false QUIET certificates**. Legitimate pre-epoch `NO_CANDIDATE` remains a valid separate case. [Epoch witnesses](</private/tmp/g1e-epoch-status-j6ongcx6/results.json>), [unfinished-epoch witness](</private/tmp/g1e-epoch-status-vbtzug4q/no-decision-results.json>)
