## 1. PropertiesService: atomicity, concurrency, limits

- Google's PropertiesService reference/guide pages do **not** state anywhere that a read‑modify‑write cycle (e.g., `getProperty` then `setProperty`) is atomic, and do not mention thread-safety. This is an undocumented gap, not a documented guarantee. [Properties Service guide](https://developers.google.com/apps-script/guides/properties) · [Class Properties reference](https://developers.google.com/apps-script/reference/properties/properties)
- Google's recommended mechanism for coordinating access to a shared resource across concurrent executions is LockService: "This service allows scripts to prevent concurrent access to sections of code. This can be useful when you have multiple users or processes modifying a shared resource and want to prevent collisions." [Lock Service overview](https://developers.google.com/apps-script/reference/lock)
- Three lock scopes are available: `getScriptLock()` — "Gets a lock that prevents any user from concurrently running a section of code"; `getUserLock()` — "Gets a lock that prevents the current user from concurrently running a section of code"; `getDocumentLock()` — "Gets a lock that prevents any user of the current document from concurrently running a section of code." [Class LockService reference](https://developers.google.com/apps-script/reference/lock/lock-service)
- A lock is not actually acquired until `tryLock(timeoutInMillis)` (returns immediately, boolean) or `waitLock(timeoutInMillis)` (blocks until acquired or throws) is called; `releaseLock()` releases it, and the lock is also auto-released when the script terminates, but Google advises releasing explicitly "as soon as you no longer need exclusive access." [Class Lock reference](https://developers.google.com/apps-script/reference/lock/lock)
- Property size/count limits, from the official quotas table: **9 KB / val** (max size per property value) and **500 KB / property store** (max total storage per property store — script/user/document), identical for Consumer and Google Workspace accounts. [Quotas for Google Services](https://developers.google.com/apps-script/guides/services/quotas)
- Daily quota for property read/write operations: **50,000 / day** for Consumer accounts, **500,000 / day** for Google Workspace accounts. [Quotas for Google Services](https://developers.google.com/apps-script/guides/services/quotas)
- The Properties Service guide separately notes the *manual* editor UI can add "up to fifty custom properties" via the project settings page, but "to add more than fifty properties, add them programmatically" — this is a UI convenience limit, not a hard API limit. [Properties Service guide](https://developers.google.com/apps-script/guides/properties)
- Properties are scoped and cannot cross scripts: "Properties cannot be shared between scripts." [Class PropertiesService reference](https://developers.google.com/apps-script/reference/properties/properties-service)

## 2. Session.getActiveUser() vs Session.getEffectiveUser()

- `getActiveUser()`: "Gets information about the current user. If security policies do not allow access to the user's identity, `User.getEmail()` returns a blank string." [Class Session reference](https://developers.google.com/apps-script/reference/base/session)
- The same page enumerates when the email is blank: "The user's email address is not available in any context that allows a script to run without that user's authorization, like a simple `onOpen(e)` or `onEdit(e)` trigger, a custom function in Google Sheets, or a web app deployed to 'execute as me.'" It adds: "these restrictions generally do not apply if the developer runs the script themselves or belongs to the same Google Workspace domain as the user." [Class Session reference](https://developers.google.com/apps-script/reference/base/session)
- `getEffectiveUser()`: "Gets information about the user under whose authority the script is running. If the script is a web app set to 'execute as me' (the developer), this returns the developer's user account. If the script is running under an installable trigger, this returns the account of the user who created the trigger. In most other scenarios, this returns the same account as `getActiveUser()`." [Class Session reference](https://developers.google.com/apps-script/reference/base/session)
- Both methods can require the `https://www.googleapis.com/auth/userinfo.email` scope. [Class Session reference](https://developers.google.com/apps-script/reference/base/session)
- The Web Apps guide confirms only two "execute as" choices exist: "Execute the app as me" ("the script always executes as you, the owner of the script, no matter who accesses the web app") vs. "Execute the app as user accessing the web app" ("the script runs under the identity of the active user"). [Web Apps guide](https://developers.google.com/apps-script/guides/web)
- **Gap found:** Google's current official docs do not publish a single consolidated table cross-referencing `getActiveUser()`/`getEffectiveUser()` return values against every "Who has access" setting (only myself / domain / anyone with a Google account / anyone) or against consumer vs. Workspace accounts. The behavior in Fact list item 2 above (execute-as-me → active user often blank; installable trigger → effective user = trigger owner) is the only officially documented slice; the rest is not stated verbatim on a single Google page. Do not treat any granular matrix for this as sourced — flagged in "Claims to check" below.

## 3. Concurrency of executions

- Simultaneous executions are explicitly quota-limited per user, not serialized by Apps Script: **30 / user** for both Consumer and Google Workspace accounts (i.e., the platform allows concurrency up to that cap, meaning two users' `google.script.run` calls to the same script absolutely can run at the same time). [Quotas for Google Services](https://developers.google.com/apps-script/guides/services/quotas)
- There is no per-project serialization documented; instead, Google documents LockService specifically because concurrent executions are normal and can collide: "useful when you have multiple users or processes modifying a shared resource and want to prevent collisions." [Lock Service overview](https://developers.google.com/apps-script/reference/lock)

## 4. google.script.run

- "`google.script.run` is an asynchronous client-side JavaScript API available in HTML-service pages that can call server-side Apps Script functions... it is asynchronous and does not return directly; however, the server-side function can return a value to the client as a parameter passed to a success handler." [google.script.run reference](https://developers.google.com/apps-script/guides/html/reference/run)
- `withSuccessHandler(function)`: "Sets a callback function to run if the server-side function returns successfully. The server's return value is passed to the function as the first argument." [google.script.run reference](https://developers.google.com/apps-script/guides/html/reference/run)
- `withFailureHandler(function)`: "Sets a callback function to run if the server-side function throws an exception. The Error object is passed to the function as the first argument." [google.script.run reference](https://developers.google.com/apps-script/guides/html/reference/run)
- `withUserObject(object)`: "Sets an object to pass as a second parameter to the success and failure handlers," letting callbacks respond to call context without sending the object to the server. [google.script.run reference](https://developers.google.com/apps-script/guides/html/reference/run)
- Legal argument/return types: "JavaScript primitives like a Number, Boolean, String, or null, as well as JavaScript objects and arrays that are composed of primitives, objects, and arrays." Prohibited: "Date, Function, or DOM element besides form" (including nested inside objects/arrays); circular references fail; `undefined` array entries become `null`. Return values follow the same rules except a form element is not a legal return type. [google.script.run reference](https://developers.google.com/apps-script/guides/html/reference/run)

## Claims to check

- **Wrong belief:** "Properties read-modify-write is atomic, so it's safe for counters without a lock." **Correction:** Not documented as atomic anywhere in Google's PropertiesService docs — treat it as unsafe for concurrent read-modify-write and wrap with `LockService.getScriptLock()`/`getUserLock()` + `tryLock`/`waitLock`. Source: absence of any atomicity claim in [Properties Service guide](https://developers.google.com/apps-script/guides/properties) and [Class Properties](https://developers.google.com/apps-script/reference/properties/properties); locking guidance from [Lock Service overview](https://developers.google.com/apps-script/reference/lock).
- **Wrong belief:** "Apps Script serializes all executions of a script, so two users can't run it at once." **Correction:** False — up to 30 simultaneous executions per user are permitted; this is exactly why LockService exists. Source: [Quotas for Google Services](https://developers.google.com/apps-script/guides/services/quotas), [Lock Service overview](https://developers.google.com/apps-script/reference/lock).
- **Wrong belief:** "`getActiveUser()` always returns the caller's email in a web app." **Correction:** It returns a blank string in several documented contexts, notably any web app deployed as "execute as me," and simple triggers/custom functions. Source: [Class Session reference](https://developers.google.com/apps-script/reference/base/session).
- **Wrong belief:** "There's an official Google table listing every getActiveUser()/getEffectiveUser() result for every combination of execute-as × who-has-access × consumer/Workspace." **Correction:** No such consolidated official table was found on developers.google.com or support.google.com as of this check; only the individual method descriptions and the two execute-as modes are documented. Treat any such matrix as inference, not a sourced Google claim. Source: [Class Session reference](https://developers.google.com/apps-script/reference/base/session), [Web Apps guide](https://developers.google.com/apps-script/guides/web).
- **Wrong belief:** "`google.script.run` can pass/return a JS `Date` object or a DOM element directly." **Correction:** Explicitly prohibited (Date, Function, DOM elements besides `form`); serialize dates as strings/timestamps instead. Source: [google.script.run reference](https://developers.google.com/apps-script/guides/html/reference/run).
- **Wrong belief:** "Manually adding properties via the Script Properties editor UI has the same 500 KB/9 KB API limits as programmatic properties, with no separate cap." **Correction:** The UI itself additionally caps manual entry at 50 properties before you must switch to code — a separate, lower practical limit than the storage quota. Source: [Properties Service guide](https://developers.google.com/apps-script/guides/properties).
