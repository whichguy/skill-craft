## 1. Architecture Decision

**Actors:** ~20 internal, authenticated org users (no anonymous access, no external Experience Cloud need stated).

**State & ownership:** A single shared team task board, server-authoritative. `Task__c` custom object holds title, description, `Status__c` (picklist = board columns: New/In Progress/Done), `Assignee__c` (Lookup to User). Comments are **not** a custom object — reuse native Chatter (Feed Tracking enabled on `Task__c`) so commenting, feed visibility, and notifications come free from the platform instead of being built. Org-Wide Default = Public Read/Write for `Task__c` (a 20-person team board has no need for row-level privacy; all colleagues see/edit all tasks). No board/project grouping — single shared board, since the request doesn't call for multiples (assumed default; flag to user if they actually want per-team boards).

**Concurrency:** Standard Salesforce record locking + last-write-wins on save is sufficient for a 20-person team; no custom optimistic-lock/merge logic is warranted at this scale.

**Lifecycle/end of state:** Tasks persist indefinitely once created (no expiry stated); "Done" is a status, not a deletion. Deletion is manual via standard record delete, respecting object delete permission. No auto-archival — carried to user as an open question with this default (skip auto-archive).

**Freshness channel:** The requirement is "within a minute," not sub-second — this rules out Platform Events/CometD/empApi (unnecessary Streaming API allocation cost) and points to **polling**, the lightest channel that meets the stated bound. LWC polls an `@AuraEnabled(cacheable=true)` Apex wire every ~20–30s and calls `refreshApex`, re-reading authoritative server state each cycle (not caching mutated data). Timer is cleared on `disconnectedCallback` to avoid leaks. Chatter comments render via the standard `lightning-feed` (embedded feed) component, which has its own native refresh; the same poll cadence is applied to keep it consistent with the ~1-minute bound rather than adding a second channel.

**Server-side enforcement:** All Apex mutation methods (`createTask`, `updateTaskStatus`, `assignTask`) run `WITH SECURITY_ENFORCED`/`Security.stripInaccessible` and validate inputs (required title, assignee must be an active user) — this is a caller the org doesn't fully control (any of 20 users), so CRUD/FLS/sharing checks apply on every write even though there's no anonymous-input abuse-limiting need.

**Personal/secret data:** Only user names and task text; no PII beyond standard user identity already in Salesforce. No custom logging of comment/task content; standard org data retention/backup applies — no additional storage/removal policy needed.

**Quotas:** Polling per user every ~20–30s across 20 users stays well within Apex/API daily limits for a scratch org; no Streaming API or Platform Event allocation is consumed since polling (not push) is used.
