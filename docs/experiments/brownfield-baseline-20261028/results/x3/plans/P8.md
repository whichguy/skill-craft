## Summary

S1 is already delivered by this repository (baseline `f6c46b59`), so the plan adds no endpoint. `GET /api/v3/checks/` (`hc.api.views.checks` -> `get_checks`, behind `authorize_read`) returns a project's checks as JSON with each check's `status` (recomputed on every request by `Check.get_status`) and `last_ping`. It accepts the project's read-only API key (`Project.api_key_readonly`, an `hcr_` key created and revoked in Project Settings) in `X-Api-Key`, allows cross-origin GET, and every state-changing route (`authorize`, `accept_ro=False`) answers that key with 401. The built-in `/tv/` dashboard already polls it this way and `templates/docs/api.md` documents it. One work item, W1, owns all three outcomes of S1 (O1: a JSON listing of a project's checks; O2: each entry carries current status and last ping time; O3: the token cannot change anything) by adopting that path as the producer and closing the only gaps in the evidence: no test asserts `status` and `last_ping` in a read-only key's listing, and none asserts that a read-only key is refused by pause, resume or delete. No model, migration, token type, setting, module or public name is introduced.

## Decisions

AD-1 Deliver S1 with the existing Management API read-only path, `GET {SITE_ROOT}/api/v3/checks/` (`hc.api.views.checks` -> `get_checks`, `@authorize_read`), and add no endpoint, view or response field. Why: for the key's project it already returns `{"checks": [...]}` with `status` and `last_ping` per check, allows cross-origin GET with `X-Api-Key` (`cors` sends `Access-Control-Allow-Origin: *` and allows that header), is documented in `templates/docs/api.md`, and is what the built-in `/tv/` page polls. Alternatives: a new dedicated status endpoint (duplicates `get_checks`; the name is also taken, see AD-3); the session-only `hc.front.views.status` (needs a login, not a token); the Prometheus `metrics` view at `/projects/<uuid>/metrics/` (accepts the read-only key but returns Prometheus text with no `last_ping`); public badge JSON (`hc.api.views.badge`: tag totals, no per-check list). Basis: S1.

AD-2 The token is the project's existing read-only API key (`Project.api_key_readonly`; new keys are `hcr_` + 28 characters, stored as an 8-character prefix plus an HMAC-SHA256 digest, created and revoked by read-write members in Project Settings -> API Access); add no new token type, scope, expiry or per-dashboard key. Why: it is project-scoped and revocable, `authorize` (`accept_ro=False`) refuses it on every write route, and in read-only mode `Check.to_dict` drops `uuid`, `ping_url`, `update_url`, `pause_url`, `resume_url` and `channels`, so it cannot yield a ping URL (a ping URL is itself a write capability). Alternatives: scoped, expiring per-dashboard tokens (new model, migration and settings UI); the instance-wide `METRICS_KEY` (not project-scoped, guards only `/api/v*/metrics/`); a login session. Basis: S1.

AD-3 Add no stored data, schema, setting, module, route or public name; W1's tests extend existing test modules. Why: the key (`Project.api_key_readonly`, `CharField(128)` with `db_index`, owned by the `hc/accounts` migrations) and the checks (`hc.api` `Check`: `status`, `last_ping`, `timeout` or `schedule`, `grace`, `last_start`, owned by the `hc/api` migrations) already hold everything S1 reads, on every supported database (SQLite by default, PostgreSQL, MySQL/MariaDB); and `status` is already `hc.api.views.status` (`/api/v1/`, `/api/v2/`, `/api/v3/` `status/`, the database probe), `hc.front.views.status` and `status_single`, and `Check.status`, so any new code under that name would collide. Alternatives: a snapshot or last-seen table per dashboard (stale, needs a writer); a new `hc/api/dashboard.py` module or `/api/v3/dashboard/` prefix; a route or view called `status`. Basis: S1.

AD-4 Keep the existing safeguards as the only ones: `authorize_read` verifies the key on the server for every call (32-character length gate, then `Project.objects.for_api_key`, hashed keys compared with `hmac.compare_digest`), reads the key from the `X-Api-Key` header only (never a URL), scopes the query to `request.project`, and answers a missing or wrong key with a 401 JSON error before any project data is read; every state-changing route uses `authorize`. Add no in-app rate limiter and no failure record. Why: the listing performs no writes and has no background or async step whose failure needs recording; keys carry 168 bits (`token_urlsafe(21)`), so guessing is impractical; `TokenBucket.authorize` writes a row on every call, which would turn a read-only GET into a database write. Alternatives: a `TokenBucket` limit per key or IP; accepting the key as a query parameter (leaks into logs) or as `Authorization: Bearer` (only the Prometheus view does); an origin allow-list instead of `Access-Control-Allow-Origin: *`. Basis: S1.

AD-5 Dashboards pull by polling the same endpoint with plain HTTP GET, and the status is computed at request time by `Check.get_status`; add no push channel, cache or webhook. Why: S1 asks for the current status of a list; `get_status` reports `down` as soon as `last_ping` + timeout + grace has passed, without waiting for the `sendalerts` job to persist the change, and the built-in `/tv/` page already polls every 5 seconds. Alternatives: server-sent events or webhooks (subscription storage plus a live channel); response caching (stale status); returning the stored `Check.status` column (stale between `sendalerts` runs). Basis: S1.

## Assumptions

- "A project's checks" means one Healthchecks project and "a token that cannot change anything" means that project's read-only API key; keys are project-scoped (there is no account-wide key), so a dashboard covering several projects holds one key per project, as `/tv/` does.
- "Current status" is the API v3 `status` value (`new`, `up`, `grace`, `down`, `paused`; a running check is the separate `started` flag, whereas v1 reports `started` as the status) and "last ping time" is `last_ping` (set by success and fail signals, not by start or log pings; null until the first ping), the same field the UI shows; dashboards call `/api/v3/`.
- Dashboards can send an `X-Api-Key` request header (the CORS preflight allows exactly that header); a client restricted to `Authorization: Bearer` or to a key in the URL is not covered by S1 as written and would be a new request.
- Exposing every field of the read-only check payload (name, tags, desc, `next_ping`, filter keywords, `badge_url`, `unique_key`) to a read-only key holder is acceptable, because that is what the existing read-only mode returns and S1 does not ask to trim it.
- The documented "100 requests per minute" guidance is enforced outside this repository (hosted edge or operator proxy); no code path in `hc.api` returns 429, and S1 asks for none.
- Environments: the local checkout (Django 6.1.2; Python 3.12 in CI and 3.14 in `docker/Dockerfile`; SQLite by default; `./manage.py test`), any deployment of the same code (gunicorn in the Docker image or another WSGI host; PostgreSQL or MySQL/MariaDB) serving `/api/v3/checks/` from the same `hc.api` code, and external dashboards (browser or server-side) calling it over HTTP; W1 changes only test files in the first, so no deployment, configuration or migration step exists.
- The listed existing tests pass at `f6c46b59`; this stage ran nothing, so W1's first act is to run them.
- Pagination, a trimmed payload, UUIDs in the read-only response, per-dashboard tokens and rate limiting are not part of S1; if the requester wants one, that is a new request and W1 does not pre-build it.
- The work stays in this local checkout and nothing is sent upstream; the project's conventions (CONTRIBUTING.md: ruff formatting and a test with each change; CI: `manage.py test` and `mypy --strict hc`) govern W1's test additions.
