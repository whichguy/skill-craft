## Summary

Failed deliveries are retried by the process that already delivers them, using the rows that already record them. When `Channel.notify` gets a non-permanent `TransportError` for a saved status change, it writes on that attempt's own `Notification` row the status change (new nullable `flip`), the attempt number (`attempt`) and the time the next retry is due (`retry_at`: 1, 5 and 25 minutes after each failure, at most 3 retries); `sendalerts` gains one poll in its existing loop that claims a due row with a conditional UPDATE and calls `Channel.notify` again, so every retry is a new row and the Events log, which already lists notifications with their "Error:" line, shows every attempt with no display change. Kept as they are: the pull model without broker or scheduler, claim-first delivery, one transport per kind (no transport file changes), the in-attempt tries, log assembly, retention, authorization and configuration (no new setting). Changed because S1 asks for it: AD-6 (a failed attempt is final) and AD-12 (retries only inside an attempt, no back-off, no stored count), replaced by AD-28 and AD-29; AD-30 (three columns, migration 0124) and AD-31 (one row per attempt) are new. Test notifications, account-deletion notices and a group's own attempt are not retried (a group's members retry individually). Two items in order: W1 records and schedules (safe to ship alone), W2 executes the retries, proves the log shows each attempt and aligns the user-facing text; S1's retry count and delays are owned by W1 (schedule) and W2 (execution), its display clause by W2. The decisions are also recorded in `docs/shiploop/architecture.md` (AD-28 to AD-31 added, AD-6 and AD-12 moved to Superseded with Basis: S1) and R-2, R-3, R-15 and R-18 in `docs/shiploop/spec.md` gain Basis: S1.

## Decisions

- AD-1 (inherited) One Django project with one app per feature area; delivery, its models and the alert process live in `hc/api`, and every new name goes there (`Notification.flip`, `Notification.attempt`, `Notification.retry_at`, a delays constant in `hc/api/models.py`, a retry step and worker function in `sendalerts.py`, migration `0124`) with no new app, package or module. Why: it keeps each feature area self-contained, so the retry code sits beside `Channel.notify` and `sendalerts`. Alternatives: a new app for retries (more structure than a few columns and one poll step need). Evidence: `hc/settings.py` `INSTALLED_APPS`; `hc/urls.py` `urlpatterns`. Basis: none
- AD-3 (inherited) All state lives in one relational database through the ORM (SQLite, PostgreSQL, MySQL, MariaDB), schema changes are numbered per-app migrations (latest `0123`), and code avoids engine-specific behaviour and known slow plans. Why: the same code and tests must run on all four engines. Alternatives: none considered; the plan adds columns to the existing store only. Evidence: `hc/settings.py` `DATABASES`; `.github/workflows/tests.yml` `matrix`; `hc/api/migrations/0123_alter_channel_kind.py` `Migration`. Basis: none
- AD-4 (inherited) Alert delivery is a pull model with no broker: the web process (or the alert process) writes a status change row and the separate `sendalerts` process polls and delivers; there is no scheduler. Why: the web process only records the change and the alert process picks it up. Alternatives: a broker or scheduler for delayed retries (rejected in AD-28); "no retry table" stays true because retry state is columns on an existing table. Evidence: `hc/api/models.py` `Check.create_flip`; `hc/api/management/commands/sendalerts.py` `Command.process_one_flip`. Basis: none
- AD-5 (inherited) Work is claimed with conditional UPDATEs that must change exactly one row, so several processes run without locks and a lost race is skipped. Why: several `sendalerts` processes may share one database. Alternatives: none; the retry claim copies it. Evidence: `hc/api/management/commands/sendalerts.py` `Command.process_one_flip` (`num_updated`); `Command.handle_going_down`. Basis: none
- AD-7 (inherited) `sendalerts` is one long-running command: a poll loop with a 2 second idle sleep, a thread pool of `--num-workers`, signal handlers that let running deliveries finish and stale DB connections closed per thread; operators keep it running and the Docker image stops when it exits. Why: alerts are a continuous duty of an instance. Alternatives: a second process for retries (more to supervise; rejected in AD-28). Evidence: `hc/api/management/commands/sendalerts.py` `Command.handle`; `docker/run.sh` `wait -n`. Basis: none
- AD-8 (inherited) One transport class per integration kind behind `Transport.notify(flip, notification)`, registered in `TRANSPORTS`; the plan edits no transport. Why: a uniform contract lets the alert process treat every kind alike. Alternatives: per-kind retry code (rejected in AD-29). Evidence: `hc/api/models.py` `TRANSPORTS`; `hc/api/transports.py` `Transport`. Basis: none
- AD-9 (inherited) Delivery errors are `TransportError(message, permanent)`: the message is user-facing text, `permanent` disables the integration, and any other exception is a bug and propagates; the plan retries only non-permanent ones. Why: it separates expected remote failures from bugs and lets a transport say "stop trying". Alternatives: a non-retryable flag for quota refusals (not added; assumption 5). Evidence: `hc/api/transports.py` `TransportError`; `hc/api/models.py` `Channel.notify`. Basis: none
- AD-10 (inherited) One delivery attempt is one `Notification` row, inserted with the error text "Sending" before the call and finalized after it; late callbacks and bounces address the same row by its code and save only the `error` column; `Channel.last_notify`, `last_notify_duration` and `last_error` summarize the latest attempt. Why: the row must exist before sending so callbacks can name it; the plan keeps this and gives each retry its own row. Alternatives: none; extended with columns in AD-30. Evidence: `hc/api/models.py` `Channel.notify` (`n.error = "Sending"`), `Notification`; `hc/api/views.py` `notification_status`, `bounces` (`update_fields=["error"]`). Basis: none
- AD-11 (inherited) `Channel.notify` is the single entry point for one delivery and returns the outcome as text ("" for success, "no-op" or the error); the alert process, the Test! view, the group transport and the deletion-notice command call it, and the retry step becomes a fifth caller. Why: one choke point keeps records, integration state and quota use consistent. Alternatives: a second delivery path for retries (would duplicate the record keeping). Evidence: `hc/api/models.py` `Channel.notify`; `hc/integrations/group/transport.py` `Group.notify`; `hc/front/views.py` `send_test_notification`; `hc/accounts/management/commands/senddeletionscheduled.py` `Command.send_channel_notifications`. Basis: none
- AD-14 (inherited) A check's event log is assembled per request from the ping, notification and status-change tables and rendered by shared row templates; there is no unified event table. Why: retention bounds the rows, so three small queries are cheap. Alternatives: none; AD-31 reuses it. Evidence: `hc/front/views.py` `_get_events`; `templates/front/log_row.html` `event.check_status`; `templates/front/event_summary.html` `event.error`. Basis: none
- AD-15 (inherited) Retention of notifications follows ping retention (default 100 pings per check), runs inline on every 100th ping plus an optional batch command, and has no setting of its own. Why: one knob keeps the log consistent. Alternatives: none; pending retries live and die with their rows. - AD-16 (inherited) Authorization is per project, checked in each view through helpers that resolve the check and the caller's role (404 for non-members, 403 for anonymous live polls); the plan adds no endpoint, page or anonymous input, so retry attempts are visible to exactly the people who see the first attempt. Why: teams share projects with roles. Alternatives: none. Evidence: `hc/front/views.py` `_get_check_for_user`, `log_events`. Basis: none
- AD-18 (inherited) Configuration is read from environment variables in `hc/settings.py` and every setting is documented; the plan adds no setting because S1 fixes the delays. - AD-19 (inherited) Expected failures are data (row error text, integration last error, statsd counters, the alert process's log lines); unexpected exceptions go to the `hc` logger, whose handler writes them to the database. Why: small installs need failures visible without an external log service. Alternatives: none; retries follow it. Evidence: `hc/api/management/commands/sendalerts.py` `Command.on_notify_done`; `hc/settings.py` `LOGGING`. Basis: none
- AD-25 (inherited) Tests run with Django's runner, one `tests/` package per app (`BaseTestCase`, `time_machine` for time), and CI runs them on SQLite, PostgreSQL, MySQL and MariaDB with Python 3.12 to 3.15. Why: the supported-environment promises are proven only by running the suite on each. Alternatives: none. Evidence: `.github/workflows/tests.yml` `matrix`; `hc/test.py` `BaseTestCase`; `hc/api/tests/test_check_model.py` `time_machine`. Basis: none
- AD-26 (inherited) Every module starts with `from __future__ import annotations` and the tree passes `mypy --strict` with django-stubs; Python is formatted with ruff. Why: CI enforces the type check on every push. Alternatives: none. Evidence: `.github/workflows/mypy.yml` `mypy --strict`; `mypy.ini` `django-stubs`. Basis: none
- AD-27 (inherited) User-visible changes are written into `CHANGELOG.md` under the top "## v..." heading in the same commit as the code. Why: the changelog is the release record. Alternatives: none. Evidence: `CHANGELOG.md` "Unreleased"; `hc/settings.py` `VERSION`. Basis: none
- AD-28 (changes AD-6) A failed delivery is no longer final. Delivery stays claim-first as in AD-6 (the status change is marked processed before any integration is contacted, and a crash or escaped exception still abandons that status change's remaining integrations), but a non-permanent failed attempt is re-queued on its own `Notification` row: the `sendalerts` loop polls for due retries after its flip step, claims one with a conditional UPDATE that clears the due time before delivering (as AD-5), and delivers through `Channel.notify` (AD-11) on the existing worker pool; a crash after the claim loses that retry instead of duplicating it. Why: S1 needs a stored due time and something to wake up for it; the pull loop, its pool, its signal handling and its claim rule already exist, so a retry is one more poll and operators run nothing new. Alternatives: a broker with delayed tasks (Celery, RQ) or OS timers (new infrastructure for self-hosters, against AD-4); a separate retry table (a second record to keep in step with the log, pruning and cascades); sleeping 25 minutes in a worker thread (blocks the `--num-workers` pool, lost on restart); leasing a retry by pushing its due time forward (survives crashes but can send duplicate alerts, which AD-6 avoided). Basis: S1
- AD-29 (changes AD-12) Retry policy: the per-transport in-attempt tries stay as they are (HTTP kinds 3 tries, Signal 2, email 3, the webhook test opt-out) and run inside every attempt; on top, a platform-level delayed retry gives each integration delivery up to 3 retries, due 1, 5 and 25 minutes after the failure of the previous attempt, as an explicit tuple of timedeltas in `hc/api/models.py` with no setting and no change to any transport. Eligible: a `TransportError` that is not `permanent` (AD-9), returned for a saved status change. Not eligible: permanent errors; successes and no-ops; test notifications and account-deletion notices (unsaved dummy status changes, answered to a user at once); the group integration's own attempt (its members each retry on their own, so members that already succeeded are not sent again). Why: S1 fixes the count and the delays; placing the policy in `Channel.notify` gives every kind the same behaviour without per-kind code (AD-8) and keeps AD-12's per-transport handling of transient errors intact; a constant matches the existing constants (30 second timeout, 3 tries) and avoids a documented setting nobody asked for (AD-18). Alternatives: per-transport retries (one edit per kind and no shared delays); a formula such as 5**(n-1) (less explicit, harder to test); a settings entry for the delays; a non-retryable flag on `TransportError` to exempt quota refusals (changes AD-9). Basis: S1
- AD-30 (new) Retry state is three columns on `Notification`, added by one additive migration `0124` in `hc/api/migrations` (no backfill, no data migration): `flip` (nullable foreign key to `Flip`, CASCADE: the status change being delivered; null for test notifications, deletion notices and rows from before the migration), `attempt` (small integer, default 1: 1 for the first delivery, 2 to 4 for retries) and `retry_at` (nullable datetime: when the next retry is due, null when none is pending), with a conditional index on `retry_at` like the two indexes the alert process already polls (`api_flip_not_processed`, `api_check_aa_not_down`). `Channel.notify` gets an optional `attempt` argument, sets `flip` only when the passed status change is saved (most integration tests pass an unsaved one, so they leave `flip` empty and schedule nothing, and the few that save one succeed) and writes `retry_at` in the same UPDATE that records the error. Retention and deletion follow the row (AD-15): pruning, clearing events and deleting the check, integration or status change also drop pending retries. Late provider callbacks and bounces save only the `error` column (`save(update_fields=["error"])`), so they never overwrite `retry_at`. Environments: the `sendalerts` process and the web process both run `Channel.notify`; the database is SQLite, PostgreSQL, MySQL or MariaDB through the same migration (AD-3); all new names live in the `hc/api` app (`Notification.flip`, `Notification.attempt`, `Notification.retry_at`, a delays constant in `hc/api/models.py`, a retry step and worker function in `sendalerts.py`) and collide with nothing there. Why: the attempt row already exists before sending and outlives the attempt (AD-10), so the due time gives the poller one indexed query and ties the retry's lifetime to the log row it explains. Alternatives: a new table (see AD-28); `retry_at` on `Flip` (one status change fans out to many integrations, each with its own chain); rebuilding the status change from check and status at retry time (ambiguous when several changes queue up); keeping the attempt count only in the error text (not queryable); `SET_NULL` on the flip (leaves pending retries with no status change to deliver). Basis: S1
- AD-31 (new) Each retry is its own `Notification` row, so the existing Events log lists every attempt with its error and the display path stays as it is: `_get_events` and its "Downtime alert" filter, `event_summary.html` with its "Error:" line and the live poll's created-after cursor are reused unchanged; no new page, endpoint, API field, template or setting, and access follows AD-16 exactly as for the first attempt. Why: S1 asks to show attempts where past notifications are listed today; a row per attempt carries its own error, its own start time and its own provider callback address, and the live feed finds it because it was created later. Alternatives: update one row in place (hides later attempts from the live feed and keeps one 200-character error); one row per delivery with an attempt history column; a new attempts panel or Management API listing; an attempt-number label in `event_summary.html` (not asked for). Basis: S1

## Assumptions

- Backoff reading: each delay counts from the failure of the previous attempt, so retries start about 1, 6 and 31 minutes after the first failure; counting all three from the first failure would give gaps of 1, 4 and 20 minutes, which is not the usual meaning of exponential backoff.
- "Up to 3 times" means 3 retries after the first attempt, at most 4 attempts, each still making its in-attempt tries (one failing HTTP integration can make up to 12 requests per status change, each retry calling the integration's service again); worker time used by slow failing integrations grows up to 4 times, `--num-workers` stays 1 by default, flips are served before retries, and no per-project limit is added because S1 names none.
- Only a failure the attempt itself returns is retried; failures reported later by Twilio status callbacks or email bounces (R-4) and escaped non-`TransportError` exceptions (R-2) are not.
- A retry is built and sent at retry time even if the check's status changed, or the integration was disabled or unassigned, since the failure (a webhook `$JSON` then shows the check as it is now); preferred alternative, not requested: skip retries of a status change that a newer one superseded and retries to a disabled integration.
- Retried failures that have side effects repeat them: SMS, WhatsApp and call quota refusals each email the owner and team again (R-5, AD-13) and Signal CAPTCHA failures repeat their notices and admin mail, while "not enabled" failures only add rows; preferred alternative, not requested: a non-retryable flag on `TransportError` set at those raise sites (it would change AD-9).
- The Events log keeps listing only "down" notifications behind the unticked "Downtime alert" box (R-8), so attempts of "up" alerts are retried but not listed; the probable live-update defect in `static/js/log.js` (R-10) stays out of scope, so new attempts appear after a reload or a filter change.
- A group's own row keeps its first-attempt error ("N out of M notifications failed") even when a member's retry later succeeds; the members' rows show the outcome.
- A pending retry exists only as long as its row: a check that receives more pings than its retention limit (100 by default) within about 30 minutes prunes older notifications (AD-15), and clearing events or deleting the check, integration or status change deletes them; accepted because the row is both the log entry and the queue entry.
- A retry starts within a few seconds of its due time (the loop's 2 second idle sleep), later when the worker pool is busy; while `sendalerts` is not running, due retries wait in the database and run, however late, once it restarts, and no age limit is added.
- User-facing text changes are limited to the webhook set-up page's retry sentence and a CHANGELOG "Improvements" entry under v5.1-dev; no Markdown documentation page describes delivery retries, so the rendered fragments and `search.db` are not regenerated.
- The work stays in a local checkout: CONTRIBUTING.md's AI policy (no AI-assisted contributions, pull requests disabled) is not triggered because nothing is sent upstream, and offering the result upstream is the owner's decision (baseline note in `docs/shiploop/architecture.md` "Conventions").
- Re-verification at f6c46b59 was by reading code, tests and history only; nothing was run, so the test suite on the four CI databases, `mypy --strict`, ruff and `makemigrations --check` are the proving checks still owed at build time.
