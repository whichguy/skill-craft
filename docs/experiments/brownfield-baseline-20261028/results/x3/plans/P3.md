## Summary

The repository is Healthchecks (Django: `hc.api`, `hc.front`, `hc.integrations.<kind>`). Today a notification delivery is one `Channel.notify()` call made by the `sendalerts` worker; it writes one `Notification` row whose `error` is what the Events log shows under the "Downtime alert" filter, and a failure is final. The plan keeps that shape and adds time: a failed, retry-eligible attempt stamps its own row with the moment the next attempt is due (1, then 5, then 25 minutes after that attempt failed), `sendalerts` claims due rows with the same compare-and-set it uses for flips and calls `Channel.notify()` again, and so every attempt is its own `Notification` row that the existing Events log already lists with its error. Three increments in dependency order: W1 adds the state (three columns on `api_notification`, one migration, the delay constant, scheduling inside `Channel.notify()`), W2 runs due retries inside the existing `sendalerts` loop, W3 labels retry rows in the Events log, corrects the webhook form's retry-policy sentence and the changelog, and proves the whole request end to end. No new process, service, queue, package, setting or API surface.

## Decisions

AD-1 Environments and ownership: the change lives in the two Django processes and the one database they already share (`sendalerts` schedules and runs retries, the web process renders the Events log, `api_notification` holds the state); the integration services are reached only through the unchanged transports; no new process, service, package, directory, setting or environment variable. Why: `sendalerts` is the only process that sends notifications and the web process already serves the log; `docker/run.sh` already runs `migrate` and then `sendalerts`, and the README setup runs both, so self-hosters need no new step. Alternatives: a dedicated retry worker or management command (another process to supervise), a Celery/Redis queue (new services for every self-hoster), a family of `RETRY_*` settings. Basis: S1

AD-2 Retries are scheduled in the database and executed by `sendalerts`' own polling loop: `Command.process_one_retry()` runs after the flip loop each pass, takes the oldest row with `retry_at <= now()`, claims it with `UPDATE ... SET retry_at = NULL WHERE id = ? AND retry_at IS NOT NULL` (the compare-and-set `process_one_flip` uses on `processed`), takes a seat from the existing `BoundedSemaphore` and submits `retry_notification()` to the existing executor. Why: a due time held in the database survives restarts and is safe with several `sendalerts` processes, the idle 2-second loop is far finer than the shortest 1-minute delay, and draining flips first keeps first alerts ahead of retries. Alternatives: `threading.Timer` or sleeping in the pool (lost on restart, holds one of the `--num-workers` seats for up to 25 minutes), row locks with `skip_locked` (a no-op on SQLite), a lease column (more state than the at-most-once flips already accept). Basis: S1

AD-3 Retry state is three added columns on the existing `api_notification` table, in one migration `hc/api/migrations/0124_*`: `flip` ForeignKey(Flip, CASCADE, null=True; null for test notifications and pre-migration rows), `attempt` PositiveSmallIntegerField(default=1; 1 is the first delivery, 2-4 are retries), `retry_at` DateTimeField(null=True; set on a failed row while its retry is pending and NULLed when claimed), plus a conditional index `api_notification_retry_due` on `retry_at` where not null (the pattern of `api_flip_not_processed` and `api_check_aa_not_down`); every attempt is its own `Notification` row. Why: one row per attempt is exactly "a delivery attempt with its error", so `_get_events`' created-ordered paging and the live updates list it unchanged; `clear_events`, `Check.prune()` and the cascades on flip, check and channel delete cancel pending retries without new cleanup; Django migrations already own and change this schema, and retention is the existing prune. Alternatives: a separate retry-queue table (a new model plus its own cleanup, but it leaves `api_notification`'s indexes alone, which matters only on very large installs), attempts as a JSON list on one row (later attempts would not move `created`, so paging and live updates would miss them), deriving state from the `error` text (no flip link, no failure time, no index). Basis: S1

AD-4 The retry decision is made inside `Channel.notify()` (new keyword-only `attempt=1`), in the UPDATE that already records the error: `retry_at = now() + NOTIFY_RETRY_DELAYS[attempt - 1]` only when the transport raised a `TransportError` that is not `permanent`, the flip is saved, the call is not a test, `kind` is not `group`, and `attempt <= len(NOTIFY_RETRY_DELAYS)`. Why: it is the one place that sees the `permanent` flag together with the stored row; group members call `Channel.notify()` themselves, so each failing member retries on its own, while retrying the group's own row would re-send to members that already succeeded and double-retry the ones that failed; a permanent error disables the channel, so there is nothing left to retry. Alternatives: decide in `sendalerts.notify()` (sees only the error string and misses group members), a hook in each of the 29 transports, a `Transport.can_retry` method (new surface for one exception, Group). Basis: S1

AD-5 `NOTIFY_RETRY_DELAYS = (td(minutes=1), td(minutes=5), td(minutes=25))` in `hc/api/models.py` beside `DEFAULT_TIMEOUT`; delay n runs from the moment attempt n failed to the start of attempt n + 1, so a delivery has at most 4 attempts; `Notification.max_retries` exposes `len(NOTIFY_RETRY_DELAYS)` to templates. Why: S1 gives the values and the count; one constant feeds the scheduler and the log label so they cannot drift. Alternatives: all offsets measured from the first failure (retries at 1, 5 and 25 minutes, spacing 1/4/20, not exponential), a Django setting or environment variable (an unrequested surface to document and test). Basis: S1

AD-6 Leave `HttpTransport.request()`'s immediate 3-try loop, the Signal 2-try loop and the email thread's retries as they are; a deferred retry re-runs the whole `Channel.notify()` attempt. Why: not asked for; they absorb connection blips inside one attempt, the Slack, Google Chat and webhook tests assert their call counts, and the webhook form documents them. Alternatives: remove or reduce them so the deferred schedule is the only retry (changes every HTTP transport and delays recovery from a blip to a minute). Basis: none

AD-7 Attempts are shown through the existing Events log with no new view, endpoint, API field, script or table: `_get_events()` -> `log_rows.html` -> `log_row.html` -> `event_summary.html` already prints each `Notification` with its `Error:` line, so retry rows appear under the "Downtime alert" filter and in the existing live polling (`log.js` -> `hc-log-events`, no push channel) as they are written; `event_summary.html` adds "Retry n of 3" for `attempt > 1` and the `check_status="down"` filter stays as it is. Why: S1 says "where the check's past notifications are listed today", and `_get_events` is the only place that lists them (`notification_set` is otherwise touched only by `clear_events` and `Check.prune()`). Alternatives: nest attempts under one row (needs `_get_events` and `log.js` changes), a new attempts page or API field, also listing "up" notifications (changes today's listing). Basis: S1

AD-8 No new caller-facing surface, so no new authorization or input validation: the log keeps `login_required` and `_get_check_for_user`, and retries are triggered only by rows the server itself wrote. Every failed attempt is recorded where failures are recorded today (its `Notification.error`, `Channel.last_error` on the Integrations page, the sendalerts log line, the `hc.notifications.<kind>.fail` statsd counter); the failure after attempt 4 simply stays visible, and an exception inside a retry thread is logged by the existing `on_notify_done` callback. Why: it reaches the project owner (log, Integrations page) and the operator (sendalerts log) through records that already exist; an extra alert for exhausted retries was not requested. Alternatives: email the owner when retries run out, an admin view of pending retries. Basis: S1

AD-9 Home namespaces, no new module: `NOTIFY_RETRY_DELAYS`, `Notification.flip` / `attempt` / `retry_at` / `max_retries` and the `Channel.notify(attempt=)` parameter live in `hc.api.models` (public attributes, like `DEFAULT_TIMEOUT`); `Command.process_one_retry` and `retry_notification()` live in `hc.api.management.commands.sendalerts` beside `process_one_flip` and `notify` (that module imports from `hc.api.models`, never the reverse, so no import cycle); the label lives in `templates/front/event_summary.html`; the only new files are migration `0124_*` and test modules under `hc/api/tests` and `hc/front/tests`. Names checked free: no existing `NOTIFY_RETRY_*`, `retry_at`, `retry_notification` or `max_retries`; `attempt` appears only as a local in `hc.lib.emails` and inside `TokenBucket.authorize_totp_attempt`; the new `flip` FK adds only the reverse accessor `Flip.notification_set`. Why: it matches where the neighbouring responsibilities already live (constants and models in `hc.api.models`, the polling loop in `sendalerts`, row templates in `templates/front`). Alternatives: a new `hc/api/retries.py` (it would have to import models while models needs its constant), delays in `hc/settings.py`. Basis: none

## Assumptions

- A delivery "fails" when `Channel.notify()` records a `TransportError` message; failures reported later (Twilio status callbacks, email bounces, which edit `Notification.error` after the send) and unexpected exceptions are not retried.
- An "attempt" is one `Channel.notify()` run; the transports' own immediate tries (HTTP 3, Signal 2) belong to it and report only their last error, so "every delivery attempt" means the original delivery plus the 3 deferred retries.
- The delays 1, 5 and 25 minutes each run from the failure of the previous attempt (retries at about T + 1, T + 6 and T + 31 minutes); if the owner meant offsets from the first failure, only the constant changes.
- Up and down alerts are both retried, but the log keeps listing only down alerts (`check_status="down"`) and keeps the "Downtime alert" filter unticked by default, so attempts of "up" alerts are stored (and visible in the Django admin) but, as today, not in the Events log.
- A retry is skipped, with a sendalerts log line and no new row, when the check has a newer flip (a late DOWN after recovery would mislead; pause, resume and reset also create flips) or `Flip.select_channels()` no longer includes the channel (disabled, unassigned from the check, or no-op for the status); the request is silent on this and the rule is one query plus one membership test to drop.
- A retry re-runs the transport unchanged, so it can duplicate a delivery that reached the service but reported failure (webhook, shell command, GitHub issue, Trello card), and SMS / WhatsApp / call quota counters with their limit-notice emails and Signal's CAPTCHA and rate-limit alerts fire once per attempt; accepted as inherent in S1 and worth the owner's confirmation.
- Claiming is at-most-once, like flips: a `sendalerts` crash between claiming a retry and writing its row loses that one retry; retries that fall due while `sendalerts` is stopped run when it restarts.
- A pending retry ends with its row: "Clear events", deleting the check or the integration, and `Check.prune()` (only reachable inside the ~31-minute window for a check whose pings push the notification outside the retained ping window) cancel it; accepted.
- Pre-migration rows get `attempt=1`, no flip and no retry; no data migration is needed.
- The work stays in this local checkout and nothing is submitted upstream (CONTRIBUTING.md says the project does not accept AI-produced contributions); proving uses only tooling the repo already carries: the Django test runner (SQLite locally, the CI matrix for PostgreSQL, MySQL and MariaDB), `time_machine`, and `mypy --strict hc`.
