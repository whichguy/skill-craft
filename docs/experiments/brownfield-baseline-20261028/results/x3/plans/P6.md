## Summary

S1 is already delivered by the repository, so this plan reuses it and builds nothing. The Management API list call `GET <SITE_ROOT>/api/v3/checks/` (`hc/api/views.py` `get_checks`, behind `authorize_read`) returns one project's checks as JSON, each with `status` (`new`, `up`, `grace`, `down` or `paused`, derived at request time) and `last_ping` (ISO 8601 UTC, null until a success or fail ping). The token is the project's read-only API key (`hcr_...`, issued once on the Project Settings page by a read-write member) sent in the `X-Api-Key` header; every endpoint that creates, updates, pauses, resumes or deletes a check refuses it with HTTP 401, and the API answers cross-origin browser calls. The bundled `/tv/` dashboard already consumes exactly this call. The plan therefore adds no endpoint, token type, table, migration, setting, dependency, process or documentation page, and changes no inherited decision (nothing moves under Superseded and no baseline requirement gains a Basis). Its single work item, W1, adds the script-run proof that is missing for the read-only path, because the current read-only tests assert neither `status` nor `last_ping` and do not cover refusal on pause, resume or delete. The inherited decisions it relies on are AD-1, AD-2, AD-3, AD-16, AD-25 and AD-26, plus AD-28 to AD-30 which the baseline had not recorded; AD-31 is the one new decision (reuse, do not build). Nothing was run: every finding comes from reading code, tests and docs.

## Decisions

- AD-1 (inherited) The Management API lives in the `hc/api` app and is routed at `/api/v1/`, `/api/v2/` and `/api/v3/` from one shared route list; S1 is served there, and no app, package or URL prefix is added. Evidence: `hc/settings.py` `INSTALLED_APPS`; `hc/urls.py` `urlpatterns`; `hc/api/urls.py` `api_urls`. Why: one app per feature area keeps the API, its views and its tests together. Alternatives: a new app, or a new `/status/` prefix for dashboards. Basis: none
- AD-2 (inherited) Clients learn about changes by polling over HTTP; there is no push, stream or websocket, and the bundled `/tv/` dashboard polls the same JSON list every 5 seconds. External dashboards do the same at a cadence they choose, with status computed per request (AD-29). Evidence: `templates/front/dashboard.html` `updatePanel`; `static/js/adaptive-setinterval.js` `adaptiveSetInterval`. Why: S1 states no freshness figure, so a GET is the lightest hop, and self-hosting needs no extra service. Alternatives: webhooks or server-sent events to dashboards; a cached snapshot. Basis: none
- AD-3 (inherited) All state stays in the relational database reached through the ORM; S1 only reads existing `Check` rows (`status`, `last_ping`, `last_start`, `timeout`, `schedule`, `grace`), so no table, column, migration or storage policy is added. Evidence: `hc/settings.py` `DATABASES`; `hc/api/models.py` `Check`. Why: the same code and tests must run on SQLite, PostgreSQL, MySQL and MariaDB. Alternatives: a status table or cache kept for dashboards. Basis: none
- AD-16 (inherited) Callers are authenticated per project; the Management API uses project API keys stored as an 8-character prefix plus an HMAC-SHA256 digest (legacy plain 32-character keys still work), and a key selects a project, never a user. Evidence: `hc/accounts/models.py` `for_api_key`; `hc/accounts/models.py` `_make_api_key`; `hc/api/decorators.py` `authorize`. Why: scripts need a credential that is not a user session and reaches one project only (`templates/docs/api.md` "There are no account-wide API keys"). Alternatives: user tokens; account-wide keys. Basis: none
- AD-25 (inherited) Tests run on Django's runner, one `tests` package per app, deriving from `BaseTestCase` (alice owns the project, whose read-write key is 32 `X`); CI runs the whole suite on four databases. W1's tests live in `hc/api/tests`. Evidence: `hc/test.py` `BaseTestCase`; `.github/workflows/tests.yml` `matrix`. Why: the supported-database promise is proven only by running the suite on each. Alternatives: a separate contract-test harness for the API. Basis: none
- AD-26 (inherited) Code is typed for `mypy --strict` with the django-stubs plugin, every module starts with `from __future__ import annotations`, and Python is formatted with ruff; W1's tests follow it. Evidence: `.github/workflows/mypy.yml` `mypy --strict`; `mypy.ini` `django-stubs`. Why: the type check runs in CI on every push. Alternatives: untyped test code. Basis: none
- AD-28 (inherited) A project has up to two Management API keys, read-write (`hcw_`) and read-only (`hcr_`), and two view decorators turn them into capabilities: `authorize` accepts only the read-write key (from the `X-Api-Key` header or the JSON body of a POST) and guards every endpoint that creates, updates, deletes, pauses or resumes a check as well as list integrations, list pings and ping body; `authorize_read` accepts either key from the `X-Api-Key` header only and guards list checks, get check, list status changes and list badges; a missing or wrong key is HTTP 401 with a JSON `{"error": ...}` body; with a read-only key `Check.to_dict(readonly=True)` leaves out `uuid`, `ping_url`, `update_url`, `pause_url`, `resume_url` and `channels` and adds `unique_key`. Read-write members create and revoke keys on the Project Settings page, and a new key is shown once. Evidence: `hc/api/decorators.py` `authorize_read`; `hc/api/decorators.py` `authorize`; `hc/api/models.py` `to_dict`; `hc/accounts/views.py` `project`; consumers `templates/front/dashboard.html` and `hc/integrations/prometheus/views.py` `metrics`. Why: a script that only reports status can hold a key that can neither change a check nor learn how to ping it, and naming the decorator on each route makes the choice visible (stated: `templates/docs/api.md` "Omits sensitive information from the API responses"). Alternatives: scopes on one key class; session cookies for API clients; expiring signed tokens. Basis: none
- AD-29 (inherited) The status a caller sees is derived when it is read: `Check.get_status` combines the stored status, last ping, schedule or timeout, grace time and the clock into `new`, `up`, `grace`, `down` or `paused`, and the Management API, badges, Prometheus view and web UI report that value rather than the stored column. Evidence: `hc/api/models.py` `get_status`; `hc/api/models.py` `to_dict`; `hc/api/views.py` `badge`; `hc/integrations/prometheus/views.py` `metrics`. Why: a ping request updates the stored status at once, but the stored `down` is written later by the alert process (AD-4), so the column alone would show an overdue check as up (stated: `hc/api/models.py` `get_status` "Return current status for display"). Alternatives: serving the stored column; caching the derived status. Basis: none
- AD-30 (inherited) Management API views are CSRF-exempt and open to browsers on other origins: the `cors` decorator answers `OPTIONS` with 204, answers methods outside the view's list with 405, and adds `Access-Control-Allow-Origin: *` and `Access-Control-Allow-Headers: X-Api-Key` to every response. Evidence: `hc/api/decorators.py` `cors`; `hc/api/views.py` `checks`; `hc/api/tests/test_list_checks.py` `test_it_handles_options`. Why: the credential is a header that a browser never attaches by itself, so no cookie or session is exposed and a page on another site can act only if it already holds the key (inferred). Alternatives: an allowed-origins setting; same-origin only. Basis: none
- AD-31 (new) S1's API is the existing list call `GET /api/v3/checks/` used with the project's read-only key. The plan adds no endpoint, key or token type, table, column, migration, setting, dependency, process, response format or URL prefix, and changes only two test modules in `hc/api/tests`; the local checkout and CI are the only environments touched, and web workers, `sendalerts`, `sendreports`, `smtpd` and the database are unchanged. Safeguards stay where they are: the key is checked server-side on every request before any query (AD-28), the only input is the optional `tag` and `slug` filters, and no background or async work is added, so there are no failures to record. Why: the call already returns each check's `status` and `last_ping` as JSON, the read-only key is already refused by every state-changing route, and the bundled `/tv/` dashboard and the Prometheus scrape already consume it; a second surface would have to copy and then keep in step the key rules, serialization, status derivation and CORS handling. Alternatives: a dedicated status-only endpoint with its own serializer; a new scoped token model with its own table and migration; the JSON badge (counts per tag only, no per-check list or last ping time) or the Prometheus text endpoint (not JSON, no last ping time). Basis: S1

## Assumptions

- The "token that cannot change anything" is a project read-only API key (`hcr_...`): one key per project, created on the Project Settings page by a read-write member (read-only team members cannot see or create it) and shown once. The plan issues no key and touches no live instance; a dashboard for several projects holds one key per project, as `/tv/` does.
- "External dashboards" means any client that can send an `X-Api-Key` header, from a server or, through the CORS headers (AD-30), from a browser on another origin. A client that can carry its token only in a URL is out of scope: the JSON API has no URL-key or `Authorization: Bearer` form (only the Prometheus route has).
- "Current status" is the API's `status` and "last ping time" is `last_ping`, as the web UI's Last Ping column shows it: success and fail pings move it, start and log signals do not, and resuming a paused check clears it. Dashboards should call v3, because v1 reports "started" inside `status`.
- Preferred but not planned, because no S1 sentence asks for them: a status-only response, `Authorization: Bearer`, pagination, a defined order for the list (it has none; `/tv/` sorts by name) and keys scoped to a tag. Each would be a new decision that needs its own request sentence.
- Volume: the list is unpaginated, and no code in the repository rate-limits the API or returns HTTP 429 (`templates/docs/api.md` asks for under 100 requests a minute and mentions 429, presumably enforced by the hosted deployment); S1 gives no size or frequency, so none is planned.
- Baseline accuracy: spec R-11 says read-only keys work "for GET endpoints", but the code is narrower: only list checks, get check (UUID or unique key), list status changes and list badges accept one, while list integrations, list pings and ping body need the read-write key. The plan follows the code and `templates/docs/api.md`; `docs/shiploop/spec.md` is left alone because the plan changes no requirement, and it has no requirement for the list call itself.
- `templates/docs/api.md` describes the call, the read-only key and the omitted fields but not the CORS headers; the plan leaves documentation alone (S1 does not ask, and regenerating the `.html-fragment` files and `search.db` is a separate cost), and the existing tests pin the CORS behaviour.
- `CONTRIBUTING.md` "AI Policy" refuses AI-produced contributions and pull requests are disabled; this plan assumes the work stays in the owner's local clone or fork and prepares nothing for upstream (no issue, branch mention or pull request). Whether to offer anything upstream is the owner's decision; the plan keeps the AI-produced surface to two test methods.
- Nothing was run (no tests, tooling or instance); every statement about behaviour comes from reading code, tests and docs at 9f12cd8d (baseline f6c46b59 plus the knowledge commit), and W1's first done condition re-checks the central premise by script.
