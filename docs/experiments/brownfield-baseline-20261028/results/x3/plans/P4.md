## Summary

The repository is Healthchecks, a Django project. It already has everything a delayed retry needs except a due date: `Channel.notify` is the single place a delivery is attempted and recorded (one `Notification` row per attempt, with its `error`), the long-running `sendalerts` command already owns background work by polling dated columns and claiming rows with conditional UPDATEs, and the Events log already lists a check's `Notification` rows and prints their error. The plan reuses all three instead of adding a queue, a process or a page. A failed, retryable attempt stamps `retry_at` on its own `Notification` row (new columns `retry_at`, `attempt`, `flip` and a partial index, one migration); `sendalerts` gains a `process_one_retry` step that claims due rows, checks the alert is still wanted, and calls `Channel.notify` again, which records the retry as a new row; because every attempt is then a row, the Events log shows each one with its error and only needs a "Retry n" label. S1 has two outcomes: delayed retries (W1 schedules, W2 executes) and every attempt visible with its error (W1 and W2 produce the rows, W3 shows and labels them). Order: W1, then W2, then W3. No inherited decision is changed; where S1 could be read another way (how the delays are counted, whether the immediate in-call tries stay) the plan keeps the existing behaviour and records the alternative under Assumptions.

## Decisions

AD-1 (inherited) State lives in relational tables defined as Django models in `hc/api/models.py` and changed by numbered migrations; work due later is a dated column with a conditional index commented "Used in the sendalerts management command". Evidence: `hc/api/models.py` `Flip.processed` with index `api_flip_not_processed` and `Check.alert_after` with `api_check_aa_not_down`; `hc/api/migrations/0123_alter_channel_kind.py` (latest); `hc/settings.py` `DATABASES` (SQLite default, PostgreSQL, MySQL, MariaDB, all four in `.github/workflows/tests.yml`); `requirements.txt` has no queue or cache library. Why: pending retries must survive restarts and be visible to every sendalerts process. Alternatives: Redis/Celery/APScheduler, in-memory timers, sleeping worker threads (a 25 minute sleep would hold a pool slot). Basis: none

AD-2 (inherited) Background work is the `sendalerts` management command: a polling loop (2 s idle sleep) that claims one row with a conditional UPDATE and runs the job on a `ThreadPoolExecutor` guarded by a `BoundedSemaphore`; `docker/run.sh` starts it and the README requires it to run constantly. Evidence: `hc/api/management/commands/sendalerts.py` `Command.handle`, `Command.process_one_flip` (`Flip.objects.filter(id=flip.id, processed=None).update(processed=now())`), `notify`, `Command.on_notify_done`; the same claim style in `hc/api/management/commands/sendreports.py` `handle_one_report`. Why: retries need no new process, deployment step or shutdown handling. Alternatives: a second management command (changes `docker/run.sh`, README, service units), `threading.Timer`. Basis: none

AD-3 (inherited) One delivery attempt is one `Channel.notify` call: it inserts a `Notification` (`error="Sending"`), runs `transport.notify(flip, notification=n)`, stores the final `error`, and updates `Channel.last_notify`, `last_notify_duration`, `last_error` and `disabled`; the row's `code` is what third parties call back with. Evidence: `hc/api/models.py` `Channel.notify`, `Notification.status_url`; `hc/api/views.py` `notification_status`, `bounces`. Why: a retry is the same call, so callbacks keep mapping to the attempt they belong to. Alternatives: none needed. Basis: none

AD-4 (inherited) Transports report failure by raising `TransportError(message, permanent=False)`; `permanent=True` disables the channel. Evidence: `hc/api/transports.py` `TransportError`; `hc/api/models.py` `Channel.notify`. Why: the existing classification decides what can be retried (permanent never). Alternatives: none needed. Basis: none

AD-5 (inherited) Immediate in-call retries stay inside one attempt and only the last error is recorded: `HttpTransport.request` (3 tries, 1 for test notifications), `EmailThread` (3 tries, 1 s apart), `Signal.notify` (2 tries). Evidence: `hc/api/transports.py` `HttpTransport.request`; `hc/lib/emails.py` `EmailThread`; `hc/integrations/signal/transport.py` `Signal.notify`; `hc/integrations/webhook/transport.py` `Webhook.notify`. Why: S1 asks for delayed retries, not for removing these. Alternatives: lower or drop them (assumption 2). Basis: none

AD-6 (inherited) Test notifications call `Channel.notify(dummy_flip, is_test=True)` with an unsaved flip, store `owner=None` and never retry (Webhook passes `retry=False`). Evidence: `hc/front/views.py` `send_test_notification`; `hc/accounts/management/commands/senddeletionscheduled.py`; `hc/integrations/webhook/transport.py` `Webhook.notify`. Why: they are interactive, synchronous and have no check to revalidate. Alternatives: none needed. Basis: none

AD-7 (inherited) A group channel notifies each member by calling `member.notify(flip)`, which writes one `Notification` per member plus one for the group; groups hold only non-group channels of the project, and members need not be assigned to the check. Evidence: `hc/integrations/group/transport.py` `Group.notify`; `hc/integrations/group/forms.py` `GroupForm`; `hc/api/models.py` `Channel.group_channels`; `hc/integrations/group/tests/test_notify.py`. Why: members must retry on their own and the group row must not, or members that already succeeded would be notified again. Alternatives: none needed. Basis: none

AD-8 (inherited) A check's past notifications are listed in its Events log: `_get_events` returns `Notification` rows with `check_status="down"` when the "Downtime alert" filter (off by default) is ticked; `log_events` renders them through `log_rows.html`, `log_row.html` and `event_summary.html` (which prints `event.error`), `static/js/log.js` polls for newer rows with a created-timestamp cursor, and access is login plus team access via `_get_check_for_user`. Evidence: `hc/front/views.py` `_get_events`, `log`, `log_events`; `hc/front/forms.py` `LogFiltersForm`; `templates/front/log.html`; `templates/front/event_summary.html`. Why: this is the "listed today" place in S1, and one row per `Notification` means every attempt is listed without a new query, endpoint or filter. Alternatives: a new attempts page or an expandable sub-list (extra view, template and JS). Basis: none

AD-9 (inherited) Failures reach whoever must act through stored state, not push messages: `Notification.error`, `Channel.last_error` (the "Failed" label on the Integrations page), statsd counters `hc.notifications.<kind>.fail` and `.success`, sendalerts stdout lines, and `on_notify_done` logging unexpected job exceptions. Evidence: `templates/front/channels.html`; `hc/api/management/commands/sendalerts.py` `notify`, `Command.on_notify_done`. Why: retries record through the same path, so no new alerting is needed. Alternatives: email the owner when the last retry fails (not asked). Basis: none

AD-10 (new) Retry state lives on the failed attempt's `Notification` row: `retry_at` (DateTimeField, null), `attempt` (PositiveSmallIntegerField, default 0) and `flip` (ForeignKey to `Flip`, null, SET_NULL), with a conditional index `api_notification_retry_pending` on `retry_at` where it is not null, added by one migration (AddField x3, AddIndex) after `0123`; existing rows get NULL/0/NULL with no backfill, and rows are still removed only by `Check.prune`, `clear_events` and cascades from check or channel deletion, so a pending retry disappears with its row. Why: AD-1's dated-column pattern; the row is already the attempt record; `flip` is needed to rebuild the alert, since the row links to a check and a channel but not to the flip today; SET_NULL means pruning flips never deletes notification history. Alternatives: re-open the `Flip` (re-notifies channels that already succeeded), a separate pending-retry table (extra model and cleanup), in-memory timers (lost on restart). Basis: S1

AD-11 (new) Every retry is a new `Notification` row created by `Channel.notify(flip, is_test=False, attempt=0)` called with `attempt+1`; the old row keeps its own error and only loses its `retry_at` when claimed. Why: S1 asks to show every delivery attempt with its error, and a row per attempt keeps its own time, error and callback `code`. Alternatives: update one row and append errors to a text field (loses per-attempt time and callback mapping), a child attempts table. Basis: S1

AD-12 (new) Retries run inside `sendalerts`: a `Command.process_one_retry` step after `process_one_flip` in `Command.handle` (flips first, same seats and executor) claims a due row with a conditional UPDATE that sets `retry_at` to NULL, and a module function `retry(notification)` mirrors `notify(flip)` (connection handling, log lines, statsd counters). Why: AD-2. Alternatives: a separate command or process. Basis: S1

AD-13 (new) The schedule is the constant `NOTIFY_RETRY_DELAYS = (td(minutes=1), td(minutes=5), td(minutes=25))` in `hc/api/models.py`, indexed by the failed attempt's number and counted from the end of that failed attempt: at most 3 retries, none after the fourth failure; it is not a setting. Why: S1 fixes the numbers, and a setting would need `hc/settings.py`, `docker/.env.example` and docs for flexibility nobody asked for (`PUSHOVER_EMERGENCY_RETRY_DELAY` shows the pattern). Alternatives: an env var, offsets counted from the first failure (assumption 1). Basis: S1

AD-14 (new) A failed attempt schedules a retry only if all hold: the error is a `TransportError` that is not `permanent` and not `retryable=False` (new optional constructor argument, default True), the notification is not a test, and its flip is saved (`flip.pk`; existing tests pass unsaved flips). `retryable=False` is passed by `Group.notify` and by the refusals that already email their own notice: the SMS, WhatsApp and call monthly limits and `SignalRateLimitFailure`. Why: permanent failures already disable the channel (AD-4), group members retry individually (AD-7), tests do not retry (AD-6), and retrying a limit refusal would repeat its notice email. Alternatives: retry everything, a `kind == "group"` test inside `Channel.notify`. Basis: S1

AD-15 (new) Before a retry runs it is revalidated, and dropped (clear `retry_at`, write a log line, create no row) unless `flip` still exists, no later flip of the same check exists (index `api_flip_owner_created`), and the channel is not disabled, is not a no-op for the status, and is still reached by the check: `Flip.select_channels()` plus the members of any group among its results (one level, groups cannot nest). Why: never send a stale DOWN after recovery or a pause (pause and resume create flips) or to an integration the user unassigned; reusing `select_channels` keeps one selection rule. Alternatives: no revalidation, comparing `Check.status` only (misses down, up, down inside the window). Basis: S1

AD-16 (new) Display: no new endpoint, query, filter or JS; the Events log keeps AD-8's rules, live updates use the existing poll, and `event_summary.html` gains a "Retry n" label when `event.attempt` is above 0; `NotificationsAdmin.readonly_fields` gains `flip` so the admin form does not render a select of every flip. Why: S1 says to show attempts where past notifications are listed today. Alternatives: a separate attempts view. Basis: S1

AD-17 (new) Safeguards: no new caller-facing action, identity or anonymous input (retries are started by sendalerts and the log keeps AD-8's access check); volume is bounded to 3 retries per failed delivery (4 attempts); every failed attempt is its own row plus `Channel.last_error`, and dropped retries and job exceptions go to the sendalerts log (AD-9). Why: the failure record reaches whoever looks at the log or the Integrations page without new surfaces. Alternatives: email on exhaustion and jitter on the delays (neither asked). Basis: S1

AD-18 (new) Home namespaces: all code goes into existing modules (`hc/api/models.py`, `hc/api/transports.py`, `sendalerts.py`, the five transports named in AD-14, `hc/api/admin.py`, two templates, `CHANGELOG.md`) plus one migration file in `hc/api/migrations/`; no new package, module, setting, URL or static file. New names are `Notification.retry_at`, `Notification.attempt`, `Notification.flip`, `NOTIFY_RETRY_DELAYS`, `TransportError.retryable`, `retry`, `Command.process_one_retry` and a `Flip` helper for "is the check's latest flip"; none is defined anywhere in the repository today (grep-checked; `attempt` and `retry` appear only as unrelated local variables, keyword parameters and comments, for example in `hc/lib/emails.py` `EmailThread.run` and `HttpTransport.request`). Why: avoids collisions and speculative structure. Alternatives: a new `hc/retries` module (an extra layer for one function). Basis: none

## Assumptions

- Each delay runs from the end of the previous failed attempt, so the retries land about 1, 6 and 31 minutes after the first failure (plus attempt time and the loop's 2 s poll); the other reading (1, 5 and 25 minutes from the first failure) is a change to the constant in AD-13.
- S1 is read as adding delayed retries beside the immediate in-call tries of AD-5, not replacing them; with both, one delivery can cost 4 attempts x 3 HTTP tries (30 s timeout each), and lowering the immediate tries to 1 for real notifications is the change I would suggest, left for the owner.
- A "delivery attempt" is one `Channel.notify` call (AD-3); the immediate tries inside an attempt keep recording only their last error.
- Only failures raised by `Transport.notify` are retried; failures reported later through `notification_status` (Twilio) or `bounces` (SMTP, up to 48 hours) still only update that attempt's row and schedule nothing.
- Every integration kind retries, including Shell (a non-zero exit re-runs the command) and the paid kinds whose monthly counters (`Profile.authorize_sms`, `authorize_call`) count every attempt, so a retried failing SMS, WhatsApp or call uses one unit per attempt (no refund planned); local "Rate limit exceeded" refusals are retried on purpose (their token buckets refill within a minute), and "not enabled" or "Email not verified" refusals are retried too and only add rows.
- The listing keeps today's rules (AD-8): only `check_status="down"` attempts, only when "Downtime alert" is ticked (off by default); attempts of "up" notifications are stored but not listed, and a retry that has not run yet is not shown.
- A dropped retry (AD-15) leaves only a sendalerts log line; the last failed attempt row stays as the visible record.
- Claim-then-send is at-most-once, like `Flip.processed`: a crash right after a claim loses that retry; retries that fall due while sendalerts is down run after it restarts, through the same revalidation.
- Upgrade: existing notifications get NULL/0/NULL, so only failures after deployment retry; the migration adds a nullable foreign key and its index to `api_notification`, which can lock a very large table while it builds; MySQL and MariaDB skip conditional indexes (as for `api_flip_not_processed`), so there the poll is unindexed.
- A group member that is not assigned to the check is still retried when an assigned group contains it; the group's own row keeps its "N out of M notifications failed" text after a member's retry succeeds.
