## Summary

S1 is already delivered by this repository (Healthchecks, v5.1-dev, HEAD f6c46b59), so the plan builds nothing new. `GET /api/v3/checks/` (`hc/api/views.py` `get_checks`, behind `authorize_read`) lists a project's checks with `status` (computed at request time by `Check.get_status`) and `last_ping`. It accepts the project's read-only API key (`hcr_...`, minted in Project Settings > API Access). Every state-changing endpoint that takes an API key rejects that key with 401 (`authorize`), and the read-only response carries no check UUID or ping URL (`Check.to_dict(readonly=True)`). The route sends CORS headers for browser dashboards, and the bundled `/tv/` dashboard already consumes it. The plan therefore adds no route, view, token type, model, migration, dependency, setting, template, background job or namespace, touches no execution environment, and changes or supersedes no inherited decision (AD-1 to AD-10 hold the evidence). It has one work item, W1, which owns S1 by reuse on an unmodified tree and proves it with the repository's existing tests; minting the real key stays the project owner's action in the UI. The alternatives I would have preferred (slimmer payload, per-dashboard tokens, Bearer header, extra contract tests) are recorded as assumptions and not built, because no request sentence asks for them.

## Decisions

AD-1 (inherited) The Management API is plain function views in `hc/api/views.py`, routed by `hc/api/urls.py` `api_urls` and mounted at `api/v1/`, `api/v2/` and `api/v3/`; a project's check list is `GET checks/` (`views.checks` -> `views.get_checks`), documented in `templates/docs/api.md` (List Existing Checks). Evidence: `hc/api/urls.py` `api_urls`; `hc/api/views.py` `checks`, `get_checks`. Why: this is the listing S1 describes, and the names `status/` (the database probe `views.status`), `metrics/`, `badges/`, `channels/`, `bounces/` under `api/v*/` are already taken, so a new "status" route would collide. Alternatives: a new dashboard-only route or app, a REST framework. Basis: none

AD-2 (inherited) API callers authenticate with a per-project key in the `X-Api-Key` header: read-write `hcw_...` and read-only `hcr_...`, stored as an 8-character lookup prefix plus HMAC-SHA256 of the key under `SECRET_KEY` (legacy plain-text keys still accepted) and resolved by `ProjectManager.for_api_key(api_key, accept_rw, accept_ro)`; there are no account-wide keys. Evidence: `hc/accounts/models.py` `ProjectManager.for_api_key`, `Project._make_api_key`, `Project.compare_api_key`; `hc/api/decorators.py` `authorize_read`. Why: S1's "token" is the read-only key, so no second token scheme is needed. Alternatives: a new token table with scopes and expiry, OAuth, signed URLs. Basis: none

AD-3 (inherited) "Cannot change anything" is enforced by the endpoint decorator and by the payload: read endpoints use `@authorize_read` (either key), every other API-key endpoint uses `@authorize` (`for_api_key(accept_rw=True, accept_ro=False)`, so a read-only key gets 401), and for a read-only key `Check.to_dict(readonly=True)` drops `uuid`, `ping_url`, `update_url`, `pause_url`, `resume_url`, `channels` (the UUID is the capability to ping a check) and adds `unique_key`. Evidence: `hc/api/decorators.py` `authorize`, `authorize_read`; `hc/api/views.py` decorators on `create_check`, `update_check`, `delete_check`, `pause`, `resume`, `channels`, `pings`, `ping_body`; `hc/api/models.py` `Check.to_dict`; `CHANGELOG.md` ("Don't include ping URLs in API responses when the read-only key is used"). Why: S1's "cannot change anything" already holds by construction. Alternatives: a per-route scope table, deciding by HTTP method instead of key type. Basis: none

AD-4 (inherited) The read-only key's lifecycle is the "API Access" block of Project Settings: members with write access create or revoke it, a newly created (hashed) key is shown in full only once, and each project has one read-only key (creating another replaces it). Evidence: `hc/accounts/views.py` `project` (`create_key`, `revoke_key`); `templates/accounts/project.html` (API Access); `hc/accounts/models.py` `Project.set_api_key_readonly`. Why: S1 needs a token per project, and this is how it is minted and rotated; the run never mints one. Alternatives: per-dashboard tokens (new table, migration and UI). Basis: none

AD-5 (inherited) State is the relational database through the Django ORM with per-app migrations, and S1 only reads existing columns (`Check.status`, `kind`, `last_ping`, `last_start`, `grace`, `timeout`, `schedule`, `tz`; `Project.api_key_readonly`), so no field, table or migration is added; the response is a hand-built dict typed `CheckDict` sent with `JsonResponse`, `status` is computed at request time by `Check.get_status()`, and `last_ping` is `isostring(Check.last_ping)` in UTC (set by success and fail pings in `Check.ping`, null before the first ping or after a resume). Evidence: `hc/api/models.py` `Check`, `CheckDict`, `Check.get_status`, `Check.ping`, `isostring`; `hc/settings.py` `DATABASES`. Why: both fields S1 names are already in the payload. Alternatives: a stored status snapshot, a cache, a summary table. Basis: none

AD-6 (inherited) Cross-origin and CSRF: the list route is wrapped in `@csrf_exempt` and `@cors("GET", "POST")`, which answers `OPTIONS` with 204 and sends `Access-Control-Allow-Origin: *` and `Access-Control-Allow-Headers: X-Api-Key`; this is safe because the credential is a header key, not a cookie. Evidence: `hc/api/decorators.py` `cors`; `hc/api/views.py` `checks`. Why: browser-based external dashboards on other origins work as is. Alternatives: an allowed-origins setting. Basis: none

AD-7 (inherited) Errors reach API callers as JSON `{"error": ...}` with 401 for a missing or wrong key, and plain 403 or 404 for another project's or a missing check; there is no in-app rate limit on the Management API (the docs ask for at most 100 requests per minute, and `TokenBucket` throttles logins, invites, sudo and TOTP codes and outgoing notifications, never `hc/api/views.py`), and keys carry 21 random bytes, so guessing is not a practical abuse path. Evidence: `hc/api/decorators.py` `error`, `authorize_read`; `templates/docs/api.md` (Rate Limits); `hc/api/models.py` `TokenBucket`; `hc/accounts/models.py` `Project._make_api_key`. Why: S1 adds no new anonymous input. Alternatives: a per-key request throttle in the app. Basis: none

AD-8 (inherited) Background work runs as separate management-command processes (`sendalerts` writes the timeout-driven `down` status and sends alerts; `sendreports`, `smtpd`, `prune*`), and the API does not depend on them for freshness because `status` is derived at request time; the channel from server to dashboard is polling `GET`. Evidence: `hc/api/management/commands/sendalerts.py`; `hc/api/models.py` `Check.get_status`; `templates/front/dashboard.html` (`setInterval`, 5000 ms). Why: S1 states no push or latency requirement beyond "current status", and nothing async is added, so there is no new failure to record. Alternatives: webhook, SSE or websocket push, a periodic snapshot job. Basis: none

AD-9 (inherited) Configuration is read from environment variables in `hc/settings.py` with an optional `hc/local_settings.py`, and the API's absolute URLs come from `SITE_ROOT`; S1 adds no setting. Evidence: `hc/settings.py` (`SITE_ROOT`, `envbool`, `envint`, the `local_settings` import); `hc/local_settings.py.example`. Why: the endpoint is always on and nothing about S1 is deployment-specific. Alternatives: a feature flag such as `READONLY_API_ENABLED`. Basis: none

AD-10 (inherited) The repository already builds this kind of feature on the same pieces: the bundled read-only dashboard `/tv/` polls `GET /api/v3/checks/` with a read-only key (held in the URL fragment) and shows name, `status` and `last_ping`; the Prometheus exporter authenticates the same key with `accept_rw=False, accept_ro=True`; the docs list three community dashboards. Evidence: `templates/front/dashboard.html`; `hc/front/views.py` `dashboard` with `hc/front/urls.py` `hc-dashboard`; `hc/integrations/prometheus/views.py` `metrics`; `templates/docs/resources.md` (Dashboards). Why: these are working consumers and the reference for any external dashboard. Alternatives: the session-only UI JSON `hc/front/views.py` `status` (login required, check UUIDs, `last_ping` as rendered HTML), badge JSON (no per-check last ping), Prometheus text (no last ping time). Basis: none

AD-11 (new) Deliver S1 by reuse: no new route, view, token type, model, migration, dependency, setting, template, background job or namespace is added, and no execution environment is touched; external dashboards call `GET {SITE_ROOT}/api/v3/checks/` with `X-Api-Key: hcr_...` exactly as AD-1 to AD-6 describe. Why: every clause of S1 (read-only JSON, a project's checks, `status` and `last_ping`, a token that cannot change anything, cross-origin dashboards) is met by inherited decisions, and a second read-only path would duplicate them and drift. Alternatives: a slim new endpoint returning only name, status and last_ping (its natural name `status/` collides with the database probe), a dedicated dashboard-token model with scopes, a public unauthenticated status JSON (no token, so not S1). Basis: S1

## Assumptions

- The "token" in S1 is the project's read-only API key: one per project, shared by every dashboard using it, so rotating it affects all of them; per-dashboard revocable tokens would need a new table, migration and UI, which S1 does not ask for.
- The existing read-only payload is acceptable as is: besides `status` and `last_ping` it shows `name`, `slug`, `tags`, `desc`, schedule or timeout, grace, filter keywords, `badge_url` and `unique_key` to anyone holding the key; a slimmer dashboard-only payload (name, status, last_ping, unique_key) is what I would have preferred for third-party dashboards, and it is not planned because changing AD-3 needs a request sentence.
- Dashboards can send a custom `X-Api-Key` header: the Management API reads the key from that header only (the Prometheus endpoint alone accepts `Authorization: Bearer`), and adding Bearer would also need `Access-Control-Allow-Headers` changed, so it is not planned.
- "Current status" is the v3 value of `Check.get_status()` (new, up, grace, down, paused), and "last ping time" is `last_ping`, which success and fail pings update and start or log pings do not; no new status semantics are wanted. v1 and v2 stay mounted, and v3 is the documented current version.
- The project owner (a member with write access) mints the real read-only key in Project Settings; this plan and its run mint, store or paste no key.
- No in-app throttling is added: dashboards are expected to follow the documented limit of 100 requests per minute (the bundled `/tv/` polls once every 5 seconds per key).
- The proving tests are expected to pass on the current tree (they were not run while planning). Two thin spots remain: no test asserts `status` and `last_ping` in a read-only response specifically, and read-only rejection for delete, pause, resume and channels is pinned only through the shared `authorize` decorator (`AuthTestCase`); extra tests are not planned because no behaviour is added.
- If the requester needs more than S1 states (unauthenticated public status, an account-wide listing, push delivery), that is a new request and not part of W1.
- This is local analysis and nothing is sent to the project; `CONTRIBUTING.md` (project data) says the project accepts no AI-assisted contributions and has pull requests disabled, which matters only if the owner later wants to upstream a change, and this plan makes none.
