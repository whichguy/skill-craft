## Summary

`sendalerts` keeps detecting checks that go down and claiming unprocessed flips (the atomic `processed` update), but instead of handing a claimed flip to its in-process thread pool it publishes a `hc.api.tasks.notify_flip(flip_id)` Celery task to a Redis broker. Celery workers, a separate `celery -A hc.celery worker` process that can run on any number of machines, reload the flip and run today's per-flip channel loop unchanged, so `Channel.notify` and all 29 transports in `TRANSPORTS` are not touched. The plan adds the Celery app and settings, moves `notify` into `hc/api/tasks.py`, makes `sendalerts` survive a Redis outage without losing or duplicating alerts, makes SMS/call limit accounting safe for parallel workers (today's default of one delivery thread hides a read-modify-write race), adds `redis` and `worker` services to the reference Docker stack, and documents what multi-machine operators must provide (identical settings, a server database, a TCP Signal socket, upgrade order). There is no schema change, and tests run Celery eagerly so CI needs no Redis.

## Decisions

AD-1 Celery 5 with the Redis transport (`celery[redis]`), delivery in separate `celery -A hc.celery worker` processes. Why: S1 names it, and fan-out across machines, pool management and graceful shutdown come from Celery instead of repo code. Alternatives: several `sendalerts` processes (the DB claim already allows them, but delivery stays coupled to detection and S1 is not met), a DB-polling worker, RQ or Dramatiq. Basis: S1

AD-2 One task per flip, `hc.api.tasks.notify_flip(flip_id)`: the message holds only the integer id, the worker reloads the flip and runs today's sequential per-channel loop (moved verbatim as `notify`). Why: it preserves the unit of work, so channel order by `last_notify_duration`, group channels, nag-date updates, statsd timings and `Channel.notify` behave as before, and the DB stays the single source of truth. Alternatives: one task per channel (more fan-out but loses ordering and per-flip timing and needs per-channel failure handling), serialising the Flip into the message. Basis: S1

AD-3 Detection and the claim stay in `sendalerts`: after the atomic `processed` update wins, it publishes the task; if publishing raises, it restores `processed=NULL` and retries on a later loop; the 2-second DB poll stays the only polling hop and there is no Celery beat. Why: it keeps the multi-process-safe claim (no duplicate publish), so a Redis outage delays alerts instead of dropping them. Alternatives: claim in the worker (`sendalerts` would republish the same unclaimed flip every loop), publish before claiming (duplicates), poll from Celery beat. Basis: S1

AD-4 At-most-once delivery as today: default early ack (no `acks_late`), no automatic task retry, no result backend (`ignore_result`), JSON serializer only. Why: a crash mid-delivery does not resend today, duplicated phone calls and SMS cost money and webhooks need not be idempotent, and `HttpTransport` already retries inside the task. Alternatives: `acks_late` with retries (at-least-once), a result backend to track outcomes. Basis: S2

AD-5 Namespace: the Celery app in `hc/celery.py` (exports `app`), the task and the moved `notify` in `hc/api/tasks.py` (exports `notify`, `notify_flip`); `hc/api/tasks.py` is the only importer of `hc.celery`, `hc/__init__.py` stays empty, no new Django app or `INSTALLED_APPS` entry. Why: it matches where the repo keeps similar code (commands under `hc/api/management/commands/`, transports resolved lazily through `TRANSPORTS`, settings in `hc/settings.py`) and Celery's autodiscovery; web processes never import Celery, so a broken Celery or Redis cannot affect the web UI; the registered name `hc.api.tasks.notify_flip` is the unique producer/worker contract; absolute imports keep `from celery import Celery` inside `hc/celery.py` pointing at the library. Alternatives: import the app in `hc/__init__.py` (Celery's default recipe, loads Celery in every process), leave `notify` in the command module (workers would import a management command), put tasks under `hc/integrations`. Basis: S1

AD-6 Celery reads Django settings with the `CELERY_` namespace; the broker URL is the `CELERY_BROKER_URL` environment variable read through `envsecret` (so `CELERY_BROKER_URL_FILE` works) with no default, and `sendalerts` and the worker exit with a clear error when it is unset unless `CELERY_TASK_ALWAYS_EAGER` is on. Why: it follows the env-plus-`local_settings.py` convention of every other setting, the URL carries the Redis password, and a silent default would let an upgraded instance keep running while nobody delivers alerts. Alternatives: default `redis://localhost:6379/0`, a separate `celeryconfig.py`, falling back to in-process delivery. Basis: S1

AD-7 Broker and worker options set in `hc/settings.py`: `worker_prefetch_multiplier=1`, bounded Redis socket timeouts in `broker_transport_options` (option names confirmed against the pinned kombu), `broker_connection_retry_on_startup=True`; the pool type is left to the operator (prefork by default, `--pool=threads` also valid since today's code ran in threads). Why: a delivery can last minutes (30 s curl timeout times 3 tries, 5 s ping-body wait), so prefetching would park flips behind a slow one while other machines idle; a stalled Redis socket must raise (handled by AD-3) instead of freezing `sendalerts`'s detection loop; workers must tolerate starting before Redis. Alternatives: Celery defaults, fixing a pool type in code. Basis: S1

AD-8 No in-process delivery remains: `sendalerts` drops its thread pool, semaphore and done-callback, with no flag or fallback that delivers inside it; the "Test!" button, `senddeletionscheduled` and `sendreports` keep calling `Channel.notify` or sending email synchronously in their own processes. Why: S1 names only the delivery of flips by `sendalerts`, the test button returns its result to the user within the request, and two delivery paths would double the test surface. Alternatives: an `--inline` fallback, routing the test button and the other commands through Celery. Basis: S1

AD-9 `--num-workers` and `--pool` stay accepted by `sendalerts` and are ignored with a warning, as `--pool` is today. Why: existing systemd, supervisor and compose command lines keep starting instead of failing on an unknown argument, and concurrency moves to `celery worker --concurrency`. Alternatives: remove the flags. Basis: none

AD-10 Failure and log routing: unexpected exceptions in `notify_flip` and publish failures go to the `hc` logger (persisted by `hc.logs.Handler` as `hc.logs.Record` rows, summarised by `sendlogs`), publish failures once per outage plus a recovery line; the per-flip OK/Error delivery lines go to the worker's stdout through a logger outside the `hc` hierarchy. Why: today `on_notify_done` logs exceptions through `hc` and prints the delivery lines; Celery's own error logging would reach only the worker's stderr, and logging delivery lines through `hc` would write one DB row per notification and flood the `sendlogs` digest. Alternatives: Celery's default logging only, an external error tracker. Basis: S2

AD-11 Make `Profile.authorize_sms` and `Profile.authorize_call` atomic (conditional `UPDATE` with `F()`, month rollover as an idempotent reset, no full-row `save()`). Why: they are read-modify-write with a full-row `save()`, and today's default of one delivery thread (`--num-workers` defaults to 1, `run.sh` passes no flag) hides it; parallel workers would lose increments and exceed SMS/call limits, and a stale full-row save can overwrite concurrent profile changes. Alternatives: leave as is (as `TokenBucket.authorize` tolerates), row locks with `select_for_update` (no effect on SQLite, holds locks during delivery), route SMS and calls through a concurrency-1 queue. Basis: S2

AD-12 Tests and development: the `manage.py test` settings block enables `CELERY_TASK_ALWAYS_EAGER` and `CELERY_TASK_EAGER_PROPAGATES` with a `memory://` broker URL; CI gets no Redis service; developers without Redis may set `CELERY_TASK_ALWAYS_EAGER = True` in `hc/local_settings.py` to deliver inside `sendalerts`. Why: it keeps the four-database, four-Python CI matrix hermetic and leaves the per-integration tests, which call `Channel.notify` directly, untouched; eager is a Celery setting, not a second code path in the repo. Alternatives: Redis in CI, a real worker thread in tests (`celery.contrib.testing`), patching `delay` in every test. Basis: none

AD-13 Reference Docker stack: add `redis` (append-only persistence on a named volume, no host port) and `worker` (same image and `env_file`, `celery -A hc.celery worker`, own healthcheck replacing the image's HTTP probe, `stop_grace_period` above the slowest delivery); `run.sh` still starts `sendalerts`, `sendreports`, `smtpd` and gunicorn and gains no embedded worker. Why: a separate service scales with `--scale worker=N` or the same image on other hosts, the same image plus `env_file` gives settings parity, and persistence narrows the window in which queued alerts can be lost. Alternatives: an embedded worker in `run.sh` (cannot scale separately, and a Celery crash would restart the web container through `wait -n`), a second Dockerfile. Basis: S1

AD-14 Multi-machine contract, documented and not coded: every worker runs the same release and the same settings and secrets as the `sendalerts` host (environment or `hc/local_settings.py`), uses a server database (not SQLite) and reaches Redis; Signal needs the TCP form of `SIGNAL_CLI_SOCKET` (a UNIX socket works only on hosts that have it); Shell Commands run on whichever worker takes the flip; no integration gets its own queue. Why: with one task per flip every worker must be able to deliver every channel kind. Alternatives: per-integration queues (needs per-channel tasks, AD-2), a pinned local worker for shell and Signal. Basis: S2

AD-15 No schema change: `Flip.processed` keeps meaning "claimed by `sendalerts` and queued", Redis holds only transient JSON messages (task name and flip id) with no result backend, so `num_unprocessed_flips` in the metrics endpoint no longer counts queued-but-undelivered flips (backlog is the Redis queue length and `hc.sendalerts.dwellTime`). Why: the request needs no new persisted state, and a delivered marker with a requeue sweeper would be new scope. Alternatives: `Flip.delivered` or `queued` columns plus a recovery sweep so Redis data loss cannot drop alerts. Basis: none

## Assumptions

- The current Celery release (with kombu and billiard) installs and runs on every Python in the CI matrix (3.12 to 3.15, including the prerelease job) and on Django 6.1; this is checked when pinning, and the owner is asked if a job cannot pass.
- Celery ships no type information, so `mypy --strict hc` needs stubs (`celery-types`) or a narrow ignore; the choice is made when pinning, provided the CI job stays green.
- The change stays in a private fork or deployment: CONTRIBUTING.md declines AI-assisted contributions and pull requests, so no upstream submission step is planned.
- Multi-machine deployments use PostgreSQL or MySQL/MariaDB, and `max_connections` must cover the total worker process count because each worker process holds a connection (the trade-off the maintainers accepted when they dropped the DB pool).
- Per-check ordering is not guaranteed across concurrent workers, as with `--num-workers` above 1 today; strict order means one worker process with concurrency 1.
- After a worker outage queued alerts are delivered late and never expire; a Redis data loss or hard worker kill can lose in-flight alerts like a `sendalerts` crash does today, and unacked prefetched messages return after Redis's visibility timeout (default 1 hour).
- A publish error raised after Redis already stored the message can cause one duplicate delivery; this is accepted.
- During an upgrade workers run the new release before or together with `sendalerts`, because a worker without `notify_flip` discards the message as unregistered.
- CI never exercises a real broker; the Redis path is proven by the smoke runs in W3 and W4, recorded in the change description rather than added to CI.
- Behaviour inside `notify` that the request does not mention stays as is: an unexpected exception aborts the remaining channels of that flip, and `Channel.notify` and every transport are unchanged.
- The statsd names `hc.sendalerts.*` and `hc.notifications.*` stay; `dwellTime` now includes queue wait and so doubles as the worker-lag signal.
