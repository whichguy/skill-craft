## Summary

The request (S1, S2) moves the per-status-change delivery that `sendalerts` runs in its thread pool into Celery workers on a Redis broker, with every integration kind still delivering. The plan keeps everything else where it is: web processes only write `Flip` rows, `sendalerts` still marks overdue checks down and claims each status change with the conditional UPDATE (AD-5), and the delivery body stays the existing `notify()` -> `Channel.notify` path (AD-11), now run by a `deliver_flip(flip_id)` task, so all 29 transport kinds are reached through unchanged transport classes (S2). Celery is configured to keep the inherited at-most-once semantics (AD-6): early acknowledgement, no automatic retries, an id-only JSON payload, and an un-claim when the publish fails, so a Redis outage delays alerts instead of losing them. There is no schema change; Redis holds only transient messages. Three items in dependency order: W1 adds the Celery app and the task while `sendalerts` still delivers in-process; W2 makes workers deployable (Docker `run.sh`, compose Redis, the broker setting and its documentation) before anything publishes; W3 switches `sendalerts` from the thread pool to enqueueing, rewrites the docs that describe the new flow (including several worker machines) and ships the upgrade note. AD-4 and AD-7 change (Basis S1) and move under Superseded in `docs/shiploop/architecture.md`, where AD-28 to AD-38 are added; R-2, R-14, R-15 and R-17 in `docs/shiploop/spec.md` gain `Basis: S1`. Hazards that scale-out exposes but the request does not ask to fix (SMS and call quota counters, per-check ordering, Redis data loss) are recorded as assumptions.

## Decisions

- AD-1 (inherited) Delivery code and models live in `hc.api`; each integration kind is its own app; new code goes into the app that owns the models it uses. Why: keeps areas self-contained, so the plan adds `hc/api/tasks.py` and one `hc/celery.py` and touches no integration app. Evidence: `hc/settings.py` `INSTALLED_APPS`; `hc/api/transports.py` `Transport`. Alternatives: a new `tasks` app or package (rejected: it would hold one module). Basis: none
- AD-3 (inherited) Durable state is in the one relational database through the ORM, with numbered migrations; this plan adds no table, column or migration, and Redis holds only transient task messages (AD-33). Why: the same code and tests must run on SQLite, PostgreSQL, MySQL and MariaDB. Evidence: `hc/settings.py` `DATABASES`; `.github/workflows/tests.yml` `matrix`. Alternatives: a `queued` column or table on `Flip` (rejected: no request sentence needs it). Basis: none
- AD-5 (inherited) A status change is claimed on the `sendalerts` main loop with a conditional UPDATE that must change one row, before any work is handed on. Why: several `sendalerts` processes may run, and claiming on the main loop stops the same flip being found twice (commit e581a8fa). Evidence: `hc/api/management/commands/sendalerts.py` `process_one_flip` (`num_updated`). Alternatives: claim inside the worker task (rejected: the unclaimed flip is found and enqueued again on every poll until some worker runs, the problem e581a8fa removed). Basis: none
- AD-6 (inherited) Delivery is at most once per status change and integration: the claim precedes contact, a failed attempt is recorded and never re-queued, a crash abandons the rest. The plan configures Celery to keep it (AD-32). Why: a duplicate alert is judged worse than the documented loss after a crash. Evidence: `hc/api/management/commands/sendalerts.py` `process_one_flip`; `hc/api/transports.py` `HttpTransport.request`. Alternatives: at-least-once through late acknowledgement or Celery retries (rejected: duplicates alerts and changes R-3). Basis: none

Delivery concurrency belongs to the worker (`--concurrency`) and to the number of workers. Why: S1 moves delivery out of the process; rejecting the old argument would break existing launch scripts on upgrade. Alternatives: remove `--num-workers` (rejected: breaks scripts); keep the thread pool as a no-broker fallback (rejected: contradicts S1, Assumptions). Basis: S1
- AD-30 (new) Layout and names: the Celery app is `hc.celery:app`, configured from Django settings with the `CELERY_` namespace; the task and the moved delivery function live in `hc/api/tasks.py`, which imports `hc.api.models` (`Flip`), `hc.lib.statsd` and `hc.celery`, is imported by `sendalerts` (which calls `deliver_flip`) and found by the worker's autodiscovery, and is never imported by `hc.api.models`; workers start with `celery -A hc.celery worker`; the web process and every other command never import Celery. Names do not collide: the module name `hc.celery` is safe because imports are absolute and nothing runs with `hc/` on `sys.path`, the task name is `hc.api.tasks.deliver_flip`, the queue is `healthchecks` (AD-31), and no `CELERY_*` setting exists yet. Why: AD-1 and a web process that works without a broker. Alternatives: the documented recipe that imports the app in `hc/__init__.py` and uses `shared_task` (rejected: every process, including web workers and tests, would import Celery); leaving `notify` in the command module (rejected: workers would import a management command, and `sendalerts` importing the task would be circular). Basis: S1
- AD-31 (new) Task contract: one task, `deliver_flip(flip_id)`; the payload is the status-change id only, JSON is the only accepted serializer, results are ignored, and the queue is named `healthchecks` so a shared Redis does not mix tasks with another Celery application; the worker re-reads the flip, check, integrations and settings, and a missing flip is a no-op. No inbound endpoint is added; the broker is inside the operator's trust boundary, and a hostile message can at worst re-trigger delivery for an existing status change, never supply content or code. Why: S1 introduces the broker as a new input channel and the payload must not carry stale data, secrets or code. Alternatives: pass the flip's fields in the message (rejected: stale data, personal data in Redis); pickle (rejected: code execution); a result backend (rejected: nothing reads results). Basis: S1
- AD-32 (new) Delivery semantics stay at most once (AD-6): early acknowledgement (late acks off), no automatic retries, one prefetched task per worker slot so a slow delivery does not hold tasks other workers could take. The claim stays before the enqueue; if the publish fails with the broker-connection error (kombu `OperationalError`), `sendalerts` restores `processed=None` for that flip, logs the error on the `hc` logger and lets the loop's 2 second sleep pace the retry, so a broker outage delays alerts instead of losing them; broker connect and socket timeouts are bounded to seconds so an unreachable Redis cannot stall overdue-check detection. A publish whose outcome is ambiguous may duplicate one alert, which is accepted. Why: S1 adds a failure source (the broker) that AD-6's crash-only model does not cover, and undoing the claim is the smallest repair with the existing mechanism. Alternatives: leave the flip claimed and lose the alert (rejected: a Redis outage would drop every alert raised during it); claim in the worker (rejected, AD-5); a database outbox with re-enqueue of stale claims (the stronger design, needs new state, Assumptions). Basis: S1
- AD-33 (new) Redis is only the broker: no result backend, cache or session store; its keys are the ones kombu manages (the `healthchecks` list and bookkeeping keys), the application defines none; no migration or schema; messages are transient and may be lost with the Redis data, as AD-6 already allows for crashes. The reference compose runs Redis with append-only persistence on a named volume and no published port; operators give the broker its own Redis database number and add a password or TLS (`rediss://`) as needed. Why: S1 requires a Redis broker; anything more would add state no sentence asks for. Alternatives: RabbitMQ or the Django database as broker (rejected: S1 names Redis). Basis: S1
- AD-34 (new) Configuration: `CELERY_BROKER_URL` is an environment variable read through `envsecret` (so `CELERY_BROKER_URL_FILE` works) with the default `redis://localhost:6379/0`; the fixed options of AD-31 and AD-32 are set in `hc/settings.py` under the `CELERY_` namespace and can be overridden in `hc/local_settings.py`; both variables are documented in the settings reference; the `manage.py test` override block turns on eager execution with propagation, so tests and CI need no Redis; no system check or startup failure is added because the web process and the tests must start without a broker and the existing check tests assert exact id lists. Why: AD-18 and AD-25. Alternatives: a `REDIS_URL` name translated in code (rejected: extra mapping); failing when unset (rejected: breaks `runserver` and tests). Basis: S1
- AD-35 (new) Observability in the worker keeps AD-19: the per-status-change lines ("<code> goes <status>" and one line per integration) go to the worker's process log at INFO through a logger outside the `hc` hierarchy, so the database handler does not store a row per delivery; unexpected exceptions are logged on the `hc` logger (rows carry the worker's host name) and re-raised so Celery records the failure too; the statsd names are unchanged, with the delivery ones (`hc.notifications.*`, `hc.sendalerts.dwellTime`, `hc.sendalerts.sendTime`) emitted by workers, `hc.sendalerts.processFlip` staying with the claim, and the dwell time now including queue wait; the metrics endpoint is unchanged (`num_unprocessed_flips` counts status changes not yet claimed). Why: S1 moves the code that emits them. Alternatives: store the delivery lines as `hc.logs.Record` rows (rejected: a row per alert); add a queue-depth field to the metrics endpoint (rejected: a Redis read in the web process that no sentence asks for). Basis: S1
- AD-36 (new) Worker environment: workers run the same release, settings and environment variables (and `hc/local_settings.py`) as the web and `sendalerts` processes (`SECRET_KEY`, `SITE_ROOT`, database, SMTP, S3, integration credentials), reach the same database and Redis, and have the outbound network access `sendalerts` had, so every integration kind runs unchanged in whichever worker takes the alert. Machine-local integrations run on the worker's machine: Shell commands with the worker's permissions, and Signal through `SIGNAL_CLI_SOCKET` (a UNIX socket must exist on every worker machine, a TCP `host:port` works from any); there are no per-kind queues or routing. Workers on several machines need PostgreSQL, MySQL or MariaDB, since SQLite is one machine. Why: S1 puts workers on several machines and S2 keeps every kind working. Alternatives: per-kind queues with routed workers (rejected: needs one task per integration). Basis: S1, S2
- AD-37 (new) Reference deployment: `docker/run.sh` supervises one worker (Celery's default prefork pool, `--concurrency=1` to match the former `--num-workers` default, `--loglevel=INFO` so the delivery lines stay visible) beside `sendalerts` and `sendreports`, and the container still exits when any child exits; more capacity is more worker processes or containers started from the same image with `celery -A hc.celery worker`; compose gains a Redis service and a commented-out `worker` service; a local checkout runs `runserver`, `sendalerts` and a worker in separate shells beside a Redis. Why: single-container installs keep working with one extra service, the default concurrency stays as it was, and a dead worker fails loudly as AD-7's container-exit rule did. Alternatives: a worker-only compose service enabled by default (rejected: a single `docker run` install would stop delivering); Celery's thread pool (rejected: less used than prefork); Celery's default concurrency of one slot per CPU (rejected: a silent change of default). Basis: S1
- AD-38 (new) Typing: `celery.*` and `kombu.*` are listed in `mypy.ini` with `ignore_missing_imports` and the task decorator carries a targeted `type: ignore`, as the repository already does for `statsd`; no stub package is added unless the pinned release ships usable types. Why: AD-26 without a new development dependency. Alternatives: `celery-types` in `requirements-dev.txt` (rejected: a third-party stub package to track). Basis: none

## Assumptions

- Redis becomes a hard requirement for every install that sends alerts: S1 says to move delivery out of the process, so no in-process fallback is kept, and `sendalerts` cannot deliver while the broker is unset or unreachable (the web process and the tests still start without one).
- The alternative I would have preferred, not planned: the repository already scales delivery by running several `sendalerts` processes on several machines against one network database (AD-5, AD-13), and a no-broker mode could keep the thread pool for small installs; S1 asks for Celery, so neither is built.
- `CONTRIBUTING.md` says AI-assisted contributions are not accepted and a larger change needs an issue first; this plan and its implementation are local, nothing is sent to the project, and carrying the change as a private fork is the owner's decision.
- A Celery release that keeps the 5.x setting names and supports Django 6.1 and Python 3.12 to 3.15 can be pinned; W1 checks it against the CI matrix, and if the newest Python row is unsupported the owner decides between dropping that row and waiting.
- Celery's option names, the kombu publish error type and the Redis transport timeout options are as AD-31 and AD-32 describe for the pinned release; W1 and W2 confirm them in tests and in the live run.
- Redis may lose queued messages (restart without persistence, eviction, flush); those alerts are lost, as AD-6 already allows for crashes. The stronger design I would prefer, keeping the database the source of truth by claiming in the worker and re-enqueueing stale unclaimed status changes, needs new state and no sentence asks for it.
- The SMS and call quota counters (`Profile.authorize_sms`, `authorize_call`) are a read-modify-write with a full-row `save()`, so simultaneous deliveries for one owner on different workers can lose counts, exceed a monthly limit and overwrite other Profile fields; one slot per container hides it today. The fix, a conditional UPDATE in the AD-5 style, is a small independent item the owner can add before advertising multi-worker scale-out; `TokenBucket` limits are already documented in code as inexact.
- Two status changes of one check handled by different workers can be delivered out of order, and concurrent deliveries to one integration overwrite each other's `last_*` and `disabled` summary (last writer wins); `--num-workers` above 1 allowed both before, and neither is addressed.
- Several worker machines need PostgreSQL, MySQL or MariaDB; a SQLite install can only add workers on the machine that holds the database file.
- Every worker machine runs the same release and the same environment as `sendalerts`; upgrades restart workers and `sendalerts` together, because the task carries only an id and the worker's code defines the behaviour.
- The metrics endpoint is unchanged, so `num_unprocessed_flips` counts only status changes `sendalerts` has not claimed; queue depth and worker liveness are watched with Redis and Celery tools (documented in W3), and a long broker outage writes one error row per 2 second retry while a status change waits.
- Email alerts are sent synchronously (`hc/lib/emails.py` `alert` passes `block=True`), so SMTP failures still reach the notification record; the fire-and-forget threads used for limit notices outlive the task and are lost only on a hard worker stop.
- Celery's Django integration closes stale database connections around tasks and runs the Django system checks at worker start; `notify` keeps its own `close_old_connections()` call, and the W2 live run confirms the worker starts cleanly.
- W2 and W3 ship in the same release: W2 alone is harmless (an idle worker), W3 without W2 would leave the reference image unable to deliver.
- The "Interfaces and boundaries" text of `docs/shiploop/architecture.md` ("no message broker, cache or task queue") and the overview of `docs/shiploop/spec.md` are refreshed by the baseline refresh after implementation; this stage records decisions and `Basis` marks only.
