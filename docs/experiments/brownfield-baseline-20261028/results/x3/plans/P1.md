## Summary

Healthchecks already splits alerting into detection and delivery through its database: web code and `sendalerts` write `Flip` rows, and `sendalerts` atomically claims each unprocessed flip (`Flip.processed`) and runs `notify(flip)` on an in-process thread pool sized by `--num-workers`. The plan keeps that outbox-and-claim design and replaces only the last hop (S1): `sendalerts` still detects checks going down and claims flips, but publishes a Celery task `notify_flip(flip_id)` to a Redis broker instead of submitting to the pool, and `celery worker` processes on any number of machines run the unchanged `notify` body against the shared database. Models, schema, `Channel.notify`, every transport and the interactive "Test!" path are not touched, so all 29 integrations keep one code path (S2); what changes for them is where that code runs, handled as an explicit worker-environment requirement (same image, same environment including `SECRET_KEY`, same local resources) rather than as code. Three items in dependency order: W1 adds the pinned dependency, the `hc.celery` app and the `CELERY_*` settings and clears the Python, Django and mypy compatibility gate; W2 moves `notify` into `hc/api/tasks.py`, adds the task and switches the `sendalerts` dispatcher (un-claim on broker failure, `--num-workers` retired to a warning, tests); W3 adds the Redis and worker services, operator docs and the upgrade note, and proves delivery across two workers. The consequences to know: Redis and at least one worker become mandatory for alerts to leave the system (no in-process fallback is built), delivery stays at-most-once, and `num_unprocessed_flips` stops reflecting delivery backlog; each is recorded below as a decision or an assumption.

## Decisions

- AD-1 (inherited) The application database is both system of record and work queue for alerts: `Flip` rows with `processed` NULL are inserted by web code (`Check.create_flip`) and by `sendalerts` (`handle_going_down`), and `sendalerts` finds them by polling every 2 s through the partial index `api_flip_not_processed`; the web tier touches no background infrastructure. Evidence: `hc/api/models.py::Flip`, `hc/api/models.py::Check.create_flip`, `hc/api/management/commands/sendalerts.py::Command.handle`. Why: kept, it keeps pings independent of any broker and Redis out of the web tier. Alternatives: publish the task from the web request when the flip is created (rejected: pings would depend on Redis). Basis: none
- AD-2 (inherited) Claim before dispatch: `process_one_flip` sets `Flip.processed` with `UPDATE ... WHERE id=? AND processed IS NULL` and only the process that updated one row continues, so several `sendalerts` processes on several machines are already safe and a flip is delivered at most once. Evidence: `sendalerts.py::Command.process_one_flip` (claim moved to the main thread in commit e581a8fa), same pattern in `Command.handle_going_down`. Why: reused as the only dedupe, Celery adds none of its own. Alternatives: none. Basis: none
- AD-3 (inherited) The unit of delivery is `notify(flip)`: update nag dates, `Flip.select_channels()` (fastest channels first), `Channel.notify` per channel (writes `Notification`, updates `Channel.last_*`), statsd counters and timings, a result text; transports are synchronous classes in `hc/integrations/<kind>/transport.py` found through `TRANSPORTS` and `Channel.transport` and know nothing about scheduling. Evidence: `sendalerts.py::notify`, `hc/api/models.py::Channel.notify`, `hc/api/models.py::TRANSPORTS`, `hc/api/transports.py::Transport`. Why: leaving it and the 29 transports untouched is how "keep every integration working" is met. Alternatives: one task per (flip, channel) (rejected: rewrites channel ordering, timing and result text, and is not needed to spread flips across machines). Basis: S2
- AD-4 (inherited) Delivery runs on a `ThreadPoolExecutor` inside the `sendalerts` process, sized by `--num-workers` (default 1) with a `BoundedSemaphore` for back-pressure, and failures are logged from a done-callback. Evidence: `sendalerts.py::Command.__init__`, `Command.handle`, `Command.on_notify_done`. Why: it was the only delivery path. Alternatives: n/a. Basis: S1 asks to replace it; superseded by AD-12 and AD-16
- AD-5 (inherited) Configuration comes from environment variables read in `hc/settings.py` (`envbool`, `envint`, `envsecret` with `_FILE` variants for secrets), optionally overridden in `hc/local_settings.py`; every variable is listed in `docker/.env.example` and documented in `templates/docs/self_hosted_configuration.md`; test-only overrides sit in the `sys.argv[1:2] == ["test"]` block. Evidence: `hc/settings.py::envsecret`, the final test block of `hc/settings.py`, `docker/.env.example`. Why: new settings follow it. Alternatives: none. Basis: none
- AD-6 (inherited) Long-running management commands run beside gunicorn; `docker/run.sh` starts `sendalerts`, `sendreports --loop`, optional `smtpd` and gunicorn as children and the container exits when any child exits (since v5.0); the image HEALTHCHECK probes gunicorn `/health`. Evidence: `docker/run.sh`, `docker/Dockerfile` (HEALTHCHECK), `docker/fetchstatus.py`, `hc/api/middleware.py::HealthMiddleware`, CHANGELOG v5.0. Why: kept, `sendalerts` stays one of these commands. Alternatives: none. Basis: none
- AD-7 (inherited) Failures are recorded by logging on the `hc` logger, whose handler writes `hc.logs` `Record` rows (with hostname) that `sendlogs` emails to admins; per-channel errors go to `Notification.error` and `Channel.last_error`; statsd counts `hc.notifications.<kind>.fail`; the main loop never crash-loops on one bad row. Evidence: `.github/workflows/tests.yml`, `.github/workflows/mypy.yml`, `mypy.ini`, the test block of `hc/settings.py`. Why: the plan must not add a service to CI. Alternatives: none. Basis: none

Why: S1 asks for it; keeping the database outbox keeps ping handling broker-free, and the hop to workers is one Redis push with a blocking pop (no new polling). Alternatives: the task does the claim (rejected: without a schema change the dispatcher cannot tell queued from unqueued flips and would re-publish on every 2 s poll); Celery beat replacing the polling loop (rejected: S1 moves delivery only); more `sendalerts` processes (already possible, S1 asks for Celery); Django's `django.tasks` API (rejected: S1 names Celery). Basis: S1
- AD-13 (new) Redis broker through `celery[redis]` (exact pin like the other requirements), configured by one new env var `CELERY_BROKER_URL` read with `envsecret` (the URL may embed a password; `_FILE` works; `rediss://` for TLS) plus fixed constants in `hc/settings.py`: `CELERY_TASK_DEFAULT_QUEUE = "healthchecks"` (a shared Redis does not mix queues with other Celery apps), `CELERY_WORKER_PREFETCH_MULTIPLIER = 1` (a long delivery must not hold queued alerts while other machines idle), `CELERY_BROKER_CONNECTION_RETRY_ON_STARTUP = True`, `CELERY_TASK_ALWAYS_EAGER = False`; Celery's default JSON serializers and no result backend. Data: no table, column or migration is added; Redis holds only transient messages (task name plus `[flip_id]`) in the `healthchecks` list, and durable state stays in `Flip`, `Notification` and `Channel`. Why: S1 names Celery and Redis; results are not needed because the database already records outcomes. Alternatives: RabbitMQ or SQS (S1 names Redis); a result backend (nothing reads results); a DB `queued` state column (schema change). Basis: S1
- AD-14 (new) Namespaces: `hc/celery.py` holds the app (imported only by `hc/api/tasks.py` and the `celery -A hc.celery` CLI); `hc/api/tasks.py` holds the moved `notify` and the task `notify_flip`, next to the models and transports they use; tasks bind with `@app.task` and `hc/__init__.py` stays empty, so gunicorn, `smtpd` and `sendreports` never import Celery; `sendalerts` imports `hc.api.tasks`; the old `sendalerts.notify` name is removed, not aliased. Collisions: `hc.celery` does not shadow the third-party `celery` because imports are absolute, no existing `notify_flip`, `tasks` or `hc.celery` symbol exists, the task name is `hc.api.tasks.notify_flip`, the queue is `healthchecks`, the app is named `hc`. Why: a worker should not import a management command, and no empty package is created for the future. Alternatives: keep `notify` in the command module (rejected: workers would import a CLI module); `shared_task` plus a Celery import in `hc/__init__.py` (rejected: loads Celery in every process); autodiscovery across all `INSTALLED_APPS` (rejected: one module needs it, `include=` is explicit). Basis: none
- AD-15 (new) Delivery stays at-most-once: claim first (AD-2), early ack (Celery's default), no `autoretry`, no `max_retries`; if publishing fails (`kombu.exceptions.OperationalError`) the dispatcher logs on `hc`, returns the flip to `processed=NULL` and waits for the next loop, so a Redis outage delays alerts instead of dropping them; a worker killed mid-task or Redis losing queued messages loses those alerts, the same exposure as a `sendalerts` crash today, and a publish whose acknowledgement is lost may rarely deliver twice, which is preferred to losing an alert. Why: S1 does not ask to change delivery guarantees and retries would add duplicates. Alternatives: `acks_late` plus per-(flip, channel) idempotency from `Notification` rows (preferred if loss is unacceptable, recorded as A3); a `queued` column on `Flip` (rejected: schema change). Basis: none
- AD-16 (changes AD-4) `sendalerts` stops owning delivery concurrency: `--num-workers` is accepted and ignored with a printed WARNING (as `--pool`, AD-11) and concurrency becomes `celery worker --concurrency N` per machine; `handle` raises `CommandError` when neither `CELERY_BROKER_URL` nor `CELERY_TASK_ALWAYS_EAGER` is set, so a missing broker fails at startup (and, through AD-6, stops the container) instead of silently stalling alerts. Why: the thread pool and semaphore no longer exist, and failing fast matches `envsecret`'s fail-loudly stance. Alternatives: delete the option (breaks existing unit files); a Django system check (rejected: also fires for gunicorn-only deployments and changes the exact id lists asserted in `hc/api/tests/test_system_checks.py`). Basis: S1
- AD-17 (new) Tests and local development need no Redis: the settings test block sets `CELERY_TASK_ALWAYS_EAGER = True` and `CELERY_TASK_EAGER_PROPAGATES = True`, so `.delay()` runs inline inside the test transaction and task errors fail tests; dispatcher failure paths are tested by patching `notify_flip.delay`; a developer can set `CELERY_TASK_ALWAYS_EAGER = True` in `hc/local_settings.py` to run `sendalerts` as before (one inline delivery at a time) - it is Celery's own flag, not an env var, and not offered as a production mode. Why: keeps CI (AD-8) and the SQLite-only development path. Alternatives: a Redis service in all 16 CI cells (rejected); an in-memory broker (`memory://`, rejected: a second path to maintain). Basis: none
- AD-18 (new) Deployment shape: Redis and workers are separate roles from the web container; the compose sample gains `redis` (AOF persistence on a volume) and `worker` (same image and `.env`, `command: celery -A hc.celery worker`, healthcheck disabled because the image HEALTHCHECK probes gunicorn); `docker/run.sh` and the Dockerfile do not change; further worker machines run the same image and environment against the same database and Redis (distinct `-n` names when several workers share one host). Why: S1 wants workers on several machines, so worker count must not be tied to web container count. Alternatives: start a worker inside `run.sh` (rejected: every web container would carry a prefork pool, and a single-container `docker run` would hide the new Redis requirement). Basis: S1
- AD-19 (new) Safeguards: no new externally reachable entry point, and the HTTP API's authentication and error contracts are untouched; no new caller-controlled input either (the task's only argument is a flip id the dispatcher produced, validated by loading the row; an unknown id is logged and dropped, never retried); Redis is trusted infrastructure on a private network with credentials or TLS in the URL; every async failure (publish error, task exception, missing flip) is logged on the `hc` logger so it reaches `Record` and `sendlogs` with the worker's hostname, while per-flip result lines go to the executing process's own output, as `sendalerts` printed them to its stdout. Why: reuses AD-7 instead of a new alerting path. Alternatives: Celery error callbacks or a Sentry hook (rejected: not in the project). Basis: none
- AD-20 (new) Execution environments: (a) web/gunicorn creates flips and runs interactive tests, unchanged, and needs neither broker nor workers; (b) `sendalerts`, one or more, needs database and broker and runs no transport code; (c) Celery workers, new, on any number of machines, run all transport code and so need what `sendalerts` needed plus the broker: the same image or virtualenv and the same environment as web, in particular the same `SECRET_KEY` (email unsubscribe links, bounce IDs and rate-limit bucket keys are derived from it), `SITE_ROOT`, `MAILERS`, `S3_*`, `STATSD_HOST`, every integration credential, the Apprise package, `SHELL_ENABLED` and the shell commands, and `SIGNAL_CLI_SOCKET` in `host:port` form when signal-cli is not local to every worker; (d) Redis, new, reached only by `sendalerts` and workers; (e) the database, now reached from every worker machine. URL building needs no extra worker state because the subpath lives in `hc/urls.py` (commit 45b8bd64). Why: transports read `django.conf.settings` at send time, so a thinner worker fails per notification (visible on the channel but easy to miss), and parity is what keeps S2 true. Alternatives: a startup check comparing worker and web settings (rejected: no shared source of truth). Basis: S2

## Assumptions

- A1. A Celery release that supports Python 3.12 to 3.15 and Django 6.1 exists; this could not be checked offline, so W1 verifies it first and stops for the owner if it does not.
- A2. No in-process fallback is built: Redis and at least one worker become mandatory for alerts to leave the system, because S1 says to move delivery out; the alternative I would have preferred for gentle upgrades, falling back to the thread pool when `CELERY_BROKER_URL` is unset, is left out. The version label (v5.1 or a major bump, as v5.0 got for the gunicorn switch) is the owner's call.
- A3. Delivery stays at-most-once (AD-15); if lost alerts after a worker kill or a Redis flush are unacceptable, the preferred alternative is `acks_late` with per-(flip, channel) idempotency using `Notification` rows, not built.
- A4. Only `sendalerts` flip delivery moves (AD-9); the Test! button, deletion notices, `sendreports` reports and nags stay in their processes.
- A5. Once several workers run, the down and up flips of one check can be delivered out of order; this already holds for `--num-workers` above 1, but the default was 1, so default installs now lose serial ordering; not addressed.
- A6. Monitoring meaning shifts: `num_unprocessed_flips` counts only flips awaiting dispatch, and a stalled or absent worker fleet shows as Redis queue length, a flat `max_notification_id`, missing `hc.notifications.*` counters or growing `dwellTime`; the docs say so and the metrics endpoint is not changed (a broker-backed queue-depth field would be preferable but puts the broker on the web tier).
- A7. Capacity: the old default of one delivery thread becomes a prefork pool per worker (`--concurrency=4` in the sample); PostgreSQL `max_connections` must cover workers times concurrency plus the existing processes (the repository chose raising `max_connections` over pooling, commit e581a8fa); worker clocks should be synced because `dwellTime` compares worker time with `flip.created`.
- A8. Host-local integrations behave per worker machine: a Shell command runs on whichever worker takes the task with that worker's permissions, `Channel.send_signal_captcha_alert` names the worker's hostname in its instructions, and Apprise exists only where installed (the Docker image has it).
- A9. Celery behaviours are taken from its documentation and could not be verified offline: early ack default, the eager flags, `OperationalError` on publish failure, the Django fixup closing connections per task, `hc` logger records surviving Celery's logging setup, `-A hc.celery` discovery; W2's real-broker smoke is where each is confirmed, and prefetch 1, the queue name and `--concurrency=4` are starting values to confirm there.
- A10. The plan is for local use; upstream's CONTRIBUTING.md (no AI-assisted contributions, pull requests disabled) is a project fact, so if this change is meant for upstream the owner must decide how to submit it.
- A11. S1's goal of spreading delivery across machines is partly available today by running more `sendalerts` processes (AD-2); the plan still builds Celery because S1 names it, and the added value is separating detection from delivery capacity, which the owner may want to confirm.
