## Stack

### Runtime and web framework
- Language runtime: Python 3.12 or newer (README.md:16, CHANGELOG.md:138); CI runs 3.12, 3.13, 3.14 and 3.15 (.github/workflows/tests.yml `python-version`); the container image uses Python 3.14.10 on Debian trixie (docker/Dockerfile)
- Web framework: Django 6.1 (README.md:17), pinned `Django[argon2]==6.1.2` in requirements.txt; project package `hc`, settings module `hc.settings`, URL root `hc.urls`, WSGI callable `hc.wsgi:application` (hc/settings.py, hc/urls.py, hc/wsgi.py `application`)
- Pinned runtime libraries (requirements.txt): cronsim 2.7 (cron expressions), oncalendar 1.1 (systemd OnCalendar), django-compressor 4.6 (offline bundles), fido2 2.2.1 (WebAuthn), minismtpd 0.5 (inbound SMTP), psycopg 3.3.6 (PostgreSQL driver), pycurl 7.48.0 (HTTP client), pydantic 2.14.1 (JSON models), PyJWT[crypto] 2.15.1 (GitHub app tokens), pyotp 2.10.0 (TOTP), segno 1.6.6 (QR codes), statsd 4.0.1, whitenoise 6.12.0 (static files), django-stubs-ext 6.1.2
- Optional or development-only libraries (requirements-dev.txt): apprise 1.13.1 (Apprise integration, preinstalled in the image), minio 7.2.20 (object storage client, also pinned in docker/Dockerfile), Markdown 3.10.2 and Pygments 2.21.0 (documentation and snippet rendering), mypy 2.4.0 with django-stubs and types-* packages, time-machine 3.5.1 (tests); the MySQL driver mysqlclient is installed by CI and by the image, not listed in requirements.txt (.github/workflows/tests.yml, docker/Dockerfile)
- Web server: any WSGI server; the reference image runs gunicorn (installed in the image, configured in docker/gunicorn.conf.py), and the README suggests gunicorn or uWSGI elsewhere (README.md:566, README.md:570)

### Data stores
- Relational database through the Django ORM: SQLite by default (hc.sqlite in the checkout), PostgreSQL, MySQL or MariaDB selected by the `DB` variable; minimum server versions PostgreSQL 15, MySQL 8.4, MariaDB 10.11 (README.md:18, hc/settings.py `DATABASES`, CHANGELOG.md:70); schema migrations live in each app's `migrations/` directory
- A second, read-only SQLite file `search.db` holds a full-text (FTS5) index of the documentation and is queried with the standard library, outside the ORM (hc/front/views.py `docs_search`, hc/front/management/commands/populate_searchdb.py `Command`)
- Optional S3-compatible object storage for large ping bodies, reached through the minio client (README.md:347, hc/lib/s3.py `client`)

### Front end
- Server-rendered Django templates (templates/ for shared and page templates, `hc/integrations/<kind>/templates/` for per-integration ones); no JavaScript build step: plain scripts in static/js (jQuery 3.6.0, Bootstrap scripts, noUiSlider, Tom Select, DOMPurify, zxcvbn, webauthn-json) are bundled and compressed by django-compressor offline at deploy time (hc/settings.py `COMPRESS_OFFLINE`, static/js, templates/base.html)
- CSS is compiled from Bootstrap Less sources in stuff/bootstrap with `lessc` into static/css/bootstrap.css; the icon font comes from an IcoMoon project file (stuff/bootstrap.sh, stuff/icons_icomoon_project.json)

### Tooling, CI and packaging
- GitHub Actions: tests on SQLite, PostgreSQL, MySQL and MariaDB across four Python versions; `mypy --strict` over `hc` (Python 3.12); coverage upload; Docker image publication on release for linux/amd64, linux/arm/v7 and linux/arm64/v8 (.github/workflows/tests.yml, .github/workflows/mypy.yml, .github/workflows/coverage.yml, .github/workflows/publish_docker_image.yml)
- Formatting with ruff and a preference for simplicity (CONTRIBUTING.md:24, CONTRIBUTING.md:25); strict typing configured in mypy.ini with the django-stubs plugin (mypy.ini)
- The Docker image is a two-stage build that compiles wheels in a builder stage, bakes `collectstatic` and `compress` output into the image, and starts through a bash script (docker/Dockerfile, docker/run.sh)

## Conventions

### Code
- Nearly every module starts with `from __future__ import annotations` and all code is annotated for `mypy --strict`; request objects that carry extra attributes use typed subclasses (`ApiRequest` with `project`, `readonly`, `v`, `json`; `AuthenticatedHttpRequest` with `profile`) (hc/api/decorators.py `ApiRequest`, hc/accounts/http.py `AuthenticatedHttpRequest`, mypy.ini)
- Views are plain functions guarded by decorators: `login_required`, `require_POST`, `csrf_exempt` for machine endpoints, `require_setting("<SETTING>")` to answer 404 when an integration is switched off, `authorize` and `authorize_read` for the API, `require_sudo_mode` for sensitive account actions (hc/front/decorators.py `require_setting`, hc/api/decorators.py, hc/accounts/decorators.py)
- Access to a check, channel or project is always resolved through the `_get_*_for_user` helpers, which return 404 for non-members and let the caller refuse read-only members with `_get_rw_*`; new views follow this pattern (hc/front/views.py `_get_check_for_user`, `_get_rw_check_for_user`)
- Browser input is validated with Django forms (forms.py next to the view); JSON input and the per-kind configuration stored in `Channel.value` are validated with pydantic models (hc/front/forms.py, hc/api/views.py `Spec`, hc/api/models.py `WebhookSpec`, `TelegramConf`, `NtfyConf`)
- Integration enable flags are `<KIND>_ENABLED` settings that default to true for kinds that need no operator credentials and to false for Apprise (optional dependency) and Shell (security), kinds that need operator credentials are offered when the credential is set, and the integrations page decides what to show from `settings` in one place (hc/settings.py, hc/front/views.py `channels`)
- Performance notes are written as comments where they matter and should be preserved: build API URLs by string formatting instead of `reverse`, defer large columns and prefetch with `only`, sort Postgres-sensitive queries by `created` or `n` rather than `id` (hc/api/models.py `Check.to_dict`, `Check.prune`, hc/front/views.py `_get_events`)
- Hosted-service forks are expected: `hc/front/views.py` ends with a marker comment saying where to add custom views (hc/front/views.py `Forks: add custom views after this line`)

### Tests
- Each app keeps tests in `tests/test_<topic>.py`, one `TestCase` class per topic, methods named `test_it_<behaviour>`; web and API tests subclass `hc.test.BaseTestCase` and use its alice, bob and charlie fixtures to test owner, member and outsider access (hc/test.py `BaseTestCase`)
- Integration tests mock network access at `hc.api.transports.curl.request` (the pycurl handle in the wrapper's own tests), time is controlled with `time_machine`, configuration with `override_settings`; the test runner swaps in a fast password hasher and synchronous email (hc/settings.py, hc/lib/emails.py `send`, hc/lib/tests/test_curl.py `test_get_works`)
- The same suite must pass on SQLite, PostgreSQL, MySQL and MariaDB; avoid database-specific SQL unless guarded by the connection vendor (.github/workflows/tests.yml, hc/api/apps.py `mariadb_uuid_check`)

### Documentation and release notes
- User documentation is Markdown in templates/docs, rendered to committed `.html-fragment` files with `manage.py render_docs`, listed in the navigation of templates/front/docs_single.html, and indexed into search.db with `manage.py populate_searchdb` (CONTRIBUTING.md:29, hc/front/management/commands/render_docs.py `Command`)
- Every user-visible change adds a line to CHANGELOG.md under "Improvements" or "Bug Fixes" of the unreleased section, with issue numbers when there are any (CHANGELOG.md:4)

### Invariants a change must not break
- Whatever changes a check's schedule, grace, status, last ping or started time must also refresh `alert_after` through `going_down_after()`; `sendalerts` finds overdue checks only through the partial index on `alert_after` for non-down checks (hc/api/models.py `Check.Meta`, `Check.going_down_after`, hc/api/views.py `_update`)
- Every status change must be recorded as a `Flip`; a change made for housekeeping (pause, resume, editing the schedule in the UI) must be created already processed so no alert is sent, while real up and down changes must stay unprocessed for `sendalerts` (hc/api/models.py `Check.create_flip`, hc/front/views.py `update_timeout`, `pause`)
- `Check.ping` is one transaction under a row lock that updates the check and inserts the ping together; object-store upload and pruning stay outside it (hc/api/models.py `Check.ping`)
- Deleting a check that may still be pinged goes through `rename_and_delete`, never a plain delete (hc/api/models.py `Check.rename_and_delete`)
- All stored times are timezone-aware UTC; zones apply only to schedule evaluation (`Check.tz`) and display (`Profile.tz`), results of zone arithmetic are converted back to UTC, and `TIME_ZONE` must stay "UTC" (hc/api/models.py `Check.get_grace_start`, hc/api/apps.py `settings_check`)
- Integration code reaches the network only through `hc.lib.curl` (or the library the integration is built on) so the private-address guard, protocol restriction and header encoding apply; integration failures are reported by raising `TransportError`, marked permanent only when retrying can never work (hc/lib/curl.py `request`, hc/api/transports.py `TransportError`, `HttpTransport`)
- A new integration kind needs entries in `TRANSPORTS`, `INSTALLED_APPS`, hc/urls.py, the integrations page and event-summary templates, an enable flag where applicable, an icon and tests for adding and notifying (CONTRIBUTING.md:39, hc/api/models.py `TRANSPORTS`, hc/settings.py `INSTALLED_APPS`)
- Links sent by email or chat must not carry the ping address: use `cloaked_url` or `absolute_reverse`; links in email that change state must stay two-step (confirm form, then POST) because mail scanners fetch links (hc/api/models.py `Check.cloaked_url`, hc/accounts/views.py `check_token`, hc/integrations/email/views.py `unsubscribe`)
- Values derived from `SECRET_KEY` (API key hashes, badge signatures, verification tokens, signed bounce identifiers, signed login and unsubscribe links) must not change algorithm silently, because existing keys, URLs in the wild and links in sent mail would stop working (hc/accounts/models.py `Project._make_api_key`, hc/lib/badges.py `check_signature`, hc/api/models.py `Channel.make_token`, hc/lib/signing.py)
- Management API request validation messages and response shapes are a public contract across v1, v2 and v3 (hc/api/views.py `CUSTOM_ERRORS`, `Spec`)

## Interfaces and boundaries

### Where input enters
- HTTP pings: `/ping/<uuid>[/...]` and `/ping/<ping-key>/<slug>[/...]` routed in hc/api/urls.py to `ping` and `ping_by_slug`, unauthenticated capability URLs (R-4, R-5)
- Email pings: SMTP connections to the `smtpd` process, routed by recipient address to `Check.ping` (R-6)
- Management API: `/api/v1/`, `/api/v2/`, `/api/v3/` in hc/api/urls.py, authenticated by project API key (R-50 to R-56)
- Web UI: routes of hc/accounts/urls.py, hc/front/urls.py, hc/payments/urls.py and the `urls.py` of every integration, all mounted by hc/urls.py below the `SITE_ROOT` path prefix; sessions and CSRF protection apply (R-58 to R-71)
- Third-party callbacks: Telegram bot webhook, delivery-status callbacks, bounce webhook, and the OAuth or subscription redirects of Slack, Discord, GitHub, Pushbullet, Pushover, PagerDuty and Trello (R-19, R-22, R-23, R-28, R-33, R-34, R-37, R-44, R-45)
- Monitoring probes: `/health`, `/api/v*/status/`, `/api/v*/metrics/`, and the Prometheus scrape path (R-49, R-84)
- Administrators: the Django admin at `/admin/`, `manage.py` commands, and the processes started by operators (R-76, R-80)
- Environment: all configuration enters through environment variables and the optional `hc/local_settings.py` read once at start-up (R-77)

### What leaves the system
- Email through the configured SMTP server; HTTPS requests to integration endpoints; messages to signal-cli over a local socket; shell commands in the Shell integration; object store reads and writes; statsd datagrams; database writes (hc/lib/emails.py, hc/lib/curl.py, hc/integrations/signal/transport.py, hc/integrations/shell/transport.py, hc/lib/s3.py, hc/lib/statsd.py)

### Process boundaries and shared state
- Four process roles share only the database: the web server, `sendalerts`, `sendreports` and `smtpd`; they coordinate through columns (`Check.alert_after`, `Flip.processed`, `Profile.next_report_date`, `Profile.next_nag_date`) and conditional updates, with no queue, cache or shared memory (hc/api/management/commands/sendalerts.py, hc/api/management/commands/sendreports.py)
- Several `sendalerts` or `sendreports` processes may run at once; work is claimed with an update that must change exactly one row (hc/api/management/commands/sendalerts.py `Command.process_one_flip`)
- The Docker entry script runs all roles in one container and ends the container when any one exits (docker/run.sh)

### Trust boundaries
- The reverse proxy is trusted for the client address (`X-Forwarded-For`) and, in the image, for the scheme (`X-Forwarded-Proto`); the external-authentication header is trusted absolutely when enabled (README.md:554, README.md:309, docker/gunicorn.conf.py)
- A ping UUID, or ping key plus slug, is a bearer capability; API keys are bearer secrets stored hashed; badge, unsubscribe and verification links are signed; notification links are cloaked (hc/api/views.py `ping`, hc/accounts/models.py `Project.compare_api_key`, hc/lib/badges.py)
- Integration users are semi-trusted: URLs they enter are fetched by the server, hence the private-address block, and the Shell integration is off unless the operator trusts every user (hc/lib/curl.py, README.md:504)

## Decisions

- AD-1 (inherited) The product is one Django project made of apps split by concern (`accounts`, `api`, `front`, `logs`, `payments`) plus one app per notification integration under `hc/integrations/`, deployed as a single codebase for hosted and self-hosted use. Why: a single deployable keeps self-hosting to "an application server and a database", and the hosted service runs the same code (inferred). Evidence: hc/settings.py `INSTALLED_APPS`, hc/urls.py `urlpatterns`, README.md:22.
- AD-2 (inherited) The web process only records state; separate long-running processes detect overdue checks and deliver notifications, and the processes share only the database. Why: notifications are sent asynchronously, the web process creates a status change record and a separate `sendalerts` process picks it up (stated: hc/api/models.py `Check.create_flip`). Evidence: hc/api/management/commands/sendalerts.py `Command`, README.md:224.
- AD-3 (inherited) Overdue detection polls a stored per-check instant (`alert_after`) that every ping and edit recomputes, instead of scheduling timers. Why: a stored instant survives restarts and schedule edits and can be served by one partial index (inferred). Evidence: hc/api/models.py `Check.Meta`, hc/api/models.py `Check.going_down_after`, hc/api/management/commands/sendalerts.py `Command.handle_going_down`.
- AD-4 (inherited) Status changes are stored as `Flip` rows that are both the notification work queue (unprocessed rows) and the history for downtime statistics. Why: the model documents exactly these two uses (stated: hc/api/models.py `Check.create_flip`). Evidence: hc/api/models.py `Flip`.
- AD-5 (inherited) A ping updates the check and inserts the ping in one transaction while holding a row lock, and uploads large bodies and prunes after the transaction. Why: without the lock concurrent pings can deadlock on MariaDB, sendalerts must not see the updated check before its ping exists, and object store calls can be slow (stated: hc/api/models.py `Check.ping`). Evidence: hc/api/models.py `Check.ping`, hc/api/tests/test_ping.py `test_it_uploads_body_to_s3`.
- AD-6 (inherited) Workers claim work with a conditional update that must affect exactly one row instead of taking database locks. Why: it lets several worker processes run concurrently on every supported database engine without lock management (inferred). Evidence: hc/api/management/commands/sendalerts.py `Command.process_one_flip`, hc/api/management/commands/sendreports.py `Command.handle_one_report`.
- AD-7 (inherited) Each notification integration is a `Transport` subclass registered by dotted path in `TRANSPORTS`, imported on first use, and shipped as its own Django app with views, forms, templates, icon and tests. Why: the contribution guide tells authors to copy an existing integration and replicate every aspect of it, which this layout makes mechanical (stated: CONTRIBUTING.md:39). Evidence: hc/api/models.py `TRANSPORTS`, hc/api/models.py `Channel.transport`, hc/api/transports.py `Transport`.
- AD-8 (inherited) An integration's configuration is one text column, `Channel.value`, holding either a bare string (older kinds) or JSON, read through typed accessor properties. Why: no table or migration per integration, while older rows in their original formats stay valid (inferred). Evidence: hc/api/models.py `Channel.value`, hc/api/models.py `EmailConf.load`, hc/api/models.py `PdConf.load`, hc/api/models.py `Channel.slack_webhook_url`.
- AD-9 (inherited) Delivery failures are classified: a `TransportError` flagged permanent disables the integration, other errors only record the message, and HTTP integrations retry up to three times unless permanent. Why: dead endpoints stop being hit while transient errors do not silently disable alerting (inferred). Evidence: hc/api/models.py `Channel.notify`, hc/api/transports.py `HttpTransport.request`, hc/integrations/slack/transport.py `Slack.raise_for_response`.
- AD-10 (inherited) All outbound HTTP from integrations uses a thin pycurl wrapper that refuses private addresses unless `INTEGRATIONS_ALLOW_PRIVATE_IPS`, allows only HTTP and HTTPS, limits redirects to three and applies to OAuth setup calls too. Why: letting users define webhooks that probe internal addresses is a security risk (stated: templates/docs/self_hosted_configuration.md:449). Evidence: hc/lib/curl.py `request`, hc/lib/tests/test_curl.py `test_it_rejects_private_ip`.
- AD-11 (inherited) Rate limiting is a database-backed token bucket keyed by short strings (hashed where they hold personal data), pruned by a command. Why: a multi-process deployment has no shared cache to rely on, and the README tells operators to prune the table (inferred). Evidence: hc/api/models.py `TokenBucket`, README.md:270.
- AD-12 (inherited) Configuration is read from environment variables in one settings module, then overridden by an optional `local_settings.py`, and secrets can come from `<NAME>_FILE` files. Why: one environment-driven module suits container and systemd deployments, and secrets can then be mounted as files (inferred). Evidence: README.md:141, CHANGELOG.md:159, hc/settings.py `envsecret`.
- AD-13 (inherited) The project, not the user, owns checks, integrations, API keys, the ping key and the badge key; the account of the project's owner carries the check and message limits; team membership is per project with three roles. Why: each project has its own team, so access can be granted selectively (stated: templates/docs/projects_teams.md:15). Evidence: hc/accounts/models.py `Project`, hc/accounts/models.py `Member`, hc/accounts/models.py `Profile`.
- AD-14 (inherited) Project API keys are stored as a keyed hash with the first eight characters kept for lookup, prefixed `hcw_` or `hcr_`, and legacy plain-text keys are still accepted. Why: a database leak should not expose usable keys while old keys keep working (inferred). ## Superseded

- S-1 (inherited) uWSGI as the web server of the Docker image, with child processes restarted individually. Replaced by gunicorn and a container that exits when any child exits; `UWSGI_PROCESSES` and `UWSGI_DISABLE_LOGGING` are still honoured as fallbacks. Why replaced: the release notes describe the change and its consequences but give no reason (inferred). Evidence: CHANGELOG.md:34, docker/run.sh, docker/gunicorn.conf.py.
- S-2 (inherited) Shell integration commands built by substituting `$NAME`, `$STATUS` and similar text into the command line. Replaced by environment variables. Why replaced: escaping and command injection problems, per the message of commit ca8b9c03 (inferred). Evidence: CHANGELOG.md:60, hc/integrations/shell/transport.py `Shell.notify`.
- S-3 (inherited) Plain-text storage of project API keys. Replaced by hashed storage with `hcw_` and `hcr_` prefixes; old plain-text keys remain valid. Why replaced: a database leak should not expose usable keys (inferred). Evidence: CHANGELOG.md:196, hc/accounts/models.py `ProjectManager.for_api_key`.
- S-4 (inherited) The in-tree billing implementation (customer, subscription and payment handling). Replaced by stubs. Why replaced: dead weight for self-hosters and diverging from the hosted service's private billing code, per the message of commit a308997b (inferred). Evidence: hc/payments/views.py `pricing`, hc/payments/models.py `Subscription`.
- S-5 (inherited) A general-purpose asynchronous SMTP library for the inbound listener. Replaced by a smaller purpose-built one (minismtpd) in 5.0, which gained concurrent sessions in 5.0.2. Why replaced: smaller scope and less complexity, hopefully easier to maintain, per the message of commit d5c6faba (inferred). Evidence: CHANGELOG.md:23, CHANGELOG.md:59, hc/api/management/commands/smtpd.py `Server`, requirements.txt.

Why kept: existing clients, rows and scripts must keep working (inferred). Evidence: hc/api/views.py `_update`, hc/api/models.py `Channel.discord_webhook_url`, hc/api/management/commands/sendalerts.py `Command.add_arguments`.
- S-7 (inherited) The croniter library for cron expressions. Replaced by cronsim in 2021, first vendored and then installed from PyPI. Why replaced: not stated in the repository files (inferred). Evidence: requirements.txt, hc/api/models.py `Check.get_grace_start`.
