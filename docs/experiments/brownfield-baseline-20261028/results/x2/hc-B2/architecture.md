# Healthchecks: baseline architecture

As of 9f12cd8d (every file outside `docs/shiploop` is identical to f6c46b59, the commit of the earlier baseline). The repository keeps no decision records and no architecture document (census: none found); everything below is read from the code, its tests and its instruction files. Instruction files are linked, never copied: `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG.md`, `.github/pull_request_template.md`.

## Stack
- Python 3.12 or newer, Django 6.1.2 (Argon2 password hashing) served as a WSGI app; gunicorn in the reference Docker image. (`requirements.txt` `Django[argon2]==6.1.2`)
- Database through the Django ORM: SQLite by default, PostgreSQL (psycopg 3), MySQL or MariaDB (mysqlclient, installed separately). (`hc/settings.py` `DATABASES`)
- Outbound HTTP through pycurl behind `hc/lib/curl.py`; pydantic 2 models for the JSON configuration of integrations; email through Django's SMTP backend with a retrying wrapper. (`requirements.txt` `pycurl==7.48.0`)
- Scheduling libraries cronsim and oncalendar; 2FA with fido2 and pyotp; segno for QR codes; PyJWT; optional minio for ping bodies in S3-compatible storage and optional apprise. (`requirements.txt` `cronsim==2.7`)
- Front end: server-rendered Django templates, jQuery 3.6.0 and Bootstrap 3.4.1 vendored in `static`, django-compressor in offline mode, whitenoise for static files; no JavaScript build step and no JavaScript tests. (`hc/settings.py` `COMPRESS_OFFLINE`)
- Quality tooling: mypy 2.4 in strict mode with django-stubs, ruff for formatting (named in `CONTRIBUTING.md`; no configuration file and no pinned version), time-machine for time in tests, coverage with Coveralls in CI. (`requirements-dev.txt` `time-machine==3.5.1`)
- Metrics out: statsd over UDP when `STATSD_HOST` is set, otherwise a no-op client. (`hc/lib/statsd.py` `get_client`)

## Structure
- `hc/api`: the domain core and delivery. Models Check, Ping, Flip (status change), Channel (integration), Notification (delivery record), TokenBucket (rate limiting); the `Transport` base classes; management commands `sendalerts`, `sendreports`, `smtpd`, the prune commands, `settelegramwebhook`, `submitchallenge`; ping endpoints; delivery callbacks; Django admin for these models; and the Management API: the route list `api_urls` (mounted at `/api/v1/`, `/api/v2/`, `/api/v3/`), the key and cross-origin wrappers in `hc/api/decorators.py`, the handlers in `hc/api/views.py` and the JSON form of a check, `Check.to_dict`.
- `hc/integrations/<kind>`: one Django app per integration kind (29 transport kinds plus the Prometheus scrape endpoint). Each kind has a transport module (delivery), views and forms (set-up), a URL module, templates, static images and tests; see `hc/integrations/webhook` for a complete example.
- `hc/front`: web UI views (dashboard, checks list, details, Events log, integrations list, badges, docs), forms, validators, template tags, and the `render_docs` and `populate_searchdb` commands.
- `hc/accounts`: users, `Profile` (limits, quotas, report and reminder settings), `Project` (including its read-write and read-only API keys and their lookup, `ProjectManager.for_api_key`), `Member` roles, the project settings page where keys are created and revoked, login by email link or password, WebAuthn and TOTP, account admin.
- `hc/lib`: stateless helpers: curl wrapper, email sending, bounce-id signing, S3, dates and time zones, badges, statsd, URLs, strings.
- `hc/logs`: database log handler and `Record` model. `hc/payments`: placeholders (billing is off unless `USE_PAYMENTS`).
- `templates` and `static`: base layouts, page templates per area, email templates, Markdown documentation with its rendered `.html-fragment` files (the Management API reference is `templates/docs/api.md`, `templates/docs/apiv2.md`, `templates/docs/apiv1.md`), CSS and JavaScript. `templates/front/dashboard.html` is the self-contained read-only dashboard served at `/tv/`. `stuff`: design-asset sources, removed from the Docker image.
- `docker`, `.github`: reference image and process supervisor script; CI workflows and the pull request template.

## Conventions
- Rule that restricts the requested work (owner decision needed): `CONTRIBUTING.md` does not accept content generated or touched up by AI tools, closes AI-assisted pull requests and issues without discussion, and has disabled pull requests (contributors mention a branch in an issue comment instead); `.github/pull_request_template.md` asks the author to confirm that no AI tools were used. (`CONTRIBUTING.md` "AI Policy")
- Process rules: open an issue before anything larger than a small bugfix; add a test with every fix or feature; prefer simplicity over cleverness; format Python with ruff. (`CONTRIBUTING.md` "Code Style")
- New integration kinds are built by copying a similar kind and replicating every aspect: transport, templates, tests, the `TRANSPORTS` entry, views, URLs, a `templates/front/channels.html` entry and a `templates/front/event_summary.html` branch. (`CONTRIBUTING.md` "Developing a New Integration")
- Documentation is Markdown under `templates/docs`, rendered with `manage.py render_docs`, with navigation added to `templates/front/docs_single.html`. (`CONTRIBUTING.md` "Adding Documentation")
- Every Python module starts with `from __future__ import annotations` and is fully annotated for `mypy --strict`; views stay thin and use access helpers (`_get_check_for_user` and its siblings); domain logic sits on models; integration configuration is parsed by pydantic models or typed dictionaries. (`hc/front/views.py` `_get_rw_check_for_user`)
- Error texts shown to users are short plain sentences; whether they end with a period varies by transport. (`hc/integrations/webhook/transport.py` "Webhook notifications are not enabled."; `hc/integrations/sms/transport.py` "SMS notifications are not enabled")
- Tests live in `tests/` beside each app as `test_*.py`, derive from `BaseTestCase` (alice owns the project, bob is a regular member, charlie has no access), patch `hc.api.transports.curl.request` for HTTP integrations, and use time_machine for time. (`hc/test.py` `BaseTestCase`)
- Changes are recorded in `CHANGELOG.md` under the top "## v..." section (Improvements, Bug Fixes), in the same commit as the code; commit subjects are short imperative sentences. (`CHANGELOG.md` "Unreleased")
- Existing features most like the earlier, delivery-related request, and what each touched: Twilio status callbacks (commit 95d58d26: `hc/api/models.py`, `hc/api/transports.py`, `hc/api/urls.py`, `hc/api/views.py`, tests, CHANGELOG); statsd counters for notifications (924ad468: `hc/api/management/commands/sendalerts.py` and its tests); Flip.reason (9edae634: a model field, migration `hc/api/migrations/0114_flip_reason.py`, template use); per-integration retry tuning (8c210e15 Signal retries, 71f1a8d9 Slack no retry on invalid_token, 9c8bb54f Twilio no retry on 21211). (`hc/api/migrations/0114_flip_reason.py` `Migration`)
- Management API handlers take an `ApiRequest`, carry the decorator that matches the key power they need (`authorize` for read-write keys, `authorize_read` for both kinds) under the `cors(<methods>)` and `csrf_exempt` wrappers, answer with `JsonResponse`, and build every check with `Check.to_dict(readonly=..., v=...)`; a handler that serves both key kinds branches on `request.readonly`. (`hc/api/views.py` `get_checks`)
- Management API tests: one `TestCase` per call in `hc/api/tests`, deriving from `BaseTestCase`, calling `/api/v1/...` with `HTTP_X_API_KEY` set to the plain keys of 32 `X` (read-write) or 32 `R` characters (read-only), and asserting the status code, the JSON body and `Access-Control-Allow-Origin`; list calls also assert query counts with `assertNumQueries`; `hc/api/tests/test_auth.py` covers hashed keys of both kinds. (`hc/api/tests/test_list_checks.py` `ListChecksTestCase`)
- Existing features most like this request, and what each touched: the read-only API key (432e592e: decorators, views, the Project model with migrations in both apps, the settings view and template, tests, CHANGELOG); hashed `hcw_` and `hcr_` keys (d953c7b6: Project model, decorators, settings view, template and script, docs, tests); the read-only dashboard page (b7e2404f: `templates/front/dashboard.html`, `hc/front/urls.py`, `Project.dashboard_url`, CHANGELOG); the `/api/v1/badges/` call (98eb7cc1: route, view, test, docs, CHANGELOG); Prometheus gauges (456e846d: view, tests, CHANGELOG). (`hc/api/tests/test_get_badges.py` `GetBadgesTestCase`)
- A setting gets one section in the settings reference; five older settings lack one (spec R-16). (`templates/docs/self_hosted_configuration.md` "PROMETHEUS_ENABLED")

## Interfaces and boundaries
- Inbound, unauthenticated: ping URLs `/ping/<uuid>[/fail|/start|/log|/<exit status>]` and project-key slug URLs; email pings to the `smtpd` listener; status badges at public hard-to-guess URLs; the Twilio status callback and the bounce endpoint (spec R-4); the Telegram bot webhook; `/health` and the status endpoint. (`hc/api/urls.py` `urlpatterns`)
- Inbound, project API key: Management API v1 to v3 under `/api/v*/`; the key goes in `X-Api-Key`, and read-write calls also take it from the `api_key` field of a POST body; a read-write key works on every call, a read-only key on four read calls (spec R-23). Reference: `templates/docs/api.md` (linked, not copied). (`hc/api/decorators.py` `authorize`)
- Inbound, browsers of any origin: every Management API address answers cross-origin requests (`Access-Control-Allow-Origin: *`, header `X-Api-Key`), which is how the bundled `/tv/` page and other web dashboards call it. (`hc/api/decorators.py` `cors`)
- Inbound, session user: the web UI (`hc/front`, `hc/accounts`, integration set-up pages) with CSRF protection; Django admin for superusers. (`hc/urls.py` `urlpatterns`)
- Inbound, operator key: the metrics endpoint (`X-Metrics-Key`); Prometheus scrape of a project with a read-only key, in the URL or as a Bearer token, while `PROMETHEUS_ENABLED` is true. (`hc/api/views.py` `metrics`; `hc/integrations/prometheus/views.py` `metrics`)
- Outbound: HTTP(S) by pycurl to webhooks and SaaS APIs; SMTP; the signal-cli socket; local shell commands; the Apprise library; S3 (minio); statsd UDP; Twilio; OAuth providers during integration set-up. (`hc/lib/curl.py` `request`)
- Processes: web workers, `sendalerts`, `sendreports --loop`, optional `smtpd`; they share only the database. There is no message broker, cache or task queue between them. Docker supervises them with `docker/run.sh`. (`docker/run.sh` `sendalerts`)
- Trust boundaries: project members are trusted with the project's data (read-only members can read everything the log shows); integration targets are user-supplied and untrusted (private addresses blocked by default); callbacks are unauthenticated and rely on unguessable or signed identifiers; a holder of a project's read-only API key can read every check of the project but not its integrations or ping logs (spec R-23). (`templates/docs/self_hosted_configuration.md` "INTEGRATIONS_ALLOW_PRIVATE_IPS")
- Contracts linked, not copied: Management API reference `templates/docs/api.md` (v3), `templates/docs/apiv2.md`, `templates/docs/apiv1.md`; Prometheus guide `templates/docs/configuring_prometheus.md`; team roles `templates/docs/projects_teams.md`; settings reference `templates/docs/self_hosted_configuration.md`; container notes `docker/README.md`.

## Decisions
- AD-1 (inherited) One Django project with one app per feature area (accounts, api, front, logs, payments) and one app per integration kind under `hc/integrations`, each listed in `INSTALLED_APPS` and routed from `hc/urls.py`. Why: it keeps each feature area and each integration kind self-contained, so a kind can be copied or removed as a unit (inferred). Evidence: `hc/settings.py` `INSTALLED_APPS`; `hc/urls.py` `urlpatterns`.
- AD-2 (inherited) The user interface is server-rendered templates with small jQuery scripts; pages update by polling endpoints that return HTML fragments or JSON, with no single-page app, build step, websocket or server push. Why: self-hosting stays simple because nothing needs building or serving beyond Django itself (inferred). Evidence: `templates/base.html` `jquery-3.6.0.min.js`; `static/js/adaptive-setinterval.js` `adaptiveSetInterval`.
- AD-3 (inherited) All state lives in one relational database reached through the ORM, on SQLite, PostgreSQL, MySQL or MariaDB alike; schema changes are numbered migrations per app (latest: `hc/api` 0123, `hc/accounts` 0053); code must not rely on engine-specific behaviour (a tag filter is an approximate database filter followed by an exact check in Python), and query code is written to avoid known slow plans (sort by `created`, not `id`). Why: the README names these database families as the supported building blocks, and the same code and tests must run on all of them (stated: `README.md` "PostgreSQL, MySQL or MariaDB"). Evidence: `hc/settings.py` `DATABASES`; `.github/workflows/tests.yml` `matrix`; `hc/api/views.py` "approximate filtering by tags"; `hc/accounts/migrations/0053_alter_profile_sms_limit.py` `Migration`.
- AD-4 (inherited) Alert delivery is a pull model with no broker: the web process (or the alert process itself) writes a status change row, and the separate `sendalerts` process polls for unprocessed rows and delivers them; there is no scheduler and no retry table. Why: the web process only records the change, and the separate alert process picks it up and processes it, using the same rows for downtime statistics (stated: `hc/api/models.py` "picks it up and processes it"). Evidence: `hc/api/models.py` `create_flip`; `hc/api/management/commands/sendalerts.py` `process_one_flip`.
- AD-5 (inherited) Work is claimed with optimistic conditional UPDATEs that must change exactly one row (a status change is claimed by setting its processed time where it is still empty; a check goes down by an update guarded on its old status; reports claim by their next date), so several processes can run without locks. Why: several worker processes may share one database, and a lost race is simply skipped (stated: `hc/api/management/commands/sendalerts.py` "another sendalerts process got there first"). Evidence: `hc/api/management/commands/sendalerts.py` `handle_going_down`; `hc/api/management/commands/sendreports.py` `handle_one_report`.
- AD-6 (inherited) Delivery is at most once per status change and integration: the status change is marked processed before any integration is contacted, a failed attempt is recorded and never re-queued, and an escaped exception or crash abandons the remaining integrations of that status change; retries exist only inside one attempt. Why: marking the work done first prevents duplicate alerts from concurrent workers or restarts, at the price of no recovery after a crash (inferred). Evidence: `hc/api/management/commands/sendalerts.py` `num_updated`; `hc/api/transports.py` `request`.
- AD-7 (inherited) `sendalerts` is one long-running management command: a poll loop with a 2 second idle sleep, a thread pool of `--num-workers` (default 1), signal handlers that let running deliveries finish, stale DB connections closed per thread, and the DB application name set to the command; operators must keep it running, and the Docker image stops the container when any child exits. Why: alerts are a continuous duty of an instance, so operators must supervise the process and containers must fail loudly when it dies (stated: `README.md` "Running in Production"). Evidence: `hc/api/management/commands/sendalerts.py` `handle`; `docker/run.sh` `wait -n`; `CHANGELOG.md` "v5.0 - 2026-10-20".
- AD-8 (inherited) One transport class per integration kind, registered in the `TRANSPORTS` table in `hc/api/models.py` and imported on first use; a transport implements `notify(flip, notification)` and, when it can ignore a status, `is_noop(status)`; HTTP kinds extend `HttpTransport` and Slack-compatible kinds extend `Slackalike`. Why: a uniform contract lets the alert process treat every kind alike and keeps each kind's code in its own app (stated: `CONTRIBUTING.md` "Developing a New Integration"). Evidence: `hc/api/models.py` `TRANSPORTS`; `hc/api/transports.py` `HttpTransport`.
- AD-9 (inherited) Delivery errors are the typed exception `TransportError(message, permanent)`: the message is user-facing text that is stored and shown verbatim; `permanent` disables the integration and ends in-attempt retries; any other exception is treated as a bug and propagates out of the attempt. Why: it separates expected remote failures, which users must see, from bugs, which go to the log, and lets a transport say "stop trying" (inferred). Evidence: `hc/api/transports.py` `TransportError`; `hc/api/models.py` `transports.TransportError`.
- AD-10 (inherited) One delivery attempt is one `Notification` row, inserted before sending with the error text "Sending" and finalized afterwards; later callbacks address the same row through its random public `code`; the `Channel` columns `last_notify`, `last_notify_duration` and `last_error` are a denormalized summary of the latest attempt, overwritten each time. Why: the row must exist before sending so provider callbacks and bounces can name it and so in-progress attempts are visible (inferred). Evidence: `hc/api/models.py` `n.error = "Sending"`; `hc/api/views.py` `notification_status`.
- AD-11 (inherited) `Channel.notify` is the single entry point for one delivery and returns its outcome as text ("" for success, "no-op", or the error); the alert process, the Test! view, the group transport and the account-deletion command all call it and read that text. Why: one choke point keeps record keeping, integration state and quota use consistent across the four callers (inferred). Evidence: `hc/api/models.py` `notify`; `hc/integrations/group/transport.py` `notify`.
- AD-12 (inherited) Retrying is a per-transport concern inside one attempt: `HttpTransport.request` makes up to 3 immediate tries, Signal 2, email sending 3 with a 1 second pause; transports opt out through `permanent` errors, and the webhook transport opts out for test notifications; there is no shared policy object, no back-off, no stored attempt counter and no setting. Why: transports differ in protocol, so each handles transient errors itself, and for webhooks the policy is promised to users (stated: `hc/integrations/webhook/templates/webhook_form.html` "retries failed webhook calls up to 2 additional times"). Evidence: `hc/api/transports.py` `tries_left`; `hc/integrations/signal/transport.py` `tries_left`; `hc/lib/emails.py` `MAX_TRIES`.
- AD-13 (inherited) Quotas and rate limits are enforced inside each transport at send time, through account counters (`authorize_sms`, `authorize_call` on the profile) and `TokenBucket` rows; a refused attempt is an ordinary failed attempt with a short text, so each call to a transport spends quota. Why: SMS and calls cost money per use, so the check sits next to the provider call (inferred). Evidence: `hc/integrations/sms/transport.py` `authorize_sms`; `hc/api/models.py` `authorize_telegram`.
- AD-14 (inherited) A check's event log is assembled per request from the ping, notification and status-change tables, merged and sorted in Python, and rendered by shared row templates for the Events page, its live fragment and the details page; there is no unified event table and no stored per-event rendering. Why: retention limits the events per check, so three small queries per request are cheap and no duplicate event table is needed (inferred). Evidence: `hc/front/views.py` `_get_events`; `templates/front/log_row.html` `event.check_status`.
- AD-15 (inherited) Retention of notifications and status changes is derived from ping retention (`Profile.ping_log_limit`, default 100) and runs inline on every 100th ping plus an optional batch command; there is no separate retention setting. Why: one knob keeps the log consistent, and status changes are kept for about three months because downtime statistics need them (stated: `hc/api/models.py` "We need ~3 months of flips for calculating"). Evidence: `hc/api/models.py` `prune`; `hc/api/management/commands/prunepingsslow.py` `Command`.
- AD-16 (inherited) Authorization is per project and checked in each view through helpers that resolve the object and the caller's role (superuser, then owner, then membership; no membership gives 404; the member and manager roles are read-write, read-only is not; mutating views demand read-write and answer 403); the Management API authenticates with a project API key kept as an HMAC-SHA256 digest with a readable 8-character prefix (legacy plain-text keys are still accepted); a project has one read-write and one read-only key, and keys belong to the project, never to a person or an account. Why: teams share projects with owner, member and read-only roles, and scripts need a key rather than a user session; keys are project-specific, with no account-wide key (stated: `templates/docs/api.md` "All API keys are project-specific"). Evidence: `hc/front/views.py` `_get_check_for_user`; `hc/accounts/models.py` `for_api_key`; `hc/api/decorators.py` `authorize`; `hc/api/decorators.py` `authorize_read`.
- AD-17 (inherited) Callbacks from third parties are CSRF-exempt, unauthenticated endpoints whose only credential is an unguessable record code or a signed identifier with a short life (1 hour for status callbacks, 48 hours for bounces); missing or expired identifiers get HTTP 200. Why: external services cannot log in, so the identifier in the URL is the credential and must expire, and answering 200 stops the sender from retrying (stated: `hc/api/views.py` "so the other party doesn't retry over and over again"). Evidence: `hc/api/views.py` `notification_status`; `hc/lib/signing.py` `ShortHexTimestampSigner`.
- AD-18 (inherited) Configuration is read in `hc/settings.py` from environment variables (helpers `envbool`, `envint`, `envsecret` with `_FILE` support), then overridden by the optional local settings file; integration availability is a boolean or credential setting checked when an integration is added and again at send time; settings sanity problems are registered Django system checks; settings are documented in the settings reference, one section each (five older settings have none, spec R-16). Why: self-hosters configure by environment, notably in Docker, with an optional local override file (stated: `README.md` "Configuration"). Evidence: `hc/settings.py` `envsecret`; `hc/api/apps.py` `settings_check`.
- AD-19 (inherited) Expected failures are data (record error text, integration last error, statsd counters, the alert process's log lines); unexpected exceptions go to the `hc` logger, whose handler writes rows to the database, and Django emails ADMINS about request errors when configured. Why: small installs need failures visible without an external log service, and the README points operators at ADMINS email or Sentry (stated: `README.md` "Running in Production"). Evidence: `hc/settings.py` `LOGGING`; `hc/logs/__init__.py` `Handler`.
- AD-20 (inherited) All outbound HTTP from integrations goes through `hc.lib.curl.request`: HTTP and HTTPS only, at most 3 redirects, a 30 second timeout set by `HttpTransport`, private addresses refused unless `INTEGRATIONS_ALLOW_PRIVATE_IPS`; Apprise is the documented exception. Why: users define the target URLs, so the client is the choke point for blocking probes of internal addresses (stated: `templates/docs/self_hosted_configuration.md` "allowing users to define webhooks that probe"). Evidence: `hc/lib/curl.py` `opensocket`; `hc/api/transports.py` `timeout=30`.
- AD-21 (inherited) Capabilities that run code or reach internal systems are opt-in by setting (`SHELL_ENABLED` is off by default), and webhook text is built by placeholder substitution that never re-expands substituted values. Why: shell commands run with the alert process's permissions, so the operator must trust the instance's users first (stated: `README.md` "fully trust the users of your Healthchecks instance"). Evidence: `hc/settings.py` `SHELL_ENABLED`; `hc/lib/string.py` `replace`.
- AD-22 (inherited) An integration's own configuration is stored as text in `Channel.value`, whose format depends on the kind (a bare string, a delimited string, or JSON parsed on access through pydantic models and typed dictionaries such as `WebhookSpec` and `EmailConf`); there is no per-kind table. Why: one text column holds 29 kinds of differing shape without a schema change per kind (inferred). Evidence: `hc/api/models.py` `WebhookSpec`; `hc/api/models.py` `EmailConf`.
- AD-23 (inherited) Integration code is replicated per kind rather than abstracted: a new kind starts as a copy of a similar kind, and shared behaviour sits in base classes only where several kinds already agree. Why: the maintainer recommends replicating a similar integration in every aspect (stated: `CONTRIBUTING.md` "The best way to build a new integration"). Evidence: `hc/integrations/discord/transport.py` `Slackalike`; `hc/integrations/mattermost/transport.py` `Slackalike`.
- AD-24 (inherited) Documentation is Markdown under `templates/docs`, rendered by `manage.py render_docs` into committed `.html-fragment` files and indexed into `search.db` by `populate_searchdb`; the docs pages are served from the fragments with placeholder substitution. Why: the Markdown tooling is a development-time dependency, so the running site serves pre-rendered fragments (inferred). Evidence: `hc/front/management/commands/render_docs.py` `process_directory`; `hc/front/views.py` `serve_doc`; `requirements-dev.txt` `Markdown==3.10.2`.
- AD-25 (inherited) Tests run with Django's runner, one `tests/` package per app; CI runs them on SQLite, PostgreSQL, MySQL and MariaDB with Python 3.12 to 3.15, plus `mypy --strict` and a coverage run; `TransactionTestCase` appears once, where a test needs real commits and an `IntegrityError`. Why: the supported-environment promises are only proven by running the suite on each of them (inferred). Evidence: `.github/workflows/tests.yml` `matrix`; `hc/api/tests/test_notify.py` `TransactionTestCase`.
- AD-26 (inherited) Static typing is enforced: every module starts with `from __future__ import annotations` and the tree must pass `mypy --strict` with the django-stubs plugin; formatting is ruff. Why: the style section asks for ruff and simplicity, and the strict type check runs in CI on every push (stated: `CONTRIBUTING.md` "Code Style"). Evidence: `.github/workflows/mypy.yml` `mypy --strict`; `mypy.ini` `django-stubs`.
- AD-27 (inherited) User-visible changes are written into `CHANGELOG.md` under the top "## v..." heading, and the application's displayed version is read from the first such heading at start-up. Why: the changelog is the release record and the running version is derived from it (stated: `CHANGELOG.md` "All notable changes"). Evidence: `hc/settings.py` `VERSION`; `CHANGELOG.md` "Unreleased".
- AD-28 (inherited) The Management API is one route list mounted three times, at `/api/v1/`, `/api/v2/` and `/api/v3/`, and served by plain function views: each call is wrapped by `cors(<methods>)` (which answers OPTIONS and refuses other methods) and `csrf_exempt`, its handler by `authorize` or `authorize_read`; calls that share an address are split by a small dispatch view (`checks`, `single`); the version is read from the request path and passed down as `v`. Why: one set of handlers serves every version, so older clients keep working while the versions differ only where input or output differ (inferred). Evidence: `hc/api/urls.py` `api_urls`; `hc/api/views.py` `single`; `hc/api/decorators.py` `_get_api_version`.
- AD-29 (inherited) The decorator decides what a key may do and the handler shapes what it returns: `authorize` accepts read-write keys only (and also reads the key from a POST body), `authorize_read` accepts both kinds and sets `request.readonly`; read handlers pass that flag to `Check.to_dict`, which drops the UUID-bearing fields and adds `unique_key`; there are no scopes, roles or permission tables behind keys. Why: the read-only key serves tools that only look, so it works on read calls and its responses omit sensitive information (stated: `templates/docs/api.md` "Omits sensitive information from the API responses"). Evidence: `hc/api/decorators.py` `authorize_read`; `hc/api/models.py` `to_dict`.
- AD-30 (inherited) A check's API form is built in one function from stored columns, per request: the displayed status comes from `Check.get_status` (clock plus stored data) and is never persisted, absolute addresses are assembled from `SITE_ROOT` and `PING_ENDPOINT` without `reverse()`, and list handlers load only what the response needs (integration codes for read-write keys, nothing extra for read-only keys). Why: lists of hundreds of checks must stay cheap (stated: `hc/api/models.py` "returning hundreds of checks"). Evidence: `hc/api/models.py` `to_dict`; `hc/api/views.py` `Prefetch`.
- AD-31 (inherited) API keys are created only on the project settings page (POST `create_key`), shown once, stored as `<8-character prefix>.<HMAC-SHA256 hex>` keyed with `SECRET_KEY`, replaced by creating again, cleared by revoking and never rotated automatically; plain legacy keys keep working until replaced; creating and revoking need a read-write role and no sudo step. Why: read-only members are kept away from keys because that would give them read-write access through the API (stated: `templates/docs/projects_teams.md` "cannot access the project's API keys"). Evidence: `hc/accounts/views.py` `create_key`; `hc/accounts/models.py` `_make_api_key`; `CHANGELOG.md` "Store project API keys in the database in a hashed form".
- AD-32 (inherited) Cross-origin access is open and credential-free: the `cors` wrapper adds `Access-Control-Allow-Origin: *` to every API answer, allows only the `X-Api-Key` header and the call's methods, and the key rides in a header; the Prometheus endpoint, which browsers are not meant to call, takes its key in the URL or a Bearer header instead. Why: browser dashboards on other origins call the API with a read-only key (inferred). Evidence: `hc/api/decorators.py` `cors`; `templates/front/dashboard.html` "X-Api-Key".
- AD-33 (inherited) API errors are plain HTTP statuses: a JSON `{"error": text}` body only for key problems and for unreadable or invalid write bodies (`error` and `format_first_error`), everything else an empty or framework-default response; there is no error envelope, error code or request id. Why: API clients are scripts that branch on status codes (stated: `templates/docs/api.md` "SITE_NAME uses HTTP status codes wherever possible"). Evidence: `hc/api/decorators.py` `error`; `hc/api/views.py` `format_first_error`.
- AD-34 (inherited) The application does not throttle Management API calls: no middleware, decorator or `TokenBucket` guard sits in front of them, although the documentation tells callers to stay under 100 requests a minute; `TokenBucket` guards login, sudo, invitation, TOTP and outbound-message paths. Why: request-rate control is not built into the application, so the operator's reverse proxy is the only place to add it (inferred). Evidence: `hc/api/models.py` `TokenBucket`; `templates/docs/api.md` "Rate Limits".
- AD-35 (inherited) The read-only API key is the only credential for outside tools that read a project: the Prometheus scrape (`PROMETHEUS_ENABLED`, `for_api_key(accept_rw=False, accept_ro=True)`), the bundled `/tv/` page and the documented cloning example use it, and the documentation lists third-party dashboards for the same API; there is no separate viewer token, per-user token, OAuth or key scope. Why: integrators are told to use a read-only key, never a read-write one, for tools that only read (stated: `templates/docs/configuring_prometheus.md` "Make sure to use a"). Evidence: `hc/integrations/prometheus/views.py` `metrics`; `templates/front/dashboard.html` "X-Api-Key"; `templates/docs/cloning_checks.md` "SOURCE_PROJECT_READONLY_KEY".

Why: the documentation workflow is stated for every page (stated: `CONTRIBUTING.md` "Adding Documentation"). Evidence: `templates/docs/api.md` "API Endpoints"; `templates/docs/apiv1.md` "List Project's Badges"; `hc/front/views.py` `_replace_placeholders`.
