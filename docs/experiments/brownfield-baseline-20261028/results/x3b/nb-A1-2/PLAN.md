## Summary

The request extends one existing route, and almost everything it needs already exists, so the plan keeps the repository's structure and adds only what the request adds. The listener in `src/server.js` already builds a URL for each request but never reads its query (R-1); the in-memory store is read through `listUsers` (AD-6); `send` writes every answer and every error (AD-4); and `src/paginate.js` is the repository's paging helper, which no source file calls yet. The helper cannot be reused as it is: it rounds the page count down (the conflict recorded in R-5), so the three stored users at the default size 10 would answer `pages` 0 and no items, against S4 and S5; and its result is pinned to exactly `page`, `pages` and `items` by a strict-equality test, so `size` and `total` cannot be added inside it without breaking S8. The plan therefore makes three increments. W1 changes the helper's page count to round up and leaves its result shape, argument checks and tests alone (AD-13, changes AD-12). W2 adds the `name` filter to the GET /users branch, plain text and ignoring case, while the answer stays the bare array (AD-15). W3 reads and validates `page` and `size` (digits only; `page` at least 1; `size` 1 to 100; a bad value answers 400 with a constant `error` sentence, AD-14 which changes AD-5, and AD-16) and, whenever either is given, answers `{ page, size, total, pages, items }` built from the corrected helper (AD-17). Every other inherited decision stays (AD-1 to AD-4, AD-6 to AD-11): no dependency, file, module, store, setting, identity, background work or try/catch is added, and the edits are confined to `src/paginate.js`, `src/server.js` and additions to the matching existing test files, so the seven existing tests stay exactly as they are (S8, S9). The decisions are recorded in `docs/shiploop/architecture.md` (AD-13 to AD-17 accepted; AD-5 and AD-12 moved to Superseded) and R-1, R-3 and R-5 in `docs/shiploop/spec.md` gain their Basis. What the plan relies on was re-verified against the source (`src/server.js`, `src/users.js`, `src/paginate.js`, the four test files, `package.json`, `README.md`): the code matches the committed baseline.

## Decisions

- AD-1 (inherited) No dependencies: only built-ins (node:http, node:test, node:assert/strict, the global fetch and URL). Evidence: `package.json` `description`; `src/server.js` `node:http`. Why: S1 states "no npm dependencies"; the new code needs only `URL.searchParams` and string and Math built-ins. Alternatives: a router, query-parser or validation library (rejected, each adds a dependency). Basis: none
- AD-2 (inherited) CommonJS in strict mode, one `module.exports` object per file, built-ins with the `node:` prefix and local files by relative path. Evidence: `package.json` `type`; `src/users.js` `module.exports`. Why: new code follows it; `src/server.js` gains one relative require of `./paginate` (a leaf, so no import cycle) and still exports only `createServer`. Alternatives: none, kept. Basis: none
- AD-3 (inherited) Routing is hand-written inside the one listener that `createServer` builds: a route is a branch on method and pathname, the list an exact comparison and one user an anchored digits pattern. Evidence: `src/server.js` `createServer`. Why: the request extends one existing route, so GET /users stays that branch and GET /users/:id stays untouched (S7). Alternatives: a router or framework (adds a dependency); a module per route (nothing else needs it). Basis: none
- AD-4 (inherited) One helper `send` writes every answer as JSON with only the JSON content type; an error answer is an object whose only property is `error`, holding a constant text. Evidence: `src/server.js` `send`. Why: the array, the paged object and the 400 all go through it unchanged. Alternatives: none, kept. Basis: none
- AD-6 (inherited) State is the module-level `USERS` array in `src/users.js`, read only through `getUser` and `listUsers` (a new list of the stored records) and never written. Evidence: `src/users.js` `USERS`, `listUsers`. Why: filtering and paging work on the list `listUsers` returns and write nothing; the store gains no user and no function, and `test/users.test.js` pins the count at 3 (R-4). Alternatives: a store-level search function (the home I would prefer, see Assumptions). Basis: none
- AD-7 (inherited) The only configuration is `PORT`, read once in the program-entry block with a fallback of 3000. Evidence: `src/server.js` `require.main`. Why: the default page and size and the size limit are constants in code; no variable, option or file is added, and loading the server still reads no environment. Alternatives: limits set by environment (nothing asks for it). Basis: none
- AD-8 (inherited) `createServer` returns a server that is not listening; tests start it on an ephemeral 127.0.0.1 port, call it with the global fetch and close it in a finally block; nothing is mocked. Evidence: `test/server.test.js` `withServer`. Why: the new HTTP behaviour is proved the same way, reusing `withServer` in `test/server.test.js`. Alternatives: fake request objects (the repository never mocks). Basis: none
- AD-9 (inherited) Tests use node:test with node:assert/strict; one test file per source module, named after it; tests named as sentences; `npm test` is the runner's own file discovery. Evidence: `package.json` `scripts`; `test/users.test.js` "listUsers returns every user". Why: new tests are added as new tests to `test/server.test.js` and `test/paginate.test.js` and never edited into existing ones, so the seven existing tests stay as they are (S8) and `npm test` runs the new ones (S9) with no new file, helper module or script. Alternatives: a new test file for the listing (needs its own copy of `withServer`, since helpers stay local to the file that uses them). Basis: none
- AD-10 (inherited) Requests are answered synchronously from memory in the listener; there are no timers, queues, workers or shutdown hooks. Evidence: `src/server.js` `createServer`. Why: filtering three users and slicing a list is immediate, so no background or async work, extra channel or failure record is added. Alternatives: none, kept. Basis: none
- AD-11 (inherited) No identity or access layer: every caller may use every route and users are returned whole, email included. Evidence: `src/server.js` `createServer`; `src/users.js` `USERS`. Why: the request adds no caller identity; the server-side safeguard for these anonymous callers is validating the query before use (AD-14, AD-16) and bounding the page size. Alternatives: none, kept. Basis: none
- AD-13 (changes AD-12) The server pages the listing with the existing `paginate` helper, and the helper's page count rounds up so a trailing partial page counts; its result stays exactly `{ page, pages, items }` and the server adds `size` and `total` itself; the text helpers stay standalone and unused. Evidence (the old AD-12): `src/paginate.js` `paginate`; `test/paginate.test.js` "paginate returns the requested page of an evenly divided list". Why: S4 puts the first `size` matches on page 1 and S5 defines `pages` as the pages the matches fill, but the helper rounds down, so the three stored users at the default size 10 would answer `pages` 0 and no items (R-5, the conflict with `README.md:6`); one rounding expression fixes it, the existing tests (an even split, size 0) are unaffected, and the repository keeps one paging implementation. Alternatives: page inside the server and leave the helper (rebuilds a capability and leaves its defect); add `size` and `total` to the helper's result (fails the existing strict-equality test, S8); put the 100 limit in the helper (R-5 records no upper limit and no sentence asks for one). Basis: S4, S5
- AD-14 (changes AD-5) A `page` or `size` that is not valid is a second anticipated failure: HTTP 400 through `send` with `{ error }` holding constant text, one sentence per bad parameter ("page must be a whole number of at least 1", "size must be a whole number from 1 to 100"), joined when both are bad, never echoing the value; helpers still throw on bad arguments and the listener still has no try or catch, because the listener validates first and passes the helper only a finite whole number (a `page` text too large for an exact number is held at `Number.MAX_SAFE_INTEGER`), so no caller input can make a helper throw. Evidence (the old AD-5): `src/server.js` `send`, `createServer`; `src/paginate.js` `paginate`. Why: S6 asks for 400 with an `error` that says what is wrong; an unhandled throw would stop the whole process (R-3, inferred), so the check must come before the helper is called. Alternatives: let the helper's RangeError surface (stops the process); wrap the listener in try/catch with a 500 answer (changes AD-5 beyond what S6 asks); one fixed sentence for any bad value (does not say what is wrong). Basis: S6
- AD-15 (new) The name filter runs in the `/users` branch of the listener over the list `listUsers()` returns: the user's name and the query text are lower-cased and compared with `includes`, never as a regular expression; an absent or empty `name` keeps every user (every string includes the empty text); id order is kept. Why: S3 asks for plain text, ignoring case; a pattern built from caller text would read `.` and `*` as pattern characters and throw on `(`, which stops the process because nothing catches (AD-5); filtering in the listener leaves the store's two read functions as they are (AD-6). Alternatives: a new read function in `src/users.js` (the home I would prefer, see Assumptions); `RegExp` with escaped text (heavier than `includes`); locale-aware comparison (not asked). Basis: S3
- AD-16 (new) The query is read from the URL object the listener already builds (`url.searchParams`), only inside the `/users` branch: `page` and `size` count as given when present, even if empty (`has`, not truthiness); a whole number is decimal digits only, tested with an anchored pattern like the id route's `\d+`; `page` must be at least 1 and `size` from 1 to 100; the defaults (page 1, size 10) and the limit 100 are module constants in `src/server.js`; the parsing helper is private to that file; a repeated parameter uses its first value; no other parameter is read. Why: S5 and S6 make an empty value "given" and invalid (`Number('')` is 0 and a truthiness test would skip it and answer the array); `Number()` or `parseInt` alone accept `1e1`, `0x10`, ` 1 ` and read `1.5` as 1, which S6 rejects; the id pattern is the repository's own whole-number precedent (the permissive `PORT` conversion is not one to copy). Alternatives: `Number.isInteger(Number(text))` (accepts those forms); a shared query-parsing module (one caller, not built); limits read from the environment (nothing asks). Basis: S4, S5, S6, S7
- AD-17 (new) GET /users answers a JSON array (every user, or the name matches) unless `page` or `size` is given; then it answers 200 with `{ page, size, total, pages, items }`: `page` and `size` are the values used, defaults included, `total` is the matched count before paging, `pages` and `items` come from `paginate`, and a page after the last answers empty `items`, also when nothing matched (`pages` 0). Paging is stateless: each request recomputes its page, with no cursor, session or cache. Why: S5 and S7 split the two shapes on whether `page` or `size` is given; a plain request and response read from memory is the lightest channel that meets the stated behaviour. Alternatives: always the object (breaks S7); 404 or 400 beyond the last page (contradicts S5); cursors or Link headers (not asked). Basis: S5, S7

## Assumptions

- A whole number in `page` or `size` is decimal digits only: no sign, fraction, exponent, hex, spaces or empty text; leading zeros are allowed and read as the same number (`page=01` is 1), since the request names no other form.
- A repeated `page`, `size` or `name` uses its first value; percent-encoding and `+` decode as `URLSearchParams` decodes them (`name=a+b` is `a b`); the name text is not trimmed; parameter names are case-sensitive, so `Page` is another parameter and is ignored (S7).
- Ignoring case means lower-casing both sides with `toLowerCase`, with no locale rules and no accent folding.
- A `page` beyond `Number.MAX_SAFE_INTEGER` (a 400-digit text becomes `Infinity`, which would make `paginate` throw) is held at that value and answers 200 with empty `items`; S6 names no upper limit for `page`, so a 400 there would go against it.
- When both `page` and `size` are bad, one 400 names both (the two constant sentences joined with "; "); S6 only asks that `error` says what is wrong.
- Tests page the three stored users (size 1 gives 3 pages, size 2 gives 2, size 100 gives 1) and prove the limit at 100 and 101; the store is not extended because `test/users.test.js` pins its count at 3 (R-4).
- Rounding the helper's page count up is the defect fix the request needs (the recorded R-5 conflict with `README.md:6` and the doc comment); no existing test pins the old rounding and no other source calls the helper; the 100 limit lives in the listener, not in `paginate`.
- Preferred but not done (AD-6 kept): the name search would be cleaner as a read function in `src/users.js`; no sentence asks to change the store's two read functions, so the filter stays in the listener.
- Preferred but not done (AD-5 kept as to try/catch): a try/catch around the listener turning any thrown error into a JSON 500 would also cover request targets the URL parser rejects (R-3, inferred, not run); no sentence asks for it, so it stays out, and the plan only makes sure its own new code cannot throw on caller input.
- `README.md` and `package.json` stay unchanged: the README lists the modules and the test command, and `node --test` already finds new tests in the existing files.
- New code follows the baseline style: strict mode, 2-space indent, single quotes, semicolons, `const`, arrow callbacks, a doc comment above each new function.
