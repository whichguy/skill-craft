## Summary

Extend `GET /users` in `src/server.js` with a `name` filter and `page`/`size` paging, planned backward from the answer the request describes: the handler can only assemble `{page, size, total, pages, items}` once a correct pager, a name-filtered list in id order and a strict parameter check exist. Reading the repository shows the pager is already there (`src/paginate.js`, required by nothing but its own test) but it counts pages with `Math.floor`, so the last partial page vanishes and any list shorter than `size` (the default size 10 over the three stored users) reports `pages: 0` and no items; its `{page, pages, items}` return is also pinned by an existing `deepEqual` test, and it throws on bad input, which inside a request listener would end the process. W1 therefore repairs that one expression in place, and W2, which consumes it, adds the optional `name` argument to `listUsers` in `src/users.js` and, module-private in `src/server.js`, the digits-only validation (400 before `paginate` is called), the choice between the bare array and the paged object, and the `size` and `total` fields the pager does not return. There is no new module, dependency, state, store or schema; the tests are new files under `test/` so the four existing test files stay byte-identical, and `npm test` (`node --test`) discovers them without registration.

## Decisions

- AD-1 One local Node >= 20 environment, CommonJS, no dependency: `npm start` runs `node src/server.js` (port from `PORT`) and `npm test` runs `node --test`, and the server tests start `createServer()` on 127.0.0.1 port 0 and call it with the global `fetch`; current structure is `src/strings.js` (`capitalize`, `truncate`; used by no other module), `src/paginate.js` (`paginate`), `src/users.js` (`getUser`, `listUsers`) and `src/server.js` (`createServer`; requires `node:http` and `./users`), all `'use strict'` files joined by relative `require('./x')` with no prefix, package or index file; no remote runtime, hosted platform or service is reached. Why: that is the project as S1 describes it and the request is a read-only change inside it. Alternatives: a web framework or query-string package; a different test runner. Basis: S1
- AD-2 No new state, identity, store, cache or channel: user data stays in the in-memory `USERS` array owned by `src/users.js` (shape `{id, name, email}`, changed only by editing code and restarting), so there is no schema change, migration or storage policy; the only new schema is on the wire, the paged answer `{page: integer >= 1, size: integer 1..100, total: integer >= 0, pages: integer >= 0, items: user[]}` and the error `{error: string}`, both sent through the existing JSON `send`. Why: a GET computed per request is fresh as of the request and needs nothing persistent; no background or async work is added, so no failure record is needed. Alternatives: a precomputed or cached index; a persistent store; polling or push. Basis: S2
- AD-3 Home of each new responsibility: name matching is an optional `{ name }` argument of the exported `listUsers` in `src/users.js` (default every user); query parsing, validation and the answer envelope are module-private in `src/server.js`; paging stays in `src/paginate.js`; the only new import edge is `server.js` to `./paginate` (a leaf, no cycle); no module, directory or export is added and `src/strings.js` is not touched; the new private names (`DEFAULT_PAGE`, `DEFAULT_SIZE`, `MAX_SIZE`, the reader and listing functions) differ from the existing `send`, `createServer`, `http`, `getUser`, `listUsers` and `paginate`. Why: each concern stays with the module that owns its kind (store = user data, server = HTTP, paginate = paging) and the exported surface stays compatible with the existing tests and callers. Alternatives: filter inline in the server; a new `src/query.js` or `src/listing.js` for one consumer; a text helper in `src/strings.js` for one `includes`; an extra `findUsers` export. Basis: none
- AD-4 Plain-text name match: `user.name.toLowerCase().includes(name.toLowerCase())`, no regex or wildcard, no trimming or normalisation, only the `name` field (not `email`); decoding is the `url.searchParams` the handler already builds (`+` and `%20` are spaces). Why: S3 says plain text ignoring case; `includes('')` is true, so an empty `name` keeps everyone with no special case, and caller text can neither throw nor cost like a regex. Alternatives: a `RegExp` built from the input (metacharacters, `(` throws); `toLocaleLowerCase` or normalisation; searching `email` too. Basis: S3
- AD-5 Reuse `paginate` and fix its page count in place (`Math.floor` becomes `Math.ceil`), keeping the `{page, pages, items}` return, the argument order and the guards; the server adds `size` and `total` itself. Why: floor drops the last partial page and reports `pages: 0` for any list shorter than `size`, so the default size 10 over three users would answer no items, against S5; `test/paginate.test.js` compares the whole return with `deepEqual` on an evenly divided list, where floor and ceil agree, so the fix passes it while adding `size`/`total` to the return would fail it; nothing else requires `paginate`. Alternatives: re-implement paging in the server and leave a wrong helper unused; call `paginate` and recompute `pages` outside; extend its return. Basis: S5, S8
- AD-6 Validate at the HTTP boundary before `paginate` runs: a parameter is given when present (`searchParams.has`), so an empty value is given and invalid; a whole number is a string of ASCII digits only (`/^\d+$/`, then `Number`), so `-1`, `+1`, `1.5`, `1e1`, `0x10`, spaces and `''` answer 400 while `010` is 10; `page` >= 1; `size` 1..`MAX_SIZE` (100, a server constant because `paginate` is generic); `page` is capped at `Number.MAX_SAFE_INTEGER` before the call, since a digit string that long parses to `Infinity`, `paginate` throws on a non-integer and an exception inside the `http` request listener ends the process; the 400 body `{error}` names every bad parameter ("page must be a whole number of at least 1", "size must be a whole number from 1 to 100"). Why: anonymous callers control these values, S6 fixes what is valid, and the check must make every `paginate` throw unreachable. Alternatives: `Number()` or `parseInt` with `Number.isInteger` (accepts `''` as 0, `' 1'`, `1e1`, `0x10`, and `1.5` as 1); catching `paginate`'s `RangeError` (cannot enforce 100 or name the parameter); a catch-all 500 handler (hides defects). Basis: S6
- AD-7 The answer form is chosen only by the presence of `page` or `size` (even when invalid, which is a 400): otherwise the answer is today's bare array, name-filtered when `name` is given; defaults are page 1 and size 10 and the paged answer echoes the effective `page` and `size`; `total` counts after the name filter; a page past the last is a normal 200 with empty `items`; no other query parameter is read; `/users/:id` and the 404 paths are not touched. Why: S5 and the compatibility clause S7 read literally, and a client that sends neither parameter keeps getting an array. Alternatives: always answer the envelope; a version header or a new route. Basis: S5, S7
- AD-8 Tests are new files under `test/` in the existing style (`node:test`, `node:assert/strict`, `'use strict'`, CommonJS); the four existing test files stay byte-identical; the HTTP tests copy the nine-line `withServer` helper (port 0 on 127.0.0.1) instead of editing `test/server.test.js`; no helper module goes under `test/` because `node --test` would run it as a test; nothing is registered in `package.json` because `node --test` discovers new files. Why: S8's "as they are" is proven by an untouched diff and S9's "`npm test` runs them with the existing ones" holds by discovery. Alternatives: append to the existing test files; export `withServer` from a shared file; add a runner or glob script. Basis: S8, S9

## Assumptions

- The store holds exactly the three users in `src/users.js` (ids 1 to 3, listed in id order) and nothing adds users, so array order is the required id order, no sort is added, and larger-list cases are proven on `paginate` directly.
- Only `test/paginate.test.js` requires `src/paginate.js` (grep over `src/` and `test/`), so no code or test depends on the `Math.floor` behaviour; the two existing paginate tests use an evenly divided list and size 0.
- "Whole number" means plain decimal digits; leading zeros are accepted (`010` is 10) and every other spelling of a number answers 400.
- A repeated parameter uses its first occurrence (`URLSearchParams.get`), and parameter names are case-sensitive, so `PAGE` or `Name` are other parameters and are ignored.
- A `page` beyond the safe-integer range is still a whole number >= 1 and so a page past the last: the answer is 200 with empty `items` and `page` saturated at 9007199254740991.
- When both `page` and `size` are bad the single 400 message names both; its exact wording is free as long as it names the parameter and the rule.
- `name` is neither trimmed nor Unicode-normalised, so a `name` of spaces only matches names that contain spaces.
- `README.md` (its module list stays true) and `package.json` (scripts, engines) stay unchanged, so there is no documentation or configuration item; the listing needs no authentication because the project has none and the request adds none.
- This stage ran no repository code or tests; platform facts used here (`URLSearchParams` returns `''` for a bare `?page`, `+` decodes to a space, a 400-digit string parses to `Infinity`, `new URL('//', base)` throws) were checked in an isolated snippet. The last one means a request target such as `//` already escapes the listener today; that is left as it is because the request does not cover it.
