## Summary

The request adds `name` filtering and `page`/`size` paging to `GET /users` in a project that already works (Node.js 20+, no dependencies, a hand-written `node:http` listener, an in-memory three-user store, a paging helper that no code calls yet, 7 passing tests). The plan keeps the inherited decisions it relies on (AD-1 to AD-4, AD-6 to AD-11) and changes two, each on a request sentence: AD-5, errors reach callers only as a 404, gains a 400 for a bad `page` or `size` (S6); and AD-12, the paging helper stands unused, is replaced because the request needs that capability and the helper's page count is wrong for it (it rounds down, so a trailing partial page is lost and 3 users at size 10 make 0 pages, while S5 wants the pages the matches fill). The helper is therefore reused and its count fixed, not rebuilt. The work is three increments: W1 fixes the helper's page count, W2 gives the user store an optional name filter (W1 and W2 are independent), and W3 makes the `/users` handler read and validate `name`, `page` and `size`, call both and answer (after W1 and W2). Two existing tests shape the work (S8): the helper's result of exactly page, pages and items is pinned by a strict-equality test, so the handler adds `size` and `total` itself, and the store's count of 3 is pinned, so the HTTP tests page the three users with sizes 1 and 2. The 400 texts are constants that never echo the request, and `page` and `size` are validated before any helper runs because the listener catches nothing. No dependency, file, export, setting, store or background work is added. The decisions are recorded in `docs/shiploop/architecture.md` (AD-13 to AD-20 accepted; AD-5 and AD-12 moved under Superseded), and R-1, R-3 and R-5 in `docs/shiploop/spec.md` now carry their Basis.

## Work items

  - Ready when: the repository is at its baseline (commit c5b4963, clean tree) and `npm test` passes its 7 tests. Nothing else is needed.
  - Scope: `src/paginate.js` `paginate` (the page count rounds up instead of down; the argument checks and their order, the guard for a page after the last, the three-property result and the doc comment stay); `test/paginate.test.js` (new tests appended after the two existing ones, which are not edited).
  - Done when: 7 entries at size 3 give pages 3 and page 3 holds the 7th entry; 3 entries at size 10 give pages 1 and page 1 holds all 3; an empty list gives pages 0 and empty items; a page after the last gives empty items and no error; every result has exactly the properties page, pages and items; the evenly divided case still gives pages 2 as the existing test asserts.

## Decisions

- AD-1 (inherited) No dependencies beyond the runtime's built-ins (node:http, node:test, node:assert/strict, the global fetch and URL). Evidence: `package.json` `description` (no dependency fields); `src/server.js` `node:http`. Why: rules out a router, a query-string library or a validation library; the query is read from the URL object the listener already builds (S1). Alternatives: none, kept. Basis: none.
- AD-2 (inherited) CommonJS modules in strict mode, one `module.exports` per file, `node:` prefix for built-ins, style kept by hand (2-space indent, single quotes, semicolons, a doc comment on each export). Evidence: `package.json` `type`; `src/users.js` `module.exports`. Why: new code matches it, and `src/server.js` still exports only `createServer`. Alternatives: none, kept. Basis: none.
- AD-3 (inherited) Hand-written routing inside the one listener that `createServer` builds, each route a branch. Evidence: `src/server.js` `createServer`. Why: the `/users` branch is extended in place and the `/users/:id` branch is not touched, so S7's "unchanged" holds by construction. Alternatives: none, kept (a router would be a new dependency). Basis: none.
- AD-4 (inherited) Every answer goes through `send`; an error answer is an object whose single property `error` holds a constant text. Evidence: `src/server.js` `send`. Why: the new 400 answers use it unchanged. Alternatives: none, kept. Basis: none.
- AD-6 (inherited) State is the module-level `USERS` array, read only through `getUser` and `listUsers`; nothing writes it. Evidence: `src/users.js` `USERS`; `test/users.test.js` "listUsers returns every user" (pins 3). Why: the filter reads through `listUsers`, and no user is added because the pinned count would fail (S8). Alternatives: none, kept. Basis: none.
- AD-7 (inherited) The only configuration is PORT, read once in the `require.main` block; `createServer` takes no options. Evidence: `src/server.js` `require.main`. Why: the default size, the largest size and the largest page are code constants that S5 and S6 fix, not settings, and `npm start` is untouched (S1). Alternatives: none, kept. Basis: none.
- AD-8 (inherited) Building and listening are separate steps; tests call a real server on an ephemeral 127.0.0.1 port with fetch and close it in a `finally`. Evidence: `test/server.test.js` `withServer`. Why: the new HTTP tests use it. Alternatives: none, kept. Basis: none.
- AD-9 (inherited) The runtime's built-in test runner with strict assertions, `node --test` file discovery with no configuration, one test file per module named after it, test names that are sentences. Evidence: `package.json` `scripts`; `test/users.test.js` "listUsers returns every user". Why: `npm test` finds the new tests without a change (S9); AD-20 says where they go. Alternatives: none, kept. Basis: none.
- AD-10 (inherited) Requests are answered synchronously from memory in the listener; there is no background work. Evidence: `src/server.js` `createServer`. Why: nothing asynchronous is added, so no background or async failure needs a record, and the one channel stays request and response, the lightest hop for fixed data. Alternatives: none, kept. Basis: none.
- AD-11 (inherited) No identity or access layer; every caller gets whole records, email included. Evidence: `src/server.js` `createServer`; `src/users.js` `USERS`. Why: the new parameters change what a caller selects, not who may call, and the records are fixed example data, so nothing is added; the safeguard on this anonymous input is the validation in AD-13 and AD-18. Alternatives: none, kept. Basis: none.
- AD-13 (changes AD-5) HTTP errors reach callers as the `error` answer for two anticipated cases: not found, 404 as before, and an invalid `page` or `size`, 400 with a constant text that names the parameter and its rule and never the supplied value; helpers still signal bad arguments by throwing and the listener still has no try or catch, so the handler checks `page` and `size` before it calls any helper and no request can reach a thrown error. Why: S6 asks for a 400 with an `error` that says what is wrong; constant texts keep R-3's property that no part of the request is echoed; checking first keeps anonymous input from stopping the process (a digit string of more than 309 digits parses to Infinity, which `paginate` rejects by throwing). Alternatives: a catch around the handler mapping helper exceptions to 400 (hides real faults and alters every route); echoing the bad value (breaks no-echo); a non-JSON body (breaks AD-4). Basis: S6.
- AD-14 (changes AD-12) The paging helper stays a pure, argument-checking function whose result is exactly page, pages and items (the list length and the size are not in it, and a strict-equality test pins that), but its page count rounds up: a trailing partial page is counted and returned, a short non-empty list fills one page, an empty list has 0 pages; the `/users` handler becomes its caller (AD-15) and the text helpers stay unused by the server. Why: S5 defines `pages` as how many pages the matches fill, 0 when none matched, and S4 puts the first `size` on page 1, while the baseline helper rounds down, so 3 users at size 2 lose user 3 and at size 10 make 0 pages (R-5); the existing test fixes the result shape, so only the count changes. Alternatives: leave the helper alone and slice inside the handler (rebuilds a capability the repository has and leaves a helper that returns wrong counts); add `size` and `total` to its result (fails `test/paginate.test.js` "paginate returns the requested page of an evenly divided list"). Basis: S5.
- AD-15 (new) The `/users` handler filters first with `listUsers(name)`; when neither `page` nor `size` is given it answers the filtered array, otherwise it calls `paginate(matched, page, size)` and answers `{ page, size, total, pages, items }` with `total` the number matched and `size` the size used, 10 when only `page` is given and page 1 when only `size` is given. The answer is an HTTP shape only: nothing is stored, so no schema, key, version or migration. Why: S4, S5 and S7 fix the shapes, and the handler holds `size` and `total` because the helper's result is pinned. Alternatives: build the object in `src/users.js` (puts an HTTP shape in the data module); page by hand (rebuild). Basis: S4, S5, S7.
- AD-16 (new) Name matching lives in the user store: `listUsers(name)` takes optional text (default empty) and returns a new list of the stored users whose name contains it, comparing both sides lower-cased with `toLowerCase` and `includes`, so it is plain text and never a pattern, in stored (id) order; empty text returns every user; a non-string throws a TypeError as the other helpers do. Why: S3; the store owns the data and its read functions (AD-6), `listUsers()` and its pinned test are unchanged, no export is added, and the rule is testable without HTTP. Alternatives: filter in the handler over `listUsers()` (a data rule in the HTTP layer, testable only over HTTP); a second export `searchUsers` (two read functions for one list); a regular expression built from the text (S3 says plain text, and unescaped input can throw and stop the process); `localeCompare` or `Intl.Collator` (also folds accents, S3 says case only). Basis: S3.
- AD-17 (new) The handler reads `name`, `page` and `size` from `searchParams` of the URL the listener already builds, and nothing else from the query; a parameter is given when its key is present (`has`), so `?page=` and a bare `?page` are given and invalid; the first value of a repeated key counts; the `/users/:id` branch never reads the query. Why: S4 to S7; "an empty one included" in S6 needs presence, not truthiness; `URLSearchParams` does not throw on odd escapes (checked: `%zz` is kept as text). Alternatives: truthiness of `get` (treats empty as absent, against S6); `node:querystring` (legacy, arrays for repeated keys); splitting `req.url` by hand (rebuilds URL). Basis: S6, S7.
- AD-18 (new) `page` and `size` are valid only as digit strings (anchored `^\d+$`, the pattern of the id route) read with `Number`: `page` from 1 to the largest safe integer, `size` from 1 to 100; the default size 10, the largest size 100 and the largest page are named constants in `src/server.js`; anything else is a 400 (AD-13). Why: S6 "whole number" and its bounds; digits-only rejects the sign, decimal point, exponent, hex and spaces that `Number` alone would accept, the size bound limits output, and the safe-integer cap keeps the echoed page exact and Infinity away from `paginate`. Alternatives: `Number` or `parseInt` alone (accept `1e1`, `0x10`, ` 2`, `5abc`); no upper bound on `page` (Infinity throws, huge values echo rounded). Basis: S5, S6.
- AD-19 (new) One execution environment, the local Node.js 20+ process (`npm start`, or `node --test` in process on 127.0.0.1); no remote runtime, hosted platform or service is reached. Home and visibility of each new responsibility: name matching in `src/users.js` through the existing export `listUsers`; the page count in `src/paginate.js` through the existing export `paginate`; reading, validating and answering in `src/server.js` as module-private names (`module.exports` stays `{ createServer }`) plus one new import, `require('./paginate')` (relative, no cycle, the helper imports nothing); no new file, directory, package, export or setting, so no name collides (the new private names are checked against `http`, `getUser`, `listUsers`, `send` and `createServer`); no server state, identity, store, job or live channel is added. Why: S1, and the simplest structure that meets S2. Alternatives: a separate query-parsing module (one caller, hypothetical reuse). Basis: S1, S2.
- AD-20 (new) New tests are appended to the matching existing files (`test/paginate.test.js`, `test/users.test.js`, `test/server.test.js`), named as sentences, using the server file's `withServer`, and no existing test case is edited; the store stays at three users, so HTTP tests page them with sizes 1 and 2 (3 users at size 2 put user 3 on page 2) and uneven or long lists are tested on the helper. Why: S8 pins the old tests and the count of 3; S9 asks for node:test tests under `test/` that `npm test` finds, which the existing discovery does. Alternatives: new test files (copy `withServer` and break one file per module); adding users to the store (fails "listUsers returns every user"). Basis: S8, S9.

## Assumptions

- The stored order is the id order (ids 1, 2, 3 ascend and nothing sorts, R-4), so "in id order" needs no sort; the tests assert ascending ids.
- A "whole number" is a string of decimal digits only (no sign, decimal point, exponent, hex or spaces), and leading zeros read as the same number, as `/users/01` does (R-2).
- A `page` above 9007199254740991 is answered 400 instead of an empty page, the one place the plan departs from a literal reading of S6, because a long enough digit string parses to Infinity and `paginate` would throw inside a listener that catches nothing; the effect is limited to absurd values and the 400 text is the page text.
- When both `page` and `size` are invalid the one 400 text names both, `page` first; error texts are constants and never echo the value (R-3, R-9).
- Query names are case-sensitive, a repeated name uses its first value, and `name` is matched as typed (no trimming, no normalization beyond `toLowerCase`) with no length limit beyond the runtime's own request-line limit.
- Appending new test cases to the existing test files leaves the existing tests "as they are" (S8): no existing case is edited, which `git diff` shows as no removed line.
- The baseline conflict in R-5 (round-down count against the README's "split a list into pages") is settled by S5, so the helper's old count is a defect to fix, not behaviour to preserve; if the owner wants the helper untouched, the fallback is to slice in the handler, which changes only W1 and W3.
- Preferred alternative not taken for inherited AD-5: a try or catch around the handler answering a JSON error, which would also close the baseline hazard that a request target the URL parser rejects stops the process (R-3, inferred, not run); no request sentence asks for it, so it is left as it is.
- The README lists modules only and documents no route or parameter (spec, repository records), so it and `package.json` stay unchanged.
- HEAD, other methods, other paths, a trailing slash on `/users` and the `/users/:id` route keep their baseline answers (R-1 to R-3) because those branches are not edited; `total` counts the users that matched `name` before paging.
