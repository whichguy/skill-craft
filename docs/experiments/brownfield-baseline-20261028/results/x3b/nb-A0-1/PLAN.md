## Summary

Planned backward from the HTTP outcomes (S3-S7) to their producers, the feature is composed from the three modules that already own the matching responsibilities, adding no dependency, module, directory, stored data or server state. `src/users.js` (the store) gains the `name` filter as an optional argument of its existing `listUsers`. `src/paginate.js` (the page splitter the README lists, which no source file calls yet) is reused for the page slice and page count after a one-expression correction: it counts pages with `Math.floor`, so it drops a partly filled last page (with the 3 seeded users the default size 10 answers pages 0 and empty items, and size 2 loses user 3), and its only test uses an evenly divided list, which hides the defect. `src/server.js` gains private query parsing, strict 400 validation and the two response shapes, confined to the `GET /users` list branch so `/users/:id`, the 404 fallthrough and the `npm start` block stay as they are. W1 (paginate) and W2 (name filter) are independent leaf changes; W3 (server) consumes both and owns the HTTP-visible outcomes. Each item adds its own new `test/<module>-<topic>.test.js` file, leaves the four existing test files unmodified and ends with `npm test` passing (S8, S9); S1 is a constraint on all three (no dependency added, PORT handling untouched).

## Decisions

AD-1 Run as one local Node.js process (>= 20, CommonJS, `'use strict'`) on the existing `node:http` server and in-memory `USERS` array, stateless per request, with no new dependency, module, directory, stored data, server state, identity, store or channel; the user record `{ id, name, email }` is unchanged and nothing outside the process is reached. Why: S1 forbids dependencies and the listing is a pure read of 3 in-memory records, so offset paging computed per request meets every requirement. Alternatives: cursor tokens or a page cache (state no sentence needs), a web framework or query/validation library (S1), a new `src/listing.js` for a single consumer. Basis: S1

AD-2 Homes and visibility of the new responsibilities: page slice and count stay in `src/paginate.js` (public `paginate`, name and signature unchanged); name matching is a private predicate in `src/users.js` behind the existing public `listUsers`; query parsing, the limits (default size 10, maximum 100) and envelope assembly are private to `src/server.js`; exports remain `{ paginate }`, `{ getUser, listUsers }` and `{ createServer }`, and the only new import edge is `server.js` to `./paginate` (the graph stays acyclic: server to users and paginate, both leaves). Candidate private names (`matchesName`; `DEFAULT_SIZE`, `MAX_SIZE`, `parseWhole`, `readPaging`) collide with none of `USERS`, `getUser`, `listUsers`, `http`, `send`, `createServer`, `paginate`. Why: each responsibility goes beside its siblings (user queries in the store, the HTTP contract's limits in the HTTP layer, page arithmetic in the page helper), and adding no export leaves existing importers and tests unaffected. Alternatives: a `src/query.js` for parsing and a `containsIgnoreCase` in `src/strings.js` (one consumer each, speculative), the 100 cap inside `paginate` (turns an HTTP policy into a change of a generic helper's contract). Basis: S7, S8

AD-3 Reuse `paginate` for the slice and the page count and change its `pages` from `Math.floor(items.length / size)` to `Math.ceil(items.length / size)`; the server adds `size` and `total` itself. Why: the helper is the project's page splitter with the right argument checks, but the floor drops a partly filled last page (3 users at the default size 10 give pages 0 and empty items for `?page=1`; size 2 gives pages 1 and loses user 3), contradicting S5 ("how many pages they fill") and S4; its only test covers an evenly divided list and a bad size, so `test/paginate.test.js` passes as is, and nothing else calls the helper (checked by grep), so only results for lists that do not divide evenly change. Alternatives: leave `paginate` alone and compute slice and pages in the server (duplicates the helper and leaves the defect for the next caller), keep the floor and add 1 in the server (the last partial page's items would still come back empty). Basis: S4, S5

AD-4 Put the name filter in the store as an optional `{ name }` argument of `listUsers`, matching with `user.name.toLowerCase().includes(name.toLowerCase())`; an absent, null or empty `name` means no filter and `listUsers()` behaves as today. Why: user queries live in `src/users.js` beside `getUser` and `listUsers`, so the rule is unit-testable without HTTP; `includes` is plain-text containment (no RegExp, so `.`, `(` and `*` are ordinary characters) and the locale-independent `toLowerCase` ignores case; the filter and the page slice both preserve the store's id order. Alternatives: filter in `server.js` (a domain rule in the transport layer), a second export `findUsers` (two listing entry points), a RegExp with the `i` flag (needs escaping of input), a `strings.js` helper (single consumer). Basis: S3

AD-5 Read `page` and `size` only through the request's `URLSearchParams`: a parameter is given when `has(...)` is true, empty included; its text must be a run of ASCII digits (`/^\d+$/`), is converted with `Number`, then range-checked (`page` finite and >= 1, `size` 1 to 100); the default (page 1, size 10) fills only the absent one. Why: S6 makes an empty value invalid, and `Number()` would take `''` as 0 and accept `' 1'`, `'1e1'`, `'0x10'` and `'1.0'`, while `parseInt` accepts `'1abc'`; a digits-only grammar is the narrowest reading of "whole number". Alternatives: `Number` plus `Number.isInteger` (accepts exponent, hex and whitespace forms), `parseInt` (accepts trailing junk), a validation library (S1). Basis: S6

AD-6 Choose the response shape by whether `page` or `size` is in the query: neither gives the plain array from `listUsers({ name })` (so `name` alone still answers an array); either gives the object `{ page, size, total, pages, items }` with exactly those five keys: `page` integer >= 1 and `size` integer 1 to 100 (effective values, defaults applied), `total` integer >= 0 (users matching `name`), `pages` integer >= 0 (`Math.ceil(total / size)`, taken from `paginate`), `items` the unchanged `{ id, name, email }` records, at most `size` of them in id order; a page past the last answers 200 with `items: []`. It is a response shape only, so nothing is stored, versioned or migrated. Why: S5 and S7 together require both shapes at one URL, told apart by the presence of the paging parameters. Alternatives: always an object (breaks S7), an object whenever `name` is present (breaks S7), a versioned route such as `/v2/users` or paging headers (not requested, new surface). Basis: S5, S7

AD-7 Confine the `src/server.js` change to the `GET /users` list branch: parsing, validation and both response shapes live only there, while the `/users/:id` branch, the 404 fallthrough, `send`, the `require.main === module` start block and `module.exports = { createServer }` stay as they are. Why: `GET /users/:id` must be unchanged and today ignores its query string, so `/users/1?page=abc` must keep answering the user rather than 400; the start block is what `npm start` runs with PORT. Alternatives: validate the paging parameters at the top of the handler for every route (changes `:id` and 404 behaviour). Basis: S7

AD-8 Safeguards on the anonymous input: validation runs before filtering and before any call that can throw, so no request value reaches `paginate` unchecked; `size` <= 100 bounds the work and body of one response; a `page` that is not finite (roughly 309+ digits becomes Infinity) answers 400; `name` is only ever compared with `includes`, never compiled into a pattern; no authentication, rate limit or logging is added and the handler stays synchronous, so no background or async failure exists to record. Why: an exception thrown inside the `http.createServer` listener (for example `paginate` rejecting Infinity) ends the Node process, so one bad GET would take the server down; the endpoint is already anonymous and read-only. Alternatives: catch `paginate`'s `RangeError` and map it to 400 (its rules differ: no cap, exceptions as control flow), a try/catch around the whole handler answering 500 (unrequested and hides defects), authentication or rate limiting (not requested). Basis: S6

AD-9 Add tests only as new files `test/paginate-last-page.test.js` (W1), `test/users-filter.test.js` (W2) and `test/server-listing.test.js` (W3), named `<module>-<topic>.test.js` beside the existing `<module>.test.js`; leave the four existing test files unmodified; the new server test carries its own copy of the 8-line `withServer` helper (server on port 0 of 127.0.0.1, closed in `finally`) and imports `../src/<module>` as the existing tests do. Why: S8 says the existing tests pass "as they are"; `node --test` executes every `.js` file under `test/`, so a shared helper module there would itself be run as a test file, and `withServer` is not exported from `server.test.js`; files named `*.test.js` under `test/` are found by the unchanged `npm test` (S9). Alternatives: append to the existing test files (edits tests the request leaves as they are), a shared `test/helpers.js` (run as a test file), a runner or `package.json` script change. Basis: S8, S9

## Assumptions

- A "given" parameter is one present in the query string with any value, empty included (`?page=`, `?size`, `?page=&size=5`): it takes the validated path and answers 400 (S6), never the compatibility array; `name` absent, `?name` and `?name=` all keep every user.
- A whole number is a run of ASCII digits; leading zeros are accepted (`007` is 7); signs, spaces, decimals (`1.0`), exponents (`1e1`), hex and non-ASCII digits answer 400.
- A `page` too long to be a finite number (roughly 309+ digits becomes Infinity) is the one whole number the server cannot hold, so it answers 400 rather than reach `paginate`, which would throw inside the request listener and end the process; every finite page past the last answers 200 with empty `items`.
- A repeated parameter uses its first value (`URLSearchParams.get`); parameter names are case-sensitive, so `PAGE=0` is an unknown parameter and ignored; when both `page` and `size` are bad, the `page` error is reported (one error per response).
- Error wording is free provided `error` is a non-empty string naming the parameter and its rule (planned: `page must be a whole number of at least 1` and `size must be a whole number from 1 to 100`); tests assert the 400 status, a JSON body and that the message names the parameter, not the exact sentence.
- `name` is compared as given after `toLowerCase()` on both sides: no trimming and no Unicode normalisation, and `+` and `%20` in the query decode to spaces as for any query value.
- Listing order is the store's order (ascending id), which the filter and the page slice preserve; no re-sort is added.
- Tests use the 3 seeded users (size 1 gives three pages and size 2 a partly filled last page); no store-injection hook or reset API is added.
- No authentication, rate limiting or logging is added (the endpoint is already anonymous and read-only and the request asks for none).
- `README.md`, `package.json`, `.gitignore` and `src/strings.js` do not change: the README lists modules and none is added or removed, and `node --test` already discovers every `.js` file under `test/`.
- New code follows the surrounding style: `'use strict'`, CommonJS, single quotes, semicolons, two-space indent, a one-line `/** */` comment per function.
