1. ANSWER
---------------------------------------------------------------------

Yes. The script can own a stop point, with one split.

- Stage, visit and work-item boundaries (stop after a stage is accepted; the Nth acceptance of it; for a named work item) can be script-owned and exactly deterministic. This is the "first test-spec accept" case.
  - A prototype built from the real navigator functions paused the run inside the accepting transition.
  - The run then resumed cleanly at the next stage (section 5.3, lab_stop_proto.out).
- Iterations inside an Until Loop child (Improve review pass N, Backchain pass N, quality-loop iteration N) cannot be script-owned in the current architecture (section 6.3).
  - The loop runs in the vendored runtime. ShipLoop is not called between passes.
  - They need a runtime change, a SPEC decision, or harness polling.
  - I recommend not doing this in v1.

The crux (the model starts ShipLoop, so the harness cannot pass a flag) has three workable resolutions.
- Recommended: after the run directory appears, the harness runs a new script verb `stop-at --set` itself. This is host-independent. It also serves the "continue later" case.
- Second choice: a creation-time environment variable recorded in state.md. It reaches the model's tool shell on all three hosts (section 3).
- Reject: a file in the work directory, or text in the case prompt.

A stopped run is not a failure and not a pass of the full case. It needs a "partial run" grading rule and a SPEC amendment in its own commit first (section 7).

5. THE ENGINE DESIGN
---------------------------------------------------------------------

5.1 What exists [M, shiploop_navigator.py]
- _STATUSES = active, paused, blocked, halted, done.
- control(state, "pause"|"resume"|"halt") is the one function that returns a new state for each.
  - A pause needs status_reason and refuses housekeeping words (_HOUSEKEEPING_PAUSE).
  - A resume of a plain pause clears status_reason.
- The active packet prints "Pause without consuming the action: <callback pause --reason ...>".
- Packets for paused, blocked, awaiting, halted and done print whole, up to PRINT_LIMIT.
- Optional state keys already exist: status_reason, delivery_contract_version, chain_bindings, delegation_hold. They are exempt from the "missing" check in _validate_current_state. A new key can join them.
- Today's validate() refuses an unknown `stop_at` key: "unexpected: stop_at". [M, lab]
- Option plumbing precedent: backchain_passes (a89135f7) and lint, delegation. Each is a flag on init and workspace start, a retry guard (_require_retry_*), a state key, and docs. Lint and delegation also have a `--set` verb.
- _knowledge_close and _item_commit already key on the history rows added by a transition (rows = after["history"][len(before["history"]):]). That is the same signal a stop point needs.

5.2 Proposed state and grammar
- New OPTIONAL key `stop_at` in state.md:
  {"after": "<stage>", "nth": 1, "item": null, "set_revision": N, "set_by": "...", "reached": {"revision": R, "action": "...", "visit": V}}
- The key is absent when unused, so saved runs keep loading. This is the delegation_hold pattern, not a migration.
- An older ShipLoop refuses a run carrying the key, which fits the one-supported-version rule.
- CLI grammar: --stop-after <stage>[#n][@item], for example test-spec, test-spec#2, carry-forward@W1.
- Stage names come from stage_spec. The final stage `handoff` is refused.
- The setter refuses an unknown stage, nth < 1, a bad item id, a terminal run, and a point already behind the run ("test-spec was accepted at revision N"). A late set is an error, never a silent miss.

5.3 Where it fires
- Best choke point: wrap _apply_result. Both `apply` for non-Improve stages and `finish_improve` go through it.
  - Call the inner function, then compare history rows: if a new done row matches the spec, the state becomes paused in that same transition.
  - The graph dry-run oracle calls apply and finish_improve, so it exercises stop points for free.
  - A replay of an accepted action returns early and never refires. A model's retried `complete` after the stop just gets the stop packet again.
- Prototype [M, lab_stop_proto.py, using the real navigator.apply, finish_improve, control and save; nothing in the repo edited]. Log for `after test-spec`:
  - complete at step-plan: 0 new rows, active_improve parked
  - improve-complete at step-plan: 1 row
  - complete at test-spec: 0 rows, parked
  - improve-complete at test-spec: 1 row, status paused
  - Final state: paused at `baseline`, revision 16 (accept and pause are two revisions).
  - hook-status reported status paused with the reason. `resume` gave an active baseline packet at revision 17.
  - This shows an Improve-reviewed stage is accepted at improve-complete, not at complete. The stop must key on the history row.
- Knowledge and item commits run after save and key on rows. A stop leaves the repo exactly as a normal run would at that moment. [M, code]
- Side facts:
  - NA-recorded test stages write synthetic done rows (_record_not_applicable_tests). They count as rows, so `after test-red` can fire on one.
  - One transition can add several rows. The hook fires once.

5.4 One-shot and the stop packet
- `reached` is stored in the same transition, so the stop is inert afterwards. `resume` needs no change and the audit record stays in state.md.
- Render the stop packet only when status == paused and stop_at.reached.revision == state.revision. A later generic pause then renders normally.
- The stop packet goes FIRST and stays short: "stopped at the requested stop point: after X accepted; paused on purpose for testing; nothing failed. Do not resume or run any ShipLoop command. End your turn now."
- Do not put the resume command in the printed head. It stays in the packet file and in `status`.
- Active packets stay byte-identical with or without a stop point. This follows the backchain_passes precedent, and it keeps the measured run identical.
  - The stop shows only in `status`, progress.html, state.md and the stop packet.
  - Open owner choice: show it to the user in packet heads, at some cost to measurement purity.
- Use `paused`, not a new status, so the exporter, hook_status, keepalive and termination code need no change.
- Do not use `halt`. It is irreversible.

5.5 Verb and flags
- Flags: --stop-after on init and workspace start, with a retry guard like lint's.
- Verb: `stop-at --run-dir R --set <spec> | --clear [--reason ...]`, the lint-mode and delegation shape.
- The verb is needed for continuation (a next stop after `resume`) and for the harness route in section 6.
- Touch list, from the backchain_passes precedent: shiploop_navigator.py (state key, new_state, validation, setter, wrapper, render, status_block), shiploop_protocol.py (flags, verb, retry guard), shiploop_status_hook.py (PACKET_VERBS), shiploop_navigator_dry_run.py, README, SKILL.md, references/navigator.md, references/state-files.md, and a changes/shiploop note (minor).

5.6 Stage versus iteration (the real limit)
- Script-owned and deterministic:
  - after a stage is accepted;
  - the Nth acceptance, which covers revise redos and per-item repeats;
  - after a stage for work item Wk;
  - stop at the Improve checkpoint, meaning the producer result is submitted and the review has not started. This is a possible later `review:<stage>` form. The prototype shows the parked state (0 rows, active_improve set).
- Not script-owned: passes inside an Until Loop child.
  - The runtime (skills/improve/runtime/until-loop/scripts/until_loop_ephemeral.py) owns the pass counter (`action_number`), terminal conditions and receipts.
  - ShipLoop is not called between passes. Its only per-pass touchpoints are the model's optional `improve-commit` and a read-only receipt read in hook_status.
  - The loop's terminal statuses are complete and stopped, and a stop comes only from a model-written report.
  - The vendored runtime is hash-pinned (test/improve.test.sh) and S-10 forbids an iteration cap. In the Backchain loop the host model even writes the contract (SPEC S-10 carve-out).
- Options for pass-level, none recommended for v1:
  (a) Accept the limit. Pass counts and per-pass commits are measured after the fact.
  (b) The harness watches the child receipt (progress.action_number) and runs `shiploop pause` at or after pass N. It is not deterministic, and the model keeps looping until its next ShipLoop call.
  (c) A requested-stop field in the Until Loop contract that makes `done` return a stopped packet. This needs a vendored-runtime change, an Improve skill change, a SPEC note and a reconcile mapping. It is a separate owner decision.
- S-10 text for the design: a stop point is a user stop (S-10 names it), taken only at an accepted-stage boundary after the stage's own loop finished. It is not an iteration cap and never ends a loop.

6. THE CRUX: HOW A HARNESS-LAUNCHED RUN RECEIVES A STOP POINT
---------------------------------------------------------------------

Route evaluation (reliability, honesty, S-clauses):

(a) Harness sets it by script via the new `stop-at` verb after the run directory appears. RECOMMENDED.
- Host-independent: no env or model dependence.
- The harness finds the run through grade_shiploop (rglob state.md under out/). main already finds the ShipLoop CLI as host.plugin_cli(out/"home") or plugin_dir/.../shiploop.
- Needs a tick callback in launch's 2 s loop.
- Window: the verb lands about 2 s after the run dir appears. The shortest first accept ever recorded is 11.6 s, so there is a margin of about 5x. A late set is refused by the verb and recorded as a failed stop verdict, never silent.
- Honest on both sides: state.md has stop_at, and the harness writes S-style stop-point.json (requested, how given, +seconds, revision at set, verb exit and stdout head).
- The verb takes the run lock and blocks if a complete is running tests, so run it in a thread.
- It is the same code path as continuation, and a person can use the verb too.
- Not model glue: it is outside the host event stream.

(b) Environment variable read at run creation (for example SHIPLOOP_STOP_AT), recorded in state.md with its source. VIABLE SECOND CHOICE.
- Reaches the tool shell on all three hosts (section 3.4).
- Peer prototype end to end [M-peer]: Claude and Grok models ran init, the stop fired at after:intake, and the sessions ended.
- Simplest harness change: one line in the host env dict.
- Costs:
  - It is the first graph-affecting environment input. Today's SHIPLOOP_* variables are operational: KEEPALIVE, KEEPALIVE_HOME, PROGRESS, GIT_TIMEOUT.
  - SKILL.md says "Environment settings do not change this boundary" (the ShipLoop versus launcher boundary). Re-read that before choosing.
  - It is ambient: a person's exported variable would silently stop their real runs.
  - It must be ignored on an `init` retry that finds a saved run. A retry guard must not refuse over the env.
  - Any init notice printed to the model changes the measured run.
  - The harness cannot know it worked until it reads state.md. It can detect a miss about 3 s in and fall back to (a).
- Verification before relying on it: the engine must read os.environ itself. A model-run `env` is denied by Claude and Grok classifiers.

(c) A file in the work directory read by init. REJECT.
- launch requires an empty work directory ("working directory is not empty").
- workspace start treats an empty directory as a fresh repo, and a non-empty one differently, which perturbs the probe.
- A file in the parent of the repo is an invisible convention.

(d) Text in the case prompt telling the model to pass the flag. REJECT.
- The model can mistype or omit it.
- The text pollutes the recorded request and the spec (state.md prompt is the verbatim request; init retries compare it).
- It adds model-written glue (S-4).

(e) The harness runs `workspace start --stop-after` itself, then launches the host. This is the seed_run precedent and is deterministic. GOOD for harness-started runs and continuations, but the model no longer runs the skill's own start. The seeded host prompt differs. Seeded runs are not baselines today. It does not give start-path fidelity.

(f) Interim, engine unchanged: the harness polls state.md at the 2 s tick and runs the existing `shiploop pause` verb. Weaker:
- The pause lands 0 to 2 s late, after the model has started the next stage's work.
- The refused next `complete` ("navigator is not active; resume or inspect it first") invites self-resume.
- The paused packet can be truncated (section 3.2).
- It is still better than kill-and-relaunch, and it gives metrics.
