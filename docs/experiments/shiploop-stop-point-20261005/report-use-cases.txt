0. VERDICT

Yes, the script can own a stop point, and a prototype shows it works. I built a scratch-only patch that does the following:
- **State:** it records an optional `stop` key in state.md.
- **Pause:** it pauses the run in the same saved transaction that accepts the named stage.
- **Packet:** it prints a short "end your turn" directive at the head of the paused packet.
- **Resume:** the normal `resume` verb continues the run.

No repository file was edited.

The prototype ran four ways:
- Through the real CLI, with no model.
- Through a real Improve child import.
- Against three real hosts: Claude Sonnet 5.5, Grok 4.7 and Codex gpt-6-luna. Each ended its own turn at the stop and exited 0 with no kill.
- Through a patched harness copy driving a scripted fake host. The run exited 0, wrote result.json, metrics.json and the Run Review export, and wrote no baseline row.

Crux answer: how a harness-launched run receives a stop point.
- **Environment variable:** I verified that all three hosts' tool shells inherit a variable the harness sets on the host process, using the harness's own host adapters. I recommend an environment variable (`SHIPLOOP_STOP_AT`) read when the run is created, plus a `--stop-at` flag.
- **Honesty:** state.md records the value and its source. The harness records what it asked for and whether state.md shows it took effect.
- **Rejected routes:** a file in the work directory (breaks the empty-start rule), a case-prompt flag (the model assembles it), and arming after start (a race on early stages).

Smallest slice with most of the value:
- Engine: `after:<stage>[#n]` as a creation-time option with the pause hook.
- Harness: `--stop-at`, stop-run grading, and `--resume-run` of a reached stop.

That delivers:
- Planning-only probes (a), deterministic and with metrics.
- "Plan once, re-run one later stage" (b, c) with a manual snapshot copy, same ShipLoop version only.
- Hermetic tests (e).

Iteration-level stops:
- Iterations the engine already sees (per-step implement actions, repeated stage visits) come free with `#n`.
- Improve and Backchain pass-level stops cannot be script-owned without a per-pass ShipLoop verb or a change to the hash-pinned vendored Until Loop runtime.
- I rank that last and recommend deferring it.

Three findings the owner did not ask about:
- Paused packets already lose their directive and Resume line to the print limit. This is an existing defect; section 8.
- `--continue-from` copies only work/ and `--seed-at` only seeds step-plan, so neither can serve as the "plan once" seed; section 5.
- A stopped run's state pins its own installed plugin path, which limits later-stage re-tests to the same version; section 5.

Corrections to the premises:
1. "Paused packets print whole" is true only up to 16,000 characters.
   - The directive and "Resume:" lines of a paused packet come last in `render`.
   - With the original code, a plain user pause after two accepted stages gave a 16,323-character packet.
   - The "Resume: " line starts at character 15,994, but only 15,920 characters printed (probe_pause_len.py: `printed chars: 15920 | mentions 'longer than a host': True | prints 'Resume:' line: False`).

2. `--continue-from` copies only `<prior>/work`, drops `.git/worktrees`, and ignores the ShipLoop run directory [M, run.py `continue_from`].

3. `--seed-at` accepts only step-plan [M, `SEED_STAGES`] and synthesizes every earlier result [M, `SEED_SCRIPT`]. It cannot produce the real step-plan, test-spec and baseline results that later stages need [I].

Also confirmed:
- `--resume-run` refuses a paused run ("needs an active, blocked or finished ShipLoop run") [M, run.py main()]. The test `test_resume_run_refuses_a_run_that_is_neither_active_nor_done` pins it.
- The resume loop already treats any non-active status as terminal and breaks with `resume_stop` "ShipLoop run is paused" [M]. A script-owned pause therefore ends the harness loop with no kill.
- The keepalive Stop hook allows a stop on paused, quietly [M, shiploop_keepalive.py line ~416 and references/keepalive.md decision table].

3. THE DESIGN

State:
- One optional key in state.md: `stop: {"at": "after:test-spec", "source": "<how it was given>", "reached": null}`.
- On firing, `reached` becomes the revision number of that pause. That makes it an integer.
- A later pause by a person has a different revision, so it is not mistaken for the stop. This avoids coupling to the reason text.

Grammar:
- `after:<stage>[#n]` means "when the n-th accepted `done` result of <stage> is accepted" (n defaults to 1).
- Stage names are the 34 in the graph. `handoff` is refused at parse time, because acceptance ends the run.
- `before:<stage>` is just `after:<predecessor>`. A true arrival form would also catch the revise redo (arrive at step-plan for the second time); that is slice 2.

The hook:
- One pure function, `_stopped(before, after)`, wraps the only two callers of `_apply_result`: `apply` for non-checkpoint stages and `finish_improve` for Improve-reviewed stages.
- It fires only if the transition added exactly one new history row that is `done` for the named stage, it is the n-th such row, and the run is still active afterwards.
- It produces the paused state, sets `stop.reached`, and `validate()`s it.
- Because it sits before `save()`, the acceptance stamp in timeline.json and the pause are in one transaction. Nothing can be accepted without the stop being recorded.
- A replay, a repeat, a blocked result and a revise never fire.
- Not covered: `reconcile()` (the `improve-reconcile` path) bypasses the hook. That is a known limit.

Why `paused`, not a new status:
- A sixth status would touch every consumer: the exporter's RUN_STATUS enum, keepalive, `hook-status`, the harness, and the status block.
- Existing consumers already handle paused. I showed the exporter maps paused [M, export.py `RUN_STATUS`], and `hook-status` reports it [M, probe].
- The `stop` record is what distinguishes it.

Optional key, not required:
- The precedent keys lint and backchain_passes are required, and a saved run without them is refused.
- Absence of `stop` has a defined meaning (no stop), so this is not a compatibility shim.
- Keeping it optional means no in-flight run is refused and no hand-built test state breaks.
- An older ShipLoop loading a state that has `stop` refuses it as an unexpected key, which fits "one supported version" [M, the unexpected-key check in `_validate_current_state`].

The packet:
- The directive leads the packet, right after the title line, because of the print cut above. Wording: "Stop point reached: after:X (source). The script paused this run on purpose: a requested stop for testing, not a blocker and not a question for the user. End your turn now; do not resume the run, submit a result or choose another action. Only the person who set the stop point resumes it (not you): <resume command>".
- It also adds one line at creation: "Stop point recorded: … (source)".
- Runs without a stop print byte-identical output (section 6).

SPEC clauses:
- S-1, S-2: the script pauses; the model does nothing special.
- S-6: the stop persists in state.md, and `next` reprints the directive after a context loss.
- S-9: the stop is a script-checked condition, not a model judgment.
- S-10: see section 2.
- S-14: the packet says explicitly that it is not a question. The harness resumes by verb, not a person. The existing refusal to resume a person's or a model's pause stays.
- S-13: nothing names a case or host.

Iteration-level stops, three classes:
1. Engine-visible, free with `#n`.
   - Stage visits, including repeats and revise redos, because each acceptance is a history row.
   - Per-step implement actions on the inline route: `after:implement#2` pauses exactly when the second step is accepted (probe_iteration_stop.py: `('implement','produce','paused','test-green')`, 2 accepted).
   - Limit: `#n` counts across work items, so W2's first test-spec is "#2" only if W1 had no revise. Per-item addressing is a later refinement.
   - With the ask-agent route, implement is a single action, so `#2` never fires.
2. Work-item boundaries, `after:carry-forward#1`. Same mechanism.
3. Improve and Backchain pass N, plus quality and test loop iterations inside one action.
   - ShipLoop sees no per-pass event, as shown in section 2.
   - The two options are a shim verb wrapping the runtime's `done_argv`, which changes the packet contract and adds model glue under S-4, or a change to the vendored runtime, which is hash-pinned and which the S-10 carve-out text says stays unchanged.
   - A partial option exists: pause inside `improve-commit` once the receipt's `action_number` reaches N. That covers only passes that changed files.
   - Grok's spec review had 9 passes, of which six changed the spec [M, grok-medium-improve-children.json].
   - A pass-level "accept at pass N" would be an iteration cap, which S-10 and the owner rule forbid. Only a pause that is later resumed is legitimate.
   - Not prototyped [I].

4. THE CRUX: HOW A HARNESS-LAUNCHED RUN RECEIVES A STOP POINT

Facts that frame it:
- In recorded runs the model itself runs `workspace start`. For Grok and Luna it ran `workspace start --help` first; for Claude it passed --repo and --prompt [M, events.jsonl of v1210-battleship-grok-medium, v1210-battleship-luna-xhigh, v1190-hello-sonnet]. The harness therefore cannot add a flag.
- Both `init` and `workspace start` create state in one place, `shiploop_protocol.main`'s init branch. `workspace start` forwards its flags to `init` [M].
- ShipLoop already reads ambient `SHIPLOOP_*` variables for tuning: SHIPLOOP_KEEPALIVE, SHIPLOOP_PROGRESS, SHIPLOOP_GIT_TIMEOUT [M]. None changes run semantics.

5. TESTING VALUE AND REUSE

Minutes below come from docs/experiments/shiploop-planning-time-20261005/stage-clock.md and README.md, test/shiploop_e2e/LEARNINGS.md ("Planning time"), and the a89135f7 commit message. The inputs are [M]; the trial arithmetic is [I].

Today's pain, measured:
- Three runs have no metrics.json, result.json or review-export: v1200-battleship-luna, v1210-battleship-grok-medium and v1210-battleship-luna-xhigh [M, directory listing].
- The Grok probe's polling auto-stop missed the baseline stage. Baseline was accepted 32 s after the test-spec accept (15:38:00Z to 15:38:32Z), shorter than a 2-minute poll [M, timeline.json].
- The host ran 1.8 min past the intended stop, killed in test-author [M, timeline.jsonl last stamp, state at test-author revision 21].
- Stages shorter than a poll interval cannot be hit by polling: select-work 0.3 min, baseline 0.5, prepare 0.7.

(a) Planning-only probes. Stop `after:test-spec`.
- Planning windows are Grok medium 72.7 min, Luna xhigh 375.9, and Luna max on 1.16.1 647.5.
- The tail avoided per probe is at least 212 min on Luna xhigh, which the owner cut at 588 min, and 511 min on Luna max 1.16.1 (1,158.5 total minus 647.5). For Grok medium it is unknown, because the probe was killed.
- Stage times vary about 2x between runs, so a planning change needs repeated probes. Three Luna xhigh probes cost at least 1,128 min.
- Needs only a stage-level stop.

(b) Plan once, test later stages many times. Stop `after:select-work` or later, snapshot the output directory, then resume trials.
- On Luna xhigh, step-plan to test-red is 38.7 + 39.9 + 2.9 + 14.2 + 3.5 = 99.2 min per trial, against 396.5 min cold. That saves 297.3 min per trial after the first.
- Stage-level stop is enough.

(c) Reproduce the W1 test-red revise. Stop `after:baseline`, or `after:test-author` to re-run only test-red.
- Luna xhigh: a cold trial to test-red costs 396.5 min (planning 375.9, baseline 2.9, test-author 14.2, test-red 3.5). The trial from an `after:baseline` snapshot costs 17.7 min, saving 378.8 min (95.5%).
- Three trials cost 431.9 min against 1,189.5 cold, and all share the same upstream state. That removes the 2x upstream variance.
- The revise redo cost 165.9 min of stages against 99.2 the first time. Stage-level stop is enough.

(d) Improve or Backchain pass N.
- Per-pass facts (passes changed vs unchanged, minutes) are already measurable after the fact: Luna xhigh had 22 passes, 12 that changed something (146.5 min) and 10 that changed nothing (28.2 min).
- A stop there needs the iteration-level mechanism of section 3, class 3. I cannot name a measurement that a stop at pass N would give and the existing artifacts do not.
- The right lever for the review question is the existing run-level option `--backchain-passes` and not-running Improve; that is outside this study.

(e) CI-style hermetic test of the stop itself. See section 6. Stage-level is enough, plus the `#n` check.

Ranking by value per implementation cost:
1. (c), then (b): about 95% and 75% saved per extra trial.
2. (a): a deterministic probe that also finishes cleanly.
3. (e): required for any of it.
4. (d): last.

Single smallest slice: slice 1 (section 7).

Caveats the owner needs for (b) and (c):
- **Absolute paths.** Relocating a copied run fails silently, not loudly.
  - A relocated copy of a stopped workspace run kept `repo` pointing at the original worktree. state.md, workspace.md (3 places), context-index.md, the packet files, and the worktree's `.git` gitdir link all hold absolute paths (probe_relocate.py).
  - `next` and `complete` worked on the copy even after I removed the original, because early stages do not touch the worktree. Later stages would hit the stale or aliased path (probe_relocate2.py and probe_relocate3.py). That a later stage fails is [I].
  - The safe pattern is an in-place restore: snapshot the whole output directory, restore it over the same path, then resume.
  - Verified (probe_restore_in_place.py): snapshot 0.01 s for 164 KiB, advanced to revision 5, restored to revision 3, trial 2 reached revision 4.
  - Parallel trials need distinct paths and so cannot use plain copy. Real snapshot sizes are about 100–250 MB (Grok home 98 MB plus events 20 MB, Luna xhigh home 225 MB).
- **Same plugin version only.** The harness keeps a resumed run on its original plugin install [M, main()'s resumed-same-host branch ignores `--plugin-dir`], and the state pins that install.
  - state.md holds `improve_skill` as an absolute path inside the installed plugin, plus 5 Improve result records carrying skill paths [M, the Grok run].
  - So a snapshot supports same-version trials: variance, model, effort and host comparisons, and reproducing a defect. A host switch on resume is already proven [M, LEARNINGS "temperature-report resumed on Codex"].
  - It does not validate a fix released in a newer version unless the CLI the model runs is swapped and the Improve binding re-pointed. That relaxes "a resumed run keeps its plugin", so it is an owner decision. The alternative is one snapshot per release.
- **Resume gap.** The first stage after a resume absorbs the idle gap, because stage minutes are accept-to-accept [M, README "Reading per-stage figures"; `_updated_timeline` stamps only accepts]. Resume promptly or subtract the gap. Its size is unmeasured.
- **Trials need fresh sessions.** A resumed Claude, Grok or Codex session starts without the planning conversation. That is a feature for controlled trials. Event streams append, so whole-run cost and turns accumulate; per-stage minutes stay attributable.

Use with suites:
- `run_suite` forwards unknown flags to every case [M], so `--stop-at after:test-spec` on a suite gives a planning-only breadth run.
- A follow-on case after a stop run must be skipped, since there is no product to build on. That is a to-do.

`--interrupt-at` remains separate: it kills on purpose to test recovery. `--stop-at` tests continuation after a clean stop.

6. TESTING THE STOP THROUGH THE REAL NAVIGATOR CLI

The repository's own conventions (fresh `subprocess` runs of skills/shiploop/scripts/shiploop with a scratch repo, `PYTHONDONTWRITEBYTECODE`, the dry-run's synthetic rows, the full-runtime helpers, fake hosts in shiploop-e2e.test.py) cover five layers:

   - Drive `navigator.apply`, `finish_improve`, `control` and `render` with the graph dry run's own producer and Improve rows (shiploop_navigator_dry_run.py `activity()`). No process.
   - The dry run could also take a `stop_at` scenario field; today it refuses any top-level field except `steps` [M, `run_scenario`].
2. Real CLI, fresh processes. `init --stop-at`, the environment route, `workspace start`, then `complete`, `next`, `status`, `hook-status`, `resume`, `pause`.
3. Real CLI through a checkpoint stage. A subclass of test/shiploop-full-runtime.test.py's helpers (`_begin_stage`, `_start_child`, `_receipt`, `_submit_child`, `_import_child`, `_assert_exact_replay`) so the stop fires from the real `improve-complete` import with the real vendored runtime.
4. Harness with a fake host, using the FAKE_CLAUDE pattern in test/shiploop-e2e.test.py. The fake runs the real CLI to the stop, the harness grades it, and no kill occurs.
5. DAG replay: a synthetic case with an expected `paused` after the producing step (dag_replay.py already supports pause, resume and halt rows).

Change admission (adversarial evaluation, abbreviated):

| Scenario | Disposition |
|---|---|
| A stray exported `SHIPLOOP_STOP_AT` pauses real runs | Mitigated: creation notice, source recorded, named in the paused packet. Accepted: the harness needs the route. Tested: env-route test asserts the notice. |
| The model resumes or ignores the stop | Mitigated: the directive leads the packet; the harness records reached vs status; 5/5 live probes obeyed. Residual risk: long contexts, unknown. |
| Replay or crash loses or duplicates the pause | Mitigated: the pause is in the accepting transaction; replay is a no-op (tested). |
| The stop is never reached | Reported as `reached` null; the harness verdict fails with expected and observed (tested). |
| Checkpoint stages | Tested through the real Improve import. |
| Old saved runs | Mitigated: optional key; older ShipLoop refuses a state with `stop`. |
| Another host or style | Engine-only, no host branch, neutral fixtures. |
| Added text | Zero for runs without a stop (byte-identity probe); one line of about 480 characters in a stop pause. |
| Waiting on a person (S-14) | Mitigated: the packet says it is not a question; the harness resumes by verb. The refusal of other paused runs stays. |
| Misleading verdicts | Stop runs write no baseline row; the verdict is `stop`, never "shiploop done"; follow-ons are skipped. |
| Snapshot restore confusion | Mitigated: restore only in place; document that copies keep stale absolute paths. |
| Cost over savings | Engine tests about 2–5 s; footprint like a89135f7. |

8. OTHER FINDINGS

- Existing paused and blocked packets print their directive and "Resume:" line last. In the original code the 16,000-character print limit already cut a plain paused packet's Resume line at two accepted stages (section 2).
- `status_block` says "The packet prints the resume command." For the stop packet the command is in the leading directive, so it stays accurate.
- `shiploop-drive` returns EXIT_NEEDS_USER (3) for any non-active, non-done run, so a reached stop would read as "needs user" [M, shiploop_keepalive.py `drive`].
- The Run Review exporter handles `paused` ("paused after N") but does not say the stop was requested [M, export.py].
