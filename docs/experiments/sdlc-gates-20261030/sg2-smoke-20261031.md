## Why a smoke, and what it is

Owner, 2026-10-31: "Yes, start smoke", after "Keep 4, pool SG2" and a recommendation to measure before spending on the 32
pooled slices (README.md, "Pooled reading"). Nothing of SG2 has run. Three things are unknown and matter before 27 more
Terra slices are paid for:
1. whether a slice runs end to end and scores on each of the four cases (a seeded tree, a final tree, `sg2_recall.py`);
2. minutes per slice for each route, for the bar's 1.5x cost bound and to plan the rest;
3. whether the inline review (arm A) already catches the planted defect almost every time. The pooled test sees a gain
   only below that: with B at 100%, its power is 0.86 at A = 60%, 0.42 at 75%, 0.25 at 80% and 0.03 at 90%
   (`sg2_pool_power.py`'s `pooled_power`).

## What the smoke decides (fixed before any slice)

- **A slice fails to complete or to score** (a host refusal, a harness error, a missing final tree): find the cause and fix
  it before anything else runs; that sample does not count.
- **Arm A catches 0 to 3 of the 4 cases:** the cases leave room. Continue with the rest of the pool
  (`queue SG2-K1 SG2-K2 SG2-K3 SG2-K4 --arms A,B --jobs 4 --no-early-stop` skips what finished).
- **Arm A catches all 4:** a ceiling warning, not a verdict (4 of 4 has probability 0.32 at a true 75% and 0.66 at 90%).
  Run arm A sample 2 on all four cases before any more B. If A then holds 8 of 8, stop and report: the pool would have
  about 3% power at a true 90%, so the cases need harder planted defects (a change of the cases, which is the owner's). Any
  other result: continue as above.
- **Minutes:** reported per slice and per arm. One B slice does not decide the 1.5x bound; the pooled run does. If a slice
  takes more than 100 minutes, say so and decide then (background tasks are killed near 120).
- **Nothing is concluded about B against A from one B sample on one case.**

### What the nine slices show

1. **The pipeline works.** Nine of nine slices completed and scored. Inline slices took 4.9 minutes on average
   (range 4.2 to 5.7); the one fresh-worker slice took 13.4 on SG2-K1, where the two inline
   slices took 5.3 on average, so about 2.5 times as long. One B sample is an indication, not the
   bar's 1.5x measurement; it fits the 7 to 17 minutes a fresh review cost in 2026-09.
2. **The cases do not test the review on this subject.** All nine scored 1 (the defect is absent from the final tree), but
   in all nine the carry-forward Improve review was classed trivial and changed nothing, and no product file changed after
   the step's own commit. The producer wrote the correct code in the first place: each step commit already states the
   behaviour the trap is about. The case prompts spell that behaviour out ("the mean of an empty array is 0, not NaN";
   "case-sensitive: every upper-case letter sorts before every lower-case one"), and Terra at xhigh follows what is
   specified. First samples of arm A:
  - SG2-K1 (A/1): "Use code-point iteration and lexicographic comparison because default JavaScript sort compares UTF-16 code units; copy before sort. Existing modules do not implement this behavior."
  - SG2-K2 (A/1): "Copy before numeric descending sort to preserve the input, then slice to n."
  - SG2-K3 (A/1): "Validate array shape, return 0 for empty input, and sum without mutation."
  - SG2-K4 (A/1): "Private array and limit preserve capacity; a separate class fits the requested distinct module rather than reusing unrelated utilities."
3. **`improve_fix_commits` does not tell a review's fix from a defect that was never written.** It was 1 in nine of nine
   slices, because `e5_regression.fix_commits` counts any commit since the seed with a `Key learnings:` line that changes a
   product file, and the step's own `feat(W1/S1)` commit has one (every step commit in these slices does). The guide and the proposal
   leaned on that column for exactly this distinction. A real Improve fix would be a later commit; there was none.
4. **So the pooled run would read nothing.** Arm A scored 8 of 8. With 0 of 9 producers writing the defect, the rate at
   which Terra writes it is below 28% at 95% confidence (1 - 0.05^(1/9)), so arm A is at 72% or more; with B at 100% the
   pool's power is 0.42 at 75% and 0.03 at 90% (`sg2_pool_power.py`). Even a perfect fresh review has almost nothing to
   improve, and when the producer never writes the defect neither route's review is tested.

### The decision, by the rule fixed above

Arm A caught all four, so A sample 2 ran on every case; A held 8 of 8, so the smoke stops and reports. The other 23 pooled
slices were not run. The cases need a defect that is present when the review starts, and "harder" traps would likely be
avoided the same way: the remedy is to plant the defect, not to word the task more cleverly.

What this does not show: how often a review catches a defect that is there (0 of 9 had one to catch); anything about a fresh
review's recall; behaviour on larger tasks, other subjects (a weaker model may write the defect) or other builds. It does show
that, on these four stated-behaviour traps with this subject, a fresh review would cost about 2.5 times as much
and have nothing to fix, and that the carry-forward review does not invent changes (nine trivial passes).

### Options for the owner

1. **Close SG2 as declared (recommended).** No evidence either way about a fresh review's recall; the 2026-09-24 inline
   default stays, and D3b gets no result. Nothing is spent. Reopen if a live run shows a defect surviving the review.
2. **Plant the defect and measure the review directly.** Seed each case's `naive` reference tree (already in the harness,
   `seeded_defects.reference_tree`) so the review has something to catch, then compare routes. The existing seed points end at
   `test`, and a recorded test-spec from a real run would test the trap and send the naive tree back to implement, so this
   needs a new seed route (a harness change that moves the evaluator digest, between epochs) and defects the case's own
   tests do not exercise, not stated behaviours. The scorer (`seeded_defects.score`) and the pooled reader (`sg2_pool.py`)
   carry over; `improve_fix_commits` must stop counting the step commit. Cost: a build, then 32 slices of about 5 to 13
   minutes.
3. **Probe a weaker subject first.** Run arm A on the four cases at a lower effort (or another model) to see whether the
   producer then writes the defect. About 20 minutes; a different subject cell, so the owner's call and not a baseline.

### The same flaw in E5's scorer (found while closing)

`sg2_recall.py` takes its fix-commit count from `e5_regression.fix_commits`, so E5's own scorer shares the flaw. Run on the
current slice folder `SG2-K4/A/1/slice`, `python3 test/shiploop_e2e/evaluators/e5_regression.py score` returns `value: 1` with one
"fix", the step's own commit `5f686eb2dc66` (`feat(W1/S1): Implement bounded Basket`, product files `README.md` and
`src/basket.js`), marked `fails_before_fix: true`. No review fix exists in that run (the review changed nothing). So on a build
whose step commits carry a `Key learnings:` line, E5's scorer passes a run vacuously. Whether E5's 2026-10-24 results were
affected was not checked here. The fix belongs in `fix_commits` (leave out the step's own commit) and moves the qualification
snapshot, so it waits for a quiet moment between epochs and the owner's go.
