# Stillroom delivery look

I ran the app against fresh synthetic data and drove it with Playwright in headless Chromium at 1440 × 900 and 390 × 700. For the steps below, start `node server.js` with `PORT=0` and a fresh `DATA_DIR`, open the address printed by Node, choose **Continue as Maya**, and use **Generate local token** unless a step says otherwise. Use a new conversation where indicated. The existing `npm test` suite passed.

## Shortfalls

- **high — A new save can silently overwrite an existing reusable item.** Save a task named `Weekly` with `How many orders can you see?`. In the cleared form, enter `Weekly` and `How many accounts can you see?`, and click **Save task** without first choosing **Edit Weekly**. There is still one task, with no alert or confirmation, and **Edit Weekly** now shows the accounts request. Repeat in **Saved instructions** with the same name and two different texts to see the first text replaced there too. An ordinary save with a duplicate name needs to preserve the existing entry until the user chooses to replace it or changes the name.

- **high — Opening a conversation again loses the draft and reading position.** In a new conversation, send several screenfuls of text. Type `Unsent follow up draft`, scroll up to read the beginning, and reload. The same conversation opens at the bottom with an empty composer. Opening the same saved conversation should preserve the draft and the place the user was reading.

- **high — A starter example overwrites an unsent message.** In an empty conversation, type `Quarterly draft I have not sent`, then click **Explore your records**. The composer immediately changes to `how many orders can you see`. Preserve the draft or ask before replacing it.

- **high — Sending a follow-up makes an earlier failed reply unrecoverable in the UI.** Send `First lost reply [fail once]` and wait for the alert and **Retry**. Send `what did I ask first` instead, wait for the answer, and reload. The original message is still there, but its alert and **Retry** are gone. It remains marked failed in the saved conversation. Keep the failure and a way to retry that message without entering it again.

- **high — Over-limit input silently drops the tail.** Paste 12,000 `x` characters followed by `Z` into **Message**. The textbox keeps the 12,000 characters, drops the final `Z`, shows no limit or warning, and allows sending. The same check drops the final character after 80 in the three name fields and after 6,000 in **Instruction text**, **Task request**, and **Memory text**. Direct requests at the corresponding limits succeed and one character over returns a validation error. In the page, make the limit and any truncation apparent before the user sends or saves a partial value.

- **high — Steering can add work to the wrong task.** Start Node with `STANDIN_STEP_MS=1600`. In one new conversation, send `research: Alpha`, `research: Beta`, then `add step: check Alpha invoices` while both are **Running**. The reply says it will add the step to the task that is running. At completion, only Beta lists `Done: check Alpha invoices`. With several eligible tasks, the user needs to be able to identify the target and see where the added step went.

- **high — A background task can stay Running after the worker has stopped.** Start Node with `STANDIN_STEP_MS=1400` and a disposable data directory whose path is in `review_data`. Send `research: storage recovery`. As soon as the first finished step appears, run `mv "$review_data" "$review_data-offline"`, wait about two seconds, then run `mv "$review_data-offline" "$review_data"`. Node logs `Workspace operation failed.` After restoring the folder, wait more than the task’s remaining normal runtime and reload. The task still shows **Running**, `Working in the background.`, and only the first finished step. A new order-count question works, but the stalled task has no **Retry task**. The user needs an accurate status and a way to recover from the checkpoint, and the operator needs a log that identifies the task and storage error.

- **high — A large numeric total can be silently changed before approval.** On fresh records, send `create an order for Precision Test totalling 9007199254740993`. The preview shows `total: 9007199254740992` with **Confirm changes** available. Confirm it and ask `what is the total of ORD-1005`. The reply reports the rounded value. An amount that the product cannot represent exactly needs an explicit rejection before approval is offered.

- **medium — Documented record prompts give wrong or unhelpful results for capitalized fields and decimal creates.** Ask `What is the STATUS of ORD-1001?` and get `ORD-1001 has no STATUS.`; the lowercase field returns `open` on the same data. Send `set the Status of ORD-1001 to closed` and the reply invites confirmation, but **Change result** says the proposal cannot change that field and there is no confirmation button. Send `create an order for Decimal Test totalling 35.50` and get the provider’s echo with no preview, although `set the total of ORD-1001 to 35.50` does offer a preview. The provider guide says capitals do not matter and describes creation with a number. The app needs accurate behavior for these forms or clear guidance about the supported spelling and amount format. These cases follow from the required stand-in’s parsing.

- **medium — Rejected steering loses its outcome from the conversation.** With no task running, send `add step: check payment`. The bot says it will add the step, and a separate notice says there is no running task. Send `hello there` and reload. The bot’s promise is still in the transcript and the corrective notice is gone. A user returning to the thread needs to see that the step was never added.

- **medium — The return summary has no time boundary and its task links can leave the target offscreen.** Send `research: inbox review` and keep the tab visible until it completes. **Since you were away** lists it as finished during that same visit and still lists it after a reload with no new work. For navigation, run `research: Alpha` and `research: Beta` in the same conversation, let them complete, then scroll the conversation to the top. Click **Alpha · Completed** in the summary. The scroll position stays at the top with the task card below the visible area. The summary should distinguish changes that happened during an absence and take the user to the selected task.

- **medium — Some remembered entries cannot be corrected at their saved length.** Send `remember that ` followed by 6,001 `m` characters. **Memory** stores the whole fact. Choose **Edit memory**. The editor opens with all 6,001 characters, blocks inserting a character, and **Save memory** returns `Memory text must contain between 1 and 6000 characters.` A fact the bot accepted needs to remain editable, including a correction that keeps its original length.

- **medium — Separate conversations can be indistinguishable in navigation.** Start two conversations with `Hello there`, then send `Notes about quarterly planning` in one and `Notes about next week` in the other. Both buttons in **Conversations** are named `Hello there`, and both hover titles repeat it. The current marker identifies the open conversation, but the titles give no way to identify the discussion from its content before opening it. Saved discussions need a distinguishing label or clue when their openings match.

- **low — Keyboard focus falls out of the workspace flow when opening a saved conversation in a narrow window.** At 390 pixels wide, open **Chats**, focus an existing conversation button, and press Enter. The panel closes and focus lands on the document body. **New conversation** in the same panel moves focus to **Message**. Similarly, cancelling a running task removes the focused button and leaves focus on the body. After these actions, focus should land on a meaningful visible control or status so keyboard use can continue from there.

- **medium — Ordinary work questions and completed research can provide no usable answer.** On fresh records, ask `Which of my open orders has the biggest total, and what should I follow up on?`. Maya gets her question echoed back, even though her available records contain order status and total. Then run the README’s `research: monthly order review [long]`, leave the tab, and return after completion. The card shows `All steps finished.` and entries such as `Done: Write the summary of monthly order review`, but gives no summary or findings. The request calls for usable answers and a clear account of completed work. The README discloses the stand-in’s echo behavior, and the required stand-in returns checkpoint acknowledgments as its task outputs. The broader chat and research outcomes remain unmet under that constraint.

## Choices the customer was not told

- Bot names can repeat. Each repeated name identifies a separate bot, and renaming a bot also relabels its earlier message articles.
- Conversation titles use the first sent message, collapse whitespace, and keep its first 56 characters. New conversations and bots are listed newest first.
- The starter examples put a prompt in the composer for review before sending.
- Instructions and saved tasks are shared across a person’s bots. Each bot selects one active instruction, and editing or deleting that entry affects every bot using it.
- Memory treats case-insensitive exact matches as the same fact when remembering or forgetting. Forgetting removes the memory entry and leaves the transcript intact.
- Existing record edits are limited to order `customer`, `status`, and `total` and account `name`, `tier`, and `owner`, with the current field type preserved.
- A pending creation reserves its displayed order ID across people and conversations. Rejecting releases it for future previews, and other previews retain the IDs already shown.
- Confirmation compares the reviewed field values at commit time. An intervening change followed by a restoration of the reviewed value still lets the earlier proposal apply.
- A valid environment token takes precedence over a saved token. An invalid environment token falls back to the saved one. A token saved through Setup is stored as plain text in the owner-only `workspace.json` snapshot under `DATA_DIR`.
