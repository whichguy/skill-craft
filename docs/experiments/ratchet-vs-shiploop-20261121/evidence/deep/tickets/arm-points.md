# Points raised by people who built the product

## Marked as open for the customer

- The requester decides how to count Unicode characters and how to treat whitespace-only names, surrounding whitespace, line breaks and other control characters. The existing single-line conventions for titles and requesters do not define agent names.
- The requester decides whether repeated assignments of the same ticket to the same agent while their earlier notice is still pending are separate news or can share that pending notice.
- The requester decides whether case variants, Unicode equivalents or differently spaced names identify the same agent. Assignment, no-op detection and filtering must agree for a given accepted name.
- The requester decides how repeated `assignee` parameters are interpreted and whether a nonempty value outside the accepted name domain is rejected or yields no matches. A repeated parameter is distinct from combining assignee with status or priority.
- The requester decides whether raw consumers also need the assignee in `list --raw`. The existing raw column contract applies either way.

## Requirements added after looking at a running build

- A failed assignment save leaves the running service ready to retry the change. Observable: Make a file-backed assignment fail before the new state is saved. The request returns HTTP 500 with `error.code` equal to `internal`. The running API still shows the previous ticket, audit history and outbox, and the saved state is unchanged. Restore storage and send the same request without restarting. It records the assignment once, with one new audit entry and one notice to the incoming agent.
- Clearing or closing a ticket preserves assignment notices already waiting for delivery. Observable: With the worker off, assign two tickets to agents. Clear the assignment on one and take the other through resolution to closure. Each assignment notice remains pending for its recorded ticket and recipient. When the worker can deliver, the respective agent receives the notice about the assignment that occurred.
- The CLI ticket detail shows the current assignee. Observable: Run `node bin/tickets.js --data FILE show ID` for an assigned ticket and for an unassigned ticket. The ticket details show the current agent or make the unassigned state explicit. The operator can read that state directly from the details, including for a legacy ticket with no assignment history.
- Operators can keep the supported `MAX_BODY_BYTES` settings when enabling assignment. Observable: The service starts with `MAX_BODY_BYTES` set to an integer from 1,024 through 1,048,576 bytes inclusive. Starting with 1,023 or 1,048,577 fails with a diagnostic naming `MAX_BODY_BYTES`.
- The CLI ticket detail remains read-only. Observable: Run `tickets show ID` with the data file selected by `--data FILE` and again with it selected by `DATA_FILE`. After each command, the selected file is byte-for-byte unchanged.
- The CLI ticket detail keeps the ticket's history available in chronological order. Observable: After two assignments by different actors, `tickets show ID` displays the existing ticket history and both assignment entries in the same oldest-first order as the audit API. The current assignee is still visible in the detail fields.
- The CLI history distinguishes clearing an assignee from assigning a name. Observable: When `null` is an accepted agent name, compare the history shown by `tickets show ID` after a handoff from Dana to the agent named `null` and after a clear from Dana. The history itself makes it possible to tell which change assigned an agent and which left the ticket unassigned.
- An assignment request with malformed UTF-8 is rejected without changing the ticket. Observable: Send a JSON assignment body with an invalid UTF-8 byte such as `0xFF` inside the assignee string. The API returns HTTP 400 with `error.code` equal to `invalid`, the ticket keeps its prior assignee, and no audit entry or notice is added.
- The CLI history distinguishes agent names from the separators used to show a handoff. Observable: When the names are accepted, use `tickets show ID` to compare a handoff from `Sam ->` to `Jo` with one from `Sam` to `-> Jo`. The rendered change in each history row makes clear which name is the previous assignee and which is the incoming assignee. A name containing a field separator, such as `Agent; Relief`, is likewise shown as one name in either position.
- Malformed UTF-8 in an assignee filter cannot select another agent's tickets. Observable: If `Da�na` is an accepted agent name, assign a ticket to that agent. `GET /tickets?assignee=Da%EF%BF%BDna` finds it. `GET /tickets?assignee=Da%FFna` may return an error or an empty result, but must not return that ticket by substituting a replacement character for the malformed byte.

## What a reader of the code remarked was missing or risky

- Logic is right and follows the request literally (trimmed names counted in code points, no-op on the same agent, one notice per assignment, AND filters); the risks are the column appended to the positional `list --raw` script output and the rewritten apply() that every change now passes through.
- Rejects wrong types, blank and over-long names, control characters and unknown fields, returns 404/409, validates stored assignees on load and restores memory when a save fails; lone surrogates and C1 controls are accepted, and the filter value is not checked.
- The main behaviour is correct and the raw output and apply() are left as they were, but names keep surrounding spaces (so ' Dana' and 'Dana' are different agents and notice recipients), the limit counts UTF-16 units (33 emoji are refused), and `list --raw` does not show the assignee.
- Thorough: strict UTF-8 bodies, a required key, well-formed strings, Unicode control and separator characters, validated filter values, stored-data checks and rollback on a failed save, each pinned by a test.
- The feature logic is sound: filters are ANDed, each assignment gets its own notice key and legacy tickets default to null. But it adds a column to the documented `list --raw` format, which scripts read by position, and it rewrites apply() for every change, so existing behaviour changes beyond the request.
- It checks type, emptiness, length and control characters, refuses unknown fields, returns 409 and 404, validates assignees when loading the file and rolls back any failed save. Filter values are not validated, and C1 or line-separator characters and lone surrogates are accepted.
- The feature is complete and leaves existing behaviour alone: the raw script format is kept, filters are ANDed, notice keys are unique, legacy tickets default to null and a failed save rolls back. The remaining risks are design choices: names are not trimmed, so 'Dana' and ' Dana' are different agents, and clearing is logged as ticket.assigned.
- Validation is thorough. A missing field gets its own error message. Control characters, line separators and badly formed strings are rejected, bodies must be valid UTF-8, filter values are validated, assignees are checked when the file loads, and state is restored after a failed save.
