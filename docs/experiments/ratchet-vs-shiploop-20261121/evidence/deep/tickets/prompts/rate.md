## The conditions

- **U-1**: What a caller gets when assigning or unassigning a ticket that is not open or in-progress (resolved or closed), including a request that would change nothing there (the current agent again, or null on an unassigned ticket), and that the stored assignee stays as it was. (Why it might matter: Clients branch on the error `code`; the API's conventions (docs/api.md, decision 4) make a request the ticket's state does not allow a 409 `conflict`. Someone will try to hand a resolved ticket to another agent or clear it, and a dashboard may re-send the current value; a success answer, or a refusal that changes the ticket anyway, misleads the client.)
- **U-2**: What the endpoint answers for a malformed request: no `assignee` field, a non-string non-null value (a number, an object, an array), extra unknown fields, a body that is not a JSON object, a body that is not valid JSON or not valid UTF-8, and an unknown ticket id. (Why it might matter: The API refuses unknown fields and malformed bodies with 400 `invalid` and unknown tickets with 404 `not_found`; an assignment endpoint that treats `{}` as an unassign or accepts `{"asignee":"dana"}` would quietly change tickets, and a desk form will send such values.)
- **U-3**: How an agent name is normalised and which characters it may hold: surrounding whitespace, a whitespace-only name, tabs, line breaks and other control characters, and whether the 64-character limit counts before or after trimming. (Why it might matter: Titles and requesters are trimmed and refused when they hold control characters, because a tab or newline breaks the command line's tab-separated `list --raw` output and its table; a whitespace-only name is empty in practice; ' dana' and 'dana' being different agents would split one agent's tickets across two filters.)
- **U-4**: Whether an assignment or unassignment is recorded in the audit log, under which action, with which actor and changes, and that a no-op records nothing. (Why it might matter: Internal audit requires every change to a ticket to be traceable to a person (decision 7); 'who took this ticket off dana?' is exactly the question the log exists for. The conventions say a change that changes nothing adds no entry.)
- **U-5**: Whether an assignment or unassignment moves the ticket's `updated` time, and whether a no-op leaves it as it was. (Why it might matter: `updated` is documented as when the ticket last changed, and the command-line table shows it; agents sort and triage by it.)
- **U-6**: Whether unassigning an open or in-progress ticket that is already unassigned (including a repeated unassign) is a no-op like re-assigning the same agent. (Why it might matter: The request settles the same-agent case only; the desk will retry a clear, and a second audit entry, a newer `updated` or a notification would make an unchanged ticket look newly worked.)
- **U-7**: Where the assignment notification goes and whether it can be delivered: the agent is a name, not an address; each notification type needs wording; what the message says; and whether the PUT waits for delivery. (Why it might matter: Without wording for a new notification type the event can fail its retries and go dead (decision 6), so agents are never told; the mail relay reads `to` from NOTIFY_FILE lines, so the operator needs to know what `to` holds for an agent; the agent needs the ticket id and title to know which ticket it is.)
- **U-8**: Whether every assignment notifies its agent when assignments of one ticket follow each other before the worker delivers, given that the outbox drops an enqueue whose key is still pending (the default key is type + ticket). (Why it might matter: Assigning a ticket to dana and then to lee within one worker interval (or while the relay is down) would, with the default key, leave only dana's pending notification, and lee, who now owns the ticket, is never told.)
