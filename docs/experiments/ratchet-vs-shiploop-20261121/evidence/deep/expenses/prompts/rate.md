# Would the customer care?

`/Users/dadleet/e2e-runs/d20261122-360a9f/deep/expenses/request.md` is a request a customer gave a software builder. The builder started from an empty folder. Below are conditions the request
leaves unsaid. For each, say whether the customer, an operator or the next maintainer would care how the product
behaves there once it is in use:

- `must`: getting it wrong loses data, misleads a user, breaks something that worked, or is a plain defect anyone
  would report.
- `should`: a careful builder handles it, or tells the customer what was chosen; getting it wrong is a real but
  smaller cost.
- `no`: a reasonable builder could ignore it; handling it is taste, speculation or over-engineering for this
  request.

Rate each on its own. Most lists like this hold a good share of `no`.

Answer with one JSON object and nothing else: `{"ratings": [{"id": "U-1", "rating": "must|should|no", "why": "one sentence"}]}`

## The conditions

- **U-1**: What status a request body that is not valid JSON gets, and whether the server keeps serving afterwards. (Why it might matter: Client code and the operator need a predictable refusal for a truncated or garbled body; a 500 or a crashed process would take down every group's service.)
- **U-2**: What happens when a required field is missing: an expense without payer, cents or split, split "exact" without shares, or a group without id or members. (Why it might matter: These are the first bad requests a client sends; the stated 400 list does not name a missing field, and a throw becomes a 500 or a dead process instead of a refusal.)
- **U-3**: Whether JSON values of the wrong type are refused or coerced: cents as a string, members as a string, a member that is not a string, or shares that is not an object. (Why it might matter: A client sending "100" instead of 100 looks like the documented call; the request's 400 list names only non-integer amounts, so the service may coerce, refuse, or crash.)
- **U-4**: Which group ids are accepted (empty, missing, numeric, containing '/', spaces, '%', unicode), and whether every group that got 201 can then be addressed through /groups/<id>/ by all three group routes, percent-encoded where the path needs it. (Why it might matter: The id is the only way to address a group later; a group created with an id that no later request can reach is lost to the customer.)
- **U-5**: Whether exact shares may be negative or non-integer (for example {"Ann": 150, "Bob": -50} or {"Ann": 50.5, "Bob": 49.5} for cents 100), since only zero is said to be allowed and only the total is said to be checked. (Why it might matter: A negative share credits a member who paid nothing and moves debt the wrong way; fractional shares break the whole-cent balances and settlements.)
- **U-6**: How a member list is handled when it holds two distinct non-empty names plus a duplicate, an empty or whitespace-only entry (for example ["Ann", "Ann", "Bob"] or ["Ann", " ", "Bob"]), and whether names differing only in case or surrounding spaces count as distinct. (Why it might matter: A duplicated member counted twice changes an equal split and who gets the leftover cents; customers typing names by hand will hit these cases.)
- **U-7**: Whether an exact split must list every member, or a member left out of shares owes nothing. (Why it might matter: Users splitting a bill among part of the group need omitted members to be uncharged or a clear refusal.)
- **U-8**: Whether an expense or group is already safely written to DATA_FILE when its 201 is sent, and whether a crash or kill during a write can leave DATA_FILE truncated or corrupt. (Why it might matter: The customer was promised that data survives a restart and no expense is lost; an operator restarting after a crash must not find an unreadable file and lose every group.)
- **U-9**: What the server does when DATA_FILE names a file that does not exist yet. (Why it might matter: An operator's first start is on an empty machine; the request says data lives in that file, not that it already exists.)
- **U-10**: What the server does at startup when DATA_FILE is empty or holds invalid JSON. (Why it might matter: A corrupt or hand-edited file must not be silently replaced with an empty store, which would wipe the customer's data.)
- **U-11**: What server.js does when DATA_FILE is unset. (Why it might matter: An operator who forgets the variable should get a clear failure or a documented default, not data written to an unexpected place.)
- **U-12**: What server.js does when PORT is unset, empty, not a port number, or 0. (Why it might matter: The person starting the process has only 'listens on PORT'; a missing or bad value is the usual first mistake and they need to know whether it exits, picks a default, or binds an ephemeral port.)
- **U-13**: Whether concurrent expense posts to one group each get a distinct expense number with no repeats or gaps, and each acknowledged expense is applied exactly once. (Why it might matter: Expense numbers are how users refer to expenses; two expenses both numbered 3, or one applied twice, means the ledger is wrong.)
- **U-14**: Whether a balances read that overlaps in-flight expense posts returns a consistent state. (Why it might matter: A balances view that does not sum to 0, cannot be shown to users checking who owes what.)
- **U-15**: What two overlapping POST /groups calls for the same new id do. (Why it might matter: Two people can create the same group at once; two 201s, a group stored twice, or a last-write-wins member list breaks the 409 rule under the only load the request mentions.)
- **U-16**: Whether expense numbering continues after a restart instead of starting again at 1. (Why it might matter: Users refer to expenses by number; restarting the numbers would give two expenses the same number in one group.)
- **U-17**: How unknown paths and wrong methods are answered (GET /groups, DELETE /groups/g, POST /groups/g/balances, GET /groups/g/unknown, GET /other). (Why it might matter: Client developers need to tell a typo from a missing group; the request only says unknown groups get 404.)
- **U-18**: What Content-Type the responses carry. (Why it might matter: Clients and tools decide how to parse a response from its Content-Type; JSON sent as text/html or with no type trips them.)
- **U-19**: What body, if any, POST /groups returns with its 201, and whether a Location header is set. (Why it might matter: A client or a test has to know whether to parse JSON, read an empty body, or follow a Location header after creating a group.)
- **U-20**: What body a 400, 409 or 404 carries. (Why it might matter: Whoever calls the API, or debugs a failure, cannot tell a refusal's reason from a bare status, and a client may try to parse the body as JSON.)
- **U-21**: Which status POST /groups uses when the id already exists and the member list is also invalid, and whether the stored members change. (Why it might matter: A retry that reuses an id with a bad body is a normal client mistake; the caller must know which case it hit, and the original members must not be replaced.)
- **U-22**: Which status is used when the group is unknown and the expense body is also invalid. (Why it might matter: The request states 404 for an unknown group and 400 for a bad expense separately; a client branching on status needs to know which check wins.)
- **U-23**: Whether extra fields on an otherwise valid body are ignored, stored or rejected, including a shares object sent with split "equal". (Why it might matter: Clients add notes and titles; a strict server fails those calls, and a server that applies shares on an equal split changes who owes what.)
- **U-24**: Whether a JSON body must be sent with Content-Type: application/json. (Why it might matter: A client or curl command that omits the header or sends text/plain is either accepted or refused, and the request does not say which.)
- **U-25**: Whether GET /groups/<id>/balances and GET /groups/<id>/settlements only read, or also change stored state. (Why it might matter: A client that polls the settlement plan would wipe the debts if the GET recorded the payments.)
- **U-26**: Whether DATA_FILE written by the server is read back to the same state: a group with both an equal and an exact expense gives the same balances, settlements and next expense number after restart. (Why it might matter: The next maintainer has to inspect or repair the only copy of the data, and a file the server cannot read back as written loses the customer's ledger.)
- **U-27**: Whether the tests are self-contained: they start their own server on a free port with a temporary DATA_FILE, need nothing running, leave no stray files or processes, and pass repeatedly. (Why it might matter: The next maintainer runs `node --test` on a fresh checkout or in CI; tests needing a fixed port or a real data file fail or clobber data.)
- **U-28**: When a write to DATA_FILE fails (unwritable file or directory, full disk), a refused expense or group creation leaves no trace: reads do not show it, it is absent after restart, the expense numbering is unchanged and a refused group id stays free. (Why it might matter: A caller told 'failed' will retry; if the failed write still shows up later the expense is counted twice, and if a refused group id is taken the customer cannot create it.)
- **U-29**: How amounts and running totals beyond JavaScript's safe integer range (about 9.007e15 cents) are handled. (Why it might matter: A large or accumulated amount that loses precision silently gives wrong balances and settlements that no longer add up to 0.)
- **U-30**: Whether very large request bodies are limited. (Why it might matter: Without a limit, one oversized request can exhaust the server's memory and take every group offline.)
- **U-31**: Whether a group creation and an expense in another group, sent at the same time, both survive a restart. (Why it might matter: Two writes that each rewrite the whole data file can drop each other; the request promises concurrent requests never lose an expense and that groups survive restarts.)
- **U-32**: Whether member names that coincide with JavaScript object properties ("__proto__", "constructor", "toString") work throughout the API. (Why it might matter: A member called "constructor" or "__proto__" can be mistaken for a built-in property, giving wrong balances, missing keys, or a crash.)
- **U-33**: Whether whole-cent values written in an equivalent JSON number form (1.0, 10e-1, 1e2) are accepted as integers. (Why it might matter: JSON libraries in other languages write whole numbers as 100.0 or 1e2; refusing them, or treating them as different amounts, breaks those clients.)
- **U-34**: Whether every group in DATA_FILE stays reachable after a restart, including one whose id would be refused for a new group. (Why it might matter: A limit on new ids added later, or a stored id the service would now refuse, must not cut the customer off from a group they already have.)
- **U-35**: What happens when a client disconnects in the middle of sending a request body. (Why it might matter: A dropped mobile connection is ordinary; an unhandled request error can crash the process or store a half-read expense.)
- **U-36**: Which Node.js versions the service needs, and whether it works on the versions an operator is likely to have. (Why it might matter: A server that silently relies on a very recent Node feature fails at the first balances request on an operator's older but supported Node.)
