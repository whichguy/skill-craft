# Points raised by people who built the product

## Marked as open for the customer

- The requester would settle handling for missing, invalid, or unavailable PORT values and whether callers need a way to discover the assigned port when PORT is 0.
- The requester would settle the response to malformed or unreadable saved JSON, an unwritable path, or a write failure.
- The requester would settle which ID strings are valid beyond ordinary non-empty path segments, how ID strings that need URL escaping map to routes, and the response to a missing or non-string ID. The success response body is unspecified and the requester would settle any client-facing schema.
- The requester would settle whether 409 or 400 takes precedence when the ID already exists and the member list is invalid.
- The requester would settle whether a list with two valid distinct names plus a duplicate, empty entry, or non-string entry must be rejected or accepted with a defined membership. The requester would also settle whitespace-only names and any normalization that would make different strings refer to the same member.
- The requester would settle the supported range for large amounts and accumulated totals beyond JavaScript Number's consecutive safe integer range of -9007199254740991 through 9007199254740991. The runtime's safe integer bound does not by itself set an API limit.
- The requester would settle status codes for malformed JSON, bodies of the wrong shape, or missing or non-object exact shares where the stated validation rules do not already determine a status. The requester would also settle any error response body contract or request-size limits.
- The requester would settle whether a read that overlaps an expense submission must include that in-flight expense. A read begun after the successful expense response includes that expense.
- The requester would settle whether overlapping submissions need a particular relationship between arrival order, assigned number, and response order.
- The requester would settle recovery guarantees for a crash, power loss, or an interruption while a request or write is in progress.

## Requirements added after looking at a running build

- An expense explicitly rejected after a failed ledger write does not appear after restart Observable: Record expense 1 and temporarily make its ledger unwritable without changing the saved contents. Submit an otherwise valid expense. If the service explicitly rejects that expense, any balance read it serves still reflects expense 1 alone. Restore write access and restart normally. The balances still reflect expense 1 alone, and the next successful expense returns {"expense":2}.
- A group creation and an expense recorded concurrently both survive restart Observable: In a service with an existing group, concurrently create a second group and record an expense in the first. After both requests return 201, restart with the same DATA_FILE. The first group's balances include the expense and the second group contains its submitted members.
- Member names that coincide with JavaScript object properties work throughout the API Observable: Create a group with ["__proto__","constructor","toString"]. Record an exact expense of 1 cent paid by toString with shares {"__proto__":1}. The balance object contains all three names as keys with values -1, 0, and 1 respectively. The settlement array contains one 1-cent payment from __proto__ to toString.
- Whole-cent values can use equivalent JSON number spellings Observable: In a group with Ana and Bo, send a raw exact expense JSON body with Ana paying, cents written as 10e-1, and shares written as {"Ana":0.0,"Bo":1.0}. The expense returns 201 and produces the same balances as the same request with cents written as 1 and shares as {"Ana":0,"Bo":1}.
- Every successfully created group is addressable by all three group routes Observable: Submit a fresh group with valid members and an ID made of URL-safe letters long enough to exercise request-target limits. If creation returns 201, GET its balances and settlements using the accepted ID and ordinary HTTP headers. The balances contain the submitted members at zero, the settlements are empty, and a valid expense POST returns 201 with {"expense":1}. The supported ID range remains the open point in C-5.
- An explicitly rejected group creation leaves its ID available for retry Observable: With a saved ledger, temporarily make the ledger unwritable and submit a valid creation for a fresh ID. If the service explicitly rejects the creation, a balance read cannot show the rejected group. Restore write access and restart normally with the same DATA_FILE. The ID returns 404, and creating a group with that ID and a different valid member list returns 201 and exposes the new list.
- A group member records a settlement payment they have made Flow: Ana pays an 8-cent expense assigned entirely to Bo. Read the settlement proposing that Bo pay Ana 8 cents. After Bo makes the payment, record it through the existing exact split endpoint with {"payer":"Bo","cents":8,"split":"exact","shares":{"Ana":8}}. Both balances are now zero and the next settlement read returns [].
- A tighter limit for new group IDs preserves access to groups already saved Observable: Start an upgraded service with the same DATA_FILE used by the previous version. The ledger contains an ordinary group and a successfully created group whose ID is longer than the upgraded service accepts for new groups. Both groups remain accessible under their original IDs. The longer ID still works for balances, settlements, and expense submissions, with its saved membership, balances, and next expense number preserved. After recording another expense in that group and restarting normally, both groups remain accessible and the new expense still contributes to the longer-ID group's balances.

## What a reader of the code remarked was missing or risky

- The core rules look right: the remainder goes to the first-listed members, exact shares must sum to cents, settlement is greedy with first-listed ties, and commits are serialized copy-on-write, published only after the rename succeeds. The risks: it rejects a member list with duplicates even when it holds two distinct names, it adds extra 400s for very long IDs and huge balances, and its intricate number-source code has a regex fallback that never runs on current Node.
- Very thorough: fatal UTF-8 decoding, whole-cent checks on the number as written in the request, full validation of the saved ledger with a fail-fast start, temp-file cleanup, failed saves leave memory unchanged, request errors are handled and bodies drained. Gaps: no body-size limit, and error responses have no body.
- Small and correct for the request: shares stored by member index, BigInt balances, first-listed ties, and no lost updates because everything after the body read is synchronous. The risks: it needs a recent Node without saying so (JSON.rawJSON runs on every balances and settlements response), it rejects whitespace-only names, it checks for 409 before validating members, and its atomicity depends on an unenforced rule that a future await would silently break.
- Good request validation: safe integers, share sums that cannot overflow, distinct non-blank names, and URI errors. Writes use a temp file and rename with cleanup, and failures return 500 with a JSON error body. But the saved ledger is trusted without validation, there is no body-size limit, and only error.message is logged.
- The split math, greedy settlement and serialized commit queue are correct, and reloads are validated. But a lot of intricate extra logic (wire-format number checks with a regex fallback that modern Node never runs, ID-length and header sizing, an overflow guard) widens the surface and adds 400s the request does not ask for, such as rejecting any repeated member name.
- Strict PORT and DATA_FILE checks. It tells a missing ledger apart from a bad path, validates every saved group and expense, rejects invalid UTF-8 and non-object bodies, ignores request errors, drains bodies and rolls back failed writes. The only weakness is error replies that carry just a status code.
- Small and correct: a synchronous read-modify-write makes lost updates impossible, and BigInt keeps balances exact. The risks: balances and settlements replies depend on JSON.rawJSON (Node 21+), the ledger file is loaded without validation, and repeated members are silently merged.
- Validates the payer, safe-integer cents, split, share objects, non-negative shares and their sum, malformed JSON and odd paths, and returns JSON error messages. A failed write leaves state untouched and removes the temp file. But the data file is trusted blindly.
