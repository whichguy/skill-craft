# Points raised by people who built the product

## Marked as open for the customer

- The requester decides precedence and recovery when the environment credential and a saved credential differ or when the environment credential is refused.
- The requester decides naming rules if blank, duplicate or unusually long names need defined handling.
- The requester decides how conversation buttons are named and which conversation opens by default when no prior selection is restored.
- The requester decides finer restoration behavior, including the last selected conversation across visits, unsent drafts and scroll position.
- The requester decides how additional submissions within the same discussion are handled while a reply is pending.
- The requester decides whether a reply interrupted by stopping the server is retried automatically or waits for the person to retry.
- The requester decides whether saved instruction entries are shared among a person's bots or saved per bot, and how name conflicts are handled.
- The requester decides whether editing an instruction already in use updates the active instructions immediately or only after Use is selected again.
- The requester decides what deleting a saved entry does to the instructions of a bot already using it.
- The requester decides whether saved task entries are shared among a person's bots or saved per bot, and how name conflicts are handled.
- The requester decides how to match wording that paraphrases a fact, and whether forgetting should also affect earlier conversation history.
- The requester decides which fields can be updated, including whether changes to id, type or readers can ever be offered while preserving valid records and access rules.
- The requester decides how to present an assigned order ID before confirmation if the next free ID could change before the write.
- The requester decides whether cancel is the same user action as Reject changes and what navigation away from a pending proposal does to its availability.
- The requester decides whether multiple pending proposals may coexist within one conversation, and what happens to an older pending proposal when a newer one is offered there.
- The requester decides whether conflicts leave a proposal expired or offer a refreshed proposal, and how to handle a pending proposal when another action has already produced its intended value.
- The requester decides what defines the absence period and when previously reported updates stop appearing.
- The requester decides how to identify the intended task if several could be running in one conversation.
- The requester decides whether a step already in flight at cancellation may finish or is discarded.
- The requester decides whether task retries should also be available in any state other than Failed or Interrupted.
- The requester decides whether interrupted work resumes automatically after server restart or waits for Retry task, and how to treat a step whose completion had not been reported when the process stopped.
- The requester decides any specific narrow viewport widths or responsive breakpoints that must be supported.
- The requester leaves the visual design to the builder, including typography, spacing and styling. Any more specific aesthetic acceptance criteria come from the requester.

## Requirements added after looking at a running build

- Similar saved conversations can be told apart before opening them Observable: Start two conversations under one bot with the same long opening and different customer names at the end. When returning to Conversations, there is enough identifying information to tell which entry opens each discussion before selecting it, both visually and through the accessible interface.
- An unsupported record change gives the person a way to correct the request Observable: Ask to create an order totalling 42.50 or to set an order's total to “banana”. If a request cannot be previewed as entered, the app makes clear that there is no change to confirm and identifies what to correct, for example by showing an amount format it accepts. The person can submit the corrected request in the same conversation.
- Capitalization preserves the meaning of supported record requests Observable: As Maya, ask for the status of ORD-1001 using `STATUS` as the field name, then request an authorized update using `Status`. The lookup returns the same value and the update offers the same exact preview as the equivalent lowercase requests. The existing reader restrictions still apply.
- Recovery after an unacknowledged send prevents accidental resubmission Observable: Send a long-task request, interrupt the browser before it sees the acknowledgement after the server accepts the turn, and reload. Returning to the conversation makes clear that the turn was received and prevents resending the same original submission from starting a second task. A deliberate new submission of the same wording can still start separate work.
- Steering feedback identifies the specific task that received the added work Observable: If two running tasks in a conversation have the same displayed title and a follow-up is accepted, the person can match the success feedback to the affected task in Tasks, including by accessible controls and labels. If the app requires clarification before applying the steer, the feedback identifies the task once the step is added.
- A damaged saved store is preserved for operator recovery Observable: Start with a DATA_DIR containing a saved state snapshot that is damaged or cannot be opened by this version. Startup reports the storage problem and gives the operator an actionable recovery step. The saved data remains available for recovery, and the app does not silently replace it or present freshly seeded records as recovered work.
- A field lookup preserves the record identifier the person supplied Observable: As Maya, ask for the status of ORD-1001A while ORD-1001 exists and is readable. The answer indicates that the supplied identifier could not be used and gives the person a way to correct it. It does not present the status of ORD-1001 as the answer to the question about ORD-1001A. Asking for ORD-1001 itself still returns its status.
- Bots that share a name can be distinguished before selection Observable: If the app accepts two bots with the same name, give each a different discussion and switch away. On returning to Bots, the person can tell which entry opens each bot, visually and through the accessible interface, before selecting it.
- Reaching a message length limit does not silently change what is sent Observable: If the composer limits message length, insert a message that fits and one that exceeds the limit by a character that changes its meaning. The longer message is either accepted intact or the person is told that it exceeded the limit and can review or correct what will be sent. The app does not silently send only the part that fit.
- Recovery of a saved-task Run uses the request originally selected Observable: Interrupt a saved-task Run before its acceptance is known, then edit or delete the saved entry. Recover the original Run in its conversation. Any resulting turn uses the request from the original Run and its effect occurs at most once, even if the earlier delivery arrives later. A later deliberate Run of an edited entry uses its revised request.
- Reconciling a submission preserves later composer edits Observable: While the outcome of a send is being checked, type a different draft in the same conversation. Resolve the original submission as received. The later draft remains available to edit and send. If the app restores that draft after a reload, reconciliation leaves the restored text intact as well.
- Submission recovery distinguishes delivery from reply success Observable: Lose the acknowledgement for a submitted message containing `[fail once]` after the server accepts it. On returning to the conversation, the person can tell that the message was received and that its reply failed. Recovering the reply continues the accepted turn and leaves exactly one copy of the person's message.
- A storage failure during use leaves the actual save outcome recoverable Observable: Make the data directory unavailable to writes while the app is open and attempt to save an instruction. The app does not report the uncommitted instruction as saved and gives an actionable storage recovery step. After restoring access and reopening the same directory, previously committed work is still present and the person can see whether the attempted instruction was saved.
- Length limits in reusable text and memory editors preserve the intended content Observable: Where Task request, Instruction text or Memory text has a length limit, enter text that fits and then text that exceeds the limit by a meaningful final character. The app either saves the intended text intact or makes the length restriction clear before accepting a shortened version, so the person can review and correct it. Saving a task request intended to end in `totalling 90` cannot silently make a later Run propose a total of 9.
- An overlapping launch preserves work committed to the same data directory Observable: Start the app on a free port, then launch another instance on a different free port using the same DATA_DIR. If overlapping use is unsupported, the operator receives an actionable explanation before the second instance can change shared state. If both accept work, confirm a distinct new order through each and restart with that directory. Both acknowledged orders are still present with distinct IDs and their reviewed values.

## What a reader of the code remarked was missing or risky

- The flows are small and hang together: the task worker is guarded by runId, the preview is recomputed and compared at confirm, decide is idempotent, and restart recovery works. But updates are not checked against a schema, so a total can become a string or a new field can be added.
- Request-level guards are good (a Host allowlist, an Origin check, body type and size limits, an HMAC-signed cookie) and background failures are handled gracefully. Domain checks are weak: no field-type or empty-value checks, a corrupt snapshot crashes startup with a raw error, and saving under an existing name silently overwrites that entry.
- The server rules are tightly guarded (a schema-checked atomic decide, generation, run and attempt guards, submission receipts) and well tested. But the large client state machine and the text parsing written for the stand-in provider add surface, and the strict load-time validator could lock the data if the provider returns output of an unexpected shape.
- Thorough: schema and exact-amount checks, values screened for secrets, atomic writes with a directory fsync, damaged snapshots refused rather than replaced, 409 responses for stale controls, friendly startup errors. But there is no Host check against DNS rebinding, and any background exception marks the whole store unavailable.
- The core flows work: duplicate request IDs are ignored, the preview is re-run before commit, the task loop is guarded by runId, and a restart recovers. But proposals are never checked against a field schema or type. A failed reply blocks new messages until it is retried, and a write failure mid-reply leaves the reply stuck pending. Focus is restored by accessible name, so it can land on another proposal's Confirm button.
- Request checks are good: Host and Origin checks, JSON and size limits, length checks, and 401/404/409 responses. But the snapshot is parsed without validation, so a damaged file crashes startup with a raw exception. Listen errors are unhandled, unexpected errors become an unlogged 500, and proposed values are not type-checked.
- Very defensive. Previews are checked against a typed schema, amounts must match exactly, and confirms apply all changes or none. Submission receipts survive a reload, run numbers guard task controls, and restart recovery is tested. The risk is its complexity. The 'what is the X of Y' pre-parser also misfires on ordinary questions (e.g. 'of my order'): it withholds the records and shows a notice asking for a record ID.
- Thorough. It checks origin, fetch-site, content type and size, and enforces length limits. Snapshots are validated and never overwritten, symlinks are refused, writes are atomic with a directory fsync, a storage-unavailable mode is reported clearly, and startup errors are friendly. But there is no Host check against DNS rebinding, and any background exception is treated as a storage failure that disables the whole app.
