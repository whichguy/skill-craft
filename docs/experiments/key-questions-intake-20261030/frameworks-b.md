## 2. OpenSpec (deep)

### 2.1 Phases, gates, who runs them
- Default "core" profile: `explore` (optional) -> `propose` -> `apply` -> `update` (when the plan changes) -> `sync` -> `archive`. The "expanded" profile adds `new`, `continue`, `ff` (fast-forward all artifacts), `verify`, `bulk-archive`, `onboard`. [workflows.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/workflows.md)
- Each command is a generated prompt (skill or slash command) from `src/core/templates/workflows/*.ts`, e.g. [propose.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/propose.ts), [explore.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/explore.ts), [apply-change.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/apply-change.ts), [verify-change.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/verify-change.ts), [archive-change.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/archive-change.ts), [update-change.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/update-change.ts).
- Division of labour: the agent drives and writes artifacts; the CLI gives deterministic scaffolding, status and per-artifact instructions (sequence diagram in [workflows.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/workflows.md)). `openspec status` is existence-based (a file exists or not), per [propose.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/propose.ts). A 2026-10-19 change made status print exactly one `Next:` command, derived from one resolution so text and JSON cannot disagree: [cli-artifact-workflow delta spec](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/archive/2026-10-19-add-status-next-step/specs/cli-artifact-workflow/spec.md). This is the same "script names the next step" idea ShipLoop uses.
- Gates are deliberately soft. Dependencies "enable" artifacts and are not phase gates ([concepts.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)). Real stops: propose has a "planning boundary" (create planning artifacts only, then stop and wait for a fresh user request before apply); `apply` reports `state: blocked` until the artifacts in `apply.requires` exist ([apply-change.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/apply-change.ts), shape in [agent-contract.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/agent-contract.md) section 4.6); archive warns about incomplete artifacts/tasks and asks the user to confirm ([archive-change.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/archive-change.ts)); `verify` is advisory and cannot block ([verify-change.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/verify-change.ts)).

### 2.2 Prompt / template driving each phase
- The artifact graph and the per-artifact instruction text live in [schemas/spec-driven/schema.yaml](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml): artifacts `proposal` -> `specs` and `design` (both require proposal) -> `tasks` (requires specs and design); `apply: requires [tasks], tracks tasks.md`.
- The agent fetches one artifact's brief with `openspec instructions <artifact> --change <name> --json`, which returns `context`, `rules`, `template`, `instruction`, `dependencies`, `resolvedOutputPath`, `unlocks`, and a `skipped`/`warning` flag ([agent-contract.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/agent-contract.md) section 4.5). The propose prompt tells the agent that `context` and `rules` are constraints for it and must not be copied into the artifact.
- Project customization: [openspec/config.yaml](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/config.yaml) holds `context` (injected into every artifact) and per-artifact `rules`, plus `operations.apply/archive.guidance` ([customization.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/customization.md)). Teams can fork the schema (`openspec schema fork`) to add artifacts such as a `research` or `review` node.
- Templates: [proposal.md](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/templates/proposal.md) (Why, What Changes, Capabilities split into New and Modified, Impact), [spec.md](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/templates/spec.md), [design.md](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/templates/design.md), [tasks.md](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/templates/tasks.md).
- Notable instruction content in `schema.yaml` (paraphrased): the proposal's Capabilities list is a contract that creates one delta spec per capability; research existing specs with `openspec list --specs` and `openspec show <id> --type spec` before naming capabilities; specs must describe observable behavior not implementation; write spec files one at a time so an interrupted run keeps progress; every requirement needs a scenario with WHEN/THEN; `design.md` is conditional; tasks must each state how completion is verified, must land their own tests/docs inside the group (no catch-all final group), and are ordered by dependency.

### 2.3 Artifacts, lifetime, location
- Per change (`openspec/changes/<name>/`): `proposal.md`, `specs/<capability>/spec.md` (a delta), `design.md`, `tasks.md`, `.openspec.yaml` (schema, `skip_specs`, `retire_capabilities`, custom `x-*` keys). Archived to `openspec/changes/archive/YYYY-MM-DD-<name>/` ([concepts.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)).
- Living: `openspec/specs/<capability>/spec.md`, updated only when a change is synced/archived. Delta sections `ADDED`, `MODIFIED` (must carry the full updated requirement block), `REMOVED` (must carry Reason and Migration), `RENAMED` (FROM/TO). Two changes can touch one spec file without conflict if they touch different requirements.
- Experimental maintainer layer `openspec/work/` : goal -> roadmap -> slice (`spec.md`, `plan.md`, `result.md`, optional `log.md`); rule of thumb is that spec says what must be true, plan says how, result records what happened with evidence; plan is generated only once the spec is clear enough ([work/README.md](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/work/README.md)).

### 2.4 Question-asking
- Explore mode carries a "Planning a Change" block ([explore.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/explore.ts)): inspect OpenSpec artifacts, source, tests, docs and config before asking factual questions and do not make the user repeat what can be verified; resolve the next blocking decision before its dependent details and revisit downstream assumptions when an earlier answer changes; ask one focused question at a time and say why it matters and which decision it unlocks; give a recommendation with alternatives when evidence supports one; keep a conversational record that separates confirmed decisions, proposed defaults and unresolved questions, and treat silence as not accepted; stop when the user has enough clarity; never force a proposal.
- Where answers go: nothing is written until the user confirms a named write scope, and accepting a recommendation is not permission to write. Once a change exists, the explore prompt maps insights to files (new or changed requirement -> specs delta, design decision -> `design.md`, scope change -> `proposal.md`, new work -> `tasks.md`).
- Propose: ask only if ambiguity would materially change scope, externally observable behavior, compatibility or acceptance criteria; for anything smaller, assume and record the assumption in the planning artifacts ([propose.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/propose.ts)).
- Schema-level rules reinforce this: `design.md` Open Questions are for genuinely deferrable unknowns only, and a question that would change specs, approach or task breakdown must be resolved with the user now; before writing `tasks.md` the agent re-checks design Open Questions and resolves those that change what gets built ([schema.yaml](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)).

### 2.5 Research / spike / experiments
- No dedicated phase. Substitutes: explore is research-by-conversation; propose requires read-only inspection of code, tests, config and docs before drafting each artifact, and forbids leaving generic "explore the codebase" tasks for implementation ([propose.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/propose.ts)); explore suggests a spike task when implementation hits an unknown.
- Community schemas show the extension point: `ml-research` fixes metrics, success criteria and the falsification condition before a run and records refuted hypotheses; `anvil` adds a fresh-context, read-only adversarial `review` artifact that emits a `VERDICT:` line and a `test-plan` that maps each spec scenario to a named test ([customization.md, Community Schemas](https://github.com/Fission-AI/OpenSpec/blob/main/docs/customization.md)). The review gate there is not enforced by OpenSpec itself.

### 2.6 Task decomposition, dependencies, traceability
- `tasks.md`: `## N. Group` headings with `- [ ] N.M description` lines; small enough for one session; each task states its own verification; tests and docs live with the work that needs them. Order is dependency order, with no explicit dependency edges between tasks ([schema.yaml](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)).
- Scripts check structure: [task-numbering.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/task-numbering.ts) flags a task numbered into the wrong group; [task-checkboxes.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/task-checkboxes.ts) defines what counts as done.
- Traceability is by convention (requirement -> scenario -> test case). The `verify` skill searches code for each ADDED/MODIFIED requirement and checks scenario coverage, with special inverse logic for REMOVED (behavior must be gone) and RENAMED (behavior must be unchanged), and refuses to mark skipped checks as passing ([verify-change.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/verify-change.ts)).

### 2.7 Verification before implementation
- `openspec validate [--strict]` is a script. Thresholds in [constants.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/constants.ts): Why section 50-1000 characters; every requirement contains SHALL or MUST and has at least one scenario; requirement text over 500 characters warns; more than 10 deltas suggests splitting; Purpose at least 50 characters and not a placeholder; a change with zero deltas fails unless `skip_specs: true` is set; `--strict` turns warnings into failures.
- No built-in LLM plan checker. The model-judged review is `verify`, after implementation.

### 2.8 State and brownfield
- No STATE.md; position is derived from the filesystem (`status --json` with `isPlanningComplete`, `applyRequires`, per-artifact `done/ready/blocked/skipped`, plus `list --json`).
- Brownfield is the stated focus: specs start nearly empty and grow only for what a change touches; first move on a big codebase is explore; existing PRDs are source material, not converted wholesale ([existing-projects.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/existing-projects.md)).

### 2.9 Evidence of effectiveness
- No first-party benchmark in README or docs (grep for benchmark/measured found nothing relevant). Adoption signal only (stars). The repo is built with OpenSpec (its own `openspec/specs` and archived changes are public).
- One vendor-run benchmark covers it (see section 9): 50 brownfield Python tickets, OpenSpec arm 84% merge rate vs 72% no-spec control, lowest spec overhead of the four spec frameworks (12 min, 93 lines, 2.4% spec drift), but differences between spec frameworks are inside the authors' own plus/minus 10-point noise band.

### 2.10 Worth borrowing vs ceremony
- Borrow: (a) the per-artifact `instructions` packet (context, rules, template, instruction, dependency list, output path) and a single script-chosen `Next:` command; (b) the question-triage rule in propose and the "ask only when it changes scope/behavior/compatibility/acceptance, otherwise assume and record" threshold; (c) conversational record kept out of files until a write is confirmed; (d) deterministic structural validation with an explicit opt-out marker (`skip_specs`) that the validator honors and cross-checks; (e) delta-style living spec (ADDED/MODIFIED/REMOVED/RENAMED) merged at archive, which gives a history of why each requirement changed.
- Ceremony or unproven: four artifacts for every change (design is conditional but proposal+specs+tasks are not); numeric caps (500 characters, 10 deltas) are arbitrary though cheap; no measurement of whether `verify` finds real defects.

## 3. GSD / GSD Core (deep)

Lineage matters: the prompts the task describes (`PROJECT.md`, `REQUIREMENTS.md`, `ROADMAP.md`, `STATE.md`, discuss/plan/execute/verify) are the "GSD v1" lineage, now maintained as GSD Core at https://github.com/open-gsd/gsd-core. The files below are from its `next` branch. The "GSD 2" lineage (`open-gsd/gsd-pi`) is a different architecture with a database-backed state machine; a few of its ADRs are cited at the end because they address the same problem as ShipLoop.

### 3.1 Phases, gates, who runs them
- README loop: Discuss -> Plan -> Execute -> Verify -> Ship, repeated per phase within a milestone; heavy work runs in fresh-context subagents ([README.md](https://github.com/open-gsd/gsd-core/blob/next/README.md), [the-phase-loop.md](https://github.com/open-gsd/gsd-core/blob/next/docs/explanation/the-phase-loop.md)). An optional spec stage (what and why) runs before Discuss, whose `SPEC.md` discuss-phase then treats as locked requirements; an optional UI-design stage sits between Discuss and Plan.
- Project start: `/gsd-new-project` -> [new-project.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/new-project.md): setup; brownfield offer; "deep questioning"; write `PROJECT.md`; workflow preferences; optional research (four parallel `gsd-project-researcher` agents for Stack, Features, Architecture, Pitfalls, then `gsd-research-synthesizer`); define requirements; `gsd-roadmapper` creates `ROADMAP.md`.
- Per phase: optional `/gsd-spec-phase` first ([spec-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/spec-phase.md); it settles what and why, and discuss-phase's `check_spec` step loads its `SPEC.md` as locked requirements); `/gsd-discuss-phase` ([discuss-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/discuss-phase.md)); `/gsd-spike` when feasibility is open; `/gsd-plan-phase` ([plan-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/plan-phase.md)) which runs `gsd-phase-researcher`, `gsd-pattern-mapper`, `gsd-planner`, `gsd-plan-checker`; `/gsd-execute-phase` ([execute-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/execute-phase.md)) with `gsd-executor` per plan in waves; `gsd-verifier` writes `VERIFICATION.md`; `/gsd-verify-work` is conversational UAT ([verify-work.md command](https://github.com/open-gsd/gsd-core/blob/next/commands/gsd/verify-work.md)).
- Commands under `commands/gsd/*.md` are thin wrappers that point at a workflow file; agents live in `agents/*.md`; shared rules in `gsd-core/references/*.md`; file templates in `gsd-core/templates/*.md`. Workflows call a `gsd_run query ...` tool for init data, hooks and gates, so some navigation and checks are scripts ([discuss-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/discuss-phase.md) initialize step, [plan-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/plan-phase.md) steps 13-13a).
- Gates: plan-phase refuses to mark a phase planned if the decision-coverage script fails (user may override, recorded in STATE.md); the plan-checker loop is capped at 3 revisions with a stall rule (below); the execute workflow filters plans by script-computed readiness and halts on blocked predecessors.

Also `.planning/spikes/` (with `MANIFEST.md`), `sketches/`, `quick/`, `todos/`.

### 3.4 Question-asking (how generated, how many, who answers, where recorded)
- Project level: ask "what do you want to build" as freeform text, then follow the user's thread with option-bearing questions; no fixed count; a "Ready to create PROJECT.md?" gate loops until the user agrees ([new-project.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/new-project.md) step 3).
- Phase level (discuss-phase): the model first loads project docs, up to three prior `CONTEXT.md` files (or a rolling decisions index), any spike/sketch findings, matched todos and a lightweight codebase scout (~10% of context), then identifies "gray areas": phase-specific implementation ambiguities that would change the result, not generic categories. It shows 3-4 of them as a multi-select; the user picks which to discuss. Default mode asks 4 single questions per area, each with 2-3 concrete options (recommended one marked, annotated with code context, an optional "you decide"), then offers "more questions or next area", and finally asks which gray areas remain unclear. Overlays: `--batch` groups 2-5 questions per turn, `--analyze` adds a trade-off table, `--auto` lets the model pick the recommended option and records it ([discuss-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/discuss-phase.md), [default.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/discuss-phase/modes/default.md)).
- Scope guard: the phase boundary comes from the roadmap and is fixed; discussion clarifies how, never whether to add capabilities; new ideas go to a "Deferred Ideas" section.
- Division of knowledge: the user is treated as owner of vision and preferences; things the code can answer (patterns, risks, implementation approach, success metrics) are explicitly not asked ([discuss-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/discuss-phase.md) philosophy block).
- Spec level (`/gsd-spec-phase`) is the most relevant mechanism for ShipLoop: a Socratic loop with quantitative gating. Four dimensions scored 0-1 by the model each round: Goal clarity (weight 35%, minimum 0.75), Boundary clarity (25%, 0.70), Constraint clarity (20%, 0.65), Acceptance criteria (20%, 0.70). Ambiguity = 1 - weighted sum; gate is ambiguity <= 0.20 and every dimension at or above its minimum. Up to 6 rounds, 2-3 questions per round, rotating "perspectives" (researcher, simplifier, boundary keeper, failure analyst, seed closer focused on the lowest dimension). On passing the gate the user may still ask for another round; at the cap the spec is written anyway with unresolved dimensions flagged, which the planner then treats as assumptions ([spec-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/spec-phase.md)). After the gate, an "edge-completeness probe" runs through a compiled script (below).
- Assumptions mode (alternative to asking): `gsd-assumptions-analyzer` reads 5-15 relevant files and returns assumptions with file-path evidence and a Confident/Likely/Unclear rating, with output size set by a calibration tier, and the user only corrects what is wrong ([gsd-assumptions-analyzer.md](https://github.com/open-gsd/gsd-core/blob/next/agents/gsd-assumptions-analyzer.md)).
- Recording decisions: `CONTEXT.md` holds `<domain>` (phase boundary), optional `<spec_lock>`, `<decisions>` as numbered `D-NN` entries (each may carry a reversibility rating of reversible/costly/one-way with a required rationale, and a one-way rating makes the planner insert a decision checkpoint before the implementing task), "Claude's Discretion", deferred ideas, `<canonical_refs>` (mandatory full paths to docs the user pointed at), and code context. A JSON checkpoint is written after each area so an interrupted discussion resumes ([context.md template](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/discuss-phase/templates/context.md)). Project-level decisions go to the Key Decisions table in `PROJECT.md` and the decisions list in `STATE.md`.

### 3.5 Research / spike / experiments
- Trigger: plan-phase asks "research first (recommended) or skip" with guidance (new features, unfamiliar integrations, architectural change vs bug fixes and well-understood work); skipped automatically with `--skip-research`, `--gaps`, `--reviews`; `--auto` follows config ([plan-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/plan-phase.md) step 5). The planner also classifies discovery level 0-3 (skip; quick doc check; standard research with a DISCOVERY file; deep dive) from signals such as a new dependency or "choose/evaluate" wording ([gsd-planner.md](https://github.com/open-gsd/gsd-core/blob/next/agents/gsd-planner.md)).
- Researcher output `RESEARCH.md` ([gsd-phase-researcher.md](https://github.com/open-gsd/gsd-core/blob/next/agents/gsd-phase-researcher.md)): first section copies the user's locked constraints; then Standard Stack, Architecture Patterns, Don't Hand-Roll, Pitfalls, Code Examples, State of the Art, an Assumptions Log (claim, section, risk if wrong), Open Questions (known / unclear / recommendation), Environment Availability (probes installed tools/runtimes/services with a fallback column), Validation Architecture (requirement -> test map, sampling rate, "Wave 0" gaps for missing test scaffolding), Security Domain. Every claim carries a provenance tag `[VERIFIED: ...]`, `[CITED: ...]` or `[ASSUMED]`, with strict rules about what earns VERIFIED (for example an in-repo enum counts only if the source file was opened this session and quoted verbatim, and a package found by search stays ASSUMED unless confirmed by official docs). ASSUMED items are routed to discuss-phase or the planner for user confirmation.
- Research is directed by a script seam: the agent writes a JSON list of questions, a `research-plan` query chooses providers and cache, and findings are cached.
- Resolution gate: plan-checker Dimension 11 fails (BLOCKER) if `RESEARCH.md` has an Open Questions section not marked RESOLVED ([gsd-plan-checker.md](https://github.com/open-gsd/gsd-core/blob/next/agents/gsd-plan-checker.md)).
- Spikes: `/gsd-spike` builds focused experiments, each with Given/When/Then validation questions and a verdict (VALIDATED, PARTIAL, INVALIDATED); a "frontier mode" proposes integration spikes for validated pairs and new spikes for gaps; wrap-up packages findings into a project-local skill that later discuss/plan steps read ([spike.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/spike.md)). `/gsd-sketch` does the same for UI.
- Optional `research_before_questions` config adds a brief web search before each discussion area and shows findings next to the question.

### 3.6 Task decomposition, dependencies, traceability
- A "plan" is one `NN-NN-PLAN.md` for a bounded unit. Frontmatter: `phase`, `plan`, `type`, `wave`, `depends_on`, `files_modified`, `autonomous`, `requirements` (required, must not be empty), optional `estimate` (tokens, tasks, confidence derived from sample count), `must_haves` with `truths` (user-observable behaviors), `artifacts`, `key_links`. Body sections: objective, context, tasks, optional threat model (STRIDE), verification, success criteria. Tasks carry `<files>` (exact paths), `<action>` (directive prose, no code blocks, includes what to avoid and why), `<verify>` with an `<automated>` command (a task with no existing test must name the Wave 0 scaffold that creates it), and acceptance criteria ([gsd-planner.md](https://github.com/open-gsd/gsd-core/blob/next/agents/gsd-planner.md)).
- Sizing: 2-3 tasks per plan; split if more than 3 tasks, multiple subsystems or any task touching more than 5 files; default decomposition is "tracer-first" vertical slices; the planner may not call a feature too hard to plan, and the only legitimate reasons to split or flag are context cost over about half a window, missing information, or a dependency conflict. Scope reduction wording ("v1", "static for now", "future enhancement", "placeholder") is prohibited; if everything cannot fit, return a phase-split recommendation for user approval.
- Dependencies/parallelism: waves come from `depends_on` and file ownership; a script (`phase-plan-index`) returns waves, readiness and `blocked_by`; plans in a wave touch non-overlapping files and run in parallel executors with fresh contexts; atomic commit per task ([execute-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/execute-phase.md) discover_and_group_plans).
- Traceability: ROADMAP phase -> REQ-IDs -> plan `requirements` frontmatter; discussion decisions `D-NN` -> cited inside plan tasks/must_haves; multi-source "source audit" in the planner covers GOAL, REQ, RESEARCH and CONTEXT items and returns an "unplanned items found" report rather than silently dropping any.

### 3.7 Verification before implementation
- `gsd-plan-checker` is adversarial by instruction (assume every plan set is flawed). Dimensions include requirement coverage, task completeness, dependency correctness, undeclared coupling, key links planned, scope sanity (tasks, files and context thresholds with warning and blocker levels), verification derivation (must_haves are user-observable), context compliance (locked decisions honored, deferred ideas excluded), scope-reduction detection, architectural tier compliance, Nyquist compliance (every task has an automated check), cross-plan data contracts, CLAUDE.md compliance, research resolution, pattern compliance, verify-command format and path resolvability, and numeric-claim authority. Each issue must carry severity (BLOCKER/WARNING/INFO), the violated `required_property`, and evidence; `fix_hint` is advisory ([gsd-plan-checker.md](https://github.com/open-gsd/gsd-core/blob/next/agents/gsd-plan-checker.md)).
- Revision loop: at most 3 iterations; issue count (blockers + warnings) must strictly fall each round or a stall prompt appears (proceed anyway / adjust approach, with re-planning re-entries capped at 2); an entry with missing severity counts as a blocker ([plan-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/plan-phase.md) step 12).
- Script gates after the checker: requirements coverage (every phase REQ-ID appears in some plan's frontmatter; CONTEXT features appear in plan objectives) and decision coverage (`check.decision-coverage-plan` returns JSON with covered/uncovered `D-NN`, blocking) ([plan-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/plan-phase.md) steps 13-13a).
- Optional: `/gsd-plan-review-convergence` loops plan -> external-AI review -> replan until no unresolved HIGH concerns, default max 3 cycles ([command](https://github.com/open-gsd/gsd-core/blob/next/commands/gsd/plan-review-convergence.md)).
- Post-execution: `gsd-verifier` works goal-backward (truths -> artifacts -> key links, with exists / substantive / wired / data-flows checks), distrusts SUMMARY claims, and classifies each truth VERIFIED / FAILED (blocker) / UNCERTAIN (human decision) ([gsd-verifier.md](https://github.com/open-gsd/gsd-core/blob/next/agents/gsd-verifier.md)).

### 3.8 State and brownfield
- `STATE.md` is the navigation layer every workflow reads first; `.continue-here.md` (pause-work) can carry "critical anti-patterns" that a resuming agent must restate understanding of before proceeding; discuss checkpoints are JSON; `/gsd-next`, `/gsd-progress`, `/gsd-resume-work` route from state ([state.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/templates/state.md)).
- Brownfield: `/gsd-onboard` routes through codebase map -> doc ingest -> project init -> onboarding summary, and `PROJECT.md` Validated requirements are inferred from existing code ([onboard.md](https://github.com/open-gsd/gsd-core/blob/next/commands/gsd/onboard.md)).
- Scaling ceremony down: `/gsd-fast` (inline, no planning), `/gsd-quick` (same guarantees, skips research, discussion, plan-checker and verifier by default; composable `--discuss`, `--research`, `--validate`, `--full`) ([quick.md](https://github.com/open-gsd/gsd-core/blob/next/commands/gsd/quick.md)).

### 3.9 Evidence of effectiveness
- None independent. README makes qualitative claims. Searches found only practitioner write-ups; the Pulumi comparison of Superpowers/GSD/GSTACK reports no measurements of its own (I fetched it: [pulumi.com/blog/claude-code-orchestration-frameworks](https://www.pulumi.com/blog/claude-code-orchestration-frameworks/)).
- One internal measurement in the edge-probe reference: a verifier reported about 0.93 confidence while catching none of 12 defects that came from edges the spec never stated, yet caught all defects whose edges were stated; the doc concludes the fix is spec completeness at the front of the pipeline ([edge-probe.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/references/edge-probe.md)). The corpus is tiny (the doc names three canonical defects) and no replication is linked.

### 3.10 Worth borrowing vs ceremony
- Borrow:
  1. The ambiguity gate: fixed dimensions, weights, per-dimension minimums and an overall threshold make "enough questions asked" computable. Caveat: the per-round scores are the model's own estimates; only the arithmetic is scripted, and the weights and minimums have no published calibration.
  2. The edge-completeness probe: a closed 8-category taxonomy (boundary, adjacency, empty, encoding, ordering, precision, idempotency, concurrency); a script classifies each requirement's shape first so only applicable edges are raised; each edge ends `resolved`, `dismissed` (needs a non-empty reason) or `unresolved`, with `explicit` vs `backstop` verification, and the script emits coverage counts ([edge-probe.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/references/edge-probe.md)).
  3. Stable IDs for decisions and requirements plus script gates that every ID is cited downstream; "proceed anyway" is allowed but recorded.
  4. Claim provenance tags and an Assumptions Log with "risk if wrong", with an Open Questions section that a checker refuses to pass until RESOLVED.
  5. The reversibility rating on decisions, which turns a one-way choice into a forced checkpoint.
  6. Environment Availability as a probed table with fallbacks; Validation Architecture with Wave 0 gaps.
- Ceremony or unproven: the size of the planning pipeline (plan-phase is a ~98 KB workflow with about 40 numbered sections and sub-steps; the discuss workflow is held under a 32,000-byte budget by lazy-loading mode files, and agents ship "compact" variants), 12+ checker dimensions each justified by a numbered issue rather than by measured benefit, per-phase artifact sprawl, and caps (3 revisions, 3 review cycles, 6 spec rounds).

### 3.11 GSD Pi (GSD 2 lineage) ADRs relevant to ShipLoop
- ADR-028 "grounded questioning": discuss units get a script-assembled preload (existing planning artifacts) plus a bounded codebase "Preparation Snapshot" (at most 5 files, 8 KB each, 3000-character brief) and must not run an open-ended repo survey before the first question; they read a specific file only when an answer hinges on it ([ADR-028](https://github.com/open-gsd/gsd-pi/blob/main/docs/dev/ADR-028-preload-authoritative-discuss.md)).
- ADR-029 reports a measured run trace on a 3-file app: about 115 tool calls across a retried research unit, 80-100% redundant, a timed-out unit that repeated 100% of the first run's commands, and three parallel validators each re-reading preloaded files; the fix was a bounded snapshot plus a project-size classification, forwarded evidence, and incremental saves so a re-dispatch resumes ([ADR-029](https://github.com/open-gsd/gsd-pi/blob/main/docs/dev/ADR-029-preload-authoritative-auto-research-validate.md)).
- ADR-011: plans written in full upfront go stale (a "roadmap still fine" reassessment almost always says yes), so it adopts sketch-then-refine planning per slice just before execution ([ADR-011](https://github.com/open-gsd/gsd-pi/blob/main/docs/dev/ADR-011-progressive-planning-escalation.md)). ShipLoop's per-work-item step-plan stage already follows this shape.
- ADR-046: a new project starts with discovery, research, requirements and roadmap milestones; new uncertainty creates targeted research dependencies instead of being guessed away; the agent asks one focused question, recommendation first with reason, evidence, confidence and what could change it; corrections supersede earlier decisions and trigger downstream revalidation; humans block only for missing authority/credentials, destructive or paid or public consent, materially ambiguous product intent with several valid routes, required subjective UAT, or a user-set limit; recovery picks one of retry, repair, replan, remediate, clarify, pause, abort ([ADR-046](https://github.com/open-gsd/gsd-pi/blob/main/docs/dev/ADR-046-database-authoritative-workflow-lifecycle.md)).

## 4. obra/superpowers (deep)

### 4.1 Phases, gates, who runs them
- Workflow per README: brainstorming -> using-git-worktrees -> writing-plans -> subagent-driven-development or executing-plans -> test-driven-development -> requesting-code-review -> finishing-a-development-branch ([README.md](https://github.com/obra/superpowers/blob/main/README.md)). Skills trigger automatically: [using-superpowers](https://github.com/obra/superpowers/blob/main/skills/using-superpowers/SKILL.md) says to invoke a relevant skill if there is even a small chance one applies, before any response including clarifying questions.
- Gates: a hard gate in brainstorming (nothing is built until the human approves the design document; spikes the human agreed to are the only exception) ([brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)); the plan is shown to the human for review and an execution method is chosen ([writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)); execution runs without check-ins and stops only for four conditions (irreversible or destructive action, security-sensitive action, side effect outside the worktree such as push or publish, or a plan so broken every path is a guess) ([executing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md), [subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)).

### 4.2 Prompt / template driving each phase
- Brainstorming (rebuilt in v7.0.0, retuned in v7.0.1): [SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md), [builder-check-prompt.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/builder-check-prompt.md), rationale in [2026-10-05 rebuild design](https://github.com/obra/superpowers/blob/main/docs/superpowers/specs/2026-10-05-brainstorming-rebuild-design.md).
- Planning: [writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md). Execution: [executing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md) with scripts [task-start](https://github.com/obra/superpowers/blob/main/skills/executing-plans/scripts/task-start) and [task-done](https://github.com/obra/superpowers/blob/main/skills/executing-plans/scripts/task-done); subagent route in [subagent-driven-development](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md) (implementer, task-reviewer and re-review prompts, `references/fix-loop.md`, `preflight.md`, `final-review.md`, scripts `sdd-workspace`, `task-brief`, `review-package`). Claims discipline: [verification-before-completion](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md).

### 4.3 Artifacts, lifetime, location
- Design doc: `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, committed, per feature; a small change gets agreed in chat with no file. Plan: `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`, committed, per feature. Execution ledger and briefs: `<repo>/.superpowers/sdd/<plan-basename>/` (git-ignored), first ledger line names the plan, deleted after a clean final review. The skills library itself is the "living" asset; there is no living product spec.

### 4.4 Question-asking
- Opening check: before replying, ask "what do I actually know about what they want and why?" If the request already contains everything that matters (their example is changing an icon colour), do it and say what was done; otherwise start the conversation.
- Look before you ask: in an existing project or when given a spec, plan or files, read them (and what they connect to) until able to explain how the relevant parts work and what the change touches; never ask what the project or the user's material already answers.
- First message: if the user already stated what they want, restate it in about 200 words (what, who, why as far as stated), add what was found that bears on it including conflicts or cheaper paths, invite corrections in one line, then ask one question about the thing the request leaves open whose answer would most change what gets built. If not, ask one open question about the biggest unsettled point and say what the answer would change. If the user did not ask for brainstorming by name, add a one-line offer to skip the questions.
- Conversation rules: exactly one question per message; plain language; open questions before menus (menus steer); propose something concrete if the user says "just guess"; Socratic questions that build on the last answer or a finding and say what the answer would change; probe which "how it gets made" choices (platform, language, libraries, medium) the user wants to own and record any default as the agent's call; cover goals, non-goals and anti-goals, prior art, current state, details they care about, as territory not a script.
- Playback: after understanding each part, describe it back in about 200-300 words and ask what is wrong or missing; mark anything the agent filled in as its proposal.
- Approaches: before writing the design, present two or three real alternatives in a message of their own, recommend one, and have the user pick.
- Sizing: after intent and approach, say whether the work is a quick task, a small change (design agreed in chat) or a project (written design), and let the user override.
- Builder check (done test for a project-sized design): a fresh subagent plays a skilled builder who cannot talk to the author, reads the document, and reports only the questions where a wrong guess would matter, ranked, each with why it changes the plan; it skips anything left to the builder; if nothing important is left it says `nothing important left`. The controller sorts the questions into three piles: already answered by conversation or project (put the answer in the doc), minor (decide and mark as the agent's call), and the user's (only they can answer and it changes what is built). The user's pile is asked in one message, most important first; this is the only round of questions the check produces ([SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md), [builder-check-prompt.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/builder-check-prompt.md)).
- Release-note evidence about the question style: v7.0.0 opened every session with the same generic question and users found the questions annoying and formulaic; v7.0.1 changed to digging for context first and asking about the one open thing; the maintainers expect to keep tuning ([RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)).

### 4.5 Research / spike / experiments
- No research agent by default. The brainstorming skill says to "offer recon" (look deeper into the codebase, the user's files, or the web, with the user deciding) and to offer a throwaway spike when a quick build is the cheapest way to learn what the user wants or whether something works; spikes skip tests and review and anything kept comes back through the design gate ([SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)).

### 4.6 Task decomposition, dependencies, traceability (writing-plans)
- A task is the smallest unit that carries its own test cycle and is worth a fresh reviewer's gate; fold setup, config and docs into the task whose deliverable needs them; split only where a reviewer could reject one task and approve its neighbour. Steps are single actions with a checkable result (write failing test, run, implement minimal code, run, commit). Plan header holds Goal, Architecture, Tech Stack, a link to the spec, a **Global Constraints** section (spec-wide requirements with exact values copied verbatim, implicitly part of every task) and a **Review Focus** section (the five failure modes or input classes the spec implies but no task's tests exercise, each given a test in the owning task). Each task lists Files (exact paths), **Interfaces** (what it consumes from earlier tasks and what it produces, with exact signatures, because an implementer sees only their own task), and steps with `Expected:` output. A plan longer than the code it describes has written the code instead; "TBD"-style lines decide nothing. Dependencies are expressed through order and Interfaces, not an explicit graph ([writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)).
- Self-review (a checklist the author runs, not a subagent): spec coverage (point to a task for each requirement), step scan, type/name consistency across tasks, Review Focus coverage, and proportion of plan length to spec length.
- Before Task 1, execution scans the plan's Interfaces for conflicts between tasks, one ledger row per consumer/producer pair, and rules on each with the spec as authority ([executing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md)).

### 4.7 Verification before and during implementation
- Before: plan self-review; builder check on the design; user approval of the design (hard gate) and review of the plan; pre-flight interface scan.
- During: `task-start` extracts the task brief and records the BASE commit; `task-done` runs the task's test command and appends the completion line to the ledger only if it passes, so a task cannot be recorded complete on a failing run ([task-done](https://github.com/obra/superpowers/blob/main/skills/executing-plans/scripts/task-done)). A "completion contract" requires evidence from this session for every named test and every `Expected:` line. Deviations from the plan must be ledgered as `Ruling: <decision> - <why> - <cost if wrong>`, and all rulings and deferred minors are listed in the final message ([executing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md)). The subagent route adds a fresh implementer and task reviewer per task, a fix loop, and a whole-branch review.
- `verification-before-completion`: no success claim without running the proving command in the same message and reading its output.

### 4.8 State and brownfield
- State: the git-ignored ledger `progress.md` (identity first line, one `Task N: complete (...)` line per task); after compaction the agent must trust ledger and `git log` over memory; the workspace and ledger are shared between inline and subagent execution so a plan can change executors mid-flight.
- Brownfield: handled by "look before you ask", building on what the project already uses, and worktree isolation; there is no codebase-mapping step.

### 4.9 Evidence of effectiveness
- Internal, honest measurements, no independent benchmark:
  - Release notes v7.0.1: in one test scenario, brainstorming skipped writing the design doc in 24 of 24 runs before a change and 3 of 24 after; a reported session lost the fix-loop round limit after context compaction truncated a skill past 20,000 characters and ran 18 fix rounds on one task; a session designed an iOS app, never asked about platform, and built a web app ([RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)).
  - Strict-cost SDD study: a ~$13 run on a Go example; most cost is controller turns and implementers; review-loop count (2-4 per run) is the biggest cost variance and is mostly caused by plan ambiguity the implementer resolved wrongly; a constraints header and Interfaces blocks were elicited reliably (0 to 5 of 5 runs, exact values) and a version-floor violation had shipped because constraints were not passed along; moving the controller to a cheaper model failed the pre-registered gates (planted defect shipped in 4 of 5 runs) ([strict-cost design](https://github.com/obra/superpowers/blob/main/docs/superpowers/specs/2026-06-10-strict-cost-sdd-design.md)).
  - Plan-scoped workspace evals: five reps per arm, scored by hand; the originally hypothesised failure (blind adoption of a stale ledger) did not reproduce in 25 of 25 reps, and the change was justified on structural grounds and a resume-cost measurement ([eval results](https://github.com/obra/superpowers/blob/main/docs/superpowers/specs/2026-07-06-sdd-plan-scoped-workspace-eval-results.md)).
  - Prompt wording micro-tests (5 reps, programmatic scoring): a prohibition on restating the brief produced more restating (4.4 spec values) than no guidance (3.6); a positive recipe produced 3.0 with zero variance ([positive-instruction design](https://github.com/obra/superpowers/blob/main/docs/superpowers/specs/2026-06-10-positive-instruction-redesign-design.md)).
  - Independent: a web search found only tutorials and install counts; the Pulumi comparison reports no measured results ([pulumi.com](https://www.pulumi.com/blog/claude-code-orchestration-frameworks/)).

### 4.10 Worth borrowing vs ceremony
- Borrow: the builder check as a stage exit ("what would a fresh reader still need to ask?") with the three-pile triage and a single batched user round; the opening "what do I actually know" check and quick path; playback-and-correct; approaches in their own message; Global Constraints, Interfaces and Review Focus blocks in plans; `task-done` style scripts where the ledger line exists only if the proof command passed; `Ruling:` lines with cost-if-wrong, and a final list of every decision taken on the user's behalf; recipe-form instructions instead of prohibitions for composition behaviours; keeping SKILL text short enough to survive truncation.
- Ceremony or unproven: absolutist trigger language, rationalization tables and "iron law" framing are behavior shaping without outcome measurement; a seven-skill chain even for small work (mitigated by the quick path); the questioning style itself needed a retune after user complaints.

## 9. Cross-cutting evidence (what exists)

- Vendor benchmark, not independent: Uvik Software ran 50 brownfield Python tickets (five client repos, 10 per category, five engineers, each ticket in one arm, blind senior reviewer, `claude-sonnet-5` in all arms, Claude Code except Kiro in its own IDE), arms Spec Kit 1.0, Kiro, BMAD 6.x, OpenSpec (propose/apply/archive) and a no-spec control; merge rates 80% / 82% / 82% / 84% vs 72% control; the authors state a plus/minus 10-point noise band and decline to rank arms inside it. By ticket type, spec arms gained most on feature and data-pipeline tickets (about +30 points, e.g. 60% control) and nothing on bug-fix and refactor tickets; by size, no gain for 1-2 file tickets (85% control vs 85% best spec) but 70% vs 85% at 3-5 files and 50% vs 80% at 6+ files; spec phase consumed 28-44% of tokens; review defects per merged ticket 0.86 control vs 0.39-0.57 spec arms; merge rate was higher when the spec covered at least 6 of an 8-item checklist (81-93%). Disclosures: Uvik sells Python/AI staffing, one team, Python only, one model; the page header says last updated 2026-10-08 while the run date is stated as 2026-10-15. Raw CSV is published under CC BY 4.0. Source: https://uvik.net/blog/spec-driven-development-benchmark/ (fetched and numbers re-checked in the raw HTML). It does not test GSD, Superpowers, Taskmaster, PRP or SPARC.
- Academic caution about adding context: Gloaguen et al. (ETH Zurich), "Evaluating AGENTS.md", arXiv 2602.11988 (submitted 2026-02-12, v3 2026-09-29): repository-level context files did not generally improve task success and raised inference cost by over 20% on average across models and agents; instructions in them were followed, but repository overviews did not help. I read the abstract page only: https://arxiv.org/abs/2602.11988. Relevance: extra prompt context has a cost and needs evaluation.
- Qualitative third-party review: Böckeler (Thoughtworks, martinfowler.com, October 2025) tried Kiro, spec-kit and Tessl on small tasks, one attempt each, no metrics; found the workflows oversized for a small bug and a modest feature, markdown specs tedious to review, agents ignoring parts of the specs, and non-deterministic regeneration: https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html (read through the fetch tool's summarizer).
- Pulumi's comparison of Superpowers, GSD and GSTACK: few weeks of use, no measurements of its own: https://www.pulumi.com/blog/claude-code-orchestration-frameworks/.
- Search results also surfaced a single-developer token comparison (OpenSpec vs Spec Kit) and a speed anecdote; I did not open those sources and do not rely on them.

### Top 5 ideas worth borrowing
1. Question triage and the ask-threshold: classify every open question as answered-by-repo, assume-and-log, or needs-user, and interrupt only for needs-user that would change scope, observable behavior, compatibility or acceptance; one question at a time, each saying what it unlocks, ordered so blocking decisions come first. Sources: [OpenSpec explore.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/explore.ts), [OpenSpec propose.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/propose.ts), [Superpowers brainstorming](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md), [GSD Pi ADR-046](https://github.com/open-gsd/gsd-pi/blob/main/docs/dev/ADR-046-database-authoritative-workflow-lifecycle.md).
2. A fresh-reader readiness check as the exit of elaboration: a clean-context reader lists the questions it would still need answered, ranked with why; triage into answered / minor / user's; one batched user round at most. Source: [Superpowers builder-check-prompt.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/builder-check-prompt.md).
3. A script-computable clarity gate plus a closed edge taxonomy: fixed dimensions with weights and minimums, edges resolved or dismissed with a reason, script-emitted coverage. Caveat: model-estimated scores, no calibration data. Sources: [GSD spec-phase.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/spec-phase.md), [GSD edge-probe.md](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/references/edge-probe.md).
4. Stable IDs with script-checked coverage across stages: decision and requirement IDs that downstream items must cite, with the gate result and any override recorded. Sources: [GSD plan-phase.md steps 13-13a](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/plan-phase.md), [OpenSpec constants.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/constants.ts).
5. A research and spike contract with pre-registered falsifiers and provenance tags: spike only when uncertain, falsifiable, architecture-changing and cheap to test; write kill criteria and verdict boundaries before building; tag claims VERIFIED/CITED/ASSUMED; hold planning while Open Questions are unresolved. Sources: [PRP prp-spike](https://github.com/Wirasm/prp/blob/development/.claude/skills/prp-spike/SKILL.md), [PRP planning-craft.md](https://github.com/Wirasm/prp/blob/development/.claude/skills/prp-plan/references/planning-craft.md), [GSD phase-researcher](https://github.com/open-gsd/gsd-core/blob/next/agents/gsd-phase-researcher.md).

Runners-up: grounded questioning with a bounded script snapshot instead of an open survey ([GSD Pi ADR-028](https://github.com/open-gsd/gsd-pi/blob/main/docs/dev/ADR-028-preload-authoritative-discuss.md)); `task-done` style ledger lines gated on the proof command ([Superpowers](https://github.com/obra/superpowers/blob/main/skills/executing-plans/scripts/task-done)); Global Constraints and Interfaces blocks ([writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)); deterministic dependency validation ([Taskmaster](https://github.com/eyaltoledano/claude-task-master/blob/main/scripts/modules/dependency-manager.js)); delta-style living spec with archive merge ([OpenSpec concepts](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)); reversibility rating that forces a checkpoint on one-way decisions ([GSD context template](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/discuss-phase/templates/context.md)).

### Looks like ceremony without evidence (or with evidence against)
- Running the full question/spec stack for every request: the only quantitative data (Uvik) shows no gain on 1-2 file or bug-fix and refactor tickets and a 28-44% token share for the spec phase; Böckeler found workflows oversized for small tasks; GSD and Superpowers both ship skip paths (`/gsd-quick`, `/gsd-fast`, the brainstorming "quick, clear task" path), and Agent OS v3 removed stages. Any ShipLoop question stage should be size- or ambiguity-gated, and its value should be measured on ShipLoop's own E2E rounds, not assumed.
- Model-judged phase gates with count or percentage proxies (SPARC's at least 3 ACs, coverage over 80%); structural smoke tests presented as validation (SPARC README admits this).
- Fixed, formulaic question openers: Superpowers' own users complained and the maintainers retuned.
- Large always-loaded prompt text: Superpowers measured that text past 20,000 characters is lost after compaction and moved material into on-demand reference files; the ETH study found extra context files raised cost over 20% with no general success gain.
- Numeric thresholds with no calibration (GSD ambiguity weights, Taskmaster 1-10 complexity, OpenSpec 500-character cap): cheap to compute but treat as tunable defaults.
