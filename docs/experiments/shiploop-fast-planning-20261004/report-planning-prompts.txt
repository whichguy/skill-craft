## 4. THE BACKCHAIN ONE-PASS CHANGE

### 4.1 What the runtime supports [M]

In `skills/improve/runtime/until-loop/scripts/until_loop_ephemeral.py`, the completion test is `exit_assessment == satisfied and (trivial_streak >= required_trivial_reviews or unchanged_first_pass)`.
- `required_trivial_reviews` accepts 0, 1 or 2. The runtime reference says "satisfied plus the count gate completes".
- At gate 2, `unchanged_first_pass` completes after one pass only if the first pass is trivial and the workspace tree is unchanged. That never happened here, because pass 1 changed the candidate.
- At gate 1, a pass that repairs anything is non-trivial. `convergence.md` says edits to obligations, suppliers, edges, ordering or verification are non-trivial even if repaired. So gate 1 needs a trivial pass after the last change.
- At gate 0 the loop ends the first time the host reports `satisfied`.
- ShipLoop's own quality loop and test loop use gate 1, and `references/execution-planning.md` documents a selective per-step loop at gate 0. Gate 0 is not new to the repo.

### 4.2 What it would have saved on the 1.16.1 plan loop (exporter pass minutes)

| Gate | Plan loop | Step-plan loop |
|---|---|---|
| 2 (today) | 7 passes, 103 min | 4 passes, 107 min |
| 1 | completes at pass 6 [M]; saves pass 7 (4 to 5 min) | completes at pass 3 [M]; saves pass 4 (4 min) |
| 0 | completes at pass 1; saves 92 to 94 min | completes at pass 1; saves 65 to 66 min |

- The gate-0 figures assume the host reports satisfied at pass 1. In 1.16.1 it reported unsatisfied through pass 6 because the exit condition it wrote required two reviews [M]. The exit text must change with the gate.
- The 66-min step-plan figure applies only if the step-plan loop recurs.

### 4.4 Design

- Default: gate 0 with an exit condition that a single complete review pass counts. Its findings are repaired and rechecked inside that pass, and the printed `backchain-check` passes on the final candidate.
- Opt-in flag `converge` restores today's two-clean gate. Mechanism, in order of preference:
  - **Recorded start option**, like `--lint` and `--delegation`: it sits in state.md and a script constant produces the text. This adds a state key, so older saved states are refused, which is consistent with "one supported version".
  - **Environment variable**: no state change, but not recorded in state, so a mid-run environment change would print different text. Worse under S-1.
- Strict enforcement needs a script-written Backchain contract (a02). `loop_contract.contract()` already exists as the one shape of a ShipLoop-written Until Loop contract, and Backchain's child is the hand-built exception (the harness counts it as glue).
- Pair the pass with a script-run check (S-9). The step-plan loop's pass-1 repair added a discovered step D1 that nothing consumes. Passes 2 to 4 and Improve accepted it, and the reference validator rejects it [M, journal "Second correction"]. A script check at exit finds what 4 model passes missed, and it takes seconds.

### 4.5 SPEC carve-out (proposed wording, own commit before the prompt change)

S-10 gains: "Owner decision 2026-10-04: Backchain's planning loop (a whole `plan`/`draft` or `repair`/`revise`) ends by default after one complete review pass whose findings are repaired and rechecked, with a script-run `backchain-check` as exit evidence; the two-consecutive-trivial gate is opt-in. Quality, test and Improve loops keep S-10 unchanged."

Gate 0 is not an iteration cap in the runtime's sense, and the loop still ends on a stated condition. The condition is weaker and the cap is effectively 1 in a normal run.

### 4.6 Adversarial scenarios, one line each (SPEC change-admission shape)

1. The host reports "unsatisfied" at pass 1 anyway. The loop continues and nothing is saved. The next run's pass count shows it.
2. A pass-1 repair introduces a defect no pass rechecks. Mitigated by `backchain-check` and the Improve loop that follows. A residual risk is accepted.
3. Standalone Backchain callers must keep gate 2, so the skill default stays 2 and ShipLoop passes its own gate.
4. Another host or style: the text is generic and Sonnet never runs a loop, so there is no effect.
5. Saved runs: text-only means no refusal. A recorded option adds a state key, so old states are refused.
6. Gaming: a "satisfied" with no check. `backchain-check`'s receipt in `evidence_refs` is already required by BACKCHAIN_CHECK.
7. Pins gating a future obligation: re-pin by content, not by counts.
8. Spec drift: carve-out in its own commit.

## 7. MEASURABILITY

- **The in-progress run measures I2b only.** None of the proposed changes can show in it.
- **The next run, on a release carrying the change,** shows the effect in:
  - Stage minutes from the exporter's accept-to-accept deltas (`review-export/`, `docs.runs[...].stages[].min`). Compare plan against 196.4 min. The harness `metrics.json` stage minutes are known to be misattributed.
  - The Backchain ledger: pass count and `facts` (Passes, Trivial streak "x of y required"), `segments` (Pass 1 only).
  - Receipts: `scratch/backchain-plan/until-loop-start-input.json` and `until-loop-receipt.json` should show `required_trivial_reviews: 0` and one `action1-done-packet.json`.
- **Only a loop-level change shows up through the noise.** Stage times vary about 2x run to run, so the next run can detect the gate change (more than 90 min) but not packet trims (under 10 min).
- **A seeded run cannot test it.** `--seed-at` accepts only `step-plan`, and the gate is at plan. A plan-stage measure needs an unseeded Luna run, or the Backchain evaluation harness on planted drafts.
