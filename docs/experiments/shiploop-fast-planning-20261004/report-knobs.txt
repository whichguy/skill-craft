1. [M] Three different parties decide pass counts.
   - The Backchain whole-loop child (plan/draft, and repair/revise) has a contract the host model writes by hand. No ShipLoop script writes, reads or checks it. The value `required_trivial_reviews: 2` comes from skills/backchain/references/convergence.md and is echoed in ShipLoop's plan packet.
   - The ShipLoop Improve children have a contract ShipLoop writes (`improve_start_contract` in skills/shiploop/scripts/shiploop_navigator.py). It is a literal 2. The import validator refuses anything below 2.
   - The test loop (test-green, regression) and quality loop (static-checks) are written by ShipLoop with gate 1. They are S-10 loops and out of scope.

2. [M] The vendored Until Loop can do one pass without any change to the vendored files.
   - Its contract takes `required_trivial_reviews` (default 0).
   - It has no max-iterations or budget field.
   - Gate 0 completes on the first report that says `exit_assessment: satisfied`, whatever that pass found.
   - Gate 1 does not give one pass when the first pass changes the candidate.
   - Experiment tables are in section 3.

3. What "one pass" means when the first review CHANGES the candidate (what the owner asked for).
   - It means gate 0 plus an exit condition the model can assess as satisfied after one cycle.
   - The pass reviews, repairs and runs the checks on the repaired candidate.
   - It reports `non-trivial` with exit `satisfied`, and the loop completes. There is no confirming review of the repair.
   - If the pass itself reports an open gap (`unsatisfied` or `unknown`), the loop still continues. So it is "one pass unless that pass reports an open gap", not a hard cap.
   - The runtime has no field for a hard cap [M]. Hard-capping would need a runtime change, and the provenance tests forbid that.

4. [M] Backchain one-pass is a text-and-state-option change with no validator change. Improve one-pass is a larger change. ShipLoop's own import validator refuses any Improve terminal packet below gate 2, or whose last report is not `trivial`. I demonstrated that in a scratch run.

5. [M/I] Where the time goes in the 1.16.1 Luna run.
   - Backchain and Improve loops took about 83% of the planning window (intake through the first W1 test-spec accept, 647.5 min).
   - Packets are not the driver. Sonnet planned the same request in a few minutes.
   - Luna's per-pass cost is about 38 times Sonnet's, while Luna has only about 1.7 times as many Improve passes.
   - One-pass Backchain saves an estimated 153 min. One-pass Improve saves 96 min in the planning window and 126 min over the whole run. Together that is about 249 min of the 647.5-min planning window.
   - Even with both, about 400 min of planning remain. One-pass alone does not make Luna max fast.

6. The change needs an explicit SPEC S-10 amendment. S-10 says review loops have no iteration cap and run until a stated condition. A default one-pass exit is a carve-out. Proposed wording is in section 6.

7. Flag home. `delegation` and `lint` are the only run-level options. Both live in state.md and are set by `init` and `workspace start`. They are changed mid-run by `delegation --set` and `lint-mode --set`. A third option (proposed name `planning-loops`, values `one-pass` default and `full`) follows the `lint` precedent exactly.

8. Suggested order, each increment verified by a script-run test:
   - A: Backchain one pass (explicit owner request).
   - B: Improve planning children one pass. The owner must confirm this one; he only said "Backchain" explicitly.
   - C: a script-written Backchain contract (a02) if a live run shows the model ignoring the printed gate.
   - D: option to not offer Backchain at all.

3. THE VENDORED UNTIL LOOP (what it accepts and when it completes) [M]
====================================================================

Files: /Users/dadleet/src/skill-craft/.claude/worktrees/a1a3-integ-7f216e/skills/improve/runtime/until-loop/ (ADAPTER.md, scripts/until_loop_ephemeral.py, references/runtime-ephemeral.md, PROVENANCE.json). The copy under plugins/skill-craft/... is release output.
Provenance pin: test/improve.test.sh checks the sha256 of ADAPTER.md, until_loop_ephemeral.py and runtime-ephemeral.md against PROVENANCE.json. Contract values are not vendored, so a different `required_trivial_reviews` touches no hash.

Contract fields [M, schema_experiment.py]:
  workspace, work, exit_condition, repeat_condition, required_trivial_reviews, context{request, scope, authority, environment, resources[{purpose, locator}]}.
  Anything else is refused: `max_iterations` and `budget` both gave "contract has an invalid schema".
  `required_trivial_reviews` is optional, default 0, a non-negative integer; negative, string and boolean are refused.
  The only size limit is the 16 KiB state file (MAX_STATE_BYTES).

`done` completes the run when (`done` in until_loop_ephemeral.py):
  exit_assessment == "satisfied"
  AND (trivial_streak >= required_trivial_reviews OR unchanged_first_pass)
  and continuation is not "cancelled".
  `unchanged_first_pass` is: first report trivial, action 1, the workspace Git tree identical to the tree recorded at start. The tree is recorded only when the gate is 2 or more.
  "blocked" before completion stops the run. "unresolved" with "satisfied" is refused.
  The streak adds 1 for trivial and resets to 0 for non-trivial or unresolved.

Scratch experiment (/private/tmp/claude-501/-Users-dadleet-src-skill-craft/f7d9360d-b88d-417b-8773-fc5b3eee6419/scratchpad/fast-planning/gate_experiment.py) [M]:

  gate 2, first pass trivial and Git tree unchanged:        complete after 1 pass (unchanged_first_pass)
  gate 2, first pass trivial but edited:                    2 passes
  gate 2, first pass non-trivial/unsatisfied, then T, T:    3 passes
  gate 2, non-trivial first pass with exit satisfied:       still 3 (the gate holds it)
  gate 1, first pass trivial:                               1 pass
  gate 1, first pass non-trivial and edited, then trivial:  2 passes
  gate 0, first pass non-trivial and edited, exit satisfied: complete after 1 pass, streak 0
  gate 0, first pass non-trivial, exit unsatisfied:         continues; completes at the next satisfied report
  gate 0, unresolved + satisfied:                           refused by the runtime

So, as stated in the bottom line: gate 0 plus an exit condition satisfiable after one cycle is the owner's "only 1 pass". The model's `exit_assessment` stays the safety valve. A wrong exit text defeats it: Luna's 1.16.1 contracts said "after two distinct complete trivial/no-change reviews", and Luna reported `unsatisfied` on every earlier pass.
