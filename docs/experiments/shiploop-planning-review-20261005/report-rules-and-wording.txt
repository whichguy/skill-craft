## 1. BOTTOM LINE

1. **The option plumbing is verified.** A recorded state key with a flag on `init` and `workspace start`, no `--set`, a retry guard, and a refused saved run without the key follows the `backchain_passes` precedent exactly. I built it in a scratch prototype and it works end to end:
   - the flag records the key in state.md;
   - the default is recorded when the flag is omitted;
   - a retry naming another value is refused;
   - an invalid value is rejected by argparse.
2. **The candidate's per-item merge should be dropped.** Moving the step-plan review to a single child after test-spec has a structural hole. A child anchored at `test-spec` cannot revise the step plan's `steps`, `paths`, `criteria` or `test_commands` [M, `_canonical_result`; run in the prototype, E2]. It would save at most the test-spec child's own minutes (Luna 14.2 and 12.1, Grok 3.0).
3. **Recommended `once`.** One Improve child at `plan` covering spec, test-strategy and plan together (80% of Luna's review minutes, 79% of Grok's). Per-item `step-plan` and `test-spec` children stay as today.
4. **The option must name five stages, not seven.** `guidance.PLANNING_REVIEW_STAGES` has seven members. `system-test-author` and `release-plan` are in it, and the owner wants them untouched.
5. **A hard engine invariant would refuse every `once` or `none` state.**
   - `_validate_current_state` requires an Improve record for every history entry at those seven stages.
   - Verified in the prototype: with the mode-aware change the engine accepts such runs, and without it the refusal is "Improve results must belong to completed steps, including every planning-stage result".
6. **There is a silent breakage outside the engine.** `skills/shiploop-e2e-audit/harness/workflow_review._observed_improve_actions` marks an engine-valid `once` run as comparable=False (unverified, no error) [M, experiment exp_workflow_review.py].
7. **The 30-minute ceiling is not reachable by this change on either measured configuration.**
   - Grok medium: even `none` leaves 30.3 min. `once` leaves at least 39.2, with the merged child's own cost unknown.
   - Luna xhigh: `none` leaves 172.5 min and `once` at least 213.4 (section 2).
8. **Blast radius of flipping the default to `once`, measured on a prototype with the real suites.**

   | Variant | Newly failing tests | Suites |
   |---|---|---|
   | Owner's candidate (plan plus per-item test-spec) | 140 | 22 |
   | Recommended `once` | 116 | 20 |
   | Pure API stays `stage`, CLI defaults `once` | 33 | 4 |

   The split-default variant is a lint-style trap and I recommend against it.
   - Roughly 70% of the failures are fixtures that use `spec` as a convenient first Improve checkpoint.
   - Roughly 30% are real schedule pins (counts, order, names).
   - Details in section 8.
9. **Sequence the work so the default flip is its own last commit.** The mechanics land first with default `stage`, which keeps every existing test green.
10. **`none` is a bigger relaxation than `once`.** It removes the planning-experiment and reconcile route, because those need the bound initial plan Improve child. Ship it later, after `once` is measured live.

## 3. CODE FACTS THE DESIGN RESTS ON

**C1.** `shiploop_stage_spec.Stage.improve` is "always", "last-item" or None.
- "always" belongs to seven stages: spec, test-strategy, plan, step-plan, test-spec, system-test-author, release-plan.
- `guidance.PLANNING_REVIEW_STAGES = stage_spec.with_improve("always")` is therefore seven stages.
- Used by `_improve_checkpoint`, `_IMPROVE_STAGES`, the `_validate_current_state` record check, `_improve_line`, `_render_improve` (focus text), `STEP_PLANNING_STAGES`, and the dry-run and apparatus oracles [M].

**C2.** `_improve_checkpoint(state, stage, result)` is the only place that decides whether a producer result parks an Improve child [M]. `apply` creates `active_improve` only if it returns True. Otherwise `_apply_result` advances directly, the same path as `intake` or `prepare`.

**C3.** `_validate_current_state` computes the set `planning` of history actions at `PLANNING_REVIEW_STAGES` (excluding N/A test stages) and requires `planning <= set(improve_results) <= expected` [M]. It also asserts `_improve_checkpoint(...)` for any `active_improve`. The message "a stage that never starts an Improve child; only planning stages and the final carry-forward do" becomes self-contradictory in `once` [M, exp_forged.py]. A forged child at spec in once is refused with exactly that text, while spec is a planning stage.

**C4.** Extra records are allowed, because `records <= expected` [M]. Mode ordering stage ⊃ once ⊃ none means a mid-run switch toward fewer reviews would always be state-valid, and the opposite never. That is one more reason for "no `--set`" besides KISS [I].

**C5.** The producer's `complete` path runs the same script gates as `improve-complete` [M, `dispatch`]:
- `_check_submitted_evidence`
- `_check_submitted_assumptions`
- `_check_submitted_test_commands`
- `_check_submitted_consumer_entry`
- `_check_submitted_recorded_commands`
- `_check_submitted_awaiting`
- `_knowledge_gate`

So under `once` and `none` no script check is skipped at spec or test-strategy. What is lost is the model-run review, plus a second application of the gates to a child's revised final_result.

**C6.** S-11 is independent of Improve [M]. `knowledge.commit` runs "after an accepted stage that changed [the knowledge home] (every stage, not only closes)", and the closes are `prepare`, `test-spec`, `release-plan` and `release-verify`. The privacy screen and the dropped-requirement-ID check run on every stage that changes the home. Consequence: under `once` and `none` the spec is committed to docs/shiploop/ before any review, and later runs inherit it.

**C7.** `_canonical_result` allows `steps`, `paths`, `criteria` and `test_commands` only on a done step-plan result [M]. A child at test-spec canonicalises its final_result with stage test-spec. Experiment E2 in the prototype:
- `steps`, `paths` and `test_commands` in a test-spec child's final_result are all REFUSED.
- Outcome `revise` is ACCEPTED by the pure `finish_improve`: the item returns to step-plan and uses one of its two revisions.
- The packet text says a child's final_result outcome is done, repeat, blocked or, at OUTER stages, replan. So `revise` from a child is undocumented, and I did not verify the CLI route with it [I].

**C8.** `improve_start_contract` writes the child's frozen exit condition and appends `loop_contract.stage_exit(child["stage"])` [M]. That is the one stage's own done_when. This is the script-written carrier of "iterate until a stated check confirms each exit criterion". For a merged plan child it must carry spec's, test-strategy's and plan's done_when lists, plus the covered results' locators in the scope.
- Measured size: spec 310 B, test-strategy 254 B.
- Measured effect on the host-writable opening allowance (`improve_opening_allowance`): spec child 5,262 B, plan child 4,869 B today.
- With the covered criteria and locators added in the prototype, the plan child's allowance is 3,954 B (−18.8%).
- CONTRACT_BUDGET is 9,216 B and derives from the vendored Until Loop state cap, so it cannot simply be raised.
- Existing precedent: `improve-start` refused an oversized opening 4 times in the old run, 3 of them on size [per the fast-planning plan, c8].

**C9.** `_render_improve` attaches planning experiments, the assumption-list text and the reconcile route only when `child["stage"] == "plan"`. `_reconciliation_permitted` requires the bound active initial plan Improve child [M]. Experiment E3 on `none`: after the plan result the stage is prepare with no child, and reconcile is refused. `planning-experiments.md` states the duty applies only to that child. Under `none` the experiment and reconcile machinery is unreachable. `_check_submitted_assumptions` still enforces the assumption list at the producer's submit.

**C10.** Text that becomes false when a stage skips its child [M]:
- `_improve_line`: "Every {stage} result, including blocked and repeat, starts this action's Improve child."
- `guidance.COMMON`: "Only planning results (spec, test-strategy, plan, step-plan, test-spec, system-test-author, release-plan) and the carry-forward ... get an actual Improve-skill handoff".
- `DUTIES["plan"]`: "mandatory actual Improve handoff. The plan remains a draft until that loop completes".
- `DUTIES["step-plan"]` and its `_INLINE_DUTY_PARAGRAPHS` variants: "mandatory actual Improve loop must review the created steps".
- `DUTIES["test-spec"]`: "The next review is the packet's automatic Improve handoff immediately after this producer result".
- Under the recommended `once`, only `_improve_line` for spec and test-strategy and `COMMON` change. Under `none` all of the above change.

**C11.** Planning stages: child text is large. `improve_prompt` is 9.5, 9.4, 10.9, 11.4 and 8.9 KB for the five stages, about 50 KB across them [M]. A merged plan child needs 18 reference locators against plan's 12 (six added: Behavior-model, Behavior traceability, Repeatable test-suite, Target-native test selection, Test-case planning, System-test catalog) [M]. Net printed text per run falls [I].

**C12.** Tolerant by construction, because these read records through `.get` or skip when absent [M]:
- `shiploop_planning_context._collect_improve_artifacts` and `_improve_projection`
- `shiploop_context_index._entry_lines`
- the navigator's packet "Prior Improve evidence" line (written only when a record exists, as for intake today)
- `narrative_facts`
- the "(reviewed by Improve)" marker
- `_render_report`

No script subscripts `improve_results[...]` except reconcile paths, which need the plan child.

## 4. THE DESIGN: VERIFIED, REFINED, REPLACED

**Option.** Key `planning_review`, flag `--planning-review stage|once|none` on `init` and `workspace start`. Same shape as `backchain_passes` and `lint`:
- recorded in `_STATE_KEYS` and `new_state`;
- validated in `_validate_current_state`;
- a `recorded_planning_review(state)` accessor;
- a `_require_retry_planning_review` guard in `shiploop_protocol` (a retry naming another value is refused, and no `--set`);
- a saved run without the key refused by the existing generic missing-fields check with `FRESH_RUN_HINT`;
- recovery retry cannot change it.

**Which stages start a child.**

| Mode | Children for a 2-item run | Which stages |
|---|---|---|
| stage | 10 | spec, test-strategy, plan, step-plan, test-spec (per item), carry-forward (last), system-test-author, release-plan |
| once (recommended) | 8 | plan, step-plan and test-spec per item, carry-forward (last), system-test-author, release-plan |
| once (owner's candidate) | 6 | plan, test-spec per item, carry-forward (last), system-test-author, release-plan |
| none | 3 | carry-forward (last), system-test-author, release-plan |

Single definition site, as `offers_whole_backchain_loop` is for Backchain: `guidance.starts_planning_review(stage, mode)`.
- It is True for any stage outside the five.
- It is True for all five under `stage`.
- It is False for the five under `none`.
- Under `once` it is True for plan, step-plan and test-spec.

Consumers: `_improve_checkpoint`, the `_validate_current_state` record set, and the dry-run and apparatus oracles.

**What changes under `once` (recommended), by symbol.**
- **Engine:** `_improve_checkpoint`; the `_validate_current_state` record set; the forged-child message.
- **Script-written contract:** `improve_start_contract` plus `loop_contract.stage_exit`. For the plan child under `once`, add spec's and test-strategy's done_when to the exit condition, and append the covered results' locators to the scope. Prototype allowance numbers are in C8.
- **Text:**
  - `_improve_line` becomes mode-aware: spec and test-strategy say "advances directly; one planning review runs after plan".
  - `COMMON` is reworded.
  - `IMPROVE_SCOPES["plan"]` and `improve_prompt("plan")` name three documents.
  - `PLANNING_REVIEW_FOCUS` gains a cross-document consistency clause, which is a benefit a per-stage child cannot deliver [I].
- **Docs and tests:** see section 7.

**Reject the owner's per-item merge** (candidate: the step-plan and test-spec reviewed once after test-spec).
- Structural hole (C7).
- Saving at most the test-spec child's cost: Luna 14.2 min (W1) and 12.1 (replan), about 9% of Luna's Improve minutes in the run; Grok 3.0 (7%).
- Test and fixture churn differs by only 24 tests (140 versus 116).
- The merged child still needs `revise` as an escape route, which has no tested path and carries the 165.9-min replay cost.
- Possible later alternative: keep only the step-plan child and drop the test-spec child. That has no structural hole and saves exactly the test-spec child. But the old 1.16.1 run's test-spec children did change things (5 passes, 54.5 min), so it is unproven.

**`none` (later increment).**
- Planning experiments and reconcile are unreachable (C9).
- Knowledge is committed unreviewed (C6).
- The assumption list is still script-enforced at the producer.
- Producer sentences in C10 must change.
- `planning-experiments.md`, `improve-context.md` and `SKILL.md` ("The existing Plan Improve child investigates consequential assumptions") need a `none` clause.

**Default flip handling.** A single default (`once`) is needed. A lint-style split, with the pure API defaulting to `stage` and the CLI to `once`, drops churn to 33 tests but means pure-navigator tests no longer exercise what production runs. SPEC Change admission names "pass the tests while failing a live run" explicitly. Rejected.

## 5. OWNER RULES IN TENSION, AND WHAT CARRIES THE EXIT CRITERION

- **"Steps iterate until a stated check confirms each exit criterion" (primary).**
  - Today each planning stage's exit is confirmed by its own child. The script freezes that stage's done_when into the child's exit condition via `stage_exit` (C8). The pass judgement is the model's: planning passes are "self-passes by this same executor" [M, `_render_improve`].
  - Under `once`, spec's and test-strategy's criteria are not confirmed by any loop when the stage is accepted. The deferred confirmation is the plan child, whose frozen exit condition (extended by this change) names all three stages' done_when. The tension is real: spec and test-strategy are accepted, and test-strategy and plan are written against them, before any review.
  - Under `none`, no loop ever confirms them.
- **S-9 (passing script-run check is the evidence).**
  - Present on every path: the C5 gates, `backchain-check` (structural, record-only), `_planning_sources_current`, and the knowledge gates (required files, privacy screen, no dropped requirement ID).
  - The first script-run proof of planning-document content is `test-red`, which fails the stage unless the focused commands fail for the right reason. That is the check that caught the W1 defect both times, at 123–166 min of redo.
  - Neither review mode changes that exposure, because the review missed it in both runs (n=2, one request) [from the ledger].
  - Not present: requirement-ID traceability across strategy, plan and test-spec. `knowledge.check` only compares the spec's `R-n` set with the committed one. This is ledger lever L11 and the Luna review's first warranted-fix class; I recommend it as a follow-up before `none` claims any S-9 compensation. It is not part of this change.
- **S-10.** `once` keeps S-10 for each child that runs (no cap, exit until condition). `none` relaxes it for five stages.
- **S-11.** Unaffected in mechanism (C6).
- **S-14.** No prompt added.
- **Enterprise rigour.** Tests, deploy, quotas, ownership and security gates are untouched. What is removed is a model-run quality aid. Where it is the only design review of test oracles before code is where I would watch: the five warranted fixes in the Luna window were traceability and test-design classes (labels are the ledger's, judgement).
- **Loops unbounded.** `once` keeps every remaining loop unbounded.
- **Owner's wording "yes, do the planning review change".** I treated this as approval of the direction, not of my refinements. The per-item merge rejection and the staging are the owner's to confirm.
