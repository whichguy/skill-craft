1. Neither `once` nor `none` makes Luna xhigh reach 30 minutes. `none` with no extra authoring leaves 166 of 375 min. `once` as I would build it leaves about 328-361. [M arithmetic on measured minutes, plus stated assumptions]

3. The `once` described in the brief cannot be built as written for the per-item pair. An Improve child is bound to one action, and `finish_improve` can only replace that action's result.
   - A child bound to test-spec cannot repair the accepted step-plan result.
   - That result (steps, test_commands, criteria) is what the script enforces and later stages read.
   - 3 of 5 step-plan children across the runs changed those fields (Luna xhigh replan, Grok, 1.16.1 first step-plan).
   - Recommendation: collapse only the global trio (spec, test-strategy, plan) into one child at `plan`. That trio is 79% of Luna's review minutes and 78% of Grok's. Leave step-plan and test-spec children as they are.
   - Only if the owner insists on per-item collapse: bind the single child at step-plan and drop test-spec's. That saves 15.7 min on Luna and 3.2 on Grok.

4. The owner's "review missed it twice" premise is true for Luna xhigh only.
   - The xhigh revise was the missing module.
   - The 1.16.1 revise was a different defect. Test code contradicted its own helper (SYS-PORT-09), found at implement. No planning document could show it.

5. The W1 revise (165.9 min) was not detection-limited. The existing test-red gate already refuses a run where no test ran (measured with the real `judge`, section H). The cause is an engine gap, which the guard in section H closes.
   - test-red forbids product edits.

   - No stage or packet text says who creates a loadable placeholder.
   - The Luna host never submitted `done` at test-red. It submitted `revise` directly, so the gate never ran.
   - The cheapest guard is one script-run probe at test-author's `done` plus two sentences. It reuses `test_loop.verify` and `judge`.
   - This guard also cuts the cost of any revise, so it should land before or with the review change.

What happened [M]:
 - Luna test-author (nav-6b3d41c9) accepted done while saying "The focused rules command has not run: game.js is absent."
 - test-author's own done-when, #1 in `stage_spec`, is "each case in the test spec has a test the focused command runs". Nothing checks it: test-author has no `complete_runs`.
 - test-red (nav-7474e0b2) submitted revise: "The focused command was not run because it would fail during import... forbids product-code edits." The packet says "Do not edit production code" at test-red and `stage_spec` gives test-red edits=tests only.
 - No packet, reference or stage row mentions a seam, stub or placeholder. A grep of shiploop_prompts.py, references/*.md and SKILL.md for seam|loadable|stub|placeholder finds nothing relevant.
 - The redo fix was three lines: test-author created a placeholder root game.js.
 - The redo cost 165.9 min against 99.2 first time: step-plan 120.1 (Backchain 41.2, Improve 69.5), test-spec 25.2, baseline 5.1, test-author 12.2, test-red 3.3.

Detection already exists. I fed a real node:test missing-module output to the real judge (S/probe_judge.py):
 - With ids listed, red mode returns `ids-missing` (refused).
 - Without ids it returns `uncounted` (refused).
 - Node's summary is not recognised by `shiploop_test_counts`, so the `ids` list is what carries the verdict for node:test.
So the test-red gate would have refused. The host never called it.

Cheapest guard, as one increment (script-run check plus two sentences):
 1. Stage table, `shiploop_stage_spec.py`: add `"test-probe"` to COMPLETE_RUNS and give the test-author row `complete_runs=("test-probe",)`, like the test-red row.
 2. `shiploop_test_loop.py`:
    - `stage_commands` returns the focused commands for the probe stage.
    - `verify` gets a probe mode. It accepts any verdict where tests ran: `red` or passing. It refuses `no-tests`, `not-red`, `ids-missing`, `uncounted`.
    - `_explain` names the placeholder rule.
 3. `shiploop_navigator.py`: in the gate chain beside `_test_red_gate`, add `elif cursor_stage == PROBE_STAGE`. Same refusal shape, same MAX_REFUSED_RUNS.
 4. `shiploop_prompts.py`: one sentence in the test-author text and one in step-plan: tests that load something this item creates need the smallest loadable placeholder, created in test-author, with its path in the step plan's `paths`; or the load happens inside the test. Do not add language-specific text (S-8).
 This is the script-run check that carries test-author's own stated exit criterion (S-9), and the exit criterion check the owner's primary rule asks for.

Cost: one run of the focused commands per test-author done, seconds, already a path ShipLoop runs at test-red.
Saving if the guard had existed: roughly the redo, 165.9 min on Luna xhigh, less a few minutes in-stage [I]. Cost measured; saving is an estimate.

Rejected alternatives:
 - Static import analysis: language-specific (S-8).
 - Backchain-check consumers: the graph models implement steps only, so tests-before-code ordering is invisible to it.
 - Lint at test-author: needs a configured resolver, so it is not generic.
 - Text alone: Luna's reviews and host ignored text of this kind; 1.16.1 and Grok found a route by themselves, Luna xhigh did not.
 - A cheaper revise path (L17): complementary, a separate increment.

Not covered by this guard: the 1.16.1 SYS-PORT-09 class (a test that contradicts its helper looks RED at test-red).

J.1 Option and modes
 - Name: `--planning-review stage|once|none`, state key `planning_review`. Not `improve_cadence`.
   * That key was removed at 0.23.0 (b960891b), after the 2026-09-24 decisions (0.21.0 plan-and-end, then 0.22.0 keeps test-spec and the other planning reviews).
   * It is pinned refused by `test_saved_improve_cadence_key_is_refused_with_a_named_error` in test/shiploop-improve-schedule.test.py.
   * The earlier evidence from that session ("only contract-sentence reviews (step-plan, test-spec) found bugs") supports keeping the per-item pair as is.
 - Recorded in state.md like lint, delegation and backchain_passes; flag on `init` and `workspace start`; a recovery retry cannot change it (`_require_retry_planning_review`, copy of the backchain one); no mid-run `--set`; a saved run without the key is refused with FRESH_RUN_HINT by the generic missing-keys check. No shim, no migration.
 - Values:
   * `stage`: today. One Improve child per planning stage.
   * `once` (refined): spec and test-strategy results are accepted on the script's checks. The plan result starts the one child, scope = living spec, feature spec, test-strategy, feature plan, README, environment, SHIPLOOP.md. Its exit condition carries the done-when of spec, test-strategy and plan. step-plan and test-spec children are unchanged.
   * `none`: no child at spec, test-strategy, plan, step-plan, test-spec. The carry-forward, system-test-author and release-plan children are unchanged.

J.2 Why per-item `once` is not buildable as stated [M code]
 - `apply` parks one action. `finish_improve` computes `result = child["seed_result"] if final_result is None else final_result`, canonicalises it for `child["stage"]`, and `_apply_result` records that one action.
 - A child bound to test-spec cannot change the accepted step-plan result; the only route is `revise` (back to step-plan, at most 2 per item), which costs what the owner is trying to avoid.
 - Seed-versus-accepted comparison across the three runs: step-plan changed structured fields in 3 of 5 children; plan changed work_items in 2 of 3. All other children changed only summary or evidence_refs. The structured fields are the ones the script enforces (`_normalise_criteria`, `normalise_commands`).
 - Options if the owner still wants per-item collapse: drop test-spec's child (saves 15.7 / 3.2 min) or accept unrepaired step plans. I recommend neither.

J.5 Exit criteria without the review: which script-run check carries them
 Existing script-run checks [M] and what each stage's done-when leaves model-judged:
  - spec: knowledge.check (no R-ID dropped, credential screen); evidence refs exist. Model-judged: outcomes map to criteria; criteria verifiable; NFR assessed.
  - test-strategy: none specific. Model-judged: criterion to check and surface; harness choice; planned-not-passed.
  - plan: `_check_submitted_assumptions` (list complete); backchain-check structural (record-only); `_planning_sources_current` at prepare. Model-judged: each criterion owned; order and readiness.
  - step-plan: schema, `_normalise_criteria`, `normalise_commands`. Model-judged: whether the commands actually prove the criteria (Grok sp p1).
  - test-spec: knowledge.check requires the file at the close. Model-judged: cases and oracles.
 A small, generic addition that stays within S-8 and S-12 by extending `knowledge.check` at the closes: (a) each living-spec R-n appears in test-strategy.md and in the feature plan; (b) each step-plan criterion id appears in the item's test-spec; (c) local links and anchors under docs/shiploop resolve. It uses only engine-owned IDs. Ledger lever L11 reports 100 model-written check scripts (73.8 min) in the Luna window, which this replaces [ledger, not re-derived].
 Honest limit: none of the 9 warranted findings above would be caught by (a)-(c). Under `none`, the semantic part of the exit criteria becomes model-asserted with downstream script evidence only. Under `once` it is deferred to the plan close. This is the tension with the primary rule and with "enterprise rigour"; the carve-out must name it.

J.7 E2E selector prerequisite [M]
 The harness invokes `$skill-craft:shiploop <request>` (host-prompt.txt) and the host picks CLI flags. Nothing in test/shiploop_e2e/run.py or skills/shiploop-e2e-audit/harness passes a run option; `--backchain-passes` was never selected by a harness run. To compare `stage`, `once` and `none` on the same case the harness needs a channel. Cheapest without a new engine surface: a harness-appended sentence on the host prompt, with the harness verifying the recorded key in state.md (export fact) and failing setup on mismatch. An environment variable read by `init` would be a new surface (S-13); none exists today.

J.8 Recommendation on default [for the owner to decide]
 - Evidence cannot separate `once` from `none` on quality (no counterfactual).
 - The owner's ceiling separates them: only `none` on Grok can meet it. If the ceiling governs the default, the default is `none`, with a real, unmeasured rigour cost. If rigour governs, `once` is defensible but then planning stays over 30 min on both models.
 - I would build all three with the owner's stated default `once`, ship the red-seam guard first, and run one measured Grok `none` and one `once` comparison before claiming either meets the ceiling.
