Readable seven-phase workflow

The seven labels are an operator map. The script stores a more granular phase/stage cursor and issues a fresh action ID at each boundary; the phases are not extra state records or product runtime states.

P1 — Frame and baseline

preflight and approach select a committed baseline, preserve unrelated work, identify usable checks, and establish a bounded delivery direction.

P2 — Survey, research, behavior

Survey, research, and behavior candidates are reviewed iteratively against the current environment, then converge through planning, apply, verification, audit, and fresh finalization.

P3 — Specification and sequence

The specification/lifecycle are frozen only after the same convergence discipline; sequence validates the dependency DAG and authorized preparation placement.

P4 — Ready-step planning and execution

The scheduler selects a dependency-ready step. A nested step-plan loop produces a fresh, evidence-bound plan before implementation begins.

P5 — Improve, learn, merge

Review findings, mapped test evidence, learning commits, fresh verification, knowledge carry-forward, and a broader-plan decision precede local merge.

P6 — Whole-product quality

Coverage and quality examine lifecycle acceptance across steps. A finding returns work to a corrective pending DAG step rather than bypassing the loop.

P7 — Authorized handoff

Publish is conditional and separately authorized. Handoff records facts and limitations; done is allowed only when terminal evidence is complete.

Implementation and verification sequence

  1. Persist the real control plane in Markdown. The command host maintains the active action, state cursor, history, results, checks, receipts, and handoff under a run directory. Completion replay is checked against an action-bound fingerprint instead of treating chat history as authority.
  2. Converge planning candidates before source edits. Research, behavior, specification, and generic substantive objectives use candidate-bound review/apply/check/audit cycles. The embedded continuation policy needs two verified, distinct trivial audit passes and no open findings before it is merely ready for a fresh final check.
  3. Make step readiness and completion inspectable. Versioned Ready/Done/test/documentation criteria tie a selected step’s produces to named evidence. Current-step knowledge or source changes invalidate stale evidence rather than silently preserving a “ready” flag.
  4. Keep implementation and review boundaries separate. The step-plan loop is audit-only; the implementation stage owns scoped product edits and meaningful checks. Improve cycles record findings, checks, learning commits, and a broader-plan decision before merge.
  5. Require whole-product evidence before terminal handoff. Outer coverage and quality use lifecycle acceptance, concrete lint and test checks, and corrective replanning if evidence is incomplete or changes invalidate prior results.
  6. Derive the HTML report; never promote it to authority. At a terminal transaction, the delivery layer renders a deterministic offline report from selected Markdown evidence. It rejects incomplete evidence for a successful terminal cursor and stores report metadata only as a derived binding.

Honest limits and non-claims

What the implementation can establish

  • Durable, action-bound state and evidence transitions in the checked-in harness.
  • Refusal of missing, stale, malformed, changed, or incomplete evidence at the gates implemented by the scripts.
  • A deterministic offline run report derived from bounded Markdown records.
  • Focused verification results recorded above, subject to their stated scope.

What this page does not establish

  • That any downstream application was deployed or published during this implementation verification.
  • That a host selected meaningful tests, performed a complete semantic review, or made truthful external assertions.
  • That every possible behavior, integration, or host was covered by these tests.
  • That the cold-operator trial covers every host or proves a physically reset context at each action boundary.
  • That a generated per-run report is authoritative state; the run Markdown remains authoritative.

The practical boundary is deliberate: ShipLoop can enforce evidence shape, freshness, and transition rules, but it cannot infer product correctness or external reality from a host’s prose. Failures, pauses, exhausted budgets, missing dependencies, and unverified effects remain unfinished rather than alternative success paths.

The original full-message paging gap was resolved in f47dcfa with identity-bound, character-paged reads and coverage checks. That increment also added explicit merge-intent recovery and restoration of recoverable legacy intent. Genuinely absent prompts still cannot be reconstructed, and ambiguous Git reconciliation may require operator direction. See the later completion record; these limits never authorize bypassing evidence or authority.
