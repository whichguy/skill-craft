## Sequence model

LEVELS in v1 (each has a count, a duration and, where measured, a context). Run: one run output directory. Visit (the column): one accepted action, from state.md history joined to timeline.json by action id. Inner pass: an Improve review pass or a Backchain loop pass, shown as a count (Improve passes above the column; loops in their existing cards). Later, not in this plan: round (a work item's pass, ended by revise or replan) and chain attempt.

COUNT
- Visits: history length [M*, four named runs; M, r1 for 22 to 26 dirs]. Work visits = visits minus `skipped`.
- Improve passes: improve/<action>/terminal.json progress.action_number (durable). [M*] Luna 41 across 9 children, hello-1190-2 19 across 11. The exporter's review-note count (volatile worktree) is retired.
- Loop passes: existing loop cards, unchanged.
DURATION
- Visit: accept minus the previous accept (the first from timeline.started); whole-second stamps, so good to about 1 s per boundary. A visit `skipped` (no packet issued) is drawn hatched and consecutive ones collapse into one 'xN' column. A 1 s work visit stays work and is drawn at a 2 px minimum. Elapsed is accept to accept: it includes any host-kill or resume gap, so the card says 'Elapsed (accept to accept)'.
- Improve child span: mtime of improve/<action>-bind.md to mtime of improve/<action>/receipt.md [M*: Luna 360.3 min over 9 children, hello-1190-2 3.73 over 11].
CONTEXT (v1 is run-level only; the per-visit strip is deferred until you confirm what 'meta context' means)
- Measure: per call = input_tokens + cache_read_input_tokens + cache_creation_input_tokens (the harness's context_tokens); run peak = tokens.input_peak; window = result.modelUsage[model].contextWindow, which the harness does not record today [M*: no contextWindow in test/shiploop_e2e/*.py] and R11 adds as window_tokens (Claude 1,000,000). [M*] hello-1190-2: peak 271,220 of 1,000,000 under the current harness. Calls = unique assistant message ids [M*: 149 where turns says 254; hello-1190 113 versus 194; hello-1161 84 versus 143]; label it 'main thread' because chain workers and Improve agents report elsewhere [M, r2].
- The page's packetBytes is the packet FILE size, not text printed to the model (Sonnet read back 4 of 47 packet files [M, r2]); the label changes and it is never called context.
PER HOST (measured or not)
- Claude: count, duration, Improve, run-level calls, peak and window measured. Compactions, refusals, glue and tool counts are not measured (CLAUDE_BLIND lists shiploop_failures, model_glue and stage_tool_calls; no compact_boundary event exists in any recorded stream [M, r2]).
- Codex: count, duration, Improve measured. Refusals and glue are measured (Luna 13 and, under the current harness, 20; the stored 21 is stale [M*]). Calls, context and compactions exist only in the per-run CODEX_HOME rollouts (Luna 2,919 calls, 34 compactions in the main thread, 93 to 99% of the window [M, r2]), not in events.jsonl, so v1 shows 'not measured' with the harness's own reason (stage_turns: no per-call usage events). Cost unavailable.
- Grok: per-call usage and auto_compact_completed per harness code; [I] unverified, no Grok run on disk.
NEVER ZERO
- Every measure is a number, or is absent with a reason in runs.unmeasured[name]. The exporter takes the reasons from metrics['unmeasured'] and refuses a metrics.json without that key (the message says to regrade a finished run). A sum over an unmeasured part is itself unmeasured. The page prints 'not measured' with the reason as caption; there is no zero-height bar. A fixed MEASURES list (refusals, glue, calls, contextPeak) is tested to be a number or have a reason.
- A paused run keeps status paused (RUN_STATUS maps paused to active today [M*]); a stopped run's open stage gets no row.

## The guided flow

ONE RUN, FOUR STEPS, built by reorganising the current page (not a rewrite). Header: run selector (renderFlow already fills it), compare select (existing cmpsel and table compare, kept), a stepper of four pills with live counts ('3 Findings, 5 ticked'), and on a phone a sticky bar 'N ticked, Your plan'. One step shows at a time; Back and Next end each step; the current step is kept in localStorage (try/catch). No hash routing (it may not survive the artifact wrapper [I]). A 3 to 6 line arc written by Claude (reviews.summary) heads step 1.

STEP 1 WHAT HAPPENED (you read, tap a column). The picture (inline SVG, inner scroller, 16 px minimum column, so Luna's 39 columns are about 624 px and hello's 54 about 864 px; a collapsed table is the phone-readable form and the accessible alternative): a column per visit in order; height = square root of minutes on the run's own scale (maximum printed), 2 px minimum; colour = outcome (done, revise, replan, blocked) plus a text mark on non-done; `skipped` visits hatched and consecutive ones collapsed; Improve passes as a number above a column. Below the axis the existing phase chevrons of renderFlow (expected, observed, Backchain rows) with a small per-phase finding count. Six cards (two by three on a phone): Visits (54: 47 work, 7 skipped), Elapsed (accept to accept), Improve (passes, minutes, share of elapsed), Backchain loops (as today), Context (peak as % of window, 'main thread', or not measured with the reason), Refusals (a number or not measured with the reason). Tap a column for a detail card: stage, outcome, minutes and share, packet and result file sizes, Improve passes and minutes, and the findings marked at that phase. Below: the existing run detail (planning documents, harness verdict chips, failing commands when measured) and the existing Backchain loop cards unchanged. Until the picture increment (R14) lands, step 1 holds the phase chevrons, the existing stage table and the loop cards. Comparison stays the existing second-run select and table; no overlay and no same-scale toggle in this plan (journal C8).

STEP 2 EXPECTED VERSUS SEEN (you scan, tap a row). One row per criterion (11, grouped Principles and Backchain; this is the old 'contract' and 'expectations' sections): chip holds, bent, broken or not examined, S-clause chips, 'N open findings' that jumps to step 3 filtered to that expectation, and 'revised xN' that expands the revision history inline (the old 'how expectations changed' section). The chip is derived, not stored: the worst `effect` among the run's open findings for that criterion; else holds if the run's review has a one-line basis for it; else not examined. A chip therefore cannot disagree with its findings. Nothing is edited here: changing an expectation is an option in step 3.

STEP 3 FINDINGS AND OPTIONS (you tick any mix). Filter chips: open for this run (default), all for this run, other runs, general. A finding card: title; chips (expectation, S-clauses, kind, effect); what happened (expected, saw, evidence); advice (Claude's recommendation); then its options. Each option renders once, under its first finding (later findings show a reference chip), with a 44 px checkbox, kind (fix ShipLoop, fix harness, change expectation, gather evidence, accept as known limit), status (open, planned, built; done is hidden under 'Already done'), effort (S, M, L), cost note and a recommended flag; the instruction opens in a details block. 'Tick recommended' ticks the recommended option of each open finding. A finding with no option shows 'no option yet' and a checkbox 'ask Claude to propose options'. The one capture path is the existing 'Add an observation' form.

STEP 4 YOUR PLAN (you copy one prompt). Counts by kind, the ticked options grouped by kind with untick controls, cost-gated options flagged, 'wait for my go-ahead' (default) or 'then execute', a notes box, and the aggregate prompt with Copy.

WHY IT IS ONE STORY: each step consumes the previous step's output (a finding marks a phase; an expectation row counts its findings; the plan lists only ticked options and their findings), each option renders once, one selection store (per run, localStorage), one capture path, and no section renders the same data twice. Steps 2 to 4 are always about the primary run.

WHAT BECOMES OF THE ELEVEN SECTIONS: contract and expectations -> step 2 rows; expected versus observed (chevrons) -> step 1 phase band; run detail -> step 1; Backchain -> step 1 loop cards (unchanged, with their hand-verdict selects); observations -> step 3 findings; actions -> step 3 options; how expectations changed -> per-row disclosure in step 2; prompt -> step 4. REMOVED: iterations and expectations (the Backchain comparison tracker I0 to I6; preserved in the committed snapshot; its planned items already live in action a01), the unexpected section and its prompt text (the 'Add an observation' form is the one capture path), the UML process diagram (renderSequence, SEQ_ACTORS), the include toggles and the synth or concatenate mode, the global expectation-status editor, the inline expectation editor, and the Backchain tally sentence in the prompt.

## The aggregate prompt

ONE BUILDER, ONE PLACE: buildPrompt(state) is a pure function in the template's logic block (the old renderPrompt string building, extracted so node can test it; one implementation). The skill does not rebuild the text and has no apply mode: you paste the prompt.

STRUCTURE (expectation changes first, so later work is judged against the new wording)
1. Head: 'Repair work from the Run Review of <run name> (<release>; <host> <model>; <date>; <status>). In the skill-craft repository. Page: <url>. Run evidence: <output dir>. Review file: test/shiploop_e2e/evidence/<runKey>.review.json.' Then 'You ticked N options (kind counts). Plan them as one plan: merge overlap, resolve conflicts, order by dependency, split into the smallest verifiable increments, mark what can run in parallel.' Then the after line: 'Present the plan and wait for my go-ahead.' (default) or 'Then execute it.' Then one 'Run facts' line with measured values only (for example '54 visits, 15.2 min elapsed, 19 Improve passes; refusals not measured on this host').
2. CHANGE AN EXPECTATION, per option: 'id key title: target page or spec. Now: <to>. Was: <current text>. Why: <reason>.' plus the kind note: page means edit skills/shiploop-run-review/defaults/expectations.json (text, clauses, a revs entry naming the option) and journal it; spec means amend test/shiploop_e2e/SPEC.md first, in its own commit, stating why.
3. FIX SHIPLOOP, then FIX THE HARNESS (its own commit), then GATHER EVIDENCE (read-only unless the instruction says run), then ACCEPT AS KNOWN LIMIT (record in test/shiploop_e2e/LEARNINGS.md with evidence, no code change). Each option: '<n>. <id> <title> [<status>, effort <S|M|L>]. Resolves: <finding ids>. Expectation: <key title> (<chip in this run>); clauses <S-n>.' then 'Do: <instruction>' and, only when the option has a cost, 'Ask me before starting: costs <cost>.'
4. INVESTIGATE (only for ticked findings with no option): ids and titles, 'read the evidence, propose options of the five kinds, change no code'.
5. EVIDENCE, each finding once and only those linked to ticked options: '- id [expectation, status] title. Expected: ... Saw: ... (evidence: <string>; run: <key> at <run dir>)'. The pointer to memory stays because AGENTS.md carries layout, release and test-registration rules but not KISS, journaling or read-the-last-three-commits; those sit in your memory index, which loads into every session [M*].
7. Notes, then REPORT BACK: for each option say done, not done or blocked with evidence (test name, commit) and whether the evidence changes the engine or our expectation; for each landed option set its status to done in the review file citing the commit, then run /skill-craft:shiploop-run-review publish.
