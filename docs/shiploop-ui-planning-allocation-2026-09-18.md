## Decision and scope

Determine whether ShipLoop elicits the UI decisions needed before architecture
and environment preparation, then preserves and revalidates them during feature
work. Exercise both creation and incremental work. Change canonical guidance
only for a demonstrated gap or misleading allocation; retain the existing
Markdown records, graph, result fields and automatic Improve handoffs.

| Owner | Decisions and observable output |
| --- | --- |
| Discovery, research and specification | Inspect prior design, code and current target; define or augment component, interaction/state and skin premises; apply available design guidance; retain consequential unknowns. |
| Initial architecture and global plan | Connect UI promises to actual runtime/asset/storage/transport/lifecycle capabilities, owners, preparation prerequisites and checks before their first consumers. Preserve adequate existing choices. |
| Environment preparation | Perform only the assigned authorized setup or probe; retain current target/artifact identity and observed readiness. A planned operation is not a readiness receipt. |
| Per-feature planning and execution | Read the applicable premise sections, specify the delta and concrete UI/state/failure tests, revalidate affected readiness, and preserve unrelated journeys and identity. |
| Correction and carry-forward | Reopen an affected shared premise when new evidence contradicts it; retain the original requirement, impacted consumers, missing producer and correction route. Keep independent ready work separate. |
| Existing Improve handoff | Review decisions and proposed checks before implementation; review actual outcomes afterward, including the source and evidence needed after context loss. |

## Preregistered experiments

Inputs and expectations are hashed before fresh producers start. Producers see
only their product, request and selected package/guidance. Independent assessment
uses semantic obligations, resolved references, assigned work and observed state;
it does not score keyword frequency or prescribe a plan template.

1. **Creation.** An archive export UI starts without UI code. The controlled
   target accepts same-origin static assets and existing request/response APIs;
   it disallows inline/external assets, a deployed server and persistent sockets.
   Run real intake, discovery, research, spec, test strategy and global planning,
   including actual selected Improve cycles and parent imports. Stop before
   preparation. Expect concrete UI premises, service/client authority, truthful
   async outcomes, deployment-compatible choices, preparation/check dependencies
   and honest unexecuted target validation.
2. **Augmentation.** Existing Field Notes components and branding must survive
   reload-recoverable account-scoped drafts and remote export status. Historical
   notes say storage was available; the current controlled target observation
   says it is unavailable and no draft API exists. Use real early producers and
   reviews. Expect actual baseline inspection/checks, preserved requirements,
   detection of the capability contradiction and a scoped readiness gap. An
   honest blocked stage is a useful result, not a failed experiment apparatus.
3. **Cold dependent and independent steps.** Deliberately synthetic predecessor
   records place fresh producers at step planning. One item depends on draft
   persistence; another needs only existing export APIs. Expect current sources
   and UI premises to be reopened, stale readiness to remain visible, and only
   the dependent item to stop. These cases cannot prove earlier planning quality.
4. **Browser capability control.** Serve external script/style under same-origin
   CSP. Check rejection of an inline script, persistence across ordinary-origin
   reload, and continued rendering but rejected storage in a sandboxed frame.
   This is a real local Chromium observation of a controlled host boundary, not
   a remote deployment or a model-selected architecture.

## Evidence and stopping rules

Retain requests, baseline source hashes, exact rendered packets, producer notes,
raw callback responses, current Markdown state and terminal Improve packets.
Distinguish real reviews from synthetic navigation. Mechanical evidence checks
can establish identities and transitions, not the truth of semantic judgments.
Retain original failures and candidate retries separately; do not rewrite a
failed output into a pass after fixing it.

For a demonstrated gap, first write the smallest allocation/routing correction
plan, then amend shared guidance and only the stage-local references that need
it. Re-run the affected case with a fresh producer against frozen candidate
bytes. Add focused recovery/routing regression coverage where meaningful,
regenerate the plugin views, and run the repository's required hermetic suite.
Run actual Improve over the scoped final candidate through two consecutive
qualifying reviews. Report remaining product, platform and host limits.

## Findings and implemented correction

Both initial cases completed actual intake, discovery, research, specification,
test strategy and global planning, with six real Improve imports each. Both
stopped at the assigned, unexecuted `prepare` action. Independent assessment
accepted their bounded semantic criteria: the new case supplies concrete
components, state/interaction and skin decisions plus the selected design-card
identity; the existing case preserves the Field Notes baseline and retains the
contradiction between historical storage availability and the current probe.
Their target, account, carrier, test and documentation dependencies remain
explicit future work. Planning acceptance is not environment readiness.

The greenfield global review corrected an unnecessary dependency: local static
and test bootstrap follows durable requirements authority and can precede the
integration contract and live target access. Its accepted schedule is requirements
authority → local bootstrap → integration contract → behavior → UI/local checks
→ target/consumer validation. The prior producer note still contains the obsolete
ordering. The final state and accepted result carry the correction, but recovery
must not treat that old note as the current plan.

This produced the final small guidance change: carry a reviewed replacement
locator and its precedence through the existing handoff; change item contexts
only where the stage owns them; preserve immutable evidence as historical; and
retain a prohibited durable update as pending. A fresh cold supersession control
[passed all five preregistered criteria](../test/experiments/shiploop_ui_allocation/evidence/candidate-supersession/oracle/assessment.md) with the original note still present. Its
real W2 producer followed the replacement, kept W3 external integration separate
and nonblocking, and retained the pending durable correction. It stopped at an
unbound, unrun Improve handoff; its eight predecessor records are synthetic. The missing
supplier rule also explicitly forbids inventing the unresolved supplier contract.

The cold dependent producer reopened the current storage contradiction and
retained UI premises, but its prerequisite lacked an explicit preparation owner
and its plan absorbed export notification work outside selected draft item W1.
The independent producer added export creation/download behavior to status work;
the added POST introduced a collection-selection prerequisite. Independent
assessment found this scope ambiguous: the product request emphasizes change
notifications, but the selected item context also names POST/reconciliation APIs.
That is a requirement-reconciliation question, not a proved scope failure. If
creation remains in scope, its missing collection-ID supplier still needs an owner.
Both original producer callbacks returned
`done` and parked their parent actions for Improve; that state alone does not
establish implementation readiness.

The implemented change is a shared planning-owner subsection plus direct
discovery/global-plan/prepare/step-plan reference routing. Keep initial shared
choices distinct from the selected feature delta; distinguish available
capability from requested behavior; require supplier/ownership and a real blocked
or correction disposition when an external prerequisite cannot be supplied by
the selected item. Review those boundaries in the existing Improve handoff.
The graph and result schemas are unchanged. The paired cold producers ran
against frozen candidate bytes before the additional controls below.

Both candidate cold producers returned `blocked`. Independent assessment accepted
the dependent plan's current evidence,
supplier/ownership route and preserved requirement. For the other case, the
assessment accepted blocking its full seeded scope but identified a fixture
limitation: POST/create and operation/job references, plus missing API payload
contracts, make it unsuitable as a ready read-only status control.

The candidate dependent case subsequently completed an actual three-cycle
Improve run: one material correction distinguished observed note-save code from
the documented export contract, followed by two qualifying reviews. Its parent
imported the child once and remained **blocked at step-plan**, with no active
child. This is the decisive observed transition for the missing draft supplier;
the independent paired candidate remains parked with its review unrun.

Three additional controls were therefore declared before their fresh producers:
an authorized preparation item with its own build/harness output absent; a
headless job-event item; and a clarified read-only status item with a complete
controlled schema and separately blocked draft work. These are diagnostic
controls, not another paired comparison or retroactive passes for the originals.

The clarified status case exposed another consequential missing input during
Improve: the local account selector does not establish the account authorized by
the host-scoped endpoint. A valid response could therefore be attributed to the
wrong account despite correct stale-response cancellation. The plan must retain
that authorization-context dependency. A separate, fourth diagnostic control
supplies an explicit controlled request/response account contract to test ready
status work while draft persistence remains separately blocked. It passed all
five preregistered criteria and a four-cycle actual Improve run (two material
corrections, then two qualifying reviews). One parent import advanced to the
unexecuted `test-spec` action. Account replacement clears the active snapshot
and held revision; equal revision is a heartbeat only while held. The plan adds
no per-account cache or invented API size limit. It does not retroactively repair
the earlier fixture or establish a live identity bridge.

The prior status control completed 12 review cycles and one parent import,
remaining blocked at step planning. This disproves its original ready hypothesis.
The missing host identity bridge is a real dependency. Review also accumulated
response-normalizer constraints; the separate successful control shows that
client-owned exact integer comparison and aggregate counts can avoid invented
API bounds or uniqueness requirements. This review churn is a limitation, not
evidence that more review cycles necessarily produce a better plan. Reviewers
must distinguish actual contract gaps from optional implementation choices and
future checks from missing present-day implementation proof.

The preparation and headless controls completed their actual producer callbacks

## Resulting implementation plan

1. Retain shared UI decisions in the existing requirements/design authority;
   discovery and global planning allocate runtime capabilities, owners, earliest
   consumers and observable checks. Augment existing decisions when contradicted.
2. Route preparation and each selected feature to that authority. Keep local
   preparation outputs inside their owner; record outside prerequisites without
   inventing a supplier protocol or absorbing unrelated behavior.
3. Use the existing automatic Improve handoff at the same planning level. Carry
   corrected decisions and replacement precedence into recovery packets.
4. Keep this prompt-first: no new scheduler, graph, result schema or transport.
   Add routing/recovery regressions, retain diagnostic evidence and synchronize
   generated plugin packages. Version the ShipLoop skill as `0.15.1`.

All four steps are implemented. Toolkit selection remains conditional on prior
code and actual deployment capabilities; Bootstrap, Material or native controls
are examples, not mandated defaults. Rich UI planning still includes components,
interaction/state, visual identity, accessible async feedback and restrained
motion. Shared message/lifecycle/state concerns apply to headless systems too;
only human-facing surfaces receive UI-specific obligations.

## Platform grounding

The capability control is consistent with MDN's documented
[sandbox origin restrictions](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe):
without `allow-same-origin`, a sandbox has a special origin that can prevent
storage access. The result does not justify weakening that policy.

Lifecycle is a shared architecture concern with platform-specific checks.
Chrome documents that [frozen pages suspend timers and fetch callbacks](https://developer.chrome.com/docs/web-platform/page-lifecycle-api).
Apple similarly requires applications to [adjust work and resources across foreground/background transitions](https://developer.apple.com/documentation/uikit/managing-your-app-s-life-cycle).
These sources support planning suspension, durable state and foreground
reconciliation; they do not prove native behavior in this web-only experiment.
