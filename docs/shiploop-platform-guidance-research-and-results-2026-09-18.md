The local browser/interpreter checks execute real tools; Apps Script and Salesforce substitutes establish only the specific local model's behavior. ### Concrete observations

**UI:** An older request completed after a newer one. The reference retained the newer rendered result; the stale variant overwrote it. Both passed an ordinary one-response check and a deliberately weak structural check. Separately, a clickable `div` passed pointer interaction but failed the named-button/Tab oracle. These results justify stronger behavioral checks, not a mandate for React, Radix or a particular test library.

**Apps Script contract model:** Two increments under the reference's shared-state protocol ended at value **2** with two commits. The no-lock variant recorded two commits but ended at **1**. A cache-only variant lost the durable receipt on restart; a blanket-lock variant made a pure read fail when its unnecessary lock was unavailable. A 2×2 grid write used **one synthetic service crossing instead of four**, while another attempted batching optimization changed a required notification's content. This measures the model's call counts and behavior, not Google service speed. The final RPC test uses explicit release barriers; the earlier timed run remains recorded separately.

**Salesforce:** The access-intent scanner is deliberately not a security oracle. Current Salesforce documentation changes the default security behavior at API 67.0, so absence of explicit user-mode text must not be reported as proof of a vulnerability. The card requires checking the applicable API version, access context and real permission behavior. Collection-oriented code shape is useful review evidence, but only actual Apex execution can establish transaction budgets. [Salesforce secure Apex guidance](https://developer.salesforce.com/docs/platform/lwc/guide/apex-security.html), [Salesforce query access modes](https://developer.salesforce.com/docs/platform/salesforce-soql-sosl/guide/sforce-api-calls-soql-select-with.html).

**Ruff:** The original expression returned `7` for `[7, 9]` and raised `IndexError` for `[]`. Applying the selected unsafe fix retained the ordinary output but changed the empty-input error to `StopIteration`. A manual exception adaptation restored those list observations, yet both rewritten versions consumed only the first iterator item while the original consumed the iterator fully. Matching the happy path and one error is therefore insufficient to establish compatibility. [Ruff fix-safety documentation](https://docs.astral.sh/ruff/linter/#fix-safety).

**Python and Bash:** A failed Python child retained exit **17** and its causal stderr while its temporary workspace was removed. The cleanup-masking variant lost that cause. All three state implementations returned **7** for one ordinary credit, but separate isolation/rejected-transition checks exposed shared state and partial commits. In Bash, the reference pipeline retained exit **42**, reported the handled failure and cleaned up; the no-cleanup variant matched status/output while leaking its workspace. With all of `set -euo pipefail` verified enabled, a function invoked as an `if` condition continued after `false` and returned success. Explicit control-flow assertions are necessary even with useful strict-mode options.

Independent review identified missing source identities in initial domain receipts. The parent reran Apps Script, Salesforce, Python, Bash and the selected ShellCheck cases with before/after SHA-256 manifests and captured stdout, stderr and exit codes; all matched expectations with unchanged source. Original receipts remain intact. UI and Ruff receipts already bind their fixture/runner identities. Documentation should retain the consequential decision, version and check locator; put evolving platform details behind a maintained source link rather than duplicate a manual.

## Additional official grounding

- [Apps Script best practices](https://developers.google.com/apps-script/guides/support/best-practices) support minimizing service crossings and batching compatible work. The same page notes library startup overhead in chatty HTML Service use: library reuse is not automatically a latency win. Check [current quotas](https://developers.google.com/apps-script/guides/services/quotas) for the relevant execution context instead of hard-coding a remembered universal limit.
- [Playwright best practices](https://playwright.dev/docs/best-practices) support isolated tests and user-visible assertions. They do not turn a role query into a full accessibility audit.
- [pytest fixture documentation](https://docs.pytest.org/en/stable/how-to/fixtures.html#safe-teardowns) describes setup/teardown failure boundaries; [Hypothesis stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html) provides a concrete approach when sequences, not isolated examples, carry the risk.
- [Python cleanup stacks](https://docs.python.org/3/library/contextlib.html#contextlib.ExitStack) and [async cancellation guidance](https://docs.python.org/3/library/asyncio-task.html#task-cancellation) ground the resource/cancellation cues. Not every documented case was separately exercised here.

## Incorporation and remaining experiment boundary

The new card document is an experimental reference. The core candidate gains a selector pointer; installed skills, generated plugin views and production runtime remain unchanged. Incorporation means retaining grounded questions and runnable counterexamples, while keeping the model-effectiveness decision at **pilot**.

For the next matched guidance trial, freeze current core versus current core plus the relevant platform card. Use these calibrated cases as preparation examples and construct fresh holdouts so workers do not see the reference solutions. Keep planning and implementation contexts separate and retain the original protocol's access isolation, equal budgets, allocation manifest and independent grading. Do not count these researcher-authored reference implementations as model successes or mix their costs into an LLM token-efficiency claim.

Before a hosted-platform claim, the Apps Script track needs a disposable project with identified execution role/scopes, real RPC and state/service probes, then deployed-consumer evidence. The Salesforce track needs a disposable org with intentional low-privilege permission fixtures, actual Apex allow/deny and bulk-limit assertions, then LWC/browser observations. These boundaries remain explicitly unrun. Local evidence is sufficient to design and challenge the proposed guidance; it is insufficient to certify those hosted behaviors.
