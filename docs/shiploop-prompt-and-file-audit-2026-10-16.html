Design decisions, learnings and validation plan

Should shared rules depend on run mode?

Yes · information gain 0.93. The generated reference is a recovery input, so it must agree with the selected schedule. Reuse the existing stage table; the navigator remains authoritative.

Should a chain receive one review or one per node?

Keep one aggregate review · information gain 0.85. The action owns the whole delegated chain. Correct its wording and preserve the current chain boundary; inline actions retain their per-step reviews.

Does “no model launch” apply to every shipped executable?

No · information gain 0.70. Scope the statement to skill/navigator invocation and name the optional outer driver. The source supports that distinction; no execution change is needed.

Learnings: packet text is only one part of context; short Improve wrappers move work into a handoff; same-context execution and fresh recovery need different loading decisions; whole-file reads were chosen to avoid real omissions; similar file names do not establish duplicate authority.

Validation order: fix the three wording defects with narrow mode/route assertions, then pilot one context change at a time. Existing relevant suites include shiploop-reference, shiploop-navigator-contract, shiploop-step-packets, shiploop-chain, shiploop-packet-completeness and shiploop-package-integrity. Run a focused suite as python3 -B test/<name>.test.py with SHIPLOOP_PROGRESS=off, then the documented quick tier for affected consumers. These additional suites were not run for this analysis-only report.

Before adopting compression, compare a populated one-item run, a multi-step delegated chain and a context-loss/recovery case. Record task correctness, missed requirements, refused callbacks, rework, actual reads/tokens and elapsed time. Keep scope and authorization identical. Require no loss of obligations before considering size or speed; do not replace evidence-based exits with new caps. Broad prompt migration also needs the repository’s release/E2E checks.
