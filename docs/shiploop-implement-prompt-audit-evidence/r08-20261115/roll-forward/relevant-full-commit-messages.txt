    fix(shiploop): the test-stage judge no longer trusts exit 0 over a reporter-recognised failure
    
    R08/T37: a wrapper or build step that swallows a runner's nonzero exit while the
    output still shows a failed test (count()'s failed tally, or a listed ID's own
    outcome) was being judged "passed". judge() now checks both signals and reports
    "failed" instead, for both check and focused/regression commands.
    
    A quality review of the fix (7 independent angles + verification) found that
    _explain() had no branch for this new failed-at-exit-0 case and fell through to
    the bare "exit 0" fallback -- read as success and dropping the runner's tally.
    Added a scoped branch for it without touching the pre-existing "exit N" wording
    pinned by other tests for genuinely nonzero exits.
    
    The same review also surfaced two related issues left open as follow-ups,
    not fixed here to keep this change small:
    - _judge_base() (~line 1699) has the identical masking bug in its own
      no-ids code path, untouched by this diff.
    - Making count()/outcomes() authoritative for status (rather than merely
      informational) means a wrapper with internal retry-to-pass (flaky test
      retried and ultimately passing) could now be misjudged "failed", since
      _jest()/_vitest() sum "failed" across every summary block and
      outcomes()'s fail-wins rule can't distinguish a retry from a double print
      of one real failure.
    
    Reproduces docs/shiploop-implement-prompt-audit-evidence/probe-judge-zero-exit.py.
    Full shiploop-test-loop suite: 172/172 passed (165 existing + 7 new).

    fix(shiploop): _judge_base's no-ids path has the same exit-zero masking bug judge() had
    
    Follow-up to 5fb29784. The quality review of that fix found the identical bug in
    _judge_base() (the base-run judge): a focused command with no ids whose wrapper
    swallows a nonzero exit, despite the output showing a real failure, was reported
    "passes-on-base" using only `code == 0` -- the same tally it already computed
    (`counts.count`) and stores in verdict["counts"] was never consulted.
    
    A masked failure here is the inverse harm from judge()'s: a test that genuinely
    fails on the base (good -- it discriminates the change) gets told by
    _explain_base that it "exited 0 on the item's base: no test failed without this
    item's change", which is backwards. The fix mirrors judge()'s masked_failure
    check using the tally alone (no ids exist on this path, so there is no per-ID
    outcome to consult). No _explain_base change is needed: the fix only shifts
    more cases into the already-correct, already-unexplained "red" (accepted)
    status; it does not create a new reachable status the way the _explain() gap
    did for judge().
    
    Verified the new tests fail against the pre-fix code and pass with it. Full
    shiploop-test-loop suite: 175/175 passed.
    
    The other review finding left open (jest/vitest's failed-count summed across
    every output block, and outcomes()'s fail-wins rule, both now authoritative via
    masked_failure and able to misjudge a wrapper that retries a flaky test to a
    genuine pass) still needs a change to shared count()/outcomes() semantics used
    by many other callers -- a bigger, separate change, not addressed here.
